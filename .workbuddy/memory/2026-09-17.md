### 核对后推翻/修正的既有结论

1. **「页面内裸 fetch 会被平台自动补签名」是未验证的生死假设**（docs/10 §2.2 自己标注需实测但没给方法）。原生 fetch 无法被自动加头，只有平台 monkey-patch 全局 fetch/XHR 才成立。已在文档 §2.3 给出 6 步判定 spike（hook fetch/XHR 记录头 → 手动搜索 → 页面内裸 fetch 同接口 → 失败则枚举平台签名入口如 `_webmsxyw` → 对 RAP 白名单路径重复）。三种结论对应三条实现路径。
2. **「131 个 API 端点零改动」不成立**。至少 4 处必须改：
   - `api/login_sessions.py:224`（`not session.qr_id` 守卫）和 `:229`（`not session.code` 守卫）——浏览器方案下 qr_id/code 不存在。模型层不用改（`models/login_session.py:23-24` 均 nullable）。
   - 前端**可以不改**：`login_sessions.py:174` 的 `qr_image_data_url` 靠「对浏览器登录页二维码截图」保住契约，`qr-login-panel.tsx:41/63/66` 无需改动。
   - adapter 构造参数（见下方架构建议，可压到零）。
3. **手机验证码登录建议不迁**：web 端手机号登录必经滑块验证，headless 无解。扫码为唯一主路径。
4. **架构建议改为独立「浏览器网关」进程**，而非 docs/12 的 `services/browser_pool.py` 内嵌。理由：多 worker 下浏览器状态分裂、崩溃隔离、Docker 拆分、可复用给 XhsSkills。关键收益：网关按 cookies/account_id 复用 context，`XhsPcApiAdapter(cookies)` 构造签名可保持不变。
5. **adapter 边界实际 7 处不是 6 处**：`api/accounts.py:48` 的 `XhsSelfProfileAdapter` 定义在 API 层（二次封装，轻度越界），docs/12 漏计。

## 收益利弊量化分析（同日追加）

用户要求：分析切换前后的收益利弊。产出 **`docs/14_无头浏览器化_收益利弊量化分析.md`**（决策级分析，8 章）。

### 新量化的硬数据（本次实测）

- 代码总量：Python 16,920 行（`apis/` 3,841 + `xhs_utils/` 4,808 + `backend/app/` 8,271）；前端 ts/tsx 11,513 行 / 37 文件
- `xhs_utils/**/js/` 共 16 文件 / 2,174 行 / **92.8KB**，按可退出性拆成三段：
  - 真正可退出 **55.9KB / 1335 行 / 60%**（sign、mns、b1、xs_common、websectiga_env、websectiga_cli）
  - **RAP 系 13.7KB / 243 行 / 15%（待定，采集链路上很可能保不住）**（rap、rap_crypto、rap_cli）
  - 必须保留 **23.3KB / 596 行 / 25%**（deflate、aes_encrypt/decrypt、两个 profile.js、creator_sign/ signature）
- 适配层迁移面：`backend/app/adapters/xhs/` 共 **369 行 / 21 个公开方法 / 5 个文件**（另加 `api/accounts.py:48` 的越界适配器 = 22 处）。**接缝出奇地小，是方案可控的根本原因**
- `requirements.txt` 中 playwright/selenium/pyppeteer 匹配数 = **0**（确认无浏览器依赖）

### 本次新增的关键判断

1. **「删掉近万行算法」是错觉**：真正可退出的只有 60%（55.9KB），RAP 系因采集主接口在白名单内很可能保留，上传链路的独立签名 + Node 运行时必须保留 → **切换后部署栈是 Python + Node + Chromium 三者并存，比现在更重**
2. **收益兑现是「递延」的**：旧路径正式下线前是「双轨成本 + 潜在收益」，中途放弃则双轨成本白付。**不要把收益写在切换当天，要写在降级路径下线那天**
3. **采集链路的头号收益被 RAP 白名单抵消**：`apis/xhs_pc_apis.py:37-44` 的 `_RAP_PATH_MARKERS` 内含 `search/notes`、`feed`、`user_posted` —— 正是采集核心接口。要么 DOM 驱动（慢 + 脆），要么保留 rap.js。**两条路都拿不到「采集零签名维护」**
4. **灰度维度应改为「按账号」而非「按链路」**（与 docs/10 §5 建议冲突）：旧 Cookie 是在伪造指纹模板下铸造的，新浏览器是真指纹，按链路灰度会让**每个账号都处于指纹混用状态**，迁移期反而是风控暴露最大窗口。此项未验证，列入阶段 0 待测
5. **新增一个单点故障：浏览器网关**。需配套健康检查、自动重启、并发限额、降级回旧路径 —— 这部分属于「新建一个服务」而非「迁移」，估算时易漏
6. **脆弱面性质变化**：签名 1 处致命（全局同步失效、失败很响）→ DOM / 反检测 / 注入多处轻微（局部、可修，但**可能几天没人发现**）。净判断是好转，但**前提是有监控能力**
7. **发布链路新增幂等风险**：DOM 驱动「填表单 + 点按钮」没有幂等请求 ID，网络卡顿/重试可能点两次；浏览器 context 不能跨进程共享 → 账号级互斥锁是硬约束

### 逐链路净评分（收益−代价）

登录 ★★★★★、巡检 ★★★★★（只读低频，先做）> 采集 ★★（需 spike 定形态）> 自动运营 ★ / 发布 ★（最后做）> 上传 负（维持现状）

### 待办（阶段 0 的三组决策数据）

1. 裸 `fetch` 是否被平台签名（docs/13 §2.3 的 spike）
2. **算法返工频率** —— 本仓库无 Git 历史（`.git` 不存在），218 个文件 mtime 全为 2026-09-08（一次性整体导入），**本地无法测量**，这是整个决策的分母
3. 指纹一致性是否被校验（决定灰度维度）

外加一个低成本高价值项：**先只把巡检链路浏览器化**（只读、无需签发、零接口配额），可在不改架构的前提下验证「浏览器 context 能否稳定复用登录态」这个地基假设。

## 约束变更：无企业资质 → 路线重构（同日追加）

用户明确：**没有也无法获取企业资质 + 应用审核**。产出 **`docs/16_无企业资质前提下的商品笔记自动化_路线重构.md`**。本文取代 `docs/15` 的 ①②（官方通道）两节，③④ 与合规/防重发设计继续有效。

### 推翻自己上一轮的判断（重要）

`docs/15` 写的「明确否决全逆向 ark：要新逆向一套签名」**是错的**。代码核查发现签名器与业务域解耦，四条证据：

1. `xhs_pc/runtime.py:68-106` `run_signer(api, data, a1, cookie, b1, dsl_pair, tier, sign_context)` —— **签名输入只有 path + body，host 完全不参与**，域名差异只在 HTTP 层（`self.base_url + api`）
2. `xhs_utils/xhs_core/auth.py:15-84` 的 `XHSPlatformConfig` 就是多业务域扩展点，已有 `PC_PLATFORM_CONFIG(app_id='xhs-pc-web')` / `CREATOR_PLATFORM_CONFIG(app_id='ugc')` 两个实例
3. `xhs_utils/xhs_core/cookies.py:44-171` `HostCookieStore` 已按 host 分域管 cookie，ark 域名天然支持
4. **已有先例**：`apis/xhs_pugongying_apis.py:19-26` 直接用 `PcDeviceProfile(cookies)` 给 `pgy.xiaohongshu.com` 签名 —— 同栈服务多域在本仓库跑通过

→ **接千帆是「加配置 + 加接口」，不是「重新逆向」。** 未知量只剩三个，全靠抓包：`app_id`（参与 mns 签名与 DS 获取）、登录态 cookie 名、是否带 `x-s-common`/`x-rap-param`。

### 推荐路线 C（而非全逆向）

**人工登录千帆 → 导出 Cookie → 系统只读逆向商品/店铺 → 发布仍走 creator + `goods_info`。**

核心理由：**登录逆向是全链路成本最高、风控最严、失效最频繁的一环，收益只是省一次人工操作。** 绕开它，`XhsPcApiAdapter(cookies)` 的构造签名可保持不变，改动趋近于零。

可能白捡：百科称「可直接使用小红书账号登录千帆，无需额外注册」→ 若成立，千帆与 creator 可能共用 `.xiaohongshu.com` 域的 `a1`/`web_session`，**已接入账号的 Cookie 或许直接可用**，连人工导入都省。验证成本极低，列为阶段 0 第二项。

### 地基假设换了（新的头号风险）

从「有无企业资质」换成 **「个人店能否获得商品分享权限」**。外部资料在此点**互相矛盾**（有称须个体户/企业，有称个人店亦可）→ 置信度低，**必须实机验证**。若为否 → 需求④落不了地 → 方案退为路线 B（只生成不挂商品）。

另需用户澄清一个口径：**个体工商户营业执照算不算他说的「企业资质」**——若可拿到，选中个体户店，可经营类目宽松很多。

### 外部事实（未实机验证）

- **个人店免营业执照**（身份证 + 人脸，保证金 1000 元起，可先发品后缴），但**可经营类目受限**（服饰/家居/文创/数码配件；食品/美妆/医疗器械不开放）—— 多来源一致，置信度中高
- 千帆 PC 端登录入口：`zhaoshang.xiaohongshu.com/seller/company?from=ark-login`（单来源，置信度中）
- 商品标签需「专业号认证 + 绑定店铺」—— 多来源一致，中高

- `docs/` 编号文档已续到 16；`docs/15` 附录 B 的置信度表被 `docs/16` 附录 A 取代

## 三类店铺统一支持设计（同日追加）

用户澄清需求：店铺**可能为个人店、个体店、企业店任意一种，三种场景均须支持**。产出 **`docs/17_三类店铺统一支持设计.md`**，取代 `docs/16` 的 §1.2/§1.3/§4.3/§6.1（那几节隐含了「假设为个人店」）。

### 核心设计判断

> **把「支持三种店铺」实现为 1 套能力探测机制，而不是 3 套类型分支。**

理由：类型→能力的映射**目前是猜的**（外部资料在「个人店能否挂商品」上直接矛盾）。**写死的类型判断 = 用未验证假设驱动代码分支**，猜错会扩散到前端/后端/调度三层。

**正模式**：`shop_type` 只用于展示与探测失败的兜底默认；**逻辑分支一律读运行时探测出的 `capabilities`**。这样三种场景天然支持，且未来出现第四第五种店铺类型**代码零改动**。

### 关键设计点

1. **必须引入 `shop_account_bindings`（N:M）**：企业店一执照最多 3 店 × 主账号 + 多子账号 → 账号:店铺是 N:M。沿用单外键 `shops.platform_account_id` 会导致子账号同步时产生重复行或丢失访问路径。用 `can_sync` 标记唯一同步来源账号。
2. **Cookie 存账号层，能力存店铺层**：能力是店铺属性（主/子账号看到的能力相同），登录态是账号属性。
3. **探测失败 → 保守默认 + `capabilities_verified_at=NULL` + 只开放只读**（不误发也不死锁，用户仍可生成草稿）。
4. **降级是合法业务流程**：无 `can_attach_goods` 的店铺自动走「生成 + 普通笔记发布」，这正是统一支持三种场景的关键。
5. **前端置灰而非隐藏**：三店共存时用户需理解「为什么这家不能挂商品」，隐藏会被当成 bug。
6. **企业店有「发品前必须缴保证金」硬前置** → 能力探测须含此项，否则会给错误诊断。
7. **子账号岗位权限可能细到「能看到店铺但无权发笔记」** → 探测可能需按「账号+店铺」组合维度，`shop_account_bindings` 已预留位置。

### 阶段 0 调整

`docs/16` §6.1「验证个人店能否挂商品」→ 改为「**为每种实际持有的店铺类型各产出一行能力矩阵**」。某个类型当前无可访问店铺则留空，**不影响上线**（`shop_type=unknown` + 保守默认已能兜住）。另需顺带确认：子账号登录后能看到几个店铺（验 N:M 是否真实）、未缴保证金时上架与发布分别报什么错。

### 新增发现的代码缺陷

`apis/xhs_pugongying_apis.py:24` 调 `generate_pugongying_headers(cookies, api, data, profile=self.profile)` 4 个参数，而 `xhs_utils/xhs_pugongying_util.py:26` 只定义 `(a1, api, data='')` 3 个参数 → **必 TypeError**。与 `docs/15` 发现的 creator 健康检查 bug 同类，说明蒲公英链路已与新版签名栈脱节（`xhs_pc/params.py:132-161` 的 `generate_xs` 注释提到「蒲公英等接口只携带 X-s/X-t」，说明重构做了一半）。

## 第四种账号形态：非店铺账号（同日追加）

用户补充：**还有一种账号——非店铺账号**，也须支持。产出 **`docs/18_非店铺账号与账号店铺二维模型.md`**，并在 `docs/17` 头部加勘误指向。

### 核心设计判断（比 docs/17 更硬）

> 「有没有店铺」是**业务维度**，「账号走哪条技术链路」是**协议维度**。把前者塞进 `sub_type` 是用业务状态驱动技术路由。

模型：`sub_type ∈ {pc, creator}`（协议）+ `shop_account_bindings 0..N`（业务），**两个正交维度**。「非店铺账号」= `creator` 且 0 个 binding。

**比 docs/17 多出的两个代价**（docs/17 只说了另外两个）：
- **改绑即改路由**：`api/accounts.py:57-58` `_select_adapter` 是 `creator → creator_adapter`，**否则一律 pc_adapter**。用户开店/关店若改 `sub_type`，登录适配器跟着变 → 登录态失效。
- **状态与事实不同源**：`sub_type` 是静态字段，"有没有店铺"是平台侧事实。不一致时系统拿过期本地字段当真且无机制发现。

### 修正了 docs/17 §4.3 的 `sub_type="shop"` 设计

**推荐维持 `sub_type ∈ {pc, creator}`，不新增类型**。若真加 `shop`：`api/publish.py:415/453` 会拒绝该类型发布，且 `_select_adapter`(`accounts.py:57-58`) 与巡检适配器选择(`scheduler_service.py:652`) 两处 `else` 兜底会**静默走错分支**（比抛异常更危险）。备选方案：加但定义为只读、永不发布。

### 本次实测：sub_type 硬编码点全表（13 后端 + 7 前端）

后端：`api/accounts.py:35`（Pydantic `^(pc|creator)$`，新增类型直接 422）、`:57-58,114,120,135,173,190`、`api/login_sessions.py:124,224,228-236,254,359,383`、`api/publish.py:415,453`、`api/auto_tasks.py:90-102`、`api/platforms/xhs/creator.py:79`、`pc.py:287`、`crawl.py:220`、`api/notes.py:436`、`services/scheduler_service.py:124,652`、`services/monitoring_crawl_service.py:33,39`
前端：`types/index.ts:51`、`lib/api.ts:770,809,821`、`pages/platforms/xhs/{accounts:195,auto-ops:123-124,crawler:182,190,discovery:98,103,publish:104}-page.tsx`

### 关键事实：现有代码无「账号必须绑店铺」校验

全量 grep 确认 **13 处 creator 守卫全部只看 `sub_type`**（`creator.py:76-81`、`publish.py:415/453`、`scheduler_service.py:124`）。→ **非店铺账号一直是合法可用的，本需求是把既有能力显性化，不是新建机制。** creator + 0 店的普通笔记发布**零改动**。

### 最重要的业务推论（docs/15/16 均未覆盖）

**商品来源账号 ≠ 发布账号**，发布分两条路径：
- 挂链商品笔记 → 必须店铺账号 + `can_attach_goods`（账号池 1-3 个，受店铺数限制）
- 不挂链种草笔记 → 任意 creator 账号（**非店铺账号在此，池子可数十个**）

→ `docs/17` §6.3 的「降级路径」**重新定性为独立业务模式**（种草发布），并新增「同一商品 × 多账号矩阵分发」业务能力。这也是非店铺账号值得单独立项的理由：**店铺账号数量被平台（一执照最多 3 店）天然限制，内容号不受限。**

### 需要的改动（很小）

1. `serialize_account` 增派生字段 `has_shop` / `shop_count`（**不落库**，可从 bindings 算出）
2. 新增 `resolve_capabilities(account, shop=None)` —— 能力作用域从"店铺"扩展到"账号×店铺"
3. `types/index.ts:51` 前端类型补字段；账号列表/发布页展示账号形态 badge
4. `product_note_jobs.creator_account_id_fk` 允许指向非店铺账号
5. 表结构（`shops`/`shop_account_bindings`/`shop_products`/`product_note_jobs`）**无需改动**

### 关联：creator 巡检 bug 优先级上升

`api/accounts.py:190-201` 的健康检查 bug（docs/13 已记录）影响面变大——**非店铺账号就是 creator 账号**，矩阵铺量场景账号数多、以编程方式批量探活是常态，而该接口对 creator **100% 误报**。

### 新增风险

营销号识别（无店铺账号发商业内容判定更严，最高风险）、内容同质化（多号发同款→去重降权，需按账号维度变异模板）、账号数放大巡检压力（复用 docs/14 结论：先用「cookie 是否存在」做低成本前置判断）。

### 阶段 0 追加验证项

① 千帆登录态能否复用 creator Cookie（决定是否引入 `shop` 类型）② 现有 creator 账号中无店铺绑定的占比 ③ 非店铺账号发布普通笔记完整链路 ④ 一个 creator 账号能否同时绑多家店铺
