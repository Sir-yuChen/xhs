### 7. M0 前置验证 · T-010 已完成（缺陷成立）

**结论：`config/default.yaml` 完全压制环境变量。** 2026-09-18 实测（系统 Python 3.12 + pydantic-settings 2.15.0）：
注入 `SCHEDULER_ENABLED=true` / `FRONTEND_SERVE_STATIC=true` / `SECRET_KEY=ENV_SECRET_WINS`，
实际取值 `False` / `False` / `'dev-only-change-me'` — **三个全部失效**。

根因：`core/config.py:157` 的 `Settings(**yaml_values)` 把 YAML 作为**初始化参数**传入，而 pydantic-settings 的优先级是「初始化参数 > 环境变量 > `.env` > 默认值」。
`default.yaml:6-7` 与 `core/config.py:18-20` 的注释声明「环境变量优先级最高」——**注释与代码行为相反**。

生产后果（已确证，非推断）：
1. `SECRET_KEY` 失效 → JWT 用默认弱密钥 `dev-only-change-me` 签发
2. `FERNET_KEY` 失效 → Cookie 加密密钥不稳定，**容器重建后历史 Cookie 永久解不开（不可逆数据损失）**
3. `FRONTEND_SERVE_STATIC` 失效 → Dockerfile:66 的 `true` 被压回 `false`，生产静态服务挂不上

**修复方向（T-110，推荐方案②）**：把 `default.yaml` 中应由环境变量控制的键
（`security.secret_key`、`security.fernet_key`、`scheduler.enabled`、`frontend.serve_static`）
从 YAML 移除，只保留在 `Settings` 类默认值里。改动最小、语义最清晰，且不产生「原本靠 YAML 生效的配置突然翻转」的反向风险。

### 13. 部署验证阶段发现并修复 DEF-032（2026-09-18 17:34，用户报告）

**用户报告**：模型配置页「新增模型」的 **Base URL 显示当前登录账号、API Key 显示密码**。

**归因结论：✅ 纯前端页面问题，后端无责。**（用户问的正是「页面问题还是后端问题」）

**根因**：`frontend/src/pages/models/model-config-page.tsx` 用**原生 `<form>`** 包裹输入区，内含 `<Input.Password>` 且**未声明任何 `autoComplete`** → 浏览器「登录表单启发式」判定这是登录框，把**已保存的本站凭据**自动填入；Chrome 取**离密码框最近的上一个文本输入框**作为用户名目标 —— 正好是 Base URL（字段序：配置名称 → 模型名称 → **Base URL** → **API Key**）。

**四条证据**（判定后端无关）：
1. `_serialize_config()`（`api/model_configs.py:38-48`）只返回 `base_url` + `has_api_key` **布尔**，**无任何用户字段**，`api_key` 明文**从不回传**
2. 前端 `emptyForm` 的 `base_url`/`api_key` **初始为空串**；编辑态也刻意不回填 `api_key`
3. 实测 DB `model_configs` 仅 1 条：`base_url='https://api.deepseek.com'`、`encrypted_api_key` 为 Fernet 密文，**无凭据**
4. **判定铁证**：React 受控组件的 `value` 绑定空 state，**页面自身不可能渲染出账号密码** → 显示的值只能来自浏览器注入
5. **唯一差异点**：全项目共 4 个 `<Input.Password>`，登录页 3 个**都声明了 `autoComplete`**，**只有模型配置页这一个漏了** —— 出问题的正是漏掉的那个

1. 表单根节点 `autoComplete="off"`
2. Base URL：`autoComplete="url"` + `name="model-base-url"`
3. API Key：`autoComplete="new-password"` + `name="model-api-key"` ← **决定性的一招**（告诉浏览器这不是登录密码）
4. 配置名称 / 模型名称：`autoComplete="off"` + 语义化 `name`
5. **纵深防御**：`handleSubmit` 校验 `base_url` 必须是以 `http(s)://` 开头的合法 URL —— **即使 autofill 未被拦下，脏值也无法入库**

### 三、用户实测三个反馈（全部已修 + 已回写）

#### 反馈 1：勾选「登录 PC 后同步 Creator 账号」时**登录无响应，页面无任何反应**（DEF-036，P1）

**根因（实测复现）**：`qr-login-panel.tsx` 的会话创建 effect 依赖了 `syncCreator` →
**勾选即调 `/pc/qrcode` 建新会话**（实测 session 81 → 82，两次都 200）。

页面就永远停住；因为返回 200，连错误都没有。

**三层修法**：
1. 后端轮询端点新增**可选查询参数** `sync_creator`（实时覆盖，与手机路径的 `PhoneConfirmRequest.sync_creator` 同构）
   → **改偏好不再需要重建会话**；新增响应字段 `creator_sync_error`。
2. 前端勾选状态改用 `ref` 读取，**从会话创建 effect 依赖中移除**；三种登录面板（扫码/手机/Cookie）
   都展示同步结果（成功含 Creator 昵称 / 失败给可读原因）；确认后复选框置灰并说明。
3. 两处 `except Exception: return None` 改为 `logger.warning` + 返回值
   （`login_sessions.py::_sync_creator_account_from_pc_login`、`accounts.py::_sync_creator_account_from_pc_cookie`）。

> **规律（新，重要）**：**`except Exception: return None` 用在「可选步骤」上是最坏的写法**——
> 它把「没必要做」「没做」「做失败了」压成同一个值。可选步骤**可以不阻塞主流程，但必须留下结果**。

#### 反馈 2：我的笔记页刷新异常提示 **Not Found**（DEF-037，P2）

**根因**：全局响应拦截器（`api.ts:134-158`）对**任何**非 401 失败都 `message.error(detail)`。
`fetchXhsSelfCapabilities` 在设计上「失败即保持全 Tab 可用」，其 `catch` 置 `null` 继续工作
——**但 `catch` 拦得住 promise，拦不住已经弹出的 toast**。

**修法**：给该请求加 `{ _silent: true }`（拦截器既有机制）。
**规则确立**：`_silent` = 「这个失败的展示权归调用点」，不是「静音一切」。

> **同时查明诱因**：运行中的后端进程是**旧构建**（`GET /openapi.json` 只有 115 条路由，
> 不含 `/api/xhs/pc/users/capabilities`）→ **需要重启后端**。
> **排障经验**：看到裸英文 `Not Found`/`Unauthorized`，先怀疑**后端路由缺失（进程未重启）**，
> 再看前端代码。

## 16:15 · 第三轮用户实测：PC 扫码登录**全线失效**（DEF-038）+ PC 账号卡片补「小红书号」

### 一、用户反馈（两条独立诉求）

### 二、先取证再改：用 `gid` 当「这个会话被轮询过吗」的判据

- 查 `login_sessions`：19:13 之后 14 条 PC 会话**全部停在 `pending`**，但同账号表里确有一条 19:13 **成功**的 PC 账号（`晨晨家`, `red_id=63532415321`）
  → **链路本身可用**，是**条件性/竞态性**失败，不是接口坏了。
- 解剖 `encrypted_temp_cookies`：PC 扫码链路的 webprofile `gid` **只在首次轮询时被注入**，
  于是「cookies 里有没有 `gid`」= 「这个会话被至少轮询过一次」。
  18 条 PC 会话：**8 条有 `gid`、10 条没有** —— 每隔一条就凭空多出一个「创建了却从未被轮询」的会话，
  这正是 **`React.StrictMode` 把 effect 跑两次**（`main.tsx:9`）而 `startSession` 无幂等守卫的指纹（两条 POST 相隔约 2.2s，被签名层串行化）。

### 三、根因（DEF-038，P1）

- **放大器**：StrictMode 双挂载 → 一次开抽屉建**两个**会话，只有一个被轮询。
- **真正致命的一步**：轮询回调**无条件**写回 state ——
  `setSession(cur => ({...polled, qr_image_data_url: cur?.qr_image_data_url}))`。
  若旧会话的轮询响应在新会话已上屏之后才返回，`session_id` 被**拉回旧会话**，而 `qr_image_data_url` 仍是**新会话的图**
  → **屏幕上是 QR-B，轮询器盯着 session-A**；用户扫 B、确认记在 A，**永远无人观测**，页面自然「无任何反应」。
- **为什么「以前能用」**：这是**竞态**（第一条会话的首次轮询早于第二条落屏时恰好一致）。时序抖动决定成败。
- **与 DEF-036 的关系**：同一根因族 —— DEF-036 是「**偏好**改变了会话身份」，DEF-038 是「**响应**改写了会话身份」。
  共同不变式：**视图上的二维码与正被轮询的会话 id 必须同源**。

### 四、修复（三层，缺一层仍可复现）
