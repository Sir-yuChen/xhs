## 追加（当晚七）：DEF-040 —— 覆盖率数字落后一步（用户实测报出）

**修法**：`my-notes-page.tsx` 加载「我发布的」时存下 `goods_source`，覆盖率/巡检时间行改为
`goodsInfo = goodsSource ?? capabilities?.capabilities.goods`（**新鲜值优先**，顺序有意，已写注释）；
账号切换与各动作后清空该快照（那之后 capabilities 才最新）。`types/index.ts` 把
`XhsSelfGoodsCapability` 与 `XhsGoodsSource` 收敛成同一形状（后端同源，类型别各写一份）。

**真机受控复现**（`.workbuddy/tmp/verify_goods_coverage_fresh.py`）：记录 270 → 删本页首条笔记的映射行

## 追加（当晚五）：商品映射改「按需补齐」（T-30 关闭）

**用户定调**：「千帆商品映射改为后台全量同步，**不改为全量**，而是**加载笔记时才同步**对应笔记挂载的商品。」

**关键发现（推翻了我们自己写进文档的结论）**：旧文档说「千帆商品笔记列表没有按 note_id 查询的口子」
—— 那是**只试了单数 `note_id`**。用「阳性/阴性判别式实验」扫了 15 个候选后，**复数的 `note_ids`** 立刻命中：

| 输入 | total |
|---|---|
| `note_ids=<真实 note_id>` | 1（且行的 item_id 与店铺口径一致） |
| `note_ids=<不存在的 id>` | 0 |
| `note_ids=a,b,c…`（2/6/10/20/50 个） | = 传入个数（**一页一次请求**的依据） |
| 混入不存在的 ID | 仍是真实条数（不污染） |
| 单数 `note_id` / `keyword` / `search_filter.*` | 1968（被忽略） |

**教训**：断定「平台没有这个能力」之前，先把候选名**穷举**一遍（尤其**单复数**）；
一条错误的「不可能」会把设计带偏 —— 差一点就去做上百页的后台全量慢跑。

**实现**（`services/shop_goods_service.py`，存储 + 补齐唯一实现；`pc.py` 与 `qianfan.py` 共用）：
- 加载「我的笔记」时，只对**本页缺映射**的笔记发**一次**请求（`note_ids` 逗号拼接，上限 50）；
- 命中即落库 → 第二次浏览该页 **零平台请求**；平台**不返回负记录**，所以「确认没商品」的笔记每页会重查那 1 条；
- 失败静默（页面照常 200，原因进 `goods_source.on_demand.error`）；`-13000` → 绑定 `invalid` 但**不清映射**；

- `sync-goods` 降级为**批量补齐**（可选）；**不新增任何开关**（没有后台任务，项目约定「不写没人读的配置」）。

**真机受控实验**（真实库、自我修复）：首屏 10/10 带商品且 `on_demand=None`（0 次查询）→ 删掉 1 条映射行

**数字**：单测 +5（`test_self_content.py` 61→66），回归 **284 passed**；端点仍 145 / path 125；用例 **245**（P0 **83**）、完成度 **47.3%**。

## 二、可复用教训（下次别再踩）

1. **「这条链路没有这个字段」≠「这个数据不存在」。** 创作者列表空壳 + 平台 UI 零商品标识，很容易误判成「笔记没挂商品 / 功能不可做」；
   真正钉死结论的是**跨平台同一 `note_id` 对照**。已写入设计 12 §19.0 与 ADR-019。
2. **另一个后台的登录态不能靠 SSO 复用**，但**浏览器里人工登录一次**就能拿到它自己的 Cookie——比逆向登录省一个量级的成本。
3. **统计数字不能靠增量维护**：本轮发现测试跟踪 §3 的用例总数（204）与用例库 §14（217）**跨表漂移**——

4. **「删掉一句文案」也要写成断言/用例**（TC-SELF-47 反向守卫、TC-SELF-59），否则下次重构会被抄回来。
