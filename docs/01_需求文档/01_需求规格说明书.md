## 一、10 句话需求

1. **开发者的角色**：逆向工程与全栈开发者，负责维护小红书的签名算法与运营后台，把平台能力封装成可编程接口。
2. **项目名称**：XHS_ALL_IN_ONE（小红书一站式智能运营平台）。
3. **项目主要功能**：把「数据采集 → 内容库 → AI 改写 → 图片处理 → 一键/定时发布 → 全自动运营」串成一条闭环。
4. **项目主要用户**：需要批量运营小红书账号的运营人员与内容团队。
5. 用户用浏览器登录系统，绑定自己的小红书账号（可多个），系统代为采集和发布。
6. 用户采集他人笔记入库，用 AI 改写成功自己的内容，再选择账号发布出去。
7. 用户也可以不手动操作——配好关键词与频率，系统自动完成搜索、改写、发布。
8. 系统本身也作为底层能力仓库，可被上层 Agent 工具链通过 skills 复用。
9. **技术形态**：Web 后台（浏览器访问），**无移动端**。
10. **合规边界**：项目声明仅供学习交流，禁止商业化；商品笔记属商业推广，用途合规性需自行评估。

## 二、主要用户

| 用户 | 是谁 | 核心诉求 | 对应系统能力 |
|---|---|---|---|
| **运营人员**（主要） | 管理多个小红书账号的内容运营 | 少手工操作、批量产出、可控发布 | Web 运营端全部功能 |
| **内容创作者** | 需要灵感与选题的个人 | 高效采集爆款、快速改写 | 笔记发现、内容库、草稿工坊 |
| **投放/品牌方** | 需要监控竞品与行业趋势 | 看数据、看趋势 | 数据洞察、竞品监控 |
| **上层 Agent 工具链** | Clawbot / Claude Code / Codex 等 | 把小红书能力当成一个 skill 调用 | `apis/` + `xhs_utils/` 底层 SDK |
| **系统管理员** | 部署与维护系统的人 | 装得上、跑得稳、出问题能查 | 配置体系、任务中心、通知系统 |

**用户量假设**：单机自部署，**单实例并发用户数十人量级，小时级中低频任务**。非 SaaS 多租户高并发场景。

## 三、功能域（按用户可见的模块划分）

| # | 功能域 | 用户能做什么 | 现状 |
|---|---|---|---|
| F1 | **账号矩阵** | 绑定多个 PC / Creator 账号（扫码、手机验证码、Cookie 导入），查看健康状态，删除账号。**账号卡片统一展示五字段：类型 / 小红书号 / 粉丝 / 关注 / 获赞数**（PC 与 Creator 一致） | ✅ |
| F2 | **笔记发现** | 按关键词搜索小红书全站笔记，URL 直查，多维筛选，查看详情与评论，一键入库 | ✅ |
| F3 | **数据抓取** | 批量抓取（URL / 搜索 / 评论），SSE 实时进度，Excel 导出，素材本地下载 | ✅ |
| F4 | **内容库** | 统一管理采集内容，标签、搜索、批量操作、JSON/CSV 导出 | ✅ |
| F5 | **关键词组** | 维护关键词集合，供自动运营与采集复用 | ✅ |
| F6 | **草稿工坊** | 三栏编辑器：草稿队列 + 编辑区 + AI 助手；AI 改写/润色/生成标题标签；素材拖拽排序 | ✅ |
| F7 | **图片工坊** | AI 生成图片（支持参考图）、图片描述、AI 与普通图片资产管理 | ✅ |
| F8 | **发布中心** | 选账号 → 预览 → 立即/定时发布到小红书创作者平台；状态追踪、重试、取消 | ✅ |
| F9 | **自动运营** | 配置关键词 + 调度频率，无人值守执行「搜索 → 改写 → 上传 → 发布」 | ✅ |
| F10 | **数据洞察** | 总览仪表盘、互动趋势、Top 内容、热门话题、评论分析 | ⚠️ 基础版 |
| F11 | **竞品监控** | 监控关键词/账号/品牌/URL，自动刷新快照，查看历史 | ✅ |
| F12 | **任务中心** | 全量任务审计、调度器状态、手动触发/取消/重试 | ✅ |
| F13 | **模型配置** | 配置任意 OpenAI 兼容 API（火山引擎、阿里百炼等），设为默认 | ✅ |
| F14 | **通知系统** | Cookie 过期、任务失败自动通知，铃铛实时展示 | ✅ |
| F15 | **系统设置** | 安全边界说明（⚠️ 原第二项「项目声明」**已于 2026-09-26 按用户口径从设置页整卡移除**，原句保留备查） | ✅ 静态页 |

> 视觉工坊：视频工坊目前为空壳页（2026-09-25 §36 起为「笔记工坊 → 视频工坊」页签的面板 `frontend/src/pages/platforms/xhs/video-studio-panel.tsx`），视频发布在服务端被显式拒绝（`backend/app/api/publish.py:499`）。**视频能力属于「范围外」**。

## 四、非功能需求

| 类别 | 要求 | 现状 |
|---|---|---|
| **性能** | 采集与发布为小时级中低频负载；签名走 Node 子进程，单次约 100ms 级 | 满足 |
| **并发** | 单账号发布必须串行（避免重复发布与风控）；调度器 `max_instances=1` | 满足，但**多副本不安全**（见技术债） |
| **数据一致性** | 写操作（发布）不可逆 → 必须有幂等与防重机制 | 靠定时补跑幂等 + 状态机 |
| **安全** | Cookie / API Key 加密落库；JWT 鉴权；用户间数据隔离 | 满足（有配置风险点） |
| **可运维** | 一条命令启动；Docker 单容器部署；首次启动自动建库 | 满足 |
| **时区** | 全系统统一东八区 | 强制约定 `backend/app/core/time.py::shanghai_now()` |
| **可用性** | Cookie 过期是常态 → 2 小时自动巡检 + 通知 | 满足 |
| **合规** | 遵守平台规则与广告法；不提供规避风控的能力 | 见 `11_安全设计.md` |

## 五、约束与边界

| # | 约束 | 后果 |
|---|---|---|
| C1 | 依赖**逆向签名**，非官方 API | 平台改版会导致签名失效，需持续维护 |
| C2 | 无企业资质、无法通过官方开放平台审核 | 官方通道机制性关闭，只能走逆向链路 |
| C3 | 账号 Cookie 有生命周期 | 过期即不可用，需重新登录 |
| C4 | 发布是写操作，**不可撤销** | 必须有防重发与人工审核机制 |
| C5 | 平台对批量营销内容有风控 | 频率必须保守 |

---

## 六、范围外（明确不做）

| 不做的事 | 理由 |
|---|---|
| 移动端 App | 本项目定位为 Web 运营后台，单机自部署 |
| 视频发布链路 | 一期未实现，服务端显式拒绝 |
| 抖音 / 快手 / 微博 / 闲鱼 / 淘宝 | 注册表中标记 `coming_soon`，未实现 |
| 商业化 SaaS 多租户 | 项目声明禁止商业化 |
| 规避平台风控的能力 | 合规红线 |
| 官方开放平台接入 | 无企业资质，机制性关闭（见 C2） |
