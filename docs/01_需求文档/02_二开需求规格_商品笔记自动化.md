## 一、10 句话需求

1. **开发者的角色**：在现有逆向 SDK 与运营后台基础上做增量开发的工程师，不重写底层，只做扩展。
2. **项目名称**：XHS_ALL_IN_ONE · 商品笔记自动化（二开）。
3. **本次要加的功能**：让系统能读取小红书店铺的商品数据，并用 AI 生成挂载该商品的笔记，自动发布出去。
4. **主要用户**：有小红书店铺的商家运营（店铺是自己开的，需要给自己店铺的商品做内容推广）。
5. 用户在千帆商家后台人工登录后导出 Cookie，导入本系统，系统据此只读同步店铺列表与商品列表。
6. 系统探测每家店铺的能力（能不能挂商品、能不能发笔记、经营类目、是否需缴保证金等），把结果落库并展示。
7. 用户为某个商品生成商品笔记草稿，AI 使用商品专用 Prompt 撰写，并经过违禁词与一致性护栏校验。
8. 用户确认草稿后，系统通过现有的 Creator 发布链路，把商品挂到笔记上发出去。
9. 同一商品可以由店铺账号挂链发 1 篇，另由多个非店铺账号各发 1 篇不挂链种草笔记（矩阵分发）。
10. **合规红线**：商品笔记属商业推广内容，违禁词、功效宣称、货不对板三类风险必须由系统内建护栏拦截，不能靠人盯。

## 二、需求条目

| # | 需求 | 优先级 | 说明 |
|---|---|---|---|
| **R1** | 登录小红书店铺 | 高 | 口径：取得**店铺级访问能力**，可读该店铺的商品数据。**不逆向登录**，采用人工登录后导入 Cookie |
| **R2** | 获取店铺列表 | 高 | 口径：账号可访问的**多店铺列表** + 店铺基础信息（名称、类型、状态） |
| **R3** | 根据商品信息 AI 生成商品笔记 | 高 | 口径：要能**挂载自己店铺的商品**；同时保留不挂链的种草笔记形态 |
| **R4** | 自动化发布商品笔记全流程 | 高 | 口径：复用现有发布链路，仅补全发布体的商品槽位 |
| **R5** | 店铺能力探测与矩阵分发 | 中 | 见第 10 句：店铺账号挂链 + 非店铺账号种草的组合能力 |
| **R6** | **商品列表页（千帆只读，含搜索条件）** | 中 | ✅ **2026-09-19 已实现**（用户追加：「新增一个商品列表单独页面，千帆获取商品列表，展示商品相关的数据」+「主要要包括搜索条件功能」）。口径：独立页面展示店铺商品，**必须带搜索条件**（关键词 / 状态 / 价格 / 库存 / 销量 / 排序 / 分页）；只读、不落库、不碰写接口。设计真相源 `02_设计文档/12` **§25**；需求条目承接 R1（店铺级访问能力）的真数据 |

## 三、约束

### 3.1 用户侧约束（硬约束，不可绕过）

| # | 约束 | 后果 |
|---|---|---|
| **C1** | 没有也无法获取企业资质 + 应用审核 | **官方开放平台通道机制性关闭**。这不是「申请难」，而是入口本身不面向无主体开发者开放 |
| **C2** | 店铺可能是**个人店 / 个体工商户店 / 企业店**三种，都要支持 | 必须**能力驱动**而非类型分支（类型→能力的映射目前是猜的） |
| **C3** | 还有**非店铺账号**（有 creator 能力但没绑店铺），也须支持 | 需要「账号 × 店铺」二维模型，店铺关系不能塞进 `sub_type` |

### 3.2 技术侧约束（来自现状代码）

| # | 约束 | 说明 |
|---|---|---|
| **C4** | 不新增签名维护面 | 论证见 `docs/_legacy_v1/PROJECT_MASTER.md` §13.4：签名器与业务域解耦，`run_signer` 只吃 path + body，host 不参与签名 |
| **C5** | 上传链路保持不动 | `apis/xhs_creator_apis.py` 的 PyExecJS 独立签名维持现状 |

## 七、非功能需求

| 类别 | 要求 |
|---|---|
| **合规（最高优先）** | 违禁词库命中必须拦截；不得编造商品参数、价格、销量；不得使用绝对化用语与功效宣称 |
| **防重发（硬指标）** | 同一商品 × 同一发布账号的**重复发布次数必须为 0** |
| **安全性** | 千帆 Cookie 与一期账号 Cookie 同等加密存储；不与一期 Cookie 混写 |
| **频率** | 商品笔记比普通笔记更保守：**建议 ≤5 篇/日、间隔 ≥60min**、同商品冷却 ≥72h |
| **降级** | 能力探测失败 → 取保守默认 + 显式标记未验证 + **只开放只读功能**，不开放发布 |
| **兼容** | 一期所有现有功能的行为与接口保持不变 |

## 九、范围外（明确不做）

| 不做的事 | 理由 |
|---|---|
| 逆向千帆登录（扫码/密码） | 登录逆向是全链路成本最高、风控最严、失效最频繁的一环，而收益只是「省一次人工操作」 |
| 千帆写接口（改价、上下架、订单操作） | 只读边界，保持低风控面（C6） |
| 自动缴保证金、自动开店 | 涉及资金与资质，人工完成 |
| 用 AI 重绘商品图作为主图 | 商品失真 → 与实物不符 → 售后与违规风险。**电商类目优先真实商品图 + 版式差异化** |
| 跨账号同文分发 | 会触发内容去重降权 |
| 官方开放平台接入 | C1，机制性关闭 |

## 十、决策点

### 10.1 已拍板（2026-09-18）

| # | 决策 | 结论 | 影响 |
|---|---|---|---|
| **D1** | 商品笔记是否**必须**挂商品 | ✅ **两者都做**。① **由商品信息生成的商品笔记，必须挂载对应商品链接**；② 普通笔记的挂/不挂**由账号能力在运行时决定**（有 `can_attach_goods` 则挂，无则不挂） | R1/R2 **不降级**，仍为高优先。挂链是商品笔记的硬要求 → M2（店铺接入）、M3（能力探测）**全部保留**。<br>⚠️ 由此派生的两点：<br>	· **账号池受限**：挂链必须店铺账号 + `can_attach_goods`，可发布账号数 ≤ 店铺数<br>	· **D1 的答案本身印证了 ADR-003 的能力驱动原则**：普通笔记「按账号能力挂/不挂」正是 `resolve_capabilities(account, shop)` 的标准用法，前端按能力**置灰而非隐藏**。设计无需推翻，只需按此口径固化 |
| **D2** | 店铺数据来源 | ✅ **只读逆向 `ark.xiaohongshu.com`**。不做人工 CSV 导入（若一期实测发现逆向不可行，再启动降级方案，需回到本文档变更） | 需求 N1/N2 依赖**千帆只读链路**可通 → **T-003（Cookie 复用性）与 T-004（抓包定签名参数）升级为 M0 必答项**，不再可选。<br>约束 C6（不碰 ark 写接口）继续有效 |
