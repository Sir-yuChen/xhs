## 一、11 句话需求

1. **开发者的角色**：在现有逆向 SDK 与运营后台基础上做增量开发的工程师，不重写底层，只做扩展。
2. **项目名称**：XHS_ALL_IN_ONE · 账号矩阵同步。
3. **本次要加的功能**：在账号矩阵页给每个账号加「同步笔记」能力，把平台侧的笔记同步到本地数据库；Creator（创作者）账号额外加「同步店铺商品」，把千帆店铺的商品数据同步到本地。
4. **主要用户**：手上有多个小红书账号、希望本地有一份完整内容台账的矩阵运营者（平台列表翻页太慢、数据看不全、掉线就翻不到历史）。
5. **同步入口在账号卡片上**，由用户显式点击触发；PC 账号与 Creator 账号都支持「同步笔记」，但取数链路按账号实际具备的能力选择。
6. **Creator 账号的「同步笔记」是增强版**：除笔记本身，还要把该笔记在千帆后台挂载的**商品信息**（标题、主图、规格、商品 ID）与店铺侧指标（阅读数、支付金额、支付订单数）一起落库。
7. **「同步店铺商品」把千帆商品列表落库**：商品标题、主图、价格、库存、销量、上下架状态，供本地检索与后续商品笔记生成使用。
8. **同步是异步的、慢的**：后端建任务行，后台线程慢慢跑，调度器定时续跑；请求接口立即返回任务 id，不等同步完成。
9. **风控是第一优先**：翻页有界、按账号限流、页间停顿；超限就停本次，等下一轮，绝不连续打爆。
10. **同一个同步任务不允许重复发起**：已有未完成的同类型同步任务时，再次触发返回已有任务，不重发平台请求。
11. **增量同步按维度**：全量 / 增量由 `mode` 区分 —— 手动触发默认全量，调度器默认增量。增量不是笼统的「只取新的」，而是拆成**新增 / 变更 / 删除 / 状态变更**四个维度分别处理：商品的变更能靠 `update_time` 时间窗感知，**笔记的变更做不到**（列表没有 `update_time`、也没有时间窗参数，只能全量重扫）；**删除两个列表都感知不到**（平台不返回删掉的行），这一条要显式声明，不能假装能做。

## 二、需求条目

| # | 需求 | 优先级 | 口径 |
|---|---|---|---|
| **R1** | 所有账号同步笔记 | 高 | PC 账号与 Creator 账号都支持「同步笔记」，把平台侧笔记落本地 `notes` 表（复用既有采集落库链路）。链路选择按**能力**（有无 `web_session`）而非仅看 `sub_type`（沿用 `03_需求规格_我的笔记列表.md` D5 的口径） |
| **R2** | Creator 卡片「同步店铺商品」按钮 | 高 | ~~仅 `sub_type=creator` 的账号卡片显示该按钮~~ → **已被 R11 修订（2026-09-21 v1.31）：所有账号卡片均显示**。未绑定千帆 → 400 `QIANFAN_BINDING_REQUIRED`（沿用既有错误码），按钮仍在、给出可读原因，不隐藏 |
| **R3** | Creator 同步笔记含千帆后台数据 | 高 | 笔记落库 + 本页 note_id 批量调千帆 `goods-note/list`（`note_ids` 逗号拼接，**每页 ≤1 次**只读请求）把挂载商品与店铺指标落 `shop_note_goods`（`entry_json` 存整条原文）。**这是「拉千帆后台数据」的落点** |
| **R4** | 风控与异步 | 高 | ① 有界翻页（默认 3 页、上限 20 页 × 100 条）；② 按账号限流 + 页间停顿；③ 超限停本次等下一轮；④ 手动触发立即返回 task_id，后台线程异步执行 |
| **R5** | 防重复发起 | 高 | ① 手动触发：同账号同类型已有未完成任务 → 返回已有 task_id，**不重发平台请求**；② 调度器每轮同样检查未完成任务；③ 同一 limiter 计数（笔记同步与商品同步共用，更保守） |
| **R6** | 开关可配置 | 中 | 4 个配置项（同步笔记开关/周期、同步商品开关/周期），**开关默认关**、周期默认 6 小时；阈值不写死，全部可配置 |
| **R7** | 缺值口径 | 中 | 解析不到留空/null，**不造 0、不造占位值**；进度口径 `已落库 / 平台总数`，总数缺值留空（前端显示「-」） |
| **R8** | 只读边界 | 高 | 本次三个平台操作**全部是读取**：creator 笔记列表（GET）、千帆 `goods-note/list`（GET）、千帆 `product/search_item_v2`（**只读查询 POST**）。不碰任何写接口，Cookie 全程 `[REDACTED]` |
| **R9** | 增量同步**按维度** | 高 | 全量 / 增量由 `mode` 区分（手动默认全量、调度默认增量）。增量拆四个维度分别设计：**新增**（笔记 `publish_time` 游标 / 商品 `create_time` 时间窗）、**变更**（商品 `update_time`；**笔记无 `update_time` 也无时间窗，只能全量重扫**）、**删除/下架**（**平台不返回删掉的行，两个列表均不感知**，显式声明）、**状态变更**（行内字段，upsert 自然覆盖）。详见设计 13 §17 |
| **R10** | 互动数据一律走网页版（v1.31 新增，2026-09-21） | 高 | 账号卡片的粉丝 / 关注 / 获赞**均来自网页端、走网页端接口**：取数通道一律选 **www 通道**（不再按 `sub_type` 选通道），打 PC 端接口 `/v1/user/otherinfo`。「同步数据」按钮即该取数动作。**PC 会话不可用时弹窗提示登录**（不发起同步）。**移除**「创作者平台不返回互动数据，请改用网页版登录的账号查看」文案（该归因已被真机抓包推翻）。详见设计 12 §21.4 |
| **R11** | 卡片按钮不按账号类型区分 + 千帆门禁（v1.31 新增，2026-09-21） | 高 | ① 账号卡片底部按钮**全部账号统一展示**（「同步数据」「同步笔记」「同步商品」「删除」），不再有「仅 Creator 显示」的按钮；② 「同步笔记」「同步商品」**走千帆**：千帆（ark）会话不可用（`missing`/`guest`/`expired`）时点击**不发起同步**，弹窗提示「需要千帆商家后台会话，请先补登千帆」，弹窗内可一键打开千帆续期；③ **移除「检查」按钮**（登录态探活已由进入页面/刷新自动完成）。详见设计 13 §6.1.0 |

## 三、约束

### 3.1 用户侧约束（硬约束，不可绕过）

| # | 约束 | 后果 |
|---|---|---|
| **C1** | 平台对持续翻页有风控限制 | 同步必须**有界 + 限流 + 停顿**；不允许 `while True` 全量方法（项目硬约束 C5） |
| **C2** | 用户明确要求「慢慢同步」 | 默认周期 6 小时、开关默认关；单次同步有页数上限，大账号靠多轮调度分摊 |
| **C3** | 用户明确要求「不允许重复发起相同同步任务」 | 防重是**硬指标**，不是最佳实践：数据库任务行 + 应用层查询两道 |
| **C4** | 账号 Cookie / 千帆登录态可能过期 | 同步失败时把可读原因写入任务行与绑定状态，**不清空已有数据** |

### 3.2 技术侧约束（来自现状代码与项目硬约定）

| # | 约束 | 说明 |
|---|---|---|
| **C5** | 禁止调用 SDK 的全量循环方法 | `get_all_posted_notes` / `get_user_all_notes` 会翻到 `has_more=false`，几百条笔记 = 几十次连续请求，直接触发风控。**必须单页方法 + cursor 透传** |
| **C6** | 不修改 `apis/`，只能经 `backend/app/adapters/xhs/` 中转 | 架构硬约定（`03_开发文档/01` H-6） |
| **C7** | 不碰千帆（ark 域）的**写接口** | 只读同步；`search_item_v2` 是查询 POST，不是写操作 |
| **C8** | 不影响一期任何现有功能 | `/xhs/qianfan/items`（实时商品列表，不落库）行为不变；本需求新增独立同步链路，不改它 |
| **C9** | 任务跟踪复用 `tasks` 表，不新建任务表 | tasks 表已被一期发布链路与无流量清理使用，task_type 区分；payload 查询足够（`no_traffic_cleanup_service._running_cleanup` 范式） |
| **C10** | 改前端必须 `vite build` | 8000 端口吃 `frontend/dist` 构建产物（AGENTS.md §2） |

## 七、非功能需求

| 类别 | 要求 |
|---|---|
| **风控（最高优先）** | ① 有界翻页（默认 3 页、上限 20）；② 按账号限流（`CrawlRateLimiter`，每分钟上限可配置）；③ 页间停顿 ≤60s；④ 超限**停本次**，已同步的保留提交，原因写入任务行；⑤ 调度器 `max_instances=1 + coalesce` 保证两轮不重叠 |
| **性能** | 手动触发接口 **立即返回**（建任务行 + 起线程），HTTP 请求不阻塞等待同步完成 |
| **错误可见性** | Cookie 失效 / 未绑定千帆 / 平台限流 → 必须给可区分的中文原因，不得静默返回空 |
| **数据真实性** | 笔记与商品数据一律来自平台；解析不到留空并标注，**禁止填 0 或占位假值** |
| **安全性** | Cookie 沿用现有加密存储；接口必须鉴权并校验账号归属（`user_id` 匹配）；日志中 Cookie 一律 `[REDACTED]` |
| **兼容** | 一期所有现有功能的行为与接口保持不变；`/xhs/qianfan/items` 不改 |
| **可观测** | 每次同步留任务行（开始/结束时间、进度、结果计数、失败原因）；调度器轮次可追溯 |

## 八、验收指标

| 指标 | 目标 |
|---|---|
| PC 账号「同步笔记」 | 笔记落 `notes` 表，条数 = 平台总数（在翻页上限内） |
| Creator 账号「同步笔记」 | 笔记落库 + 挂载商品落 `shop_note_goods`；`goods_note_total` **不被过滤后 total 污染** |
| Creator 账号「同步店铺商品」 | 商品落 `shop_products` 表，字段与平台对齐（含 `item_id`） |
| **重复发起次数** | **0**（硬指标）：同账号同类型未完成任务存在时，第二次触发返回同一 task_id 且**平台请求数 = 0** |
| 限流停本次 | 超限后立即停止，已同步条数保留，任务行有原因 |
| 平台请求数 | 单次同步 ≤ `max_pages`（默认 3）；调度器单轮每账号 1 批 |
| 未认证访问全部端点 | 100% 返回 401 |
| 跨用户访问他人账号 | 100% 返回 404 |
| Cookie 泄漏 | 日志/响应中 **0 处**明文 Cookie |
| 缺值字段 | 渲染「-」或留空，**0 处假数据** |
| 一期功能回归 | 全部通过，行为无变化（基线 316 passed） |

## 九、范围外（明确不做）

| 不做的事 | 理由 |
|---|---|
| 发布 / 删除 / 改赞等**写操作** | 只读边界，保持低风控面（本次需求全部是读取） |
| 自动批量下载全部笔记素材 | 同步只落笔记元数据与 `raw_json`；素材下载沿用既有按需下载（D3） |
| 「我的笔记」页改造 | 那是实时浏览页（需求 03，D2 不落库）；本需求落库后**不自动改它的渲染口径**，仅在需要时本地 join |
| 逆向千帆登录 | 沿用既有「人工登录 → 导入 Cookie → 绑定」链路（D8） |
| 千帆写接口（改价 / 上下架 / 订单） | 只读边界（C7） |
| 同步历史趋势 / 时序快照 | 同步的是当前快照，不做时序存储与趋势分析 |
| 自动重试失败任务 | 失败留任务行 + 可读原因，由用户决定是否再点一次；自动重试会放大风控面 |
| 为同步新建任务表 | 复用 `tasks` 表（C9） |

## 十、决策点

### 10.1 已拍板（2026-09-19）

| # | 决策 | 结论 | 影响 |
|---|---|---|---|
| **D1** | 同步语义 | ✅ **异步任务**：接口立即返回 task_id，后台线程执行，调度器续跑。同步期间用户可离开页面 | R4；任务状态可查询；避免长连接与请求超时 |
| **D2** | 任务跟踪 | ✅ **复用 `tasks` 表**，两个 task_type：`xhs_note_sync` / `xhs_shop_goods_sync`；payload 存 `account_id` | C9；防重查询沿用 `payload->>'account_id'` 模式；不新建表 |
| **D3** | 防重口径 | ✅ **两道**：手动触发查未完成任务 → 返回已有 task_id 不重发；调度器每轮同样查 | R5 硬指标；调度器与手动触发互不重叠 |
| **D4** | 表名口径 | ✅ **沿用既有规划**：商品表用 `shop_products`（`03_数据模型设计.md` §9.3 已规划，FK 指向 `shops.id`），不另起 `shop_goods`。`shop_note_goods` / `notes` **不加列** | 避免两套真相源；`shop_products` 此前属 M2 待建，本需求**提前补齐** |
| **D4b** | `shop_products` 的主键口径 | ✅ 唯一约束 `(shop_id_fk, item_id)`，`shop_id_fk` **不允许空**（一个商品必须属于一个店铺实体） | 与既有规划一致；落库前必须能解出 `shops` 行 |
| **D5** | 「全部」的边界 | ✅ **有界的全部**：默认 3 页、上限 20 页 × 100 条 = 2000 条，覆盖一个店铺的总量级（实测 1994）。`has_more=false` / 游标 `-1` / 翻够 total 提前结束 | C1/C2；不是无界全量 |
| **D6** | 限流策略 | ✅ 笔记同步与商品同步**共用同一个 `CrawlRateLimiter`**（按账号维度） | 更保守：同一账号两类同步不会同时打满；代价是一个账号两类同步不能并行——可接受 |
| **D7** | 调度器口径 | ✅ 开关默认**关**、周期 6 小时；只扫「有待同步」的账号；`max_instances=1 + coalesce` | C2；用户要「慢慢同步」；开关关 = 不注册 job |
| **D8** | 同步过的笔记是否重复打平台 | ✅ **不跳过**：每次同步都重新翻页取平台最新值（笔记数据会变：互动数、状态） | 简单一致；成本由有界翻页控制；若将来要优化，按 `raw_json` 的 hash 做跳过层，不改本口径 |
| **D9** | 「有待同步」的判定 | ✅ 本地 `notes` 表该账号笔记数 < `profile_json.notes_count`（上次 check 刷新的平台总数）。**缺值（平台总数未知）视为待同步** | 宁可多跑一轮，不可漏；平台总数由「检查」按钮刷新（`account_service.merge_metrics_into_profile` 只写三项计数，`notes_count` 需由本需求补写） |
| **D10** | 进度推送方式 | ✅ **前端轮询**状态端点（沿用 `/users/no-traffic/cleanup/{task_id}` 范式），不引入 SSE | 与项目现状一致；改动面最小 |
