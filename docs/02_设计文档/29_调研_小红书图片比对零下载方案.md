# 调研：小红书图片比对的零下载 / 极低下载量方案

- 日期：2026-10-11（真机实测）
- 范围：千帆 `ark.xiaohongshu.com` 图片空间 + 商品链路 + `qimg.xiaohongshu.com` CDN
- 纪律：**全程只读**（GET / 只读查询 POST），未调用任何写接口；未打印任何 Cookie/token（一律 `[REDACTED]`）
- 证据来源：本地已缓存的线上 JS bundle（`.hermes/tmp/ark-bundle`、`.hermes/tmp/itemark`、`.hermes/tmp/evidence_size_qual/js`）+ 真机抓包 JSON（`.hermes/tmp/evidence_publish/*.json`、`ark_picture_api.json`、`edit_render.json`）+ 对真实 CDN 直链的实测请求

---

## 核心结论（先看这段）

> **图片空间直链 `qimg.xiaohongshu.com/material_space/<uuid>` 的 HTTP 响应头直接携带「整文件 MD5」。**
> `ETag` 在单块存储的对象上 **= 文件全文 MD5**（实测 5/5 命中），另带 `x-cos-hash-crc64ecma`（整文件 CRC64，实测 4/4 命中）与 `x-cos-meta-redimage-crc32`（整文件 CRC32，实测 4/4 命中）。
> **取头的方式根本不需要下载 body**：一次 `HEAD`（0 字节）或 `GET + Range: bytes=0-0`（1 字节）即可拿到全部指纹。
> ⇒ **「零下载（内容字节）拿到平台侧图片哈希」是可行的**，这是本次调研的答案主干。

## 逐题结论

### Q1 商品列表 / 详情接口是否下发图片 md5/sha1/size/尺寸？规格图 `skuData[].specImage` 有没有哈希字段？

**结论：不可行（平台不下发任何哈希）。** 但**尺寸/size 有下发**，且跨接口口径不一致。

证据（真机抓包逐字段核对）：

- `search_item_v2`（`/api/edith/product/search_item_v2`，只读、无签名）的 `image_descriptions[]` 每个对象键集恒为：
  `material_id / path / extension / width / height / link / size` —— **无任何哈希键**。
  实拍（`evidence_publish/reverse_lookup_target.json`）：`{material_id:"0cdc8691-…", path:"material_space/0cdc8691-…", extension:".jpeg", width:750, height:960, size:50, link:"http://qimg.xiaohongshu.com/material_space/…"}`。
- 商品**编辑页回读**（`edit_render.json`，`product/publish_render` 的 `productDetail.item`）**219 个图片对象**键集全部为：
  `extension / height / link / materialId / path / size / sourceLink / width` —— **无哈希**（`sourceLink` 只是同一 URL 的 http 变体，不是外链也不是哈希）。
- `skuData[].specImage` / `skuList[].specImage` / `skuVariantInfos[].specImage` 对象形状与上面**完全相同**（同 219 个样本口径），**无哈希字段**。
- 商品发布/存草稿提交体（`batch_create_item_body.json`、`real_save_draft_body.json`、`real_submit_video_batch_create_item.json`）里的图片对象键集：
  `key / type / name / width / height / size / extension / link / path / materialId / uploaderInfoModel / errors` —— **无哈希**。

⚠️ `size` 字段**跨接口口径不一致，不能当指纹**：
`search_item_v2` 里 `size` = **50 / 46 / 30**，而同一 material 的 CDN 实长 = **50852 / 46380 / 30106 字节** ⇒ 该处 `size` 是 **KB 取整**；
但编辑页 / 提交体里 `size` = **115712、81196**（字节）。同一字段名两种单位 ⇒ 不可用作稳定判据。

- 触发：`search_item_v2` 只需登录态 Cookie、**无需签名**；`publish_render` 需签名（只读语义但平台强制签名）。均**只读**。

### Q2 千帆是否有「以图搜图 / 图片重复检测 / 素材去重」类接口（传我方图，返回平台素材 id）？

**结论：不可行（平台不存在该接口）。**

证据：对本地缓存的全部线上 JS bundle（`ark-bundle/index.27091098.js`、`itemark/8091.31a2a571.js` 等）做端点全量枚举，共 **192 个 `/api/edith/*` 路径**（含 `/app_api/edith/*` 变体）。对该清单 grep
`image_search|search_by_image|searchByImage|similar_image|搜同款|以图搜图|图片相似|image_feature|image_embedding|duplicate 检测` 等关键词 —— **零命中**。
图片空间相关端点只有 4 个：`search_directory_manageable / get_directory / get_seller_space_usage / batch_add_directory_manageable`（无一个做内容比对）。
仓库文档（`docs/`、`AGENTS.md`、`README.md`）grep「以图搜图 / 搜同款 / 图片相似 / 比图」亦无命中（现有相似度仅指**话题↔商品的文本语义相似度**，非图像）。

补充：唯一与「duplicate」相关的平台语义是 **`DUPLICATE_NAME_CHECK`（商品标题重名检查）**（bundle `8091` 逐字：`"DUPLICATE_NAME_CHECK"===e.checkType` ⇒ `duplicatedMessage`），**是标题文本，不是图片**。

- 触发：无此接口，不适用。

### Q4 平台是否提供任何图像相似度 / 特征 / embedding 接口？

**结论：不可行（不存在）。**

证据：同 Q2 的 192 端点清单 grep `image_feature|image_embedding|feature_vector|视觉特征|embedding|perceptual|phash|感知哈希` —— **零命中**。bundle 里 23 处 `Fingerprint` 全部是**浏览器反爬指纹 SDK（xhsuba）**的字符串，与图像无关。
平台确有「以图参与推理」的接口（`getRecommendItemTitle` / `getRecommendCategory` / `predictProductProperty` 会吃 `imageUrl` 生成标题/类目/属性），但**只返回文本标签，不返回向量或相似度分**，无法用作图片比对。

- 触发：`publish_async` 的这三个 action 需签名、只读语义；但产出不可用于比对。

### Q5 商品发布/编辑页选图时，前端是否把本地图哈希一并提交？

**结论：不可行（前端不上传任何本地图哈希）。**

证据：对上传器 bundle（`itemark/9515.b067cd1d.js`、`9995.61f441c0.js`、图片空间 chunk `evidence_size_qual/js/5022.7c870446.js`）grep `md5|sha1|sha256|CryptoJS|SparkMD5|arrayBuffer|FileReader|readAs` 与 File 序列化代码 ——
**在 5022 / 9515（业务侧）零命中**。所有 `md5:` / `sha1` / `CryptoJS` / `Content-MD5` 命中**全部集中在 ROS/COS 上传 SDK**（`ark-bundle/index.27091098.js` 与 `itemark/8091.31a2a571.js` 内嵌的 cos-js-sdk），且是 **分块上传时对 chunk 计算 MD5**（`getFileMd5` / `getBodyMd5` / `checkByMD5`，默认 `checkByMD5:!1`），写入 `this.uploadedList[t]={etag,md5,size}` —— **用于断点续传缓存，不是提交给业务后端的字段**。

⚠️ 重要旁证：ROS **分块上传**的 ETag 带 `-N` 后缀（真机抓包原文：`"ETag":"\"0b44bb332dff2c8f9a0c52b55958b851-5\""`，5 块），**分块 ETag ≠ 全文 MD5**。这直接决定 Q8 的适用边界。

- 触发：不适用（前端不上报）。

### Q8 ⭐ 小红书 CDN 响应头是否带 ETag / Content-MD5 / crc64 / Last-Modified / Content-Length？（实测）

**结论：可行（强证据）。CDN 响应头携带整文件 MD5 + CRC64 + CRC32。零 body 下载即可获取。**

实测方法：对真实图片空间直链 `https://qimg.xiaohongshu.com/material_space/5c33d08f-a3a7-4a9d-8b89-38a3678fef83` 发 `HEAD`（0 字节）与 `GET + Range: bytes=0-0`（1 字节），并**各自重复多次**。

**实测出现的响应头（Range GET 原文，节选）**：

```
HTTP/1.1 206 Partial Content
Content-Type: image/jpeg
Content-Length: 1
ETag: "6856398f580568895b877eca7a5bee9b"
Last-Modified: Wed, 15 Jul 2026 23:23:49 GMT
x-cos-hash-crc64ecma: 11966752237503242117
x-cos-meta-redimage-crc32: 483241644
x-cos-meta-x-redimage-extend: P3:false;Hdr:false;Psnr:;Ssim:
x-cos-request-id: NmFjYWYxOWNfZTgzZjBmMWVfYWZiZV9hYWE1NTYw
Content-Range: bytes 0-0/220142
Accept-Ranges: bytes
Access-Control-Allow-Origin: *
Server: openresty
```

- **CDN 实体是腾讯云 COS**（`x-cos-*` 头、`x-cos-request-id`）。
- **`HEAD` 同样返回上述头**（含 ETag / crc64 / crc32 / Last-Modified / Content-Length），**响应体 0 字节**。前几次 HEAD 偶缺 crc64/crc32，缓存命中后稳定齐全 —— 取头时应对缺失做一次 retry。

**交叉验证（这是能否当指纹的关键）**：把 body 全文下载后本地计算，与响应头逐一比对：

| material_id | 实长(字节) | ETag == MD5(全文) | 头 crc64 == 本地CRC64 | 头 redimage-crc32 == zlib.crc32 |
|---|---|---|---|---|
| 4008a634-… | 29020 | ✅ True | ✅ True | ✅ True |
| 0b11bb4c-… | 101382 | ✅ True | ✅ True | ✅ True |
| 37b8826d-… | 88668 | ✅ True | ✅ True | ✅ True |
| 5c33d08f-… | 220142 | ✅ True | ✅ True | ✅ True |
| 1d4b8d2e-…（近期上传） | 80686 | ✅ True | ⚠ 头缺失 | ⚠ 头缺失 |

**结论：`ETag` = 未加密、单块存储对象的全文 MD5（5/5）；`x-cos-hash-crc64ecma` = 全文 CRC64（4/4 有该头的对象全命中，用 Go 反射多项式 CRC64-ECMA 复算一致）；`x-cos-meta-redimage-crc32` = 全文 CRC32（4/4 命中）。** 稳定性：同一 URL 连发 5 次，三个指纹**完全不变**。

腾讯云 COS 官方文档佐证（`cloud.tencent.com/document/product/436/7729`、`/43887`）：
> ETag `"<etag_value>"`，「此头部并不一定返回对象的 MD5 值，而是根据对象上传和加密方式而有所不同」；「如果您需要校验上传到云端的文件和本地文件的一致性，我们推荐您使用 `x-cos-hash-crc64ecma`」。

⇒ 与实测吻合，并给出**两个必须遵守的边界**（见 Q9 局限）。

- 触发：**公开直链，无需登录态、无需签名、无需 Cookie**（无 Cookie 实测 206 且头齐全）。**纯读**（HEAD/GET）。
- 附带发现（可用作存在性判据）：不存在的 uuid → **404 `{"message":"download origin failed because resource not found","code":1603005}`**。
- ⚠️ `arkgoods/<id>` 裸链（商品发布上传图）在 `qimg` 上 **404**、`ros-preview.xhscdn.com` 裸链 **403**，需**带签名的 `ros-preview` URL**（形如 `https://ros-preview.xhscdn.com/arkgoods/<id>?sign=…&t=…`）才可取。**图片空间 `material_space/<uuid>` 这条是公开无签的**，是本次可用的主路径。

### Q9 只下「头尾若干字节」（HTTP Range）能否得到稳定指纹？部分下载当弱指纹的判据与局限

**结论：部分「内容」指纹不可行（弱、易碰撞）；但通过「部分请求」拿到「全文权威哈希」完全可行 —— 这是两件事，务必分清。**

**(A) 通过 Range 拿到权威全文哈希 —— 可行（推荐，本次主方案）**
实测：`GET + Range: bytes=0-0`（**只传 1 字节**，甚至在缓存命中后 `HEAD` 0 字节）即返回 `ETag`(=全文 MD5) + `x-cos-hash-crc64ecma` + `Content-Range`(=全文长度)。
⇒ **不需要下载正文**就能得到「整文件级」的稳定指纹。请求量：每图 1 次 HEAD，约 0 字节 body。

**(B) 用「头/尾字节本身」当内容指纹 —— 不推荐（弱指纹）**
实测首 4KB / 末 4KB：
- JPEG 确为 `FFD8`(SOI) 开头、`FFD9`(EOI) 结尾；首 2KB 内含 marker 序列 `FFE0(APP0) / FFE2(APP1-EXIF) / FFDB(DQT) / FFC0(SOF0) / FFC4(DHT) / FFDA(SOS)`。
- 但这些 marker 的**参数（DQT 量化表、DHT 霍夫曼表、EXIF 缩略图、时间戳）随编码器/时间变化**，两图极易相同；`md5(head4k)`、`md5(tail4k)` 对「同源重编码」的图会不同、对「不同图」也可能偶然一致 ⇒ **既非稳定也非唯一**。
- 可实现的弱判据（仅作预筛，不可作最终判定）：
  1. 尺寸：`Content-Range` 总长 + `image_descriptions[].width/height`（Q1 有下发）；
  2. 结构：首 N 字节的 JPEG marker 序列 或 PNG `IHDR`（宽高/位深/色彩类型）+ 尾部 `IEND` 前 8 字节；
  3. 首尾各 4KB 的 `md5`。
  **局限**：会因重编码/加水印/裁剪而漏配（假阴），也会因同批次模板图而误配（假阳）⇒ 只能做候选集收敛，**最终必须回落 (A) 的 ETag/crc64**。

- 触发：Range 请求公开无签、只读；但 (A) 已足够，(B) 通常不需要。

## 落地建议（推荐路径）

1. **首选**：对图片空间直链 `https://qimg.xiaohongshu.com/material_space/<uuid>` 逐个发 **`HEAD`**，取 `ETag` 即得全文 MD5；缺失时补发一次 `GET + Range: bytes=0-0`，并取 `x-cos-hash-crc64ecma`（跨对象更可靠，COS 官方推荐）做交叉校验。指纹 = `MD5` 为主键、`CRC64` 为辅键。
2. **必守边界**（来自 Q5/Q8 + COS 文档）：
   - **`-N` 后缀的 ETag（分块上传）≠ 全文 MD5** —— 商品发布链路的 **视频** 走分块上传（真机抓到 `"…-5"`），遇到带 `-` 的 ETag **不要当 MD5 用**，改用 `x-cos-hash-crc64ecma`；
   - 服务端加密（SSE）会改写 ETag ⇒ 同样以 `crc64` 兜底；
   - 实测有个别对象**不带** `crc64`/`crc32` 头（如近期上传的 `1d4b8d2e`）⇒ 以 `ETag` 为准、缺失即降级，不臆造。
3. **`material_space/<uuid>` 是公开无签直链**（可用作主路径）；`arkgoods/<id>` 裸链 404/403，需带签字（`?sign=…&t=…`）URL，未签字时不可用 —— 商品发布上传图要拿指纹，需先用带签 URL（来自 `publish_render`/提交体里的 `link`）。
4. **不要**依赖商品接口下发字段做精确比对：`size` 跨接口单位不一致（KB vs 字节），且无任何哈希。
5. **不要**用「头尾 4KB 内容 md5」当最终判据：只看作候选预筛，最终一律回落到 ETag/CRC64。

## 未决 / 需进一步实测

- `arkgoods/<id>` 的**带签 URL** 是否能稳定 `HEAD` 出 ETag（本次只验证了裸链 404/403）—— 令牌时效内可补测。
- 分块上传的对象是否有任一头部等价于全文 MD5（本次仅证 `-N` ETag 非全文 MD5；`crc64` 在 head 请求下对分块对象是否齐全未测）。
- 千万级扫描的**限速策略**（公开 CDN 高频访问的软风控阈值）未测，落地时应加并发上限与退避。
