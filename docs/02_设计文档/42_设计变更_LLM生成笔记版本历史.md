# 42 · 设计变更：LLM 生成笔记的版本历史与局部重生成

> **状态**：已实现（2026-10-17）
> **来源**：用户口径（逐字）
>
> > 「千帆生成的笔记不存，LLM 生成笔记记录，且还有一个问题，比如基于指定生成的某一版本，
> >   用户只想重新生成正文或只重新配置生成图片」
>
> **关联**：设计 41（大模型生成商品笔记）、设计 17 §7.4（LLM 生成链路）

---

## 1. 问题（改造前实测）

| 现象 | 实测证据 |
|---|---|
| 生成历史**看不到** | `generation_records` 只有 2 行、**全是失败**；3 篇 `local_generated` 笔记都**无生成记录可追溯** |
| 溯源**断了** | `note_generation_links` **0 行**（且表里**没有**指向生成记录的列） |
| 同商品多次生成 ⇒ 只剩最后一版 | 每次生成覆盖式落一篇 `notes`，前几版**无处可查** |
| 无法「只改一半」 | 链路只有「整篇重新生成」一个入口 |

## 2. 决策（回答两个开放问题）

| 问题 | 决定 | 理由 |
|---|---|---|
| 千帆生成的笔记要不要存 | **不存** | 平台侧生成不返回提示词/模型参数，存了也是「参数未知」的空壳；混进同一张表会让「缺值」变成常态噪音 |
| LLM 生成要不要记录 | **要，且是版本历史** | 用户会生成多次挑一版；没有历史就无法对比、无法选回 |
| 历史版本要不要支持「回退/采用」 | **要（标记采用 + 基于某版局部重生成）** | 挑中了却不能直接用，体验是断的 |

## 3. 数据模型

### 3.1 `generation_records` 新增 5 列

| 列 | 类型 | 用途 |
|---|---|---|
| `version_no` | int，默认 1 | 同商品内的版本序号（1,2,3…） |
| `parent_record_id` | int，可空，自引用 FK | 基线版本（全量生成 ⇒ NULL） |
| `regen_scope` | varchar(16)，默认 `all` | `all` / `text` / `media` |
| `is_adopted` | bool，默认 false | 是否当前采用版 |
| `copy_requirements_json` | text，默认 `{}` | 当时的**文案要求快照** |

### 3.2 `note_generation_links` 新增 1 列

| 列 | 用途 |
|---|---|
| `generation_record_id` | **哪次生成了这篇笔记**（版本 ↔ 笔记的唯一桥） |

> ⚠️ 这一列是本次的关键修复：没有它，「只重写文案」时无法从基线记录反查它产出的笔记
> （沿用其媒体），那条路径原本是断的（实测 0 行）。

### 3.3 两条不变量

1. **版本行永不覆盖** —— 生成 N 次 ⇒ N 行，历史可回溯；
2. **同商品最多一条 `is_adopted`** —— DB 层用**部分唯一索引**兜底
   （`uq_generation_records_adopted`，`WHERE is_adopted = 1`）。

> **为什么「采用」不是「最新一条」**：用户可能生成 3 版后**选回第 1 版**。
> 采用是**用户的选择**，不是时间序；用时间序会永久丢掉这个信息。

## 4. 局部重生成

### 4.1 三种范围

| `regen_scope` | 做什么 | 复用哪一半 |
|---|---|---|
| `all` | 整篇重新生成（走 `/generate-llm`） | 不复用 |
| `text` | **只重写标题/正文/话题** | **媒体沿用基线**（不烧一次出图费用） |
| `media` | **只重配图片** | **文案沿用基线**（措辞一个字不变） |

### 4.2 为什么局部重生成**落成新版本行**而不是改基线

- 改基线 = 丢历史，用户无法对比「改文案前后」；
- `notes` 行可能已被发布，改它会让本地记录与平台内容不一致（平台侧无法回滚）。

### 4.3 基线校验（同步段，400 结构化）

局部重生成**必须**给一个合格基线：

| 判据 | 失败码 |
|---|---|
| 存在且属于当前用户（不跨租户） | `LLM_RECORD_NOT_FOUND` |
| `status == success`（失败版没有可沿用的内容） | `LLM_BASELINE_NOT_SUCCESS` |
| 必须给基线（`text`/`media`） | `LLM_BASELINE_REQUIRED` |
| `regen_scope` 只能是三种 | `LLM_REGEN_SCOPE_INVALID` |

> ⚠️ **未知范围不静默按 `all`**：用户点「只重写正文」，实际整篇（含图片）都重生成了
> —— 既费钱又把他满意的图换掉，而他以为只是改了文案。

## 5. 接口（+4 端点 / +4 path）

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/xhs/product-notes/versions?shop_product_id=` | 版本历史（新→旧，**含失败版本**） |
| `GET` | `/api/xhs/product-notes/versions/{record_id}` | 单版详情（**含正文全文** + 文案要求快照） |
| `POST` | `/api/xhs/product-notes/versions/regen` | 基于某版局部重生成 |
| `POST` | `/api/xhs/product-notes/versions/{record_id}/adopt` | 标为采用版 |

**端点/路径基线**：323 ops / 277 paths → **327 ops / 281 paths**。

## 6. 踩到的坑（实测记录）

### 6.1 `alembic.ini` 指向了**另一个库**（最危险的一类静默失效）

`alembic.ini` 的 `sqlalchemy.url` 原先是
`sqlite:///./backend/app/storage/spider_xhs.db`（**1MB 空壳**），
而应用实际用 `data/spider_xhs.db`（505MB）。

后果：手动 `alembic upgrade head` **报成功**，但改的是空壳库，
应用库一行没动，而 `alembic_version` 已被推到新 head
⇒ 看上去「迁移跑过了」，表结构完全没变。

测试侧（`tests/backend/conftest.run_alembic`）一直用 `DATABASE_URL` 覆盖，
所以**从未暴露**。已修：`alembic.ini` 指向应用真库。

### 6.2 SQLite 不支持 `ALTER TABLE ADD CONSTRAINT`

直接 `op.create_foreign_key()` 会抛
`NotImplementedError: No support for ALTER of constraints in SQLite dialect`。
必须用 **batch mode**（建新表 → 拷数据 → 换名），它顺带保留数据与索引
（实测：迁移后 `generation_records` 行数、`notes` 3791 行均无损）。

### 6.3 `alembic.ini` 里的中文注释会让**应用起不来**

该文件按**平台默认编码**读（本机 GBK），中文注释触发
`UnicodeDecodeError: 'gbk' codec can't decode byte` ⇒ `Application startup failed`。
⇒ 该文件注释**只用 ASCII**。

## 9. 文案要求 vs 提示词模板：**补充关系**（2026-10-17 用户口径）

用户原话：

> 「已经有一个提示词模板与下面的各个部分的提示词以及相关的配置是否有冲突，
>   但是各个部分的提示词用户是**可选填**的，关系应是**对顶部公共模板的补充说明**」

### 9.1 层级

| | 提示词模板（顶部） | 三块提示词 + 区间/表情（下方） |
|---|---|---|
| 地位 | **主体** | **补充** |
| 必填 | 有默认模板 | **全部选填** |
| 作用 | 骨架、写法、输出格式 | 这一次的具体调整 |
| 冲突时 | — | **以补充为准**（追加段里显式声明） |

### 9.2 落地判据（`build_instruction`）

1. **全默认 ⇒ 返回空串** —— 完全按模板走，**一个字都不加**。
   （改造前是固定输出「标题 8–20 字 / 正文 30–300 字 / 话题 3–6 个 / 表情自动」，
   于是模板里写死的「正文 600–900 字」每次都被覆盖，用户看不出是哪里覆盖的 ——
   这正是用户指出的「冲突」。）
2. **只输出与默认不同的项** —— 逐项与 `CopyRequirements()` 默认值比较。
3. **三块提示词填了才算** —— 空 ⇒ 不提。
4. **追加段自称补充** —— 文案为「以下要求是在上述模板基础之上的补充，与模板冲突时以此处为准」，
   显式给出层级，模型才知道听谁。

### 9.3 实测

| 输入 | 输出 |
|---|---|
| 全默认 | `''`（空串） |
| 只填标题提示词 | 只有「标题方向：…」一条 |
| 改正文字数 500–800 + 关表情 | 只出这两条，标题/话题不提 |
| 三块都填 | 三条都在 |

## 10. 约束走**槽位**，模板不写死（2026-10-17 用户口径）

> 「字数，表情以及话题设置均有**默认值**，公共模版中应无需**固定添加固定提示词**，
>   调用大模型时需**最终拼接**」

### 10.1 改了什么

默认文本模板里原来写死：「标题 **≤20 字**」「正文 **600–900 字**」「话题给 **9 个**」
—— 与前端的字数/数量设置**两处各说一套**，改前端设置模板不认，改模板前端不认。

现在模板只写**槽位名**，数值在调用时由 `copy_requirements.build_slots()` 填：

| 槽位 | 模板里写成 | 调用时被填成 |
|---|---|---|
| `{title_length}` | 「字数 {title_length}」 | `8–20 字` |
| `{body_length}` | 「【③ 正文】{body_length}」 | `30–300 字` |
| `{topic_count}` | 「数量 {topic_count}」 | `3–6 个` |
| `{emoji_rule}` | 「表情要求：{emoji_rule}」 | `表情符号按文案调性自行决定` |
| `{copy_supplement}` | 独立一段 | 用户填的补充（空 ⇒ 空串） |

模板里**不再有任何写死的字数区间**（守卫 `test_text_template_embeds_publishable_hard_limits`
反向断言，并排除「前 4–6 字内出现」这类**位置**描述）。

### 10.2 两个函数别混

| | 用在 | 默认值下 |
|---|---|---|
| `build_slots()` | 模板**占位符** | **必须给值**（句子骨架不能残） |
| `build_instruction()` | 提示词**末尾**补充段 | **空串**（不补充就不加） |

⚠️ 曾经只加了槽位白名单与 `build_slots()`，忘了让 `render_skeleton` 的取值循环
遍历新槽位 ⇒ 占位符被替换成**空串**，句子变成「字数 ，核心搜索词必须前置」。
守卫 `test_renderer_actually_fills_them` 专咬这个。

### 10.3 种子与库的同步（`.hermes/scripts/sync_prompt_templates.py`）

播种判重是「按 `(user_id, name)` 存在就不覆盖」—— 保护用户改动的代价是
**改了种子，已播种的用户永远看不到新内容**（本轮实测：库里 26 行仍是旧骨架）。

脚本判据（**不许盲覆盖**）：

| 情况 | 处理 |
|---|---|
| 与**新种子**逐字相同 | 跳过（幂等） |
| 与**旧种子**（`git show HEAD:`）逐字相同 | 覆盖（用户没动过） |
| 两者都不同 | **跳过并报告**（用户改过） |
| 旧种子里**没有**这条 | 走**跨行指纹**：同组 ≥2 行且逐字相同 ⇒ 覆盖；否则报告不猜 |

默认 dry-run，`--apply` 才写库。本轮实测：26 行更新、0 行用户改过、0 行无法判定，
重跑幂等（0 行待更新）。

## 11. 生成改**同步等待** + 媒体清单入记录（2026-10-18 用户口径）

用户原话：

> 「配图没有展示，分析原因，是否未生成，生成异常还是其它原因，调整一下生成笔记
>   **不要放入队列中直接同步等待**，因为用户生成后应支持用户对生成后的结果部分位置
>   进行重复生成，也允许用户对生成图视频等选择性保留或重新生成补充等」

### 11.1 「配图没有展示」的真因（不是没生成）

| 事实 | 证据 |
|---|---|
| 图**确实用了** | `product_image` 来源 = 台账商品图直链；该商品 4 张图 |
| 记录里**没有任何媒体字段** | `generation_records` 原字段只有标题/正文/话题 |
| `AigcMediaAsset` 也帮不上 | 它是 **AI 生成图**的溯源表，`product_image` 分支返回 `([...], [])` —— 第二个返回值（溯源行）**恒空** |

⇒ 于是「笔记带图、记录不带图」，版本详情抽屉无从展示。

**修法**：`generation_records` 新增 `media_json`（TEXT，`[{url, local_path, sort_order, asset_type}]`），
在 `_persist_generated_note` 里写**落库时的最终清单**（不是入参 plan —— 段级失败会让实际张数少）。

### 11.2 生成改同步（`POST /generate-llm`）

| | 改造前 | 改造后 |
|---|---|---|
| 语义 | 毫秒级回执 `{status:queued}` + 轮询 | **跑完才返回**，响应体直接带结果 |
| 返回体 | `{ok, status, item_id, record_id}` | `{ok, record_id, note_id, title, body, topics, media[], copy_requirements, version_no}` |
| 失败 | 200 + 队列项 `failed` + 轮询看到 | **直接 4xx/5xx + 结构化 code** |
| 重复点 | `already_queued`（幂等） | **生成新版本**（版本号递增） |

实现：`generate_llm_note_sync()` —— 复用 `_run_one_llm_generate(item_id)`（**不重写生成逻辑**），
跑完用**新开 Session** 回读队列项终态与 `generation_records`（worker 自建连接，本请求看不到它提交的改动）。

⚠️ 队列项仍会建一条：那是**参数载体 + 审计承载**，建完立刻被当前请求线程消费掉，不是「等别人跑」。

### 11.3 批量整条退场

用户口径「**暂时不支持批量生成**」。批量求快（排队跑），单篇求可控（看到结果马上改）——
两者方向相反。20 篇串行必然超过任何 HTTP 超时，所以不是「改成同步批量」，而是**退场**：

* 端点 `POST /batch-generate-llm` → `include_in_schema=False` + **410 墓碑**（`LLM_BATCH_GENERATE_GONE`）；
* 前端商品列表「批量生成智能笔记」按钮删除。

### 11.4 话题恒为 0（同一轮实测发现）

模型返回的键是 `['body','cover_text','tags','title','titles']`，**`tags: []` 恒空**。

1. 原代码只读 `parsed.get("tags")`，而模板输出契约写的是 `topics` ⇒ **两边都对不上**；
2. 改成两个键都收（`topics or tags`）后仍为 0 ⇒ 模型**稳定不生成话题**；
3. 提示词里加「必须给满、不许留空数组」也无效（模型侧固执）。

⇒ **兜底派生** `derive_topics_fallback()`：按**商品类目路径**（`住宅家具 / 桌类 / 梳妆台/桌`
⇒ `梳妆台`、`桌类`、`住宅家具`）+ 标题里**出现过的**类目词补齐，标记 `topics_derived=True`。

⚠️ 反例记录：第一版按「标题尾部截 2–4 字」派生，得到 `办公` / `+办公` / `妆+办公` ——
这些不是话题，是句子碎片。**截片段这条路整条废弃**，只收类目词。
