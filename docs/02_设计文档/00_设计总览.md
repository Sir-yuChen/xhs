## 2. 十条关键设计决策

这十条是本项目设计的骨架，任何改代码前必须理解。

| # | 决策 | 理由 | 详见 |
|---|---|---|---|
| **D-1** | 单体 + 严格分层（前端 SPA → API → Service → Adapter → SDK） | 单机自部署、小时级中低频负载，微服务是过度设计 | `02` |
| **D-2** | **`apis/` 禁止直接改**，上层必须经 `backend/app/adapters/` 中转 | 隔离逆向代码的变更影响面，SDK 可独立复用 | `02` `09` |
| **D-3** | 签名算法**唯一实现**在 `xhs_utils/**/js/`，Python 只做调用与校验 | 避免双份实现漂移；Node 侧是唯一事实源 | `09` |
| **D-4** | 签名器与业务域**解耦**：`run_signer(api, data)` 只吃 path + body，host 不参与 | 接新的业务域（如千帆）只需加配置，不需要重新逆向 | `09` |
| **D-5** | 平台身份用 `XHSPlatformConfig` 表达，多业务域 = 多实例 | 已验证可扩展（PC / Creator 两实例共存） | `09` |
| **D-6** | Cookie **不覆盖写**，按版本追加 + Fernet 加密 | 可回溯、可回滚；账号失效时可对比历史版本 | `03` `11` |
| **D-7** | 全项目时区统一 `shanghai_now()`，禁裸 `datetime.now()` | 避免混时区导致排期错乱（曾有 UTC 存量数据迁移） | `02` `03` |
| **D-8** | **能力驱动而非类型分支**：逻辑只读运行时探测出的 `capabilities`，不读 `xxx_type` | 类型→能力的映射是猜的，写死会让错误扩散到前后端与调度三层 | `08` |
| **D-9** | 排期用 `scheduled_at` 落库 + 定时补跑，**不用执行侧 sleep** | 进程崩溃不丢任务，且天然幂等 | `07` `08` |
| **D-10** | 发布前必须有**幂等键**与串行约束 | 发布是写操作，不可撤销 | `07` |

## 4. AI 发散：功能是否可完善（图片第 5 条要求）

以下是通读现有实现后，**指出现有功能可被完善的点**。分三档：值得做、可选、慎做。

### 4.1 值得做（投入产出比高）

| # | 可完善点 | 现状 | 建议 | 理由 |
|---|---|---|---|---|
| **E1** | **发布幂等键** | 现有 `publish_jobs` 靠状态机 + 定时补跑防重复，但**无数据库级唯一约束**；`scheduler_service.py:181` 的补跑在多副本下会重复执行 | 给 `publish_jobs` 加 `idempotency_key` 唯一索引 | 发布不可逆，重复发布是最高级别事故；DB 约束是唯一可靠防线 | ✅ **已落地（2026-09-18，T-103 迁移 `b1e4d7c9a2f3`）**；多副本部分仍待 T-108 |
| **E2** | **订阅型开关落库** | `scheduler.enabled`、`frontend.serve_static` 只能改 YAML 或环境变量，**UI 无入口**，改动需重启 | 引入 `system_settings` 表 + 管理端开关面板 | 图片要求「开关与配置要在后台设计系统管理功能」。当前已识别的 12 个开关里，**只有 6 个有 UI** |
| **E3** | **多副本调度锁** | `BackgroundScheduler` 与 FastAPI 同进程，`max_instances=1` 只约束单进程内 | 用 DB 行锁 / advisory lock 做分布式互斥 | 一旦水平扩容或多 worker，定时发布会重复。⚠️ **必须复用 T-103 的幂等键语义**（键非空 ⇔ 占用态），不得另起判断口径 |
| **E4** | **`sub_type` 收敛为枚举** | 13 处后端 + 7 处前端硬编码，其中 2 处是 `else` 兜底（`api/accounts.py:57-58`、`scheduler_service.py:652`），新类型会**静默走错分支** | 改显式枚举 + `raise` + 统一 helper | 比抛异常更危险的是不报错 | ✅ **已落地（2026-09-18，T-102；`core/account_types.py`）** |
| **E5** | **mock 端点接线** | **原有 4 个 mock 端点**（`xhs/pc` 的 search/users、users/notes、homefeed×2）。其中 `users/notes` 已在本次「我的笔记」需求中**原地替换为真实实现**，**剩 3 个** mock | 按同一套 adapter 包装法逐个接线 | 有现成实现却返回假数据，属于「半成品」而非「未开发」 |
| **E6** | **前端死代码清理** | `drafts-page.tsx`（1250 行）与 `rewrite-page.tsx` 都导出 `XhsDraftsPage`，router 只引后者；`monitoring-page.tsx` 被 import 但无 `<Route>` | 删除重复页 / 挂载孤儿页 | 两个同名导出极易改错文件 |

### 4.2 可选

| # | 可完善点 | 说明 |
|---|---|---|
| E7 | 账号健康检查的批量探活 | 目前逐个调用，账号数放大后应支持批量 + 分级降频 |
| E8 | 采集结果增量去重 | `notes` 表按 `note_id` 索引，但入库时未见显式去重策略 |
| E9 | 通知聚合 | 大量账号同时过期会产生通知风暴，可按来源聚合 |
| E10 | `crawl_interval_minutes` 死配置 | `monitoring_targets` 有此字段但定时刷新未读取，要么接线要么删除 |
| E11 | AI Prompt 版本化 | 商品笔记 Prompt 落地时一并给普通改写 Prompt 加 `prompt_version` |

### 4.3 慎做（明确记录不建议的理由）

| # | 想法 | 不建议的理由 |
|---|---|---|
| X1 | 拆成微服务 | 单机自部署 + 低频负载，拆了只增加运维成本 |
| X2 | 引入消息队列 | APScheduler + DB 状态机已能覆盖，MQ 是新增单点 |
| X3 | 无头浏览器替换自维护签名 | **v1 已完整评估并否决**，理由见 ADR-001。核心：本项目是小时级中低频负载，浏览器方案的收益（失效自恢复）与「新增一个重型运行时」的代价相抵 |
| X4 | AI 重绘商品主图 | 商品失真 → 货不对板 → 售后与违规，风险高于收益 |
| X5 | 跨账号同文分发 | 触发内容去重降权 |
