> 口径：`<平台或域>:<资源>:<动作>`；**每页必有一条查看码**，只读页也不例外（见下方铁律）

> ⚠️ **「只读」≠「免授权」（用户 2026-10-23 口径）**
> **每一个页面都必须有一条查看码**（`<域>:<资源>:view`），包括纯只读页（数据中心 / 内容洞察 / 商品洞察 / 总览 / 用量看板）。
> 只读页没有变更按钮，但它有「看得见什么」—— 那同样是权限。
> 判据：`GET` 类端点**一律**挂 `<域>:<资源>:view`，不许因为「它不改数据」就留空。
> 落地：`menus` 每个 C 行必带 `perms`；`role_menus` 没授这条 C 行 ⇒ 侧栏不显示该页；直接敲 URL ⇒ `/403`。

# 模块一 · 用户管理（`/system/users`）

**模块职责**：系统登录账号的增删改查 + 状态流转（待审 → 正常 / 停用）+ 单角色分配 + 安全操作（重置密码 / 强制下线）。
**数据来源**：`users`（26 行 · +5 列）· `roles`（2 行）· `api_logs`（审计）
**页面形态**：三段式（搜索区固定 / 表体内滚 / 分页固定）· 权限码前缀 `system:user:`

## 1.1 权限码与端点对照

| # | 按钮 | 权限码 | 端点 | 归属校验 |
|---|---|---|---|---|
| 1 | 进页 / 查询 / 翻页 / 看详情 | `system:user:view` | `GET /api/system/users` | 仅登录 |
| 2 | 新建用户 | `system:user:create` | `POST /api/system/users` | 仅登录 |
| 3 | 编辑 | `system:user:edit` | `PUT /api/system/users/{id}` | 仅登录 |
| 4 | 分配角色 | `system:user:edit` | `PUT /api/system/users/{id}`（`role` 字段） | 仅登录 |
| 5 | 启用/停用（行内 Switch） | `system:user:edit` | `PUT /api/system/users/{id}` | 仅登录 |
| 6 | 重置密码 | `system:user:resetPassword` | `POST /api/system/users/{id}/reset-password` | 仅登录 |
| 7 | 强制下线 | `system:user:forceLogout` | `POST /api/system/users/{id}/force-logout` | 仅登录 |
| 8 | 通过审核（`pending` 行） | `system:user:approve` | `POST /api/system/users/{id}/approve` | 仅登录 |
| 9 | 删除 | `system:user:delete` | `DELETE /api/system/users/{id}` | 仅登录 |
| 10 | 刷新/重置筛选/导出 CSV/列设置 | `system:user:view` | — / `GET /system/users?export=csv` | — |

> 合计 **10 个权限位**（14 个可见按钮实例，其中 4 个复用查询码）。

## 1.2 逐个按钮逻辑

### B1 · 进入页面 / 查询

**前端**
```
mount → 若无 system:user:view ⇒ <Navigate to="/403">
     → GET /api/system/users?page=1&page_size=20&username=&email=&status=&role=
     → 表格渲染 13 列：ID / 用户名 / 姓名 / 角色 / 邮箱 / 手机号 / 状态（含「默认口令」Tag）
                       / 在线 Tag / 最后登录 / 创建时间 / 操作列
     → WaitMask 覆盖等待，标题「正在加载用户列表」
     → 空结果 ⇒ Empty + 「没有匹配的用户」
```
**后端** `GET /system/users`
```
1  require_perm("system:user:view")
2  分页（page 1..N，page_size 1..100 默认 20）
3  筛选：username/email 模糊(ILIKE)、status/role 精确
4  排序：id DESC（新建在最前）
5  每行派生：online = (login_sessions 最近 confirmed 且未过期) ∧ (token_version 未变)
6  响应 {items:[UserResp], total, page, page_size}
```
**失败面**：403 `PERMISSION_DENIED` ⇒ 前端不吞，气泡显示码；后端 500 ⇒ 原样上抛 detail。

---

### B2 · 新建用户 `system:user:create`

**前端**
```
点「＋新建用户」→ AppModal(md) 表单：用户名* / 密码* / 姓名 / 邮箱 / 手机号 / 角色(默认 user) / 状态(默认 normal)
  校验：用户名 3-80；密码 ≥6；邮箱 email 格式
  提交 → POST /api/system/users  → 成功后：关弹窗 + 列表刷新 + toast「已创建」
  409 EMAIL_TAKEN / USERNAME_TAKEN ⇒ 表单字段级红字（不整页报错）
```
**后端**
```
1  require_perm("system:user:create")
2  唯一性：username / email（email 可空但非空必须唯一）
3  hash_password（PBKDF2-SHA256 26 万轮）
4  插 users 行：status='normal'（管理员建号不需审核）、must_change_password=1（要求首登改密）
5  role 校验：code 必须存在于 roles 且 status='normal'
6  token_version=0
```
**边界**：管理员不能建 `admin` 角色用户？→ **可以**（admin 也是人，需要备份管理员）；但建完系统里 admin 数 +1，触发 P6 保护逻辑检查。

> 📌 **B9 定稿（2026-10-23 用户「按照推荐」）**：`users` **+1 列 `deleted_at`**，采用**软删**。
> 理由：① 与 `platform_accounts.deleted_at` 同一口径；② 能回答「这人是被删了还是改过名」；
> ③ 49 张表按 `user_id` 关联，物理删会留下孤儿行或撞 FK。

---

### B3 · 编辑 `system:user:edit`

**前端**：编辑态**禁改** 用户名 / 邮箱 / 角色 / 身份类型（与 dataPanel 一致）；只能改 姓名 / 手机号 / 状态。
```
行内「编辑」→ AppModal(md) 回填 → PUT /api/system/users/{id} {real_name?, phone?, status?}
成功 ⇒ 刷新行（不整表刷新）
409 CANNOT_MODIFY_SELF（改自己角色）⇒ 按钮本就 disabled + title 说明
```
**后端**
```
1  require_perm("system:user:edit")
2  目标存在性（404 USER_NOT_FOUND）
3  P7：target.id == current.id 且改 role/status ⇒ 409 CANNOT_MODIFY_SELF
4  改 status='disabled' ⇒ token_version += 1（立即踢下线，不是等令牌过期）
5  P6：若目标是 admin 且改成 disabled ⇒ 检查剩余 admin ≥1，否则 409 LAST_ADMIN_PROTECTED
6  role 变更：校验 code 存在 + P6（把唯一 admin 降级）
```
**为什么禁用这几项**：用户名/邮箱是登录凭据（改了等于换账号）；角色走独立入口是为了让「谁能改角色」有日志可追。

---

### B4 · 分配角色 `system:user:edit`

**前端**：`Checkbox.Group`（非 Tree）。过滤规则：`role.status !== 'normal'` 不显示；`admin` 角色只对 `role==='admin'` 的用户显示。
```
勾选 → PUT /api/system/users/{id} { role }  → toast「角色已更新」
```
**后端**
```
1  require_perm("system:user:edit")
2  P6：若原角色是 admin 且新角色不是 ⇒ 剩余 admin ≥1 校验
3  P7：不能改自己的角色
4  改成功后 token_version += 1（权限变了，旧令牌的权限快照必须作废）
```
> ⚠️ 本项目是**单角色**（`users.role` 一列），不是 dataPanel 的多对多。UI 用单选（Radio）比 Checkbox 更诚实 —— **以单选为准**。

---

### B5 · 启用/停用（行内 Switch）`system:user:edit`

```
Switch onChange → PUT {status:'normal'|'disabled'} → 成功刷新行
禁用态：目标是自己 ⇒ disabled + title「不能停用自己」
      目标是最后一个正常 admin ⇒ disabled + title「至少需要保留一个可用管理员」
```

---

### B6 · 重置密码 `system:user:resetPassword`

**前端**：AppModal(sm) · 新密码* + 确认密码* · 前端校验 min6 + 两次一致（实测预览已验）。
```
确定 → POST /api/system/users/{id}/reset-password {new_password}
     → 成功后强制提示：「该用户所有设备已下线」
```
**后端**
```
1  require_perm("system:user:resetPassword")
2  P7 不适用（可以重置自己的密码走 /auth/change-password）
3  hash_password → 写 password_hash
4  token_version += 1（撤销全部旧令牌）
5  must_change_password = 1（被重置的人也要求首登改密）
```

---

### B7 · 强制下线 `system:user:forceLogout`

```
点「强制下线」→ Modal.confirm「该用户所有设备立即退出，确定？」
  → POST /api/system/users/{id}/force-logout
  → 后端 token_version += 1
  → 该用户下一次任意请求 401 ⇒ 前端拦截器 refresh 也 401 ⇒ 清令牌跳登录
只对 online=true 的行显示该按钮（离线的人没什么可踢的）
```

---

### B8 · 通过审核 `system:user:approve`（只在 `status=pending` 行显示）

```
行内绿色「通过审核」→ POST /api/system/users/{id}/approve
后端：status: pending → normal，must_change_password=1（注册者自己设的密码，不强制改）
      若拒绝：DELETE（即「拒绝」按钮复用删除码）
```

---

### B9 · 删除 `system:user:delete`

```
点「删除」→ Modal.confirm「确定删除用户「xxx」？
该用户的登录凭据立即失效，业务数据保留但不再可见。」
  → DELETE /api/system/users/{id}
后端（软删，B9 定稿）：
1  require_perm("system:user:delete")
2  P7：不能删自己 ⇒ 409 CANNOT_DELETE_SELF
3  P6：删的是正常 admin ⇒ 剩余正常 admin ≥1，否则 409 LAST_ADMIN_PROTECTED
4  UPDATE users SET deleted_at=now(), status='disabled', token_version=token_version+1
5  **不删业务数据**：notes / platform_accounts / tasks 等行原样保留（`user_id` 指向软删行）
6  所有查询（登录 / 列表 / 归属校验）统一加 `User.deleted_at IS NULL`
```

**软删后的一致性要求（三条必须同时成立，缺一不可）**

| # | 判据 | 落点 |
|---|---|---|
| 1 | 登录时 `deleted_at IS NOT NULL` ⇒ 400 `USER_NOT_FOUND`（不透露「存在但已删」） | `auth.py::login` |
| 2 | 用户名/邮箱**唯一索引不排除软删行** ⇒ 删掉的人名不能再注册（防冒名顶替他人历史数据） | 现有唯一约束不变，`create` 查重也不排除软删行 |
| 3 | 用户列表默认 `WHERE deleted_at IS NULL`，勾「显示已删除」才查全 | `/system/users` 加 `include_deleted` 参数 |

**为什么不是物理删**：`api_logs`（70,325 行）/ `notes`（3,790）/ `platform_accounts` 都用 `user_id` 指向用户。
物理删会让这些行**指向一个不存在的 ID**（SQLite FK 若 ON 就报错，若 OFF 就是脏数据）；
软删让「历史是谁做的」永远可查 —— 这一条对审计页有直接价值。

|---|---|---|---|
| 1 | 进页 / 列表 / 查看已授权 | `system:role:view` | `GET /api/system/roles` · `GET /roles/{id}/menus` |
| 2 | 新建角色 | `system:role:create` | `POST /api/system/roles` |
| 3 | 编辑（名称/描述/排序） | `system:role:edit` | `PUT /api/system/roles/{id}` |
| 4 | 启用/停用 | `system:role:edit` | `PUT /api/system/roles/{id}` |
| 5 | 删除 | `system:role:delete` | `DELETE /api/system/roles/{id}` |
| 6 | 分配菜单 · 打开 | `system:role:view` | `GET /roles/{id}/menus` |

## 2.2 按钮逻辑要点

### B-角色-新建/编辑
```
code：小写字母数字下划线，唯一；**编辑态禁改**（disabled）
内置角色 is_system=1 ⇒ 名称可改？→ **不可改 code、不可停用、不可删**；名称/描述/排序**可改**（dataPanel 的坑：UpdateRole 漏了 is_system 拦截，XHS 补上）
```
**后端 `PUT /roles/{id}`**
```
1 require_perm("system:role:edit")
2 role.is_system=1 ⇒ 禁改 code（422）、禁改 status（409 ROLE_SYSTEM_PROTECTED）
3 名称非空、sort 数字
```

### B-角色-删除
```
点删除 → 确认 → DELETE /roles/{id}
后端：
1 is_system=1 ⇒ 409 ROLE_SYSTEM_PROTECTED（内置不可删）
2 有用户占用（SELECT COUNT(*) FROM users WHERE role=code > 0）⇒ 409 ROLE_IN_USE
3 事务删 roles 行（role_menus 由 FK CASCADE 自动清）
4 无需清 token_version（没人用这个角色）
```

### B-角色-分配菜单（Tree）★核心
```
打开 → GET /roles/{id}/menus → 返回 menu_ids
     → 前端取「checked」+ 需要补「半选父级」：
        回填 checkedKeys = 返回的 ids
        保存时提交 = checkedKeys ∪ halfCheckedKeys   ← dataPanel 的坑，XHS 必须补
     → Tree checkable + checkStrictly={false}（父子联动）
     → 显示 F 行（按钮）作为叶子：标签后带权限码灰色小字
保存 → PUT /roles/{id}/menus {menu_ids:[...]}
```
**后端 `PUT /roles/{id}/menus`**
```
1 require_perm("system:role:assignMenu")
2 role.code='admin' ⇒ 403 ROLE_ADMIN_IMMUTABLE（admin 权限是代码派生全量，改授权没意义）
3 事务：DELETE role_menus WHERE role_id=? → 批量 INSERT
4 校验 menu_ids 全部存在（否则 422）
5 **失效受影响用户的权限缓存**：该角色下所有用户 token_version += 1
   （⚠️ 这会让这些人掉线 —— 与「改授权立即生效」的代价，见 46 §4.2 链路 B）
```

### B-角色-管理用户
```
打开 → GET /roles/{id}/users → 已分配列表（表格 + 移除按钮）
     → 「＋添加用户」→ 子弹窗（邮箱精确搜索 + 勾选）
保存 → PUT /roles/{id}/users {user_ids:[...]}
后端：对比差异 → 增的写 users.role=code（单角色，覆盖），删的置回 'user'
      每个变动用户 token_version += 1
P6：若把某 admin 从 admin 角色移走 ⇒ 剩余 admin ≥1
```

# 模块三 · 菜单管理（`/system/menus`）

**职责**：菜单树（M/C/F）+ 权限码维护 + **平台启停**（抖音/闲鱼接入）+ 排序。
**数据**：`menus`（≈205 行种子）· `role_menus`

## 3.1 权限码与端点

| # | 按钮 | 权限码 | 端点 |
|---|---|---|---|
| 1 | 进页 / 树表 / 搜索 / 预览详情 | `system:menu:view` | `GET /api/system/menus/tree` · `GET /menus/{id}` |
| 2 | 新增菜单 | `system:menu:create` | `POST /api/system/menus` |
| 3 | 编辑 | `system:menu:edit` | `PUT /api/system/menus/{id}` |
| 4 | **启用/停用（行内 Switch）** | `system:menu:edit` | `PUT /menu/{id}` |
| 5 | 拖拽排序 | `system:menu:edit` | `PUT /menus/reorder` |
| 6 | 删除 | `system:menu:delete` | `DELETE /api/system/menus/{id}` |

## 3.2 按钮逻辑

### B-菜单-新增/编辑（12 字段）
```
上级菜单（TreeSelect，可空=顶级）
菜单类型 M/C/F ← 联动：
   M：只填 名称/图标/排序/可见/状态（不填 path/perms）
   C：必填 path + perms
   F：只填 perms（必须挂在 C 行下，否则 422）
名称* / 权限标识 / 路由地址 / 组件路径(预留) / 图标 / 排序 / 是否可见 / 状态
```
**后端 `POST /menus` 校验链**
```
1 perms 非空 ⇒ 全局唯一（409 PERMS_DUPLICATED）
2 path 非空 ⇒ 全局唯一（409 PATH_DUPLICATED）
3 menu_type='F' ⇒ parent 必须存在且 parent.menu_type='C'（422 F_MUST_UNDER_C）
4 menu_type='C' ∧ parent_id=0 ⇒ workspace 必填（422 WORKSPACE_REQUIRED）
5 menu_type='M' ⇒ path/perms 必须为空（422 M_HAS_PATH）
6 perms 格式正则 ^[a-z]+:[a-zA-Z]+(:[a-zA-Z0-9]+)?$（422 PERMS_FORMAT）
```

### B-菜单-启用/停用 ★（抖音/闲鱼接入开关）
```
行内 Switch → PUT /menus/{id} {status:'normal'|'disabled'}
后端：
1 require_perm("system:menu:edit")
2 **不静默级联**：停 C 行不改其 F 子行状态（启用父级即恢复）
3 生效判据：build_user_menus 只下发 status='normal' 的行
   ⇒ 停 M 行 ⇒ 其下 C 行**也不下发**（因为祖先链断了）
4 **清缓存**：该行所属 workspace 下所有用户的权限缓存失效
   实现：token_version += 1 太粗暴（会踢全站）⇒ 改为 invalidate(workspace) 只清内存缓存，
        不碰 token_version（菜单变更不改变「能做什么」，只改变「看得见什么」）
```
> ⚠️ **这一条是设计修订**：46 §2.3 曾写「授权变更 ⇒ token_version+1」。
> 细化为：**授权（role_menus）变更 ⇒ 踢**；**菜单状态（status）变更 ⇒ 只清缓存不踢**。
> 理由：菜单启停不该让用户掉线（尤其平台接入是低频但全站的操作）。

### B-菜单-删除
```
点删除 → AppModal 必须**输入菜单名称** → 确认按钮才可用
后端：
1 require_perm("system:menu:delete")
2 有子节点 ⇒ 409 MENU_HAS_CHILDREN（不级联删）
3 被 role_menus 引用 ⇒ 409 MENU_IN_USE
4 通过 ⇒ 物理删
```

### B-菜单-拖拽排序
```
TreeTable 拖拽 → 收集受影响行的 (id, sort_order) → PUT /menus/reorder {items:[{id,sort_order}]}
后端：事务批量 UPDATE（只改 sort_order，不改 parent_id —— 跨父拖拽本轮不做，避免形成环）
```
