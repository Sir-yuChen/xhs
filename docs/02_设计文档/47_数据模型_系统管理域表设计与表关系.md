## 2. 新增表逐字段设计

### 2.1 `menus` —— 菜单与权限码同表（M 目录 / C 菜单 / F 按钮）

| # | 列 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|---|
| 1 | `id` | INTEGER PK | 否 | autoincrement | — |
| 2 | `parent_id` | INTEGER | 否 | `0` | `0` = 根。**不建外键**（自引用树 + 删除策略是「有子节点即拒」，用应用层保证；建外键会让级联语义与 P8 冲突） |
| 3 | `name` | VARCHAR(100) | 否 | — | 菜单名 |
| 4 | `menu_type` | VARCHAR(1) | 否 | `'C'` | `M` 目录 / `C` 菜单 / `F` 按钮 |
| 5 | `path` | VARCHAR(200) | 否 | `''` | 路由路径。**仅 `C` 行必填**，且必须与 `router.tsx` 登记一致 |
| 6 | `component` | VARCHAR(200) | 否 | `''` | 预留（XHS 不做动态 import，见设计 46 D5） |
| 7 | `perms` | VARCHAR(120) | 否 | `''` | 权限码 `<平台或域>:<资源>:<动作>`。**非空即全局唯一** |
| 8 | `icon` | VARCHAR(64) | 否 | `''` | antd 图标名（前端 `lib/menu.ts::ICONS` 查表，查不到用默认） |
| 9 | `workspace` | VARCHAR(32) | 否 | `''` | **仅根 `C` 行有值**：`xhs` / `douyin` / `xianyu` / `ai` / `system` |
| 10 | `sort_order` | INTEGER | 否 | `0` | 同级排序 |
| 11 | `is_visible` | BOOLEAN | 否 | `1` | 隐藏 = 不进侧栏，但权限码仍生效（可从页面内跳转） |
| 12 | `status` | VARCHAR(16) | 否 | `'normal'` | `normal` / `disabled`（**平台接入开关**，见 §4.2） |
| 13 | `created_at` | DATETIME | 否 | now | — |
| 14 | `updated_at` | DATETIME | 否 | now | — |

**索引 / 约束**

```sql
CREATE UNIQUE INDEX uq_menus_perms ON menus(perms) WHERE perms <> '';   -- 部分唯一：M 行 perms 为空互不冲突
CREATE UNIQUE INDEX uq_menus_path  ON menus(path)  WHERE path  <> '';   -- 同一路由不能挂两个菜单
CREATE INDEX        ix_menus_parent     ON menus(parent_id);
CREATE INDEX        ix_menus_workspace  ON menus(workspace);
```

**为什么 `parent_id` 不建外键**（这是个要解释的决定）：

| 选项 | 后果 |
|---|---|
| 建 `FOREIGN KEY(parent_id) REFERENCES menus(id)` | 删除父节点时要么 `RESTRICT`（与 `F` 行的存在冲突、每次删前手动清），要么 `CASCADE`（正好与 P8「有子节点即拒」相反） |
| **不建，应用层守（本设计）** | 删除前显式查 `has_children` ⇒ 409；树构建在服务层；**但**要有一条守卫测试断言「库里不存在孤儿 `parent_id`」 |

> 守卫：`test_no_orphan_menu_parent` —— 全表断言 `parent_id=0 OR EXISTS(SELECT 1 FROM menus WHERE id=parent_id)`。

### 2.2 `roles` —— 角色

| # | 列 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|---|
| 1 | `id` | INTEGER PK | 否 | auto | — |
| 2 | `name` | VARCHAR(64) | 否 | — | 显示名 |
| 3 | `code` | VARCHAR(32) | 否 | — | **唯一**。小写字母数字下划线；内置 `admin` / `user` |
| 4 | `description` | VARCHAR(255) | 否 | `''` | — |
| 5 | `is_system` | BOOLEAN | 否 | `0` | 内置角色：**禁删 / 禁停 / 禁改 code / 禁改授权** |
| 6 | `status` | VARCHAR(16) | 否 | `'normal'` | `normal` / `disabled`（内置恒 `normal`） |
| 7 | `sort_order` | INTEGER | 否 | `0` | — |
| 8 | `created_at` / 9 `updated_at` | DATETIME | 否 | now | — |

**约束**：`UNIQUE(code)`；`CHECK(is_system=0 OR status='normal')`（内置必须启用 —— 用应用层守，SQLite 的 CHECK 加在 migrate 里也行）。
**种子**：仅 2 行 —— `(超级管理员, admin, is_system=1)`、`(普通用户, user, is_system=1)`。
**不做**：dataPanel 的 `operator` / `finance` / `viewer` 三个种子角色（用户口径「默认一个 admin」；要就给用户自建）。

### 2.3 `role_menus` —— 角色 ↔ 菜单授权（多对多）

| # | 列 | 类型 | 说明 |
|---|---|---|---|
| 1 | `id` | INTEGER PK | — |
| 2 | `role_id` | INTEGER | **外键** → `roles.id`（`ON DELETE CASCADE`：删角色时自动清授权行，这是唯一允许的级联） |
| 3 | `menu_id` | INTEGER | **外键** → `menus.id`（`ON DELETE RESTRICT`：有授权引用的菜单不许删 ⇒ 与 P8 一致） |

**约束**：`UNIQUE(role_id, menu_id)`；`INDEX(menu_id)`（反查「哪些角色引用了这个菜单」）。
**授权粒度**：**逐菜单行**，`F` 行也单独授权 ⇒ 天然支持「给某人某页的查看，但不给删除」。

### 2.4 `dict_types` / 2.5 `dict_items` —— 字典

**`dict_types`**

| # | 列 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|---|
| 1 | `id` | INTEGER PK | 否 | auto | — |
| 2 | `name` | VARCHAR(64) | 否 | — | 如「用户状态」 |
| 3 | `code` | VARCHAR(64) | 否 | — | **唯一**，如 `sys_user_status` |
| 4 | `remark` | VARCHAR(255) | 否 | `''` | — |
| 5 | `status` | VARCHAR(16) | 否 | `'normal'` | 停用 ⇒ 前端下拉为空（清缓存） |
| 6 | `created_at` / 7 `updated_at` | DATETIME | 否 | now | — |

**`dict_items`**

| # | 列 | 类型 | 空 | 默认 | 说明 |
|---|---|---|---|---|---|
| 1 | `id` | INTEGER PK | 否 | auto | — |
| 2 | `type_id` | INTEGER | 否 | — | **外键** → `dict_types.id`（`CASCADE`） |
| 3 | `type_code` | VARCHAR(64) | 否 | — | **冗余**（免 join；写入时由 `type_id` 推导，守卫断言一致） |
| 4 | `label` | VARCHAR(64) | 否 | — | 显示文本 |
| 5 | `value` | VARCHAR(64) | 否 | — | 存储值（**永远字符串**，不做 int） |
| 6 | `list_class` | VARCHAR(16) | 否 | `'default'` | antd Tag 颜色：`success`/`warning`/`danger`/`info`/`default` |
| 7 | `sort_order` | INTEGER | 否 | `0` | — |
| 8 | `status` | VARCHAR(16) | 否 | `'normal'` | — |
| 9 | `remark` | VARCHAR(255) | 否 | `''` | — |

**约束**：`UNIQUE(type_id, value)`；`INDEX(type_code)`。

> **和 dataPanel 的差异**：dataPanel 的 `t_dict_data` 有 `belong`（`system` / 平台编码）并把它放进唯一键
> `(dict_type_id, belong, value)`。XHS **不搬** —— 只有一条平台线时那是没人用的维度。
> 二期若真出现「同字典不同平台值」，按 `{prefix}_{platform}` 另开一组字典（AGENTS「平台差异用字典」的既定做法），而不是加列。

### 2.6 `users` 表 +6 列（唯一被改的既有表）

| # | 列 | 类型 | 默认 | 用途 | 是否参与索引 |

**既有列不动**：`role` 保留为**冗余快照**（权威是 `user_roles → roles.code`），`token_version` 继续承担「撤销令牌」。

## 4. 外键与删除策略（逐条）

### 4.1 新增表的外键

| 从 | 到 | 基数 | `ondelete` | 为什么 |
|---|---|---|---|---|
| `role_menus.role_id` | `roles.id` | N:1 | **CASCADE** | 删角色 ⇒ 授权行必然失去意义，一起删是对的（唯一允许的级联） |
| `role_menus.menu_id` | `menus.id` | N:1 | **RESTRICT** | 有角色引用就不许删菜单（P8 `MENU_IN_USE`）。**不能 CASCADE** —— 那样删菜单会静默收回别人的权限 |
| `dict_items.type_id` | `dict_types.id` | N:1 | **CASCADE** | 删字典类型 ⇒ 其值必然一起删（与 dataPanel 不同：dataPanel 是「有数据不许删」，XHS 选「明确同意后一起删」，因为删类型时页面会告诉你将删 N 项） |
| `menus.parent_id` | `menus.id` | 自引用 | **无外键** | 见 §2.1，用「有子节点即拒」+ 孤儿守卫替代 |

### 4.2 与既有表的关系（有没有外键？）

| 关系 | 结论 |
|---|---|
| `users` ↔ `roles` | **不建外键**，用现有 `users.role` 快照 + 新增 `user_roles`？ → **不新增 `user_roles` 表** |

> ⚠️ **这里做了一处简化，需要明确记录**：
> dataPanel 是 `t_user_role(user_uuid, role_id)` 多对多。XHS 的 `users` 表已有 `role` 单列（`admin`/`user`）。
> **本设计不引入 `user_roles` 表，保持 `users.role` 单角色**（用户口径「默认一个 admin 超级管理员」+ 只有两个内置角色）。
> 代价与边界：
> - 一个用户**只能有一个角色**；「运营 + 财务」这类叠加需求出现时才加 `user_roles`（那时是纯新增，不动现有列）；
> - `users.role` 存的是 `roles.code`，**强约束靠应用层**（写角色时校验 code 存在）+ 守卫测试断言「每个 `users.role` 都能在 `roles.code` 里找到」；
> - 于是 `roles` 与 `users` 之间是**逻辑外键**（值域外键），不是 DDL 外键。

| 表 | 关系 | 实现 |
|---|---|---|
| `users.role` → `roles.code` | 值域引用 | 应用层校验 + 守卫 `test_every_user_role_exists` |
| `dict_items.type_code` → `dict_types.code` | 冗余值域引用 | 写入时从 `type_id` 派生 + 守卫断言一致 |
| `menus.perms` ↔ 后端 `require_perm` | **不是表关系** | 启动期静默自检（P5）+ 三处一致守卫 |
| `menus.path` ↔ `router.tsx` | **不是表关系** | 守卫逐条比对（C 行 path 必须在路由表里存在） |
| `menus.workspace` ↔ `core/platforms.py` | **不是表关系** | G2：种子由平台注册表生成 + 脚本 `--check` 逐字节比对 |

### 4.3 既有 57 表**一律不动**

| 检查项 | 结论 | 判据 |
|---|---|---|
| 删列 | **零** | `users.role` 保留 |
| 改列类型 / 改约束 | **零** | `alembic` 迁移只做 `add_column` / `create_table` |
| 数据搬迁 | **零** | 存量 1 个用户的 `role='admin'` 直接沿用，不搬表 |
| 新增外键到既有表 | **零** | 新增 5 表不引用任何业务表（也就不会撞既有表的软删语义） |
| 既有表 + 列 | `users` **+6**、`system_settings` **零变化**（M8 专节：不加 `scope`） | 共 1 张表 6 列 |

## 5. 隔离维度（回答「数据归谁」）

| 维度 | 判据 | 表数 | 备注 |
|---|---|---|---|
| **按 `user_id` 隔离** | 表里有 `user_id` 列 | **49 / 57** | 越权面最大的一类；契约见 `core/deps.get_owned_active_account` |
| 按 `platform_account_id` | 有该列 | **12** | 账号级细分（笔记/商品/订单/监控/发布…） |
| 有 `platform` 列 | `platform` 字段 | **13** | 为多平台预留（值域 `xhs` / `douyin` / `xianyu`） |
| **不按用户隔离** | 系统域 | **5（新增）+ 0（既有）** | `menus` / `roles` / `role_menus` / `dict_types` / `dict_items` 是**全局配置**，由权限码而非 `user_id` 收口 |

> ⚠️ **新增的 5 张表刻意不带 `user_id`**：它们是**权限的定义**，不是「某用户的数据」。
> 若给它们加 `user_id`，就等于「每个用户有自己的一套菜单/角色」—— 那正是 `menus` 失效的开始。
> 写入权限由 `system:menu:*` / `system:role:*` / `system:dict:*` 收口，读权限由「登录 + 菜单可见性」收口。

## 8. 索引清单（性能判据）

| 表 | 索引 | 为什么必须 |
|---|---|---|
| `menus` | `uq_menus_perms`(部分) | 权限码唯一（P9） |
| `menus` | `uq_menus_path`(部分) | 一路由一菜单 |
| `menus` | `ix_menus_parent` / `ix_menus_workspace` | 树构建 + 按工作区取菜单（每次 `/auth/me`） |
| `roles` | `uq_roles_code` | code 唯一 |
| `role_menus` | `uq_role_menus` / `ix_role_menus_menu` | 授权去重 + 反查引用（P8） |
| `dict_types` | `uq_dict_types_code` | code 唯一（前端 `useDict(code)` 的键） |
| `dict_items` | `uq_dict_items`(type_id,value) / `ix_dict_items_code` | 值唯一 + 按 code 取（高频读） |
| `users` | `ix_users_status` | 登录校验 status + 用户列表筛选 |
| `users` | `uq_users_username` / `uq_users_email`（既有） | 登录唯一性（不变） |

**`/auth/me` 的查询代价**（这是唯一的高频读）：
```
1 次 users（主键）
1 次 roles（按 users.role 取 1 行）
2 次 menus（admin：全量 C 行；普通：menus ⋈ role_menus）
```
⇒ 加 **60 秒进程内缓存**（键 = `user_id + perm_ver`），授权/菜单变更时 `invalidate`。不引入新表存会话。
