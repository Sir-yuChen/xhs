# 缺陷 · `xsec_token` 过期导致商业笔记正文永远补不到

> **状态**：🟢 **已修**（2026-10-12）
> **性质**：**取数时效**缺陷（不是解析/会话/风控问题）
> **上游**：用户报障「内容库中同步的商业笔记均没有正文和只有一张媒体资源」，
> 且要求「**完全撤销你的假设，用原有实现，分析从抓包到现在什么条件变了**」。

---

## 1. 症状与排查路径（每一步都留下了实测）

| 假设 | 实测 | 结论 |
|---|---|---|
| 页面结构变了（DOM 易变） | 156 条请求里 0 条含详情 | ❌ 不是 |
| 解析器挂了 | `_parse_initial_state` 对当前 HTML **解析 OK** | ❌ 不是 |
| www 会话失效 | `/v2/user/me` 回 `nickname='观隅好物'`（API 有效） | ❌ 不是 |
| 平台改版 | 同一 URL 手工 urllib 拿到 112 KB | ❌ 不是 |
| 风控要验证码 | 一度出现过 `/website-login/captcha`，但随后稳定消失 | ⚠️ 波动，非根因 |
| **`xsec_token` 过期** | **对照实验见下** | ✅ **根因** |

### 1.1 决定性对照（同一个 note、同一个会话、同一份代码）

```
库里的【旧】token:       200  112,187B  "noteDetailMap":{}          ← 空对象
千帆列表【刚拿的新】token:  200  111,849B  "noteDetailMap":{"6ac65843…":{  ← 有内容
```

**唯一变量是 token 新旧。** 平台对过期令牌的答复**不是 4xx**，而是：

```
HTTP 200 + "noteDetailMap":{} + "errorCode":-510000
```

⇒ 从响应本身**分不出**「这条笔记没有正文」与「令牌已失效」。

## 2. 为什么旧实现永远修不好

`sync_note_from_platform` 只在**完全没令牌**时才回查：

```python
if not _note_detail_url(note):          # ← 有地址就跳过
    _backfill_detail_ref_for_account(note)
```

而 `backfill_note_detail_refs` 的语义是**「只补缺地址」**：

```python
if not force and str(raw.get("note_url") or "").strip():
    continue                            # ← 已有 note_url ⇒ 整批跳过
```

**两个「有就不碰」叠加** ⇒ **有旧令牌的行永不刷新** ⇒ 用户点多少次同步都拿不到正文。

## 3. 修复

### 3.1 判据从「有没有令牌」改成「令牌还能不能用」

```python
outcome = hydrate_note_detail(db, account, note, refresh=True, ...)
if outcome.get("code") == "DETAIL_EMPTY" and _refresh_note_detail_token(db, account, note):
    outcome = hydrate_note_detail(db, account, note, refresh=True, ...)   # 重试一次
```

* **由取数结果回答**「令牌还有效吗」，不由 `raw_json` 里有没有那个字符串回答；
* `DETAIL_EMPTY` 是**已存在的**机器码（§19.13.5 就在用），不新造；
* **只重试一次**（不成环）；刷不到新令牌就**如实报** `DETAIL_EMPTY`（该码文案已含
  「令牌可能已失效或该笔记不可见」）。

### 3.2 `backfill_note_detail_refs` 加 `force`

```python
def backfill_note_detail_refs(db, notes, fetch, *, force=False)
```

`force=True` 连**已有 `note_url`** 的行也重取 —— 令牌过期刷新要的正是这个。
缺省 `False` 保持既有调用方「只补缺」语义**逐字不变**。

### 3.3 `sync_note_from_platform` 把 `code` 带出来

原实现只带 `status`/`reason`，`code` 留在 `outcome` 里 ⇒ 重试分支读不到
（`outcome["code"]` 在调用方是空串）。

## 4. 附带修正：登录态绿标说假话

真机实测（同一会话）：

| 域 | 端点 | 结果 |
|---|---|---|
| `edith`（API） | `/v2/user/me` | ✅ `nickname='观隅好物'` |
| `www`（网页） | `/explore/<id>?xsec_token=…` | ❌ 一度 `/website-login/captcha` |

**卡片全绿、用户点同步报「正文取不到」** —— 绿标只探 API 域，而详情走网页域。
`_probe_www` 补**第二跳**（`_probe_www_domain`，探 `/explore` 内容页）：

* 跳 `/website-login/` / `/login` ⇒ `expired`（用户动作明确：重新登录）
* 其余（含 `/404?source=…`）⇒ `valid`
  ⚠️ **`/404` 不算「不可用」**：实测那是「该参数下无内容」的提示页，页面里照样带
  完整 `noteDetailMap`；把它判成 expired 会让用户在一切正常时被要求重登（DEF-057 同型）
* 请求失败 ⇒ `unknown`（**不冒充** expired）

⚠️ **探针的边界**：它只回答「网页域**会话**是否有效」，**不回答**「某条笔记的
token 是否有效」 —— 后者由取数本身如实报（§3.1）。

## 6. 纪律（写给下一个人）

* **平台用 `200 + 空数据` 表达「令牌失效」**，不是 4xx —— 判「取数失败」的原因时，
  **不要只按 HTTP 状态码分档**。
* **令牌有时效**：任何「本地已有 X 就不再取 X」的短路，都要问一句
  「X 会不会过期」（本缺陷正是两个这种短路叠加）。
* 排查此类问题时，**先做「同一输入换一个变量」的对照实验**（本轮的「旧 token vs
  新 token」），不要在「代码/结构/风控」上并行猜 —— 本轮前 5 个假设全部被对照实验推翻。
