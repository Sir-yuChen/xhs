# 69 · 设计 · 任务中心两级架构重构（系统级 / 工作区域级）

> 用户口径（2026-10-25，原文）：
> ① 「任务中心分为系统级别和工作区域级别，**工作区域为每个区域中私有**」
> ② 「**暂时不允许用户创建任务**」
> ③ 「不在保存用户级的任务中心，**收为公共**」
>
> 状态：设计定稿。**取代**设计 15 §4.1.1（DEF-066「每用户各持一份」）与
> 设计 64 §3.3（「系统管理定时任务页 = admin 跨工作区总览」）。

## §1 问题：一个归属字段承担了两种语义

`DEF-066`（2026-09-24）把「`user_id IS NULL` = 全局任务」整句作废，改为
**每用户各持一份**，理由是：全局共享行会被多用户互相操作（A 改参数、B 跟着变；
A 配的 `account_ids` 写进共享行，B 执行时跑的是 A 的账号）。

那条整改解决了「互相操作」，但**引出了新问题**（2026-10-25 实测）：

| 现象 | 实测 |
|---|---|
| 定义行数 | **403 行** = 31 个用户 × 13 个任务 |
| 其中测试探针账号 | **29 / 31** |
| 系统管理页能看出任务内容吗 | **不能** —— 同一个「清理记录表」重复 31 行，只有归属人不同 |
| 改一次 Cron 要改几处 | **31 处**（且新用户注册后又多一份） |

根因：**`user_id` 同时被用来表达「谁的账号」与「谁有权改这个任务」**——
两个语义被压进一个字段，于是「让每个用户管辖自己的任务」只能靠「复制定义行」。

## §2 两条口径分开表达（本次重构的核心）

| 语义 | 字段 | 说明 |
|---|---|---|
| **这个任务服务于哪个工作区** | `workspace` | `system` / `xhs` / 未来 `douyin` |
| **执行时要跑谁的数据** | 由 `JobSpec.user_scoped` 决定，运行时算出 | 不是存储字段 |

`user_id` 从「归属人」降级为「**最后修改人**」（审计用，可空）。

### 2.1 两级归属（用户口径 ①）

| 级别 | 判据 | 任务 | 谁能看/改 |
|---|---|---|---|
| **系统级**（`workspace='system'`） | 作用于**本系统自己的资源**，与接哪个平台无关 | 清理记录表、清理数据包暂存、清理未引用图片 | admin |
| **工作区域级**（`workspace='xhs'`） | 作用于**某个平台的数据** | 笔记/商品/订单同步、发布补跑、Cookie 与千帆巡检、指标同步、自动运营、商业笔记发布 | admin |

⚠️ 「工作区域级任务」**不等于**「用户各自的任务」——
它是**小红书这个工作区的任务**，工作区内**只有一份定义**，所有小红书账号共用它。

### 2.2 为什么任务仍然需要「跑谁的数据」（`user_scoped`）

`note_sync` 执行时查的是「**某个用户的**小红书账号」。收成一份定义后，
它必须**自己遍历**所有持账号的用户（fan-out），而不是靠「每个用户一份定义」。

这就是市场成熟方案的做法（见 §3）：**定义唯一，执行时扇出**。

## §3 市场调研：一致的做法

| 来源 | 结论 |
|---|---|
| **XXL-Job**（最主流的开源调度） | 任务定义在 `xxl_job_info` **一个 job 一行**，执行记录在 `xxl_job_log` 一次一行；调度中心单实例靠**数据库行锁**（`select ... for update`）保证集群里只有一个在触发。**没有「每个用户一份定义」这种形态。** |
| **Azkaban / Airflow / K8s CronJob** | 同样三层：定义（唯一）/ 触发（单调度器）/ 执行记录（每次一行）。 |
| **多租户 fan-out 模式** | `tenant-schemas-celery` 官方文档把这叫 **Dispatcher Task Pattern**：注册**一个** `sync_all_tenants()`，内部 `for tenant in tenants: with tenant_context(tenant): ...`。 |
| **社媒矩阵系统**（Buffer / Later / Postproxy / Hootsuite 类） | 平台侧**只有一个调度引擎**；到点把任务扇出到「每个账号的 PostTarget」，逐账号执行、逐账号记结果。**用户从不配置调度器** —— 用户配置的是「这条内容几点发」，那是**业务数据**，不是调度定义。 |

### 3.1 关键区分：用户配「发什么/几点发」，不是配「调度器」

矩阵系统里用户确实能"定时间"，但那是 **post 的一个字段**（`scheduled_at`），
调度引擎本身由平台管理。本项目里同构的是：

| 用户能做的 | 用户不能做的 |
|---|---|
| 在商品/笔记上设定**发布时间**（业务数据） | 新建/删除/暂停**定时任务定义** |
| 手动点「同步笔记」「同步商品」（走 `tasks` 队列） | 改 Cron、改任务参数 |

⇒ 与用户口径 ②「暂时不允许用户创建任务」完全一致，且**不影响业务能力**。

## §4 目标架构

### 4.1 数据层

```
scheduled_jobs（定义，全局唯一）
  id, job_key UNIQUE, name, workspace, cron_expression, status, params, is_builtin,
  user_id(可空，= 最后修改人，审计用), updated_at
                                                     ↑ 403 行 → 14 行

scheduled_job_logs（执行记录，一次一行）
  id, job_id, job_key, job_name, workspace,
  executed_for_user_id   ← 新增：这次执行跑的是谁的数据（系统级任务为 NULL）
  trigger_type, status, started_at, finished_at, progress, message, trace_id
                                                     ↑ 一次扇出 = 每个用户一行
```

**为什么 `executed_for_user_id` 不复用 `user_id`**：`user_id` 已改成"最后修改人"；
若执行日志也用它表示"为谁跑"，两者会混淆。新列语义单一，历史数据可空。

### 4.2 执行层（fan-out）

```
调度器触发 system.note_sync（1 行定义）
   ↓
runner：JobSpec.user_scoped == True
   → 取「持平台账号的用户」列表 [2, 5, 9]
   ↓ 逐个
for uid in users:
    run(uid) → 写 scheduled_job_logs(executed_for_user_id=uid)
   ↓
汇总一行批次记录：status=partial / success / failed
```

**单用户失败不中断整批**（与现有 `queue_record_cleanup` 的逐条容错同型）。
`JobSpec.user_scoped == False`（清理类）⇒ 直接跑一次，`executed_for_user_id=None`。

**并发与幂等**：沿用现有 `max_instances=1 + coalesce`（APScheduler 侧），
fan-out 内部按账号串行（`CrawlRateLimiter` 已保证速率）。

### 4.3 界面

**系统管理 → 任务中心**（`/system/scheduler`，admin 专属）

| 页签 | 内容 |
|---|---|
| **系统任务**（`workspace='system'`） | 清理类任务，每种一行；可改 Cron / 暂停 / 立刻执行 |
| **工作区任务**（`workspace='xhs'`，未来按工作区分组） | 小红书任务，每种一行；同上 |
| **执行日志** | 所有执行记录，可按任务 / 工作区 / 状态 / 目标用户筛选 |

**删除**：`/tasks`（用户任务中心）整个下线；对应 5 个权限码
（`create` / `edit` / `delete` / `pause` / `resume`）与菜单按钮行退场。

**保留**：`/task-records`（队列记录）——它是 `tasks` 表的**业务执行记录**，
与定时任务定义是两套东西（用户口径早期已确认）。

### 4.4 权限

| 能力 | 谁 |
|---|---|
| 查看任务定义 | admin（`system:scheduler:view`）|
| 改 Cron / 参数 / 暂停 / 立刻执行 | admin（`system:scheduler:manage`）|
| 查看执行日志 | admin |
| 用户手动触发同步/发布 | **普通用户仍可**（走 `tasks` 队列，**不是**定时任务）|

## §5 迁移（一次性，不兼容旧形态）

用户口径「不做兼容」。

1. 迁移 `scheduled_jobs`：按 `job_key` 去重，**每个 job_key 只留一行**
   （保留最早那行；`user_id` 清空改为 NULL；`workspace` 按 §2.1 重算）。
2. 新增 `scheduled_job_logs.executed_for_user_id`（可空）。
3. 删除 `scheduled_jobs` 的 `(job_key, user_id)` 唯一约束，改 `job_key` 全表唯一。
4. 现有 `scheduled_job_logs` 的存量行：`executed_for_user_id = 原 user_id`（它是
   真实"为谁跑的"），`user_id` 保留（历史归属人快照）。
5. 种子文件 `config/initial_data/scheduled_jobs.json` 从 **每用户行** 改成
   **每 job_key 一行**。

## §7 守卫（会红的断言）

1. `scheduled_jobs` 的 `job_key` 全表唯一（不能再按用户复制）
2. 每个注册表任务必须有 `workspace ∈ {system, xhs}`，且系统级任务的执行函数
   **不得**引用平台适配器（判据：系统级任务与平台无关）
3. `user_scoped=True` 的任务，runner 必须走 fan-out（不能只跑一次）
4. 普通用户调 `POST/PUT/DELETE /api/schedule/jobs` ⇒ 403
5. `/tasks` 路由已下线（410 或不存在）
6. 执行日志 `executed_for_user_id` 在 fan-out 场景必须非空（系统级任务可为空）
