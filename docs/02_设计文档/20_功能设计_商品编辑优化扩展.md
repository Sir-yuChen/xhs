## 1. 数据模型（一张新表 + 三列加列，一个迁移）

### 1.1 `product_groups`（新表）

| 列 | 类型 | 语义 |
|---|---|---|
| `id` | INTEGER PK | |
| `user_id` | INTEGER FK `users.id` NOT NULL | **租户隔离键**（与项目所有业务表同构：分组是用户的本地组织方式，不跨用户共享） |
| `name` | VARCHAR(64) NOT NULL | 分组名（用户自取，**跨用户不唯一**：允许「清仓」「主推」在两个用户名下各自存在） |
| `created_at` / `updated_at` | DATETIME NOT NULL | 时间戳 |

* **唯一键 `(user_id, name)`**：同一用户下分组名不重复（重名会让「按分组筛」歧义）。
  两列均 `NOT NULL`，无 SQLite 唯一键 `NULL` 歧义隐患。
* **为什么分组挂 `user_id` 而不是 `platform_account_id`**：分组是**用户的组织方式**，
  不是账号的属性 —— 用户可能把几个账号的商品放进同一个「主推」分组里跨账号比较。
  商品侧的归属仍由 `shop_products.platform_account_id` 保证（不可越权）。
* **删除分组 ≠ 删商品**（见 §4.4）：分组是弱关联，删分组只把商品 `group_id` 清空。

### 1.2 `shop_products` 加三列

| 新列 | 类型 | 语义 |
|---|---|---|
| `group_id` | INTEGER NULL | 指向 `product_groups.id`；**NULL = 未分组**（不是 0、不是 -1） |
| `ai_title` | VARCHAR(512) NULL | AI 润色后的标题（**采纳**后的值；润色过程不落库，见 §5.1） |
| `ai_selling_point` | TEXT NULL | AI 生成的卖点（同上） |

⚠️ **不加 FK 约束**：分组删除时若靠 FK 的 `ON DELETE SET NULL`，SQLite 的 ADD COLUMN
加 FK 需要表重建（代价大且迁移链复杂）；改为**删分组时服务端显式清空**（§4.4），
「清空」这一步是**契约的一部分**（响应里报告影响面），比 FK 的隐式行为更可审计。

⚠️ **两列初始恒为 NULL**（不是空串）：**NULL = 没采纳过**，空串 = 采纳了但内容为空。
这是两个不同的界面状态（「去润色」按钮 vs 「已润色，内容为空」），用一列两种值区分
（缺值口径，硬约束⑤）。

### 1.3 迁移

* 版本号 `g0a1b2c3d4e5`，`down_revision = "f2a3b4c5d6e7"`（M3 热点表 hot_topics）。
* ⚠️ **幂等：两件事都先判存在**（与 `e1f2a3b4c5d6` / `c9d0e1f2a3b4` 同一判据）——
  本项目「stamp 回早期 revision 再 upgrade」是**正常用法**（迁移用例这么跑），
  夹具库用 `create_all()` 建表 ⇒ 表 / 列**已经在了**，不判存在就炸。
* 加列用 `ALTER TABLE ADD COLUMN`：SQLite 的 ADD COLUMN **不幂等**（重复执行会加出
  `group_id` / `group_id_2` 两列）⇒ 必须先 `PRAGMA table_info` 查列名再决定是否加。
* ⚠️ **新增列必须 nullable**（SQLite 的 ADD COLUMN 不允许 `NOT NULL` 且无默认值）
  ⇒ 三列全为 nullable 天然合规，**不需要回填**。

## 2. 端点契约（6 个新端点 / 6 个新 path）

全部挂在 `qianfan.py` 现有 router（`/api/xhs/qianfan`），与 `/items` / `/item-detail`
**同一路由文件、同一归属校验入口**（`_owned_account`）。

| # | 端点 | 语义 | 平台请求 |
|---|---|---|---|
| 1 | `GET /api/xhs/qianfan/product-groups` | 分组列表（当前用户；每项带 `product_count`） | 零 |
| 2 | `POST /api/xhs/qianfan/product-groups` | 建分组（`name`；**唯一键冲突 ⇒ 409**，不静默覆盖） | 零 |
| 3 | `PATCH /api/xhs/qianfan/product-groups/{group_id}` | 改分组名（归属校验失败 ⇒ 404） | 零 |
| 4 | `DELETE /api/xhs/qianfan/product-groups/{group_id}` | 删分组（**级联清空 `shop_products.group_id`**，返回被清空的商品数） | 零 |
| 5 | `PATCH /api/xhs/qianfan/items/edit` | 商品编辑：**分组**（`group_id`）+ **AI 标题 / 卖点落库**（`ai_title` / `ai_selling_point`）。**纯本地写** | 零 |
| 6 | `POST /api/xhs/qianfan/items/export` | CSV 导出：按**当前筛选条件**（复用 `ShopItemsRequest` 全部筛选字段）导出台账行，`text/csv; charset=utf-8` + BOM | 零 |

### 2.1 字段级契约

```python
# 1~4：分组 CRUD
ProductGroupCreate  = { name: str (1..64) }
ProductGroupUpdate  = { name: str (1..64) }
ProductGroup        = { id: int, name: str, product_count: int, created_at: str, updated_at: str }

# 5：商品编辑（⚠️ extra="forbid"，与 ShopItemsRequest 同一纪律）
ItemEditRequest = {
    platform_account_id: int (ge=1),
    item_id: str (1..64),
    group_id: int | null,          # 显式 null = 移出分组；省略键 = 不动（两种语义）
    ai_title: str | null,          # 显式 null = 清空；省略键 = 不动
    ai_selling_point: str | null,
}
ItemEditResult = {
    item_id: str,
    group_id: int | null,
    ai_title: str | null,
    ai_selling_point: str | null,
    updated: list[str],            # 真正改了哪几列（"group_id"|"ai_title"|"ai_selling_point"）
}

# 6：导出（复用筛选条件，去掉分页字段）
ItemsExportRequest = { ...ShopItemsRequest 的筛选字段 }
→ Content-Type: text/csv; charset=utf-8
→ Content-Disposition: attachment; filename="商品台账-YYYYMMDD-HHMMSS.csv"
```

### 2.2 三个必须钉住的口径

1. **`PATCH /items/edit` 的「不传 = 不动」**：三个可编辑字段**省略键** = 保持原值；
   **显式传 `null`** = 清空。用 sentinel 默认值（不是 `None`）区分这两种 ——
   直接写 `Optional[int] = None` 会把「没传」和「传 null」混成一件事（PATCH 语义
   最常见的静默错值）。
2. **导出不限页但有上限**：`MAX_EXPORT_ROWS = 5000`（与 `MAX_BATCH_DELETE = 200`
   同一「前后端同值」纪律 —— 常量只在后端一处定义，**前端不抄第二份**）。
   超限 ⇒ 400 `QIANFAN_EXPORT_TOO_MANY`，**不静默截断**（截断的 CSV 是一个
   「看起来完整」的假全量，用户会拿它去对账）。
3. **CSV 的字段口径 = 列表页展示口径**：导出列与 `/items` 的 `normalize_item_from_raw`
   **同一个构造函数**（不另写一份字段映射 —— 两份必然漂移，DEF-044 同型）。
   ⚠️ **`ai_title` 有值时导出它，否则导出 `item_title`**（用户要的是「能用的标题」），
   列名如实标 `AI标题（无则原标题）`。

## 3. AI 润色：两个新业务点 + 一个新端点（kind = text）

### 3.1 设计：润色结果**不落库**，先回前端预览

⚠️ **这是与直觉相反的决定，理由必须写清**：

`ai_title` / `ai_selling_point` 两列是**「用户**采纳**的结果」**，不是「模型的输出」。
润色一次给出 **3 个备选**（市场惯例：只给一个等于没给，用户没有可比较的对象），
用户在备选里**挑一个**或**都不要**，**点「采纳」才写进 `ai_title`**。

| 端点 | 语义 | 落库 |
|---|---|---|
| `POST /api/xhs/qianfan/items/polish` | 调文本模型，返回 3 个备选标题 + 3 个备选卖点 | **不落库**（结果在响应里，前端暂存） |
| `PATCH /api/xhs/qianfan/items/edit` | 采纳：把选中的那个写进 `ai_title` / `ai_selling_point` | 落库 |

**为什么不落「润色历史」**：润色历史是**过程**，不是**事实**；用户采纳的那个才是
商品属性。过程类的查询需求（「上次润色出了什么」）走 `llm_gateway_usage_logs`
（本地调用台账，v1.7 已记录每一次上游调用 + prompt）—— **不为它新建表**
（§13.2 的「同一语义不留两份实现」）。

### 3.2 两个新业务点常量（`business_provider_keys.py`）

```python
BUSINESS_KEY_POLISH_PRODUCT_TITLE = BusinessKey(
    "polish_product_title", MODEL_TYPE_TEXT, "商品标题润色",
    ("商品列表-商品详情-AI润色-标题",),
)
BUSINESS_KEY_GENERATE_SELLING_POINT = BusinessKey(
    "generate_selling_point", MODEL_TYPE_TEXT, "商品卖点生成",
    ("商品列表-商品详情-AI润色-卖点",),
)
```

⚠️ **与既有的 `polish_text` / `generate_title` 是四个不同的业务点**：那两个服务
**笔记**（草稿 / 笔记标题），这两个服务**商品** —— 提示词、长度约束、平台口径全不同
（商品标题有平台字数上限、不能含广告法违禁词；笔记标题没有）⇒ 用户要能**分别挂服务商**
（§13.2 的设计目标）。加业务点**只改 `BUSINESS_KEYS` 元组**，下发端点 / 类型校验 /
前端清单自动跟进（§13.2.2 的可扩展性论证）。

### 3.3 提示词（商品特化，不抄笔记的）

商品标题润色的 system prompt 三条硬约束：

1. **平台合规**：不得含「最」「第一」等广告法违禁词（电商硬约束，笔记没有这条）；
2. **字数 ≤ 60**（千帆商品标题实测上限；超出平台会拒）；
3. **保留原意 + 核心卖点词**（不能润色成另一种商品）。

卖点约束：**≤ 100 字**、**至少一个「场景 + 痛点 + 解决方案」结构**、
**不得编造参数**（不知道的参数不写，缺值口径⑤）。

⚠️ **复用 §13.6 的公共模板机制**：用户可在「提示词模板」页建 `task_type=text` 的
商品标题模板；润色端点支持 `template_id`（与出图链路同一把尺子：模板 > 手输 > 内置兜底）。

## 4. 业务逻辑（逐条判据）

### 4.1 归属校验（所有端点同构）

* 商品维度一律先过 `_owned_account(db, current_user, platform_account_id)`
  （复用 `get_owned_active_account`，含**软删闸** —— DEF-055 的唯一实现）；
* 分组维度：`group.user_id != current_user.id` ⇒ **404**（不报 403：不泄露分组存在性）。

### 4.2 `product_count` 的口径

```sql
SELECT COUNT(*) FROM shop_products
WHERE platform_account_id IN (当前用户的账号 id 集合) AND group_id = ?
```

⚠️ **必须是「当前用户的**全部账号**」而不是某个账号**：分组挂 `user_id`（§1.1），
一个分组可以装用户多个账号的商品 ⇒ 按 `platform_account_id` 过滤会让计数和列表对不上。
计数为 0 的分组**照常返回**（用户可以建空分组先摆着）。

### 4.3 分组名唯一性的竞态

`(user_id, name)` 唯一索引是**最后防线**；服务层先 `SELECT` 查重并返回 409 结构化错误
（`code: PRODUCT_GROUP_NAME_EXISTS`，message 带已有分组 id，方便前端定位）。
⚠️ **不靠唯一索引报错兜底**：并发下仍可能两个请求同时 INSERT 同名，届时
`IntegrityError` **回退到 409**（同一语义，不 500）。

### 4.4 删分组的级联清空

```python
# 1) 先数有多少商品在用这个分组（响应里告诉用户影响面）
affected = SELECT COUNT(*) FROM shop_products WHERE group_id = ? AND user 的账号集合
# 2) UPDATE shop_products SET group_id = NULL WHERE group_id = ?
# 3) DELETE FROM product_groups WHERE id = ?
# ⚠️ 顺序不能反：先删分组后清列，中间态的查询会读到「分组不存在」的 group_id
```

### 4.5 导出的正确性边界

* **只导台账里有的**（`shop_products`），**不实时查平台**（与列表页同一零平台请求纪律）；
* **筛选条件与列表页逐字段一致**：同一个 `_apply_filters`，**不重新实现一份**
  （两份筛选实现 = 「列表看到的」和「导出的」不是同一个集合，这是导出最常见的故障）；
* ⚠️ **排序也复用**（`_apply_order`）：保证 CSV 与屏幕顺序一致（用户对账时眼睛在
  两处来回看，顺序不一致会误判「少了几行」）；
* **时间字段用秒级**（与 `_ts_text` 同口径，§32.1 的教训：精度到分钟会同批商品
  显示成同一时间，看不出排序依据）。

#### 4.5.1 ⚠️ 上面这条「复用」还有**前端一半**（DEF-093，2026-10-05 实测补漏）

后端复用一条 `_apply_filters` **不足以保证**「导出集合 = 列表集合」—— 前端也得只有一份
请求构造。修之前不是：列表 `load()` 拼 `create_time_from`（对），而导出拿的是
**本地筛选缓存草稿**的键名 `create_from` / `create_to` ⇒ 导出端点的模型带
`extra="forbid"` ⇒ **必然 422**（页面只显示「请求失败，请稍后重试」）。

三条教训，都是结构性的：

1. **两个键名体系之间必须有机械判据**：`lib/shop-items-query.ts::formValuesToQuery()`
   是列表与导出**唯一一处**构造；`formValuesToDraft()` 只服务本地缓存，键名故意不同。
2. **守卫必须穿过层边界**：`test_shop_items_query_contract.py` 从后端 Pydantic 模型取字段表，
   交给行为脚本断言「前端构造的键 ⊆ 后端模型字段」——后端直调的测试**永远发现不了**这类缺陷
   （它自己拼正确键名）。
3. **「导出 = 列表」是一个可断言的等式，不该只是文档口径**：真机判据
   「同一筛选下 CSV 数据行 == 列表 total」已跑通（1980 件筛到 3 件 → CSV 3 行）。

⚠️ 同时修掉两处**静默丢失**：导出原先既不带**排序**也不带**分组**（`group_id`）——
即「同一个筛选」这句话在当时只在填了部分字段时成立。

## 11. 商品操作与指定同步（2026-10-05，用户 8 条口径）

### 11.1 分组彻底退场（§1.1 / §1.2 / §2 端点 1–4 作废）

用户口径是「**彻底**移除」，落实为**四层一起删**（留任何一层都会长出「删了又回来」的怪现象）：

| 层 | 动作 | 原因 |
|---|---|---|
| 表 | 迁移 `h1i2j3k4l5m6` `DROP TABLE product_groups` | 数据层不留空壳 |
| 列 | 同迁移 `ALTER TABLE shop_products DROP COLUMN group_id` | 同上 |
| ORM | 删 `models/product_group.py` + `models/__init__.py` 的注册 + `shop_product.py` 的列 | **`create_all()` 会把迁移已 drop 的表建回来**（v2.0 的 `ModelConfig` 踩过这个坑） |
| 服务 / 端点 / 前端 | 删 `product_groups_service`；4 个 CRUD 路径改 **410 墓碑**（`include_in_schema=False`）；前端删 4 个请求函数 + 类型 + 筛选下拉 | 墓碑而非 404：404 会被当成「路由写错」，410 才表达「功能没了」 |

⚠️ **本地编辑能力保留**：`edit_product`（改 `ai_title` / `ai_selling_point`）原先寄居在
`product_groups_service`，分组退场时**迁到 `shop_products_service`**（功能不随宿主一起死）。

⚠️ **迁移用裸 `ALTER TABLE ... DROP COLUMN`**，不走 `batch_alter_table`：
`shop_products` 被 3 张表用 FK 引用（`shop_metric_snapshots` / `topic_goods_match` / …），
SQLite 的「建新表 + 拷数据 + 改名」路径会撞上这些引用。

### 11.2 平台商品写接口（需求 7/8 的前提，2026-10-05 真机打通）

写接口**不在 SDK 里**（一期只读边界），本节记录怎么打通的 —— 后续维护签名层时看这里。

**接口**：`POST https://ark.xiaohongshu.com/api/edith/product/batch_update_availability_v3`
（上架 / 下架；删除走 `…/product/batch_delete_v3`）。

**签名姿势**（逐一实测的结论，缺一项就 406）：

| 项 | 值 | 备注 |
|---|---|---|
| `appId` | `itemark` | 不是 `xhs-pc-web`（那是 www 的） |
| `signVersion` | `4.4.4` | 与 ark 页面 bundle 一致 |
| 签名算法 | `mns0101` | 现有 Node signer 已支持 |
| `Authorization` | **不需要** | 反问验证过：加上也无害，但去掉照样 200 |
| `x-s-common` | 不校验 | 去掉照样 200 |

**真机验证**：商品 `6a58160749fb5f0015f5fc84` 从「已下架」→「上架」
（`buyable=False→True`），返回 `code=200 data={taskId:81432}`。

⚠️ **批量上限**：SKU 明细批量 `SKU_BATCH_SIZE = 10`（真机 5/8/10 → 200，20 → 服务端 500）；
商品操作单任务 `MAX_OPERATE_ITEMS = 200`（与前端 `MAX_OPERATE_ITEMS` 同值，导入期断言）。

### 11.3 需求 7：批量上架 / 下架 / 删除 = **手动触发式任务**（不进任务中心）

**参考实现**：`no_traffic_cleanup_service`（用户点名的样板）。三条纪律逐条对齐：

1. **任务落在 `tasks` 表**（`task_type = xhs_shop_item_operate`），**不进 `scheduled_jobs` 注册表**
   ⇒ 任务中心的任务列表看不到（需求 7 原话），但队列记录页能看到；
2. **建行即返回**，真实执行在后台线程（HTTP 不被写操作阻塞）；
3. **逐条记账**：每条商品一个 `{item_id, title, result, reason}`，
   `result` 三态 = `ok` / `skipped` / `failed`。

### 11.4 需求 7 的核心：**状态门禁**，不支持的只记录不执行

> 用户原话：「**定时任务中需要根据任务状态，确定该商品是否支持执行该操作，
> 不支持的只记录不执行操作**」

**判据只实现一次**——`services/shop_item_operate_gates.py`（唯一实现）。
它同时服务两条链路：列表端点下发 `allowed_actions[]`（需求 8 的按钮）、
执行循环的 `support_reason()`（需求 7 的跳过判定）。分开实现必然分叉：
前端亮着按钮、后端静默跳过（用户点个寂寞）。

**判据来源不是拍脑袋**，是从千帆 `832.d09dac0d.js` bundle 逆出来的三个校验函数
（原文对照见模块 docstring）+ 真机 DOM 核对各 tab 给了哪些行操作：

| 状态 | 上架 | 下架 | 删除 |
|---|---|---|---|
| 售卖中 | ❌ | ✅ | ✅ |
| 已下架 | ✅ | ❌ | ✅ |
| 已冻结 | ❌ | ❌ | ✅（受 lock / 活动拦） |
| 审核中 / 驳回 / 通过 / 整改 | ❌ | ❌ | ✅ |

共性拦：**店铺冻结**（三个动作全拦）、**商品禁售**、**定金预售活动**（下架 / 删除）、
**`item_lock_infos` 里对应动作的锁**。

⚠️ **未知状态 ⇒ 上下架判「不支持」**（保守）；删除不受状态闸约束
（平台在多个 tab 都给删除入口 —— 顺手给它套上「只有已下架能删」会让售卖中的商品删不掉）。

⚠️ **本地判定 ≠ 平台判定**：平台还可能因实时原因（活动 / 锁）拒绝，那由**写接口的逐条回执**
（`failData[].reasons[].message`）如实报出，**门禁不猜**。

### 11.5 需求 8：列表操作列按状态渲染按钮

后端在 `/items` 每条上挂 `allowed_actions[]`：

```json
[{"action": "on_shelf", "label": "上架", "supported": false, "reason": "当前状态「售卖中」不支持上架（…）"}]
```

⚠️ **不可做的也下发**（`supported: false` + 中文原因）：只下发可做的，前端就无法回答
「为什么这个商品没有上架按钮」—— 用户会当成 bug。

前端按 `supported` 渲染（**不复算**）：可做 ⇒ 可点按钮；不可做 ⇒ 置灰 + Tooltip 给原因。

⚠️ **单行入口与批量入口必须两个函数**：批量的 id 来源是**勾选集**，
单行按钮若复用批量处理器会「顺带操作所有勾选的商品」（写操作撤不回来）。
两处共用 lib 的文案与后端的 `allowed_actions`，但**执行函数分开**
（`operateOneItem` vs `handleBatchItemOperate`）。

### 11.6 需求 6：同步指定商品（弹窗 + 无限列表）

**平台侧没有「按 item_id 拉商品」的读接口**（2026-10-05 真机核对：
`product/search_item_v2` 只支持分页 + 筛选；`get_skus_by_item_ids` 只回规格、不回商品本体；
`get_channel_item_by_item_ids` 只回渠道品）。⇒ 唯一可行路径：

> 把指定 ID 当作筛选条件发出去（`whole_keywords` 支持名称 / ID / 货号 / 商家编码），
> 平台按页返回命中项，**本地再按精确 `item_id` 筛一次**。

⚠️ **本地精确再筛是必须的**：`whole_keywords` 是**模糊匹配**（实测搜 ID 会命中标题里
含该串的商品）。不筛 ⇒ 台账里会多出**用户没点名**的商品 —— 比「少同步一个」更坏
（台账是用户对账的依据）。`not_found` 也按本地精确集合算。

⚠️ **只补不删**：命中之外的商品一行不动（与全量同步的「翻完删旧行」刻意不同）。

⚠️ **读接口必须传 `status=all`**：要补的商品可能已下架 / 审核中，按默认的「售卖中」筛会漏掉。

**端点**：`POST /api/xhs/qianfan/items/sync` → `{synced, not_found, scanned, matched, note}`。
**同步执行**（不是后台任务）：目的是「马上看到那几个商品的最新数据」，
丢后台就得再设计一套进度查询；代价（要翻页、可能较久）如实写在响应 `note` 与弹窗文案里。

**前端弹窗** `sync-specified-items-modal.tsx`，两个 Tab：

1. **从台账选择** —— `Table virtual` + 滚到底取下一页的**无限列表**，
   行内展示商品名 / 状态 / 同步于，勾选后「同步选中的 N 件」；
2. **手动输入 ID** —— 台账里还没有的商品只能靠 ID 指定（也是列表取不到时的逃生口）。

**逐条结果落在「提交时那份 ID 清单」上**：后端只给聚合数，不给逐条明细
⇒ 提交前把 ID 全部铺成 `pending`，拿到结果后按 `not_found` 集合标成
「已更新」/「未找到」。**没命中的不从列表里消失**（否则用户以为提交丢了）。

### 12.6 状态 tag 颜色与文案**必须同源**（2026-10-06 用户实测 bug）

用户口径：「点击上架后，商品为**售卖中**但是**售卖中 tag 为灰色**，已下架的 tag
也有绿色的」。

#### 现象与根因（两层）

**第一层（直接原因）**：列表状态标签的写法把**颜色与文案交给了两个不同的字段**：

```tsx
// 修改前（颜色 ← buyable，文案 ← status_label，两者可互相矛盾）
<Tag color={item.buyable ? "green" : "default"}>{item.status_label}</Tag>
```

* 上架后 `status_label` 已是「售卖中」而 `buyable` 还是 `false` ⇒ **灰色「售卖中」**；
* 已下架但 `buyable` 仍 `true` ⇒ **绿色「已下架」**。

**第二层（为什么两个字段会打架）**：后端 `_refresh_local_status`（上架/下架成功后的
**本地即时刷新**，乐观值）只翻了 `on_shelf_time` / `off_shelf_time`、
`card_type` 与 `status` 列，**漏翻 `buyable`**。

⚠️ `buyable` 与两个时间戳是**同一个生命周期信号的三面** —— `status_key_from_raw`
的 docstring 自己就记着实测口径：「下架行 = `buyable=false` + 无上架时间 +
有下架时间」。漏翻它，除了 tag 颜色，还连带两处矛盾显示：

| 位置 | 显示 | 实际 |
|---|---|---|
| 状态列 tag | 「售卖中」+ 灰（本次报告） | 已上架 |
| SKU 表「可售」列 | **停售** | 已上架 |
| 详情弹窗 | **不可购买** | 已上架 |

#### 修法（两处，各管一层）

1. **前端**：新增 `lib/shop-items-view.ts::statusTagColor(statusKey)`，状态标签改为
   `<Tag color={statusTagColor(item.status_key || "")}>{item.status_label}</Tag>`
   —— 颜色与文案**同取状态词汇表**（`status_key` ↔ `status_label` 同一键派生），
   结构上不可能再打架。映射：在售 `green` / 下架 `default` / 待审 `orange` /
   异常（冻结·驳回·整改）`red` / 审核通过 `cyan` / **未知 `default`**（缺值不猜）。
   `XhsShopItem` 补 `status_key?: string`（后端**两条路径都下发**它）。
2. **后端**：`_refresh_local_status` 补 `raw["buyable"] = wants_on_shelf`，
   与时间戳 / `card_type` / `status` 列在同一处翻转。
   ⚠️ `status_key_from_raw` **不读 `buyable`**（只读时间字段与 `item_freeze`）
   ⇒ 补写它**不影响**上下架门禁（不会把可操作的商品判成不可操作）。

#### 为什么测试此前测不出来

`tests/backend/test_shop_item_operate.py` 的种子夹具 `_OFF_SHELF` / `_ON_SHELF`
**只给两个时间戳、没给 `buyable`** ⇒ `bool(item.get("buyable"))` 恒为 `False`
⇒ 「上架后 `buyable` 没翻」这个 bug 在自动化里**永远不可见**。
已补 `buyable`（与真机 raw_json 一致）并加断言，本 bug 由测试钉死。

  主路径是「主表勾选 ⇒ 进来看清单 ⇒ 点同步」，而不是「进弹窗再挑一遍」。
* 独立的条件弹窗（页面层 `SyncOptionsModal`）**退场**：同一件事不留两个入口（DEF-044）。

#### 12.10.2 用户可见文案里**禁止** Markdown 的 `**`

用户口径：「商品页很多说明文案存在 `**`，移除」。

⚠️ 根因：把写文档的习惯带进了**会渲染的字符串**——`description="…**立即关闭**…"`、
`` `${label}：对选中的 ${n} 个**平台商品**执行` ``。这些不是 markdown，**星号会原样显示**。

全仓扫描后修掉 **6 处**（商品页 1 / 同步弹窗 2 / 设置页 1 / 队列记录页 1 / 订单页 1）。
新增守卫 `test_no_markdown_bold_inside_user_facing_strings` 覆盖**整个 `frontend/src`**
（不只商品页），且**剥注释后**才判 —— JSDoc 里的 `**` 是项目文档风格，允许保留。

### 12.11 「商品信息列」+ 台账补充列表的模糊查询（2026-10-06，v3）

用户口径：「弹窗的商品 ID 列，优化为**商品信息列**，缩略图，商品名称，商品 ID；
注意商品名称不要过长使用 **tip** 展示全部。从台账选择补充按钮，**点击后未展示可补充的
列表**（bug），列表之前**名称模糊查询**批量加入待同步列表」。

| 项 | 改法 | 为什么 |
|---|---|---|
| 列 | `商品 ID` → **`商品信息`**：40×40 缩略图 + 名称 + ID 两行 | 只给 ID 认不出是哪个商品 |
| 名称 | 单行 `ellipsis` + **`Tooltip` 兜全** | 承诺「不要过长」，也不许撑破列宽 |
| 缩略图 | 无图时给灰底占位（不是 `-`） | 缺值口径：位置在、内容缺，一眼看出是「没图」 |
| **空列表 bug** | 点开「从台账选择补充」**加载第一页** | ⚠️ v2 起打开弹窗只铺清单、**不再取台账** ⇒ 点开只能看到空列表（用户实测报的正是这个）。根因是 `loadPage` 只被滚动回调调用过 |
| 取数失败 | 从「安静吞掉」改**报出来** | 原来失败也长得像「没有商品」，用户分不清「空」与「错」 |
| 模糊查询 | `Input.Search` ⇒ **服务端** `keyword` | 前端只能在**已加载页**里过滤 ⇒ 搜不到没滚到的商品 |
| 批量加入 | 勾选后一次带**名称+缩略图**并入清单 | 顺带把元数据带过来，列表不必再查一次 |

⚠️ 搜索取数用 `loadPageWithKeyword(accountId, page, seq, kw)` —— **关键词当参数传**，
不走 state：搜索框刚 `setKeyword` 时 state 还没生效，用 state 会拿**旧词**去查
（「换了关键词却没生效」同型缺陷）。

### 12.12 弹窗 v3：80% 宽 / 列统一 / 批量移除 / 细滚动条（2026-10-06）

用户口径（连续三条）：「弹窗**全屏的 80%**；台账列表商品名称改为**商品信息列与待同步列
展示一样**；**复选框列 50px**；待同步信息列表新增**复选框列，支持批量移除**；商品信息列的
**商品图和名称均未展示**（bug）」、「批量同步商品信息**滚动条隐藏**」。

| 项 | 改法 |
|---|---|
| 宽度 | `70vw` → **`80vw`** |
| **图/名全空（bug）** | 根因在**页面侧**：只传了裸 ID 清单，弹窗无从得知名称与图片。改为传**带元数据的 `items`**（`data.items` 里带 `title` / `image`） |
| 列统一 | 抽出 `itemInfoCell(...)`，**待同步列表与台账候选列表共用**（原来两处各写一份，形态不一致） |
| 复选框 | 两个列表的复选列都 `columnWidth: 50` |
| 批量移除 | 待同步列表加复选框 + 「移除选中的 N 件」（执行中禁用 —— 清单要与提交的一致） |
| 滚动条 | 藏**外观**不藏滚动：`scrollbar-width: thin`（Firefox）+ 6px `::-webkit-scrollbar`（Chromium），作用域限定 `.sync-items-modal` |

⚠️ 滚动条口径容易做错：`overflow: hidden` 会让内容**滚不动**（用户说的是「隐藏滚动条」，
不是「不能滚」）。判据是「滚轮/拖拽仍可用 + 视觉上变细」。
