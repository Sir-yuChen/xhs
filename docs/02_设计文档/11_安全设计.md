## 1. 安全目标

| # | 目标 | 说明 |
|---|---|---|
| G1 | **凭据不泄露** | 小红书账号 Cookie、AI 服务商 API Key 必须加密落库，任何 API 响应不得回显明文 |
| G2 | **用户间数据隔离** | 用户 A 不能读到用户 B 的任何账号、内容、草稿、发布任务 |
| G3 | **身份可信** | 令牌不可伪造、不可无限期使用 |
| G4 | **写操作不可重复** | 发布不可逆，必须有防重机制 |
| G5 | **内容合规** | 生成的商业推广内容不得违反广告法与平台规则 |
| G6 | **边界清晰** | 系统不提供规避平台风控的能力；用途合规性由使用者自负 |

## 2. 威胁模型

| # | 威胁 | 攻击面 | 现有防护 | 缺口 |
|---|---|---|---|---|
| T1 | 令牌伪造 | JWT | HMAC-SHA256 签名 + `compare_digest` 常数时间比较 | 默认 `secret_key` 是弱值（生产必须改） |
| T2 | 越权访问他人数据 | 业务 API | 查询带 `user_id` 过滤 | 3 个 mock 端点无鉴权依赖；新增 `/users/*` 5 端点**已带鉴权 + 归属校验** |

| T4 | 中间人窃听 | 网络 | 目标站点 HTTPS；本系统按部署方式 | 自部署若用裸 HTTP，登录态与令牌可被窃听 |

| T6 | 重复发布（不可逆写） | `/publish/*` | 状态机 + 单实例调度 | **无 DB 唯一约束** |
| T7 | 敏感内容发布 | 发布链路 | — | **无违禁词护栏** |
| T8 | 逆向代码被滥用 | `apis/` | 无技术手段 | 靠 README 声明（法律与道德约束，非技术防线） |
| T9 | 依赖供应链 | pip / npm | — | 无依赖漏洞扫描 |

## 3. 认证设计

### 3.1 密码存储

```
hash_password(password):
  salt = base64url(os.urandom(16))
  digest = pbkdf2_hmac("sha256", password, salt, 260_000)
  → "pbkdf2_sha256$260000$<salt>$<hash>"
```

| 项 | 值 |
|---|---|
| 算法 | PBKDF2-HMAC-SHA256 |
| 迭代 | **260,000** |
| 盐 | 16 字节随机，每用户独立 |
| 验证 | `secrets.compare_digest`（**常数时间**，防时序侧信道） |
| 兼容 | 支持旧的裸 sha256 哈希（`security.py:35-36`），**建议登录成功后透明升级** |

**位置**：`backend/app/core/security.py:22-36`

### 3.2 令牌设计

| 项 | 设计 |
|---|---|
| 实现 | **自研 JWT**（HMAC-SHA256），非 PyJWT |
| Header | `{"alg":"HS256","typ":"JWT"}` |
| Payload | `{user_id, token_type, exp}` |
| Access 有效期 | **15 分钟** |
| Refresh 有效期 | **7 天** |
| 校验 | HMAC 签名常数时间比较 → `exp` 未过期 → `token_type == "access"` → `user_id` 为 int → 用户存在 |
| 存储（前端） | 由前端保管；请求经 `Authorization: Bearer` 头携带 |

**位置**：`security.py:48-105`、`core/deps.py:14-30`

**设计评价**：
- ✅ 短 access（15min）+ 长 refresh（7d）是合理设计
- ✅ 有 `token_type` 校验，refresh token 不能当 access 用
- ⚠️ **Refresh token 无撤销机制** —— 登出仅是前端清凭证，泄露的 refresh token 在 7 天内仍然有效
- ⚠️ 无 refresh token 轮换（rotation）

### 3.3 登录限流缺口

| 缺口 | 风险 | 建议 |
|---|---|---|
| 无失败次数限制 | T5 暴力破解 | 加每用户/每 IP 的失败计数与锁定 |
| 无验证码 | 同上 | 连续失败后要求验证码 |
| 无限流中间件 | 可被刷接口 | 复用现有 `rate_limiter`（当前只用于采集链路） |

## 4. 授权与数据隔离

### 4.1 隔离实现

```
请求 → get_current_user（解码令牌 + 取 User 对象）
     → 路由函数内：查询条件带 user_id == current_user.id
```

**隔离生效范围**：

| 表 | 隔离方式 | 状态 |
|---|---|---|
| `notes` / `ai_drafts` / `publish_jobs` / `auto_tasks` / `monitoring_targets` / `model_configs` / `keyword_groups` / `tags` / `tasks` / `notifications` | 直接 `user_id` 过滤 | ✅ |
| `account_cookie_versions` | 经 `platform_account_id` → `user_id` | ✅ 间接 |
| `note_assets` / `note_comments` / `draft_assets` / `publish_assets` / `monitoring_snapshots` | 经父表归属 | ✅ 间接 |
| **`xhs/pc` 的 3 个 mock 端点**（原 4） | **无鉴权依赖参数** | ❌ **缺失** |
| `PATCH /accounts/{id}`（stub） | 不查库 | ❌ 无隔离意义（也无副作用） |

### 4.2 角色与权限缺口

| 缺口 | 影响 |
|---|---|
| **`users` 表无角色字段** | 所有登录用户权限相同 → 无法区分管理员与普通运营人员 |
| 全局配置（`scheduler.enabled` 等）若开放 UI | 任何用户都能改系统级开关 |

> **这是二开做「系统管理功能」的前置阻塞项**（见 `10_系统管理功能设计.md` §5.1 P-1）。

## 5. 加密与密钥管理

### 5.1 加密对象

| 数据 | 位置 | 加密方式 |
|---|---|---|
| 账号 Cookie | `account_cookie_versions.encrypted_cookies` | Fernet |
| 登录会话临时 Cookie | `login_sessions.encrypted_temp_cookies` | Fernet |
| AI 服务商 API Key | `model_configs.encrypted_api_key` | Fernet |
| 用户密码 | `users.password_hash` | PBKDF2（单向哈希，非加密） |
| 二开：千帆 Cookie | 新增表（独立于一期账号） | Fernet |

### 5.2 密钥派生（⚠️ 关键风险）

```python
def get_fernet() -> Fernet:
    key = settings.fernet_key or None
    return Fernet(key.encode() if key else _derive_fernet_key(settings.secret_key))
    # _derive_fernet_key = base64.urlsafe_b64encode(sha256(secret))
```

| 场景 | 后果 |
|---|---|
| `FERNET_KEY` 已固定 | ✅ 正常 |
| `FERNET_KEY` 为空 | ⚠️ 由 `secret_key` 派生 → **改 `secret_key` 会让所有历史 Cookie 与 API Key 永久解不开** |

> **生产强制要求（P-2）**：`FERNET_KEY` 必须**显式固定**，且与 `secret_key` **不同**。
>
> 建议：密钥备份与 `.env` 分离保管，改密钥前先做数据迁移（解密→换钥→重新加密）。

### 5.3 Cookie 版本化（安全收益）

Cookie **不覆盖写**，每次登录追加新版本。安全收益：
- 账号异常时可回滚到上一版本
- 可对比不同版本，识别异常登录
- 泄露单一版本不必然影响当前使用

## 6. 传输安全

| 项 | 现状 | 要求 |
|---|---|---|
| 目标站点 | 全部 HTTPS | — |
| 系统自身 | 取决于部署方式 | **生产必须启用 HTTPS**（反向代理终止 TLS） |
| 跨域 | `server.cors_origins` 白名单 | 生产收敛为实际域名 |
| 令牌传输 | `Authorization` 头 | 不用 URL 参数、不用 Cookie（降低 CSRF 面） |
| 传输层伪装 | `impersonate='chrome146'` + 固定 header 顺序契约 | 见 `09_功能设计_逆向SDK与签名层.md` |

### 6.1 关于传输层伪装的边界声明

系统采用浏览器指纹伪装（TLS 指纹、HTTP2、header 顺序契约），其**目的是与目标平台正常通信**——平台对非浏览器客户端有技术限制，伪装是为了让自部署的运营后台能够正常调用自己的账号能力。

> **明确不做**：不提供绕过账号安全验证、不提供批量注册、不提供规避平台风控频率限制的能力。
> 系统的频率设计（§8.3）方向是**更保守**而非更激进。

## 7. 合规护栏（二开必做）

> 商品笔记 = **商业推广内容**，合规要求显著高于普通种草笔记。

| 护栏 | 说明 | 实现位置 |
|---|---|---|
| **违禁词 / 敏感词过滤** | 广告法绝对化用语（最/第一/顶级/国家级）+ 平台违禁词 + 行业特殊词 | **生成后、入库前** |
| **功效宣称拦截** | 非特殊用途化妆品不得宣称功效（治疗/根治/美白/祛痘等） | 同上 |
| **长度与格式校验** | 标题 ≤20 字、正文 300–800 字、图片 1–18 张、3:4 比例 | 发布前 |
| **与商品一致性校验** | 卖点/价格必须来自**商品真相源**，**不允许 AI 编造** | 生成约束 + 生成后比对 |
| **人工审核闸门** | `auto_publish=false` **默认开启，建议长期保留** | 状态机 + 系统设置 |
| **AIGC 标识** | 如平台要求标注 AI 生成内容，需支持 | 发布体预留字段 |

> **口径更正（2026-09-19）**：一致性校验原文写「来自 `shop_products`」——**被设计 07 §10 的同一处更正取代**：
> 比对基准 = **实时取回的商品字段**（千帆商品接口按 `item_id` 精确查回），不依赖本地商品库。
> 理由与对照表见 `07_功能设计_发布链路.md` §10；实现见 07 §12.3（价格区间一致性）。

## 8. 写操作安全（发布）

### 8.1 发布是不可逆操作

```
发布成功 → 平台上出现真实笔记 → 删除需要人工操作 → 无法"撤销"
```

### 8.2 现有四道防线及其强度

| # | 防线 | 强度 | 缺陷 |
|---|---|---|---|
| 1 | 状态机 | 中 | 无原子性（检查与写入非同一事务） |
| 2 | 调度器 `max_instances=1` | **仅单进程内** | 多副本失效 |
| 3 | 补跑幂等（只取 `scheduled` 态） | 中 | 状态写入前崩溃会重发 |
| 4 | **数据库唯一约束** | 最高 | ❌ **缺失** |

### 8.3 建议补齐（二开必做）

| 措施 | 说明 |
|---|---|
| **`idempotency_key` 唯一索引** | 键构成：`{seller_id}:{item_id}:{account_id}:{素材hash}` |
| 发布前账号状态校验 | 过期账号直接拒绝，不进入流程 |
| 发布前商品状态与价格复核 | 商品可能已下架/改价 |
| 账号级互斥锁 | 同账号串行（DB 行锁或应用锁） |
| 频率护栏 | 每日上限 / 最小间隔 / 同商品冷却（落 `system_settings`） |
| 失败熔断 | 连续失败自动暂停任务，避免雪崩 |

## 9. 生产部署安全检查清单

| # | 项目 | 要求 | 不做的后果 |
|---|---|---|---|
| **S-1** | `SECRET_KEY` | 强随机值，非默认 | JWT 可被伪造 |
| **S-2** | `FERNET_KEY` | **显式固定，独立于 SECRET_KEY** | 改密钥 → 历史凭据永久不可解 |
| **S-3** | `BACKEND_CORS_ORIGINS` | 收敛为实际域名 | 任意源可携带凭证访问 |
| **S-4** | HTTPS | 反向代理终止 TLS | 令牌与凭据可被窃听 |
| **S-5** | `DATABASE_TYPE=mysql` | 生产用 MySQL | SQLite 并发写锁表 |
| **S-6** | 数据库访问控制 | 独立账号 + 最小权限 | DB 泄露面扩大 |
| **S-7** | 单副本运行 | 或自加分布式锁 | 重复发布 |
| **S-8** | 备份 | 定期备份 DB 与 `storage/media/` | 数据丢失（**尤其 Cookie 加密密钥）** |
| **S-9** | 依赖审计 | 定期扫 pip / npm 漏洞 | 供应链风险 |
| **S-10** | 日志脱敏 | 不打印 Cookie / API Key / 密码 | 日志泄露 |
| **S-11** | `api_logs` 接线 | 补 API 审计中间件 | 无操作追溯 |
| **S-12** | 登录限流 | 失败计数 + 锁定 | 暴力破解 |
