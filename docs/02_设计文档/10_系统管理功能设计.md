## 1. 设计目标

> **任何一个会影响系统行为的开关或配置项，都必须满足三条：**
> 1. **可发现** —— 在文档里有台账记录
> 2. **可管理** —— 后台有 UI 入口（不需要改文件、不需要重启）
> 3. **可追溯** —— 明确记录它存在哪里（数据库 / git 配置文件 / 代码常量）

反过来说：**只存在于配置文件、UI 无入口的开关，是管理缺陷；存在数据库但无运行时读取点的字段，是死配置。**

**UI 设计要点**：

| 要点 | 说明 |
|---|---|
| **每个开关必须显示「当前值 + 影响范围」** | 用户要知道改了会发生什么 |
| **区分「需重启」与「即时生效」** | `requires_restart=true` 的加显式标记 |
| **危险开关二次确认** | 「关闭定时任务」这类要弹确认框 |
| **展示实际运行状态** | 不能只显示配置值——要显示调度器**实际**是否在跑（避免「配置为 true 但没起来」的误判） |
| **未接线的项要显式标注** | 如 S9，要么接线要么标注「暂未生效」 |

### 3.3 落库策略（DB or git？）

> 这是设计的关键决策：**什么配置该进数据库，什么该留在 git？**

| 判据 | 进数据库（`system_settings`） | 留在 git 配置文件 |
|---|---|---|
| **是否会影响系统能否启动** | 否 → DB | **是 → git**（如 `database.type`） |
| **是否含密钥** | 否 | **是 → git / 环境变量**（如 `secret_key`、`fernet_key`） |
| **是否需要运行时热改** | **是 → DB** | 否 |
| **是否需要审计谁改的** | **是 → DB** | 否 |
| **是否是部署环境差异** | 否 | **是 → git**（如 `serve_static`、`cors_origins`） |
| **是否是业务策略参数** | **是 → DB**（如每日上限、冷却期） | 否 |

**套用到现有开关**：

| 开关 | 现状 | 目标 |
|---|---|---|
| `scheduler.enabled` | git YAML | **DB**（需热改 + 需审计，且不阻塞启动） |
| `frontend.serve_static` | git YAML | **保持 git**（影响启动装配，且是部署环境差异） |
| `secret_key` / `fernet_key` | git YAML | **保持 git / 环境变量**（密钥不进 DB） |
| `database.type` | git YAML | **保持 git** |
| 平台注册表 `enabled` | 代码常量 | **DB**（改为 `system_settings` 的 `feature.platform.<id>.enabled`） |
| 商品笔记护栏参数 | 不存在 | **DB**（业务策略） |

**混合策略**：**启动期配置读 git/YAML，运行期配置读 DB。**

```
启动（bootstrap）
  ├─ 读 YAML / 环境变量 → 数据库、密钥、CORS、静态服务
  └─ 读 DB system_settings → 覆盖运行期配置（需 DB 已可用）
```

> ⚠️ 注意顺序依赖：读 DB 需要 DB 已连接。因此 `database.type` 这类**绝对不能**放 DB。

### 3.4 API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/system-settings` | 列出全部设置（含 `label` / `description` / 当前值 / **实际生效状态**） |
| PUT | `/api/system-settings` | 批量更新（body 为 `{key: value}`），写 `updated_by` / `updated_at` |
| PUT | `/api/system-settings/{key}` | 单项更新 |
| GET | `/api/system-settings/audit` | 变更历史（可选，若不做独立审计表则从 `updated_by`/`updated_at` 追溯） |

**权限**：仅 `scope=global` 的设置需要管理员身份 —— ✅ **已具备条件**（2026-09-18，T-104）：
`users.role` 列已新增（`admin` / `user`），鉴权依赖 `core/deps.py::require_admin`（非管理员 403），
角色判定统一走 `core/roles.py::is_admin()`。

> ⚠️ **不要用 `sub_type` 判断身份**——`sub_type` 是**协议链路**（`pc` / `creator`），
> 与「是不是管理员」完全正交。两者失败策略也相反（见 ADR-014）。
>
> ⚠️ **迁移的引导规则生效前提**：迁移把**最早创建**的用户提升为 `admin`。
> 若该账号不是实际管理员，**部署后必须手工改一次**，否则全局设置无人可改。

## 6. 配置优先级缺陷（✅ 已实测确认并修复）

> **状态：2026-09-18 实测确证 → 当日修复 → 回归通过。** 本节保留完整记录以便追溯，但**不再是待办项**。

### 6.1 现象（修复前）

`backend/app/core/config.py:154-157`：

```python
@lru_cache
def get_settings() -> Settings:
    yaml_values = _load_yaml_config()
    return Settings(**yaml_values)      # ← YAML 值作为【初始化参数】传入
```

按 pydantic-settings 的取值优先级：**初始化参数 > 环境变量 > `.env` > 默认值**。

因此 `config/default.yaml` 里**已存在的键**（`scheduler.enabled`、`frontend.serve_static`、`server.cors_origins`、`database.*`、`security.secret_key` 等）会**覆盖同名环境变量**。

这与两处声明的「环境变量优先级最高」**相反**：
- `config/default.yaml:6-7` 的注释
- `backend/app/core/config.py:18-20` 的注释

### 6.2 影响面

| 影响 | 说明 |
|---|---|
| `Dockerfile:66` 设的 `FRONTEND_SERVE_STATIC=true` | **已实测被 `default.yaml:58` 的 `false` 覆盖** → 生产静态服务失效 |
| `docker-compose.yml:20-24` 注释推荐的 `SECRET_KEY` / `MYSQL_PASSWORD` 环境变量 | **已实测失效** → 生产用了默认弱密钥 |
| 二开的 `SCHEDULER_ENABLED` 等环境变量注入 | **已实测失效** → 后续新增配置项会重蹈覆辙 |

### 6.3 ✅ 实测结论与修复（2026-09-18）

| 项 | 内容 |
|---|---|
| 置信度 | ✅ **已实测确认**（Python 3.12 / pydantic-settings 2.15.0）。注入 `SCHEDULER_ENABLED=true` / `FRONTEND_SERVE_STATIC=true` / `SECRET_KEY=ENV_SECRET_WINS` → 实际取值 `False` / `False` / `'dev-only-change-me'`，**三个全部失效** |
| 修复任务 | T-010（验证）→ **T-110（修复，✅ 完成）** |
| **实际采用的修复方式** | 方案①的**正规做法**：在 `Settings` 上实现 `settings_customise_sources`，把 YAML 注册为**最低优先级源** `_YamlSettingsSource`（`init > env > .env > YAML > secrets`），并**去掉** `get_settings()` 里 `Settings(**yaml_values)` 的初始化参数（初始化参数优先级最高，**正是根因**） |
| **明确否决的方式** | ❌ 方案②「从 `default.yaml` 删键」——会让 YAML 的配置能力**整体退化**，属于把一种错误换成另一种错误 |
| 落点 | `core/config.py`（`_YamlSettingsSource` + `settings_customise_sources` + `get_settings()`） |
| 回归 | `test_m1_governance.py` 3 条：正向（环境变量必须生效）/ 反向保护（**YAML 必须仍然生效**）/ 顺序锁定（防止一次重构改回去） |

## 7. 落地实现：运行时配置中心 `system_settings`（2026-09-27）

> **来源**：用户口径（2026-09-27）「配置表再设置页面实现前端的列表和增删改查，实现页面实时配置」。
> 本节是 §3「目标设计」的**落地版**，并结清 §5.1 的 **P-3**（缓存失效）。
> 触发它的直接原因见设计 13 §38：`crawl_rate_limit_per_minute` 声明 60、实际跑 5 —— 一个
> **「存在配置文件、UI 无入口、运行时读不到」** 的典型管理缺陷（正是 §1 要消灭的那类）。

### 7.1 与 §3 目标设计的差异（原句保留，逐条给理由）

| # | §3 原设计 | 本次落地 | 理由 |
|---|---|---|---|
| D1 | 表名 `system_settings`，列含 `scope`（`global` / `user`）+ `user_id` **nullable** | **表名沿用** `system_settings`；**去掉 `scope` 列**，`user_id` **必填**（FK `users.id`） | 全项目口径已统一为「**所有配置行必归属用户**」（DEF-066，`scheduled_jobs` 的 `user_id IS NULL` 全局行已整条退役）⇒ `scope` 是同一语义的第二份表达（DEF-044）。行按用户各持一份，天然隔离 |
| D2 | `GET/PUT /api/system-settings`，PUT 批量 | `GET/POST /api/settings` + `GET/PUT/DELETE /api/settings/{key}`（**增删改查齐全**） | 用户本次明确要「**增删改查**」；§3 只有「批量改」没有「增 / 删」。路径简化为 `/settings`（与前端 `/settings` 页同名） |
| D3 | `scope=global` 的设置需 `require_admin` | **不做管理员门禁**（只用 `get_current_user` + 归属校验） | 行是**用户私有**的（D1）⇒ 不存在「一个用户改到别人配置」的面；`require_admin` 目前**全项目零使用**，为它单开一条未测过的鉴权路径没有安全收益，只有新故障面（非 admin 用户整页 403） |
| D4 | 无「生效性」字段 | 新增 `is_live`（**派生，不落库**）：该 key 是否接进运行时读点，由代码白名单 `LIVE_KEYS` 判定 | §3.2 的「未接线的项要显式标注」需要**可判定**的判据。用户加的自定义 key 只存档、不生效 —— UI 必须说出来，不许让用户以为改了有用（硬约束⑤同源：不造假） |
| D5 | `updated_by` / `is_dangerous` / `requires_restart` | **全部保留** | 它们正是「可追溯」与「危险开关二次确认」的载体，无理由删 |
| D6 | P-3 缓存失效「随 T-701 一起设计」 | **本次落地**：进程内缓存 + **写后立即失效** + TTL 兜底 | 见 §7.4。事后补 = 存在「改了不生效」的时间窗（正是 P-3 警告的怪现象） |

### 7.4 实时生效机制（结清 P-3）

```
读：live_value(key)
      ├─ 进程内缓存命中且未过期 → 直接用
      ├─ 未命中 → 查 DB（按 user_id 收口）→ 写缓存
      └─ DB 无行 → 回落 settings（YAML/env）→ 再回落内置默认
写：POST / PUT / DELETE
      ├─ 落库 + commit
      └─ **立即清该 key 的缓存**（同进程内下一次读就是新值）
```

* **写后立即失效**是主路径（页面改完**下一次平台请求**就用新值，不重启、不等 TTL）；
* **TTL 兜底**（默认 3 秒）只为「多进程 / 手工改库」这类缓存失效通知到不了的场景；
* 为什么不用 `get_settings()` 的 `lru_cache`：那是**启动期**配置（YAML/env），
  语义是「进程生命周期内不变」；运行期配置必须能变 —— 两套缓存**不能混用**（§3.3 的分层）。

### 7.5 API 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/settings` | 列表（可按 `category` 筛选）；每项带 `value` / `value_type` / `label` / `description` / `is_live` / `requires_restart` / `is_dangerous` / `updated_at` |
| POST | `/api/settings` | 新增（key 已存在 ⇒ 409） |
| GET | `/api/settings/{key}` | 单条 |
| PUT | `/api/settings/{key}` | 改值（只改 `value`；`label` / `description` 等元数据也可改）；key 不存在 ⇒ 404 |
| DELETE | `/api/settings/{key}` | 删除 ⇒ **回落**到 settings / 内置默认（响应里回 `effective_value`，让前端立刻显示回落后的值） |

**`is_live` 白名单**（代码侧，`settings_service.LIVE_KEYS`）—— 只有这些 key 改了**真的立刻生效**：

| key | 类型 | 读点 |
|---|---|---|
| `crawl_rate_limit_per_minute` | int | `rate_limiter.CrawlRateLimiter.max_per_minute`（设计 13 §38.2） |
| `xhs_sync_account_parallelism` | int | 同步 worker 池大小（设计 13 §38.3） |
| `xhs_sync_account_gap_seconds` | int | 调度轮内账号间停顿 |
| `xhs_allow_duplicate_goods_publish` | bool | 商品笔记重复发布开关（设计 13 §31.5.2；默认 `false` = 同一商品不许重复发布） |

> ⚠️ 白名单**只增不减**：新增一个运行时读点就要在这里加一行，否则 UI 会把「已接线」说成
> 「仅存档」（负向失真同样是不诚实）。反向：用户自定义的 key 不在白名单 ⇒ UI 显式标注「仅存档，无运行时读点」。

`pages/settings/settings-page.tsx` 在既有「安全边界」卡之外，新增「系统参数」卡：
