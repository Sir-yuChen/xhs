# M3 真机探测结论：平台侧「热门话题」只读入口（2026-10-04）

> 对应任务卡 `t_46c61f6d` 验收标准第 1 条：「真机探测结论有原始输出
> （接口存在 ⇒ 贴响应；不存在 ⇒ 明确写「不可得」+ 理由）」。
> 探测脚本：`.workbuddy/tmp/m3_hot_topic_probe.py`（ark / creator / www 三通道）
> 与 `.workbuddy/tmp/m3_hot_topic_probe_www.py`（www 侧补全）；
> 原始输出：`.workbuddy/tmp/probe_result.json`、`.workbuddy/tmp/probe_www.json`。
> 账号：`platform_accounts` id=7（pc/www）、id=8（creator + ark，昵称「观隅好物」）、
> id=9（qianfan）、id=10（pc）、id=11（creator）。

## 0. 一句话结论

**小红书平台侧不存在「无参数、全局热门话题榜」的只读入口。** 我们把项目已接入的
三条只读通道（www / creator / ark）逐条真机打了一遍，能拿到「带热度的话题」的
**只有 ark 一个端点，且它必须带商品 ID**；www 与 creator 通道要拿到任何话题，
都必须先有一个**种子词**。

设计 16 §3.2 写的「www 热搜词/话题」**在 www API 里不存在**——小红书的「热搜」
是**搜索结果页的附属物**（`hot_query`「大家都在搜」），不是独立榜单端点。
本结论**取代**设计 16 §3.2 的这句表述（原句保留在 §5 对照表）。

## 1. 逐端点原始输出

### 1.1 ✅ ark `/api/edith/aigc-publish/attributes` —— 唯一带真实热度的入口

* **可读**：只读查询 POST（商品笔记 AI 生成的属性面，项目早已接入，设计 13 §31）。
* **入参**：`{"aigc_note_creation_query": [{"item_id": "<商品ID>", "sku_id": ""}]}`。
* **实测账号**：id=8（观隅好物，ark 令牌有效），商品
  `6a581608ab42de00152e782c`（中式椭圆形桌垫…）。
* **实测响应**（`success=true, msg="成功"`，`topic_list.topic_list_info[]`）：

| topic | type | hot_value |
|---|---|---|
| 毛孩子时装周 | 2（活动话题） | — |
| 椅子套罩 | 1 | 760 |
| 桌旗 | 1 | 2794 |
| **餐垫** | 1 | **4673** |
| 餐桌布 | 1 | 1781 |
| 结婚桌子摆盘 | 1 | 438 |
| 餐边柜垫子推荐 | 1 | 483 |
| 拼豆隔热垫 | 1 | 508 |
| 防水桌布 | 1 | 563 |
| 茶几桌布推荐 | 1 | 1120 |
| 椅子静音脚套 | 1 | 453 |

  *热度是平台下发的真实值（不是我们算的），跨度 438–4673。*

* **限制（关键）**：**必须带 `item_id`**。话题是**按商品类目**推荐给这个店铺的，
  不是全局榜。同一店铺换一个商品，话题跟着类目变（这是它「按商品推荐」的语义，
  不是缺陷，但**不能当作「平台热搜榜」用**）。
* **字段名**：`topic`（不是 `name`）、`type`（1=话题，2=活动话题）、`hot_value`。

### 1.2 ⚠️ www `/api/sns/web/v1/search/recommend` —— 联想词，不是榜

* **实测**（账号 7，种子词 `防晒 / 穿搭 / 好物 / 家居`）：全部 `success=true`，
  响应键 = `search_cpl_id / sug_items / word_request_id`。
* **`sug_items` 是「搜索建议词」**（补全查询），**不是热搜榜、没有热度值、没有排名**。
* **空种子词不可用**：`get_search_keyword("")` 只回 `word_request_id`，
  `sug_items` 为 `null` —— **无法空手取榜单**。
* 结论：**它不是「热门话题」入口**，且设计 16 §3.2 把它写成「热搜词」是错的。

### 1.3 ⚠️ www `/api/sns/web/v2/search/notes` 的 `hot_query` —— 搜索结果的附属物

* **实测**（账号 7，关键词「防晒」，22 条 items，`model_types = [hot_query, note]`）：
  `hot_query` 条目标题为「**大家都在搜**」，`queries[]` 每条含
  `id / name / search_word / cover`，**无热度值**。
* 例子：`防晒排名前十`、`军训防晒`、`适合黄黑皮的防晒霜`、`防晒排行榜第一名`、
  `央视认可的防晒`、`好用的防晒霜推荐`…
* **限制（关键）**：**必须先有关键词**（`hot_query` 是「搜了这个词的人还在搜什么」，
  语义上属于**搜索词的延伸推荐**，不是全局话题榜）。
* 项目现状：`pc.py::_normalize_search_item` **显式过滤掉了** `hot_query` /
  `rec_query` 条目（只留 `note`）⇒ 目前完全没被使用，是真数据但被丢弃。
* 结论：**它是「关键词的延伸」，不是「话题榜」**，且需要种子词。

### 1.4 ❌ creator `/web_api/sns/v1/search/topic` —— 话题搜索，需关键词

* **实测**：账号 8 的 creator 令牌**签名服务超时**（`ds fetch failed … timed out
  after 8014ms`，两次）；账号 10 返回「账号存在风险，请重新登录」。
* 结论：端点存在但**本机当下不可用**（令牌问题，非端点问题）；即使可用，
  它的语义是**按关键词搜话题**（发布链路用来把话题名解析成平台话题 ID），
  **同样需要种子词，且不按热度排序**。
* **不影响 M3 结论**：它从来就不是「热门话题榜」的候选。

### 1.5 ❌ www `/api/sns/web/v1/homefeed/category` —— 频道，无话题

* **实测**（账号 7，`success=true`）：返回 11 个频道（穿搭 / 美食 / 彩妆 / 影视 /
  职场 / 情感 / 家居 / 游戏 / 旅行 / 健身 / 视频），**只有频道，无话题、无热度**。
* 结论：**不是话题入口**，但它给出的**频道分类**可以作为「自有话题热度榜」的
  `category` 维度来源（见 §3）。

### 1.6 穷举确认：SDK 里没有别的话题榜端点

`apis/` 全量扫描，与「热门/热度/话题」相关的只读端点只有上述 4 个
（`search/recommend`、`search/notes` 的 `hot_query`、`search/topic`、
`aigc-publish/attributes` 的 `topic_list`）。**没有任何无参数的全局榜单端点。**

## 2. 为什么「平台热搜榜」不可得（根因）

1. 小红书的「热搜」产品形态是**搜索页的附属区块**（「大家都在搜」），它的数据
   依赖一个**搜索上下文**（关键词），不存在「打开就给你 50 条全网热词」的 API。
2. 平台对**话题**的分发是**按场景**的：创作者发布时按商品/类目推荐
   （`aigc-publish/attributes` 的 `topic_list`），用户搜索时按关键词延伸
   （`hot_query`）。**没有「全局话题热度榜」这个产品**。
3. 我们不能自己去抓网页端的热搜页（那是浏览器渲染页 + 反爬，且**不是项目已接入
   的只读 API**——属于新增采集面，违反「先真机探测确认平台侧有无该只读接口」的
   前置条件，且不稳定）。

## 3. 结论：M3 用什么口径做「热门话题」

任务卡明确允许的替代方案：「**从已同步的笔记里统计话题出现频次作为『自有话题
热度』—— 这是真实数据，但必须明确标注口径不是『平台热搜榜』**」。

**M3 采用双源口径，两源都标明出处**：

| 源 | 口径名称（页面明示） | 数据 | 热度 | 触发 |
|---|---|---|---|---|
| **A（主）** | **自有话题热度榜** | `topics` + `note_topics`（已同步的 3623 篇笔记里 3193 个话题，4695 条关系） | **本地统计**：话题被关联的笔记数 + 该话题下笔记的互动量（点赞/收藏/评论之和） | 纯本地，零平台请求 |
| **B（辅，真实平台热度）** | **平台推荐话题（按商品类目）** | `aigc-publish/attributes` 的 `topic_list.topic_list_info[]` | **平台下发的 `hot_value`**（实测 438–4673） | 只读 POST，须带 `item_id`，按账号限流 |

* **A 是主榜**：它回答「我的笔记池子里什么话题出现得多、互动好」—— 这才是
  运营「自有话题热度」该回答的问题，且**零平台请求、零限流风险**。
* **B 是可选的真实平台热度来源**：当用户选中一个商品（或一个店铺账号）时，
  可以取该账号 ark 通道的 `attributes`，拿到平台**按这个商品类目**推荐的话题和
  `hot_value`。**页面必须标明「按商品类目推荐，非全局热搜」**。
* **两者在 `hot_topics.source` 列区分**（`local_frequency` /
  `platform_recommended`），页面与 API 响应都带这个标记，**不混称为「热搜榜」**。
* **不采用** `hot_query`（搜索附属物，需关键词，无热度值）——它对「话题驱动
  生成」没有增量价值，且引入「关键词从哪来」的依赖。

## 4. 数据口径与「不许造假」对照

| 设计 16 §10 原字段 | M3 落地口径 |
|---|---|
| `hot_topics.heat` | A 源 = 本地统计的互动量合计；B 源 = 平台 `hot_value`（原值） |
| `hot_topics.trend` | **留空**（单次快照无法算趋势；需要两次快照的差值，本期不做预测，**不造趋势**） |
| `hot_topics.category` | A 源 = 互动最好的笔记的类目线索（无类目则空）；B 源 = 商品类目 |
| `hot_topics.snapshot_at` | 采集时刻（`shanghai_now`） |
| `topic_goods_match.relevance_score` | **本地计算**：关键词命中 + 词频/TF 重叠（见 § matcher 设计），**不是造的分** |

**趋势列的处理**：任务卡验收标准要求「匹配结果落库且按相关度排序（分数不是造的）」，
`trend` 列保留在表里但**首期不填**（缺值留空，符合项目「缺值口径」），等积累
两次以上快照后，后续需求再填 —— **不在首期造趋势**。
