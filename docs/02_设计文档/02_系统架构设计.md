### 1.1 分层硬约定

| 约定 | 内容 | 违反后果 |
|---|---|---|
| **单向依赖** | 上层可依赖下层，下层**不得**反向 import 上层 | 循环依赖 |
| **`apis/` 禁止直接改** | 上层必须经 `adapters/` 中转 | 逆向代码变更影响面扩散到全项目 |
| **API 层不含业务规则** | 路由函数只做鉴权 + 校验 + 调 service | 业务规则分散，无法复用 |
| **时区唯一入口** | 一切时间取 `backend/app/core/time.py::shanghai_now()` | 混时区导致排期错乱 |

## 4. 开发环境与生产环境如何隔离（图片第 4 项要求）

### 4.1 隔离矩阵

| 维度 | 开发环境 | 生产环境 | 隔离机制 |
|---|---|---|---|
| **配置来源** | `config/default.yaml` | 同名 YAML + 环境变量 | `CONFIG_FILE` 指向不同文件；环境变量覆盖 |
| **数据库** | SQLite 单文件 `data/spider_xhs.db` | MySQL 8 | `database.type` 切换；`database_url` 由组件字段拼装 |
| **前端资源** | Vite dev server（HMR，独立进程） | `frontend/dist` 静态文件，后端托管 | `frontend.serve_static` |
| **API 地址** | 浏览器访问 `:5173`，Vite 代理 `/api` | 浏览器访问 `:8000`，同源 | Vite proxy（仅 dev） |
| **CORS** | 需放开 `localhost:5173` 等 | 同源部署，无需 CORS | `server.cors_origins` |
| **调度器** | 默认关闭（`scheduler.enabled=false`） | 显式开启 | `SCHEDULER_ENABLED` |
| **密钥** | `secret_key="dev-only-change-me"` | **必须显式固定** | 环境变量 `SECRET_KEY` / `FERNET_KEY` |
| **日志/调试** | `--reload`，异常栈可见 | 无 reload | 启动参数 |
| **数据持久化** | 本地文件 | 容器卷 / 外部 MySQL | 部署配置 |
| **代理环境变量** | 开发机可能设 `HTTP_PROXY`，请求时被临时剥离 | 生产一般无 | `adapters/xhs/request_env.py:21-35` |

### 4.2 生产部署的强制清单

| # | 项目 | 要求 | 不做的后果 |
|---|---|---|---|
| **P-1** | `SECRET_KEY` | 必须改为强随机值 | JWT 可被伪造 |
| **P-2** | `FERNET_KEY` | **必须显式固定**且独立于 `SECRET_KEY` | 改 `SECRET_KEY` → 历史 Cookie/API Key 全部解不开 |
| **P-3** | `DATABASE_TYPE=mysql` | 生产用 MySQL | SQLite `journal_mode=MEMORY` 并发写易锁表 |
| **P-4** | `SCHEDULER_ENABLED` | 按需显式开启 | 默认 false → 定时发布/自动运营/Cookie 巡检**全部静默不生效** |
| **P-5** | `BACKEND_CORS_ORIGINS` | 收敛为实际域名 | 放开任意源 |
| **P-6** | 单副本运行 | 或自行加分布式锁 | 多副本 → 调度器重复执行 → **重复发布** |

> ⚠️ **已知配置优先级缺陷**：`get_settings()` 把 YAML 展平结果作为**初始化参数**传给 `Settings(**yaml_values)`（`backend/app/core/config.py:154-157`）。按 pydantic-settings 语义，初始化参数优先级**高于**环境变量，因此 `config/default.yaml` 里已存在的键会**覆盖同名环境变量**——与配置文件头部注释声明的「环境变量优先级最高」相反。**生产部署前必须实测确认**，否则 P-1/P-4 会静默失效。详见 `10_系统管理功能设计.md` §5。

## 5. 用户量与并发设计（图片第 3 项要求）

### 5.1 用户量假设

| 维度 | 假设值 | 依据 |
|---|---|---|
| 部署形态 | 单机自部署，单实例 | 项目定位为「自部署运营后台」 |
| 注册用户数 | 1–10 人 | 团队内部使用 |
| 同时在线 | 1–5 人 | 运营人员不会同时操作同一后台 |
| 绑定的小红书账号数 | 10–500 个 | 矩阵铺量场景；非店铺账号可能数十个 |
| 自动运营任务数 | 10–200 个 | 每个任务绑定一对（pc, creator）账号 |
| 日发布量 | 十至数百篇 | 受平台风控与人工审核闸门约束 |

> **结论：这是一个「低并发、低频、高单价操作」的系统。** 单个操作（一次采集、一次发布）耗时长（秒级到分钟级），但并发请求数极少。容量设计的重点是**长任务的资源占用**与**写操作的互斥**，而非 QPS。

### 5.2 请求量级估算

| 场景 | 单次耗时 | 说明 |
|---|---|---|
| 一次 PC 搜索（1 页） | ~1s | 含 1 次 Node 签名（~100ms）+ HTTP |
| 一次笔记详情 | ~1s | — |
| 一次图集发布 | 5–30s | 逐张上传素材 + 建笔记 + 发布 |
| 一次自动运营任务 | 30–120s | 搜索 → 改写（AI，秒级）→ 上传 → 发布 |
| Cookie 全量巡检 | 与账号数线性 | 每 2 小时一次，逐个账号探测 |

### 5.3 关键并发约束

| # | 约束 | 原因 | 实现位置 |
|---|---|---|---|
| **C1** | **同账号发布必须串行** | 并发发布 = 重复发布 + 风控双重风险 | 调度器 `max_instances=1` + 发布状态机 |
| **C2** | **定时任务单实例执行** | 避免同一 job 堆叠 | `max_instances=1, coalesce=True`（`scheduler_service.py:707-735`） |
| **C3** | **签名 Node 子进程按需拉起** | 每次签名一个进程，无池化 | 单请求开销 ~100ms，无并发争用问题 |
| **C4** | **代理环境变量的临时剥离需加锁** | 多线程同时摘/恢复环境变量会互相干扰 | `adapters/xhs/request_env.py`（加线程锁） |
| **C5** | **SQLite 写操作串行** | `journal_mode=MEMORY`，非 WAL | 生产改 MySQL |
| **C6** | ⚠️ **多副本不安全** | APScheduler 与 FastAPI 同进程，每副本各起一套定时器 | **未解决**（技术债 T-03） |

### 5.4 容量瓶颈与扩容路径

```
当前瓶颈排序（单机）：
  1. 平台侧风控（不可控）        ← 真正的天花板
  2. 平台侧限流（不可控）
  3. 本机 CPU（Node 子进程 + 图片处理）
  4. 数据库写锁（SQLite 时）
  5. 网络往返（xhs API）
```

**扩容策略**：

| 阶段 | 做法 |
|---|---|
| 账号数 < 100 | 单机 SQLite 足够 |
| 账号数 100–500 | 换 MySQL；巡检分级降频 |
| 需要多副本 | **先解决 C6**（加 DB 分布式锁），否则不要扩容 |
| 采集量极大 | 采集与发布拆成两个进程/实例，共享 DB |

### 5.5 频率设计（平台风控对齐）

| 操作 | 建议频率 | 理由 |
|---|---|---|
| 普通笔记发布 | ≤ 10 篇/日/账号，间隔 ≥ 30min | 避免营销号判定 |
| **商品笔记发布** | **≤ 5 篇/日/账号，间隔 ≥ 60min** | 商业推广内容风控更严 |
| 同一商品重复推广 | 冷却 ≥ 72h | 避免刷屏 |
| Cookie 巡检 | 2h 一次（全量） | 平衡时效与请求量 |
| 采集搜索 | 按需，页间隔随机 | 降低被识别为爬虫的概率 |

## 8. 架构层面的已知缺口

| # | 缺口 | 影响 | 处理 |
|---|---|---|---|
| A-1 | 多副本调度无分布式锁 | 重复发布 | 技术债 T-03，二开前建议优先修 |
