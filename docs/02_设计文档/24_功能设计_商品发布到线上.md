## 1. 真机取证：提交商品的确切形状

### 1.1 端点与参数（Network 抓 `postData` 逐字）

```
POST https://ark.xiaohongshu.com/api/edith/product/batch_create_item   （需签名 x-s/x-t）
body = {
  "itemData": [ <完整商品表单 25 个顶层字段> ],
  "options":  { "asyncExec": true, "withChild": true, "retrieveResult": true },
  "publishMode": 1        # ⚠️ 见 §1.4
}
→ {"code":200,"data":{"taskId":"…"}}
```

### 1.2 `itemData[0]` 顶层字段（真机实测 25 个）

```

### 1.3 `skuData[]` 每条（真机实测 10 个字段）

```jsonc
{
  "rowNumber": 1,
  "ipq": 1,                                  // 每件装数
  "price": {
    "price": 128000,                          // ⚠️⚠️ 单位是「分」！
    "includeTax": false,
    "priceInfo": { "preTax": 128000 }         // 必填，缺则平台报「售价计算失败」
  },
  "logisticsPlanId": "6a327c3bd0f2c70015312abe",
  "specImage": { <图片条目> },                 // mainSpecEnable=1 时每个 SKU 都要
  "deliveryTime": { "type": 4, "time": "48" },
  "variants": [
    { "attributeId": "60404e0de85df80001991224", "attributeName": "颜色分类",
      "attributeType": 1, "attributeValue": "实木三斗柜" }
  ],
  "available": true,
  "stockChange": 0,
  "stock": 0
}
```

### 1.4 ⚠️⚠️ **最容易搞反的两处**（守卫必须钉住）

1. **`price` 是「分」不是「元」** —— 与设计 23 的**草稿体相反**！
   * 草稿体（`create_product_drafts`）：`price: 1280` 回读 `1280`（**元**）。
   * **发布体**（`batch_create_item`）：页面填 **1280（元）** ⇒ 抓包 body 里是
     **`price: 128000`（分）**。bundle `8091.*.js` 逐字佐证：
     `basePriceInfo.price/100`（读形态分→元）。
   * ⇒ **两条链路的单位不同**，混用必错（且平台不报错，只是价格差 100 倍）。
     守卫：`create_item_body(price_yuan=1280)` 的 `price.price == 128000`。

2. **`publishMode`** 取值（bundle `publishMode:function()` 逆出）：
   `isBaseImagesCreateMode || opportunityId ⇒ 2 / isAiAssistant ⇒ 3 / 否则 ⇒ 1`。
   * 真机「基础图创建」路径抓到的是 **2**；
   * **普通发布用 1**（设计 20 起沿用）。
   * 本链路**固定用 1**（普通发布），2/3 是平台的其它入口。

### 1.5 图片条目形状（主图 / 详情图 / 规格图 三处同形状）

```jsonc
{
  "key": "<materialId>", "type": "spaceImage", "materialId": "<id>",
  "name": "SKU01_颜色分类(…)", "width": 800, "height": 800, "size": 115712,
  "extension": ".jpeg", "path": "arkgoods/1040g0o…",
  "link": "https://qimg.xiaohongshu.com/arkgoods/1040g0o…",
  "uploaderInfoModel": { "bizName":"ark","cloudType":4,"fileId":"arkgoods/…",
                          "isSecret":false,"scene":"goods_image","url":"https://…" },
  "errors": []
}
```
（与设计 22 图片空间 `additionalData` 同源，`specImage` 多一层嵌套。）

### 1.6 `publish_async` = **只读预检**，不是发布

真机抓到 32 个 `publish_async` 请求，**全部是只读预检 action**（一个都不改状态）：

```
getMaterialRule / checkNeedBrand / searchMarketableBrands / getCategoryProperty /
getSupportNoLogistics / getSellerCarriageTemplate / getSetSizeTableInfo /
getPriceLimit / getSalePropertyNumLimit / getProductQualificationRule /
getRecommendBrand / getRecommendCategory / getRecommendItemTitle /
checkMainImageWithWhite / getPropertyGroups / itemAuditPreCheck /
productTitleCheck / productShortTitleCheck / predictProductProperty …
```
body 形如 `{"data":"{\"publishType\":1,\"sourceType\":1,\"actions\":[{\"action\":…,\"param\":{…}}]}"}`。
⇒ 可用作**发布前体检**（设计 §3 的预检端点），但 **不产生商品**。

## 2. 数据模型：**零新表**

发布是**一次性写操作**，不落本地镜像（同设计 23 口径：草稿 / 商品的唯一真相源在平台）：

| 数据 | 落库 | 位置 |
|---|---|---|
| 提交记录（谁在何时发布了哪些商品） | ✅ 落本地 | `tasks`（`task_type = xhs_shop_item_publish`） |
| 商品本体 | 落**平台** | `search_item_v2` 可查（在售 / 审核中） |
| 图片 | 落**平台图片空间** | 复用设计 22 |

## 3. 端点契约（2 个新端点）

挂在 `qianfan.py` 现有 router（`/api/xhs/qianfan`），归属校验复用 `_owned_account`。

| # | 端点 | 语义 | 平台请求 |
|---|---|---|---|
| 1 | `POST /api/xhs/qianfan/items/publish` | **提交商品**：收「发布草稿 id」或「数据包 + 表单」，组装发布体 → 提交 → 轮询终态 → **立刻下架**（红线） | N 次（1 create + 轮询 + 1 off-shelf） |
| 2 | `POST /api/xhs/qianfan/items/precheck` | **发布前体检**（只读）：跑 `publish_async` 的预检 action，逐条回结果 | 只读 |

### 3.1 字段级契约

```python
# 1: 提交商品（⚠️ 结构上带显式二次确认位；无它就是不发）
class ItemPublishRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    platform_account_id: int = Field(ge=1)
    draft_id: str | None = Field(default=None, max_length=64)   # 二选一
    package_path: str | None = Field(default=None, max_length=512)
    confirm_off_shelf: bool = True   # ⚠️ 发布成功立即下架（红线，默认开）

ItemPublishResult = {
    "task_id": str,
    "item_id": str | None,          # 终态回执里的商品 id
    "published": bool,
    "off_shelf": bool,              # 是否已下架（红线执行结果）
    "fail_reasons": [{"index": int, "name": str, "message": str}],
}
```

### 3.2 三条必须钉住的口径

1. **`price` 单位是分**（§1.4.1）——`create_item_body` 里 `round(price_yuan*100)`。
   守卫：`test_price_is_fen_in_publish_body`（变异：改成元 ⇒ CAUGHT）。
2. **`publishMode` 恒 1**（普通发布）——常量 `PUBLISH_MODE_NORMAL = 1`。
   守卫：变异成 2/3 ⇒ CAUGHT。
3. **发布成功必须下架**（红线）——`confirm_off_shelf` 默认 `True`，
   `publish → off-shelf` 两步不可拆。守卫：断言成功路径**必然**调
   `batch_update_availability(available=False)`（变异：跳过 ⇒ CAUGHT）。

## 4. 业务逻辑

### 4.1 发布体组装（`shop_item_publish.py`，纯逻辑可单测）

```
1) 取骨架：publish_render({publishType:2, sourceType:1, itemId=<本店任一商品>})
2) 合并用户填的值：name / categoryId / images / imageDescriptions /
   attributes / variantIds / variantSequence / skuData
3) 单位换算：price 元→分（×100）；图片条目补 uploaderInfoModel
4) 平台强制字段：isGeneralSettings / stockType / deliveryMode / freeReturn /
   sizeTableType 系列 / usePlayback / enableMultiWarehouse / source=2
```

### 4.2 执行链（`shop_item_publish_service.py`，有写操作）

```
1) 组装发布体（§4.1）
2) POST batch_create_item → taskId
3) 轮询 query_task_status 至 status∈{3,4,5}
   ├─ success=true ⇒ 发布成功
   └─ failData[] 逐条报（不静默）
4) ⚠️ 红线：成功 ⇒ **立刻** batch_update_availability([item_id], available=False)
5) 回执：task_id / item_id / published / off_shelf / fail_reasons[]
```

### 4.3 发布前体检（`precheck`，只读）

跑 `publish_async` 的关键预检 action（`itemAuditPreCheck` / `productTitleCheck` /
`checkMainImageWithWhite` / `getPriceLimit` …），把平台原话逐条返回，
**在提交前把「平台会拒的理由」先摆出来**（降低一次发布失败一次改的成本）。

> ⚠️ **别和「数据包预检」混为一谈**（两个不同的预检）：
>
> | 名称 | 是什么 | 端点 | 是否碰平台 |
> |---|---|---|---|
> | **发布前体检**（本节） | 拿平台**自己**的预检 action 再问一次 | `POST /items/precheck` | ✅ 只读平台 |
> | **数据包预检** | 读**用户本地数据包**（媒体 + 表格 + 违规词 OCR），产出媒体清单与 SKU 表 | `POST /xhs/package-precheck/local` 等 | ❌ **零平台请求** |
>
> 「数据包预检」的完整口径（含 2026-10-11 的四条口径变更）见 **§18**。

### 9.2 ⚠️ 本轮实测抓到并修掉的问题（**全部真机**）

1. **`materialId` 必须是登记返回的记录 id，不是上传凭证 `fileId`**。
   用 `fileId`（`arkgoods/XOARE…`）平台报「获取图片信息失败，请检查图片是否正确后重试」。
   ⇒ 取 `register_material_files` 回执的 `data.directoryManageables[0].id`。
2. **登记的 `path`/`link` 是平台**登记时新分配的 CDN id**（`arkgoods/1040g…`）**，
   与上传凭证 `fileId` 不同。三处（`path`/`link`/`uploaderInfoModel.fileId`）必须同值。
   ⇒ 登记后**回读**该记录取真值（图片空间搜索**最终一致**：登记后立刻搜 0 命中，
   ~1–2 秒可见 ⇒ 轮询 6 次 × 1s）。
3. **成功判据不能看 `result.success`**：真机发布成功时它竟是 `false`！
   正解 = `failData` 空 **且** `itemIds` 非空。看错会把成功判成失败、
   **跳过硬线（下架）** —— 本次**实测踩中**（第一次跑通时商品真上架了，
   靠人工兜底下架）。
4. **下架 / 删除类任务回执形状不同**：`{"failCount":0,"successCount":3,"total":3}`
   （无 `failData`/`itemIds`）⇒ 判据 = `failCount==0`。复用发布判据会把成功判成失败。
5. **`logisticsPlanId` 是店级的，既有商品骨架里常缺**（平台报「商品必填信息
   [logisticsPlanId]未填写」）⇒ 从 `publish_render({publishType:1, sourceType:1})`
   的 `fulfillmentInfo.logisticsPlanList[0].planId` 取。
5b. ⚠️ **`shippingTemplateId`（运费模板）不在 `publish_render` 里**（DEF-100，2026-10-09）：
   空白 `publish_render` 的 `fulfillmentInfo` **只有** `logisticsPlanList` / `logisticsPlanStatus`
   —— **既无 `shippingTemplateList` 也无 `defaultShippingTemplate`**。运费模板必须单独调
   `getSellerCarriageTemplate`，取 `data.fulfillmentInfo.shippingTemplateList[]` /
   `.defaultShippingTemplate`（详见设计 28 §二·补）。两个字段**两个数据源**，不可互相替代。
6. **骨架必须剥掉读形态 / 尺寸表字段**：`standardSizeTableInfo`（平台：此类目不支持
   尺码表配置）、`standardImages` / `longImages` / `properties` / `itemName` /

## 10. 规格图形状差异（2026-10-10 真机确认）

真机发布体里 **规格图 `skuData[].specImage` 与主图 `images[]` 形状不同**（逐字段对比）：

| 字段 | 主图 `images[0]` | 规格图 `specImage` |
|---|---|---|
| `path` / `link` | `arkgoods/1040g0o…` | **`material_space/27c724d8-…`（UUID）** |
| `materialId` / `key` | `6ac9b4cc…`（登记记录 id） | `27c724d8-…`（UUID） |
| `uploaderInfoModel` | `{bizName:"ark", cloudType:4, fileId, isSecret:false, scene:"goods_image", url}` | `{cloudType:0, isSecret:false, setBizName:false, setCloudType:false, setFileId:false, setIsSecret:false, setScene:false, setUrl:false}` |

### 根因

- **主图 / 详情图**：走 `upload_web_permit(biz_name=ark, scene=goods_image)` → `arkgoods/<id>` 桶，登记后 `path=arkgoods/<CDN id>`。

⇒ 两者是**不同上传源**。当前后端 `shop_draft_service.upload_one_image` 只产 `arkgoods` 形状（主图/详情图正确），
**规格图若复用它会得到 `arkgoods` 形状，与真机 `material_space` 形状不符**。

### 结论：**非阻塞，无需实现独立素材库上传**

2026-10-10 真机实测：规格图沿用 `arkgoods` 形状（`build_publish_image`）提交，
`batch_create_item` 返回 `published:true, fail_reasons:[]` —— **平台接受 `arkgoods` 形状的规格图**。

⇒ 真机的 `material_space` 形状只是千帆**前端 UI 走素材库上传**时的产物；
后端 `batch_create_item` 对规格图**两种形状都接受**。当前实现（规格图与主图同形状）**正确可用**，

## 12. 价格库存表批量填写（2026-10-10 调研，待实现）

### 真机结论（bundle 逆向，权威）

发布页「价格及库存」SKU 表的**批量填写**是纯前端计算（无独立接口，提交时
才进 `skuData`）。bundle（`itemark-index.js`）逆出的两份枚举：

**① 批量修改模式** `N = { add, sub, abs }`（三模式，**无 scale 倍数**）：

| 真机模式 | 语义 |
|---|---|
| `add` | 原值 + 固定值 |
| `sub` | 原值 − 固定值 |
| `abs` | 一律改成固定值（不看原值） |

**② 可批量修改的列** `h = { title:3, price:1, stock:2, delayDelivery:9, property:14 }`：

| 列 | 含义 | 可批量 |
|---|---|---|
| `price` | 售价 | ✅ |
| `stock` | 库存 | ✅ |
| `delayDelivery` | 发货时效 | ✅ |
| `property` | 属性 | ✅ |
| `title` | 规格 | ❌（只读） |

### 我方现状（`precheck-publish.ts` 共享逻辑）

三模式 `delta / scale / fixed`：
- `delta`（原值 + 固定值，可负）≈ 真机 add + sub 合并
- `scale`（原值 × 倍数 + 固定值）—— **真机没有，多余**
- `fixed`（一律改固定值）≈ 真机 abs

### 差距与对齐方案（待用户拍板）

1. **模式**：去掉 `scale`，改为 `add/sub/abs` 三模式（add/sub 拆独立选项，不再用 +/- 符号）。
2. **影响面**：`precheck-publish.ts` 是**价格库存表 + 预检 SKU 表共用**；对齐会连预检表一起变。
3. **列**：我方 6 列（规格/售价/库存/市场价/条形码/商家编码）已覆盖真机展示列，
   但批量「可操作列」应限于真机的 price/stock/delayDelivery/property（市场价/条形码/
   商家编码是否可批量，真机枚举未含 ⇒ 需真机 DOM 再确认）。

### 17.3 前端「传文件名」的真相：后端重启导致 token 失效（根因）

前端发往后端的 `main_images: ["主图/主图02.jpg"]` 是**中间态**（本地相对路径 + token），
后端发布前会 `resolve_package(token)` 解析 → 上传 → 转远程地址对象再提交千帆（设计如此，
见 §1.5 图片通路）。

历史「图片地址错误」的**真根因**：`resolve_package` 优先查 `_LOCAL_REFS`（**进程内存
dict**，`package_staging_service._LOCAL_REFS[(user_id, token)] = 本地文件夹路径`）——
**后端一重启该 dict 清空，token 失效**，图片只能按相对路径盲试 ⇒ 上传失败。

### 17.4 修复：package_path 直接拼绝对路径，摆脱内存引用

- 后端 `ItemPublishRequest` / `ItemDraftCreateRequest` 各加 `package_path: str`（默认空）。
- 发布 / 保存草稿端点 `image_root` 解析改为**优先 `package_path`**（本地文件夹绝对路径，
  直接 `package_path / 相对路径` 拼），`precheck_token` 仅兜底（老路径 / 草稿箱发布）。
- `package_path` 目录不存在 ⇒ 404 `PACKAGE_PATH_INVALID`（明确报错，不静默回落盲试）。
- 前端 `submit()` / `saveDraft()` 传 `package_path: packagePath`（向导持有的本地文件夹绝对路径）。

⇒ 后端重启后，只要前端还持有 `packagePath`（本地文件夹还在），图片仍能正确解析上传。

### 18.3 SKU 名称拆分 + 本地图对齐（需求 2/3/5）

```
表格 sku名称  =  颜色分类:【中古风】实木三斗柜        ← 首个冒号切「规格分类 : SKU 名称」
本地图文件名  =  SKU01_颜色分类(【中古风】实木三斗柜).jpg
                 └前缀+自增序号+「_」┘ └规格分类┘└括号内=真实 SKU 名称┘
```

- `parseSkuName()`：**只切第一个冒号**（半角 `:` 与全角 `：` 都认），值内后续冒号**保留**；
  无冒号 ⇒ 分类空、整串当值（**不猜**）。
- ⚠️ **无分类时的单一维度回退（真 bug 修复 2026-10-15）**：数据包的 `sku名称` 列可能是
  **纯规格值**、不带 `分类:` 前缀（实测包：列 `[sku名称, 库存]`、行 `[A款, 3]`、SKU 目录
  只有 `SKU01.jpg`）。此时 `passedSkuRows` 把维度退化为 `SINGLE_SPEC_NAME`（`规格`）
  **一个维度**，值 = 整个名称 —— **不再是空串**。
  - 为什么必须这样：`sourceSpecNames()` 会丢掉空名 ⇒ `mappingSources = []` ⇒
    第二步「预检通过SKU导入」按钮**恒灰** + 恒提示「没有可导入的 SKU」，
    而用户在第一步明明看到有预检通过且勾选的行（用户实测报障）。
  - 这不是「按数据形态加 if」：判据只有一条通用规则 —— 名称里**有没有冒号**，
    有分类 / 无分类的包走同一个 `parseSkuName`，只是取不到分类时**退化成一个维度**，
    由用户在导入弹窗里把它映射到目标平台规格类型（弹窗本来就是干这个的）。
  - `realSpecNames()` = 只含真分类（不含合成的 `规格`），供 UI 区分「包里有没有分类」措辞。
- 本地图对齐 = 按上述**命名规则解析**后与表格 SKU 名**等值比对**
  （`matchSkuImageName` + `lookupLocalSkuImage`）。真包 **26/26 命中且逐条指回自己那张**。
  ⚠️ 无分类的包（`sku名称 = A款`、`SKU01.jpg`）**图名解析后是空串** ⇒ 该行仍判 blocked
  （这是独立判据：本地图对不上就是没通过，与本条回退无关）。
- **匹配正则可配置**：本地图片列头「规格配置」按钮 → Popover，输入框预填
  `DEFAULT_SKU_IMAGE_PATTERN`（捕获组 1=规格分类、2=SKU 名称），点「重新匹配」对所有行重跑。
  校验 `validateSkuImagePattern()`：空 / 组数 < 2 / 语法错 ⇒ 给可读说明。
- **未匹配到 ⇒ 弹窗手选**：每行「选择本地图」图标（`LocalSkuImagePickModal`，
  形态与第二步 `SkuPickModal` 一致：60vw / 卡片网格 / 单选 / 预览 / 大图切换），
  候选 = **已加载且无违规词**的 SKU 图。

4 列 × 15 行、每行带「未匹配到本地图 / 选择本地图」。

**关键判据是那几个表头名** —— `列1 / 列2 / …` **不是**数据包里的真表头，而是
**几何还原的兜底列名**：`image_ocr_service.build_table_from_boxes()` 把 OCR 出来的
**词框（word box）坐标**按 y 分行、按 x 聚类分列，列数定不下来时就叫 `列N`。

⇒ 那张表 = **对 `主图/商品属性图.png` 做 OCR，再把词框几何还原成网格**。
卡标题「商品属性图」只是因为**文件名**恰好如此。

⚠️ **此前四轮的误判**（记录以免重蹈）：

| 轮次 | 我当时改的 | 为什么没修好 |
|---|---|---|
| 1 | 删 `_read_attribute_table` / `scan_attribute_table` | 那是**属性表专用**入口，截图这条走的是**通用几何建表** |
| 2 | `_scan_media` 里按文件名「排除属性图」 | 只影响**媒体清单**，不影响**表格产出** |
| 3 | 反向：不过滤媒体、只打 `is_attribute_image` 标识 | 同上，判据压根不在媒体链上 |
| 4 | 再反向：按文件名排除 + 叶子模块 | 仍只动媒体链，`tables` 依旧多出那张 OCR 表 |
| **5（本条）** | **删 `build_table_from_boxes` 整链** | ✅ 命中真根因 |

**教训**：我一直在「属性图」这个词上找，而真判据是**表格列名形态**（`列N` = 几何兜底）。
以后遇到「表是从哪来的」这类问题，**先看它的列名/表头是不是数据包里的原值** ——
不是原值就说明它来自**派生**（OCR、推断、兜底），而不来自数据包。

### 21.3 图片上传并发（方案 B）

**新增端点**：`POST /api/xhs/qianfan/picture-space/upload-batch`（+1 端点 / +1 path）。

**⚠️ 为什么并发不触发风控**（这是方案可行的根据）：上传是**两段式** ——
- ① `GET /api/edith/upload/web/permit` 打**小红书**（要签名）
- ② `PUT https://<uploadAddr>/<fileId>` 打 **ROS/COS 对象存储**（**不是小红书域名**）

单张 ~2.5s 的耗时**基本全在第 ②段** ⇒ 并发第 ②段**不产生任何平台请求**。
平台自身证据：笔记发布链路 `note_publish_service._upload_media` 早已
`upload_web_permit(len(downloaded))` 一次批量申请。

**真机实测：平台单次 permit 封顶 14 个 fileId**

| `file_count` | 实得 fileId |
|---|---|
| 5 | 5 |
| 10 | 10 |
| **20 / 38 / 50** | **14（封顶）** |

⚠️ **这是「已上传 14/38 张详情图」的真根因**：旧实现只申请**一次** ⇒ 38 张里 14 张能传，
**其余 24 张全落「上传凭证数量不足」**（38 − 14 = 24，与用户实测数字精确吻合）。
⇒ 修法：**分批申请直到拿齐**（38 → `[14, 14, 10]`），且**每个 fileId 用自己那批的
`uploadAddr`/`token`**（不同批是不同凭证，跨批用会 401）；用完清映射防内存泄漏。

**⚠️ 另一个真 bug：静默丢图**。旧版取字节不限流（38 张**同时** `fetch`）⇒ 浏览器连接池耗尽
⇒ 部分 `fetch` reject ⇒ 被 `catch` 吞成 `null` ⇒ 静默丢弃。修法：**分块取字节**
（`UPLOAD_FETCH_CONCURRENCY = 5`）。

**保序**（用户明确要求）：旧版把失败项 `filter` 掉后再提交 ⇒ 后端 `results[].index` 是
**压缩后数组**的下标；兜底那句「按文件名找」在**两张内容相同的图（MD5 同名）**时必然串位。
⇒ 修法：`slots[]` 保「提交下标 → 原下标」映射，回填**只认 `results[].index`**，
**删掉**按文件名找的兜底。净效果：**最终顺序 == 上传前顺序**。

**逐张详情**（用户口径「新增一个详情点击弹窗展示对应的详情」）：「上传商品主图」/
「上传商品详情图」两行标题变可点，点开是逐张清单（序号 / 文件 / 结果 / 原因）；
进度文案改报 `已上传 14/38 张详情图（24 张失败，点标题看详情）`；
**有失败时标题与对号图标同时置红**；弹窗底部常驻一行操作提示。

**并发数配置**：`xhs_image_upload_parallelism`（默认 **5**），**四处同值**
（`LIVE_KEYS` / `BUILTIN_DEFAULTS` / `config/default.yaml` / 随包种子）。

### 22.5 表格正则：**覆盖原列**（不做派生列）+ 可撤销

用户口径：「表格列通过正则对原数据中的列取值操作后**覆盖原始列**」
「默认**覆盖全部**，如果存勾选行则**只覆盖勾选行**」
「**数值列不支持**只能读取原始值」。

⚠️ 本轮中间曾提议「原列只读 + 派生列」，**已被用户明确否掉**（见 §22.2）。

落地三条：
· 作用域与 `BatchColumnBar` **同一套语义**（没勾选 = 整列；勾选 = 那些行）；
· **先预览再应用**（命中 N/M + 前 5 行前后值）；
· **可撤销**（首次覆盖前存快照；覆盖是破坏性动作，原值没了就真没了）。

⚠️ **撤销的作用域 = 当前列**（用户口径 2026-10-15：「**恢复数据应只恢复当前列
而不是全表**」）。快照按**「表 + 列」复合键**存（`snapshots[snapshotKey(tIndex,
column)]`，值是**该列**的原值），撤销只把这一列抹回原样 —— 别列改过的成果留着。
- 旧实现存**整表 `rows`** ⇒ 点任意一列的「还原原始值」会把整张表所有列一起撤回，
  用户在另一列辛苦改的东西无损丢失（且不可逆），故改掉；
- `applyColumnPattern` / `applyColumnValues` 两条写值路径**按同一口径存快照**：
  同一列共用一份（不会「撤了一半」），不同列各存各的；
- 该列没有快照时**不出现**还原按钮（`canRestore` 按列判，不是按表）；
- 确认框文案必须点明**只还原当前列**（旧文案「丢弃本表所有列」已作废），
  且 `onOk: () => onRestore(column)` **要带上这一列** —— 写成裸引用 `onRestore`
  在 TS 上能过（React 把事件对象当实参递过去），但运行时撤的是错的列。

列类型由**后端判**（`column_kind`，**抽样多行** —— 只看第一行会把
`券后价格`（仅首行有值）误判、把 `1000+` 误判成数值）并随表下发。

### 22.9.1 问题：艺术字「识别不出来」被当成「没有违规词」

用户报「很多张图片中均存在违规词，均未检测出来，比如天猫、88VIP」。实测（同图）：

```

|---|---|---|

### 22.9.2 预处理**救不了** Windows OCR（实测排除，不是没试）

⇒ 一个都没提升。根因是 Windows OCR 对**中文艺术字 / 促销排版**的识别基本失能 ——
那是**引擎能力边界**，不是参数问题。**所以换引擎，不是调参数。**

### 22.9.3 落地：`rapid_ocr_service.py` 作为唯一引擎

* `backend/app/services/rapid_ocr_service.py` = RapidOCR（PP-OCRv4 ONNX，**纯 CPU**，
  `intra_op_num_threads=1`）。**进程级单例**引擎（模型只加载一次）。
* 返回结构与旧脚本**同形**（`{text, lines:[{text,words:[{x,y,w,h}]}], pixel_width/height}`）
  ⇒ 上层 `_payload_to_scan` / `locate_hits` **零改动**。
* ⚠️ RapidOCR 只给**行级 4 点 box**、不做词切分 ⇒ 每行整行当一个「词」；
  红框因此是**行框**（用户要看的是「哪一行有问题」，行框够用，且省掉一次分词）。
* ⚠️ `pixel_width/height` 必须回**原图**尺寸（识别可能在缩放后的图上做，
  但红框换算用的是原图坐标系）。
* 死代码**整段删除**（不静默留影子）：`_run_script` / `_run_batch` /

  `_run_script_with_retry`。`win_ocr_*.ps1` 脚本文件**仍在盘上但已无调用方**
  （保留以免影响其它历史引用；`.hermes/tmp/` 下有同名旧草稿，同样无调用方）。

### 22.9.4 并发：**配置起始值 + 自动调节**，30s 是**参照值不是承诺**

用户口径 2026-10-13：「并发值配置为初始并发数、配在系统参数中、默认 5」
「时间控制在 30 秒以内或者根据电脑使用情况自动调节」。

* 系统参数 **`xhs_ocr_parallelism`**（默认 **5**，范围 1–32，`category=publish`），
  三处同值：`LIVE_KEYS` / `BUILTIN_DEFAULTS` / 随包种子 `system_settings.json`。
  读点 = `image_ocr_service.resolve_parallelism()`。
* `resolve_parallelism(pending)` 三档：**起始值（配置）→ 按核数夹 → 按目标耗时上推**，
  最后夹到 `[1, MAX_PARALLELISM]` 且不超过待处理图数。配置值是**下限**，不被机器缩小。
* `scan_images` 的 `summary` **如实上报** `parallelism` / `elapsed_seconds` /
  `target_seconds`（不假装达标）。

⚠️ **实测结论：30 秒在本机达不到，如实标注**（硬约束⑤不造假）：

| 并发 | 24 张耗时 | 加速比 |
|---|---|---|
| 1 路 | 41.1s | 1.0x |
| 4 路 | 19.4s | 2.1x |
| 8 路 | 19.8s | **无提升** |
| 12 路 | 19.4s | **无提升** |

⇒ 吞吐在 **4 路**就饱和（`SATURATION_WORKERS = 4`）。单图推理 ~1.74s，
占单图耗时 **99.5%**（读图+缩放只 0.01s），是纯 CPU 密集。
118 张的**物理下限约 96s**（4 路 × 0.81s/张）。30s 只能靠更小的图 / 更强的 CPU。

⚠️ 另一条实测坑：`intra_op_num_threads` 必须显式设 **1**。默认让 onnxruntime
每路吃满所有核 ⇒ N 路 × 核数 个线程抢核数 个核（8×8=64 抢 8）。

## 22.10 SKU 图自动匹配弹窗修正（2026-10-13，用户口径追加）

### 22.10.1 根因：**未指定区域也能匹配出结果**（用户报的真 bug）

> 用户原话：「SKU 图自动匹配 弹窗图片区域未指定，已经匹配到了数据包，不正常，

### 22.10.3 新增：名称列取值正则（先提取、再匹配）

> 用户原话：「使用正则支持对选定的 sku 列使用正则提取后再与使用指定正则规则的
> 图片名称进行精确或模糊的匹配」

⚠️ 这与「匹配方式 = 正则」是**两件独立的事**，别混：

| 控件 | 管什么 |
|---|---|
| **名称列取值正则**（`matchExtract`） | **怎么从 SKU 列取值**（提取 ⇒ 再比） |
| **匹配方式**（`mode`） | **取出来的值怎么和图名比**（精确 / 模糊 / 正则） |

用户可以「先提取 → 再模糊」—— 那是绝大多数真实场景（列值是

* 留空 ⇒ 原值；有捕获组 ⇒ 取第 1 组；无组 ⇒ 取整串；
* ⚠️ **正则语法错 / 没匹配上 ⇒ 回落原值**（**不返回空串**）。
  返回空串会让该行必然判未命中，用户看到的是「这些图就是配不上」——
  真正的原因（他的正则没命中任何一行）被藏起来了。

## 22.11 SKU 匹配弹窗：布局与匹配规则修订（2026-10-13，用户口径追加）

### 22.11.1 抓到的两个真 bug（「分析原因」的答案）

**① 「SKU 名称列的下拉图标在第二行」= 布局被挤断，不是图标本身的问题。**

原写法：第 1 行是「图片区域」且 `style={{ width: "100%" }}`（**占满整宽**），
第 2 行才是 `Space wrap` 装的「SKU 名称列 + 匹配方式」。弹窗收到 **50vw** 后，
`Space wrap` 会把里面的 `Select`（含右侧下拉箭头）**当成一个可换行单元折断**

## 22.12 SKU 匹配：末段取值 + 下拉图标掉行根因（2026-10-13 追加）

用户原话：

> 「注意匹配应拿 sku 名称**最后的完整文案**与图片名称进行模糊或精确匹配，
>  SKU 名称列的下拉框的下拉图标还是在第二行，正常默认应在第一行末位的，
>  **分析原因是否存在 css，移除对应样式**」

### 22.12.1 匹配改用「最后一段完整文案」（`lastSkuSegment`）

真实列值是 `规格分类:规格值` 形态（`颜色分类:【中古风】实木三斗柜`）——
用户要比的是**规格值那一段**，不是整串。

```
lastSkuSegment("颜色分类:【中古风】实木三斗柜")  ⇒ "【中古风】实木三斗柜"
lastSkuSegment("分类:A:B")                     ⇒ "B"      ← 取**最后**一个冒号
lastSkuSegment("中古色-实木三斗柜")             ⇒ "中古色-实木三斗柜"  ← 无分隔符原样
lastSkuSegment("颜色分类:")                    ⇒ ""       ← 空末段，由调用侧兜底
```

⚠️ **取最后一个分隔符**（`lastIndexOf`），不是第一个 —— 规格值本身可能含冒号，
取第一个会把它切坏（`分类:A:B` 应得 `B`）。

⚠️ **两侧都取末段**：列值一次、图名一次。图名侧必须先过 `imageMatchKey`
（它把包 B 的 `SKU01_颜色分类(【中古风】实木三斗柜)` 整形成
`颜色分类:【中古风】实木三斗柜`），再取末段才能落到「规格值」那一层。
只对一侧取 = 精确匹配永远落空（实测就是这个症状）。

⚠️ **空末段回落整串**：`颜色分类:` 这种只有分类名没有值的脏数据，
末段是空串 —— 直接用会让该行必然判未命中，而用户看到的是「这些图就是配不上」，
真原因（名称列选错 / 数据脏）被藏起来。故空末段回落整串再比。

⚠️ 原实现的「独立算 `specValue` 再双重比较」**已被本口径取代并删除**
（末段取值本身就是那个 `specValue`，留两份实现迟早不一致）。

### 22.12.2 「下拉图标掉到第二行」= 标签与控件混排（**不是 CSS**）

用户要求「分析原因是否存在 css，移除对应样式」。**定位结论：不是 CSS。**

* 全站 `global.css`（458 行）**没有任何 `.ant-select` 规则**，实测确认；
* 真根因是**标签与控件没分成两块**：原写法把标签写成两个**行内** `<Text>`，
  紧跟一个块级 `Select`：

```jsx
<div style={{ width: 200 }}>
  <Text strong>SKU 名称列</Text><Text>必选</Text>   {/* 同一行内流 */}
  <Select … />                                      {/* 块级，另起一行 */}
</div>
```

行内标签与块级控件混排时，`Select` 的可用宽度被标签行的残余空间影响；
窄容器（50vw 下右栏固定 200px）里就表现为**下拉箭头被挤到第二行**。

⇒ 修法：**每个控件的标签单独包一层 `<div>`**（独占一行），控件另起一行，
控件的宽度来源变单一（就是那 200px）。

```jsx
<div>
  <div style={{ lineHeight: "20px" }}>     {/* ← 标签独占一行 */}
    <Text strong>SKU 名称列</Text><Text>必选</Text>
  </div>
  <Select style={{ width: "100%" }} … />   {/* ← 控件另起一行 */}
</div>
```

⚠️ 顺手**删掉了各处零散的 `marginTop: 4`**（那是用来「补」标签与控件的间距的，
分块之后由 `lineHeight: "20px"` 统一控制）—— 治因，不是调间距。

### 22.14.1 「依旧匹配到」的真因：**模糊档在用 `includes`**

`§22.13` 把判据写成：

```ts
if (mode === "exact") return key === want;
return key.includes(want) || want.includes(key);   // ← 就是这里
```

而**默认档就是 `fuzzy`**。于是：

```
want = "木;中古色-实木三斗柜;上门安装"
key  = "中古色-实木三斗柜"
want.includes(key) === true      // ← 带前缀分类的整串「包含」了子规格 ⇒ 命中
```

⚠️ **根因是概念混了**：「模糊」被实现成**子串搜索**，而用户要的是
「**完整文案**比较，只是容忍书写差异」。两者是**正交**的：

| 维度 | 用户期望 | 旧实现 |
|---|---|---|
| **内容** | 必须**完全一致**（完整文案） | 允许子串（会配到别的规格） |
| **书写** | 容忍空白/全角/大小写 | 也容忍，但被内容维度的问题掩盖 |

### 22.14.2 定论：两档都要求**相等**，差别只在书写容忍度

```ts
精确  exact : normalizeMatchKey(key) === normalizeMatchKey(want)
模糊  fuzzy : looseMatchKey(key)    === looseMatchKey(want)
```

`looseMatchKey` 只折叠**纯排版差异**（`;；:：,，、` 统一、括号去掉、
连字符/中点/下划线去掉）—— **绝不折叠字的增减**：

* `SKU图_01_ 中古色-实木三斗柜 .jpg`（多空格）⇒ **配上**；
* `…+妆凳`（**多一个规格**）⇒ **不配**（那是内容差异，不是书写差异）。

⚠️ 这就是「模糊匹配」与「子串搜索」的分界。实测 52 张真图矩阵：
* 允许子串 ⇒ 错 **58~320 条**（视写法）；

### 22.15.4 关键设计：为什么不能直接 `grex(原文)`

`grex` 学的是「**这些串的共同形状**」，它**不知道你想取哪一段**。
直接喂原文 + 开捕获组，捕获组位置由算法决定 —— 实测 **0/3**：

```
输入：木;中古色-实木三斗柜;上门安装 / 木;中古色-【伸缩桌+三斗柜】梳妆台;上门安装
产出：木;(中古色\-(?:【伸缩桌\+三斗柜】梳妆台|实木三斗柜);上门|奶油白色\-实木六斗柜;自行)安装
      ↑ 捕获组抓的是「中古色-…;上门」这种莫名其妙的区间
```

**正确问法**：拆成「前段 / 结果 / 后段」，只学前段与后段的形状。

```
原始文本 = <前段> + <结果文本> + <后段>
前段正则 = grex(每条的 前段)      → 木;
后段正则 = grex(每条的 后段)      → ;(?:上门|自行)安装
最终     = ^(?:前段)(.+?)(?:后段)$
```

技术要点（都影响正确性，不是风格问题）：

1. **必须 `without_anchors()`**：不加锚点 —— 前段/后段是要嵌进最终正则的
   **子表达式**，带 `^`/`$` 会让它只能匹配整串，拼进 `^(?:前)(组)(?:后)$` 后
   **恒不匹配**。
2. **捕获组用 `(.+?)` 非贪婪**：前段/后段已把边界钉死；贪婪组在
   「结果在结尾」（后段为空、无锚可依）时会把尾巴也吞进去。
3. **前段/后段为空时不生成 `(?:…)`**：结果就在开头/结尾，空组是噪声且会
   干扰匹配。
4. **多组样例显著更好**：引擎要看到「哪些部分在变」才能把变化段泛化成
   枚举（`(?:上门|自行)`）；只有一组时它只能原样硬编码该串。

实测（`tests/backend/test_pattern_derive.py` 参数化）：分号三段 / 冒号两段 /
中文前缀 / 结果在开头 / 结果在结尾 **5/5 全过**，含中文、全角括号、`+` 元字符。

⚠️ **`grex` 的泛化能力比预期强得多**：前段/后段形状互斥时它会用**枚举**
解决（`(?:111|abc)\-`），结果一前一后时会补**可选组**（`(?:(?:AAA\-)?)`）。
写了 10 组「看起来该失败」的样例**全部通过** ⇒ 那条「推不出来」的用例改为
**钉契约**（打桩 `build_pattern` 返回坏正则 ⇒ 必须抛且指出是哪一组），
并另加一条**反向守卫**（`test_grex_generalizes_instead_of_memorising`：
正则必须能匹配**样例之外**的同形态新文本）。

### 22.15.5 三条硬约束（都是「不造假」的落地）

1. **产出的正则必须通过校验才返回**（`validate_pattern_extracts`，三判据）：
   能编译 → 能匹配原文 → **捕获组 1 等于结果文本**（两侧 strip，不宽松比对）。
   前两条过了第三条不等，用户拿到的仍是错的 ⇒ 一律算失败。
2. **失败必须报原因并指出是哪一组**（`PATTERN_DERIVE_FAILED`）——
   用户据此判断是「样例互相矛盾」还是「写法太复杂」，而不是面对一个静默的空输入框。
3. **结果文本必须是原文的子串**（`PATTERN_DERIVE_NOT_SUBSTRING`）：
   不是子串还硬要提取 ⇒ 只能把结果文本硬编码进正则，换行数据立刻失效。
   这是**用户样例给错了**，早拦比晚拦好。

## 22.16 SKU 匹配定案：**图片名包含 SKU 名**（2026-10-14，推翻 §22.13 / §22.14 的匹配判据）

用户口径（本轮定论）：

> 「图片名称**不是固定样式**的，但**一定包含** sku 名」

> 「sku名称:木;中古色-实木三斗柜;上门安装    正则后的结果：实木三斗柜
>   也就是说"实木三斗柜"前后的任何文本我均不需要匹配，通配符即可」

### 22.16.1 触发的问题：反推后只匹配成功第一条

用户报：弹窗里反推出来的图片名正则（`^(?:SKU01_颜色分类\()(.+?)(?:\)\.jpg)$`）
**只能匹配第 1 条**，`SKU02…SKU26` 全部落空。

**根因**：`grex` 默认把「样例间相同的部分」一律写成**文本字面量**。
只给 1 组样例时，`SKU01` 被当成不变前缀写死 ⇒ 换一条就废。

⇒ 这不是弹窗的 bug，是**「靠反推学图片名结构」这条路本身的问题**：
图片名样式不固定（`SKU01_颜色分类(值).jpg` / `实木三斗柜_01.jpg` /
`SKU-实木三斗柜.png` 都可能），任何学出来的结构换个包就失效。

### 22.16.2 定案判据

```
左 = applyExtract(SKU 列值, SKU 列取值正则)      ← 用户正则，值的边界只有用户知道
右 = 图片文件名（去目录、去扩展名）                ← 无正则
命中 ⟺ 右 **包含** 左
```

* **图片名侧不再需要任何正则** —— 「样式不固定但一定包含 SKU 名」的唯一稳定判据
  就是包含；
* **SKU 列侧保留用户正则** —— 剥 `颜色分类:` 这类列名前缀，只有用户知道边界规则；
* **删掉的东西**：`imageMatchKey`（图名侧正则抽键）、`SkuMatchMode`
  （精确/模糊两档）、`looseMatchKey`、`normalizeMatchKey`、`skuNameText`、
  「图片名称取值正则」输入框 + 它的反推入口、「方式」列 + `matchModeLabel`。

### 22.16.3 消歧：**全局最长优先 + 一图一用**

包含判据的副作用：**短规格名是长规格名的子串**
（`伸缩桌+三斗柜梳妆台` ⊂ `伸缩桌+三斗柜梳妆台+云朵妆镜`）。

两道消歧（`matchSkuRows`，真包 26 条实测 **26/26 全对、零错配**）：

1. **最长优先**：所有 (行, 图) 命中对按**值长度降序**分配 ——
   长值先挑，短值不会把长值该拿的图抢走；
2. **一图一用**：一张图只能被一行占用（「一个规格一行、一行一张图」的自然语义）。

⚠️ **手选优先**：`usedCandidates` 里已被用户手选的图**不参与**自动分配。

### 22.16.4 「应用匹配结果」必须同时更新 SKU 表格（真 bug）

用户报：

> 「点击应用匹配结果后，商品sku表格依旧显示未匹配到本地数据，
>   第一列已经展示了匹配到的sku列图」

**根因**：两张表**各读各的** ——

| 表 | 读的 state | 判据 |
|---|---|---|
| 弹窗的匹配列表 | `appliedSkuImages` | 弹窗自己的匹配结果 |
| **商品 SKU 表格** | `manualPicks` / `lookupLocalSkuImage(...)` | 另一套模糊匹配 |

⇒ 弹窗里匹配成功，**表格根本不知道**。两张表读的是同一份数据（`cleanSkuMedia`），
只是判据旧。

**修法**：`applySkuMatch` 里**既写 `appliedSkuImages`（弹窗第一列预览），
也写 `manualPicks`（表格的权威覆盖，语义 = 「用户判断 > 自动匹配」）**。

### 22.16.5 弹窗列表列序（用户口径 2026-10-14）

### 22.16.7 反推器补强：`with_conversion_of_digits`（2026-10-14）

`grex` 默认把样例间相同的片段全写成字面量。开启
**`with_conversion_of_digits()`** 后，数字段被抽象为 `\d`：

| 样例 | 默认产物 | 开 `digits` 后 |
|---|---|---|
| `SKU01_颜色分类(`（**1 组**） | `SKU01_颜色分类\(` ← 写死 | `SKU\d\d_颜色分类\(` ← 通用 |

⚠️ **不**开 `with_conversion_of_words()`：实测会把整条样例抽象成
`\w\w\w\d\d\w\w\w\w\w\(【\w\w\w】…` —— **结构全丢**，连「取哪一段」都没法表达。
`SKU` / `颜色分类` 留作字面量是对的（它们是该列的**结构常量**），
