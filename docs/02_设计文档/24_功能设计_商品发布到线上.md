## 1. 真机取证：提交商品的确切形状

### 1.1 端点与参数（Network 抓 `postData` 逐字）

```
POST https://ark.xiaohongshu.com/api/edith/product/batch_create_item   （需签名 x-s/x-t）
body = {
  "itemData": [ <完整商品表单 25 个顶层字段> ],
  "options":  { "asyncExec": true, "withChild": true, "retrieveResult": true },
  "publishMode": 1        # ⚠️ 见 §1.4
}
→ {"code":200,"data":{"taskId":"…"}}
```

### 1.2 `itemData[0]` 顶层字段（真机实测 25 个）

```

qualifications[]        # 资质（空 = []）
```

### 1.3 `skuData[]` 每条（真机实测 10 个字段）

```jsonc
{
  "rowNumber": 1,
  "ipq": 1,                                  // 每件装数
  "price": {
    "price": 128000,                          // ⚠️⚠️ 单位是「分」！
    "includeTax": false,
    "priceInfo": { "preTax": 128000 }         // 必填，缺则平台报「售价计算失败」
  },
  "logisticsPlanId": "6a327c3bd0f2c70015312abe",
  "specImage": { <图片条目> },                 // mainSpecEnable=1 时每个 SKU 都要
  "deliveryTime": { "type": 4, "time": "48" },
  "variants": [
    { "attributeId": "60404e0de85df80001991224", "attributeName": "颜色分类",
      "attributeType": 1, "attributeValue": "实木三斗柜" }
  ],
  "available": true,
  "stockChange": 0,
  "stock": 0
}
```

### 1.4 ⚠️⚠️ **最容易搞反的两处**（守卫必须钉住）

1. **`price` 是「分」不是「元」** —— 与设计 23 的**草稿体相反**！
   * 草稿体（`create_product_drafts`）：`price: 1280` 回读 `1280`（**元**）。
   * **发布体**（`batch_create_item`）：页面填 **1280（元）** ⇒ 抓包 body 里是
     **`price: 128000`（分）**。bundle `8091.*.js` 逐字佐证：
     `basePriceInfo.price/100`（读形态分→元）。
   * ⇒ **两条链路的单位不同**，混用必错（且平台不报错，只是价格差 100 倍）。
     守卫：`create_item_body(price_yuan=1280)` 的 `price.price == 128000`。

2. **`publishMode`** 取值（bundle `publishMode:function()` 逆出）：
   `isBaseImagesCreateMode || opportunityId ⇒ 2 / isAiAssistant ⇒ 3 / 否则 ⇒ 1`。
   * 真机「基础图创建」路径抓到的是 **2**；
   * **普通发布用 1**（设计 20 起沿用）。
   * 本链路**固定用 1**（普通发布），2/3 是平台的其它入口。

### 1.5 图片条目形状（主图 / 详情图 / 规格图 三处同形状）

```jsonc
{
  "key": "<materialId>", "type": "spaceImage", "materialId": "<id>",
  "name": "SKU01_颜色分类(…)", "width": 800, "height": 800, "size": 115712,
  "extension": ".jpeg", "path": "arkgoods/1040g0o…",
  "link": "https://qimg.xiaohongshu.com/arkgoods/1040g0o…",
  "uploaderInfoModel": { "bizName":"ark","cloudType":4,"fileId":"arkgoods/…",
                          "isSecret":false,"scene":"goods_image","url":"https://…" },
  "errors": []
}
```
（与设计 22 图片空间 `additionalData` 同源，`specImage` 多一层嵌套。）

### 1.6 `publish_async` = **只读预检**，不是发布

真机抓到 32 个 `publish_async` 请求，**全部是只读预检 action**（一个都不改状态）：

```
getMaterialRule / checkNeedBrand / searchMarketableBrands / getCategoryProperty /
getSupportNoLogistics / getSellerCarriageTemplate / getSetSizeTableInfo /
getPriceLimit / getSalePropertyNumLimit / getProductQualificationRule /
getRecommendBrand / getRecommendCategory / getRecommendItemTitle /
checkMainImageWithWhite / getPropertyGroups / itemAuditPreCheck /
productTitleCheck / productShortTitleCheck / predictProductProperty …
```
body 形如 `{"data":"{\"publishType\":1,\"sourceType\":1,\"actions\":[{\"action\":…,\"param\":{…}}]}"}`。
⇒ 可用作**发布前体检**（设计 §3 的预检端点），但 **不产生商品**。

## 2. 数据模型：**零新表**

发布是**一次性写操作**，不落本地镜像（同设计 23 口径：草稿 / 商品的唯一真相源在平台）：

| 数据 | 落库 | 位置 |
|---|---|---|
| 提交记录（谁在何时发布了哪些商品） | ✅ 落本地 | `tasks`（`task_type = xhs_shop_item_publish`） |
| 商品本体 | 落**平台** | `search_item_v2` 可查（在售 / 审核中） |
| 图片 | 落**平台图片空间** | 复用设计 22 |

## 3. 端点契约（2 个新端点）

挂在 `qianfan.py` 现有 router（`/api/xhs/qianfan`），归属校验复用 `_owned_account`。

| # | 端点 | 语义 | 平台请求 |
|---|---|---|---|
| 1 | `POST /api/xhs/qianfan/items/publish` | **提交商品**：收「发布草稿 id」或「数据包 + 表单」，组装发布体 → 提交 → 轮询终态 → **立刻下架**（红线） | N 次（1 create + 轮询 + 1 off-shelf） |
| 2 | `POST /api/xhs/qianfan/items/precheck` | **发布前体检**（只读）：跑 `publish_async` 的预检 action，逐条回结果 | 只读 |

### 3.1 字段级契约

```python
# 1: 提交商品（⚠️ 结构上带显式二次确认位；无它就是不发）
class ItemPublishRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    platform_account_id: int = Field(ge=1)
    draft_id: str | None = Field(default=None, max_length=64)   # 二选一
    package_path: str | None = Field(default=None, max_length=512)
    confirm_off_shelf: bool = True   # ⚠️ 发布成功立即下架（红线，默认开）

ItemPublishResult = {
    "task_id": str,
    "item_id": str | None,          # 终态回执里的商品 id
    "published": bool,
    "off_shelf": bool,              # 是否已下架（红线执行结果）
    "fail_reasons": [{"index": int, "name": str, "message": str}],
}
```

### 3.2 三条必须钉住的口径

1. **`price` 单位是分**（§1.4.1）——`create_item_body` 里 `round(price_yuan*100)`。
   守卫：`test_price_is_fen_in_publish_body`（变异：改成元 ⇒ CAUGHT）。
2. **`publishMode` 恒 1**（普通发布）——常量 `PUBLISH_MODE_NORMAL = 1`。
   守卫：变异成 2/3 ⇒ CAUGHT。
3. **发布成功必须下架**（红线）——`confirm_off_shelf` 默认 `True`，
   `publish → off-shelf` 两步不可拆。守卫：断言成功路径**必然**调
   `batch_update_availability(available=False)`（变异：跳过 ⇒ CAUGHT）。

## 4. 业务逻辑

### 4.1 发布体组装（`shop_item_publish.py`，纯逻辑可单测）

```
1) 取骨架：publish_render({publishType:2, sourceType:1, itemId=<本店任一商品>})
2) 合并用户填的值：name / categoryId / images / imageDescriptions /
   attributes / variantIds / variantSequence / skuData
3) 单位换算：price 元→分（×100）；图片条目补 uploaderInfoModel
4) 平台强制字段：isGeneralSettings / stockType / deliveryMode / freeReturn /
   sizeTableType 系列 / usePlayback / enableMultiWarehouse / source=2
```

### 4.2 执行链（`shop_item_publish_service.py`，有写操作）

```
1) 组装发布体（§4.1）
2) POST batch_create_item → taskId
3) 轮询 query_task_status 至 status∈{3,4,5}
   ├─ success=true ⇒ 发布成功
   └─ failData[] 逐条报（不静默）
4) ⚠️ 红线：成功 ⇒ **立刻** batch_update_availability([item_id], available=False)
5) 回执：task_id / item_id / published / off_shelf / fail_reasons[]
```

### 4.3 发布前体检（`precheck`，只读）

跑 `publish_async` 的关键预检 action（`itemAuditPreCheck` / `productTitleCheck` /
`checkMainImageWithWhite` / `getPriceLimit` …），把平台原话逐条返回，
**在提交前把「平台会拒的理由」先摆出来**（降低一次发布失败一次改的成本）。

### 9.2 ⚠️ 本轮实测抓到并修掉的问题（**全部真机**）

1. **`materialId` 必须是登记返回的记录 id，不是上传凭证 `fileId`**。
   用 `fileId`（`arkgoods/XOARE…`）平台报「获取图片信息失败，请检查图片是否正确后重试」。
   ⇒ 取 `register_material_files` 回执的 `data.directoryManageables[0].id`。
2. **登记的 `path`/`link` 是平台**登记时新分配的 CDN id**（`arkgoods/1040g…`）**，
   与上传凭证 `fileId` 不同。三处（`path`/`link`/`uploaderInfoModel.fileId`）必须同值。
   ⇒ 登记后**回读**该记录取真值（图片空间搜索**最终一致**：登记后立刻搜 0 命中，
   ~1–2 秒可见 ⇒ 轮询 6 次 × 1s）。
3. **成功判据不能看 `result.success`**：真机发布成功时它竟是 `false`！
   正解 = `failData` 空 **且** `itemIds` 非空。看错会把成功判成失败、
   **跳过硬线（下架）** —— 本次**实测踩中**（第一次跑通时商品真上架了，
   靠人工兜底下架）。
4. **下架 / 删除类任务回执形状不同**：`{"failCount":0,"successCount":3,"total":3}`
   （无 `failData`/`itemIds`）⇒ 判据 = `failCount==0`。复用发布判据会把成功判成失败。
5. **`logisticsPlanId` 是店级的，既有商品骨架里常缺**（平台报「商品必填信息
   [logisticsPlanId]未填写」）⇒ 从 `publish_render({publishType:1, sourceType:1})`
   的 `fulfillmentInfo.logisticsPlanList[0].planId` 取。
5b. ⚠️ **`shippingTemplateId`（运费模板）不在 `publish_render` 里**（DEF-100，2026-10-09）：
   空白 `publish_render` 的 `fulfillmentInfo` **只有** `logisticsPlanList` / `logisticsPlanStatus`
   —— **既无 `shippingTemplateList` 也无 `defaultShippingTemplate`**。运费模板必须单独调
   `getSellerCarriageTemplate`，取 `data.fulfillmentInfo.shippingTemplateList[]` /
   `.defaultShippingTemplate`（详见设计 28 §二·补）。两个字段**两个数据源**，不可互相替代。
6. **骨架必须剥掉读形态 / 尺寸表字段**：`standardSizeTableInfo`（平台：此类目不支持
   尺码表配置）、`standardImages` / `longImages` / `properties` / `itemName` /
   `categoryPath` / `sellerId` … 透传会被拒或指向旧商品。
7. **`mainSpecEnable=1` 要求每个 SKU 都有规格图**（平台：「启用规格大图需上传所有规格
   的规格大图」）⇒ 有 SKU 缺规格图时自动关掉，让商品仍能发布。
8. **商品列表回执键名是 `data.items`**（不是 `data.item_list`）—— 按后者读会
   「列表拿到却读成空」，骨架都取不到。

## 10. 规格图形状差异（2026-10-10 真机确认）

真机发布体里 **规格图 `skuData[].specImage` 与主图 `images[]` 形状不同**（逐字段对比）：

| 字段 | 主图 `images[0]` | 规格图 `specImage` |
|---|---|---|

### 根因

- **主图 / 详情图**：走 `upload_web_permit(biz_name=ark, scene=goods_image)` → `arkgoods/<id>` 桶，登记后 `path=arkgoods/<CDN id>`。

⇒ 两者是**不同上传源**。当前后端 `shop_draft_service.upload_one_image` 只产 `arkgoods` 形状（主图/详情图正确），
**规格图若复用它会得到 `arkgoods` 形状，与真机 `material_space` 形状不符**。

### 结论：**非阻塞，无需实现独立素材库上传**

2026-10-10 真机实测：规格图沿用 `arkgoods` 形状（`build_publish_image`）提交，
`batch_create_item` 返回 `published:true, fail_reasons:[]` —— **平台接受 `arkgoods` 形状的规格图**。

⇒ 真机的 `material_space` 形状只是千帆**前端 UI 走素材库上传**时的产物；

## 12. 价格库存表批量填写（2026-10-10 调研，待实现）

### 真机结论（bundle 逆向，权威）

发布页「价格及库存」SKU 表的**批量填写**是纯前端计算（无独立接口，提交时
才进 `skuData`）。bundle（`itemark-index.js`）逆出的两份枚举：

**① 批量修改模式** `N = { add, sub, abs }`（三模式，**无 scale 倍数**）：

| 真机模式 | 语义 |
|---|---|
| `add` | 原值 + 固定值 |
| `sub` | 原值 − 固定值 |
| `abs` | 一律改成固定值（不看原值） |

**② 可批量修改的列** `h = { title:3, price:1, stock:2, delayDelivery:9, property:14 }`：

| 列 | 含义 | 可批量 |
|---|---|---|
| `price` | 售价 | ✅ |
| `stock` | 库存 | ✅ |
| `delayDelivery` | 发货时效 | ✅ |
| `property` | 属性 | ✅ |
| `title` | 规格 | ❌（只读） |

### 我方现状（`precheck-publish.ts` 共享逻辑）

三模式 `delta / scale / fixed`：
- `delta`（原值 + 固定值，可负）≈ 真机 add + sub 合并
- `scale`（原值 × 倍数 + 固定值）—— **真机没有，多余**
- `fixed`（一律改固定值）≈ 真机 abs

### 差距与对齐方案（待用户拍板）

1. **模式**：去掉 `scale`，改为 `add/sub/abs` 三模式（add/sub 拆独立选项，不再用 +/- 符号）。
2. **影响面**：`precheck-publish.ts` 是**价格库存表 + 预检 SKU 表共用**；对齐会连预检表一起变。
3. **列**：我方 6 列（规格/售价/库存/市场价/条形码/商家编码）已覆盖真机展示列，
   但批量「可操作列」应限于真机的 price/stock/delayDelivery/property（市场价/条形码/
   商家编码是否可批量，真机枚举未含 ⇒ 需真机 DOM 再确认）。

### 17.3 前端「传文件名」的真相：后端重启导致 token 失效（根因）

前端发往后端的 `main_images: ["主图/主图02.jpg"]` 是**中间态**（本地相对路径 + token），
后端发布前会 `resolve_package(token)` 解析 → 上传 → 转远程地址对象再提交千帆（设计如此，
见 §1.5 图片通路）。

历史「图片地址错误」的**真根因**：`resolve_package` 优先查 `_LOCAL_REFS`（**进程内存
dict**，`package_staging_service._LOCAL_REFS[(user_id, token)] = 本地文件夹路径`）——
**后端一重启该 dict 清空，token 失效**，图片只能按相对路径盲试 ⇒ 上传失败。

### 17.4 修复：package_path 直接拼绝对路径，摆脱内存引用

- 后端 `ItemPublishRequest` / `ItemDraftCreateRequest` 各加 `package_path: str`（默认空）。
- 发布 / 保存草稿端点 `image_root` 解析改为**优先 `package_path`**（本地文件夹绝对路径，
  直接 `package_path / 相对路径` 拼），`precheck_token` 仅兜底（老路径 / 草稿箱发布）。
- `package_path` 目录不存在 ⇒ 404 `PACKAGE_PATH_INVALID`（明确报错，不静默回落盲试）。

⇒ 后端重启后，只要前端还持有 `packagePath`（本地文件夹还在），图片仍能正确解析上传。
