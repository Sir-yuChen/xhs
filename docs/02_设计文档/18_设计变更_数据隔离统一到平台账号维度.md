> **决策记录**：**ADR-021**（`05_项目沉淀/01_架构决策记录_ADR.md`，状态 🟡 待确认）

## 1. 一句话

把「数据隔离键」**从店铺维度收敛到平台账号维度**：删掉 `shops` 表与
`platform_accounts.shop_id_fk` / 1:1 唯一索引，`shop_products` 改挂 `platform_account_id`；
商品页门禁从「有没有绑店」改为「**本账号 ark 会话是否可用**」。

## 2. 用户口径（原始）

> 「当前逻辑模型调整，绑定账号后，**不要再建店铺行数据**，账号下存在**三个平台的令牌**，
> 使用对应平台接口时则对应的使用该平台的**登录令牌**。另外商品页走的**本地数据库数据**，
> **不应该校验是否存在千帆店铺**，所有校验应该校验的是**该小红书账号下是否存在千帆可用的会话**。」
>
> 「数据隔离分别为：**本项目自有账号 / 平台 / 平台绑定的账号 / 数据**。」
>
> 「**所有数据以小红书账号做数据隔离**」「所有数据需进行修复，**无法定位修复的删除**」

**落成四层归属链**：

```
本项目自有账号 users
  └── 平台 platform（platform 列）
        └── 平台绑定的账号 platform_accounts（小红书账号）
              └── 业务数据（按 platform_account_id 归属）
```

|---|---|---|---|

| 2 | ~~「有没有店铺」由 `shop_account_bindings` 的存在性推导~~ | ADR-009 方案 B | 已被 2026-09-22 取代（关系 → `shop_id_fk`）；**本次再被取代**：不再问「有没有店铺」，改问「ark 会话是否可用」 |
| 3 | **「登录即建店」**：千帆登录成功即建 `shops` 行并绑上 | 设计 13 §18.17 / §18.17.5（`_bind_login_shop`，2026-09-27 提交 `b5aa749`） | **不再建店**：登录只写令牌（`ark` 通道）；「能不能用千帆」由令牌有效性回答 |
| 4 | 店铺 ↔ 账号 **1:1 由 DB 强制**（`uq_platform_accounts_shop_id_fk`） | 设计 13 §20 / 数据模型 §3.1 | **约束消失**：关系不存在了，无需约束 |

## 5. 目标模型

### 5.1 归属链

```
users (user_id)
  └── platform_accounts (platform=  'xhs' , id)
        ├── account_cookie_versions  → 三通道令牌 www / creator / ark
        ├── seller_id  ← 【新】千帆店铺标识下沉为账号属性（不再是实体）
        └── shop_products.platform_account_id  ← 【换键】
```

### 5.2 三个平台的令牌与接口对应

| 通道 | 平台接口 | 用途 |
|---|---|---|
| `www` | PC 网页端 | 采集 |
| `creator` | 创作者中心 | 发布 / 同步普通笔记 |
| `ark` | 千帆商家后台 | **商品台账 / 商品笔记** |

**用哪个平台的接口，就取哪个通道的令牌**——这已是现状（`channel_for_cookies()`），**本次不改**，
只是把「能不能用千帆」的判据从「有没有绑店」纠正为「`ark` 通道有没有令牌」。

### 5.3 商品页门禁（核心修正）

| | 现状 | 目标 |
|---|---|---|
| 后端 | `shop_id = account_shop_id(...)`；`None` ⇒ 400 `QIANFAN_BINDING_REQUIRED` | `qianfan_cookies_for_account(...)`；空 ⇒ 400 **`ARK_SESSION_REQUIRED`** |
| 前端 | `ledgerPrerequisite(bound, channels)`：`!bound` ⇒ `unbound` | `ledgerPrerequisite(channels)`：仅看 `channelUnavailable(channels,"ark")` |
| 提示语 | 「请在账号信息卡片中扫码登录千帆后再来查看。」 | 如实说明：本账号缺 `ark` 会话，请在账号矩阵完成千帆登录 |

| 账号 7 | ❌ 被拦 | ❌ 仍被拦（**正确**：确实没有 ark） |

## 6. 迁移方案

### 6.1 表结构变更（单个迁移，幂等）

| # | 变更 | 说明 |
|---|---|---|
| 1 | `platform_accounts` 加 `seller_id`（String(64), nullable） | 千帆店铺标识下沉；从 `shops` 按现关系回填 |
| 2 | `shop_products` 加 `platform_account_id`（Integer, nullable→回填→NOT NULL） | 经 `shop_id_fk → shops → platform_accounts.shop_id_fk` 回填 |
| 3 | `shop_products` 唯一约束 `(shop_id_fk, item_id)` → **`(platform_account_id, item_id)`** | SQLite 需重建表 |
| 4 | `note_comments` 加 `platform_account_id`（nullable） | 经 `note_id → notes.platform_account_id` 回填（当前 0 行） |
| 5 | `scheduled_job_logs.account_id` → **改名 `platform_account_id`** | 值不变（8 行有值、33312 行空，空值语义见 §6.3） |
| 6 | 摘除 `platform_accounts.shop_id_fk`；drop 索引 `uq_platform_accounts_shop_id_fk` / `ix_platform_accounts_shop_id_fk` | 关系消失 |
| 7 | drop `shop_products.shop_id_fk`；**`platform_accounts.shop_state` 保留** | ⚠️ 见下方 §6.1a |
| 8 | **drop `shops` 表**（`shops` 全部字段已下沉或废弃） | 实体退场 |

**回填安全性**：`shop_products` 1982 行**全部**可经 `shop_id_fk=1 → 账号 8` 定位 ⇒ 零丢失。

### 6.1a ⚠️ 与原计划的一处偏离：`platform_accounts.shop_state` **保留**

本表第 7 项原写「drop `platform_accounts.shop_state`」，**实际实现改为保留**（迁移
`b3c4d5e6f7a8` L221–226 的注释即为现场记录）。**结论被推翻，原句保留在上表**，理由：

* `shop_state` **不是关系列**。它存的是「本账号千帆侧的同步游标」——`status` /
  `status_message` / `goods_note_total` / `goods_synced_at` / `health_checked_at`，
  仍由 `shop_binding_service.get_shop_state()` / `set_shop_state()`（唯一实现）读写，
  被 `_account_shop_summary`、巡检、无流量候选等**多条在役链路**依赖。
* 第 7 项的原意是「**店铺关系消失**」；`shop_state` 表达的是**账号自己的能力状态**，
  与「店铺是不是实体」无关。把「关系列」和「能力状态列」一起删，属于把两条不同的
  语义绑在一句话里 —— 这正是「隔离键 ≠ 能力判据」要防的同一类混淆。
* 因此：`shop_id_fk` 删（关系没了）、`shop_id_fk` 上的两条索引删（`uq_` / `ix_`）、
  `shops` 表删（实体退场）；**`shop_state` 留下**。列名不改（省前端/服务连带改），
  但它的语义已在 `platform_account.py` 与 `qianfan._account_shop_summary` 的 docstring
  里写清：「账号在千帆侧的状态」，不是「店铺的状态」。

### 6.2 账号 9 的 `seller_id`（需一次只读调用）

账号 9 从未绑店 ⇒ 其 `seller_id` **库里不存在**。取回方式（用户已授权）：

```
用账号 9 的 ark 令牌 → 调 QIANFAN get_seller_info()（只读 GET）
  → 写 platform_accounts.seller_id
```

⚠️ **这是对外真实请求**，且是**只读**（不碰写接口、不逆向登录），符合项目只读边界。
**失败则留空、不编造**（DEF-057 口径：`unknown` ≠ 不可用）。

### 6.3 ⚠️ 陷阱：「无法定位 ⇒ 删除」不得误杀 `scheduled_job_logs`

用户口径为「无法定位修复的删除」。**必须把它落成不会误杀的判据**：

> **判据（建议，待确认）**：一行「无法定位」当且仅当 **它引用的父实体不存在**（悬空外键）。
> **「该列对这类行本就不适用」不算无法定位。**

据此：

| 行 | 判据 | 处置 |
|---|---|---|
| `publish_jobs` 1 行（`platform_account_id` 空/指向不存在账号） | 悬空外键 | **删除** |
| `scheduled_job_logs` 33312 行（`account_id` 空） | **用户级任务，该列本就不适用**，非悬空 | **保留**，仅列名改 `platform_account_id` |

**若按「空就删」处理，会删掉 33312 行合法历史日志** —— 这是本次迁移最大的误杀风险。

#### 7.1a ⚠️ 漏改复盘：模型层没跟上迁移 → 任务日志页一进就报错

**现象**（2026-09-30 用户报）：进任务中心 →「任务日志」页签，页面**自动**弹
「任务日志加载失败，请稍后重试。」，紧接着又弹一条拦截器兜底的「请求失败，请稍后重试」。

**根因**：迁移 `b3c4d5e6f7a8` 已把 `scheduled_job_logs.account_id` **改名**
`platform_account_id`（本文件 §6.3 判定的「列名漂移」），但 §7.1 改动清单**只有迁移、
没有模型** —— `models/scheduled_job.py` 仍声明 `account_id`。于是 SQLAlchemy 拼出的
SQL 是 `... scheduled_job_logs.account_id ...`，SQLite 抛

```
OperationalError: no such column: scheduled_job_logs.account_id
```

**影响面**：不是只有那一个接口 —— 任何 `select(ScheduledJobLog)` 都 500，包括
`/api/schedule/logs`、账号卡「同步中」判据（`sync_task_service.latest_*_log`）、
孤儿日志收口、日志删除/清空。**一条漏改，四条链路一起断**。

**为什么全量回归没抓住**：测试库一律 `Base.metadata.create_all()` 建 ⇒ 模型与库
**天然一致**，「迁移改了库、模型没跟上」这个方向在 create_all 路线下**结构性不可见**
（不是覆盖不够，是方向没测）。

**修复**：
1. `models/scheduled_job.py` 列名对齐 `platform_account_id`；
2. 连带 `services/scheduled_job_runner.py`（构造 kwarg）、`services/sync_task_service.py`
   （两处引用）、6 处测试里的 `ScheduledJobLog(account_id=…)` 构造；
3. `models/note.py` 的 `NoteComment` 补上迁移已加的 `platform_account_id`（同类风险，一并扫清）。

**新增守卫**（这一条是本节的验收物，不只写在文档里）：
`tests/backend/test_schema_matches_models.py` —— 从**空库**跑完整 `alembic upgrade head`，
再逐表比对「模型声明的列」与「迁移产出的列」，缺列即红并打印修复指引。
已过**变异验证**（把模型改回 `account_id` ⇒ 用例精确报出
`scheduled_job_logs: 缺 ['account_id']；迁移库里多出 ['platform_account_id']`）。

⚠️ **配套口径**：本次同时给 `lib/api.ts` 的 `fetchScheduleLogs` 加了 `_silent`
（2026-09-30 用户口径「先提示任务日志加载失败，又提示请求失败，这 2 个移除后一个」）——
失败的展示权归调用点，避免「调用点文案 + 拦截器兜底文案」两条 toast 同时出现（设计 04 §3.6）。
