## 1. 设计目标与范围

### 1.1 目标

在**不改动 `apis/` 底层 SDK** 的前提下，把小红书 PC 站内「账号自有内容与互动数据」的读取能力，从 SDK 层一路接线到前端页面。

### 1.2 范围

| 做 | 不做 |
|---|---|
| 新增 5 组只读端点 | 任何写操作（发布 / 点赞 / 删除） |
| 复用既有 normalize 逻辑 | 新建数据表、写库（D2 纯实时） |
| 新增 1 个前端页面 + 菜单 | 改造「内容库」「笔记发现」等既有页面 |
| 消除 1 个 mock 端点 | 触碰千帆（`ark`）链路 |

### 1.3 设计原则（沿用项目已确立原则）

| 原则 | 在本需求中的体现 |
|---|---|
| **能力驱动而非类型分支** | ⚠️ v1.0 此处写「不新增 `sub_type` 分支」，但当时的实现恰恰**反向**了——`_get_owned_pc_account_cookies` 用 `sub_type != "pc"` 一刀切（`pc.py:539`）。**v1.1 已修正为按 Cookie 能力判定**（§17）。这是本设计文档与实现不一致的一处，记录在案 |
| **降级路径是合法业务流程** | `xsec_token` 取不到不是异常，是**受支持的第二条路径**（§7）；创作者账号走创作者接口也是**受支持的第三条路径**（§17） |
| **前端置灰而非隐藏** | 账号不具备某项能力时，Tab 仍可见但给出可读原因，不静默隐藏（D9） |
| **解析不到就标注，不造假** | 商品信息（§6.3）与互动数一律来自平台；**列表未提供的指标不在卡片上渲染**（§18.3）。**唯一例外**：账号级三项计数（粉丝 / 关注 / 获赞数）缺值**渲染 `0`** 并配一行原因（R10 / D16）——`0` 是展示层默认值，**「真 0」与「没取到」由原因行区分**，库里仍写「未知」 |

## 4. API 契约

### 4.1 公共约定

| 项 | 约定 |
|---|---|
| 鉴权 | 全部端点 `Depends(get_current_user)`，未认证 → **401** |
| 账号归属 | `account_id` 必须属于当前用户、`platform=="xhs"`、`sub_type=="pc"`，否则 → **404** |
| 分页 | `cursor` 为**不透明字符串**，首页传空省略；响应回传 `cursor` + `has_more` |
| 页大小 | **由平台固定**（`user_posted` 为 30，`you/*` 为 20）。**不暴露 `page_size` 参数**，避免给了参数却改不动 |
| 时间 | 沿用 `core/time.py::shanghai_now()`，**禁止裸 `datetime.now()`** |

### 4.2 `POST /api/xhs/pc/users/me`

获取当前账号的平台身份，是其余端点的前置。

| 项 | 内容 |
|---|---|
| 请求 | `{ "account_id": 1 }` |
| 响应 | `{ "user_id": "...", "nickname": "...", "avatar": "...", "red_id": "...", "ip_location": "...", "raw": {...} }` |
| 说明 | `user_id` 用于后续 Tab 查询；`raw` 保留平台原始体便于排障（**不含任何凭据**） |

### 4.3 `POST /api/xhs/pc/users/notes`（我发布的 · R1）

| 项 | 内容 |
|---|---|
| 请求 | `{ "account_id": 1, "cursor": "", "profile_url": "", "xsec_source": "" }` |
| 说明 | `profile_url` 为**降级路径入参**：用户从浏览器粘贴自己的主页链接（含 `xsec_token`）。为空时系统按 §7 自动尝试 |
| 响应 | `{ "items": [NormalizedNote], "cursor": "...", "has_more": bool, "token_source": "url"\|"auto", "identity": {...} }` |

### 4.4 `POST /api/xhs/pc/users/liked` / `POST /api/xhs/pc/users/collected`（我赞过 / 我收藏 · R2）

| 项 | 内容 |
|---|---|
| 请求 | `{ "account_id": 1, "cursor": "", "xsec_token": "", "xsec_source": "" }` |

### 6.2 新增：列表抽取（应对字段名不一致）

```
_extract_list(data, keys) → list[dict]
```
- 依次尝试给定 `keys`（如 `("notes", "items")` / `("message_list",)`），返回第一个 list
- 兼容 `data` 本身即 list 的情况
- 全部未命中 → 返回 `[]`（**不抛异常**：平台返回空结果与结构变化的区分交给"条数为 0 + 原始体留存"在排查时完成）

### 6.3 新增：商品信息提取 `_extract_goods(card)`

**这是本需求唯一带未知量的实现，必须按「尽力解析 + 优雅降级」写。**

```
候选容器键（按优先级）：
  goods_info / goods / note_goods / goods_list / shop_info / product_info
候选字段映射（每个都做多候选探测，且**经 `_first_scalar` 展开数组容器**）：
  goods_id   ← goods_id / item_id / id
  title      ← title / name / goods_name / goods_title
  price      ← price / price_text / min_price / display_price
  image      ← image / cover / pic / images      （走 _first_url）
  url        ← url / link / scheme / jump_url / item_url
  shop_name  ← shop_name / seller_name / merchant_name
```

**降级规则（硬性）**：

| 情况 | 行为 |
|---|---|
| 未找到候选容器 | `goods = None`（前端不显示商品区） |
| 找到容器但字段缺失 | 该字段留 **空字符串**，**绝不填 0 / 占位文案** |
| 找到容器且至少有 `title` 或 `goods_id` | 视为解析成功，返回对象 |
| 容器存在但值是**空数组**（`{"goods_name": []}`） | → `None`。**不得**字符串化成标题 `"[]"`，见 §19.3.1 |

> **为什么取值必须走 `_first_scalar` 而不是 `_first_text`**：创作者链路把商品属性放在
> **数组**里（`{"goods_name": ["..."]}`），而 `_first_text` 的 `str([])` 会得到非空的
> `"[]"` —— 一个「读不到」被伪装成「读到了」的经典错误，真机上表现为每条笔记都挂着一个
> 标题为 `[]` 的假商品（§19.3.1）。

> **为什么不猜得更激进**：`[待验证]` P2 尚无抓包数据。宁可第一版解析率低但**结果可信**，也不要为了"看起来有数据"而编造。待抓到真实 `feed` 返回体后，本函数是**唯一需要修改的位置**。

### 6.4 新增：身份提取 `_normalize_identity(data)`

`/v2/user/me` 返回体结构未实测，故对 `user_id` / `nickname` / `avatar` 各做多候选探测：

```
user_id    ← data.user_id / data.basic_info.user_id / data.user.user_id / data.userId
nickname   ← data.nickname / data.basic_info.nickname / data.user.nickname / data.name
avatar     ← data.avatar / data.basic_info.image / data.user.avatar / data.imageb
```

**关键设计**：`_normalize_identity` 只做**信息展示**。`user_id` 的**权威来源**见 §7 —— 允许从用户粘贴的主页 URL 补齐，因为那是唯一能同时拿到 `xsec_token` 的途径。

### 6.5 新增：互动消息归一化 `_normalize_interaction_message(item, kind)`

统一为 `{kind, message_id, title, content, user_name, user_avatar, note_id, note_url, cover_url, time, raw}`，
对 `message_list` 中的差异字段（通知类含 `user` / 笔记卡片，关注类含 `user_info`）做多候选探测，**未知字段原样留在 `raw`**。

## 7. 身份与令牌解析：三级降级（C1 / P1 的核心设计）

`user_posted` 需要 URL 级 `xsec_token`，而它**不是 Cookie**（证据：`apis/xhs_pc_apis.py:330-334` 从 `user_url` 的 query 中解析）。
因此「怎么拿到自己的笔记列表」是本设计的关键路径，设计为三级：

| 级别 | 触发条件 | 行为 | `token_source` |
|---|---|---|---|
| **L1** | 请求带 `profile_url`（含 `xsec_token`） | 直接解析 URL 取 `user_id` + `xsec_token` + `xsec_source` | `"url"` |
| **L2** | 无 `profile_url` | 先 `get_user_me()` 取 `user_id` → 以**空令牌**试调 `user_posted` | `"auto"` |
| **L3** | L2 平台返回失败 | 抛 **400** + 结构化 detail（`code=XSEC_TOKEN_REQUIRED`），前端展示「粘贴主页 URL」引导 | — |

**设计取舍说明**：

- L2 是**乐观尝试**：若平台当前不校验令牌（或对自己的账号放行），用户零操作即可用；若校验，则退到 L3，代价仅一次失败请求。
- **不做"自动去平台抓主页 URL"**：那需要额外请求主页 HTML 并解析 `xsec_token`，属于**新增风控面**且稳定性不可控，超出「只读最小面」原则（C7）。
- L3 的 400 detail 用**结构化对象**而非纯字符串，便于前端可靠识别，避免脆弱的中文文案匹配：
  ```
  detail = { "code": "XSEC_TOKEN_REQUIRED",
             "message": "需要主页访问令牌（xsec_token）：请从浏览器地址栏复制你的主页链接并粘贴。" }
  ```
  （FastAPI 支持 dict 型 detail；此约定仅用于本模块，不影响既有端点）

> 参考：既有 `AccountRejectedError` 带 `status_code` 属性的模式（`services/account_service.py`），本项目已确立"错误要携带可判别信息"的做法。

## 8. 分页语义

### 8.1 cursor 透传

```
首次：  cursor = ""        →  平台返回 data.cursor + data.has_more
翻页：  cursor = 上次的 cursor
终止：  has_more == false  或  返回条数为 0
```

- cursor 是**不透明字符串**，后端**不得解析、不得假设其格式、不得本地生成**
- 缺少 `data.cursor` 时按 `has_more=false` 处理（沿用 SDK 全量版同款判断，见 `xhs_pc_apis.py:340-343`）

### 8.2 为什么禁用全量方法（C5）

`get_user_all_notes()`（`:321`）、`get_all_likesAndcollects()`（`:915`）等的实现是 `while True` 循环直到 `has_more=false`。

| 风险 | 说明 |
|---|---|
| **风控** | 一个有 500 篇笔记的账号 → **约 17 次连续请求**；若多账号并发浏览，极易触发限流 |
| **超时** | 后端 `REQUEST_TIMEOUT` 累计可能超出前端 120s axios 超时（`lib/api.ts:82`） |
| **资源** | 一次性返回数千条 `raw_json`，内存与响应体都不可控 |
| **不可中断** | 用户切走页面后请求仍在跑，无法取消 |

→ 本设计**只暴露单页能力**，"加载更多"由用户主动触发。这既是性能决策，也是风控决策。

## 9. 错误语义与状态码

| 场景 | 状态码 | detail | 前端表现 |
|---|---|---|---|
| 未认证 | **401** | `Not authenticated` | 跳登录（既有全局逻辑） |
| 账号不存在 / 不属当前用户 / 非 `xhs` | **404** | `Account not found` | 账号下拉标红，提示重新选择 |
| 账号无 Cookie | **400** | `Account has no cookies` | 提示「请先为该账号完成登录」 |
| **Cookie 不含网页会话，且该能力必需** | **400** | `{code: "WEB_SESSION_REQUIRED", message: ..., reason: ...}` | 该 Tab **置灰**并显示 `message`（D9） |
| 缺 `xsec_token` | **400** | `{code: "XSEC_TOKEN_REQUIRED", message: ...}` | 弹出主页 URL 输入框（§7 L3） |
| 平台返回失败 | **502** | 平台原始 `msg` | 原样展示平台原因（含 Cookie 失效提示） |
| `kind` 非法 | 422 | FastAPI 标准 | 不会被前端触发（下拉约束） |

> **v1.1 变更**：删除了「非 PC → 404」这一行。**账号类型不再是拒绝理由**；能不能用，由 `_has_web_session(cookies)` 与目标链路共同决定（§17）。
> 新增 `WEB_SESSION_REQUIRED` 与既有 `XSEC_TOKEN_REQUIRED` 是**两个不同的原因**，都必须与平台的裸错误区分开，否则用户无法自救。

**与既有端点的差异**：`/notes/detail`（`pc.py:600`）与 `/notes/comments`（`pc.py:617`）在任何失败下都返回 502。
本次**新增 400 分支用于区分"令牌缺失"**，是刻意的细化，不回溯修改既有端点（C8：不影响一期行为）。

## 10. 鉴权与账号归属

v1.1 拆成**两层**，因为「归属」与「能力」是两件事，混在一个函数里正是 v1.0 出错的根源：

```
第一层 _account_cookies()             ← 只判归属，不看 sub_type
  account is None                       → 404
  account.user_id != current_user.id     → 404   ← 归属校验（防越权）
  account.platform != "xhs"              → 404
  无 AccountCookieVersion 记录           → 400

第二层 _has_web_session(cookies)      ← 只判能力，不返回 404
  Cookie 串中含非空 web_session          → True（可走全部 PC 链路）
  否则                                   → False（可走创作者链路，其余置灰）
```

> **为什么必须拆开**：`sub_type` 表达的是**协议链路**（`pc` 搜索采集 / `creator` 上传发布），
> 它**不表达**「这个账号有没有网页会话」。按 `sub_type` 拒绝会误伤
> ——这也是项目 MEMORY 里反复强调「**禁止用 `sub_type` 判断业务含义**」的同一条规则。
> 详见 §17。

Cookie 通过 `decrypt_text()` 解密后取**最新版本**（按 `created_at desc`），符合"Cookie 不覆盖写、按时间倒序取用"的既有约定。

**安全要点**：
- 本需求**不新增**任何凭据存储，只读既有加密表
- 响应体**不回传 Cookie / 令牌明文**；`raw` 字段来自平台返回，不含本地凭据
- 日志不打印 Cookie（`01_开发规范` 红线 X11）
- ⚠️ **v1.1 新增：平台原始响应不得整体透传**。创作者身份接口 `/api/galaxy/user/info` 实测返回中含
  **`phone`（手机号）**、`realNameVerified` 等敏感字段，因此创作者身份走**字段白名单**
  （`userId` / `userName` / `userAvatar` / `redId` / `userDesc`），**其余一律丢弃**。
  PC 侧 `/v2/user/me` 实测无敏感字段，但同样按白名单构造 `raw`，不直接 `**` 展开。

**挂载商品区（v1.20 新增小节；用户 2026-09-20 报出后定稿）**

用户实测报出的现象是**一条时序**：弹窗刚打开时商品卡片是完整的，**正文请求返回后**同一块区域
只剩一行空图、版式也变了。根因不是渲染写错，而是**同一份数据被两个来源、两种形状各讲了一遍**：

| 来源 | 何时到达 | 字段 | 问题 |
|---|---|---|---|
| `goods`（列表行） | 打开弹窗**立刻**（列表接口就带着） | 最全：含 `shop_name`、含补到的 `price` | 会被详情响应覆盖 |
| `shop.goods`（详情按 `note_ids` 查千帆） | 正文到达**之后** | 少：**无**店铺名、**无**价格 | 版式与上面那块不同 |

而详情走的是 www feed，那个 payload **结构上没有商品容器**（§19.1 实测）→ 详情响应的
`goods` **恒为 `null`**。前端若用裸 `{ ...note, ...detail }` 合并，这个 `null` 就会**盖掉**
列表行已补齐的那一份 —— 于是「第二块」顶上来，用户看到的就是「区块变了」。

三条落地约束（缺一条就会复现）：

1. **后端给同一形状**：详情在 `goods` 为空时按 `shop.goods` 首条**回填**，且合成只走
   唯一一处 `_note_goods_from_parts`（列表与详情共用）。**「详情也有商品」不是目标，「两边同形状」才是**
   —— 形状不一致，前端就只能写两套渲染，那就必然漂移。
2. **前端合并必须写在展开之后**：`{ ...note, ...detail, goods: detail.goods ?? note.goods ?? null }`。
   `goods` 一行挪到 `...detail` **之前**，字符上只差一行、看着也「还在」，但运行时会被展开覆盖 ——
   **顺序本身是语义**（守卫须比下标，见 `test_page_optimizations.py`）。
3. **只渲染一块**：两处来源在 `mountGoods()` 里合成一份去重列表，旧的第二块**删除**（不是隐藏、不是置灰）。

**版式**（用户 2026-09-20 拍板，与「长文案一律 `…` + Tooltip」的 ADR-018 修订同源）：
标题**永远一行**（长度完全由平台决定，换行会撑高卡片）→ `ellipsis={{ tooltip }}`；
**规格与价格同一行**（`.goods-meta-row`，规格先让位、价格 `nowrap` 不压缩）。

**创作者账号的差异（v1.16 按真机实测修订，推翻 v1.2 的「不可得」结论）**：

v1.2 曾判「创作者账号弹窗拿不到正文/视频/评论」，理由是「创作者 Cookie 无 `web_session`
→ 详情接口不可达」。**这个判定是错的**，真机实测（2026-09-20）推翻它：

1. 创作者列表项**自带笔记级令牌 `xsec_token` 与 `xsec_source=pc_creatormng`**
   （`_normalize_creator_note` 已把它拼进 `note_url`，一直没人注意到）。
2. `xsec_token` 是**笔记级**令牌，**不**与发起方会话绑定；缺的是**任一**合法的 www 会话。
3. 同一个登录用户名下往往有一个 PC 账号，其 Cookie 含有效 `web_session`。
   **借用同用户会话 + 创作者笔记自带的 `xsec_token` → www feed 正常返回正文。**
   真机实证 5 条：正文 409–535 字、作者身份核验一致、图片可取、评论接口可达。
4. 借用的边界（安全要求）：**只借笔记维度**的读。借不等于共享自己的会话给别人；
   被借用的账号只要**同平台**即可，因为鉴权是笔记级的（下表）。全程只读，
   不改变请求的笔记与参数。

**为何能跨用户借**（安全论证）：详情端点的鉴权是**笔记级**的 `xsec_token`

读不到它。因此借用范围与「能不能读这篇笔记」无关，只与「有没有活的 www 会话」
有关。真正的数据隔离在**用户维度**端点上（下表）。

### 11.5 状态设计

- **per-Tab 独立状态**：`{items, cursor, hasMore, loading, error}`，四份互不干扰
- **懒加载**：仅当 Tab 首次被激活时才发请求（不预拉四个 Tab，符合 §12 风控）
- **不轮询**：无定时刷新，只保留手动刷新按钮
- **错误就地展示**：每个 Tab 保留自己的错误，切换 Tab 不互相覆盖

### 11.6 一个账号、两条凭据通道（v1.24，2026-09-20 用户拍板）

**需求原话**：「用户登录时默认获取两个会话令牌，一个 pc，一个千帆，调用不同接口则使用对应平台的令牌，
千帆和创作者可通用，保证数据库只有一个账号，又达到调用不同平台接口的需求。」

**真机实测依据**（§17.6.2，本轮补测三条，全部用真实 Chrome + 隔离 profile）：

| 实验 | 结果 |
|---|---|
| 只注入**创作者凭据** → 访问 `ark.xiaohongshu.com` | ✅ 直接进入后台，浏览器被种下 `access-token-ark`（19 键） |
| 只注入 **PC 网页版凭据** → 访问 `ark.xiaohongshu.com` | ❌ 被打回 `customer.xiaohongshu.com/login`，**拿不到 ark 令牌** |
| **真实登录** `www.xiaohongshu.com`（观隅好物） | ✅ 拿到 `web_session` + `id_token`，`/v2/user/me` 回 `nickname=观隅好物` |

⇒ **两个令牌必须分别获取**（www 登录给不了 ark），而**千帆与创作者可以共用一份**
（同属 `customer.xiaohongshu.com` 单点登录）。所以「两条通道」不是三条。

#### 11.6.1 模型

`account_cookie_versions` 增加 `channel` 列（迁移 `g7h8i9j0k1l2`）：

| 通道 | 关键 Cookie | 服务的接口 |
|---|---|---|
| `www` | `web_session` + `id_token` | `www` / `edith` / `sns/web`（我发布的·PC 链路、赞过 / 收藏 / 互动、详情、评论、搜索） |
| `ark` | `customer-sso-sid` / `access-token-ark` / `galaxy_creator_session_id` | **创作者平台 + 千帆（ark）共用** |

* 通道由 **Cookie 形态判定**（`account_service.channel_for_cookies()`），**不靠调用方传** ——
  分错的后果是「拿 www 的 jar 去打千帆接口」，平台只会回「缺失登录凭证」，错误信息完全指错方向。
  同时带两套键时按 `ark` 归位（www 那半边在 ark 接口上用不上）。
* 同一账号下两条通道**各有一串历史、互不覆盖**；读取必须显式选通道
  （`latest_cookies_for_channel(db, account_id, channel)`）。

#### 11.6.2 取数路由（**按目标平台选令牌，不按 `sub_type` 猜**）

| 调用方 | 通道 |
|---|---|
| `notes/detail`、`notes/comments`、`search/notes` | `www`（只有网页版提供） |
| 自内容列表 / 赞过 / 收藏 / 互动（先按能力分流） | `www` 优先，`ark` 兜底 |
| 创作者平台笔记列表（`get_posted_notes_page`） | `ark` |
| 千帆商品 / 店铺接口 | `ark` |

#### 11.6.3 「数据库只有一个账号」

* **账号按身份唯一**（`external_user_id`），`sub_type` 只描述**协议链路**、不再用来分账号；
* **PC 导入时顺带派生的创作者 Cookie，挂到同一个账号的 `ark` 通道**
  （改造前会 `upsert(sub_type="creator")` 再建一行 —— 同一个身份在库里留下两行，正是要消灭的形态）；
* **一次登录可以导入两份 Cookie**（`POST /accounts/import-cookie` 新增可选字段
  `ark_cookie_string`，前端「账号矩阵 → 导入 Cookie」已补第二个输入框），落库后仍是**一个账号**、两条通道；
* **存量重复身份**用 `backend/scripts/merge_duplicate_identity_accounts.py` 清理（默认 dry-run；
  默认**不搬**被合并行的 Cookie —— 过期凭据会让 `channels` 谎报可用）；
* **能力端点按通道上报**：`channels: {www, ark}`，`notes_link` 也改按**通道**判
  （有 `ark` 就能走创作者链路，哪怕账号当初是按 `pc` 建的号）—— 遵守「能力驱动而非类型分支」。

#### 11.6.4 边界（不做什么）

* **不做「一份 Cookie 通吃两个平台」**：真机已证明 www 与 ark 互不通用，任何「自动派生」都要碰
  带签名的 `ssologin`（台账 §4.10.9，违反只读边界 / C4）—— **不做**。
* **不删历史通道数据**：旧库里 `channel` 默认 `www`，由 `backend/scripts/backfill_cookie_channels.py`
  按形态回填（创作者 jar 会从 `www` 改判为 `ark`）。
* ~~**`shop_account_bindings` 暂不合并**：千帆侧仍走绑定表，本轮只统一「账号」这一层。~~ → **已被 2026-09-22 取代**：绑定表**整表移除**，千帆侧改为复用 `account_cookie_versions` 的 **`ark` 通道**（与 `creator` 同一存储、不同通道）—— 也就是**这两层已经合并**（契约见 §24.3.3 与数据模型 §9.2.1）。

## 17. 能力驱动的自有内容路由（v1.1 新增）

### 17.1 问题的起点：`sub_type` 被当成了能力

v1.0 的实现（`pc.py:533 _get_owned_pc_account_cookies`）里有一行：

```python
or account.sub_type != "pc"   # → 404
```

后果：**创作者账号（`sub_type == "creator"`）整页不可用**。而创作者账号同样能发布笔记，
店铺相关内容更是它独有的能力——把它挡在门外是把「协议链路」误当成了「业务能力」。

### 17.2 真实原因比 `sub_type` 更深一层

把守卫放开**并不能**让创作者账号工作。实测（2026-09-18，真实账号）：

```
XhsPcApiAdapter(creator_cookies).get_self_profile()
→ ValueError: XHSPcAuth.cookies must contain server-issued web_session;
              use qrcode/phone login when no saved session is available
```

两个账号的 Cookie 键集对比：

| 账号类型 | Cookie 键 | 有 `web_session`？ |
|---|---|---|
| `pc`（网页版登录） | `a1, abRequestId, ets, gid, id_token, loadts, sec_poison_id, webBuild, webId, web_session, websectiga, x-rednote-*, xsecappid` | ✅ |
| `creator`（创作服务平台登录） | `a1, access-token-creator.xiaohongshu.com, customer-sso-sid, customerClientId, ets, galaxy.creator.beaker.session.id, galaxy_creator_session_id, gid, loadts, sec_poison_id, webBuild, webId, websectiga, x-user-id-creator.xiaohongshu.com, xsecappid` | ❌ **没有** |

**所以拒绝发生在签名器，不在路由守卫。** 路由守卫只是提前把它变成了一个 404，
掩盖了真实原因，让用户和开发者都看不出「这个账号需要换一条链路」。

### 17.3 设计：三层路由 + 一个纯本地能力端点

```
POST /users/notes 的实现（scope == "notes"）
│
├─ 1. _account_cookies()        → 归属校验（404 / 400），不看 sub_type
├─ 2. _has_web_session(cookies)
│     ├─ True  → PC 链路：get_user_posted_page()      （/v1/user_posted）
│     └─ False → 3
└─ 3. account.sub_type == "creator"
      ├─ True  → 创作者链路：creator.get_posted_notes_page()
      │          （/api/galaxy/v2/creator/note/user/posted）
      └─ False → 400 WEB_SESSION_REQUIRED（既有账号，Cookie 失效）
```

**顺序刻意如此**：先问能力，再问类型。一个 `creator` 账号若将来补录了网页会话，
会**自动**走 PC 链路，无需改代码。反之一个 `pc` 账号若 Cookie 被换成创作者会话，也会正确降级。

**创作者链路的方法选择——必须用单页方法**：

| 方法 | 位置 | 是否可用 |
|---|---|---|
| `get_all_posted_notes()` | `apis/xhs_creator_apis.py:796` | ❌ **禁止**：内部 `while True` 循环翻页，与 §8.2 / DEF-033 同类风险 |
| `get_posted_notes_page(page, tab)` | `apis/xhs_creator_apis.py:739` | ✅ **采用**：本身就是单页，`data.page` 为下一页游标（`-1` 结束） |

这也是既有 `XhsCreatorApiAdapter.get_published_notes()`（`creator_api_adapter.py:27`）
的问题所在——它调的是全量版。**本次不为它新增全量调用，并把它登记为同类技术债的观察项。**

### 17.4 新增端点 `POST /api/xhs/pc/users/capabilities`

**纯本地端点，零平台请求**（只读 `platform_accounts` 一行 + 解密一个 Cookie 版本）：

```jsonc
// 请求

// 响应
{
```

|---|---|---|---|
| **PC 凭据**（acct 7 晨晨家） | ✅ `nickname=晨晨家`（自有会话） | ✅ 进创作中心，显示「晨晨家」 | ❌ 被打回 `customer.xiaohongshu.com/login` |
| **创作者凭据**（acct 8 观隅好物） | ❌ 只拿到**游客**会话（`nickname=None`、id 每次不同） | ✅ 显示「观隅好物」 | ✅ **直接进 `ark.xiaohongshu.com/app-system/home`，显示「观隅好物的店」** |
| **千帆凭据**（binding 1） | ❌ 同上 | ✅ | ✅ |

**机制**：千帆与创作者之间的互通走 `POST /api/cas/customer/web/service-ticket`
（`{'service': <目标站>, 'type': 'tgt'}`，`apis/xhs_creator_login_apis.py::_build_session_request`）——
凭 `customer-sso-sid` 给对方换一张 service ticket。PC 凭据里**没有** `customer-sso-sid`，
所以拿不到 ark 的 service ticket，这正是「PC → 千帆」失败的原因。

**因此**（对实现的含义）：

1. **PC → 创作者：可派生且已在用** —— 导入 PC Cookie 时
   `_sync_creator_account_from_pc_cookie()` 经 `exchange_from_user_cookies()` 顺带换出创作者会话。
2. **创作者 → 千帆：浏览器能做到，但服务端做不到（v1.22 二次更正）** ——
   浏览器里凭创作者凭据访问 `ark` 会自动登录（实测），但**服务端复现不了**：
   换票只拿到 `ST` ticket + `x-user-id-ark`，**换不出 `access-token-ark`**；
   浏览器最后一步是 **`POST https://ark.xiaohongshu.com/api/edith/open/ssologin`**
   （body `{system, ticket}`），该请求**带 `X-s` / `X-t` 签名** ——
   复现它既属**登录流程逆向**，又违反二开 C4「**不新增签名维护面**」。
   ⇒ **「免掉单独绑千帆」当前不可交付**：账号**仍须各自持有千帆令牌**（现落在 `account_cookie_versions` 的 `ark` 通道）。原句保留：~~「`shop_account_bindings` 仍是必需」~~ —— 表已移除，**结论不变**，只是凭据落点从绑定表换成账号的 `ark` 通道。
   证据与三条出路见 `docs/03` §4.10.8 的「更正」小节。
3. **创作者 / 千帆 → www：不成立** —— 反向没有交换入口（全仓仅 `exchange_creator_session_from_user_cookies`
   一个方向）。**这就是「我赞过的 / 我收藏的 / 互动消息」必须借同身份网页会话的根本原因**，
   也说明 §17.6.3 的借会话设计**不是绕路，而是唯一的办法**。
4. 三个 jar **独立过期**：实测 acct 1（pc）09-08 的会话已「登录已过期」，acct 8（creator）09-19 的仍有效。

**⚠️ 一个必须记住的陷阱（已登记 DEF-051）**：**`web_session` 存在 ≠ 已登录**。
**什么都不注入**的干净浏览器访问 `www.xiaohongshu.com` 也会被种上 `web_session`（游客会话）——
用这份 jar 调 `/v2/user/me` 回 `ok=True` 但 **`nickname=None`、`user_id` 每次不同**。
所以判「能不能读本人数据」**不能只看键在不在**（见 DEF-051）。

**被取代对照表（v1.21 → v1.22）**：

| 口径 | v1.21（旧） | v1.22（新，实测） |
|---|---|---|
| 总体表述 | 三个令牌**互不通用** | **两套体系**：`www` 独立；`creator` + `ark` 同属 customer SSO，**互通** |
| creator ↔ ark | 未测，默认「不通用」 | **✅ 互通**（`service-ticket` 换取；实测 creator 凭据可直接进 ark） |
| PC → creator | 可派生 | 可派生（不变） |
| creator/ark → www | 不可用 | 不可用（不变）；**但补充了成因**：www 只发游客会话，不是「拒绝」而是「认不出来」 |
| `web_session` 语义 | 隐含「有 = 已登录」 | **有 ≠ 已登录**（游客也有）→ DEF-051 |

#### 17.6.3 设计：只借「同一个人」的网页会话

> **⚠️ 本小节已被取代（v1.30 · 2026-09-22）**：**连「同一个人」也不借了** ——
> 目标账号自己没有 www 会话就是 400，不再去查库里有没有同一身份的另一行。
> 下表的「候选范围 / 探活 / 身份核对」整条流水线**不再存在**，见 **§17.10**。
> 仍然成立的一条：**绝不允许返回别人的赞过 / 收藏 / 互动** —— 只是现在的做法是
> 「一个都不读」，而不是「挑一个身份对得上的读」。

账号自己没存 `web_session` 时（典型：creator 账号），**借同一个人的另一个账号**的网页会话：

| 环节 | 契约 |
|---|---|
| 候选范围 | `external_user_id` 相同，或昵称相同且非空。**空值绝不参与匹配** —— 原 `external_user_id == ''` 会命中全平台所有同样为空的行，等于把「同平台」从后门放回来 |
| 身份判不出 | 目标账号 `external_user_id` 与昵称都空 → **直接不借**（否则「空 == 空」= 全平台） |
| 借用前探活 | 先发 **1 次只读** `/v2/user/me`；失败（会话过期 / 平台改形状）即跳过该候选 |
| 身份核对 | 探活拿到的 `user_id`（对 `external_user_id`）或昵称**必须与目标账号一致**；不一致就换下一个候选 |
| 借不到 | 400 `WEB_SESSION_REQUIRED` + 可读原因（**只写真原因**：凭据缺失 + 怎么修）。v1.28 起删掉了「创作者平台没有这三类数据」—— 该归因已被真机抓包推翻（§17.9.5） |
| 绝不允许 | 返回**别人**的赞过 / 收藏 / 互动。那不是「少数据」，是**显示错数据** |

> **为什么笔记维度可以借「同平台任一」而这三维不行**：详情 / 评论的鉴权是**笔记级**
> `xsec_token`，会话持有者的身份不影响可读范围（DEF-046 真机结论）；而 liked /
> collected / interactions 回答的是「**这个人**做过什么」，换个人就是换了一份答案。

#### 17.6.4 与 §17.4「纯本地能力端点」的修订

> **⚠️ 本小节已被取代（v1.30 · 2026-09-22）**：借用分支不存在 ⇒ 探活请求不存在 ⇒
> 能力端点**恒为零平台请求**（回到 §17.4 原口径），`session_source` 只剩 `own` / `""`。

代价换来的收益：页签**不会亮着却一点就报错** —— 会话过期时它老实置灰。

「网页会话可用」/「借用同身份网页会话」/「无网页会话」。

## 17.7 「账号没有自有 www 会话」不是致命错误：统一借用兜底（v1.27，DEF-056）

> **⚠️ 整节已被取代（v1.30 · 2026-09-22）**：v1.27 的诊断（**「同一个条件两套行为」**、
> 借用分支从未被执行）**仍然成立且仍然值得读**；但处置**反过来了** —— 现在的答案是
> 「**这个账号就是不能读，给结构化原因让用户去补登录**」，而不是「自有 jar 降级为加分项、
> 一律进借用」。现行契约见 **§17.10**；下文的「借他人 www 会话读该笔记 → 正文 451 字」
> 是一条**真机事实**（证明障碍是凭据不是权限），但**不再是一条允许的实现路径**。

### 17.7.1 用户实测报出的现象

在「我的笔记」页选中 **acct 8（观隅好物 · `sub_type=creator` · 库里只有 `ark` 通道）**：

| 动作 | 现象 |
|---|---|
| 打开任一条笔记 | **正文空白**（弹窗里只剩列表那份 thin 项），并弹一句**裸英文** toast `Account has no cookies` |
| 看评论 | 评论区提示同样的 `Account has no cookies` |
| 切「我赞过的 / 我收藏的 / 互动消息」 | 页签**置灰**，原因写「该账号的 Cookie 中不含网页会话（web_session）…」 |

### 17.7.2 根因：**同一个条件，两套行为**

两条链路在「账号自己没有 www 凭据」时的处理**完全不同**：

| 链路 | 取凭据方式 | 自有 www 缺失时 |
|---|---|---|
| `notes/detail`、`notes/comments` | `_get_owned_pc_account_cookies()` → 先 `_account_cookies(channel='www')` | ❌ **直接抛 400 `Account has no cookies`** —— 借用分支**从未被执行** |
| `users/liked`、`users/collected`、`users/interactions` | `_account_cookies_auto()` → 逐通道 `try`；失败再走借用 | ✅ 进入借用；借不到才抛**结构化** `WEB_SESSION_REQUIRED` + 可读原因 |

`Account has no cookies` 这句原文案是给**「这个账号一条凭据都没存」**用的；而「只存了 ark 通道」
是一种**完全正常的账号形态**（§11.6 就是为此设计的），却被它当成了错误。
⇒ 后果是 `_borrowed_web_session`（v1.25 刚落地、DEF-052 选 A 的成果）**在笔记维度形同虚设**：
只有「自有 jar 存在但过期」时才会被走到，「自有 jar 根本不存在」时反而不走。
**安全网又变成了条件性的**（与 DEF-048 同型，见台账 §4.10.12）。

### 17.7.3 真机取证（2026-09-21，生产适配器，只读 6 次请求）

用 acct 7（晨晨家 · `pc` · 完整 www 会话）的 jar，读 **acct 8** 的一条笔记：

| 请求 | 结果 |
|---|---|
| `get_note_info(note_url)` | `ok=True 成功`；**正文 451 字**、标题「夜市摆摊灯充电照明露营户外专用led灯超…」、`image_list` **4 张** |
| `get_note_all_comment(note_url)` | `ok=True 成功` |
| `/v2/user/me`（acct 7） | `ok=True`，`data` 含 `user_id` / `nickname` / `red_id` |

⇒ **借「另一个身份」的 www 会话能读到正文与评论**，§17.6（方案 A）的结论在 v1.27 再次被实测印证。
缺的从来不是权限，而是**代码没走到借用那一步**。

### 17.7.4 修法：自有 jar 是**加分项**，不是前置条件

`_get_owned_pc_account_cookies()` 的新顺序（写成一条不可回退的流水线）：

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 归属校验 `get_owned_active_account(...)` | 不变。**异租户 / 已软删仍 404**（DEF-055），这条不能被兜底吞掉 |
| 2 | 尝试取**自有** `www` 通道 jar | **取不到不算错**（区分开「HTTPException 404 归属」与「400 无凭据」两类异常） |
| 3 | 自有 jar 通过 `has_web_session()` | → 直接用，**零额外请求**（绝大多数账号走这条，行为不变） |
| 4 | 否则 → 一律进借用 | 笔记维度用 `probe_url`（调用方的**完整 URL**，含笔记级 `xsec_token`）；用户维度用 `probe_identity=True`（只借同一个人，§17.6.3） |
| 5 | 借不到 | 抛**结构化** `WEB_SESSION_REQUIRED` + 可读原因 —— **不再出现裸英文 `Account has no cookies`** |

**判据唯一化**：三条链路（detail / comments / liked·collected·interactions）此后共用同一条兜底流水线，
「同一语义不留两份实现」。

## 17.8 三个页签的门禁口径：以**取数结果**为准（v1.27，用户拍板）

### 17.8.1 用户口径（2026-09-21 原话）

> 「我赞过的 / 我收藏的 / 互动消息 均应再 PC 端获取**对应账号**的数据；
> 前端展示**不再根据账号类型进行限制**；**查询 PC 端获取到数据就展示，未获取到则不展示**。」

### 17.8.2 口径对照（旧 → 新）

| 项 | 旧（≤ v1.26） | 新（v1.27） |
|---|---|---|
| 页签可用性 | `capabilities.capabilities[scope].available === false` → **置灰 + 禁点** | **不置灰、不禁用**；页签永远可点 |
| 是否发请求 | 置灰时**不发** | **一律发**（仍 lazy：首次激活才发；分页仍受 §12 风控约束） |
| 取到数据 | 渲染 | 渲染（不变） |
| 取到**空** | 空态 | 空态（不变） |
| **取不到** | 页签置灰 + 悬浮里一段长原因 | **内容区一行 25–30 字安静提示**（§21.2 缺值口径同款）；**不弹 toast、不渲染红色错误块** |
| **接口异常** | 与「取不到」混为一谈 | **红块 + 真实原因** —— v1.28 起两者分开（§17.9 三分法） |
| 与 `sub_type` 的关系 | 「creator 账号整体受限」的观感 | **与 `sub_type` 完全无关** |

**为什么这样最合用户口径**：用户要的是「**以实际能不能取到为准**」，而不是「先用规则猜能不能取到」。
预判（capabilities 置灰）在原设计里的确避免了「页签亮着却一点就报错」（§17.6.4），
但那是以**误判**为代价换来的 —— 真机已证明**接口是通的**（§17.7.3），置灰挡掉的是可用链路。
两条诉求可以同时满足：**页签不拦**（用户口径）+ **失败降级为安静空态而不是报错**（原设计的本意）。

### 17.8.3 **不放松**的边界（重要）

| 边界 | 本版是否放松 |
|---|---|
| 用户维度只借**同一个人**的会话（§17.6.3） | ❌ **不放松**。「互动消息」没有 `user_id` 参数，借他人 jar 会返回**别人的通知** |
| `probe_identity` 探活 + `/v2/user/me` 身份核对 | ❌ 不放松 |
| 异租户 / 已软删账号 404（DEF-055） | ❌ 不放松 |
| 空值绝不参与身份匹配 | ❌ 不放松 |

> **一句话**：「取不到就不展示」是**展示口径**，不是**取数口径** ——
> 它允许界面上什么都没有，但绝不允许把别人的数据填进来。

### 17.8.4 三分类的真实响应形状（v1.27 真机补齐）

| 分类 | 真实路径 | 列表容器 | 分页字段 |
|---|---|---|---|
| 我赞过的 | `GET /api/sns/web/v1/note/like/page` | `data.notes[]` | `cursor`（str）+ `has_more` |
| 我收藏的 | `GET /api/sns/web/v2/note/collect/page` | `data.notes[]` | `cursor`（str）+ `has_more` |
| 互动·赞和收藏 | `GET /api/sns/web/v1/you/likes` | `data.message_list[]` | `cursor`（int）+ `strCursor` + `has_more` |
| 互动·提到我的 | `GET /api/sns/web/v1/you/mentions` | `data.message_list[]` | 同上 |
| 互动·新增关注 | `GET /api/sns/web/v1/you/connections` | `data.message_list[]` | 同上（item 含 `time/score/track_type/id/type/title/user`） |

实测（acct 7，2026-09-21）：liked **0 条**、collected **0 条**、`like_collect` **0 条**、
`mention` **0 条**、`connection` **1 条**，全部 `ok=True 成功`。
⇒ **「页签置灰」连它的理由都不是真的**：不是「读不到」，是「这个人恰好没数据」。

## 17.9 失败的呈现三分法：取不到 ≠ 接口异常（v1.28，DEF-058）

### 17.9.1 用户实测报出的现象（2026-09-21）

> 「我赞过的 / 我收藏的 / 互动消息**全部请求失败，请稍后重试**；
> 如果没有数据则无需展示，分析原因；**只有接口异常才真实抛出异常信息**。」

三个页签弹出的是**同一句**「请求失败，请稍后重试」。

### 17.9.2 根因：**结构化原因在最后一步被销毁**

| 层 | 事实 |
|---|---|
| 后端 | 借不到会话 → `400 {code: "WEB_SESSION_REQUIRED", message: "…"}` —— **结构化**、人可读 + 机器可读（§17.6.3） |
| 全局拦截器 | `typeof detail === "string" ? detail : "请求失败，请稍后重试"` —— **只认字符串** |
| 用户看到 | 后端辛苦给出的**真原因**被替换成一句通用文案。三个页签各一次 ⇒「全部请求失败」，且**没有任何可执行信息** |

这**不是三个页签的局部问题**：后端所有「诚实降级」的错误都是结构化 detail，
所以那句话在全站范围内都是一次**信息销毁**。

### 17.9.3 三分法（呈现口径）

| 情形 | 判定 | 呈现 |
|---|---|---|
| **有数据** | 200 且 `items` 非空 | 渲染列表（翻页失败时列表**照旧保留**，另给一条可重试提示） |
| **没数据** | 200 且 `items` 为空 | **空态** —— 那**不是错误** |
| **取不到**（预期内） | 400 `WEB_SESSION_REQUIRED` / `XSEC_TOKEN_REQUIRED` | 一行 25–30 字**安静说明** + Tooltip；**不弹 toast、不占红块** |
| **真·接口异常** | 其余（平台 5xx、签名失败、网络中断，**以及 422 请求校验失败**） | **红块 + 真实原因**（平台原话 / 状态码 / `loc：msg`） |

对应用户口径的最后一句：**只有接口异常才真实抛出异常信息** ——
所以「可自救的取不到」与「真坏了」**不能长成同一个样子**，
否则用户分不清「我该去登录」和「等一会儿再试」。

### 17.9.4 三个实现要点

1. **文案解析只有一份实现** —— `frontend/src/lib/api.ts::detailMessage()`，
   全局拦截器与页面 `readError()` 共用。同一件事留两份解析，迟早漂移出
   「toast 说的是真原因、页面说的是通用文案」这种自相矛盾。
   > 422 的 `detail` 是**数组**（Pydantic 校验错误）。v1.28 第一版把它当「不是给人看的原因」
   > 直接丢成空串，于是它只剩英文 axios 文案（`Request failed with status code 422`）兜底 ——
   > 那不是「还原真原因」，只是**换了一种看不清**。**v1.29 更正**：数组同样是接口异常
   > 要还原的对象，按 `loc：msg` 拼成一句（多项用 `；` 连接），丢掉 `type` / `input` 这类内部细节。
   > 只还原**可读**的部分，正是「只有接口异常才真实抛出异常信息」在数组形态上的落实。
2. **失败展示权归调用点** —— 自有内容四个 loader 一律 `_silent`
   （先例 `fetchXhsSelfCapabilities`）。否则页面已经安静降级了、全局再弹一次，
   等于**把置灰换成了报错**。
3. **短文案必须可执行** —— 不再写「请稍后再试」：会话过期**等一会儿不会变好**，
   唯一有效的动作是在网页版重新登录。给一个做不到的建议，用户只会反复刷新。

### 17.9.5 同轮删掉一句**已被推翻的归因**

借不到会话的原因里原有一句「（创作者平台不提供这三类数据）」。
它源自 §17.6.1 的需求前提（三分类全走创作者平台），而那个前提在
**2026-09-21 的真机抓包中已被推翻**：创作者账号持 www 会话时，
`sns/web/v1/note/like/page` / `v2/note/collect/page` / `v1/you/*` **全部可达**
（§17.7.3、§17.8.4）。

⇒ 障碍是**凭据**，不是平台能力。把「凭据缺失」说成「平台没有这个能力」，
用户**永远不会去重登** —— **一个错的归因，比不说更糟**。

> 守卫：`test_self_content.py::test_web_session_reason_does_not_repeat_a_disproven_claim`、
> `test_page_optimizations.py::test_structured_detail_reaches_the_toast_via_a_real_bundle`
> （后者用 esbuild 打包**真实** `lib/api.ts` 驱动真实拦截器，见 §17.9.6）。

### 17.9.6 为什么这里需要**行为**验证，而不只是源码断言

本项目的「前端必须做到的事」一直用源码断言钉（无前端测试框架）。
但本轮新增的断言里，**源码断言证明不了行为**：把 `detailMessage` 改成
`return ""` 之后，`"Array.isArray(detail)" in source` **依然为真**。

所以新增 `tests/frontend/detail_message.cjs`（先例：`qr_session_identity.cjs`）：
esbuild 打包真实 `lib/api.ts` → 拿到**真实**的 response 拦截器 → 驱动它 →
断言 antd 收到的文案。antd 用桩替换（放在产物的 `node_modules` 里并设为
`external`），因此**不需要 jsdom**，可以直接进 pytest：

```bash
node tests/frontend/detail_message.cjs                          # 13 PASS
DETAIL_MUTATE=generic    node tests/frontend/detail_message.cjs  # 期望 FAIL（真原因被吞）
DETAIL_MUTATE=silent     node tests/frontend/detail_message.cjs  # 期望 FAIL（不尊重 _silent）
DETAIL_MUTATE=validation node tests/frontend/detail_message.cjs  # 期望 FAIL（422 数组丢掉原因）
```

> ⚠️ 第一版把 antd 桩写成 esbuild 的 `alias` —— 桩被**内联进 bundle**，
> 于是 bundle 里 `message.error` 推的是它自己那份数组、脚本这边 `require()`
> 拿到的是另一份，断言永远看到「一条都没弹」（7 PASS / 4 FAIL，B 段全假红）。
> **桩要给运行期 `require` 留路**。

## 17.10 凭据只认**本账号**：会话借用整条路移除（v1.30，2026-09-22 用户拍板）

### 17.10.1 用户口径

> 「每个账号只使用自己账号对应的平台有效登录令牌。**获取数据必须使用对应操作账号的对应平台的登录会话令牌**，移除代码中的借用逻辑。」

这句话推翻了 v1.16 起逐步建起来的**全部**借用语义（§11.4 借用回退 → §17.6 用户维度只借同一个人 → §17.7 统一借用兜底）。它不是「把范围放宽/收紧」的调整，而是**取消借用这件事本身**。

### 17.10.2 结论对照表（旧结论原句保留在各自章节，本节只做对照）

| # | 旧（v1.16 ~ v1.27） | 新（v1.30 起） |
|---|---|---|
| ① | 笔记维度：自有 jar 不可用时向**同平台任一账号**借会话读详情/评论（DEF-052 选 A） | **不借。**自有 jar 不可用即 400 `WEB_SESSION_REQUIRED` |
| ② | 用户维度：只借**同一个人**的另一个账号的网页会话（§17.6.3） | **不借。**同上，且连「同一个人」也不借 |
| ③ | 借用前必须发 **1 次只读** `/v2/user/me` 探活（否则「页签亮着一点就报错」） | 该分支不存在 ⇒ **探活请求一并消失** |
| ④ | `session_source` 取值 `own` / **`borrowed`** / `""` | 只剩 **`own` / `""`**；`borrowed` 概念删除 |
| ⑤ | 能力端点「需要借用时发 ≤1 次只读请求」 | 能力端点**恒为零平台请求** |
| ⑥ | 正文回填在账号自己没有 www 会话时借同身份/同平台会话补正文 | 账号自己没有 www 会话 ⇒ **跳过回填**，正文留空（缺值口径，不造假） |

### 17.10.3 为什么取消（不是「更严」，是**归因换位**）

借用能解决的问题只有一个：**本账号的 www 会话过期或从未导入**。而它带来的后果是结构性的：

* **读到的始终是别人的数据面**。用户维度那三类（我赞过的 / 我收藏的 / 互动消息）回答的是「**这个人**做过什么」，借来的会话会把另一个账号的赞过/收藏/互动当成本账号的展示 —— 那不是「少数据」，是**显示错数据**。笔记维度虽以笔记级 `xsec_token` 为读闸门、扩大读范围的风险较小，但它把「凭据从哪来」变成了一条隐式规则：**页面上看不出这次读的是谁**。
* **它掩盖了真正该发生的动作**。会话过期/缺失的正确处置是**给这个账号补登录**（网页版），而借用让系统「自己想办法」，用户永远不知道某个账号其实一直没登录网页版。
* **它是一类持续漂移的温床**：借用范围（同 user_id → 同昵称 → 同平台）、探针条件化（DEF-048）、落地闸门短路（DEF-056）三轮缺陷全部长在这条路上。

### 17.10.4 新契约（三条，全部可验证）

| # | 契约 | 判据 |
|---|---|---|
| ① | **只认账号自己的平台令牌** | `_get_owned_pc_account_cookies()` 只取本账号 `www` 通道；取不到 → 400 `WEB_SESSION_REQUIRED` + 可读原因（只说一件事：给**这个账号**补登。v1.40 起文案为「该账号的 Cookie 中不含可用的网页会话，请登录创作者平台或 PC 端平台后重新导入 Cookie。」—— 用户 2026-09-24 口径：原文案太长，只留登录指引；「创作者平台」是登录入口指引，不是能力归因） |
| ② | **拿不到凭据时零平台请求** | 连「这份会话还能不能用」都不问平台 ⇒ 所有借用相关的探活请求消失（`/notes/detail`、`/notes/comments`、`/users/*`、`/users/capabilities`、正文回填） |
| ③ | **归属错误不得被兜底吞掉** | 只吞「本账号没存这条通道的令牌」（400）；**异租户 / 已软删仍 404**（DEF-055）——兜底不能变成越权 |

## 18. 列表字段保真度实测（v1.1 新增，本文档最关键的一节）

### 18.1 三个列表接口返回项的**真实**字段集

2026-09-18 用真实 `pc` 账号（Cookie 当日更新）实测：

| 接口 | 列表键 | 返回项字段 | 条数 |
|---|---|---|---|
| `/v1/user_posted` | `data.notes` | `cover, display_title, interact_info, note_id, time, type, user, xsec_token` | 30 |
| `/v1/note/like/page` | `data.notes` | `note_id, display_title, type, cover, user, interact_info, xsec_token` | 10 |
| `/v2/note/collect/page` | `data.notes` | 同 like/page | 10 |

**三个接口的列表项都只有 7–8 个字段，且：**

| 期望字段 | 是否存在 | 影响 |
|---|---|---|
| `desc`（正文） | ❌ **不存在** | 卡片无法展示正文（D6） |
| `image_list`（多图） | ❌ **不存在**（只有单张 `cover`） | 多图切换只能靠详情 |
| `video`（视频地址） | ❌ **不存在** | 视频播放只能靠详情 |
| `collected_count` / `comment_count` / `share_count` | ❌ **不存在** | 三个指标无法在卡片上显示 |
| `liked_count` | ✅ 存在（`interact_info.liked_count`） | 卡片上唯一可信的互动数 |
| `xsec_token` | ✅ 存在（**项级**，不在 `note_card` 内） | 详情请求的前提，见 §18.4 |

> ⚠️ **注意 `note_card` 的陷阱**：`user_posted` / `like` / `collect` 的返回项**没有 `note_card` 嵌套**。
> 而 `_normalize_search_item` 的实现是 `card = item.get("note_card") or item.get("note") or item`
> —— 会正确地退回 `item` 本身。**但搜索接口的 `note_card` 是嵌套的**，两种形态必须都支持，
> 不能假设其一。实测 `note_card keys=[]` 正是这一差异的表面症状。

### 18.2 「互动数恒为 0」的根因与处置

原实现（`pc.py:237-240`）用 `_metric(...)` 读四个字段，**读不到时返回 `0`**：

```python
"collects": _metric(interact.get("collected_count") or interact.get("collects")),  # 恒为 0
"comments": _metric(interact.get("comment_count") or interact.get("comments")),    # 恒为 0
"shares":   _metric(interact.get("share_count") or interact.get("shares")),        # 恒为 0
```

`_metric(None) → 0`，于是**「字段不存在」被伪装成了「数值为零」**。

| 处置 | 说明 |
|---|---|
| 卡片 | 只渲染**点赞**（唯一真实存在的指标） |
| 弹窗 | 打开时拉详情，用 `note_card.interact_info` 的**完整四项真实值**渲染 |
| 为什么不改 `_metric` 返回 `None` | `_normalize_search_item` 被「笔记发现」复用，而**搜索接口确实返回全部四项**，改动会波及无关页面（C8）。本次把保真责任放在**渲染层**：**列表没给就不渲染** |

实测详情接口的 `interact_info`（完整）：

```json
{"collected": false, "collected_count": "0", "comment_count": "0", "share_count": "0",
 "followed": false, "relation": "none", "nice_count": "0", "liked": false, "liked_count": "1"}
```

### 18.3 「不渲染」优于「渲染 0」

这是本节的**设计裁决**，也是需求验收口径「**禁止填 0 或占位假值**」的直接落实：

| 做法 | 结果 | 判定 |
|---|---|---|
| 渲染 `收藏 0 / 评论 0 / 分享 0` | 运营据此判断「这条笔记没人收藏评论」——**错误结论** | ❌ 违反验收口径 |
| 渲染 `—`（未知占位） | 不假，但三个破折号噪音大，且难解释 | 🟡 可接受 |
| **不渲染** | 信息量少，但不产生错误结论；完整数据在点击后立刻可见 | ✅ **采用** |

### 18.4 详情请求的 `xsec_source` 必须是 `pc_user` / `pc_feed`，不能是 `pc_search`

实测同一 note 的三种 `xsec_source`：

| `xsec_source` | 结果 |
|---|---|
| `pc_user` | ✅ `success=True`，`desc` 499 字，`interact_info` 完整 |
| `pc_feed` | ✅ `success=True` |
| `pc_search` | ❌ `success=False, msg="笔记不存在"` |

**含义**：列表项自带的 `xsec_token` 是**按签发场景绑定**的。
`user_posted` 签发的 token 属于 `pc_user` 场景，拿到 `pc_search` 下去用就会被判「笔记不存在」。

原 `_note_url()`（`pc.py:136`）在缺少 `xsec_source` 时默认填 `pc_feed` —— 恰好落在可用集合内，
所以**能工作**。但这属于**巧合而非设计**。v1.1 的处理：为自有内容三档显式指定
`_DEFAULT_XSEC_SOURCE`，不依赖默认值（`notes` / `liked` → `pc_user`，`collected` → `pc_user`）。

> ⚠️ 这里同时修正了一处 v1.0 的遗留不一致：`_DEFAULT_XSEC_SOURCE` 原为
> `{"notes": "pc_search", "liked": "pc_user", "collected": "pc_search"}`，
> 其中 `notes` / `collected` 的 `pc_search` **只适用于列表请求**，不能用于构造详情 URL。
> v1.1 已拆成两个常量：`_LIST_XSEC_SOURCE`（调用列表接口用）与
> `_NOTE_XSEC_SOURCE`（构造详情 URL 用，三档统一 `pc_user`）。

**「标题碰巧对（走了候选），封面空、点赞恒为 0、`raw` 里明明有值」**：

```
item: title='化妆室浴室地垫...' type='normal' likes=0 cover=
```

这比直接报错更危险：**页面正常渲染，只是每一条都少了图和数**。
教训（与 §18.2 同源）：候选探测能防崩溃，但**不能替代一次真实抓包**；
一旦拿到样本，主键必须换成真实键，候选只作保险。

**「总数」必须取 `tags`，不能取页大小**：单页 10 条而账号有 1969 篇，
若 `total` 用 `len(items)`，前端分页会显示「共 10 条」。实测已改为
读 `tags` 中 `checked: true` 那项的 `notes_count`，取不到时降级为页大小（退化为不准，而非出错）。

**旁证**：`goods_info` 这一概念在**读取与发布两条链路都存在**——
`xhs_utils/xhs_creator_util.py:177` / `:246` 的发布载荷里就有 `"goods_info": {}`（§19.1）。
即平台侧确有该字段，只是**自有内容列表里的 `goods_name` 恒为空数组**。

## 19. 商品挂载：来源与实现（v1.1 调研 → v1.6 定稿并实现）

> **状态（2026-09-19）**：✅ **已实现**。商品的唯一真实来源 = **千帆商家后台**
> （`ark.xiaohongshu.com`），接线契约见 **§24**；`/users/capabilities` 的
> `goods` 不再是一句占位说明，而是「来源 + 是否已具备读取条件」的机读声明。
>
> 本节保留 v1.1 的调研证据链——它回答的是「**为什么不能在 PC / 创作者链路上做**」；
> §19.3 的 UI 结论（一律不提示商品）由 **§24.4** 取代（现在有真实数据可展示）。

### 19.0 先把「读不到」与「不存在」分开（v1.6 补记）

v1.1 的结论原本是「PC 网页链路无法获取商品」，v1.2 又在样本里看到创作者链路的
`goods_info` 恒为 `{"goods_name": []}`，于是写成了「两条链路都不返回」。2026-09-19 用真实
店铺账号把这件事查到了底，结论要分三层说：

| # | 断言 | 证据 |
|---|---|---|
| 1 | 创作者笔记列表的 `goods_info` **是空壳** | `/api/galaxy/v2/creator/note/user/posted` 抽样 6 页 60 条（含末页 190），`goods_name` 全为 `[]`；同一响应里 `total=1968` |
| 2 | 创作者笔记管理页**自己也不渲染商品** | 本机 Chrome 打开 `creator.xiaohongshu.com/new/note-manager`，渲染后 DOM 内「商品」字样出现 **0** 次 |
| 3 | 但**商品确实存在** —— 在千帆 | 同一条 `note_id=6a7d1e2f000000002c001c33` 在千帆 `goods-note/list` 里带着 `item_id=6a3b3f61fb672a00154cba6c`、`item_title`、`item_image`、`variant_desc` |

**教训**：前两层只说明「这两条链路没有该数据」，不说明「这条笔记没挂商品」。
把前者读成后者，就会把「数据在别处」误判成「功能不可做」。

### 19.1 结论：**PC 网页链路无法获取笔记挂载的商品信息**

这不是适配遗漏，是**数据源本身没有**。证据链（全部实测，非推断）：

| # | 链路 | 接口 | 实测 |
|---|---|---|---|
| 1 | 我发布的列表 | `/api/sns/web/v1/user_posted` | 返回项 8 字段，无商品字段（§18.1） |
| 2 | 搜索列表 | `/api/sns/web/v1/search/notes` | `note_card` 无商品字段；`corner_tag_info` **只有** `{"type":"publish_time"}`，无商品角标 |
| 3 | 笔记详情 | `/api/sns/web/v1/feed` | `note_card` 13 字段：`interact_info, image_list, time, last_update_time, type, user, tag_list, at_user_list, share_info, note_statement, note_id, title, desc` —— **无商品字段** |
| 4 | 全键名正则扫描 | 详情 raw ≈ 5.5 KB | `goods\|item_id\|product\|commerce\|sku\|mall\|shop\|jump\|scheme\|link\|biz` **零命中** |

**为什么 App 里能看到**：App 走的是另一套接口（第三方聚合服务如 onebound / TikHub 提供的
`goods_list / goods_id / goods_title / goods_price / goods_url / shop_name` 正来自 App 侧）。
**PC 网页端不渲染商品卡片，其接口也就不返回该字段**——两者是一致的。

**旁证**：仓库里 `xhs_utils/xhs_creator_util.py:177` 与 `:246` 的**发布载荷**中存在
`"goods_info": {}`，位于 `common.goods_info`。说明平台侧确有该概念，只是**读取链路不返回**。

### 19.2 可选路径与决策

| 路径 | 数据 | 成本 / 风险 | 决策 |
|---|---|---|---|
| **A. 千帆商家后台（`ark`）笔记中心** | 第一方，笔记↔商品关联 | 需抓包；仓库当前**零实现**（连 `shop_account_bindings` 表都还没有，说明 M2 未开工） | ✅ **采用**（D8）：由商品笔记自动化需求（T-201~T-204）实现，本需求只消费 |

### 19.3 UI 影响：商品相关提示**全部移除**（v1.2 修订）

原实现在每条笔记的详情里显示：

> 未解析到商品信息 —— 该笔记可能未挂载商品，或平台的商品字段结构尚未适配（详见已知缺陷 DEF-006）。

问题在于：**该提示 100% 会出现**（结构上不可能有数据），且文案暗示「可能是适配没做完」，
用户会反复当成 bug 上报。**一个必然为真的警告等于噪音。**

v1.1 的处置是「条目级移除、页面级保留一条说明」。**v1.2 进一步把页面级也移除**——
理由是同一条判断的延伸：既然商品字段在 PC 链路**结构上不存在**，那么页面顶部挂一条
「暂不支持」的说明条，与条目级提示一样属于**对用户不产生任何行动价值的持续噪音**。
用户打开「我的笔记」想看的只有笔记本身；商品能力何时接入属于**交付节奏**，应由
项目文档（本文档 §19 / 缺陷跟踪）承载，而不是长期占据页面首屏。

**处置**：

| 位置 | 改法 |
|---|---|
| 条目级（详情内） | **移除**。`goods === null` 时不渲染任何内容 |
| 页面级（一次性说明条） | **移除**（v1.2）。`GOODS_LIMITATION` 常量一并删除，不留死代码 |
| 商品区块渲染 | **保留**。`goods` 非空时照旧渲染（商品名/价格/店铺/链接）——一旦千帆接入或平台变更，无需改前端 |
| 解析能力 | **保留** `_extract_goods` 多候选探测（不改） |
| 能力端点 | `/users/capabilities` 的 `goods.available = false` **保留**——它是**机读**的能力声明，与**人读**的提示不同：前端将来可在别处以必要形式消费它，且它不占页面空间 |

> `_extract_goods` 的「探测 + 返回 `None` 而非造假」设计**是正确的**，本次仅去掉它的**报警展示**，
> 不动它的**探测逻辑**。这正是当初把「解析」与「展示」分开的价值。

#### 19.3.1 顺带修掉的一个真 bug：空数组被字符串化成假商品

`_extract_goods` 原先用 `_first_text(..., container.get("goods_name"))` 读标题。
创作者链路返回的是**数组**（`{"goods_name": []}`），而 `_first_text` 的实现是
`str(value).strip()` → `str([])` 得到 **`"[]"`**，非空、为真。

后果：**每一条创作者笔记都会挂上一个「标题为 `[]`」的假商品对象**，
`goods` 由 `None` 变成真值，前端于是渲染出商品区块。真机症状：

```
"goods": {"goods_id": "", "title": "[]", ...
```

这与 §18.2「字段不存在被伪装成数值为零」是**同一类错误**——都是
**「读不到」被悄悄转成了「读到了某个值」**。修法是新增 `_first_scalar`：
先展开列表容器再取首个非空值，空数组自然退化为 `""`（→ `goods_id` 与 `title` 皆空 → 返回 `None`）。

> **规律沉淀**：本项目里凡是「缺省值」出现在**数据层**，都要先问一句
> ——这个缺省值是**平台真的给了这个值**，还是**我们没读到**？两者的下游行为往往相反。

### 19.4 对 DEF-006 的收敛

`DEF-006`（`goods_info` 待抓包）此前是一个**悬空的期望**。本次实测把它**收敛为一个确定事实**：

| 变更前 | 变更后 |
|---|---|
| 「`feed` 返回体中商品字段路径未知，需抓包」 | 「`feed` **不含**商品字段（已实测）；商品关联需从千帆笔记中心获取」 |

即：**从"未知"变成了"已知不可得"**。这不是坏消息——它把一个反复被误认为 bug 的现象
变成了一个有明确承接方（T-201~T-204）的设计决策。

## 20. 列表无限滚动（R7 / D13，v1.4 新增）

**决策变更记录**：v1.3 的设计是「`cursor` + 显式『加载更多』按钮，不做无限滚动」（原 §12 表格）。
v1.4 按用户要求取代它：**滚到底部自动加载下一页，按钮移除**。这不是"放宽风控"——触发粒度仍是
**用户的一次滚动行为**，与「点一次按钮」同阶；真正的风控面来自**循环拉取**，而循环点按钮与循环滚动等价。

### 20.1 契约（前端实现约束，测试按此钉住）

| 项 | 约束 |
|---|---|
| 触发 | 列表底部 sentinel 元素 + `IntersectionObserver`，`rootMargin: "240px 0px"`（提前约 240px 预加载，滚动不卡顿） |
| 触发条件 | `hasMore === true && loading === false && error === null` 三者同时成立 |
| 粒度 | **一次触发只拉一页**，`cursor` 原样透传（§8.1）；`in-flight` 用 ref 去重，防止同一页被并发拉两次 |
| 失败即停 | 任何一页失败 → **停止自动触发**，渲染可读错误 + 「重试」按钮。**不做自动重试**（§12「失败不重试」仍然有效） |
| 结束态 | `hasMore === false` → 显示「已全部加载」，不再触发 |
| 清理 | 组件卸载 / 切换账号时 `observer.disconnect()`；账号切换后 `cursor` 状态整体重置（避免拿旧游标继续拉） |
| 搜索态 | 搜索结果**不启用**无限滚动（搜索有自己的「继续搜索更早内容」，语义不同） |

### 20.2 为什么不用 `maxHeight` 容器监听滚动事件

`IntersectionObserver` 在「窗口滚动」与「祖先容器 `overflow` 滚动」两种布局下都成立
（祖先裁切会反映到 intersection rect 上），而手写 `scroll` 监听需要事先知道滚动容器是谁
（本项目 `app-shell.tsx` 的 `Content` 带 `overflow: auto`，实际是否滚动取决于高度约束）。
**用 sentinel 观测，布局怎么变都不用改代码。**

> 第 5 条的意义：**"找不到"与"猜一个路径写进代码"是两种完全不同的行为**。本节把 Creator 的

### 21.2 映射与实现口径

| 平台字段 | 我们的字段 | 说明 |
|---|---|---|
| `interactions[type=fans].count` | `followers`（粉丝） | 字符串数字，`_metric()` 统一转 int（支持 `万` / `w` 后缀） |
| `interactions[type=follows].count` | `following`（关注） | 同上 |
| `interactions[type=interaction].count` | `likes`（获赞） | 平台名为「获赞与收藏」，**文案按平台口径**显示「获赞数」 |

| 约束 | 做法与理由 |
|---|---|
| **按能力路由** | 判定依据是 Cookie 里有没有 `web_session`，**不是 `sub_type`**。creator 账号将来若带上 www 会话，无需改代码即可取数 |
| **省一次请求** | 优先用 `platform_accounts.external_user_id` 当 `target_user_id`（对 PC 账号它等于 `/v2/user/me` 的 `user_id`）；失败才回退 `/v2/user/me` 再重试 |
| **零平台请求** | creator-only 账号直接返回 `metrics_reason`，**一次请求都不发**（与 §17.4 能力端点同构：结构上不可能成功的事不做） |
| **失败不擦数据** | 刷新失败时保留 `profile_json` 里已有值（`_first_present(新值, 旧值)`），避免「一次网络抖动把好数据清零」 |
| **三入口同一函数** | `/check`、`/import-cookie`、`/metrics` 共用同一个取数与落库函数；**禁止在任一入口另写一套解析** |
| **提示文案 25–30 字** | `metrics_reason` 一律 25–30 个字符（R10 / D16）：四条固定原因（creator / 无 `web_session` / 平台未返回 / 读取异常）写成 26 / 28 / 27 / 25 字；**动态部分（平台 `msg`、异常文本）由 `_clamp_reason()` 截断到 30 字**——单测钉死窗口，防止文案日后又长回去 |
| **缺值渲染 `0`** | 三项计数缺值 → `0`（不是 `-`），**小红书号仍为 `-`**（它不是计数）；前端只做 `?? "0"` 的展示兜底，**不做业务判断**，原因文案一律来自后端 |
| **长文案溢出：`…` 收起 + Tooltip 看全**（2026-09-19 用户拍板，取代「直接换行」） | 账号卡片是窄列（`lg=8`），而原因文案长度**不由前端决定**（后端 25–30 字 + 动态平台原文可到 30 字），窄屏下必然放不下。规则：这些**一行放不下的文案一律单行 `…` 收起，悬停出 tip 显示全文**（`Text ellipsis={{ tooltip }}`，**只在真被截断时才出 tip**）。**不要改成换行**——换行会把卡片撑高、把下面的按钮挤出可视区，同一屏的账号卡高度还会参差不齐。适用范围：`metrics_reason` 原因行、`status_message` 平台原文行、**「更新时间」行**、以及 M1.9 的同步进度/结果行 |

| 3 | **能力判定仍按 `web_session`**（§21.2 原约定，此处补成闭环） | 有 www 会话 → 取数；没有 → **零平台请求** + 可读原因。sub_type 从此与互动数据取数**完全无关** |
| 4 | **移除「创作者平台不返回互动数据，请改用网页版登录的账号查看」**（`CREATOR_METRICS_REASON`） | 该归因**已被真机抓包推翻**（创作者账号持 www 会话时 PC 端点全部可达，DEF-058 同族：错归因让用户永远不会去重登）。取不到时的统一原因是 `NO_WEB_SESSION_METRICS_REASON`：「该账号 Cookie 不含网页会话，请重新登录网页版账号」（28 字，在 25–30 字窗口内） |
| 4b | **PC 会话不可用时弹窗提示登录**（2026-09-21 追加口径） | 点「同步数据」时若 www 状态是「确定不可用」（`missing`/`guest`/`expired`），**不发起同步**，弹窗提示登录（「去登录」打开网页版续期弹窗）。与千帆门禁同一条判据（设计 13 §6.1.0）；`unknown`（未检测）放行 —— 用「没检查」冒充「不可用」会让人做多余的重登（DEF-057 红线） |
| 5 | 两种「没有」必须分开 | **一个 Cookie 版本都没有** → `NO_COOKIE_METRICS_REASON`（「该账号没有已保存的 Cookie 版本…」）；**有版本但没有 www 通道** → `NO_WEB_SESSION_METRICS_REASON`。旧实现在这两种情况下都给前者 |
| 6 | 展示口径不变 | 缺值渲染 `0` + 原因行（§21.2）；「同步数据」仍只由显式点击触发；失败不擦已落库数据 |

**与 §21.3 的对照**：§21.3 把 Creator 计数定性为「结构不可得」是**对创作者平台**的正确结论（§21.1 第 4/5 条仍成立），
但它被误用成了「Creator **账号**取不到计数」—— 而账号可以有多个通道的令牌。v1.31 把判据从
「账号是什么类型」改成「有没有网页版会话」，同一份代码对两类账号都正确。

### 22.1 请求 / 响应契约

```jsonc
// 请求
{ "account_id": 8,
  "keyword": "地垫",
  "pages_per_scope": 3,                       // 默认 3，上限 5（服务端硬夹紧）
  "cursors": { "notes": "", "liked": "", "collected": "" } }   // 续搜时回传上一轮的值

// 响应
{ "keyword": "地垫",

  "total_matched": 4,
  "has_more": true,                            // 任一分类还有未扫页 → UI 显示「继续搜索更早内容」
  "cursors": { "notes": "CUR-X", "liked": "CUR-Y", "collected": "CUR-Z" },
```

### 22.2 为什么是「有界扫描」而不是「一次拉全」

| 方案 | 判定 |
|---|---|
| 调 SDK 全量循环（`get_user_all_*`）直到 `has_more=false` | ❌ 违反 C5；近 2000 篇笔记 = 几十次连续请求，风控面最大 |
| 只搜「当前已加载的一页」 | ❌ 语义错误：用户在搜索结果里看不到第 3 页的笔记，却以为"没有" |
| **有界扫描（每类 N 页，可续搜）** ✅ | 请求量有上界（≤ 3×N 次，默认 9）、语义诚实（元数据里明确「已扫描多少页」）、用户可推进 |

### 22.3 匹配与容错口径

| 项 | 规则 |
|---|---|
| 匹配域 | 标题 + 正文（若有）+ 话题标签；大小写不敏感 |
| 多词 | 按空白切分为多个 token，**全部命中**才算匹配（AND 语义）；单个 token 时等价于子串匹配 |
| 早停 | 某分类 `has_more === false` 即停止该分类扫描，标记 `exhausted: true`（不空跑） |
| 去重 | 按 `scope + note_id` 去重（同一条笔记可能既被赞过又自己发布） |
| 部分失败 | 某分类失败只写 `scopes[x].error`，其余分类照常返回；**绝不整单 500** |
| 能力路由 | Cookie 无 `web_session` → 400 `WEB_SESSION_REQUIRED`（creator 笔记管理页没有关键词检索接口，不假装支持） |
| 令牌 | 复用 §7 的三级降级（L1 粘贴主页 URL / L2 自动 / L3 结构化 400） |

### 22.4 UI 契约

- 搜索框只在「我发布的 / 我赞过的 / 我收藏的」三个 Tab 生效；creator 链路**置灰 + Tooltip 原因**（原因文本来自 `/users/capabilities`，前端不另写业务判断）。
- 结果卡带**来源标签**（我的笔记 / 我赞过的 / 我收藏的）；点击复用既有详情弹窗（`xsec_token` 随条目带出，否则详情会「笔记不存在」，见 §18.4）。
- 顶栏元数据：`已扫描：我发布的 3 页 · 赞过 1 页 · 收藏 0 页（失败）`，命中 `N` 条。
- `has_more` 为真时给「继续搜索更早内容」按钮（带 `cursors` 续搜）。

## 23. 详情弹窗的固定尺寸与内部滚动（R9 / D15，v1.4 新增）

**问题**：v1.3 的弹窗是 `maxHeight: 72vh; overflowY: auto` —— **整块 body 滚动**。
笔记正文越长，评论区被推得越远；评论加载完成后高度还会跳一次。
用户要的是「弹窗整体不动，内容自己滚」。

| 层 | v1.4 形态 | 理由 |
|---|---|---|
| Modal body | **固定** `height: 72vh` + `overflow: hidden` | 弹窗外框与分栏**恒定**，不随内容多少变化（`maxHeight` 会让短笔记与长笔记骨架不同 → 开合跳动） |
| 左右两栏 | 各 `height: 100%`，**各自** `overflow-y: auto` | 左栏长图 / 多图缩略图不挤压右栏 |
| 右栏 · 信息区 | flex 纵向的第一段，`overflow-y: auto; min-height: 0` | `min-height: 0` 是 flex 子项能滚动的必要条件（默认 `min-height: auto` 会撑破父容器） |
| 右栏 · 评论区 | **固定 280px** + `overflow-y: auto` | 加载中 / 空 / 失败 / 有数据**四种状态占同一高度** → 评论到达时**不跳动** |
| 窄窗（< 900px） | body 内部滚动、两栏恢复自然高度 | 用 `global.css` 的 class + `@media` 实现；固定高度在堆叠布局下会裁切内容 |
| 创作者链路 | 无评论区（§11.4）→ 信息区独占右栏全高 | 结构天然兼容，无需分支 |

**验收指纹**：打开任意长笔记 → 弹窗外框与信息区**不动**，滚动只作用在评论列表上；
无评论 / 评论加载失败时弹窗高度**一致**。

## 24. 千帆（ark）只读接线：笔记挂载商品与店铺侧数据（v1.6 新增，已实现）

> **需求**：R5（挂载商品信息）；用户 2026-09-19 的定调是
> 「**移除占位说明，直接对接千帆后台**」「**创作者账户数据全部接入千帆**」。

### 24.1 数据源判定（一句话）

笔记挂载的商品**只**存在于千帆：`{note_id → item_id / item_title / item_image / variant_desc}`。
它不在 PC 链路（§19.1 实测），也不在创作者链路（§19.0 实测）。

#### 24.1.1 按笔记查询的口子 —— `note_ids`（v1.12 实测，**更正**早前结论）

| 输入 | total | 结论 |
|---|---|---|
| `note_ids=<真实 note_id>`（一条） | **1** | 精确命中，行的 `item_id` 与店铺口径一致 |
| `note_ids=<不存在的 id>` | 0 | **真在过滤**（不是「恰好只有一条」） |
| `note_ids=a,b,c…`（实测 2/6/10/20/**50** 个） | = 传入个数 | **一页笔记一次请求**的依据 |
| `note_ids` 里混入不存在的 id | 仍是真实条数 | 不污染结果 |
| 单数 `note_id` / `keyword` / `search_filter.*` 等共 15 个候选 | 1968（= 店铺总数） | ❌ 被平台忽略 |

**被取代的旧结论**：早前文档写「千帆商品笔记列表**没有**按 note_id 查询的口子，所以只能按页翻取后
本地 join」—— 那是**只试了单数 `note_id`** 得出的。复数 `note_ids` 就是口子（2026-09-19 用
「阳性/阴性判别式实验」一次性确认，过程见附注）。

三个必须记住的坑：

1. **复数**：`note_ids`，不是 `note_id`（写错就静默退化成「全量」）。
2. 带 `note_ids` 时响应里的 `total` 是**过滤后条数**，不是店铺总数 —— 拿它当覆盖率分母会把分母写坏（1968 → 2）。
3. 与分页**正交**：命中 N 条仍受 `page_size` 约束（实测 2 条 + `page_size=1` → `total=2` 但只回 1 行），
   所以批量查询的 `page_size` 必须 ≥ 传入的 ID 个数。

> **判别式实验（可复用）**：拿「必然存在的 id」与「必然不存在的 id」各试一次同一参数名 ——
> 两次 `total` 都与基线相同 = 参数被忽略；一次命中、一次为 0 = 参数生效。比反推前端源码快得多
> （千帆 sourcemap 私有，403）。

#### 24.3.1 登录态巡检契约（v1.11 / T-31）

**问题**：千帆登录态是独立凭据（§24.2），会过期；此前只有用户点「同步商品」才会发现
—— 页面看起来「一切正常，只是没商品」，属静默失败。

| 项 | 契约 |
|---|---|
| 探活方式 | **只读** `GET /api/edith/seller/info/v2`；实现 `services/shop_health_service.py` |
| 触发 | ① 定时任务 `qianfan_health_checker`（APScheduler，默认 **6 小时**）；② 端点 `POST /qianfan/health-check`（立即） |
| 频率 | `qianfan.health_check_interval_hours`（默认 6，≥1）；`qianfan.health_check_enabled=false` 则**不注册定时任务**（手动仍可用） |
| **有界** | 按 `health_checked_at` 判到期 —— **未到期直接跳过**（`checked=0`），所以手动点一次不会变成刷请求 |
| 失效 | `status="invalid"` + `status_message=` 平台原文（截断 200 字）+ 写 `health_checked_at` |
| 通知 | 走 `notifications`（铃铛，`level=warning`，标题「千帆登录态失效」），**只在状态翻转那一次**发（否则 24 小时 4 条同样的铃铛） |
| **不毁数据** | 失效**不清空** `shop_note_goods` —— 凭据过期不等于数据作废（T-31 既有结论） |
| 失败不重试 | 一次失败即定论，等下一周期（沿用项目「失败不自动重试」纪律） |
| 恢复 | 巡检成功 → `status="active"` + `status_message=""`；店铺改名时同步刷新 `shop_name`（平台没给就保持原值，不写空） |
| 用户可见 | 「我的笔记」商品来源行显示「巡检 `YYYY-MM-DD HH:MM`」+「立即巡检」按钮；`invalid` 时额外一条告警 +「重新绑定千帆」；`/users/notes` 的 `goods_source.health_checked_at` 同步暴露 |

**同步（`sync-goods`）为什么不顺带写 `health_checked_at`**：同步成功固然说明凭据活着，但
这个字段的语义是「最近一次**巡检**」，混写会让定时巡检误判「刚查过」而长期不再主动探活。
（v1.32 起该端点已移除，结论对笔记同步 ark 源同样成立。）

#### 24.3.2 按需补齐契约（v1.12 / T-30，**取代**「后台全量同步」）

**用户定调（2026-09-19）**：不做后台全量同步；**加载笔记时**才去同步这几条笔记挂载的商品。

| 项 | 契约 |
|---|---|
| 触发 | 「我的笔记」加载某一页时，只对**该页缺映射**的笔记发起补齐 |
| 次数 | **每页 ≤1 次**只读请求（`note_ids` 逗号拼接一次拿回；不传 → **零请求**） |
| 上限 | `ON_DEMAND_NOTE_LIMIT = 50`（去重后截断；一页 10–50 条够用） |
| 缓存 | 命中过的笔记**落库**（`shop_note_goods`）→ 第二次浏览该页 **零平台请求** |
| 负记录 | 平台**不返回**「这条笔记没商品」的负记录 ⇒ 确认没商品的笔记每页加载会被重查 1 次（仍 ≤1 次/页） |
| 失败 | **静默**：页面照常 200，只是这几条暂时没有商品；原因回传在 `goods_source.on_demand.error` |
| 凭据失效 | `code=-13000` → 绑定标 `invalid` + 可读原因（页面出现「重新绑定千帆」），**不清已有映射** |
| 不删数据 | 按需补齐**只 upsert 本页**的 `note_id`，**从不删除**任何行；v1.32 起**全链路都不再删**（手动批量入口已移除，§30.2）—— 与关系表「只增不删」同口径，解绑时整账号清理 |
| 分母守卫 | **不**用带 `note_ids` 的响应 `total` 覆盖 `goods_note_total`（那是过滤后条数）；门店总数由**无过滤的翻页同步**更新（笔记同步 ark 源 / 商品笔记翻页） |

**为什么不是后台全量慢跑**：一个店铺近 2000 条商品笔记 ≈ 上百页；而用户一次只看 10 条，
大部分页可能永远不被打开。按需补齐把成本精确投在「用户真正看的那一页」，
且首次看过的页面第二次就是零请求 —— 全量慢跑没有这个性质（每轮都要重新翻）。

**代价（诚实登记）**：「我的笔记」一页的千帆请求数从 v1.9 的「0」变成 **0–2**
（0 或 1 次按需补齐 + 0 或 1 次补价），且当一页里有「确认没商品」的笔记时会**每次都花那 1 次**。
实测（账号 8）：全部命中时 **0 次**、1 条缺失时 **1 次**（1.38s vs 1.20s）。

**同步的四条纪律**（与 §8.2 / §12 同源）：

| 纪律 | 做法 |
|---|---|
| 有界 | `max_pages` 默认 3、上限 20；`page_size` 上限 100 ⇒ 单次最多 2000 条 |
| 部分失败不整单报错 | 第 1 页失败 → 502；后续页失败 → 保留已同步部分 + 原因写回绑定状态 |
| 陈旧行只在完整同步时清理 | 未扫完就删行 = 丢数据 |
| 登录态失效可判别 | `code=-13000` → 绑定标 `invalid` + 可读原因，**不清空已有映射** |

#### 24.3.3 账号 ↔ 店铺 ~~是 N:M~~ → **已改回 1:1**（v1.15 / T-32 → **2026-09-22 反转**）

> ⛔ **本节整张契约表已被 2026-09-22 取代**（原句保留在下方，供追溯「为什么曾经是 N:M」）。
> 用户口径原文：**「不再允许同店铺多账号，一个店铺下只存多个平台的会话令牌」** ⇒
> 关系回到 **1:1**（`platform_accounts.shop_id_fk` + 部分唯一索引 `uq_platform_accounts_shop_id_fk`），
> `shop_account_bindings` **整表移除**（迁移 `m5n6o7p8q9r0`），`binding_for_account()` /
> `bindings_for_shop()` / `shop_account_count` **全部不再存在**。
> **现行契约 = 数据模型 §9.2.1**（关系→`shop_id_fk`；凭据→`account_cookie_versions` 的 `ark` 通道，
> 唯一取票入口 `qianfan_cookies_for_account`；状态/游标→`platform_accounts.shop_state`）。

原来 `shop_account_bindings.platform_account_id` 上是 `UNIQUE` → 语义是「**一个账号最多读一个店**」。
这挡掉了企业店主 + 多子账号这一真实形态（几个账号读**同一个**店铺）。

| 项 | 契约 |
|---|---|
| 表结构 | 新增 `shops` 实体表；绑定表加 `shop_id_fk`；唯一约束改为 **`(shop_id_fk, platform_account_id)`** |
| 迁移 | `f4a1c8e2d935`：按 `seller_id` 去重把历史绑定回填成店铺行（**零丢失**）；SQLite 需**重建表**（`alter_column(unique=False)` 实测不生效，见数据模型 §9.2） |
| 绑定幂等 | 以 `(店铺, 账号)` 为键：重复绑定 = 重验一次凭据，不建第二行、不建第二个店铺 |
| **「用哪条绑定」** | 一个账号绑了多个店铺时，**同步过映射的优先**、其次最近绑的（确定性排序，实现在 `services/shop_binding_service.binding_for_account()` **唯一一处**）；路由层严禁自己 `.first()` |
| 解绑 | 只解本账号；别的账号的绑定与映射**一律不动**；店铺行仅在**无存活绑定**时删除（孤儿清理，见下「计数闸门」） |

| **计数闸门：软删同闸**（v1.26，DEF-055） | 已软删账号（`platform_accounts.deleted_at` 非空）的绑定**不参与**任何计数、也不参与「用哪条绑定」的判定；`drop_binding` 判「店铺行该不该删」同样只算**存活绑定** —— 否则一条被删账号的绑定会**永久顶住**店铺行，让孤儿清理永不生效。 |
| 用户可见 | 「我的笔记」来源行与商品列表页账号选项都标注所属店铺；`shop_account_count > 1`（**同租户内确实多个账号**）时说明「**同一店铺，数据是同一份，不是多套**」（不说清会被读成两套数据） |
| 属 M2 的部分 | 让用户**显式选择**用哪个店铺（`access_role` / `can_sync` 计划字段）、把凭据上提到店铺行 —— 现在没有消费者，留到 M2 |

### 24.4 数据契约（前端拿到什么）

**① `capabilities.goods`（机读，`/users/capabilities`）**

```jsonc
{ "source": "ark",                 // 固定：千帆商家后台
  "available": true,               // 已绑定即可用
  "reason": "",                    // 未绑定时给出原因 + 可执行动作（绑定/同步）
  "shop_name": "观隅好物的店", "shop_total": 1968, "synced_notes": 150,
  "synced_at": "2026-09-19 12:14" }
```

**② `NoteGoods`（每条笔记，`/users/notes` 的 `items[].goods`）**

| 字段 | 来源 | 说明 |
|---|---|---|
| `goods_id` | `item_id` | 商品 ID |
| `title` | `item_title` | 商品标题 |
| `image` | `item_image` | 商品主图 |
| `variant` | `variant_desc` | 规格（如「喵宠开心/40*60CM」） |
| `url` | 拼接 | `https://www.xiaohongshu.com/goods-detail/{item_id}`（实测 200） |
| `shop_name` | 绑定行 | 店铺名 |
| `price` | 商品接口 `min_price`/`max_price` | **v1.10 起不再恒空**：千帆商品笔记列表仍不返回价格，改由**商品列表接口按 ID 批量补一次**（§24.4.1）。同价给 `54.40`、区间给 `54.40~144.00`（分 → 元只在 `_price_text` 换算一次）；**查不到 / 失败就留空**，不填 0、不编造 |

**③ `items[].shop`（千帆为每条笔记给出的店铺侧指标）** —— 「创作者账户数据全部接入千帆」的落地：

`note_id / title / cover / note_flag / browse_num / browse_num_30d / like_num / collect_num /
comment_num / share_num / note_pay_gmv / note_pay_order_cnt / note_status / note_type /
publish_time / xsec_token`，**读不到的键是 `null` 而不是 0**（§18.2 的同一口径）。

**④ `goods_source`（页级元信息，`/users/notes` 响应）**

```
{ source: "ark", bound: bool, shop_name, shop_total, synced_notes, synced_at, status, status_message }
```

用途：把「同步了 150 / 店铺共 1968」讲清楚 —— 否则「这条没商品」会被读成
「笔记没挂商品」，而实际是**还没同步到**。**v1.10**：补价成功时多一个
`price_source: "ark:items"`（价格来自商品接口而非映射）。
**v1.12**：按需补齐发生时多一个 `on_demand: {requested, stored, error}`
（本页请求了几条 / 补到几条 / 失败原因），页面据此区分「本页确实没商品」与「这次没补上」。

> **⚠️ 两个同形来源的取舍（v1.14 / DEF-040）**：`capabilities.goods` 与这里的 `goods_source`
> **同源同形**（后端都出自 `_shop_goods_source()`），但**刷新时机不同** ——
> capabilities 只在**账号切换**与**绑/同步/解绑/巡检**之后刷新，而按需补齐发生在**每次加载笔记**时。
> 所以前端显示覆盖率**必须优先用 `goods_source`**（`goodsSource ?? capabilities.goods`），
> 否则浏览时补齐的商品永远不计入数字，只有点「同步商品」才跳到位（这正是 DEF-040）。

#### 24.4.1 价格怎么补（v1.10）——一次批量查询，失败静默

千帆商品笔记列表**没有**价格字段（§19.3 实测），但商品列表接口的 `whole_keywords`
支持**逗号分隔多个商品 ID** —— 于是：

| 项 | 做法 |
|---|---|
| 触发条件 | 本页**确有**带 `goods_id` 且 `price` 为空的商品（否则**一次请求都不发**） |
| 次数 | **每页 ≤ 1 次**（把该页所有待补 ID 拼成一个 `whole_keywords`） |
| 上限 | 去重后最多 `_GOODS_PRICE_BATCH_LIMIT = 50` 个 ID |
| 状态 | `status="all"`（不传 `card_type`）—— 已下架的商品也有价，也能显示 |
| 失败 | **静默**：价格留空，页面照常 200（商品本体来自本地映射，不受影响） |
| 缓存 | **不缓存**：价格随时会变，缓存 = 第二套真相源 |

**代价与取舍**：这让「浏览我的笔记」从「零千帆请求」变成「**最多 1 次**千帆请求」。
接受它的理由是收益明确（价格是商品信息里最有用的字段，原先恒空），
而代价有界（一页一次、只读、失败不影响页面）；真实耗时仍为秒级
（实测一页 10 条笔记合计 **1.48s**，含这次批量查价）。

**⑤ 展示规则（UI，D17 / 2026-09-19 定）**

| 项 | 规则 |
|---|---|
| 商品链接 | **文本展示 + 点击复制**，**不做跳转**：URL 以文本可见（`maxWidth` 省略显示，**复制的是完整值**），点文本本体即复制并给「商品链接已复制」；旁边保留一个复制图标按钮（两种习惯都覆盖）。理由：要的是**把链接拷去别处用**（填表、发给客服、贴进表格），不是在小红书里逛商品页 |
| 剪贴板实现 | 优先 `navigator.clipboard.writeText`；**非安全上下文**（用局域网 IP 打开而非 `localhost`）自动退回 `document.execCommand("copy")`；两条路都失败时给可读错误，**不静默** |
| 价格 | `price` 为空则**整行不渲染**（不留空位、不填 0） |
| 无商品 | `goods === null` 时整块不渲染；解释责任交给页级覆盖率元信息（§24.4 ④） |
| 页面级长说明 | **不再有**。账号能力边界改由「无网页会话」标签 + 置灰 Tab 的悬浮原因就近承担（需求 D11 修订） |

### 24.5 为什么千帆不需要签名（不新增签名维护面）

### 25.2 筛选参数（参数名逐个抓包实测，不是推测）

抓法：用 CDP 打开千帆「商品管理 → 售卖中」，**操作它的筛选控件**，抓它自己发出的请求 body。

| 条件 | 参数 | 实测校验（与页面同值） |
|---|---|---|
| 关键词（名称 / 商品 ID / 商品货号 / 商家编码，多条逗号分隔） | `search_filter.whole_keywords` | 「地垫」→ **92** |
| 状态 | `search_filter.card_type` | 售卖中 **2**（1994）/ 已下架 **3**（0）/ 已冻结 **4** / 整改 **10** / 审核中 **5** / 审核驳回 **6** / 审核通过 **7**（89）/ 全部 = **不传** |
| 价格区间 | `price_from` / `price_to`，**单位＝分** | 100~200 元 → `10000`/`20000`，**654** |
| 库存区间 | `stock_from` / `stock_to` | `stock_from: 10` |
| 销量区间 | `sales_from` / `sales_to` | `sales_from: 11` |
| 排序 | `search_order.sort_field` + `order` | `create_time` / `on_shelf_time` / `off_shelf_time` / `last_audit_time` / `item_sale_qty_30` |
| 分页 | `page_no` / `page_size` | 第 2 页 × 5 条 |
| **创建时间区间** | `create_time_from` / `create_time_to`，**单位＝Unix 秒** | 2020 空窗 → 0；2026-07-01~07-16 → **1176**；单边传（只给 from/to）也生效 |

**三个坑（都已在 SDK 里用类型/命名挡住）**

1. **价格单位是分**：页面填「100」发出去的是 `price_from: 10000`。SDK 只接受 `*_fen`，
   路由层的元→分换算**只发生在 `_price_fen()` 一处** —— 两头各乘一次 100 是这类集成最典型的静默错值。
2. **`card_type` 缺失 ≠ 全部**：页面点「全部」时干脆不发请求。所以「全部」= 不传该键，
   而不是传 0/1（传错会得到空列表而不是全量）。
3. **创建时间单位是秒**：同一组键传**毫秒**会被下游 ES 拒掉（HTTP 500
   `search_phase_execution_exception`），传**秒**才 200。判定方法是**用必然为 0 的时间窗当判别器**
   （键无效 → 平台忽略 → total 不变；键有效 → total 变 0）—— 已记下这个手法（见下）。

> **v1.9 起补记**：本节的参数表是**v1.8 建成、v1.9 补齐时间区间后**的最终形态；
> 时间区间的判定过程见 §25.2.1（含「日期选择器点不开 → 改用判别式实验」的取舍）。

**已探明（v1.9 补齐）**：页面上的「开始时间 / 截止时间」是**自研日期选择器**
（`d-daterangepicker`，标签其实是「创建时间」），它的面板走独立 portal、合成事件点不开；
最终用**判别式实验**拿到真参数名：`search_filter.create_time_from` / `create_time_to`（**Unix 秒**）——
毫秒会让下游 ES 直接 500，秒则 200 且 `total` 随窗口变化。因此 v1.9 **已实现**时间区间筛选。

#### 25.2.1 判定「时间筛选参数名」的手法（可复用）

页面点不开的选择器，不必硬啃 DOM：

1. **列候选键名**（按平台命名习惯：`create_time_from/to`、`start_time/end_time`、`*_range{start,end}`…）；
2. 用一个**必然为 0 的窗口**（如 2020 年）当判别器，逐个提交；
3. **键有效** → `total` 变 0；**键无效** → 平台忽略 → `total` 与基线相同（这两个结果不会混淆）；
4. 单位再用「毫秒 vs 秒」各试一次：**报 500 的那个往往就是键存在、单位错的信号**
   （本次毫秒 → `search_phase_execution_exception`，秒 → 200）；
5. 最后用**必然命中的窗口**（2026-07-01~07-16 → 1176）确认语义与边界，
   再把这个数值写进用例断言，让回归替你把参数钉住。

### 25.4 归一化口径（白名单构造）

### 25.6 诚实边界

| 边界 | 原因 |
|---|---|
| 不显示「价格」以外的营销口径（如佣金、活动价） | 平台未在该接口返回，**不推算** |
| 商品数据**不落库** | 实时查询即真相；若要分析/导出再单独立卡（含快照时间） —— ***被 §30 取代***（v1.32）：列表走本地台账，**时效由「同步于 X」明示**，快照时间就是 `synced_at` |
| 不碰写接口 | C6；商品上下架只能去千帆后台操作 |
| 挂链笔记反查**只覆盖已同步的那部分** | 反查走本地映射（零平台请求），所以抽屉必须报 `M/N` 覆盖率并提示可同步；**不假装完整** |
| 反查**不做实时平台查询** | 千帆商品笔记列表没有按商品查询的口子（§24.2），硬做也只能全量翻页 → 风控面 |
| **v1.32 新增**：本地区间筛选「空值行不命中」 | 价格 / 库存 / 销量 / 创建时间取不到的行无法确认是否在区间内 ⇒ 不代入（无法确认即不代入，硬约束⑤）；与平台实时筛选的可能差异不假装一致（设计 13 §30.6） |
| **v1.32 新增**：规格详情可能没补 | `detail_json` 空 = 待补队列中（多轮收敛）；弹窗明示，不渲染 0 行 |
