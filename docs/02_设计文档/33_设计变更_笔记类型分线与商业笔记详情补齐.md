# 设计变更 · 笔记类型分线与商业笔记详情补齐

> **状态**：🟢 **已实施**（2026-10-12）
> **性质**：**数据链路级变更**（新增类型判据 + 拆掉 www 硬门禁 + 按类型分限流线），
> **不改数据模型**（`notes.note_category` 列早已存在）。
> **上游**：本文件由 2026-10-12 用户口径发起 ——
> *「把商业笔记和普通笔记，新增一个类型字段进行区分，商业笔记进入笔记列表后走千帆的
> 笔记编辑接口同步笔记信息……同步按钮根据笔记类型，走不同的同步逻辑线」*
> **本文档是代码变更的发起件**（AGENTS.md §3.1「文档先行」）。

---

## 1. 起因与问题定位

### 1.1 用户报障

> 列表源不带正文。点上方「同步」触发同步任务，会在同一次任务里补齐正文与挂载商品。
> 内容库中同步的商业笔记均没有正文和只有一张媒体资源，点击同步按钮异常提示同步失败
> 1 篇（《男士凉鞋…》：**该账号没有可用的网页版（www）会话，无法读取笔记详情**）。

### 1.2 根因（实测定位）

`hydrate_note_detail()` 有一道**账号级硬门禁**：

```python
if not _has_web_session(account_cookies):
    result.update(status="no_session",
                  reason="该账号没有可用的网页版（www）会话，无法读取笔记详情")
    return result
```

而**详情取数其实只认笔记级 `xsec_token`**（`get_note_info_html` 走 explore SSR，
一次 GET 拿全、**不挑令牌来源**）。令牌从哪来？——**千帆列表返回里就带**。

所以这道门禁判错了维度：它按**账号**拦，而取数前提是**笔记**。

## 2. 实测证据（2026-10-12 抓包，主账号 id=8「观隅好物的店」）

### 2.1 `xsec_token` 与笔记类型都在千帆列表返回里

`POST 千帆 goods-note 列表`（项目现用 `get_goods_note_page`）的 `data.note_infos[]`：

```json
{
  "note_id": "6ac65843000000001203dda8",
  "xsec_token": "AB1vlsBq7Jp6HZVWxf3N_qSB3vo2umUWmLj50cqvhFMEI=",
  "note_flag": "goods_note",
  "note_type": 1,
  "note_title": "这双亚麻拖鞋，让家有了呼吸感🌿",
  "note_image": "http://ci.xiaohongshu.com/spectrum/...",
  "item_id": "6a3b3e4116b37a00151d4980",
  "item_title": "...", "item_image": "...", "goods_infos": [...]
}
```

* **`xsec_token`** —— 正是「笔记管理列表点图片」跳转 URL 里那个
  （`…/explore/<id>?xsec_token=…&xsec_source=pc_trdark`）；
* **`note_flag: "goods_note"`** —— **平台原生的笔记类型判据**（不必自造）。

### 2.2 探索过的三条「拿详情」路径（全部记录，含被否决的）

| 路径 | 正文 | 图集 | 结论 |
|---|---|---|---|
| 千帆**编辑页** XHR（`app-note/editor`） | ❌ | ❌ | 只返回商品挂链侧（`trade_note/permission`、`sku_infos`、`itemopportunity`） |
| 千帆 `butterfly/data`（已接） | ❌ | ❌（仅 1 张封面） | 指标 / 挂载商品 / explore 链接齐全，**无正文无图集** |
| explore 页 **XHR** | ❌ | ❌ | 156 条请求里 **0 条**含详情（只有 homefeed / comment / config） |
| explore 页 **SSR HTML** | ✅ | ✅ | 但**不是接口** —— 且**用户明确否决**（页面结构易变） |

**结论**：平台侧**没有**任何返回「笔记正文 + 图集」的 JSON 接口；正文只存在于
笔记渲染态（explore SSR / 发布器上下文）。

**用户口径（2026-10-12）**：

> 笔记详情走接口不要走页面 dom 中获取，页面容易变化快

⇒ **DOM / SSR 解析一律不采用**，即使它当前能跑通（实测同一页面两次抓取结构已不同：
第一次 `#detail-desc` 读到 247 字，第二次 `editableCount=41`、Vue 实例扫描为 0）。

### 2.3 但详情接口**是通的** —— 只要令牌在手

旧门禁的行为（只登千帆的账号）：

```
只登千帆 ──▶ hydrate_note_detail ──▶ _has_web_session(空) = False ──▶ no_session
                                                                      ↑ 正文永远补不到
```

而 `_note_detail_url(note)` 明明**已经拼出了带令牌的完整地址**（令牌就在
`raw_json` 里）—— 门禁挡在它前面。

## 3. 变更设计

### 3.1 判据上移一层：按**笔记**而不是按**账号**

```
旧：账号有没有 www 会话          → 没有就拦（错了维度）
新：这条笔记有没有 xsec_token     → 有就打详情；没有且没 www 会话才拦
```

| 情况 | 状态 |
|---|---|
| 有令牌 | ✅ 打详情（**www 会话不是必需**） |
| 无令牌 + 有 www 会话 | ✅ 打详情（既有路径不变） |
| 无令牌 + 无 www 会话 | ❌ `no_session` / `no_token`（一条请求都不发） |

### 3.2 笔记类型判据：平台原生 `note_flag`

```
note_flag == "goods_note"  →  note_category = "goods"
其它 / 缺省                →  note_category = ""（缺值不造，硬约束⑤）
```

落库在 `_merge_ark_notes` 的**新建行与命中行两条分支**都写
（命中行按当前数据源刷新，与 `note_data_service._upsert_note` 同口径）。

⚠️ `note_category` 列**早已存在**（迁移 `f4a5b6c7d8e9`）—— **无需新迁移**。

### 3.3 限流按类型分线

```
note_category == "goods"  →  {account_id}:ark   （千帆额度）
其它                      →  {account_id}:www   （行为不变）
```

两个平台的风控额度**各自独立**；共用一个键会让先跑的线把额度耗光、后跑的线干等。

### 3.4 详情补齐借谁的凭证：按**源**判

`_note_sources` 的 ark 条目带 `detail_with_own_token: True` ⇒ `_sync_source` 在
`www_adapter is None` 时**自己造** PC 适配器（用源自己的 cookie）。

## 6. 已知边界（如实记录，不假装已解决）

* **平台没有「正文 + 图集」的 JSON 接口** —— 这是平台的形态，不是实现遗漏。
  本文档 §2.2 四条路径已穷举。
* 正文与图集仍**经由 explore 详情取数**（`get_note_info_html`，SSR），这条路
  在 §3.1 的新判据下**只依赖笔记令牌**、不再依赖账号会话。
* `note_category` 与 `note_type` **正交**：
  * `note_type`（`synced` / `local` / `local_generated`）答「**谁搬来的**」；
  * `note_category`（`goods` / `normal` / 空）答「**属于平台的哪类笔记**」。
  两列不是一列，改一个不许顺手改另一个。
