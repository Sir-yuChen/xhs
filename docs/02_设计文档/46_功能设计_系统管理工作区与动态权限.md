# 总① · 需求总体设计

## 1.1 目标与边界

**目标**：把 XHS 从「注册即全权、零权限码、菜单硬编码」改成「**工作区 + 菜单 + 按钮三级动态权限**」，
并补成一个与 dataPanel 同骨架的系统管理工作区（用户 / 角色 / 菜单 / 字典 / 设置 / 日志）。

**给谁用**：`admin`（部署者，改全局、管用户）与 `user`（日常运营，只管自己的数据面）。

**明确不做**（写下来防止后续被顺手加回去）：
1. 不引入 MobX / `@ant-design/pro-components` / Redis / Wails（技术栈零变更）。
2. 不做多页签（Tab）工作区 —— 与现有路由模型不兼容，收益低于风险。
3. 不做 `dict_items.belong` 多平台维度（XHS 只有小红书一条平台线，多一列就是多一份没人用的语义）。
4. 不给**查询**接口挂独立权限码（查询可公用；只有变更操作一按钮一码）。
5. 不做「角色分级（超管/管理员/运营）」—— 只保留 `admin` / `user` 两个内置角色（用户口径「默认一个 admin 超级管理员」）。

## 1.2 总体流程（端到端一张图）

```
登录（邮箱 + 密码）
  → POST /api/auth/login
      ├ 账号不存在 / 密码错 ──▶ 401（失败计数 +1，达阈值 429）
      ├ status=pending  ──▶ 403 USER_PENDING（"账号待管理员审核"）
      ├ status=disabled ──▶ 403 USER_DISABLED
      └ 通过 ──▶ 签发 access/refresh（payload 带 token_version）
  → GET /api/auth/me  ← 【唯一权限真相源】
      返回 { user{id,username,email,real_name,role,status,last_login_at},
             is_admin, permissions[], workspaces[], menus{} }
  → 前端 WorkspaceGate：按 menus 决定「平台选择页显示哪些工作区卡片」
  → 进入工作区：侧栏菜单 = menus[workspace]（后端下发，前端零硬编码）
  → 页面内按钮：hasPermission(code) 控制显隐；后端 require_perm(code) 是权威拦截
  → 改密码 / 被强制下线：token_version +1 ⇒ 所有旧 access/refresh 立即 401
```

## 1.3 关键设计决策

| # | 决策 | 备选 | 为什么选它 | 代价 |
|---|---|---|---|---|
| D1 | **权限码 = `menus.perms` 一列，菜单/按钮同表**（`M` 目录 / `C` 菜单 / `F` 按钮） | A 独立权限点表 / B 代码常量 | dataPanel 实证：一列到底，前端 `hasPermission` ↔ 后端 `require_perm` ↔ SQL `t_menu.perms` 三处同源；独立权限点表会造出第二种真相 | 按钮行必须挂到 C 行下（`parent_id`），菜单页要能编辑 F 行 |
| D2 | **令牌不装权限码**，权限每次从 `/auth/me` 取 | A（dataPanel）令牌内嵌 perms | 权限现取现生效、可撤销；XHS 令牌是自签 HMAC，加长 payload 只会让 `decode_token` 更慢且仍需服务端校验 | 每个页面要多一次 `/auth/me`（已有 bootstrap 那一次，复用即可） |
| D3 | **角色只有两个内置行**（`admin` / `user`），`is_system=1` 禁删禁停 | 五个种子角色 | 用户口径「默认一个 admin」；多角色会让「谁能改全局」再次模糊 | 未来要加「运营/只读」需新增角色行（成本低） |
| D4 | **工作区 = `menus.workspace` 列上的 `C` 行**（根菜单即工作区） | A 独立 workspaces 表 | 少一张表；工作区本质就是「菜单树的根」，多一张表就要维护两套父子关系 | 校验：`parent_id=0` 的 C 行才算工作区（守卫钉死） |
| D5 | **路由仍在前端登记**，但**必须与菜单行 path 一一对应**；菜单决定「可见/可进」，路由决定「怎么渲染」 | 后端下发 `component` 字符串动态 import | XHS 用 Vite 静态分析，动态 import 字符串在打包后**会失效**（dataPanel 靠 `componentMap` 白名单绕，但那样新增页面仍要改代码）。保持静态路由 + 守卫比对，代价最低 | 新增页面 = 改 `router.tsx` + 插菜单行（守卫保证不漏） |
| D6 | **`users.role` 就是唯一角色**（值域指向 `roles.code`），**不建 `user_roles` 中间表** | A dataPanel 的多对多 `t_user_role` / B 直接删 `users.role` | 用户口径「默认一个 admin」+ 只有两个内置角色 ⇒ 一人一角色够用；删列则要动 49 张表的鉴权链。值域由应用层校验 + 守卫断言 | 将来要「运营+财务」叠加时才加 `user_roles`（纯新增，不动现有列） |
| D7 | **注册 = 邮箱验证码 + `pending` 待审**，与 dataPanel 一致 | 直接注册即用 | 用户明确「与 dataPanel 一致」；且 XHS 现在的「注册即全权」是本项目最大的越权面 | 管理员要多一步「审核通过」 |
| D8 | **设置页从 `/settings` 迁入系统管理工作区**，路由保留重定向 | 两处并存 | 用户口径「设置用户管理去」；两处 = 两份真相 | 旧深链重定向（不 404） |

### 1.5.3 与本轮权限设计的耦合点（**必须现在定，否则二期重做**）

| 判据 | 决定 |
|---|---|
| 权限码格式 | `<平台或域>:<资源>:<动作>`。平台类 = `xhs:` / `douyin:` / `xianyu:`；非平台 = `ai:` / `system:` |
| 角色授权粒度 | **按菜单行授权**，即按平台授权（给某人「抖音-笔记发布」而不给「小红书-笔记发布」是天然支持的） |

# 分 · 后端设计

## 3.1 端点（**+34 端点 / +15 path**：350/303 → 384/318）

> 分组前缀统一 `/api/system/**`；`/api/auth/**` 只做登录域增量。
> 权限码写法 `<域>:<动作camelCase>`；**查询可公用，变更一按钮一码**（dataPanel 硬口径）。

### 3.1.1 登录 / 注册 / 个人资料（`backend/app/api/auth.py`，+6 端点 / +2 path）

| # | 方法 · 路径 | 语义 | 权限码 | 请求要点 | 响应要点 |
|---|---|---|---|---|---|
| A1 | `POST /api/auth/register` | 邮箱验证码注册，落 `status=pending` | 公开（受 `register.enabled` 开关） | `{username, password, email, verify_code}`；`extra=forbid` | `{status:"pending", message:"注册申请已提交，请等待管理员审核"}` |
| A2 | `POST /api/auth/send-register-code` | 发注册验证码（**6 位数字，5 分钟，同邮箱 60s 限频**） | 公开 | `{email}`；该邮箱已注册 ⇒ 409 | `{sent:true, expires_in:300}` |
| A3 | `POST /api/auth/send-profile-code` | 改敏感资料前发验证码到**当前用户邮箱** | 登录 | — | 同上 |
| A4 | `POST /api/auth/verify-profile-code` | 校验验证码，返回一次性 `ticket`（5 分钟，只可改一次） | 登录 | `{code}` | `{ticket}` |
| A5 | `PUT /api/auth/me` | 改个人资料（`real_name` / `phone` / `avatar`；**改 `email` 必须带 `ticket`**） | 登录 | `{real_name?, phone?, avatar?, email?, ticket?}`（`extra=forbid`） | 更新后的 `me` 形状 |
| A6 | `POST /api/auth/change-password` | 旧密码换新密码 ⇒ `token_version+1` ⇒ 全部旧令牌失效 | 登录 | `{old_password, new_password}` | `{ok:true, reauth_required:true}` |
| G1 | `GET /api/auth/me`（**改造**，非新增） | 唯一权限真相源 | 登录 | — | 见 §3.2.2 |

> ⚠️ A2 与 A3 的验证码走**同一实现**（`verify_code_service`），只有「目标邮箱来源」不同 —— 一处实现两份入口（DEF-044 纪律）。

## 3.2 请求 / 响应契约

### 3.2.1 通用约定

```python
class _Base(BaseModel):
    model_config = ConfigDict(extra="forbid")   # ⚠️ 白名单：加字段必须同步改
```

| 约定 | 规则 |
|---|---|
| 分页 | 请求 `page`(≥1) / `page_size`(1..100，默认 20)；响应 `{items, total, page, page_size}` |
| 时间 | 一律 `isoformat()`（上海时区，与全项目一致） |
| 错误码 | `detail` **只放用户可读中文**；机器码放 `headers["X-Error-Code"]`（与现有 400 结构化口径一致，不破坏前端 `detailMessage` 逻辑） |
| 缺值 | 解析不到就 `null` / `""`，**不造假**（硬约束⑤） |

### 3.2.2 `GET /api/auth/me`（唯一权限真相源）

```python
{
  "user": {
    "id": 1, "username": "admin", "email": "a@b.c",
    "real_name": "",                    # 空 ⇒ 前端回落 username（不造假）
    "role": "admin",                    # 冗余快照，权威是 roles
    "roles": ["admin"],
    "status": "normal",
    "last_login_at": "2026-10-23T22:00:00+08:00",   # 无则 null
    "last_login_ip": "127.0.0.1"
  },
  "is_admin": true,
  "permissions": ["system:user:view", "..."],       # 去重排序的 perm 串
  "workspaces": ["xhs", "ai", "system"],            # 有任意可见菜单的工作区，按 sort 排
  "menus": {"xhs": [MenuNode], "ai": [...], "system": [...]},
  "register_enabled": false                          # 登录页据此决定是否显示「注册」
}

# MenuNode（只含 M / C，is_visible=1，status=normal）
{"id": 12, "parent_id": 3, "name": "商品列表", "menu_type": "C",
 "path": "/platforms/xhs/shop-items", "icon": "shopping", "sort_order": 5,
 "perms": "shop:item:view", "children": []}
```

- `permissions` **只来自** `menus.perms`（`status=normal` 且该用户角色已授权）。
- **admin 角色的权限 = 全量 perms**（不做逐条授权；`role_menus` 里 admin 行仍写全量，便于菜单管理页展示「已授权」）。
- `workspaces` 的顺序由 `menus.sort_order` 决定，**不由前端写死**。

## 3.3 底层数据结构（表 / 模型）

### 3.3.1 新表 5 张

```sql
-- ① menus：菜单与权限码同表（M 目录 / C 菜单 / F 按钮）
CREATE TABLE menus (
  id            INTEGER PRIMARY KEY,
  parent_id     INTEGER NOT NULL DEFAULT 0,      -- 0 = 根（工作区 / 一级菜单）
  name          TEXT    NOT NULL,
  menu_type     TEXT    NOT NULL DEFAULT 'C',    -- M | C | F
  path          TEXT    NOT NULL DEFAULT '',     -- C 行必填：前端路由路径
  component     TEXT    NOT NULL DEFAULT '',     -- 预留（不参与动态 import，见 D5）
  perms         TEXT    NOT NULL DEFAULT '',     -- 权限码 <域>:<动作camelCase>
  icon          TEXT    NOT NULL DEFAULT '',
  workspace     TEXT    NOT NULL DEFAULT '',     -- 仅根 C 行有值：xhs | ai | system
  sort_order    INTEGER NOT NULL DEFAULT 0,
  is_visible    INTEGER NOT NULL DEFAULT 1,
  status        TEXT    NOT NULL DEFAULT 'normal',
  created_at    TEXT    NOT NULL,
  updated_at    TEXT    NOT NULL
);
CREATE UNIQUE INDEX uq_menus_perms ON menus(perms) WHERE perms <> '';
CREATE INDEX ix_menus_parent ON menus(parent_id);

-- ② roles：两个内置行（is_system=1 禁删禁停禁改 code）
CREATE TABLE roles (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  code        TEXT NOT NULL UNIQUE,              -- admin | user | 自定义
  description TEXT NOT NULL DEFAULT '',
  is_system   INTEGER NOT NULL DEFAULT 0,
  status      TEXT NOT NULL DEFAULT 'normal',
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

-- ③ role_menus：角色 ↔ 菜单授权（多对多）
CREATE TABLE role_menus (
  id      INTEGER PRIMARY KEY,
  role_id INTEGER NOT NULL,
  menu_id INTEGER NOT NULL
);
CREATE UNIQUE INDEX uq_role_menus ON role_menus(role_id, menu_id);

-- ④ dict_types / ⑤ dict_items
CREATE TABLE dict_types (
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,
  code       TEXT NOT NULL UNIQUE,               -- 如 sys_user_status
  remark     TEXT NOT NULL DEFAULT '',
  status     TEXT NOT NULL DEFAULT 'normal',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE TABLE dict_items (
  id         INTEGER PRIMARY KEY,
  type_id    INTEGER NOT NULL,
  type_code  TEXT NOT NULL,                      -- 冗余（免 join；写入时由 type_id 推导）
  label      TEXT NOT NULL,
  value      TEXT NOT NULL,
  list_class TEXT NOT NULL DEFAULT 'default',    -- antd Tag 颜色：success|warning|danger|info|default
  sort_order INTEGER NOT NULL DEFAULT 0,
  status     TEXT NOT NULL DEFAULT 'normal',
  remark     TEXT NOT NULL DEFAULT ''
);
CREATE UNIQUE INDEX uq_dict_items ON dict_items(type_id, value);
CREATE INDEX ix_dict_items_code ON dict_items(type_code);
```

## 3.4 实现逻辑（判据式）

| # | 规则 | 判据式表述 | 落点 |
|---|---|---|---|
| P0 | **按钮级粒度 = 一个变更按钮一个码** | 判据：**这个按钮点了会改数据吗**？会 ⇒ 独立码；只是读/查/筛/翻页 ⇒ 用所在 C 行的查看码。禁用例外：同一动作的「批量」与「行内」**共用同一码**（后端接口唯一，dataPanel 硬口径） | 全仓 |
| P1 | 权限判定唯一入口 | 后端**只允许** `require_perm("code")` / `is_admin_of(user)` 两种判定；禁止在路由里手写 `user.role == "admin"` | `core/perms.py` |
| P2 | 权限聚合 | `permissions(u) = {m.perms ∀ m ∈ menus ⋈ role_menus ⋈ u 的角色, m.status='normal', m.perms≠''}` | `services/permission_service.load_effective_perms` |
| P3 | admin 特权 | `roles.code='admin'` ⇒ 权限集合 = 全量 perms（**由代码派生，不靠 role_menus 行齐全**） | 同上 |
| P4 | 菜单树裁剪 | 返回给用户的树 = 「其 `permissions` 能覆盖到的 C 行」+「C 行的祖先 M/C 行」；`F` 行不下发（前端只查权限码） | `permission_service.build_user_menus` |
| P5 | 写操作全挂码 | **每个非 GET 路由必须有权限码**：启动期扫 `app.routes`，缺码即 `RuntimeError`（fail-fast，不允许静默放行） | `core/perms.py::assert_all_write_routes_guarded` |
| P5b | **前端按钮必有码** | 每个改数据的交互点（`<Button onClick>` / `Switch onChange` / 可编辑单元格）**必须**被 `hasPermission("...")` 包裹或被 `v-if` 式条件渲染；启动前守卫扫源码：**页面里出现 `await http.post/put/delete` 而同文件无该码的 `hasPermission` ⇒ 红** | `tests/backend/test_frontend_button_perms.py` |
| P6 | 最后一个 admin 保护 | 任何会让 `count(active admin) == 0` 的操作（删用户 / 改角色 / 停用 / 删除 admin 角色）⇒ 409 `LAST_ADMIN_PROTECTED` | `system_users_service` / `system_roles_service` |
| P7 | 自己不能删自己 / 不能改自己角色 | `target.id == current.id && (delete or role change)` ⇒ 409 `CANNOT_MODIFY_SELF` | 同上 |
| P8 | 菜单删除有依赖即拒 | `has_children(menu_id) or referenced_by_role(menu_id)` ⇒ 409，**不级联**（dataPanel 是级联删，本项目选更安全的语义） | `system_menus_service` |
| P9 | `perms` 唯一 | 新建/编辑时 `perms≠''` 必须全局唯一（DB 唯一索引 + 应用层友好报错） | 同上 |
| P10 | `F` 行必须挂 `C` 行 | `menu_type='F' and parent.menu_type != 'C'` ⇒ 422 | 同上 |
| P11 | 注册开关 | `register.enabled=false` ⇒ `POST /auth/register` 与 `send-register-code` 均 403 `REGISTER_DISABLED` | `api/auth.py` |
| P12 | 注册落 pending | 新账号 `status=pending`，登录时 403 `USER_PENDING`（**不是 401** —— 让前端能区分「密码错」与「没审核」） | `api/auth.py` |
| P13 | 验证码 | 6 位数字、TTL 5 分钟、**同邮箱 60 秒内不可重发**、校验成功即销毁（防重放） | `services/verify_code_service` |
| P14 | 改邮箱需 ticket | 改 `email` 必带 5 分钟有效 `ticket`（由 `verify-profile-code` 签发，用一次即失效） | `api/auth.py` |
| P15 | 改密码即踢 | `change-password` / `reset-password` / `force-logout` 三者都 `token_version += 1` | `api/auth.py` / `system_users` |
| P16 | 「一键应用到所有用户」admin 独占 | `POST /api/settings/apply-to-all`：**非 admin ⇒ 403 `SETTING_APPLY_ALL_FORBIDDEN`** | `api/settings.py` |
| P17 | 字典读点单一 | 前端所有枚举下拉**只走** `useDict(code)` → `GET /system/dict/items?type_code=`；**禁止**再在 `.ts` 里写死枚举数组（守卫扫源码） | `hooks/use-dict.ts` |
| P18 | 内置字典类型禁删 | `code` 在 `PROTECTED_DICT_CODES`（§3.4.8）里的类型禁删；删 item 允许（用户可能想少几个选项） | `system_dict_service` |
| P19 | 审计不可删 | `/system/logs/audit` 只读；**不提供任何删除端点** | — |
| P20 | 前端菜单零硬编码 | `workspace-shell` 的 `mainItems` 一律来自 `/auth/me`；`app-shell.tsx` 的常量降级为「加载失败兜底」，且 `DEV` 断言两者 key 集合相等 | `lib/menu.ts` |

## 3.5 状态机

### 3.5.1 用户状态

| 取值 | 进入条件 | 能否登录 | 终态 |
|---|---|---|---|
| `pending` | 注册成功 | ❌ 403 `USER_PENDING` | 否 |
| `normal` | 管理员建号 / 审核通过 / 被解禁 | ✅ | 否 |
| `disabled` | 管理员停用 | ❌ 403 `USER_DISABLED` | 否（可再解禁） |

迁移：`pending → normal`（U8 审核）/ `pending → disabled`（拒绝）；`normal ⇄ disabled`。
**不存在的取值**：`locked`（dataPanel 有，XHS 不做 —— 登录失败限流用 429 表达，不落库）。

### 3.5.2 菜单 / 角色

`menus.status`: `normal ⇄ disabled`（disabled 的 C 行**不下发**给任何用户，含 admin）。`roles.status`: 同上，但 `is_system=1` 恒 `normal`。

## 3.6 不变量（违反 = 当场报错）

| # | 不变量 | 违反时 |
|---|---|---|
| I1 | 每个写路由都有权限码 | 启动即 `RuntimeError`（P5） |
| I2 | `perms` 非空即全局唯一 | DB 唯一索引 + 409 |
| I3 | 系统内至少一个 `normal` 的 admin | 409 `LAST_ADMIN_PROTECTED`（P6） |
| I4 | admin 角色不可删、不可停、授权不可改 | 409 `ROLE_SYSTEM_PROTECTED` |
| I5 | 非 admin 的权限集合 ⊆ 其角色授权并集 | 单测断言 P2 与 role_menus 一致 |
| I6 | `users.role` 快照 == 其唯一角色 code（多角色时取最强） | 守卫测试断言（D6 双写） |
| I7 | 缺值留空 / `null`，不造假 | 前端计数缺值渲染 `0` 并给原因行 |

### 2.2b.0 铁律：只读页同样要授权（用户 2026-10-23 口径）

**每一个页面（C 行）必须带一条查看码，纯只读页也不例外。**

| 判据 | 规则 |
|---|---|
| `GET` 类端点 | **一律**挂 `<域>:<资源>:view`，不许因为「不改数据」留空 |
| C 行 `perms` | 必填（此前设计允许「只读页可空」⇒ **该留空已被本口径取代**） |
| 侧栏 | 未授该 C 行 ⇒ 该页不出现（不是「灰掉」） |
| 直接敲 URL | 未授 ⇒ `/403`（前端 `RequirePerm`）+ 后端 403（`require_perm`） |
| F 行（按钮码） | 只读页**没有** F 行；靠 C 行的 view 码管「进不进得去」 |
| 码总量影响 | 业务域 **114 写码 + 22 页级 view 码 = 136**（见设计 49 附 A.2） |

**为什么不能「只读所以免授权」**：这会把「看得见的数据」变成默认公开——
`insights` / `datacenter` / 总览这些页含营收、曝光、粉丝等经营数据，
普通运营账号不该默认看到。只读的含义是「不产生变更」，不是「不设门槛」。

## 4.1 逐字段「谁传 → 谁读 → 什么形态」

| 字段 | 前端产出（准确形态） | 后端读点（准确形态） | 不一致会怎样 |
|---|---|---|---|
| `permissions` | `string[]`，来自 me | `core/perms.require_perm` 比较 `set(perms)` | 前端显示按钮、后端 403 ⇒ 用户点不动（可见但无效） |
| 菜单 `path` | `"/platforms/xhs/shop-items"`（**前导斜杠、无尾斜杠**） | `menus.path`（同形）+ 守卫与 `router.tsx` 比对 | 少斜杠 ⇒ 高亮不上 / 守卫红 |
| 菜单 `workspace` | 根 C 行有值，其余继承 | 服务层**递归填**后再返回 | 前端自己递归算错 ⇒ 页面出现在错误工作区 |
| `role` | `"admin"` / `"user"` | `roles.code`（小写） | 大小写不一致 ⇒ `is_admin` 判不出 |
| `status` | `"normal"`/`"pending"`/`"disabled"` | `users.status`（同值域） | — |
| `verify_code` | 6 位字符串（Input 不限位数，但提交前正则 `^\d{6}$`） | 服务端比较（`str`，不做 int 转换） | 前导 0 被吃掉 ⇒ 校验失败 |
| `ticket` | `verify-profile-code` 返回的串 | `update_me` 校验（5 分钟 + 一次性） | 忘传 ⇒ 改邮箱 400 |
| `apply_to_all` | `true` / 不传 | `POST /settings/apply-to-all` | 非 admin 传 ⇒ 403 |
| `perms` | `"shop:item:view"` | `menus.perms`（唯一索引） | 大小写/分隔符不一致 ⇒ 无权 |
| 字典 `value` | `string`（**永远字符串**，不做 int） | `dict_items.value` | 前端把 `1` 当数字 ⇒ `find` 匹配不到 |

## 4.2 端到端链路（三条主链路）

### 链路 A：注册 → 审核 → 首次登录

```
① 用户点「注册」 → 前端 POST /auth/send-register-code {email}
② 后端 verify_code_service.issue(email)（60s 限频）→ smtplib 发信
③ 前端 POST /auth/register {username,password,email,verify_code}
④ 后端：开关校验 → 验证码校验(销毁) → 唯一性(邮箱/用户名) → hash_password
        → 建 users 行 status='pending'、role='user' → 200 {status:'pending'}
⑤ 前端弹「注册申请已提交，请等待管理员审核」→ 回登录页
⑥ 管理员在 /system/users 看到 pending 行 → 点「通过审核」→ POST /users/{id}/approve
⑦ 用户登录 → 200（正常签发令牌）
```
失败面：② 未配 SMTP ⇒ 503 `MAIL_NOT_CONFIGURED`（**不假发送**）；④ 验证码错 ⇒ 400；⑦ 仍 pending ⇒ 403 `USER_PENDING`。

### 链路 B：权限生效（改授权 → 立即生效）

```
① admin 在 /system/roles 点「分配菜单」→ GET /system/roles/{id}/menus（回填）→ 勾选 → PUT
② 后端：事务覆盖 role_menus → 结束
③ 被影响的用户下一次任意请求：
     - 401？否（令牌有效）
     - 但其「权限集合」在每次请求时**不重算**（性能），
       ⇒ 因此后端在 role/menu 授权变更时，对该角色下用户 `token_version += 1`（强制刷新）
④ 前端收到 401 → 自动 refresh → refresh 也 401 ⇒ 清令牌跳登录（现状行为）
   ⚠️ 为体验，前端在 `me` 里带 `perm_ver`；401 时先比 `perm_ver`，一致才跳登录
```
> **设计选择**：与其每次请求查 3 张表算权限，不如**授权变更时踢一次**。判据：授权变更是低频操作（管理员手动），
> 请求鉴权是高频操作（每请求）—— 把成本放在低频侧。

### 链路 C：改密码 / 被强制下线

```
① 用户改密（或 admin 强制下线）→ 后端 token_version += 1
② 该用户所有 access/refresh 立即 401（`get_current_user` 比对 `ver`）
③ 前端拦截器：401 → refresh（也 401）→ 清令牌 + "登录已过期，请重新登录"
```

## 4.3 跨层时序与竞态

| # | 场景 | 正确行为 | 曾踩的坑 |
|---|---|---|---|
| R1 | 菜单保存后自己刷新 | 保存成功 ⇒ 前端主动重拉 `me` **一次** | 侧栏还是旧的 ⇒ 以为没保存 |
| R2 | 角色授权并发 | 后端全量覆盖（先删后插）在**一个事务**内；两个管理员同时改 ⇒ 后写覆盖（可接受，记录 `updated_at`） | 部分成功 ⇒ 授权半套 |
| R3 | 审核通过 + 用户正在登录 | 登录读到旧 status 401/403；用户重试即可（不引入乐观锁） | — |
| R4 | 删自己 / 删最后一个 admin | 前端按钮 `disabled` + `title` 原因；后端 409 兜底 | 只靠后端 ⇒ 用户体验差 |
| R5 | 改自己的角色 | 后端 409 `CANNOT_MODIFY_SELF`；前端直接禁用该行「编辑」 | 改完自己失去权限且无法恢复 |
| R6 | 首启（全新库） | 迁移/播种后**第一个注册的用户自动提级 admin**？→ **否**：全新库由迁移插一条 `admin` 种子用户（用户名 `admin`，密码随机 + 强制首登改密） | 无 admin ⇒ 永远没人能审核自己 |

> ⚠️ R6 是本设计**唯一需要你确认的取舍**（见 §5 Q1）：全新安装的 admin 账号从哪来。

## 4.4 失败路径的端到端表现

| 失败点 | 后端 | 前端 | 用户看到 |
|---|---|---|---|
| 无权限 | 403 + `X-Error-Code: PERMISSION_DENIED` | 不吞，气泡显示 code | 「没有该操作权限（system:user:delete）」 |
| 缺码自检失败 | 启动即崩 | — | 开发期立刻发现（**不允许上线后才发现某个写接口没挂码**） |
| 验证码 | 400 / 429 | 倒计时/按钮态 | 「验证码不正确或已过期」/「60 秒后重试」 |
| 邮件未配 | 503 | 气泡 | 「未配置邮件服务，请联系管理员」 |
| 最后一个 admin | 409 | 按钮禁用 + 气泡 | 「至少需要保留一个可用的管理员」 |
