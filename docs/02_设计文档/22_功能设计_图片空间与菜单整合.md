## §1 N1 · 图片空间（千帆只读代理）

### §1.1 真机实测结论（2026-10-06，账号「开心睡大觉的店」id=9）

页面 `https://ark.xiaohongshu.com/app-system/pictureSpace`，标题「图片空间」。实测数据：
**共 4910 条 / 50 页 / 已用 584.86M / 总 15G**。

**接口清单（全部 `ark.xiaohongshu.com`，`Referer` = `/app-system/pictureSpace`）**

| 端点 | 方法 | 签名 | 用途 | 实测响应 |
|---|---|---|---|---|
| `/api/edith/product/material_space/search_directory_manageable` | POST | **必需** | 列表（文件 + 文件夹，同一端点靠 `filter.basicTypes` 区分） | 未签名 `code=-1`；签名 `code=200` |
| `/api/edith/product/material_space/get_directory` | POST | 否 | 目录树（`withEntireTree`） | 200（未签名即可） |
| `/api/edith/product/material_space/get_seller_space_usage` | GET | 否 | 空间配额 | 200 |

**列表请求体（逐字来自真机抓包）**

```json
{
  "filter": { "keyword": "", "statuses": [1], "basicTypes": [1, 2], "fatherDirectoryId": "" },
  "order":  { "orderList": [{ "field": "name", "asc": true }] },
  "pageIndex": 1, "pageSize": 100,
  "option": { "withDetail": true }
}
```

- `basicTypes`：**1 = 文件夹，2 = 文件**（真机：`[1,2]` 全量、`[1]` 只文件夹）。
- `statuses`：`[1]` = 正常（回收站在页面里是**独立入口**，未在本次只读探测中触发；见 §1.5 缺口）。
- `fatherDirectoryId`：`""` = 全部；`"0"` = 根下；`-1` = 真机空结果（页面用于取文件夹树）。
- `pageSize`：真机 100（列表）/ 50（树探测）；`pageIndex` 从 1 起。

**条目字段（真机实样）**

```json
{
  "id": "bbf0fa75-4bae-4204-9a80-4efc07f9a10a",
  "sellerId": "6a33d34ece6d1200154ad7f5",
  "type": 2,                       // 1=文件夹 2=文件
  "name": "000709d6-...-9e6258",   // 文件 = 无扩展名的 uuid 基名
  "status": 1, "size": 73728,      // 字节
  "createTime": 1784708174179, "updateTime": 1784708174179,  // epoch ms
  "additionalData": {
    "extension": ".jpeg", "width": "800", "height": "800",
    "link": "https://qimg.xiaohongshu.com/material_space/<id>",  // 直链（无扩展名，可当 src）
    "path": "material_space/<id>",
    "productCount": "0"            // 引用商品数（0 ⇒ 「未引用」）
  }
}
```

**配额响应**：`{"totalSpace": 16106127360, "usedSpace": 613267456, "whiteSeller": false}`（`code:0`，注意**不是 200**）。

### §1.3 落地方案（后端只读代理）

**新增端点（3 条，全部只读，`GET`/`POST` 只做查询）**

| 端点 | 方法 | 说明 |
|---|---|---|
| `/api/xhs/qianfan/picture-space/items` | `POST` | 列表：body = `{keyword, basicTypes, fatherDirectoryId, orderField, orderAsc, page, page_size, statuses}` ⇒ 透传 `search_directory_manageable`（**带签名**） |
| `/api/xhs/qianfan/picture-space/tree` | `GET` | 目录树：透传 `get_directory`（`withEntireTree`） |
| `/api/xhs/qianfan/picture-space/usage` | `GET` | 配额：透传 `get_seller_space_usage` |

**账号维度**：`account_id` 必传（query / body），取该账号的 `ark` 通道令牌 — 与既有千帆链路**同一门禁**
（`ARK_SESSION_REQUIRED`，无令牌 400；见 `qianfan.py` 既有实现）。**不借会话**。

**SDK 层**（`apis/xhs_qianfan_apis.py` 新增三方法）：

- `search_material_space(body) -> (ok, msg, payload)` — **走 `_signed_post`**（真机证：不带签名 `code=-1`）。
- `get_material_directory(seller_id) -> (...)` — `_post` 即可。
- `get_material_space_usage() -> (...)` — `_get` 即可。

⚠️ **只读边界**：三个端点都是查询语义，不带任何写副作用；`_signed_post` 只是**签名机制**（写链路也在用），
用它**不等于**调写接口。硬约束②（只读）的判据是「有没有改变平台状态」，不是「带没带签名」。

**响应归一化**（后端做，前端不碰平台原字段）：

```json
{
  "total": 4910, "page": 1, "page_size": 100,
  "used_space": 613267456, "total_space": 16106127360,
  "items": [{
    "id": "...", "type": 2, "name": "...", "display_name": "0007...58.jpeg",
    "size": 73728, "width": 800, "height": 800,
    "create_time": 1784708174179, "link": "https://qimg...",
    "referenced": false, "product_count": 0
  }]
}
```

- `display_name` = `name + extension`（平台把扩展名拆到 `additionalData`，列表要显示全名 ⇒ 后端拼）。
- `referenced` = `int(productCount or 0) > 0`。

### §1.5 写操作与回收站（2026-10-06 用户追加口径「操作按钮功能全部要做」）

> ⚠️ **本节推翻初版「只读、不渲染写入口」的决策**（初版原句保留在本节末尾）。
> 用户明确要求：图片空间的操作按钮功能**全部**要实现 —— 上传 / 新建文件夹 /
> 批量移动到 / 批量下载 / 批量删除 / 行内（复制链接 · 移动到 · 下载 · 删除）/ 回收站。
>
> **只读边界的口径澄清**：硬约束②管的是「**探测 / 调研 / 取证**一律只读」，
> 而本轮是**用户在本系统内对自己的图片空间做的显式操作**（与商品写链路
> `batch_update_availability` / 发货同一性质）⇒ 走「用户显式点击 + 本店归属 + 两层确认」
> 的写链路，不违反边界。**不做**的是「未经用户点击的后台自动写」。

**写端点（真机抓包 + JS bundle 取证，2026-10-06）**

| 端点 | 签名 | 用途 | 请求体形状（逐字来自真机 JS bundle） |
|---|---|---|---|
| `batch_add_directory_manageable` | 必需 | 新建文件夹 | `{sellerId, directoryManageables:[{sellerId,type:1,name,size:0,additionalData:{level,productCount:"0",isLeaf:"true"}}], option:{async:false}}` |
| `batch_edit_directory_manageable` | 必需 | 移动 / 重命名 / **删除（进回收站）** / **还原** | `{sellerId, directoryManageables:[…], option:{async:false}}`（三种用法字段不同，见下方 status 语义） |
| `batch_delete_directory_manageable` | 必需 | **彻底删除**（不可还原） | `{sellerId, directoryManageableElements:[{id,type}], option:{async:true}}` ⚠️ 键名是 `directoryManageableElements`（**不是** `directoryManageables`） |
| `batch_download_files` | 必需 | 批量下载（打包任务） | `{sellerId, links:[{type:2,link,name,extension} \| {type:1,directoryId}], isAsync:true}`（键名是 `links`；缺 `isAsync` ⇒ `code=-1`） |
| `query_task_status` | 非必需 | 查下载 / 异步任务 | `{params:{taskId}}` → `data.task` |

⚠️ **`status` 字段语义（2026-10-07 真机 JS bundle `index.5dca98b8.js` 枚举取证）**：
`{USABLE:1, UPLOADING:2, UPLOAD_FAILED:3, RECYCLE_BIN:4}`。**移动与删除走同一个端点
`batch_edit`，但字段完全不同**：

| 动作 | 请求体 | 真机取证 |
|---|---|---|
| **移动** | `{…原条目…, fatherDirectoryId: <目标目录 id>}`（**不动 `status`**） | `332.d754c099.js` `case 3` |
| **删除** | `{…原条目…, status: 4}`（`4 = RECYCLE_BIN`，进回收站） | `332.d754c099.js` `case 14` |
| **还原** | `{…原条目…, status: 1}`（`1 = USABLE`，从回收站还原） | `417.d61d3cd8.js` |
| **彻底删除** | `{sellerId, directoryManageableElements:[{id,type}], option:{async}}` | `417.d61d3cd8.js` |

⚠️ **两个曾被误判的点（2026-10-07 纠正）**：
1. 初版把**移动**也写成 `status:4` ⇒ 那等于 `RECYCLE_BIN` ⇒ **把文件移进回收站**（数据丢失级 bug）。移动只改 `fatherDirectoryId`。
2. 初版用 `directoryManageables` 键发 `batch_delete_*` ⇒ 平台一律回「文件信息不能为空」，据此**误判**成「平台不接受该端点」。选对键 `directoryManageableElements` 后，它正是回收站的「彻底删除」。

**回收站**（真机路由 `/app-system/pictureSpace/recycle`）：`search_directory_manageable`
的 `filter` 换 `{statuses:[4], basicTypes:[2]}`、`order` 换 `updateTime` 倒序（逐字抓包）；
操作列变「恢复 / 彻底删除」（批量亦然）；页面提示「回收站仅为您保存 7 天内删除的图片，
超时系统将自动清除（回收站内文件不占存储空间）」。

**分页（真机口径，2026-10-07 用户「图片分页展示与千帆页面功能保持一致」）**：
每页下拉 **100 / 200 / 500 条/页**（真机实测），默认 100。⚠️ 初版写 20/50/100（错）。

**⚠️ 布局三条硬口径（2026-10-07 用户「图片列表超出页面部分 / 回收站未展示入口 /
操作列一行两个功能按钮 / 名称列固定280px」）**：

1. **表格 `scroll.x` 必须有 + 操作列 `fixed:"right"`**：名称列固定 **280px** 后全表宽
   ~1016 > 容器（1366 视口下 ~872）⇒ 表**内部**横向滚动。操作列必须 `fixed:"right"`
   钉最右，否则会被滚出视口（用户原话「图片列表超出页面部分」）。
   ⚠️ `fixed:"right"` **依赖** `scroll.x`（antd 固定列靠 scroll 容器实现），二者必须同在。
2. **操作列一行两个按钮**：`display:grid` + `gridTemplateColumns:"1fr 1fr"` + `Button block`
   （与商品列表操作列同一写法）。主视图 3 个按钮 = 复制链接/移动到 + 更多两行；
   回收站 2 个 = 恢复/彻底删除一行。
3. **页面根须收口宽度**：根是 flex（左栏 220 + 右区 `flex:1`），flex 子项默认
   `min-width:auto` ⇒ 内容一宽就把整行撑破，**左栏（含「回收站」入口）被顶出视口左侧** =
   「回收站入口不见了」。三件套：根 `width:100%` + `maxWidth:100%` + `overflowX:hidden`，
   右区 `minWidth:0`。

**⚠️ 版面分区与分页（2026-10-07 用户四条口径）**：

* **顶部工具栏固定、底部固定、只有数据行可滚动**：右区做**限定高度的纵向 flex**
  （`height: calc(100vh - 90px)`）——① 工具栏卡 `flexShrink:0`；② 数据区
  `flex:1; minHeight:0; overflow:auto` 自己滚；③ 底栏 `flexShrink:0`。
* **数据区滚动条隐藏（外观隐藏、滚动保留）**：`.ps-scroll-hidden` 类
  （`scrollbar-width:none` + `::-webkit-scrollbar{display:none}`）。⚠️ 不得改成
  `overflow:hidden`（那会让多出来的行**滚不到**）。
* **分页是卡片/列表的公共组件、底部固定**：表格自带分页**关掉**（`pagination={false}`），
  页面用**一个**独立 `<Pagination>` 放在 `flexShrink:0` 的底栏 —— 列表与卡片两视图共用
  （卡片只是展示样式变化，分页/数据同一份）。
* **名称列固定 200px + Tooltip 展示完整名**（口径由 280 → 200 演进，以后者为准）。
* **操作列三个按钮一行展示**（口径由「一行两个」→「三个一行」演进，以后者为准）+
  `fixed:"right"` 钉最右。

**⚠️ 单一真相源（2026-10-07 修，本轮最贵的坑）**：图片空间排序字段白名单曾在
`api/platforms/xhs/qianfan.py` **另存一份**（`MATERIAL_ORDER_FIELDS = ("name","createTime","size")`），
漏了回收站用的 `updateTime` ⇒ 回收站视图按删除时间排序被**自己的白名单**拦成 400
「加载失败」。两份清单必然漂移 —— 现改为**从 service 层 import**（`qianfan.py` 顶部），
本文件不得再复制。

### §5.2 落地方案

**后端**（最小改动）：`run_job_once` 加**可选 body**：

```python
class RunJobBody(BaseModel):
    params: Optional[dict[str, Any]] = None   # 本次覆盖；None = 用任务行配置

@router.post("/jobs/{job_id}/run")
def run_job_once(job_id: int, body: RunJobBody | None = None, ...):
    params_override = body.params if body else None
    if params_override:
        # 白名单 + 类型校验：只允许 params_editable 里的键，值走既有 validate_params
        spec = get_job_spec(job.job_key)
        illegal = set(params_override) - set(spec.params_editable)
        if illegal:
            raise HTTPException(400, "JOB_PARAMS_NOT_EDITABLE")
        merged = {**(job.params or {}), **params_override}
        validate_params(spec, merged)          # 复用既有校验（含 retention_days 范围等）
    log_id = run_job_in_background(job.id, trigger_type="manual", params_override=params_override)
```

## §1.9 定时清理未引用图片（2026-10-11 用户需求）

| 默认 cron | `0 0 0 * * MON`（每周一 00:00） |
| 默认状态 | **暂停**（见下「为什么默认暂停」） |
| 参数 | `account_ids`（默认 `[]` = 本人全部账号）、`delete_mode`（`recycle` / `permanent`，默认 `permanent`） |
| 平台接口 | 列表 `material_space/search_directory_manageable`（**需签名**）；进回收站 `batch_edit_directory_manageable`（`status:4`）；彻底删除 `batch_delete_directory_manageable`（`directoryManageableElements`） |
| 落库 | **零**（不写任何表、不落任何文件；唯一被写的是调度日志行，由 runner 负责） |
| 端点 / 表 / 迁移 | **±0**（复用既有 `picture_space_service` 的组装函数，不新增端点） |

### 三段链路

```
① 正常视图翻页（statuses=[1] / basicTypes=[2] / pageSize=500）
     每页挑出「未应用」的（type==2 且 productCount==0）
     ⇒ 页内每 100 条调一次 batch_edit（status=4，进回收站）
     ⇒ 翻到平台没有下一页为止

② 若 delete_mode == permanent（**先跑完 ① 才开始**）
     回收站视图翻页（statuses=[4] / basicTypes=[2] / updateTime 倒序 / pageSize=500）
     ⇒ 页内每 100 条调一次 batch_delete（彻底删除，不可还原）
     ⇒ 翻到最后一页
```

### 三条必须写在代码里的判据（都有守卫 + 变异验证）

1. **只删 `type==2` 且 `productCount==0` 的**。
   文件夹的 `productCount` **恒为 0** —— 判据漏了 `type` 就会把用户整个文件夹树删光；
   判据漏了 `productCount` 就会把**在售商品正在引用的图**删掉（图裂开，红线）。
2. **删了就不前进页号**（`_scan_pages` 的核心）。
   平台分页按**当前池子的偏移**切。每页删掉 k 条后池子缩短 k，同一 `pageIndex` 已经
   覆盖到「原来第 k+1 条之后」的位置 —— 这时还 `page += 1` 会**整段跳过 k 条**。
   ⚠️ 这不是理论问题：首版实现就是这个形态，实测 1200 条只删掉 700 条（500 条静默漏掉），
   被 `test_deleting_does_not_skip_the_tail_of_each_page` 当场抓住。
   防死循环兜底：同一页号连续两次拿到**完全相同的 id 集合** ⇒ 强制前进
   （判据是 id 集合不是条数：「条数相同但换了一批」是正常前进）。
3. **坏值落默认、缺值也给默认，但 API 边界要 400**。
   * 运行期（`coerce_delete_mode`）：凌晨没人看着，一行脏数据不该让整周任务空转 ⇒ 落 `permanent`；
   * API 边界（`validate_cleanup_params`）：用户当场填错 ⇒ **400**，否则他永远不知道自己填错了。
   合并成一处会二选一地丢掉一边。

### 为什么默认暂停

`delete_mode=permanent` 是**不可还原**的平台写操作（彻底删除连回收站都不留）。
与「每日发布商业笔记」的 `active` **刻意不同**：那个只在用户配好千帆、且有 0 篇挂链商品时
才真的出手；这个一旦跑起来就真的删图。⇒ 让用户先去任务中心确认参数（尤其删除方式）再手动启用。
种子 JSON 与代码兜底字典**同值**（`status: "paused"`）。

### 限流

每次**翻页**与每次**批量删除**都过一次 `CrawlRateLimiter.wait_allow(f"{account_id}:material")`。
⚠️ 键后缀 `:material` 必须与商品同步的 `:goods` 分开 —— 平台额度按接口族独立，
共用一个键会让先跑的那条把额度耗光、后跑的刚起步就被挡（§19 的教训）。

### 不做什么

* **不建新端点**：这是定时任务，入口在任务中心（用户口径没要求手动入口）；
  手工单条/批量删在图片空间页本来就有（`/picture-space/delete` / `permanent-delete`）。
* **不落库**：清理结果只进调度日志（`scheduled_job_logs.result`），不在本地留图片镜像。
