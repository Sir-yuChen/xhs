# 总① · 需求总体设计

## 1.1 目标与边界

| 项 | 内容 |
|---|---|
| 解决什么 | 我方平台上**不跳转千帆后台**就能看本店全部违规/预警/赔付/仲裁/抽检/免罚数据，与千帆页面**同列、同筛选、同分页** |
| 给谁用 | 运营（店铺线账号持有者）；数据隔离按 `platform_account_id`（ADR-021） |
| **明确不做** | ✗ 任何**写**平台状态：标已读（`read_mark`）、提交申诉（`appeal/submit*`）、批量操作/批量删除<br>✗ **任何落库**：不建表、不迁移、不写本地副本（含「只读同步」）<br>✗ 促销式二次统计（概览数字直接用平台返回的 `counts`，不在本地重算） |

## 1.2 总体流程（端到端）

```text
用户切账号 → 前端 ___
   │
   ├─ ① 前端 fetchViolationMeta(account) ──→ 后端 /violation/meta
   │        → 适配器 → SDK：status_enum + entity_enum + user_tag(+SPOT_CHECK)
   │        → 归一化成 {violation_status[], violation_entity[], reason_tags[], spot_check_reason_tags[]}
   │        ⚠️ 失败：502 VIOLATION_UPSTREAM_FAILED（不做静态兜底枚举 —— 见 §4.4）
   │
   ├─ ② 前端 fetchViolationList({quick|高级条件, page}) ──→ 后端 /violation/list
   │        → 服务层 build_list_body（唯一组装点，含 D9 时间换算 / D10 快捷映射 / tagName→tagIdGroup）
   │        → 适配器 → SDK post_violation_list（**必须签名**）
   │        → normalize_list_payload → {total, items[], query, scene, account}
   │        ⚠️ 失败：502（平台原文透传）；账号无 ark 令牌：400 ARK_SESSION_REQUIRED
   │
   ├─ ③ 点「查看详情」→ /violation/detail + /violation/appeal-record + /violation/evidence（三个只读）
   │        ⚠️ 详情**不自动标已读**（不调 read_mark）
   │
   └─ ④ 其余子 Tab：/compensations · /arbitrations(+arbitration-tags) · /spot-checks
                    · /exemptions/overview|items · /checkup/risks|advice|negative-feedback
            ⚠️ 全部只读、全部零落库
```

**每一步的失败归属**：门禁类（账号不属于我 / 无 ark 令牌）由路由层结构化 400/404 给 → 前端弹可执行原因；
平台类（签名被拒 / 平台报错）由路由层 502 + 平台原文 → 前端原文展示（**不吞成「未知错误」**）。

## 1.3 关键设计决策（为什么这么设计）

| # | 决策 | 备选 | 为什么选它 | 代价 |
|---|---|---|---|---|
| D1 | **零落库**：不建表、不迁移、不写本地副本 | ① 建 `violations` 表做只读同步；② 内存缓存 | 用户口径；且违规数据**强时效**（未读态、申诉截止、处罚解除）—— 落库必然出现「本地说未读、平台已读过」，而平台是唯一真相源 | 每次进页面都打平台（受限流器约束，见 §3.6 不变量 4） |
| D2 | **只读边界**：只接 16 个读接口 | 顺手接 `read_mark` 让「未读」真的消失 | 打开详情就改平台状态不是只读；且我方**没有**申诉/整改的执行链路，标已读只会让用户在千帆后台看不到 | 「未读 N」永远与平台一致，不会因我方访问而变化 |
| D3 | 写接口（申诉 / 已读）**不接后端**，UI 一比一复刻但提交处**明确标注不代提交** | 前端也做成「假成功」 | 伪造成功会让用户以为申诉已交（实际没有）⇒ 错过申诉截止 | 用户需去千帆后台提交（UI 已写明） |
| D4 | 单页 Routes 二段（`/violation-manage` + `/violation-manage/checkup`），子 Tab 走 `?tab=` | 每 Tab 一个路由 | 与千帆一致（URL 直接落子 Tab）；刷新不丢当前 Tab | — |
| D5 | 侧栏 `shopLineChildren` 加一项，`ROUTE_BUSINESS_LINES` 登记 `violation-manage → shop` | 挂在内容线 | 违规是**店铺**属性（千帆账号才有），挂内容线会导致无 ark 令牌的账号也看到入口 | — |
| D6 | 账号上下文复用店铺线既有口径（`ark` 通道账号 + 切换即重拉） | 页面自己拉全账号列表 | 与商品列表/图片空间同口径，避免「这一页能看到、那一页看不到同一账号」 | — |
| D7 | 分层：SDK 方法 → 适配器同名委托 → `violation_service`（**payload 组装 + 归一化唯一实现**）→ 路由 | 组装写在路由里 | 组装逻辑要能被单测逐字钉住（真机期望值），写在路由里只能起服务才能测 | 多一层文件 |
| D8 | 枚举由**后端下发**，前端不硬编码 | 前端抄一份枚举常量 | 平台会加枚举（实测 tag 已出现「同名不同 ID」）；抄一份必然与平台漂移且**静默** | 首屏多一次 meta 请求 |
| D9 | 时间口径**唯一实现** `day_range_to_ms`：起 `00:00:00.000`、止 `23:59:59.999` | 传日期串 / 传次日零点 | 真机：结束值 `1792252799999`；写成次日零点会**静默漏掉最后一天 23:59:59.9xx**（请求照样 200） | — |
| D10 | 快捷筛选 = 一组**判别式参数**，目录在服务层，角标数各自单独查一次 | 前端拼参数 | 拼参数散在组件里 ⇒ 「待处理」在两处定义会漂移；角标必须与列表同源（同一 `quick_filter_body`） | 首屏多几次 `list` 请求取 `counts` |
| D11 | 危险操作：**单条**是唯一可执行路径；批量入口照千帆渲染但**点后只提示、不发请求** | 真做批量 | 用户口径（绝不批量）；且平台批量删除不可回滚 | 批量操作需去千帆后台 |
| D12 | 测试用**假适配器**注入（`dependency_overrides[get_qianfan_api_adapter_factory]`） | 打真机 | 硬约束 D2；且真机数据会变（本店实测 56 条，会变） | 真机契约另用探针脚本（§附 B）验证 |

## 3.2 请求 / 响应契约

```python
class ViolationListRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")   # ⚠️ 白名单：加字段必须同步改这里
    platform_account_id: int
    scene: Literal["violation", "warning"] = "violation"
    page_no: int = 1
    page_size: int = 10        # 1..100（与千帆下拉同档位）
    keyword: str = ""          # → fuzzyMatchId
    entity_types: Optional[list[int]] = None   # → violationEntityTypes（999=全部 ⇒ 省略）
    reason_name: str = ""      # → tagIdGroup（经 user_tag 查表）
    statuses: Optional[list[int]] = None       # → violationStatus
    severe_only: bool = False                  # → severePunishmentFlag=true
    allow_appeal: Optional[bool] = None        # → allowAppeal
    correctable: Optional[bool] = None         # → correctableFlag
    unread_only: bool = False                  # → readMark=0
    exam_only: bool = False                    # → examStatusList=[1]
    pending_only: bool = False                 # → filterStatus="COMPOSITE"
    recent_days: bool = False                  # → violationStatus=[0,1,2] + 近 7 日窗口
    date_start: str = ""       # YYYY-MM-DD → violationStartTime（当天 00:00:00.000）
    date_end: str = ""         # YYYY-MM-DD → violationEndTime  （当天 23:59:59.999）
    quick: str = ""            # 非空 ⇒ 以快捷筛选为准
```

## 3.4 实现逻辑（判据式）

| # | 规则 | 判据式表述 | 落点 |
|---|---|---|---|
| R1 | 时间换算唯一 | 日期区间 → `(start 00:00:00.000, end 23:59:59.999)` 毫秒；**同一模块只有一个函数** | `violation_service.day_range_to_ms` |
| R2 | 原因 → tagIdGroup | **精确字符串相等**（不 trim、不大小写归一、不去重），命中取该 tag 的**全部** `tagIds`；未命中 ⇒ **不带该条件**并在响应 `query` 里看得出没带 | `reason_tag_ids` |
| R3 | 枚举原样下发 | `user_tag` 的 `tagName` 原样出现在 `reason_tags[].tag_name`（实测含 **U+200B 零宽空格**，见 §7.1；不可见但必须保留） | `normalize_reason_tags` |
| R4 | 「全部」对象 | `entity_types` 含 `999` ⇒ **省略** `violationEntityTypes`（真机「全部」不发该字段） | `build_list_body` |
| R5 | 快捷 = 答案 | `quick != ""` ⇒ 只用该 quick 的答案重新组装（不叠加其它条件），分页由调用方覆盖 | `quick_filter_body` |
| R6 | 缺值 | 平台没给的字段 ⇒ `None`；`_text("")` ⇒ `None`（不造空串） | `_text` / `normalize_violation_row` |

## 4.1 逐字段的「谁传 → 谁读 → 什么形态」

| 字段 | 前端产出（准确形态） | 后端读点（准确形态） | 不一致会怎样 |
|---|---|---|---|
| `reason_name` | `meta.reason_tags[].tag_name` **原样回传**（含不可见 U+200B） | `reason_tag_ids` 精确相等 | 前端 trim / 按可见文案重拼 ⇒ 那条永远查不到 ⇒ **静默丢筛选**（结果变多，用户以为「这个原因只有这么几条」） |
| `entity_types` | `number[]`，选「全部」时**不传** | 含 999 ⇒ 省略字段 | 传 `[999]` 原样下发 ⇒ 平台当作非法类型 ⇒ 空列表（看起来「没有违规」） |
| `date_start/end` | `YYYY-MM-DD` | `day_range_to_ms` | 前端自己算毫秒并传 ⇒ 两处实现漂移（末段记录丢失） |
| `quick` | 字符串键（`pending` / `unread` / …） | `quick_filter_body` | 两处各自拼参数 ⇒ 角标数与列表数对不上 |
| `statuses` | `number[]` | `violationStatus` | 传字符串 ⇒ 平台按非法值判空 |
| `page_size` | number | `pageSize` | 前端传 101 ⇒ 422（后端钳 1..100） |
| `tag_id` / `tenant` | 行里的原值（详情回传） | 详情/证据请求体 | 传空 ⇒ 平台返 `90000001 参数不正确`（账号类实测） |

## 4.2 端到端链路（用户点一下，系统发生了什么）

```text
① 用户切到账号 A（无 ark 令牌）
② 前端 POST /xhs/qianfan/violation/violation/meta {platform_account_id:A}
③ 后端 _owned_account（404）/ _ark_adapter_for（400 ARK_SESSION_REQUIRED）
④ 前端据 code 渲染「该账号未导入千帆登录态 → 去账号矩阵补登」——**不静默空表**
────────────────────────────────────────────────────────────────
① 用户点「违规列表 → 未读」
② 前端 POST …/violation/list {platform_account_id, quick:"unread", page_no:1, page_size:10}
③ 后端 quick_filter_body("unread") → {dataFlag:true, warnFlag:0, pageNo, pageSize, readMark:0}
```

| # | 场景 | 正确行为 | 曾踩的坑 |
|---|---|---|---|
| 1 | 快速切账号 | 旧账号的在途响应**丢弃**（按 `accountId` 比对） | 慢响应覆盖新账号数据（本仓曾在别页出现） |

### 7.1 ⚠️ 实测推翻调研报告一处：尾空格 tag 实际是 **U+200B 零宽空格**

调研报告 §3 记作「`违反法律法规`(尾空格) → 80005677」。本轮 `meta` 实测的 tagName 字面是
`'违反法律法规\u200b'`（**零宽空格 U+200B**，不是普通空格 `\x20`）。

| 项 | 影响 |
|---|---|
| `reason_tag_ids` 的匹配方式 | **不变** —— 仍是「精确字符串相等、不 trim、不去重」。零宽空格 trim 也去不掉（`str.strip()` 只去空白字符），所以两种写法下「不 trim」都成立 |
| 前端的显示 | `\u200b` 不可见 ⇒ 下拉里两条「违反法律法规」**看起来同名**，极易被用户当成重复项 |
| 后端的防线 | 不能按名字合并/去重（会合并两组 tagIds，实测 5 个 vs 1 个）；**必须用 `tag_ids` 区分** |

> 结论：设计判据（R2/R3）不变，但**原因下拉必须显示 `tag_ids` 数量或后缀提示**，否则用户
> 在 UI 上无法区分两条同名原因。（卡 2 的 UI 落地项。）
