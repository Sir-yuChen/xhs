# 调研：外部图床（1688 / gw.alicdn.com）无哈希头下的图片一致性判定方案

- 日期：2026-10-11（真机实测）
- 范围：`gw.alicdn.com` / `img.alicdn.com`（1688 商品图 CDN，Picasso 图片服务）+ 本地数据包 `C:\Users\admin\Desktop\商品ID_935947169189`
- 纪律：**全程只读**（HEAD / GET+Range / 只读 GET），未调用任何写接口；未打印任何 Cookie/token
- 前提（已实测，直接引用）：小红书 `qimg.xiaohongshu.com/material_space/<uuid>` 的 `HEAD` 返回 `ETag == 全文 MD5`，**平台侧已解决**；本次只攻 1688 外部图床这一卡点

---

## 核心结论（先看这段）

> **gw.alicdn.com 在任何 URL 形态下都不下发 ETag / Content-MD5 / Last-Modified —— 这条路彻底堵死，不要指望零下载拿哈希。**
>
> 但实测挖出两个**可落地**的替代判据：
> 1. **O1CN 图片内容 ID（零下载）**：URL 里的 `O1CN01...` 段是**图片内容的稳定 ID**，同一张源图的所有尺寸/质量变体共享该段，且 `i1/i2/i3/...` 分片前缀可任意替换返回同一图。⇒ **可用作「是不是同一张源图」的强身份标识**（不是内容比对，但能回答「同一图 vs 不同图」）。
> 2. **50×50 缩略图感知哈希（极低下载，约 3.8 KB）**：`<原URL>_50x50.jpg` 返回 50×50 JPEG，仅 **3.8 KB**，内容字节稳定（重复请求 md5 全等）。对其做 DCT 感知哈希，**同图变体 Hamming ≤ 6，异图 Hamming ≥ 20**，阈值 10~12 可稳定区分。⇒ 这是「逐字节比对」的**低下载量近似替代**，比拉原图（115 KB~257 KB）省 30~65 倍流量。
>
> **最终推荐**：**O1CN ID 映射（第 0 道）+ 50×50 pHash（第 1 道）** 两级预检；仅在两者冲突/缺失时才回退到 `_q90.jpg` 原图逐字节（115 KB，最后手段）。

### Q1 gw.alicdn.com 全站是否任何路径形态会给 ETag / Content-MD5？

- **无任何形态返回 ETag / Content-MD5 / Last-Modified。**
- **条件请求完全无效**：带 `If-None-Match: "abc123"` 或 `If-Modified-Since: 2099` 仍一律 **200**（不返回 304），证明服务端**根本不维护实体标签/修改时间**，条件请求「零下载判等」这条路走不通。
- 关键运维头（供排障，非判据）：`x-powered-by: Picasso`、`picasso-fmt: jpg2webp`（默认把 jpg 转 webp）、`picasso-cache-info: L3-HIT`（CDN 命中）、`back_uri`（**回显服务端改写后的规范化 URI**，实测会追加 `_q90.jpg_.webp`）。
- **`vary: Accept`**：服务端按 `Accept` 协商格式。默认（浏览器 UA 不带显式 Accept）→ **webp**（`RIFF....WEBP`，63450 B）；若显式发 `Accept: image/jpeg,image/png,image/*;q=0.8` + `Accept-Encoding: identity` + `Referer: detail.1688.com` → **拿到真 JPEG**（`ffd8ffe0...JFIF`，115491 B），即 `picasso-fmt: jpg2`、`back_uri: ..._q90.jpg`。⇒ **需要逐字节比对时必须显式请求 JPEG 且带 1688 Referer**，否则拿到的是 webp 转码件，与本地 jpg 永远不等。

### Q2 1688 图片 URL 路径规律：`O1CN01...` 段是不是内容 ID？

**结论：可行。`O1CN` 段 = 图片内容稳定 ID，同源图的所有变体共享；`i1/i2/i3/i4` 是分片前缀，可任意替换返回同一图。**

实测（同一 O1CN `O1CN01taCdOF2NXh2EHTk8j`）：

| 请求 | 返回尺寸 | 字节 |
|---|---|---|
| base / `_q90.jpg` | 800×800 | 115491 |
| `_q100.jpg` / `_1080x1080.jpg` / `_1200x1200.jpg` | 800×800 | 257483（= 原始全质） |
| `_400x400.jpg` | 400×400 | 87343 |
| `_50x50.jpg` | 50×50 | 3797 |

- **不同尺寸变体共享同一 O1CN，且保持同一画面内容（等比缩放）** ⇒ O1CN 是可靠的内容身份标识。
- **分片前缀无关**：把 URL 里 `/i3/` 换成 `/i1/ /i2/ /i4/ /i5/`，全部返回**同一张 800×800、同字节**（115491 B）。⇒ ID 段本身即全局唯一，前缀只是历史分桶。
- **注意**：1688 商品图统一是 **800×800 方形**（可能带补白），而本地主图常见 **750×1000**（3:4）。⇒ **不能用「尺寸/宽高比一致」直接判等**，只能靠 O1CN ID 或感知哈希。
- 脏数据校验：把 ID 末位 `j` 改 `z`（`O1CN01taCdOF2NXh2EHTk8z`）→ **404**。证明 ID 段是真实内容键，伪造即失效。

### Q4 HTTP 条件请求 / Content-Length 精确比字节的强度

**结论：条件请求不可行（服务端不支持 304）；Content-Length 单判据可行但强度弱（仅能确认「字节数一致」，假阳性不可忽略）。**

- **条件请求不可行**：Q1 已证，服务端无 ETag/Last-Modified，`If-None-Match` / `If-Modified-Since` 一律 200。本地即使构造出全同字节，也无从用条件请求触发 304。
- **Content-Length 判据**：可用（`HEAD` 0 字节即拿到），但**只能证伪不能证真**：
  - 若线上 `Content-Length ≠ 本地文件字节数` ⇒ **确定不同图**（强否定，可信）。但前提是**两边同一编码路径**（线上默认 webp，本地 jpg —— 所以必须用 Q1 的「显式 JPEG + Referer」路径，取 `_q90.jpg` 的 115491 之类字节数）。
  - 若字节数**相等** ⇒ **不能推断同图**。实测 4 个不同 O1CN 的 `_q90.jpg` 字节数分别为 129509 / 142136 / 153604 / 136489 —— 在 800×800 JPEG（~100–250 KB）区间，字节空间约 10^5 量级，而潜在图片量大，**生日悖论下同字节数碰撞不可忽略**。⇒ **Content-Length 是弱判据，适合作「快速排除」，不适合作「判等」。**

### Q5 分块 Range 指纹（首尾若干字节）

**结论：可行（作为弱指纹）。Range 被支持、字节稳定；但这是「下载」——只是量极小。推荐首 2 KB + 末 2 KB。**

实测：

- **Range 被支持**：`Range: bytes=0-2047` → **206 Partial Content**，带 `Content-Range: bytes 0-2047/63450`；`bytes=-2048`（尾）同样 206。注意响应无 `Accept-Ranges` 头，但实际支持。
- **字节稳定**：同一 URL 连续 3 次取 `bytes=0-2047`，md5 **全等**（`98b42a47...`）；且与整图下载后的首 2048 字节**完全一致**（`head -c 2048 full.bin | md5sum` 相同）。⇒ 分块内容可复现。
- **但注意编码路径**：默认拿到的分块是 **webp** 的首尾字节（`RIFF/WEBP/VP8`），不是 JPEG 的。要比本地 jpg 必须走 Q1 的 JPEG 路径，此时首 2 KB 含 JPEG SOI/APP0(JFIF)/APP1(EXIF)/量化表、末 2 KB 含 SOS/EOI —— **对 JPEG 而言，EXIF/量化表/末端熵码使首尾 2 KB 足以区分两张不同图**（量化表不同 ⇒ 压缩器/质量不同 ⇒ 基本可判异图）。
- **失效场景**：同图不同压缩率版本（`_q90` vs `_q100`）首尾字节**不同**（质量参数变 ⇒ 量化表与熵码不同）⇒ **分块指纹对「同图变体」失效**，会把同图误判为异图。这正是它不如感知哈希的地方。
- **推荐参数**：首 **2 KB** + 末 **2 KB**（共 4 KB/次）；判据：**两段字节全等 ⇒ 同文件（强）；任一不等 ⇒ 无法下结论（需感知哈希兜底）**。不要单用首块（JPEG 头部前缀在同类压缩器下高度相似）。

### Q6 第三方能给出 1688 图片哈希的服务/镜像？

**结论：不可行（无可靠公开服务；自建代理 = 等价于自己拉 CDN，无风控收益）。**

- 阿里图片 CDN 无公开元数据服务（Q3 已证）；Picasso 内部缓存信息（`picasso-cache-info`）**不含内容哈希**。
- 市面「1688 图床代理」本质是**反向代理转发原图**，取哈希仍需代理方下载 —— 只是把风控风险转嫁给第三方，且可用性/稳定性无保障、可能被阿里封禁。⇒ **判不可行。**

### Q7 本地侧反向：先上传本地图到千帆再比 URL？

**结论：不可行（副作用大、收益为零）。**

- 本质是「用写接口换判等」：把本地图上传到千帆图片空间 → 拿到小红书 CDN 直链 → 再用**已解决的** `ETag==MD5` 判等。
- 但：(a) 需要**写接口**（上传），违反「预检只读」原则，且会污染图片空间、产生垃圾素材；(b) 仍需把**线上 1688 图**拉到某处才能比 —— 线上图本身还是得下载，问题没解决；(c) 千帆无「以图搜图对 1688 外链」的公开能力。⇒ **判不可行，副作用明确。**

### Q8 极小尺寸缩略图（`_50x50.jpg`）做感知哈希

**结论：可行，且是本卡点的最佳「极低下载」方案。50×50 JPEG 仅 3.8 KB，pHash 稳定且区分度足够。**

实测（DCT 感知哈希，8×8 低频块，Hamming 距离）：

| 对比 | Hamming | 解读 |
|---|---|---|
| 本地图 全尺寸 vs 自身 50×50 缩放 | **2** | 同图（下采样噪声） |
| CDN 原图 vs CDN 同 ID `_50x50.jpg` | **6** | 同图变体 |
| CDN 原图 vs CDN 同 ID `_100x100.jpg` | **2** | 同图变体 |
| CDN `_50x50` vs `_100x100` 同 ID | **4** | 同图变体 |
| 本地 主图02 vs 主图03 | **22** | 异图 |
| 本地 主图03 vs 主图04 | **28** | 异图 |
| 本地详情图两两（28 对）最小 | **20** | 异图（最低重叠） |
| CDN 图 A `_50x50` vs CDN 图 B `_50x50` | **20** | 异图 |
| CDN `_50x50` vs 本地主图 | **28–36** | 异图 |

- **同图变体 ≤ 6，异图 ≥ 20，间隔极宽** ⇒ **推荐阈值 Hamming ≤ 10 判同图，≥ 14 判异图，10~14 灰区转人工/回退原图**。
- **缩略图字节稳定**：`_50x50.jpg` 连续请求 md5 **全等**（`596a0a2d...`，2076 B；另一 ID 3797 B）。⇒ 可缓存复用。
- **成本**：50×50 ≈ **3.8 KB/次**，对比 `_q90.jpg` 原图 115 KB ⇒ **省 ~30 倍**；对比 `_q100` 257 KB ⇒ **省 ~65 倍**。对 CDN 几乎是「抬手一次小请求」。
- **局限**：50×50 感知哈希是**画面级**判据（不是逐字节）。对「同图但重构图/加水印/裁切」可能判同（画面近似）；对「同主体不同款」极端情形可能误判。作为预检足够，作为唯一判据略弱。

**结论：待实测偏不可行（数据包内 O1CN 与本地文件名无直接映射规律）。**

### Q10 方案对比表 + 最终推荐

| 方案 | 是否下载 | 下载量/次 | 判定强度 | 风控风险 | 实现复杂度 | 推荐度 |
|---|---|---|---|---|---|---|
| Q1/Q4 ETag/条件请求 | 否 | 0 B | —— 服务端不支持，**不可用** | 无 | —— | ❌ 排除 |
| Q4 仅比 Content-Length | 否 | 0 B（HEAD） | 弱（仅能否定） | 极低 | 低 | ⭐ 辅助（快速排除） |
| Q1 显式 JPEG + 逐字节 | 是 | 115 KB | **逐字节（最强）** | 中（拉原图） | 低 | ⭐⭐ 最后手段 |
| Q5 分块 Range 指纹 | 是 | 4 KB（首2K+末2K） | 弱（同图变体失效） | 低 | 中 | ⭐ 辅助 |
| Q8 **50×50 缩略图 pHash** | 是 | **3.8 KB** | **画面级（强）** | **极低** | 中 | ⭐⭐⭐ **主推** |
| Q2/Q9 **O1CN 内容 ID 映射** | **否** | **0 B** | **身份级（强，同源图）** | 无 | 中（需建映射） | ⭐⭐⭐ **主推（第0道）** |
| Q6 第三方哈希服务 | —— | —— | 无可靠服务 | 转嫁 | 高 | ❌ 排除 |
| Q7 上传本地图到千帆 | 是（写） | 上传 | 画面级 | **写接口副作用** | 高 | ❌ 排除 |

**最终推荐（分层预检，越靠前越省）：**

1. **第 0 道 —— O1CN ID 精确匹配（零下载，0 B）**：从 xlsx URL 抽出 `O1CN...` 段，与本地侧已建立的「O1CN ↔ 本地图」映射做**精确字符串比对**。
   - 命中（同 ID）⇒ **判定同一张源图**（同源，强结论，零下载）。
   - 这是回答「是不是同一张源图」的**最优先、最省**判据。前提是能建立本地映射（见第 2 步，或让上游采集时把 O1CN 落库）。
2. **第 1 道 —— 50×50 缩略图感知哈希（极低下载，3.8 KB）**：当无 ID 映射、或需**内容级**确认时，取 `<URL>_50x50.jpg`（3.8 KB），DCT pHash，**Hamming ≤ 10 判同图，≥ 14 判异图，10~14 灰区回退**。
   - 兼顾「几乎不拉流量」与「画面级可靠」，是逐字节比对的低成本替身。
3. **第 2 道（兜底，罕见）—— `_q90.jpg` 原图逐字节（115 KB）**：仅当第 0/1 道冲突或处灰区时触发；必须用**显式 JPEG + `Referer: detail.1688.com`** 路径拿真 JPEG，再做 md5 全等比对（逐字节最强）。

> **一句话**：**不要指望在 1688 图床上零下载拿哈希（它永远不给 ETag）**；改用「**O1CN ID 身份比对（0 B）+ 50×50 pHash（3.8 KB）**」两级预检，把「拉原图」压到极罕见的兜底路径，即可在几乎不触发风控的前提下落地「线上图 vs 本地图」一致性判定。

## 附：实测原始证据速查

- **无 ETag 验证**：HEAD（多种后缀）返回头字段恒为 `Server/Content-Type/Content-Length/Date/x-powered-by: Picasso/picasso-fmt/picasso-cache-info/back_uri/vary: Accept` —— **无 ETag/Content-MD5/Last-Modified**。
- **条件请求无效**：`If-None-Match: "abc123"` → 200；`If-Modified-Since: 2099` → 200（无 304）。
- **真 JPEG 路径**：`Accept: image/jpeg,image/png,image/*;q=0.8` + `Accept-Encoding: identity` + `Referer: https://detail.1688.com/` → `Content-Type: image/jpeg`，`picasso-fmt: jpg2`，`back_uri: ..._q90.jpg`，body `ffd8ffe0 0010 4a46 4946`（JFIF）。
- **webp 默认路径**：body `52494646 ... 57454250`（RIFF/WEBP）。
- **Range**：`bytes=0-2047` → 206 + `Content-Range: bytes 0-2047/63450`；3 次 md5 全等 `98b42a47d5e64cfc5c646ddfba929f65`。
