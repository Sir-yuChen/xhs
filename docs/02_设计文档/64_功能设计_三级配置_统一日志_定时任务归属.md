# 设计 64 · 三级配置 / 统一日志体系 / 定时任务归属（2026-10-25 三需求打包立项）

> 用户口径：①「配置优化为系统级--用户级--工作区级：工作区级在各工作区内展示，
> 系统级在系统管理内展示，用户级在用户头像下新增下拉弹窗展示，其它由项目决策」
> ②「统一日志格式，补充完善日志体系与核心业务节点（出入口/增删改/操作），完善日志保存清理机制」
> ③「分析定时任务模块拆分还是每工作区单独，调用市场成熟企业级方案，若提取成公共则在系统管理中实现」。

## §1 需求一：三级配置（系统级 / 用户级 / 工作区级）

### §1.1 现状与痛点
`system_settings` 每用户一份（`(user_id,key)` 唯一，26 用户 × 9 键 = 冗余播种）；
`apply-to-all` 是把管理员行复制到所有人的补丁；唯一的"全局"读法是特判管理员行
（register.enabled）与全表 max（进程级并行度）。无 workspace 维度。

### §1.2 模型决策：**一张表三个归属**（不建三张表）
`system_settings` 复用全部列（value_type/category/label/审计列），归属改造：

| 级别 | 行形态 | 唯一性（partial unique，PG/SQLite 双方言） |
|---|---|---|
| 系统级 | `user_id IS NULL ∧ workspace IS NULL` | `(key)` |
| 用户级 | `user_id` 非空（原语义不变） | `(user_id, key)` |
| 工作区级 | `workspace` 非空（String32，同 `menus.workspace` 词汇表，无 workspaces 表） | `(workspace, key)` |

### §1.3 生效级联（唯一读口径）
`effective(user, workspace) = 工作区级 > 用户级 > 系统级 > YAML/env > BUILTIN_DEFAULTS`
（**最贴近人的赢**：个人偏好覆盖工作区参数，工作区参数覆盖全局默认；同一 key
多级并存合法，读的时候逐级找第一命中）。`live_value(user_id,key)` 保留签名，
内部改「用户级 → 系统级」两级（业务读点无 workspace 上下文）；带 workspace 上下文
的新读点走 `effective_value(user, workspace, key)`。

### §1.4 数据迁移（不造假不丢数据）
存量 26 用户 × 9 键行，逐 key 对比 `BUILTIN_DEFAULTS`：**值 == 默认 ⇒ 删**
（回落系统级，消除冗余播种）；**值 ≠ 默认 ⇒ 保留为用户级覆盖**（真改动不能丢）。
启动播种从「每用户一份」改为「每 key 一行系统级」；`ensure_settings`（每用户补种）
整条退场。

### §1.5 API
| 端点 | 变化 |
|---|---|
| `GET/POST/PUT/DELETE /api/settings` | 加 `scope` 参数（`user` 缺省=本人 / `system`=admin 专属（`system:setting:*` 码）/ `workspace`+`workspace=`） |
| `GET /api/settings/effective?workspace=` | **新增**（登录即可）：级联合并结果 + 每键命中级别，前端展示"这一格到底生效的是哪级" |
| `POST /api/settings/apply-to-all` | **退场**（410 墓碑，系统级取代其语义），−1 端点 |

### §1.6 UI 三处（用户口径逐条对应）
1. **系统管理 → 配置管理**：`/system/settings` 不再重定向，新面板挂系统级行
   （`SettingsTable scope="system"`）。
2. **头像下拉 +「用户配置」**：Modal 内嵌 `SettingsTable scope="user"`（与
   `/settings` 页同组件；`/settings` 路由保留为同功能的页面形态，菜单种子不动）。
3. **各工作区内展示工作区级**：`WorkspaceShell` 顶栏加齿轮按钮（壳是公共组件
   ⇒ 所有工作区自动获得）→ Modal `scope="workspace"`（当前 workspace 取自
   `workspaceOf(location)`；写权限 = `system:setting:edit` 码持有者，展示登录即可）。

## §2 需求二：统一日志体系

### §2.1 统一格式（唯一出口 `core/logfmt.py`）
`%(asctime)s [%(levelname)s] [%(name)s] %(message)s`，业务事件 message 固定为
`event=<名> key=value …`（`biz()` 构造器）；uvicorn 日志经 `dictConfig` 统一成同
格式（`backend/main.py` 启动时注入）。

### §2.2 业务日志落库（新表 `business_logs`，+1 表）
`services/business_log_service.record(event, action, actor, workspace, target, summary, detail)`
—— **双写**：DB 一行（供页面查）+ 统一格式 logger 一行（进 app.log）。DB 写自开
Session ⇒ **worker 线程可靠**（绕开"worker 里 logger 不落盘"的实测坑）。
列：id/created_at/level/event/action/actor_id/actor_name/workspace/target_type/target_id/summary/detail_json。

### §2.3 首期埋点（核心节点，用户口径"出入口/增删改/操作"）
| 域 | 事件 |
|---|---|
| 认证出入口 | 登录成功 / 登录失败(401) / 登出 / 改密 / 注册开关变更（此前 `/api/auth/*` 被审计中间件跳过，全零日志） |
| 系统管理 CRUD | 用户/角色/菜单/字典的 create/update/delete（中间件只记 API 面，这里记业务语义面：改了谁、改了什么） |
| 配置变更 | 三级配置每一级写操作（需求一的写点顺手埋，记录 scope+key+前后值摘要） |
| 队列 | 入队成功（来源/数量）与终态（done/failed/cancelled/exhausted）——`note_queue_service` 终态收口处 |

### §2.4 保存与清理机制
- **DB 日志保留**：`RECORD_CLEANERS` 注册表 +3——`api_logs`（默认 90 天）、
  `business_logs`（90 天）、`scheduled_job_logs`（30 天，**首次有了自动清理**）；
  保留天数 = 新系统级配置键 `log_retention_days` / `job_log_retention_days`，挂在
  既有内置任务 `system.queue_record_cleanup` 上（不新增任务）。
- **app.log 滚动**：`.hermes/scripts/run-app.py` 追加写前检查 >50MB ⇒ 改名
  `app.log.1~3` 轮转（launcher 拥有该文件句柄，Python 侧 rotation 管不到 fd 重定向）。
- **日志查看页**：新增第三 Tab「业务日志」—— `GET /api/system/logs/business`
  （`system:log:view`，分页 + event/actor/时间筛选）。

## §3 需求三：定时任务归属（分析 + 决策）

### §3.1 企业级方案对比
| 方案 | 形态 | 适配结论 |
|---|---|---|
| XXL-Job | 独立调度中心 + 执行器 + 自有 DB | ❌ 需独立部署一套中心，单机应用养不起 |
| Quartz | Java 系嵌入式集群 | ❌ 语言不通，思想可借鉴 |
| Celery Beat | 需 broker（Redis/RabbitMQ） | ❌ 为调度引一个中间件，得不偿失 |
| Temporal / Airflow | 工作流引擎，重 | ❌ 超出需求两个量级 |
| **APScheduler 嵌入式** | 进程内单例 + DB 行注册表 | ✅ 现状即是，配行级隔离足够 |

### §3.2 决策：**公共单调度器保留（不拆分），加工作区归属**
拆成每工作区独立调度器 = 多实例抢同一批 DB 行（看门狗/幂等/去重全部复杂化），
而调度器本来就是进程单例、行级 `user_id` 隔离已满足权限面 ⇒ 拆分无收益。
借鉴 XXL-Job 的两个思想收进单进程：**任务代码白名单**（job_registry，已有）与
**执行器分组标签**（新增 `workspace` 列，标注每个 job 属于哪个工作区）。

### §3.3 实现
- `scheduled_jobs.workspace` 列（String32，可空）——迁移按 job_registry 声明回填
  存量行；registry 每项声明默认 workspace（system.* → system，业务类 → xhs）。
- `GET /api/schedule/overview`（**新增，admin 专属**）：全量 job 跨工作区总览
  （含 owner/工作区/状态/下次执行/最近结果计数）。
- 系统管理新增「定时任务」页（`/system/scheduler`，新权限码 `system:scheduler:view`
  + `system:scheduler:manage`）：跨工作区总览 + 暂停/恢复/立即执行（manage 码）；
  各工作区任务中心（`/tasks`）不变（仍按本人）。
