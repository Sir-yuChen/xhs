# 44 · 设计变更 · 删除关联内容（先平台、后本地）

> 立项：2026-10-18（用户口径两句话，第二句推翻了第一句的草案）
>
> ① 「新增一个功能，如果未规定有关联笔记和商品信息，新增批量删除违规信息的同时
>    同步删除关联的商品或笔记信息，支持批量删除和单条信息删除」
> ② 「**改为删除平台数据后，检查本地，本地存在对应的数据则删除，不存在则跳过**，
>    所有平台操作均可以使用这种方式，先操作平台数据再检查本地是否存在对应数据，
>    存在则执行操作，不存在则跳过」

---

## 1. 规则（全项目通用口径）

> ⚠️ 本节已提炼为**通用规范**：`docs/02_设计文档/45_通用规范_平台优先本地跟随.md`
> —— 后续所有「打平台 + 动本地」的链路一律照 §45 实现，本文只保留本需求的落地细节。

| 阶段 | 做什么 | 失败处理 |
|---|---|---|
| ① 平台 | 删平台数据（商品 / 笔记） | 平台失败 ⇒ **本地不动**，如实回报原因 |
| ② 核对 | 平台成功后，查本地有没有这条 | — |
| ③ 本地 | 有 ⇒ 删本地（含从属行） | 本地删异常 ⇒ 回报，但平台已删的事实不改 |
| 缺 | 本地**没有** ⇒ **跳过** | **不算失败**（本地是缓存，不是平台镜像） |

**为什么顺序是「先平台」**：反过来（先删本地）一旦平台失败，平台还留着、本地已没了 ——
用户在平台看得到、在我们这看不到，两边对不上，而且本地再也补不回来（除非重新同步）。

**为什么「本地没有就跳过」**：本地只存用户同步过的数据。把「本地没有」当失败，
会让「删 10 条 → 7 条报错」看起来像平台坏了，实际是本地本来就没同步过。

## 2. 违规记录本身删不掉（平台事实）

千帆违规域**没有删除接口**（调研已确认：写接口只有 `ark/violation/read_mark` 一条，
且那是「标已读」）。违规单是平台处罚凭证，商家侧不可撤销。

⇒ 本功能删除的是违规**指向的商品 / 笔记**，不是违规记录本身。
UI 文案、确认框、回执处处写清这一点 —— 否则用户会以为「平台处罚被撤销了」。
店铺(0) / 账号(2) / 直播间(4) 没有可删实体，回执 `skipped` + 具体原因。

## 3. 回执四态

| status | 含义 | UI 怎么说 |
|---|---|---|
| `deleted` | 平台删成功 + 本地也有 ⇒ 一起删了 | 「已删除 N 条（平台+本地）」 |
| `platform_only` | 平台删成功 + 本地没有 ⇒ 跳过 | 「N 条仅删平台（本地无数据，已跳过）」 |
| `failed` | 平台删除失败 ⇒ 本地未动 | 「N 条平台删除失败」+ 逐条原因弹窗 |
| `skipped` | 该类型没有可删实体 | 「N 条无可删内容（已跳过）」 |

⚠️ **四类分别计数**。把它们合并成一个 `deleted` 会让用户看不出「哪几条其实没动」。

| 对象 | 平台接口 | 说明 |
|---|---|---|

### 4.2 本地删除链

- 商品：`shop_products` 行 + **4 张外键从属表**（`generation_records` /

- 笔记：`purge_note`（项目里笔记删除链的**唯一实现**，含话题/资产/评论/关系/快照/草稿引用）

⚠️ **踩过的真 bug**：只清 `note_goods` 就删商品行会撞
`FOREIGN KEY constraint failed`（本库 `shop_metric_snapshots` 3972 行、`generation_records` 21 行）。
这条既是本功能的坑，也说明**既有的 `items/delete` 在同类数据上同样会撞**（见 §6 待办）。

## 6. 同轮一并整改的两处（2026-10-18）

按「所有平台操作均可以使用这种方式」的口径，排查后**当场修掉**两处同病的地方：

### 6.1 `shop_products_service.delete_items`（商品列表页批量删除）

**病**：只清 `note_goods` 就删 `shop_products` 本体，但 **4 张表**外键指向
`shop_products.id` ⇒ 删有指标快照的商品必撞 `FOREIGN KEY constraint failed`
（本库 `shop_metric_snapshots` 3972 行）。

**修**：按「本地实体真删 ⇒ 从属数据跟着走」先清 4 张从属表，再删本体。
实测：有 2 条快照的商品删除成功，孤儿行 0。

### 6.2 `POST /notes/batch-delete`（我的笔记批量删除，删平台分支）

**病**：两个分支都在本地无记录时**直接判失败 / continue**，**根本不打平台** ⇒
「平台有、本地没同步过」的笔记永远删不掉。

**修**：

- 本地无记录不再判失败，而是**先进平台删除分组**；
- 平台删成功 + 本地没有 ⇒ 回执 `platform_only`（跳过，不是失败）；
- 新增可选字段 `platform_account_id` —— 一批笔记本地全无记录时，
  只能靠它拿平台令牌（并用 `_owned_account` 做归属校验，不给别人的账号当令牌）。

**未改**：`delete_platform=False`（只删本地）分支，那里报「本地无此笔记」是对的 ——
它本来就不碰平台。

## 6. 回写：删除商品链路的两个真 bug（2026-10-18 实测）

### 6.1 调了适配器上不存在的方法 ⇒ 删除商品恒 500

`violation_delete_service._delete_platform_item()` 写的是
`XhsQianfanApiAdapter(cookies).batch_delete_items([item_id])`，
但**适配器上的方法叫 `remove_items`**（`batch_delete_items` 只存在于 SDK 层）。
结果：点「删除商品」→ `AttributeError` → 前端「请求失败，请稍后重试」。

为什么没被发现：单测把适配器整个 mock 掉了（假绿），`tsc` 管不到 Python。

**守卫**：`TestAdapterMethodNamesExist` 用**反射**核对服务里引用的适配器方法真的存在
（`hasattr(AdapterCls, name)`），不 mock、不猜。变异（把方法名改回错的）已验证会红。

**全项目排查**：AST + 反射扫过 `backend/app` 全部 `Adapter(...).method(` 直接调用 5 处
与变量形式调用 9 处，均存在。

### 6.2 两张「按 item_id 关联但无外键」的关系表被漏清

原实现按**外键**清从属行（`_fk_referencing` 走 `PRAGMA foreign_key_list`），
但有两张关系表**按 `item_id` 挂、却没有外键**，PRAGMA 天然查不到：

| 表 | 作用 | 实测行数 |
|---|---|---|
| `note_goods` | 内容库侧 笔记↔商品 | — |
| `shop_note_goods` | 千帆商品笔记列表的本地映射 | **1977** |

漏清的后果：商品删了，笔记页仍挂着「已下架商品」。

**修法**：`purge_local_item()` 显式清这两张表（`note_goods` 按 `(user_id, item_id)`，
`shop_note_goods` 按 `(platform_account_id, item_id)`），再按真实外键逐表清，最后删本体。

**守卫**：`TestDeleteItemAlsoClearsForeignKeylessRelations` 断言 `purge_local_item` 源码里
两张表都被清；`_fk_referencing` 只保证**真外键**。

**实测**（副本库）：`shop_products=1 / shop_note_goods=3 / note_goods=1`
→ 删除后 `0 / 0 / 0`，无孤儿。

### 6.3 排查结论表

| 检查项 | 结论 |
|---|---|
| 从属外键行 | ✅ 按 PRAGMA 实测动态清理（3 张：`shop_metric_snapshots` / `topic_goods_match` / `order_items`） |
| `note_goods` 关系行 | ✅ 显式清（按平台 `item_id`） |
| `shop_note_goods` 映射行 | ✅ 显式清（本次补） |
| 适配器方法名 | ✅ 反射守卫 + 全项目 AST 扫描 |
| 笔记删除通道 | ✅ 先普通后千帆、任一成功即止（§4.1 of 设计 45） |

## 7. 前置存在性检查（2026-10-19 追加）

### 7.1 为什么要做

平台删除接口**不做存在性校验**（2026-10-19 真机实测）：同一个商品连删 3 次，
平台每次都回 `{"code":200,"success":true,"msg":"ok"}`，即使商品早就没了。

| 次数 | 平台原始返回 | 商品是否还在 |
|---|---|---|
| 第 1 次（真删） | `success:true, data:{"failData":[]}` | 删前 78 SKU → 删后不在 |
| 第 2 次 | `success:true, data:null` | 不在 |
| 第 3 次 | `success:true, data:null` | 不在 |

后果：不先查就分不清「真删掉了」与「本来就没了」，用户连点三次会看到三次成功。

### 7.2 规则（用户口径）

> 「根据笔记或商品ID检查商品是否存在，返回详情则存在不返回则表示平台没有对应数据」
> 「查不到则不在走平台删除落，直接走本地，看本地数据是否存在，如果本地数据也不存在则提示，
>   数据已经被删除，不要重复删除，如果为批量操作则直接跳过这一条数据」

| 平台详情 | 本地 | 动作 | 回执 |
|---|---|---|---|
| 有 | 有 | 删平台 → 删本地 | `deleted` |
| 有 | 无 | 删平台 → 本地跳过 | `platform_only` |
| 无 | 有 | **不调平台删除** → 只删本地 | `deleted` |
| 无 | 无 | 什么都不做 | `absent`（「数据已经被删除，不要重复删除」） |

`absent` **不是失败**（`ok=True`），批量操作里直接跳过该条，不影响其余条目。

### 7.3 查询通路（按 ID，不翻页）

用户口径 2026-10-19：「不允许使用翻页方式，使用商品id调用」。两个接口都是**服务端按 ID 过滤**：

| 实体 | 接口 | 判据 |
|---|---|---|
| 商品 | `get_skus_by_item_ids([id])` | `data.skusMap` 里有该 ID（实测：存在 → 78 SKU；已删 → 无） |
| 笔记 | `get_goods_note_page(note_ids=[id])` | `data.note_infos` 里有该 ID（实测：命中 1 条 / 不存在 → 0 条） |

⚠️ **查询失败 ≠ 不存在**：网络抖动 / 令牌过期时返回 `(True, 原因)` 放行，
让删除步骤去报真实错误 —— 否则一次抖动会被误报成「平台没有这条数据」。

### 7.4 实测（真机）

| 场景 | 结果 |
|---|---|
| 商品 存在 | `存在=True  平台存在（14 个 SKU）` |
| 商品 已删 | `存在=False 平台查不到该商品详情` |
| 笔记 存在 | `存在=True  平台存在` |
| 笔记 不存在 | `存在=False 平台查不到该笔记详情` |
| 端到端连删 3 次（已删商品） | 全部 `absent` + 「数据已经被删除，不要重复删除」，`failed=0` |

### 7.5 守卫

`TestPrecheckBeforePlatformDelete`（5 条）：前置检查在平台删除之前 / `absent` 不是失败且不调平台 /
平台无但本地有仍清本地 / 必须按 ID 查不许翻页 / 查询失败不等于不存在。

变异 `mutate_verify_precheck.py`：前置检查失效 / `absent` 说成失败 / 平台无时仍调平台删除 /
改用翻页 —— 全部 CAUGHT。
