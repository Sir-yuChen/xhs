# 52 · 部署架构 · 服务器为主，桌面端退场

> 上游：`50_技术方案` · `51_数据库方言兼容`
> 用户口径（2026-10-23，连续三条）：
> ① 「后期可能切换成 pg 数据库，所有你要兼容无缝衔接到 pg 数据库」
> ② 「应该是**以 pg 为主，sqlite 为辅**」

# 零、定位（最终）

```
         ┌──────────────────────────────────────────────┐
         │  ▲ 正式形态：Linux 服务器（多用户 Web 服务）    │
         │     PostgreSQL  ·  uvicorn/gunicorn  ·  Nginx  │
         └──────────────────────────────────────────────┘
                            ▲
         ┌──────────────────┴───────────────────┐
         │  试运行 / 开发：单机 SQLite（辅助）     │
         │   win/linux 都能跑，数据可迁到 PG       │
         └──────────────────────────────────────┘
                            ✗
         ┌──────────────────────────────────────┐
         │  桌面端（pywebview 内核 + tkinter +    │
         │  安装包 + 登录自启）—— **退场**        │
         └──────────────────────────────────────┘
```

| 维度 | 改造前（现状） | 改造后（目标） |
|---|---|---|
| 主形态 | Windows 桌面 exe（`run-app.py` + 内核窗口） | **Linux 服务器 + 浏览器访问** |
| 数据库 | SQLite 单文件 | **PostgreSQL**（SQLite 保留为单机/试用） |
| 用户 | 1 台机器上的少数人，`users` 里有 24 条测试残留 | **真实多用户**，`status` / `deleted_at` / 审核流必须有 |
| 定时任务 | 进程内 APScheduler + 文件租约（单机） | 进程内 APScheduler，**多副本需 DB 锁**（§三） |
| 部署产物 | `spider-xhs-setup-*.exe`（80MB） | **Docker 镜像 / systemd 服务** |
| 前端 | `vite build` → 8000 静态托管 | 同（Nginx 或 8000 托管二选一） |

**一句话**：这次 v1.1.0 的**权限骨架**恰好就是服务器化的前置条件 ——
没有 `status`（待审/停用）、没有 `deleted_at`（软删）、没有角色权限，多用户部署根本不成立。

# 一、服务端部署必须改的清单

## 1.1 🔴 安全面（不改进不了生产）

| # | 现状 | 问题 | 改法 |
|---|---|---|---|
| **S1** | `secret_key: str = "dev-only-change-me"` | **服务器上若忘改 ⇒ 任何人可伪造 JWT** | 启动自检：非 sqlite 模式下 `secret_key` 仍是默认值 ⇒ **拒绝启动**（不是警告） |
| **S2** | CORS 默认 `127.0.0.1:5173` | 服务器上前后端同源即可；但开放域名时会漏配 | `backend_cors_origins` 走环境变量；**默认不放开 `*`** |
| **S3** | 无 HTTPS / 反代配置 | 明文传密码与令牌 | Nginx 终止 TLS；uvicorn 只监听 `127.0.0.1` |
| **S4** | 无登录失败锁定（现有按用户名限流） | 分布式撞库 | 保留现有；补 IP 维度限流（中间件） |
| **S5** | `api_logs` 写库无上限 | 服务器长期跑会无限膨胀 | 定期清理任务（已有清理框架） |

```python
# core/config.py :: model_post_init 或 main.lifespan
if not is_sqlite() and self.secret_key in ("dev-only-change-me", "", "change-me"):
    raise RuntimeError("生产环境（非 SQLite）必须设置 SECRET_KEY，拒绝以默认密钥启动")
```

## 1.2 🔴 桌面端专属代码（服务器上会崩或卡死）

| # | 文件 | 现状 | 处理 |
|---|---|---|---|
| **D1** | `api/platforms/xhs/package_precheck.py:97-190` | **`tkinter` + PowerShell `FolderBrowserDialog`** 弹原生文件夹选择框 | **移除**。服务器无桌面会话 ⇒ tkinter 直接抛 `TclError`；PowerShell 在 Linux 不存在。改为「前端上传」，不让服务器打开本机文件对话框 |
| **D2** | `services/env_bootstrap_service.py`（917 行） | 首次启动下载 webview 内核 / OCR 模型 / node | 服务器上**不需要 webview 内核**（这是桌面窗口用的）。保留 OCR 模型与 ffmpeg 下载（真需要），删掉 window_host 相关分支 |
| **D3** | `.hermes/scripts/run-app.py` + `window_host` | 桌面窗口启动器 | 服务器用 `uvicorn app.main:app` 或 gunicorn；脚本保留但**不再是主入口** |
| **D4** | `packaging/*.ps1`（build / release / smoke） | Windows 安装包流水线 | 保留（若仍要发 Windows 单机版），但**不再是发布主路径**；主路径换成 Docker |
| **D5** | `core/singleton.py` 文件租约 | 单机防重复调度 | 服务器**多副本**时文件租约失效（各容器自己的文件系统）⇒ 见 §三 |

> ⚠️ **D1 是硬伤**：`package_precheck` 是商品发布的核心前置步骤。服务器部署后如果还保留
> 「弹本机文件夹选择框」，用户点「加载数据包」时服务器会**卡住或 500**。这条必须在 S1 之前处理。

## 1.3 🟡 存储与路径

| # | 现状 | 问题 | 改法 |
|---|---|---|---|
| **P1** | `backend/app/storage/media`、`exports` 本地目录 | 服务器重启/换机器就丢 | 挂卷（docker-compose 已挂）；长期建议对象存储（**本期不做**，只把路径收敛到 `settings.storage_dir`） |
| **P2** | SQLite 文件在 `./data/` | PG 后不再需要，但**试用模式仍用** | 保留；`data/` 目录只服务 SQLite 模式 |
| **P3** | `logs/` 相对 CWD | systemd 下 CWD 不同 ⇒ 日志找不到 | 日志路径改 `settings` 绝对路径 |

## 1.4 🟡 多用户语义（本次权限骨架已经在做）

| 项 | 状态 |
|---|---|
| 用户状态机（`normal`/`pending`/`disabled`） | ✅ S1 新增 |
| 软删（`deleted_at`） | ✅ S1 新增（B9 定稿） |

# 二、与 `51` 的衔接（数据库）

`51` 已经定了 **PG 主 / SQLite 辅**，服务器化之后这个结论**更硬**：

| 场景 | 数据库 |
|---|---|
| 正式部署（用户口径的「服务器」） | **PostgreSQL 必须** |
| 本地开发 / 演示 / 单机试用 | SQLite 可接受 |

**新增一条判据**（补进 51 §六）：
| # | 判据 | 说明 |
|---|---|---|
| **D9** | **CI 全量回归跑在 PG 上** | SQLite 只跑冒烟子集。理由：正式形态是 PG，测试主环境必须与生产同方言 |

> ⚠️ 这也解决了 51 §七 里「多实例共享权限缓存」那条：**服务器多副本时，进程内权限缓存会不一致**（A 副本改了角色，B 副本还拿旧缓存 60s）。
> 本期不解决（默认单副本部署），但**必须写进部署文档**：`permission_cache` 的多副本限制 = 60s 内可能读到旧权限。

# 三、定时任务的多副本问题（服务器化后真实存在）

**现状**：`core/singleton.py` 用**本地文件租约 + PID 探针**防重复调度。
**服务器上**：
- 单容器 / systemd 单实例 ⇒ ✅ 仍然有效
- `docker-compose --scale app=2` 或 K8s 多副本 ⇒ ❌ **每个容器自己一个文件系统，租约互不可见 ⇒ 重复调度 ⇒ 重复发文**

**三种解法与选择**

| 方案 | 做法 | 评价 |
|---|---|---|
| A | **明确约束单副本**（部署文档写死 `replicas: 1`） | ✅ **本期采用**。定时任务与 Web 请求是同一进程，扩副本本来就要拆进程，属架构级改动 |
| B | PG advisory lock（`pg_try_advisory_lock`） | 中期最优；PG 已就位后成本不高 |
| C | 独立调度进程（`--workers 1` 的专用容器） | 与 A 等价但更清晰 |

**本期定 A，但代码留好口子**：把 `acquire_scheduler_lease()` 抽成策略接口
```python
# core/singleton.py
def acquire_scheduler_lease(...): ...     # 现有文件租约（SQLite / 单机）
def acquire_pg_advisory_lease(...): ...   # 预留：PG advisory lock（多副本）
```
由 `is_postgres()` 决定用哪个 —— **现在只实现前者，后者留 `NotImplementedError` + 明确报错**（不静默降级）。

# 四、部署产物变化

## 4.1 主路径：Docker（已有基础，需补强）

现有 `Dockerfile` + `docker-compose.yml` 已经在仓库里，但**没有 PG 服务**，且依赖 SQLite 挂卷。需要：

```yaml
# docker-compose.yml（改造后）
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: spider_xhs
      POSTGRES_USER: xhs
      POSTGRES_PASSWORD: ${PG_PASSWORD:?required}
      TZ: Asia/Shanghai
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: {test: ["CMD-SHELL", "pg_isready -U xhs"], interval: 5s, retries: 10}

  app:
    build: .
    depends_on:
      db: {condition: service_healthy}
    environment:
      DATABASE_TYPE: postgres
      SECRET_KEY: ${SECRET_KEY:?required}       # ← 不设就起不来（呼应 S1）
      CONFIG_FILE: /app/config/default.yaml
    ports: ["127.0.0.1:8000:8000"]              # ← 只回环，由 Nginx 反代
    volumes: [./data:/app/data, ./config:/app/config]
    restart: unless-stopped

  nginx:
    image: nginx:alpine
    depends_on: [app]
    ports: ["443:443", "80:80"]
    volumes: [./deploy/nginx.conf:/etc/nginx/conf.d/default.conf:ro, ./deploy/certs:/etc/nginx/certs:ro]
```

## 4.2 次路径：systemd（不用容器时）

```ini
# deploy/spider-xhs.service
[Unit]
Description=Spider XHS
After=network.target postgresql.service

[Service]
Type=simple
User=xhs
WorkingDirectory=/opt/spider-xhs
EnvironmentFile=/etc/spider-xhs/env
ExecStart=/opt/spider-xhs/.venv/bin/uvicorn backend.app.main:app \
          --host 127.0.0.1 --port 8000 --workers 1
Restart=always

[Install]
WantedBy=multi-user.target
```
> `--workers 1` 不是性能妥协，是**定时任务单实例约束**（§三 A）。

## 4.3 桌面端：退场但不立即删除

用户口径「桌面端不再使用」，但**删除要分步**（避免一次性删掉还在用的代码导致回归）：

| 阶段 | 动作 |

| 本期 | ① 移除 `package_precheck` 的 tkinter/PowerShell 分支（D1，硬伤必改）② `env_bootstrap_service` 的 window_host 分支标废弃 ③ 部署文档改以 Docker 为主 |
| 下期 | 删 `run-app.py` / `window_host` / `packaging/` 整条流水线；删 917 行 `env_bootstrap_service` 中桌面专属部分 |
| 保留 | `SpiderXHS.spec` 暂留（若要发 Windows 单机版还能用），加注释「非主路径」 |

# 六、服务器部署冒烟清单（8 项）

| # | 检查 | 判据 |
|---|---|---|
| 1 | 容器能起 | `docker compose up -d` 后 app 处于 `healthy`，不是重启循环 |
| 2 | secret_key 守卫生效 | 故意不设 `SECRET_KEY` ⇒ 容器**启动失败并打印原因**（不是静默用默认值） |
| 3 | 数据库连的是 PG | `/api/health` 返回 `dialect: postgresql`（需补该字段） |
| 4 | 迁移跑过 | 表数 = 67；`alembic_version` 有值 |
| 5 | 登录闭环 | admin 首登 ⇒ 强制改密弹窗（`must_change_password=1`） |
| 6 | 权限闭环 | 用 user 身份访问 `/system/users` ⇒ 侧栏无该菜单 + 直敲 URL 得 403 |
| 7 | 数据包加载 | **不再弹服务器本机文件夹选择框**（D1 已改）⇒ 前端上传后能预检 |
| 8 | 定时任务单实例 | 起第二个 app 容器 ⇒ 第二个在日志里明确说「已有实例在跑调度器」（不是静默重复调度） |

# 七、明确不做的

| 项 | 为什么 |
|---|---|
| K8s / 多副本横向扩容 | 定时任务是同进程单实例架构（§三），要多副本必须先把调度拆出去 —— 独立议题 |
| 对象存储（S3/MinIO） | 媒体文件先挂卷；上云确定后再做（本项目已有「素材扫描服务存储抽象」的待办） |
| Redis 共享权限缓存 | 单副本部署下进程内缓存够用；多副本时再说 |
| 现在就删干净桌面端代码 | 「不再使用」≠「今天就删」。先移除会崩的（D1），其余分两期 |
| 把 SQLite 完全删掉 | 它是**试用/开发形态**，服务器化的开发环境也需要一个零依赖的启动方式 |

# 八、给用户的一句话结论

**这次 v1.1.0 从「给桌面版加权限」变成「服务器多用户服务的地基」** —— 内容上几乎不变（用户/角色/菜单/字典/配置/日志 + 161 权限码），
但**多了三件事**：① PG 是主库，② 桌面专属代码必须移除（尤指 `package_precheck` 的原生文件夹对话框），③ 部署产物从 exe 换成 Docker + Nginx。
数据库与部署这两块合计增加 **4 人日**。
