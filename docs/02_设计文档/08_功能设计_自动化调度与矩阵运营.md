## 1. 调度器设计

### 1.1 四个 job

> ⚠️ **2026-09-24 本节被 `15` §4.4 / §6.1 取代**：硬编码注册表改为 **DB 驱动**（`scheduled_jobs` 行 ⇒ 启动时注册，`auto_tasks_runner` 取消），系统 job 从 4 个变为 7 个播种行（+`qianfan_health_checker` / `no_traffic_cleanup_runner` / `note_sync_runner` / `shop_goods_sync_runner` 四个后续新增的也一视同仁）。原句保留备查：

| Job ID | 频率 | 作用 | 关键约束 |
|---|---|---|---|
| `due_publish_runner` | `scheduler.interval_seconds`（默认 60s） | 补跑到期的定时发布任务 | `max_instances=1`, `coalesce=True` |
| `monitoring_refresh_runner` | 同 interval | 刷新所有 active 监控目标快照 | 同上 |
| `auto_tasks_runner` | **60s**（固定） | 自动运营管线 | 同上 |
| `cookie_health_checker` | **2h**（固定） | 全量账号 Cookie 巡检，新过期发通知 | 同上 |

**实现**：`backend/app/services/scheduler_service.py:699-737` `build_due_publish_scheduler()`
**生命周期**：随 FastAPI `lifespan` 启动/关闭（`backend/app/main.py:18-29`）
**总开关**：`scheduler.enabled`，~~默认 `false`~~ **R24（2026-09-24）起默认 `true`**
（关闭则上述全部静默不生效）。
> ⚠️ **被 R24 取代**：原默认值 `false` 导致「装完什么都不跑、用户还不知道为什么」；
> 现改为默认启用（用户口径：「改为默认启用」）。**总开关只决定调度器起不起来**，
> 每个任务跑不跑看 `scheduled_jobs.status`（任务中心可逐条暂停/恢复）—— 两件事别混，
> 详见 `15_功能设计_定时任务中心.md` §4.5。

### 1.2 设计的三个要点

| 要点 | 说明 |
|---|---|
| **单实例约束** | `max_instances=1` 防止同一 job 在单进程内堆叠；`coalesce=True` 让错过的执行合并为一次 |
| **⚠️ 调度器时区是 UTC** | ~~`BackgroundScheduler(timezone="UTC")`（`:700`）——与业务时区（东八区）不同，job 内做时间比较需自行转换~~ **2026-09-24 被 `15` §6.6 取代：调度器改 `Asia/Shanghai`**（修 S-4），触发器求值与 `shanghai_now()` 统一东八区 |
| **⚠️ 多副本不安全** | 调度器与 FastAPI 同进程 → **每个副本各起一套定时器** → 定时发布会重复执行。`max_instances=1` 只约束单进程内。**目前没有分布式锁** |

**入口**：`run_due_auto_tasks()`（`scheduler_service.py:604`），job 名 `auto_tasks_runner`，每 60s 一次。

```
┌─ 扫描 auto_tasks ──────────────────────────────────────┐
│ 条件：status == "active"                                │
│   且   schedule_type != "manual"                        │
│   且   next_run_at <= now                               │
└────────────────────────┬───────────────────────────────┘
                         ▼
① 随机挑一个关键词（keywords 数组）
                         ▼
② PC 账号搜索      ← 复用采集链路
                         ▼
③ 按互动总量选最优笔记
                         ▼
④ 建草稿 ai_drafts
                         ▼
⑤ AI 改写标题 + 正文   ← 非致命，失败也继续
                         ▼
⑥ Creator 账号上传图片素材  ← 复用发布链路
                         ▼
⑦ 建 publish_job 并直接发布
                         ▼
⑧ 无论成败都重算 next_run_at   ⚠️ 在执行之后计算
```

### 2.1 调度类型

> ⚠️ **2026-09-24 被 `15` §4.3 / §7.1 取代**：四档枚举从 `auto_tasks` 表与 API 移除，统一为 `scheduled_jobs` 的 cron/interval 触发器；`manual` 由 job 行 `status=paused` 表达。原句保留备查：

| `schedule_type` | 行为 |
|---|---|
| `manual` | 不自动执行，只支持手动「立即执行」 |
| `daily` | 每天 `schedule_time` 执行 |
| `weekly` | 每周 `schedule_days` 的 `schedule_time` 执行 |
| `interval` | 每 `schedule_interval_hours` 小时执行 |

### 2.2 已知缺陷

| # | 问题 | 影响 |
|---|---|---|
| 1 | `next_run_at` 在**执行之后**计算 | 实际周期 = 设定间隔 + 执行耗时（漂移累积） |
| 2 | 失败无退避 | 账号失效时会每 60s 重试一次，产生通知风暴 |
| 3 | 无每日上限 / 无冷却 | 见 §5 编排约束 |

## 3. 账号矩阵模型（二开核心设计）

### 3.1 两个正交维度

这是本项目最重要的模型判断，二开必须理解。

```
sub_type   ∈ {pc, creator}      ← 只表达【协议链路】
                                   决定 adapter / 域名 / cookie 域
                                   不表达任何业务含义

shop_count ∈ {0, 1, ..N}        ← 【业务维度】
                                   由 platform_accounts.shop_id_fk 是否为 NULL 推导
                                   （2026-09-22 起；原为 shop_account_bindings 的存在性）
                                   不是字段、不落库
```

**「非店铺账号」= `creator` 且 `shop_count = 0`。**

### 3.2 全域组合矩阵

| | `shop_count = 0` | `shop_count ≥ 1` |
|---|---|---|
| **`sub_type = pc`** | 采集 / 巡检专用号（现状主力） | 少见 |
| **`sub_type = creator`** | **非店铺账号** | 店铺账号（发布端） |

### 3.3 为什么「有没有店铺」不能做成 `sub_type` 的第四个值

| # | 代价 | 说明 |
|---|---|---|
| 1 | **映射是猜测** | creator 账号既可能有店也可能没店，`sub_type` 无法表达「creator 且无店」 |
| 2 | **无限扩展** | 还要区分「个人店账号」「企业子账号」……每加一种重付一次 |
| 3 | **改绑即改路由** | `_select_adapter`（`api/accounts.py:57-58`）是 `creator → creator_adapter`，**否则一律 pc_adapter**。用户今天开店明天关店 → 登录适配器跟着变 → **登录态立刻失效** |
| 4 | **状态与事实不同源** | `sub_type` 是静态字段，「有没有店铺」是平台侧事实。店铺被关停、子账号被移除绑定时，系统会拿过期字段当真，且无机制发现 |

### 3.4 一个让人省心的事实

> **现有代码里从来不存在「账号必须绑店铺」的校验。**
>
> 全量 grep 确认：13 处 creator 守卫（`api/platforms/xhs/creator.py:79`、`api/publish.py:415/453`、`scheduler_service.py:124` 等）**全部只看 `sub_type`**。

**结论：非店铺账号一直是合法、可用的，普通笔记发布零改动。二开是把既有能力显性化，不是新建一套机制。**

## 4. 能力驱动设计（二开核心原则）

### 4.1 反模式与正模式

**反模式**（❌ 禁止）：

```python
if shop.shop_type == "personal":
    can_attach_goods = False          # ← 这个假设可能是错的
elif shop.shop_type == "enterprise":
    can_attach_goods = True
```

**代价**：① 类型→能力的映射**目前是猜的**（外部资料在「个人店能否挂商品」上直接矛盾）；② 错误会扩散到发布校验、前端渲染、任务调度、错误提示**至少 4 处**；③ 平台还有旗舰店/专卖店/买手店，每新增一种都要重付一次。

**正模式**（✅）：

```
店铺（运行时探测）
   ├─ shop_type      → 仅用于展示与探测失败的兜底默认
   └─ capabilities   → 驱动一切逻辑分支
          ├─ can_attach_goods
          ├─ can_publish_note
          ├─ categories[]
          ├─ requires_deposit_before_listing
          └─ supports_sub_account
```

> **代码只读 `capabilities`，永不读 `shop_type` 来决定行为。**
> 这样三种店铺天然支持，且未来出现第四第五种类型，**代码零改动**。

### 4.2 能力解析的唯一入口

```python
def resolve_capabilities(account, shop=None) -> Caps:
    """
    shop=None  → 账号级基础能力（不涉及挂商品）
    shop=S     → 先查 binding(account, S)，再合并 S.capabilities_json
    """
```

**为什么签名是二元输入**：子账号权限可能细到「能看到店铺但无权发笔记」，所以作用域是「**账号 × 店铺**」而非单侧。

**解析顺序**（短路，任一步失败即返回保守默认）：

```
1. binding 是否存在？否 → can_attach_goods=False（非店铺账号走这条）
2. 该 binding 是否有账号级限制？
3. 合并 shop.capabilities_json
4. capabilities_verified_at 是否过期（>7 天）？过期先重探
```

**账号级基础能力**（两种形态共有）：

| 能力 | 说明 |
|---|---|
| `can_publish_note` | creator 链路天然具备 |
| `can_browse_goods` | 只读，无绑定要求 |
| `has_shop` / `shop_count` | **派生字段，建议 API 返回但不落库**——落库就变成需要同步的状态 |

### 4.3 探测失败的降级

**不能「当作支持」，也不能「直接失败」**，而是取保守默认 + 显式标记：

```python
CONSERVATIVE_DEFAULTS = {
    "can_attach_goods": False,
    "can_publish_note": False,
    "categories": [],
    "requires_deposit_before_listing": True,
    "supports_sub_account": False,
    "shop_type": "unknown",
}
```

同时置 `capabilities_verified_at = NULL`，前端显示「能力未验证」，**只开放只读功能**（浏览商品、生成草稿），**不开放发布**。

> **效果：系统在信息不全时既不会误发，也不会死锁。**

**探测时机**：绑定店铺时 / 手动触发 / 定时巡检（复用 2h job）/ 发布前有效期检查（>7 天重探）。

### 4.4 探测失败的兜底原则总结

| 情况 | 处理 |
|---|---|
| 探测成功 | 用真实能力 |
| 探测失败 | 保守默认 + `capabilities_verified_at=NULL` + 只读 |
| 探测结果过期 | 先重探；重探失败 → 保守默认 |
| 人工确认真实能力 | 允许手动覆盖，来源标记为 `manual`（保留 `raw_json` 证据链） |

### 4.5 前端原则：置灰 + 说明原因，不要隐藏

三种店铺共存时，用户需要理解「为什么这家不能挂商品」，隐藏起来只会被当成 bug 报过来。

```
店铺卡片
  个人店    [可挂商品 ✗ 未验证]
  个体户店  [可挂商品 ✓]
  企业店    [可挂商品 ✓] [待缴保证金]
```

## 5. 矩阵分发（二开新增能力）

### 5.1 最重要的推论：发布端与商品来源端解耦

原设计隐含假设「商品来源账号 = 发布账号」。非店铺账号打破了这个假设：

```
商品库（店铺账号 A 同步）
      │
      ├─→ 挂链商品笔记  →  发布账号必须是「绑定该店铺 + can_attach_goods」的账号
      │                    账号池 1–3 个，受店铺数限制（一执照最多 3 店）
      │
      └─→ 不挂链种草笔记 →  发布账号可以是任意 creator 账号
                           非店铺账号在此，池子可数十个
```

> **因此「降级路径」需要重新定性**：它不是「无挂商品能力时的异常兜底」，而是**独立的业务模式**。

### 5.2 由此产生的新业务能力

> **同一商品 × 多账号矩阵分发**：店铺号挂链发布 1 篇，N 个内容号各发 1 篇不挂链种草笔记。

**这也是非店铺账号值得单独立项的理由**：

> **店铺账号的数量被平台（一执照最多 3 店）天然锁死，内容号不受限。**

### 5.3 矩阵分发的编排约束

| 约束 | 理由 |
|---|---|
| **单账号串行** | 并发发布 = 重复发布 + 风控 |
| **内容必须按账号变异** | 多账号发同款内容会触发去重降权；模板必须按账号维度变异（标题结构、图片版式扰动） |
| **不做跨账号同文分发** | 同上，明确禁止 |
| **账号分池** | 挂链池（受店铺数限制）与种草池（可数十个）分开调度 |
| **每日上限按账号计** | 不是按商品或按任务计 |

## 6. 监控巡检（复用模式）

```
scheduler.monitoring_refresh_runner
  → 取 status=active 的 monitoring_targets
  → 用 status=active 的账号抓取
  → 写 monitoring_snapshots
  → 失败累计 consecutive_failures，≥3 → status=paused + 通知
```

**二开可参照点**：店铺/商品同步可以走**同一套模式**（复用调度器 + 失败计数 + 通知），不需要新机制。
