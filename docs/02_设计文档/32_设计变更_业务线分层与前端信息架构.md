## §1 一句话

两条业务线「千帆商家店铺」与「非店铺内容号」在全仓**既没有名字、也没有边界**；
本设计新增**一层显式的「业务线」**（**能力派生、不落库、不新增 `sub_type`**），
并据此重组前端信息架构（侧栏 3 组 + 每页业务线徽标 + 每线一个账号范围条），
**不动数据模型、不动路由契约、不动既有页面拆分**。

## §3 市场对标（2026-10-11 调研）

| 层次 | 市场做法 | 出处 |
|---|---|---|
| 业务 / 品牌隔离 | **Workspace per brand**：资产、审批、权限、分析各自隔离 | Planable（per-workspace 审批 4 级）；Emelyn（「Make context visible」）；Quetzal（independent brand workspaces） |
| 账号归属 | workspace 分组装 connected accounts，**隔离由 API key 强制**，不靠调用方传对 ID | Postproxy：*「The isolation is enforced at the API level, not by hoping that the caller passes the right group ID」* |
| 小红书平台自身 | 三账号形态：**个人号 / 专业号 / 店铺**；个人专业号可关联 **4** 个账号带货 | 腾讯云 2025 新规；千帆 = 商家后台 |
| 小红书运营侧 | 矩阵分层：**品牌号 / 个人号 / 素人号** | Hashmeta |

**两条市场共识，本项目都缺**：

1. 隔离边界要**显式命名 + 结构承载**，不靠约定；
2. 「资产型账号」数量被平台锁死（一执照最多 3 店），「内容型账号」可数十个
   —— **这正是分线的业务根据**（`docs/02_设计文档/08` §5.1 已写对，但没落成结构）。

## §4 命名轴决策：业务线 = **能力派生**，不新增 `sub_type`

### §4.1 三层归属图

```
平台          xhs                                （已有 platform 列）
 └ 业务线     店铺线 / 内容线                      ← 本设计新增这一层（纯派生，不落库）
    └ 账号     platform_accounts                  （已有，隔离键不变）
       └ 数据  notes / shop_products / note_goods  （已有，键不变）
```

### §4.2 判据表（唯一实现：`backend/app/core/business_lines.py`）

| 业务线 | 常量 | 判据（**能力**，不是类型） |
|---|---|---|
| 店铺线 | `BUSINESS_LINE_SHOP = "shop"` | `has_ark_session(db, account_id)` —— ark 通道有令牌 |
| 内容线 | `BUSINESS_LINE_CONTENT = "content"` | `has_creator_session(db, account_id)` —— creator 通道有令牌 |
| 平台 | `BUSINESS_LINE_SHARED = "shared"` | 与两条线无业务绑定（采集 / 监控 / 内容库 / 网关） |

**一个账号可以是两条线都占**（账号 8「观隅好物的店」= `creator` + 有 `seller_id` + 有商品台账）。
⇒ `business_lines_of()` 返回**集合**，不是单选枚举。

### §4.3 为什么**不**把业务线做成 `sub_type` 的第三个取值

`docs/02_设计文档/08` §3.3 已列四条代价，此处**继续沿用**（不重复论证）：

| # | 代价 |
|---|---|
| 1 | 映射是猜测（`creator` 账号既可能有店也可能没店） |
| 2 | 无限扩展（个人店 / 企业子账号 / …每加一种重付一次） |
| 3 | **改绑即改路由**（`_select_adapter` 按 `sub_type` 选 adapter ⇒ 用户今天开店明天关店 → 登录态立刻失效） |
| 4 | 状态与事实不同源（`sub_type` 是静态字段，「有没有店铺」是平台侧事实） |

**ADR-009 已否决**，本设计不推翻它。

### §4.4 明确禁止

* ❌ 用 `sub_type` 判断业务线；
* ❌ 用 `seller_id IS NULL` 判断能力（账号 9 的 Bug 正是把**归属判据**当**能力判据**用，
  见 `backend/app/models/platform_account.py:89-92` 的告警）；
* ❌ 把业务线落成数据库列（落库就变成需要同步的状态，与「能力派生」自相矛盾）。

业务线账号范围。

**硬约束**：17 个菜单项一个不删、路由一条不改（改渲染结构，不改路由表）；
`selectedKeys` 判据不变（仍取 `location.pathname`）。

⚠️ **待实测确认**：`Sider` 折叠态（64px）下 `SubMenu` 只剩图标，分组语义会丢。

### §5.2 每页业务线徽标

| 页面 | 徽标 |
|---|---|
| 商品列表 / 图片空间 / 订单管理 | 店铺线 · 千帆令牌 |
| 笔记发现 / 我的笔记 / 内容库 / 笔记工坊 | 内容线 · 创作者令牌 |
| 账号管理 / 数据洞察 / 监控中心 / 自动运营 | 工作区一级 · 跨线 |

依据：市场共识「让上下文在选择时可见，不靠记忆」。

### §5.3 未登录：灰显 + 说明原因（**不隐藏**）

沿用 `docs/02_设计文档/08` §4.5 —— *「三种店铺共存时，用户需要理解『为什么这家不能挂商品』，
隐藏起来只会被当成 bug 报过来」*。

| 场景 | 行为 |
|---|---|
| 店铺线页面 ark 不可用 | 灰显 + 「请先在账号信息卡片中扫码登录千帆后再来查看」 |
| 内容线页面 creator 不可用 | 灰显 + 对应补登文案 |

⚠️ 未登录时**零平台请求**（复用商品列表页既有范式，设计 13 §33 v1.33）。

### §5.4 统一账号范围条（取代 3 份独立 `accountId`）

现状（实测 `frontend/src/lib/filter-cache.ts`）：

```
FILTER_CACHE_KEYS.library.accountId   = "xhs.filters.library.account-id"
FILTER_CACHE_KEYS.myNotes.accountId   = "xhs.filters.my-notes.account-id"
FILTER_CACHE_KEYS.shopItems.accountId = "xhs.filters.shop-items.account-id"
```

且 `app/providers.tsx` 里**只有主题 context**（`createContext` × 1），无任何全局账号上下文
⇒ 用户在内容库选了账号 A、切到我的笔记仍是账号 B，这是「选错账号」类事故的**结构性来源**。

**改为**：每个业务线**一个**「当前账号范围」上下文

```
{ content: number | null, shop: number | null }
```

**迁移纪律**：旧键保留为**一次性迁移源**（首次读不到新键时从旧键迁入、然后清旧键）
—— 否则老用户已选中的账号会被静默重置。

### ⚠️ 为什么**本轮没有执行**这个拆分（如实记录，不静默跳过）

实测发现拆分有一个**静默失效**风险，不是体力活：

1. **测试对模块属性做 monkeypatch**（`grep` 实测 3 处）：
   * `test_picture_space.py:744` → `monkeypatch.setattr(qmod, "_ark_adapter_for", …)`
   * `test_picture_space_upload_batch.py:112` → `monkeypatch.setattr(qianfan, "_ark_adapter_for", …)`
   * `test_product_edit.py:337` → `monkeypatch.setattr(qf, "MAX_EXPORT_ROWS", 1)`

   拆包后代码从**子模块**读这些名字，而补丁打在**包**上 ⇒ 补丁**静默失效**
   （`raising=False` 更会让它连报错都没有），测试要么打真实平台、要么以完全
   误导的方式失败。这正是本项目记过的「worker 的 Session 工厂必须用模块级
   `SessionLocal`」同一类事故。
2. **私有名跨模块 import**：`product_notes.py` 直接 import `qianfan._owned_account`。
3. `__init__.py` 若 re-export 全部名字，**行数不会减少**（6057 → 6057 + 4 个
   子模块），只有「一个文件一个域」的可读性收益，而静态扫描（`verify_doc_counts.py`
   的端点计数）依赖的是路由注册点而非文件行数 —— 收益与风险不成比例。

⇒ **处置**：本条**顺延到独立卡片**（见 `A6b`），并把上面三条风险写成卡片正文。
