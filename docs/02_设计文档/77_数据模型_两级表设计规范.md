# 77 · 表的两级设计规范（系统骨架 vs 工作区私有）

> **用户口径（2026-10-28）**：「表应分为两级设计规范 —— 项目系统级公共的是项目的结构骨架；
> 工作区域私有，应改工作区前缀，私有与其他工作区不通用。比如系统账号表菜单权限表均为骨架，
> 但小红书账号表则应为小红书工作区私有表。」+「目前表分散过多……分析合并为一张表，一张表解决问题」
>
> 本文档是**判据的唯一真相源**。新增任何表前先按 §2 定级，定不了级就不许建。

**配套预览**：`77_预览_当前全库表结构.html`（**当前真实库结构，45 张表全字段 + 表关系 + 定级**，由 `.hermes/scripts/gen_current_schema.py` 从 PG 元数据直出）、`77_预览_全库两级重构方案.html`（定级判据与合并决策的推演过程，含已否决项）

---

## 1. 两级定义

| 级别 | 定义 | 前缀 | 跨平台复用 |
|---|---|---|---|
| **L0 系统骨架** | 整个项目公共的结构，与「接入了哪个平台」无关 | 无前缀 | ✅ 换平台照用，结构不改 |
| **L1 工作区私有** | 只服务某一个平台工作区，其他工作区的数据与它不通用 | `xhs_` / `douyin_` / … | ❌ 其他工作区不读、不写、不 join |

## 2. 定级判据（四条，可机械执行）

### 2.1 L1 判据 —— 满足**任一**即 L1

| # | 判据 | 机械来源 | 说明 |
|---|---|---|---|
| **C1** | 表名含平台词 | `pg_class.relname` | `note` / `topic` / `shop` / `qianfan` / `creator` / `ark` / `forbidden` / `keyword` |
| **C2** | `platform` 列 **NOT NULL** | `is_nullable='NO'` | 平台是**隔离维度**，本表按平台分区存数据 |
| **C3** | 有平台专有列 | `pg_attribute` | `sub_type` / `external_user_id` / `seller_id` / `shop_state` / `xsec_token` / `item_id` / `note_flag` / `goods_infos` … |
| **C4** | 所有 FK 父表都是 L1，且自身无跨平台语义 | FK 图 | **2026-10-28 补**：C1–C3 漏掉了「表名不带平台词、自身无 platform 列、但只服务平台表」的子表 |

### 2.2 L0 判据 —— **三条全满足**

| # | 判据 |
|---|---|
| **S1** | `platform` 列**可空或不存在** —— 平台只是日志/审计标签，不是隔离维度 |
| **S2** | 表名不含任何平台词 |
| **S3** | 换一个平台接入，这张表的**结构**不需要改（可能多几行数据，但不加列、不改语义） |

### 2.3 三个实测陷阱（写下来防止再判错）

| 陷阱 | 实例 | 正确处理 |
|---|---|---|
| **C2 反向误判** | `tasks.platform` 是 NOT NULL，但它是「这个任务跑哪个平台」的**派发标签**，任务结构跨平台一致（`indeg=5` 是全局任务底座） | 被 **S3 覆盖** ⇒ L0 |
| **C4 漏判** | `account_cookie_versions` / `publish_assets` / `no_traffic_cleanup_logs` 表名无平台词、自身无 platform 列，但只服务 L1 父表 | 判 L0 是错的 ⇒ **补 C4** |
| **可空 ≠ 无关** | `api_logs.platform` 可空 = 日志标签 ⇒ L0；`notes.platform` NOT NULL = 隔离维度 ⇒ L1 | 看 `is_nullable`，不看有没有这列 |

### 2.4 定级流程（30 秒）

```
① 表名含平台词？                              → 是 → L1
② platform 列 NOT NULL？                      → 是 → 看 S3：结构跨平台一致？否 → L1
③ 有平台专有列？                              → 是 → L1
④ 所有 FK 父表都是 L1？                        → 是 → L1
⑤ 以上都否                                    → L0
```

## 4. 合并判据（用户口径「一张表解决问题」）

### 4.1 判据：**结构语义**，不是行数

| 决策 | 判据 |
|---|---|
| **合并** | 父行**恒**对应 ≤1 子行，**且**从属表无独立主键语义、无独立 CRUD 端点 |
| **保留分表** | 父行对应 N 行且 N 可能几十上百；或子行有独立资源语义 / 独立端点 / 时间序列 |
| **❌ 不能用的错误判据** | 「全库行数 ≤1」—— 业务没用起来 ≠ 结构恒 1:1。实例：`publish_jobs` 全库仅 1 行，但一个账号可发 N 篇；`auto_tasks` / `monitoring_targets` 都是 0 行，但它们有双账号外键 / 独立调度，不能并进账号表 |

### 4.2 本轮合并 8 张（48 → 40）

| `login_sessions` | `xhs_accounts` | 226 | — | **表删除**：扫码态走内存，只把 confirmed 的时间/方式写进账号表 |

## 5. 命名规则

| 规则 | 说明 |
|---|---|
| **R1** | L1 表名必须带工作区前缀：`xhs_` / `douyin_` … |
| **R2** | L0 表名**不带**任何平台词 |
| **R3** | L1 表**删掉 `platform` 列** —— 表名已表达工作区，再存一个恒为 `'xhs'` 的列是冗余 |
| **R4** | 子表跟随父表定级（C4），但**不自动继承前缀**（`note_assets` 不必叫 `xhs_note_assets`，因为 `note_` 已是平台词） |

> **本轮落地范围**：只对**因合并而重构的 6 张表**加 `xhs_` 前缀
> （`xhs_accounts` / `xhs_ai_drafts` / `xhs_publish_jobs` / `xhs_generation_records` /
> `xhs_no_traffic_cleanup_logs` / `xhs_monitoring_targets`）。
>
> 其余 L1 表**暂不改名** —— 改名不减少表数、不改结构，却要动全部 ORM `__tablename__`
> + SQL 字符串 + 前端类型，属于装饰性改动。等有真实收益的需求时再统一处理。
