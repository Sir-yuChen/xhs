# 72 · 参照若依（RuoYi）复核本项目的菜单权限体系

> 2026-10-26 用户口径：「你具体参考一下若依开源项目的菜单权限管理全流程」
>
> 结论先行：**若依的模型与本项目高度同构**（`sys_menu` 就是本项目的 `menus`，
> `perms` 列就是本项目的 `perms` 列，`M/C/F` 三型一致）。但若依有**三条硬纪律**
> 是本项目此前违背了的 —— 这三条正是「零路由码」「纯前端码」两个问题的根因。

## 1. 若依的模型（实测自官方 SQL 与源码，不是印象）

### 1.1 表：`sys_menu` 一张表装三件事

```sql
menu_type  char(1)  comment '菜单类型（M目录 C菜单 F按钮）'
perms      varchar(100)  comment '权限标识'
visible    char(1)  comment '菜单状态（0显示 1隐藏）'
status     char(1)  comment '菜单状态（0正常 1停用）'
```

与本项目 `menus` 表**逐列对应**（本项目的 `path`/`component`/`icon`/`sort_order`/
`workspace` 多几列，但 `menu_type` + `perms` 的核心语义完全相同）。

### 1.2 授权链：用户 → 角色 → 菜单（`sys_user_role` + `sys_role_menu`）

取菜单的 SQL（`SysMenuMapper.selectMenuTreeByUserId`）：

```sql
select distinct m.menu_id, ... , m.menu_type, ...
from sys_menu m
  left join sys_role_menu rm on m.menu_id = rm.menu_id
  left join sys_user_role ur on rm.role_id = ur.role_id
  left join sys_role ro on ur.role_id = ro.role_id
where u.user_id = #{userId}
  and m.menu_type in ('M', 'C')   -- ← 只下发目录与菜单
  and m.status = 0 and ro.status = 0
```

取权限标识的 SQL（`selectMenuPermsByUserId`）：

```sql
select distinct m.perms from sys_menu m
  left join sys_role_menu rm ...
  left join sys_user_role ur ...
where u.user_id = #{userId} and m.perms is not null and m.perms <> ''
```

⇒ **菜单树只含 `M`/`C`，`F`（按钮）只贡献 `perms` 字符串，不下发成导航项。**
本项目 `workspace-shell` + `menus/mine` 的做法与此一致（守卫已钉）。

### 1.3 前端：`v-hasPermi` 指令（`src/directive/permission/hasPermi.js`）

```js
const all_permission = "*:*:*";
const permissions = store.getters && store.getters.permissions;
if (value && value instanceof Array && value.length > 0) {
  const permissionFlag = value;
  const hasPermissions = permissions.some(permission => {
    return all_permission === permission || permissionFlag.includes(permission)
  });
  if (!hasPermissions) {
    el.parentNode && el.parentNode.removeChild(el);   // 直接移除 DOM
  }
}
```

判据三条：① admin 是通配码 `*:*:*`（**不是** `role === 'admin'` 的特殊分支）；
② 权限未加载 ⇒ 移除（fail-closed）；③ 精确字符串匹配。

本项目对应 `hasPermission(code)` + `useCan()`，判据一致（admin 由代码派生 `ALL_PERMS`）。

### 1.4 后端：`@PreAuthorize("@ss.hasPermi('...')")`

```java
@PreAuthorize("@ss.hasPermi('system:user:edit')")
@Log(title = "用户管理", businessType = BusinessType.UPDATE)
@PutMapping
public AjaxResult edit(@Validated @RequestBody SysUser user) { ... }
```

**关键**：若依官方文档原话——
> 「若依没有为后端接口专门设计权限管理模块，它认为**后端接口和菜单具有对应关系**，
> 可以直接使用菜单的角色或权限字符用于后端接口的权限声明。」

⇒ **权限码只写在一处（`sys_menu.perms`），前端指令与后端注解引用同一个字符串。**
不存在「第二张路由映射表」。这是若依最容易被忽略的一条设计。

## 2. 三条硬纪律（本项目此前违背的）

### 纪律一：`perms` 只在「有后端动作」时才有值

若依的 `F` 行**全部**对应一个具体接口动作（`system:user:add` → `POST /system/user`）。
它的 `perms` 列**不是**「前端入口标签」，因为：
* 前端入口由 `M`/`C` 行的 `visible` 控制（显示/隐藏），不需要额外码；
* 若给纯前端入口也编一个码，授权页会出现「勾了没用」的选项。

**本项目的违背**：`xhs:draft:view/save`、`xhs:workshop:uploadAsset/deleteAsset/saveDraft`、
`xhs:publish:rule`、`xhs:settings:edit` 七个码**后端零端点、前端零引用** ——
它们既不是后端动作，也不是前端判据，纯粹是空壳。

**修法**（2026-10-26，用户口径「不涉及后端的不需要权限控制」）：**删码**，不登记白名单。
白名单是把「本不该存在的码」写进例外表，等于把错误制度化。

### 纪律二：一个动作 = 一个码 = 一个端点，不做「一个端点按 body 分派多码」

若依里 `add`/`edit`/`remove` 是**三个独立端点**（`POST` / `PUT` / `DELETE`），
所以三个码天然一一对应。它**没有**「一个端点 + action 参数 + 三个码」这种形态。

**本项目的特例**：`POST /items/operate` 一个端点担上架/下架/删除（千帆平台只给一个
批量接口）。这是**平台约束**导致的，无法消除，但必须：
* 登记表只挂一个码（`onShelf`），另两个在函数内按 `action` 选码（已实现）；
* 这两个码**不算缺陷**，因为它们确实有后端判权点 —— 属于「一个端点多个码」，
  与「零路由码」是两件事。

判据：**有判权点（`has_perm` / `require_perm`）就不是零路由码**，
哪怕它不占登记表的一行。

### 纪律三：不存在「第二套路由映射表」

若依**没有** `route_perms.py` 这样的 `METHOD path → code` 表 —— 权限码直接写在
端点注解上，是唯一真相源。

本项目引入 `route_perms.py` 的理由写在它的 docstring 里：
> 「把码写在 `Depends(require_perm(...))` 里是最容易被抄错的形态（约 250 处），
> 而抄错一个字母的表现是**那个按钮对所有人 403**，只有真机点到才发现。」

**这个理由成立**（250 处手写确实容易错），但它带来了**新的失效模式**：
登记表可以全绿而端点一个都没挂依赖（实测 279 条写路由只有 25 条真挂）。
⇒ 本项目必须**两张表都对账**，这是若依不需要做、而本项目必须做的事。
守卫 `test_route_perms_integrity.py` + 设计 71 §1 的四层对账就是为此。

## 4. 剩余待定（需逐个判断，不能一刀切）

有前端引用但无后端端点的码，**不能一律删**（删了前端按钮就再也显示不出来）：

| 码 | 前端位置 | 判断方向 |
|---|---|---|
| `xhs:monitor:enable` | `monitoring-page.tsx` | 若后端 `PATCH` 有 `status` 字段 ⇒ **保留**，归 `edit` 同端点（前端用它控制开关显隐） |
| `xhs:taskcenter:viewLogs` | `workspace-tasks-page.tsx` | 日志接口挂 `system:scheduler:view`，两级共用 ⇒ **保留**（服务层选码） |
| `xhs:item:forbiddenWords` | `shop-items-page.tsx` | 打开的是违规词弹窗，动作归 `xhs:forbiddenWord:*` ⇒ **保留为入口码**（若依没有这种入口码，但本项目弹窗是跨域入口，删了按钮没法显隐） |
| `xhs:item:drafts` | `shop-items-page.tsx` | 同上 |
| `xhs:item:publish` | `shop-items-page.tsx` + `product-publish-wizard.tsx` | 打开发布向导，动作归 `xhs:publish:submit` ⇒ 同上 |

> ⚠️ 这五条是本项目**比若依多出来的一层**：若依的二级菜单一页一入口，
> 入口显隐靠菜单行；本项目的「弹窗/向导」是页面内入口，没有菜单行可挂
> ⇒ 只能用码表达显隐。**这不是设计错误，但要写清判据**：
> 只有「打开另一个域的面板」这种跨域入口才配入口码，同域内的按钮一律用动作码。
