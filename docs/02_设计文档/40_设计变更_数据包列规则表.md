## §0 一句话

把「每个数据包的**列取值规则**」从**临场反推**改为**表里配置**：新增父子两张表
（`data_package_rule_sets` 规则包 / `data_package_rules` 规则），用户可在商品 SKU 表格页
用 **60% 视口弹窗**做 CRUD（各自启用/停用）；每列**表头设置图标**的弹窗改为
「**先选规则包 → 再选该包下的列规则 → 选中即执行**」，且**只列启用项**。

**同一张表承载的不止「提取」**——规则的操作类型覆盖 `提取段` / `固定文本` / `批量运算`
（加减乘、乘+加、乘−减…），口径上**可完全取代**当前表格顶部的批量操作栏。
⚠️ **本轮不动顶栏**（用户口径：「先保留，等规则功能验证通过后我再决定」）。

## §1 背景：为什么不能继续「临场反推」

### 1.1 实证（两个真实数据包，2026-10-14 实测）

| | **包1**（斗柜梳妆台…） | **包2**（`商品ID_935947169189`） |
|---|---|---|
| 表格文件 | `店透-SKU预览-表格-827654555981-2026-10-13.xlsx` | `商品ID_935947169189_1_sku数据.xlsx` |
| SKU 列 | **`SKU信息`** = `木;中古色-实木三斗柜;上门安装` | **`sku名称`** = `颜色分类:【中古风】实木三斗柜` |
| 列形态 | **分号三段** | **冒号两段** |
| 要的那段 | **第 2 段** | **第 1 段** |
| 图片名 | `SKU图_01_中古色-实木三斗柜.jpg` | `SKU01_颜色分类(【中古风】实木三斗柜).jpg` |
| 图片形态 | 前缀 + **值裸奔** | 前缀 + **列名(值)** |
| 行数 | 52 | 26 |

### 1.2 三个已实测的结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **同一套规则**（不论正则还是位置逻辑）**跨包必然失效** | 拿包1规则跑包2 → **0/26**；包2规则跑包1 → **0/52** |
| 2 | 包内**给 1~2 行样例即可覆盖整列**（含未见过的行） | 包1 `SKU信息` 取第2段 **52/52**；包2 `sku名称` 取「颜色分类」**26/26**；包2 图名取括号内 **26/26** |
| 3 | **正则不适合**这件事（把数据写死 / 学出枚举） | `^(.+?)(?::【中古风】实木三斗柜)$` 只能匹配一行；grex 对 26 个变体吐出 26 分支枚举 |

### 1.3 为什么「规则表」优于「每包临场反推」

- 结论 1 说明**规则天然是「每类包一份」**，不是「每包现算一份」⇒ 有稳定归属，值得落库。
- 结论 2 说明**规则一旦定对，包内是全覆盖的**⇒ 不需要每次重新猜。
- 用户是**领域专家**，他一眼知道「这包该取第 2 段」；让他**配一次**，比让算法每次猜**更准、更快、可审计**。
- 反推（PBE）的定位随之变化：**从「每包的必经步骤」降级为「新建规则时的辅助」**（可选，非必需）。

## §2 数据模型

### 2.1 新表一：`data_package_rule_sets`（规则包 / 父）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | PK | |
| `user_id` | FK `users.id` | **数据隔离**（AGENTS.md 硬约束：一切按用户/账号隔离） |
| `name` | String(100) | 规则包名（用户自定义，如「店透SKU预览」「商品SKU数据」） |
| `remark` | String(500) NULL | 备注（可选） |
| `enabled` | Boolean，默认 **True** | **父停 ⇒ 下辖规则整包失效**（见 §4.3） |
| `sort_order` | Integer，默认 0 | 展示排序（列表稳定顺序，避免「刷新就变位」） |
| `created_at` / `updated_at` | DateTime | 惯例 |

**唯一约束**：`(user_id, name)` —— 同一用户规则包重名无意义，且会让「选包」歧义。

### 2.2 新表二：`data_package_rules`（规则 / 子）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | PK | |
| `set_id` | FK `data_package_rule_sets.id`（`ondelete=CASCADE`） | 父 |
| `rule_name` | String(100) | **规则名称**（如「取颜色分类」「取括号内名称」）—— 同一规则包内**不可重复** |
| `op` | String(30) | **操作类型**（枚举见 §2.3） |
| `params_json` | Text（JSON） | 操作参数（各 op 不同，见 §2.3） |
| `enabled` | Boolean，默认 **True** | 单条规则启用/停用 |
| `sort_order` | Integer，默认 0 | 展示排序 |
| `created_at` / `updated_at` | DateTime | 惯例 |

**唯一约束**：`(set_id, rule_name)` —— **一个规则包里规则名不可重复**
（用户口径：「每类数据包的每一列一个规则」）。但**同一个列名在不同包里可以各有一条**
（包1 的 `SKU信息` 与 包3 的 `SKU信息` 规则可以不同）。

⚠️ **`user_id` 不在子表冗余**：子表经 `set_id` 归属，父表已带 `user_id`；冗余会带来「父子 user_id 不一致」
的静默脏数据（本项目 DEF 系列同类教训）。查询一律 `join` 父表收口。

### 2.3 操作类型（`op` 枚举）

⚠️ **本轮只实现「提取」，其余 op 的字段一并定型**（避免后续加字段要再迁移），但**先只落提取**。
用户口径：「目前需求只有**提取 sku 名称**规则，其它**可能**支持……」。

| `op` | 含义 | `params_json` |
|---|---|---|
| `extract_segment` | **按分隔符切段取第 N 段** | `{"sep": ";", "index": 2}`（`index` 支持负数：`-1` = 最后一段；`1` 起数） |
| `extract_between` | **取包裹符之间的内容** | `{"open": "(", "close": ")", "occurrence": 1}`（缺 `close` ⇒ 取到末尾） |
| `extract_strip` | **去前缀 / 去后缀** | `{"prefix": "SKU图_01_", "suffix": ".jpg"}`（两者可只给一个；均按**字面**或 `pattern` 二选一，见下） |
| `fixed_text` | **整列设为固定文本** | `{"text": "100"}` |
| `math_scale` | **批量运算** | `{"factor": 1.7, "offset": 0, "op2": "add"\|"sub"\|null}` —— 覆盖「乘」「乘+加」「乘−减」；`op2=null` 且 `factor=1` 即「加/减固定值」 |

⚠️ **「按字面 / 按正则」二选一**：`extract_strip` 的 `prefix`/`suffix` 默认**按字面**（`"is_regex": false`）；
需要通配时用户显式打开 `is_regex`（值仍是字符串，由后端 `re` 编译）。**默认不用正则** —— 这是本轮
最重要的一条：**正则不该是普通用户的默认工具**（§1 的实证）。

⚠️ **顺序语义**：`extract_*` 是**纯函数**（输入该列原值 → 输出新值），**不叠加**（每次从原值算）；
`math_scale` 同理。⇒ 「实时生效」= 重新按规则算一遍全列，不做链式迭代（否则反复点会越算越偏）。

### 2.4 与现有 `precheck` 的关系（**不复用、不冲突**）

现有第一步已有「正则取值」能力（`ColumnPatternControl` + `applyPatternToColumn` + 快照撤销）。
本轮**不动它**，两者关系：

| | 正则取值（既有） | **数据包规则（本轮）** |
|---|---|---|
| 定位 | **临时、单次**、就地覆盖、可撤销 | **配置化、可复用**、按包类型命中 |
| 存哪 | 前端内存（快照） | **库表**（跨会话、跨数据包） |
| 适合谁 | 会写正则的高级用户 | 领域用户（**选包 → 选列**即可） |
| 交互 | 表头齿轮 → 弹窗输入正则 | 表头齿轮 → **选包 → 选列规则** |

⇒ **同一个表头齿轮弹窗内分两块**（见 §4.2）：上「**数据包规则**」（选包 + 选列规则 + 执行），
下「正则取值」（保留，作为高级/临时手段）。**两者共用「应用/还原」出口**（都写同一份快照，可一起撤销）。

## §3 迁移 `d3e4f5a6b7c8`

```
down_revision = c2d3e4f5a6b8   # 当前 head（2026-10-14 实测：无人指向它）
upgrade():
  ① op.create_table("data_package_rule_sets", …)
     + UniqueConstraint("user_id", "name", name="uq_dp_rule_sets_user_name")
  ② op.create_table("data_package_rules", …)
     + ForeignKey("set_id", "data_package_rule_sets.id", ondelete="CASCADE")
     + UniqueConstraint("set_id", "rule_name", name="uq_dp_rules_set_name")
  ③ 索引：ix_dp_rules_set_id（子表按父查是唯一热路径）
downgrade():
  ②① 按依赖顺序 drop（先子后父）
```

⚠️ **不回填、不播种存量**：规则是**用户资产**，且两类真实包的规则形态已确定（§6 种子）。
⚠️ **不 import 应用代码**（迁移必须能在「当时任意版本的代码」上跑通，R24 纪律）。

### 3.1 ⚠️ `down_revision` 是**两个父**（本轮实测踩出来的）

```python
down_revision = ("c2d3e4f5a6b8", "q8r9s0t1u2v3")
```

**为什么**：迁移图里本来就有**两条并行分支**（改动前就存在）：

```
… → f2a3b4c5d6e7 → g0a1b2c3d4e5 → ┬→ c2d3e4f5a6b8（主线，metrics/cleanup 一串）
                                   └→ q8r9s0t1u2v3（工作流 5 张表，设计 19 M5）
```

- 只接 `c2d3e4f5a6b8` ⇒ alembic 报 **`Multiple head revisions`**
  （实测红过 `test_migration_no_longer_seeds_scheduled_jobs`）；
- 只接 `q8r9s0t1u2v3` ⇒ `c2d3e4f5a6b8` 又成了悬空 head。
- ⇒ **两个都接**，让本迁移成为**合并点**，恢复单一 head。

⚠️ **副作用（要知道）**：合并之后 `alembic downgrade -1` 报 **`Ambiguous walk`**
（alembic 无法判断该回退哪一支）⇒ 降级要**显式给目标**：`alembic downgrade q8r9s0t1u2v3`。

⚠️ **另一个副作用（要留意）**：真库当时停在 `c2d3e4f5a6b8`（主线那支），
`upgrade head` 会把**另一支的 `q8r9s0t1u2v3`（工作流 5 张表）一并跑掉** ——
**这是并行分支合并的固有行为**，不是本轮的回归（工作流表本就该建，
只是在此之前没人把它接回主线）。实测真库副本 `upgrade head` 后表数 **60 → 66**（+2 本表 +4 工作流表）。

## §4 后端契约

### 4.1 端点（**9 条 / 5 path**，2026-10-14 实测）

⚠️ 端点计数 **315 → 324**（operations）/ **272 → 278**（paths）—— `GET`+`POST` 共用
`/sets`、`GET`+`POST` 共用 `/rules`、`PATCH`+`DELETE` 各共用一个 `{id}` path
⇒ 9 条端点只占 5 条 path。**实测**（`create_app().openapi()`）。

| # | 方法 | 路径 | 作用 |
|---|---|---|---|
| 1 | `GET` | `/api/xhs/data-package-rules/sets` | 规则包清单（**含 `enabled` 与子规则计数**；`?enabled_only=1` 供列头弹窗用） |
| 2 | `POST` | `/api/xhs/data-package-rules/sets` | 新建规则包 |
| 3 | `PATCH` | `/api/xhs/data-package-rules/sets/{set_id}` | 改规则包（`name` / `remark` / `enabled` / `sort_order`） |
| 4 | `DELETE` | `/api/xhs/data-package-rules/sets/{set_id}` | 删规则包（**级联删子规则**，见 §4.4） |
| 5 | `GET` | `/api/xhs/data-package-rules/rules?set_id=` | 某包下的规则清单 |
| 6 | `POST` | `/api/xhs/data-package-rules/rules` | 新建规则（`set_id` + `rule_name` + `op` + `params`） |
| 7 | `PATCH` | `/api/xhs/data-package-rules/rules/{rule_id}` | 改规则（含启用/停用） |
| 8 | `DELETE` | `/api/xhs/data-package-rules/rules/{rule_id}` | 删规则 |
| 9 | `POST` | `/api/xhs/data-package-rules/execute` | **执行一条规则**（后端算；前端不重复实现提取语义） |

**路由注册顺序**：`/sets` 与 `/rules` 是**同层不同前缀**，无 `{id}` 冲突（不是 `/{id}` 抢路由的场景）。

⚠️ **`PATCH` 而非 `PUT`**：启用/停用是**单字段改**，用 `PATCH` 表达局部更新（与项目既有 LLM 网关
`PATCH models/{id}` 同惯例）。

### 4.2 校验（结构化 4xx，不静默）

| 场景 | 响应 |
|---|---|
| `op` 不在枚举 | `400 DP_RULE_BAD_OP` |
| `extract_segment` 的 `index` 为 0 或非整数 | `400 DP_RULE_BAD_PARAM` |
| `extract_segment` 的 `sep` 为空串 | `400 DP_RULE_BAD_PARAM`（空分隔符切分无意义） |
| `math_scale` 的 `factor`/`offset` 非数 | `400 DP_RULE_BAD_PARAM` |
| 同一 `set_id` 下同列重复 | `409 DP_RULE_DUPLICATE_COLUMN`（撞唯一约束，**友好化**，不回 `500`） |
| `set_id` 不存在 / 不属于当前用户 | `404` |
| 规则包重名 | `409 DP_RULE_SET_DUPLICATE_NAME` |

⚠️ **缺值口径**（AGENTS.md 硬约束 5）：`extract_*` **提不出**（段数不够 / 找不到包裹符）⇒ **该格留空**，
**不填原值、不报错**（把原值留下会让用户以为「规则生效了」，见 §1 的教训）。
**前端以 25–30 字原因行**说明「N 行未能提取」。

### 4.3 启用语义（**父停 ⇒ 子全失效**）

```
规则是否生效 = set.enabled AND rule.enabled
```

- 父停用 ⇒ 列头弹窗里**整个包不出现**（用户口径「只展示启用的」）。
- **不级联改子行的 `enabled` 字段**（保留用户原设置）：父恢复启用后，子行按自己原来的状态生效。
  ⚠️ 若父停时把子行也置 `false`，父恢复后用户还得逐条改回来 —— 那是**破坏用户数据**。

### 4.4 删除语义

- 删**规则包** ⇒ **级联删子规则**（`ondelete=CASCADE`）。⚠️ **前端二次确认**并**明示条数**
  （「将同时删除其下 N 条规则」，本项目 `还原原始值需二次确认` 的同一条纪律）。
- 删**单条规则** ⇒ 二次确认。

## §5 前端

### 5.1 「提取数据规则」管理弹窗（60% 视口）

入口：**商品 SKU 表格 tab 下方**新增按钮「提取数据规则」。

| 项 | 口径 |
|---|---|
| 视口 | **60%**（用户明确）；与项目其它弹窗一致用 `vw`/`vh`，**不用固定像素** |
| 结构 | **父子表**：父行 = 规则包；展开 = 其下规则 |
| 列（父） | 规则包名 / 备注 / 规则数 / **状态** / 操作 |
| 列（子） | 列名 / 匹配方式 / 操作 / 参数摘要 / **状态** / 操作 |
| 操作列 | **启动 / 停用**（父、子各有）+ 编辑 + 删除 + 新增子规则 |
| 新增 | 顶部「新建规则包」；每行「+ 新增规则」 |
| 参数编辑 | `op` 下拉 → **按 op 动态渲染参数表单**（不一次性摆所有字段） |

⚠️ **参数摘要列**要**人话**（`按「;」取第 2 段` / `取 ( ) 之间` / `×1.7 再加 10`）——
不要显示 `{"sep":";","index":2}` 这种 JSON（用户看不懂，还会以为存的是乱码）。

### 5.2 列头设置图标（**所有列**）

- 用户口径：「**所有列均表头有设置图标**，不再只局限于文本列」
  ⇒ 删掉 `canApplyPattern(kind)` 的**文本列限制**（§7 的 `column_kinds` 过滤）。
  ⚠️ **数值列也给图标**，因为规则里有 `fixed_text` / `math_scale`（本来就是给数值列的）。
- 图标形态**保持现状**（小齿轮、`withTrigger={false}`）—— 2026-10-14 刚统一过。

### 5.3 齿轮弹窗内（**只列启用项 + 先包后列**）

```
┌─ 数据包规则 ─────────────────────────────┐
│ 规则包 [店透SKU预览 ▾]   ← 只列启用的包     │
│ 列规则 [SKU信息 · 按「;」取第2段 ▾]  ← 只列启用的规则 │
│ [执行规则]                                │
├─ 正则取值（高级，可选）───────────────────┤
│ 正则 [____________________] [执行]        │
├──────────────────────────────────────────┤
│ [还原原始值]                [应用]         │
└──────────────────────────────────────────┘
```

⚠️ **「先选择数据包类型再选择指定的列」**（用户原话）：第二个下拉**列的是「该包下启用的规则」**，
**每条形如「列名 · 操作摘要」** —— 这样用户看到的是「哪个包 + 哪一列 + 做什么」，一步到位。
⚠️ **规则不绑列**（2026-10-14 口径）：弹窗里只**说明**「将把『规则名』应用到『当前列』」，
但**在弹窗里显示一行轻提示**（「该规则针对『SKU信息』列，当前点是『原价』列」）—— 避免选错了还以为生效了。

### 5.4 「实时生效」的准确含义

用户口径：「数据包规则调整后**实时生效**」。落实为两条：

1. **配置改动即时可见**：管理弹窗里改完（启停/改参/新增）⇒ 关掉重开齿轮弹窗**立即可选到新状态**
   （不做前端缓存；每次打开**现拉**）。
2. **列上已应用的规则，参数变了要重算**：前端记「这一列用了哪条规则（`rule_id`）」，
   规则 `updated_at` 变了 ⇒ 下次渲染/刷新时**用新参数重算**（不是把旧结果留在表里）。
   ⚠️ 重算**从原值算**（§2.3 的纯函数语义），**不在上次结果上迭代**。

### 8.3 M6 的最终处置：该维度**本来就测不出来**（且不是缺陷）

修好判据（改用**独立连接**查库，而不是夹具那个看不见端点写入的 `db_session`）之后，
M6 仍然**三轮都绿**。继续挖下去，根因是：

> **删包有「两道保险」** —— ORM 的 `ondelete="CASCADE"` + `delete_set` 里的**显式**
> `db.execute(delete(DataPackageRule)...)`；而本项目的 engine **显式开了
> `PRAGMA foreign_keys=ON`**（`core/database.py`，2026-10-04 起，为让工作流的
> `ON DELETE SET NULL` 真生效）⇒ **去掉任意一道，另一道照常兜住**。

⚠️ **这与「守卫缺口」是两回事**：
- 守卫缺口 = 实现错了但测试没抓住（要补用例）；
- 本情形 = **实现有两道正确的保险**，去掉一道**行为不变** ⇒ 用例绿是**对的**。

⇒ 处置：**把 M6 从这个维度撤掉**，换成**真能区分**的那一面（`deleted_rules` 计数 ——
它是前端二次确认的依据，写死就等于「删了 3 条却说 0 条」）。

⚠️ **教训（值得单独记）**：**变异验证失败时，先问「这个变异在实现上真的可达吗」** ——
连续两轮把「不可达的变异」当成「守卫缺口」去补用例，是在给一个**本来就不该红**的点加测试
（新增的用例还是好的，但诊断方向错了）。判据：**把变异体跑一遍、看它的输出是否真的与原件不同**；
一样 ⇒ 变异不可达，换一个。

## 9. 同轮追加：「规则名称」+ 反推正则整条退场（2026-10-14）

### 9.1 规则改「规则名称」、不再绑列

用户口径：

> 「提取数据规则弹窗，规格应只有**两级**，一个是包级然后是包下具体的规则
> （也就是一组规则，**一个组名，组下多条规则**），规则**有规则名称不可重复，
> 不是列名**，规则**不限制只针对于固定列**，使用时**根据用户选择**」

⇒ 三处落地：

| 项 | 改前 | 改后 |
|---|---|---|
| 子表列 | `column_name` + `column_match` | **`rule_name`**（`column_match` **删除**） |
| 唯一约束 | `(set_id, column_name, column_match)` | **`(set_id, rule_name)`** |
| 执行 | 规则自带列名 ⇒ 自动落到那一列 | 规则**不带列** ⇒ 落到**用户点开的那个表头所在列** |

**为什么删 `column_match` 而不是留空**：规则不绑列了，「列名怎么匹配」这件事
**根本不存在** —— 留一个永远不读的列比删掉更容易误导后来者。

⚠️ **父子两级本来就在**（`data_package_rule_sets` → `data_package_rules`），
弹窗也是父子表；本轮只是把**子级的语义**从「某一列的规则」纠正成「一条具名取值规则」。
⇒ **表结构没加层**，改动集中在子表的列与约束。

### 9.2 兼容存量：不改「建表」而是**原地改造**

⚠️ 本迁移的**初版已经跑进过真实库**（26 个用户 × 播种 = 52 包 / 78 规则），
而 `create_table` 是可以直接改的形态 —— 但如果改成
「纯新建最终形态」，**已升级的库**会永远停在旧形态（`alembic version` 已在 head，
`upgrade` 不会再跑）。

⇒ 迁移写成**两态兼容**：

1. 表**不存在** ⇒ 按最终形态建；
2. 表**已存在**（旧形态）⇒ 原地：丢旧唯一约束 → `column_name` **改名** `rule_name`
   （**保留数据**）→ 删 `column_match` → 建新唯一约束。

⚠️ **还要接住「存量规则名还是旧列名」**：改名后那 78 条的 `rule_name` 会是
`SKU信息` / `sku名称` / `图片` 这类**旧列名** —— 语义上它们是「规则名」了，
留着会让用户以为规则还按列匹配（正是本轮要消掉的误解）。
⇒ 按 `params` 反查（**不按旧列名**，那是用户数据里任意列名，会误伤），
只把**种子那三条**改成人话名（「取颜色分类」/「取 SKU 名称」/「取括号内名称」）；
**用户自建的一律不碰**。

实测（真库副本）：`52/78` 一条不丢，规则名全变人话（26×3）。

### 10.1 后端：两个 op 落地

`OP_FIXED_TEXT` / `OP_MATH_SCALE` 从「枚举里有、调用即 400」变成**真实现**：

| op | 语义 | 关键口径 |
|---|---|---|
| `fixed_text` | 整列设为固定文本 | **含原本为空的行也写**（「无条件设为」，不是「提不出就留空」） |
| `math_scale` | `×factor` / `+offset` / `−offset` / `×factor±offset` | **空值按 0**；认不出的内容**也按 0** 但要**记原因行** |

⚠️ **两条口径方向相反，且都是刻意的**：

| 家族 | 缺值语义 | 为什么 |
|---|---|---|
| `extract_*` | **留空**（不填原值） | 「提不出」= 这条规则对不上这一行；填原值会让用户以为规则生效了，拿旧值去发布 |
| `math_scale` | **按 0** | 「计算」要求整列都有数；留空会让半列结果空洞，用户还得自己填 |

两条都写在 service 模块 docstring 的那张表里（本项目最容易被后来者「统一」错的地方）。

### 10.2 前端：运算类规则要选「计算基础列」

- 只在**选中的规则是 `math_scale`** 时出现（提取类/固定文本不显示 —— 它们读的就是当前列自己）；
- **默认当前列**（`sourceColumn ?? column`）、可换其它列；
- **下拉只列数值列** —— 判据是后端的 `column_kinds === "numeric"`
  （⚠️ 写成 `"number"` 会**恒空且不报错**，是本轮实测踩到的坑）；
- 执行时**读基础列、写当前列** ⇒ 支持「把 A 列 ×1.7 写到 B 列」。

⚠️ 换规则 / 换列时基础列**回到默认**（`useEffect` 重置）—— 否则会带着上一条规则的列去算，
是典型的静默错值。

### 10.5 ⚠️ 第三个哑弹（M12）+ 顺手消掉一处死代码

M12 原本改的是 `apply_math_scale` 的**第二返回值**（`(结果, 是否认不出)` 的元组）——
实测逃逸。按 §10.4 的判据做输出对照，**根因不是判据不够硬，而是那个返回值根本没人读**：


⇒ 那个 `bool` 是**死代码**，而且与 `count_unrecognized` 构成**两份实现**

**处置**（比「补个用例」正确）：
1. `apply_math_scale` **只返回结果文本**（不再是元组），判据仍与 `count_unrecognized`

2. M12 换成**真承重面** —— `count_unrecognized` 自身改成恒 0 ⇒ 原因行永远不出现

⚠️ **这是本项目第三次「变异失败 ≠ 守卫缺口」**（前两次：M6 删包级联、M11 不 round）。
三次的结论完全一致，已可当作**固定流程**：

> 变异没被咬住时，**先跑「变异体 vs 原实现」的输出/行为对照**。
> · 逐字相同 ⇒ **变异不可达** ⇒ 换变异（补用例没有意义，没有行为可咬）；
> · 确有差异 ⇒ 才是守卫缺口 ⇒ 补用例，并**再跑一次变异体确认变红**。

## 13. 2026-10-15 四次追加：映射表改造 + 手动列 + 删列连带提示 + 三处移除

用户口径（一口气四条 + 一条核心）：

> 「商品 SKU 映射关系需求未实现，应拿第一步预检通过的**规格分类列去重**与平台类目生成的
>   商品规格下拉选择映射，且**不允许重复选择**，**最多两个映射关系**，
>   **布局参考同一个弹窗中的其它部分**；价格库存映射关系表**不再设置默认值**；
>   **其它规则的逻辑移除**；再加一个核心逻辑，商品sku表格**支持手动添加列**，
>   弹窗用户设置表头**中文和英文名**（**英文名非必填为空则按照一定的顺序规则自动生成**），
>   手动新增的列支持**整列删除**，**非手动新增和固定列不支持删除**；
>   另外注意如果该列在第二步已经被映射使用删除该列后二次确认提示
>   会**同步删除已经映射使用的 XXX 配置参数**」

### 13.1 商品 SKU 映射关系：从「勾选 + 下拉」改为**映射表**

| | 旧 | 新 |
|---|---|---|
| 形态 | 候选名 + `Checkbox` + 紧跟的 `Select` | **`Table`**（两列 + 操作列）|
| 布局一致性 | 与同弹窗的「价格库存映射关系表」**不同款** | **同款**（用户口径：「参考同一个弹窗中的其它部分」）|
| 条数 | 无上限（勾几个就有几行）| **≤ `MAX_SPEC_MAPPING_ROWS`（2）** |
| 新增行 | 无「+」 | 有（与价格库存一致：**两列都空**）|

⚠️ 「**不允许重复选择**」**两列都要** —— 左侧规格分类去重后本就唯一，但**右侧平台规格**
必须显式 `disabled: others.includes(d.name)`，否则两个分类能映射到同一个平台维度
（导入时两条映射抢同一个 spec 分组，后写覆盖先写，静默丢数据）。

### 13.2 价格库存映射关系表：**去掉默认值**

旧实现 `useState(DEFAULT_PRICE_MAPPING.map(...))` ⇒ 一打开弹窗就预填好
「售价 ← 原价」「库存 ← 库存」… 用户会**以为映射已经配好了**，
而来源列对不对、他有没有别的意图，只有他自己知道。⇒ 初始 `[]`。

⚠️ `DEFAULT_PRICE_MAPPING` 常量**保留**（「按现行逻辑一键填充」按钮仍用它）——
删常量等于把「快速回到默认配置」的路也一起删了。

### 13.3 「其它规则」整块移除

原内容 = 「市场价计算规则：原价 × [倍率] + 恢复默认 + 取不到时回落列」。

⚠️ **不是删功能，是删入口**：倍率仍有默认值（`DEFAULT_PRICE_MULTIPLIER = 1.7`），
导入时照常按它算市场价 —— 只是用户不再在弹窗里配。

### 13.4 手动新增列 + 整列删除（本轮核心）

- **身份靠 key，不靠表头名**：表头是中文名（用户可改、可重复）⇒ 不能当身份。
  手动列的 key = `__manual_<英文名>`；**删除按钮的可见性由前缀判**
  （`canDropColumn`）。⚠️ 非手动列 / 固定列（`规格分类`）**没有前缀 ⇒ 不给删除按钮**。
- **`column_keys` 与 `columns` / `column_kinds` 等长是契约**：
  插「规格分类」、追加手动列、整列删除**三处都要同步**，否则下标整体错位。
- **英文名非必填**：留空 ⇒ `nextManualColumnKey()` 按顺序生成。
  ⚠️ 「一定的顺序规则」= **按已有手动列的最大序号 +1**（不是按总列数）——
  否则删掉 `col_1` 再加一列会撞名。
- **中文名必填**、且**不许与已有列重名**（重名会让映射查表拿到任意一条）。
- ⚠️ `column_keys` **后端不下发**（前端产物）⇒ 在向导层加载表格时初始化；
  **缺失时 `canDropColumn` 一律返回 false**（宁可少给按钮，也不能让用户删掉原始列）。

### 13.5 删列的二次确认要**点名**（本轮最容易被做成哑弹的一条）

用户原话：「会同步删除已经映射使用的 **XXX** 配置参数」—— **XXX 必须说出来**。

- 说「该列已被 **商品 SKU 映射关系** / **价格库存映射关系表** 使用」，
  再说「删除后会同步删除已经映射使用的『<列名>』配置参数」。
- ⚠️ 那两份映射的**真相源在第二步**（`PublishStep2` 内部 state），第一步拿不到
  ⇒ 必须**上抛**：`onMappingDraftChange` → 向导层 `mappingDraft` → 第一步 `TablesPanel`。
- ⚠️ 上报 effect 的**依赖数组必须含 `onMappingDraftChange`** ——
  漏了的话永远是首次渲染那份，提示会说错人（同 §12 那条「闭包陈旧值」的形态）。
- ⚠️ 用户没走到第二步时 `mappingDraft` 为空 ⇒ 退化为通用文案
  （「该列的数据会一并删除」）—— **是诚实的，不猜**。

**守卫**：`test_column_drop_warning_is_fed_by_real_mapping_drafts` 咬的是**接线**
（第二步上报 → 向导接住 → 表格收到），不是「页面上有那句话」——
后者是哑弹（文案在、但永远走不到「点名」分支）。
