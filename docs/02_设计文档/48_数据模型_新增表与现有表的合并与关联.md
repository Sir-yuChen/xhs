### M8 专节 · 为什么 `system_settings` **不加** `scope` 列（2026-10-23 裁决）

**背景**：设计 46/49 初稿曾写「`system_settings` +1 列 `scope`（global/user），`scope=global` 仅 admin 可写」。
实测发现该列**曾经存在过，并在 2026-09-27 被刻意删除**：

| 出处 | 原文 |
|---|---|
| `docs/02_设计文档/10_系统管理功能设计.md` §7.1 D1 | 「**去掉 `scope` 列**，`user_id` **必填**。理由：全项目口径已统一为『所有配置行必归属用户』（DEF-066）⇒ `scope` 是同一语义的第二份表达（DEF-044）」 |
| 同表 D3 | 「`scope=global` 的设置需 `require_admin`」→「**不做管理员门禁**」 |
| `backend/app/models/system_setting.py` | 文件头注释保留同一段，实测列确实无 `scope`（13 列） |

**裁决：不加该列。** 三条判据：

1. **同一语义不做两份表达（DEF-044）**。归属已经由 `user_id NOT NULL` 完整表达；再加 `scope` 就是给同一件事写两个字段，两者迟早打架（`scope='global'` 但 `user_id` 有值的行怎么算？）。
2. **高频读点付不起 join 代价**。`LIVE_KEYS` 8 个热键在同步 worker / 上传链路里被反复读；若改用 `scope` 判定可写性，每次写都要回查 role，把「读配置」变成「读配置 + 读用户」。
3. **单机桌面版没有「全站」实体**。本系统是**本机多用户**（26 个 `users` 行是测试残留 + 真实使用者），不是多租户 SaaS；「全站基线」目前由**随包种子**表达（`config/initial_data/system_settings.json`），那才是真正的全站真相源。

**那管理员的诉求怎么满足？** —— 靠「基线 = 种子文件」这层，不靠加列。配置管理页分两块：

| 区域 | 数据来源 | 谁可写 |
|---|---|---|
| **我的配置**（默认展示） | `system_settings WHERE user_id = 当前用户` | 任何有 `system:setting:edit` 的用户 |
| **基线默认值**（只读对照列） | `config/initial_data/system_settings.json`（随包） | **不可在页面改**，要改改文件并发版 |
| **一键应用到所有用户** | 按钮 ⇒ 把当前用户的行复写到其余用户 | 仅 `admin`（`system:setting:applyAll`，**+1 权限码**） |

⇒ 因此 48 的增列清单里**删掉 `system_settings +1 scope`**，改为 **`users` 仍 +6 列、`system_settings` 零变化**；
配置管理模块多 **1 个端点** `POST /api/settings/apply-to-all`（原计划的 `clear-cache` 保留）。

**净结果**：原计划 +5 表 → **实测 +4 表**（`roles` 保留是必要的，但 `dict_*` 2 张合并成 1 张见 §3.2）→ 最终 **+3 表**。
表数 **57 → 60**（不是 62）。

## 2. 合并决策总表（逐条）

> 判据：**同语义 == 同表**；**不同生命周期 == 不同表**；**不同隔离维度 == 不同表**。

| # | 候选 | 结论 | 判据 |
|---|---|---|---|
| M1 | `roles` 要不要新建？还是直接用 `users.role` 单列 | **新建 `roles`，但只是「码表」** | 需要 `is_system`（内置禁删）、`name`（中文名）、`description`、`status`。现有 `users.role` 只存 code 一个字符串，**放不下这四样**；但 `users.role` 保留不动（值域外键） |
| M2 | `dict_types` 能否并入现有 `system_settings`？ | **不能合并** | `system_settings` 是「每用户一份的 KV（唯一键 `user_id,key`）」，而字典是**全局共享、带层级（type → items）**的枚举。混进去会：① 26 个用户各存一份同样的枚举（实测 209 行就是这么来的）② 一个 `key` 存不下 `(label,value,list_class,sort)` 四元组数组 |
| M3 | `dict_items` 能否并入 `menus`？ | **不能** | 两者语义相反：`menus.perms` 是**权限**（决定能否操作），字典是**展示映射**（决定怎么显示）。合表会让「给某人一个字典项」被误读成「给了他一个权限」 |
| M4 | `role_menus` 能否省略（用 `roles.menus_json` 存）？ | **不能** | 需要「反查哪些角色引用了某菜单」（删菜单前置检查 P8）⇒ 必须能 SQL 索引；JSON 列无法建索引，且删菜单时要全表扫 JSON |
| M5 | 是否新建 `user_roles` 中间表？ | **不新建** | 实测 26 用户全是单角色（1 admin + 25 user）。用户口径「默认一个 admin」+ 只有两个内置角色 ⇒ 一人一角色够用。多对多是 dataPanel 的形态，XHS 不需要 |
| M6 | 是否新建 `sessions` 表（`/auth/me` 权限缓存）？ | **不新建** | 权限缓存放**进程内（60s TTL）**，不落库。理由：`login_sessions` 已有 222 行/191 pending 说明「会话表很脏」；再加一张会重复这个错。撤销靠 `users.token_version` |
| M7 | 新增表要不要都带 `user_id`？ | **都不带** | 它们是**权限/枚举的定义**，不是「某用户的数据」。带 `user_id` = 每个用户一套菜单（菜单权限立刻失效） |
| M8 | `system_settings.scope`（全局/用户）能不能加？ | **不加列 —— 维持「每用户各持一份」**（裁决见下方 M8 专节） | 该列 2026-09-27 被**刻意删除**过（设计 10 §7.1 D1，理由：与 `user_id` 是同一语义的第二份表达）。加回来 = 推翻一条有理由的既有决策 |

## 3. 逐表定稿（合并后）

### 3.1 `roles` —— **新建（码表，只 2 行种子）**

**为什么不并进 `users.role`**：`users.role` 只能存 `admin`/`user` 一个串，缺中文名、描述、内置标记、状态。

```sql
CREATE TABLE roles (
  id          INTEGER PRIMARY KEY,
  code        VARCHAR(32)  NOT NULL UNIQUE,      -- admin / user / 自定义
  name        VARCHAR(64)  NOT NULL,             -- 中文名：超级管理员
  description VARCHAR(255) NOT NULL DEFAULT '',
  is_system   BOOLEAN      NOT NULL DEFAULT 0,   -- 1 = 禁删/禁停/禁改码/禁改授权
  status      VARCHAR(16)  NOT NULL DEFAULT 'normal',
  sort_order  INTEGER      NOT NULL DEFAULT 0,
  created_at  DATETIME     NOT NULL,
  updated_at  DATETIME     NOT NULL
);
-- 种子 2 行
INSERT INTO roles (code,name,description,is_system) VALUES
  ('admin','超级管理员','全部权限（代码派生全量）',1),
  ('user' ,'普通用户',  '默认角色，按授权行取权限',1);
```

**与现有表的关联**：

| 关联 | 形态 | 实现 |
|---|---|---|
| `users.role` → `roles.code` | **值域外键（无 DDL FK）** | 应用层写角色时校验 code 存在；守卫 `test_every_user_role_exists` |
| `role_menus.role_id` → `roles.id` | **DDL FK，`ON DELETE CASCADE`** | 删角色 ⇒ 授权行自动清 |
| 迁移时存量回填 | `UPDATE users SET role='user' WHERE role NOT IN ('admin','user')` | 实测 26 用户全合规（0 行需改） |

### 3.2 字典 —— **2 张表（不合并）**

**为什么 `dict_types` + `dict_items` 不合成一张**：
1. 层级事实：一个类型下有 N 项 —— 合成一张就要「类型行」和「项行」混在同一张表里靠 `parent_id` 区分，那是 `menus` 的形状（树），而字典是**两层固定**（不是任意深度），两层用两张表更简单；
2. 实测 `system_settings` 的教训：26 人 × 9 键 = 209 行 → **枚举每用户一份是灾难**。字典必须全局一份，这就需要一个「类型」实体来兜住「这个 code 归谁」。

**为什么不并进 `menus`**：见 M3（权限 ≠ 展示映射）。

**与现有表的关联**：

| 现有唯一真相源 | 字典 code | 关联方式 |
|---|---|---|
| `note.PUBLISH_STATUSES`（4 值） | `sys_publish_status` | **镜像**，守卫 `test_dict_mirrors_python_constants` 断言一致 |
| `scheduled_job.JOB_STATUSES`（3 值） | `sys_job_status` | 同上 |
| `scheduled_job.LOG_STATUSES`（4 值） | `sys_job_log_status` | 同上 |
| `note_queue_service` 状态（6 值：pending/running/done/failed/cancelled/exhausted） | `sys_task_status` | 同上 |
| `note.note_form`（image/video） | `sys_note_form` | 同上 |
| `notifications.level`（info/warning/error） | `sys_notify_level` | 同上 |
| `notifications.source_type`（实测 4 种在用） | `sys_notify_source` | 同上 |
| 本设计新增的 `users.status` / `roles.status` / `menus.menu_type` | `sys_user_status` / `sys_role_status` / `sys_menu_type` | 本轮新建的枚举，字典即权威 |

> ⚠️ **镜像不是同步**：Python 常量仍是代码唯一真相源，字典只服务**前端下拉**（P17 保证前端不再写死数组）。漂移 ⇒ 守卫报红，人工改一处，不做双向自动同步（那是两份真相）。

### 3.3 `menus` —— **新建（唯一必须新建的「树」）**

**为什么不可合并**：它是**权限码的载体**（`perms` 唯一）+ **前端菜单的载体**（`path` 唯一）+ **工作区的载体**（`workspace`）+ **平台启停的载体**（`status`）。四件事一张表，正是 dataPanel 那套能撑住的原因。

**与现有表的关联**：

| 关联 | 形态 |
|---|---|
| `role_menus.menu_id` → `menus.id` | **DDL FK，`ON DELETE RESTRICT`** |
| `menus.workspace` ↔ `core/platforms.py::_PLATFORMS.id` | **值域外键**（种子由注册表生成，G2） |
| `menus.path` ↔ `frontend/src/app/router.tsx` | **非表关系**：守卫逐条比对「C 行 path 必须在路由表里」 |
| `menus.perms` ↔ 后端 `require_perm("…")` | **非表关系**：启动期自检（P5）+ 三处一致守卫 |
| **不引用任何业务表** | 刻意 —— 菜单不绑 `notes`/`tasks`，只绑路由 |

### 3.4 `role_menus` —— **新建（唯一的多对多）**

不可省略（M4）。**这是 `menus` 与 `roles` 之间唯一的物理连接**。

```sql
CREATE TABLE role_menus (
  id      INTEGER PRIMARY KEY,
  role_id INTEGER NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  menu_id INTEGER NOT NULL REFERENCES menus(id) ON DELETE RESTRICT,
  UNIQUE (role_id, menu_id)
);
CREATE INDEX ix_role_menus_menu ON role_menus(menu_id);
```

## 4. 要「建关联」的现有 4 处（不改表结构，只补关系/补列）

| # | 现有表 | 改什么 | 为什么必须 | 实测依据 |
|---|---|---|---|---|
| **R1** | `users` | **+6 列**：`status` / `real_name` / `last_login_ip` / `last_login_at` / `must_change_password` | 用户管理页要显示状态、姓名、最后登录；种子 admin 需强制改密 | 现有 `users` 只有 `id/username/password_hash/role/token_version/created_at` —— **连姓名和登录时间都没有** |
| **R2** | `users.role` | **值域关联 `roles.code`**（加守卫，不加 FK） | 没有这层，「角色管理页改了个 code」会让 26 个用户静默失去权限 | 实测 26 用户 role 全部合法（0 行需修） |
| **R3** | `api_logs` | **+1 列 `status_code`**（INTEGER） | 审计日志页要按「200/403/500」筛选；现在码塞在 `meta` JSON 里，**无法建索引、无法 SQL 筛** | ✅ **实测 2000 条采样 100% 含 `status_code`**，`meta` 键恒为 `{method, status_code, elapsed_ms}` ⇒ 回填可 100% 覆盖 |
| **R4** | `notifications` | **+1 列 `link`**（VARCHAR(255)，可空） | 点通知要跳转；现在要靠 `source_type + source_id` 前端拼路径（`lib/notification-routes.ts`），新增一类来源就得改前端 | 4 行，`source_type` 已有 3 种，前端已有映射表 ⇒ 保留映射同时存快照 |

> ⚠️ **R3/R4 是「关联」而非「合并」**：把 JSON 里的字段提成真列，是为了能索引/筛选，不是把表并掉。
> 回填策略：
> - `status_code`：SQLite 用 `json_extract(meta,'$.status_code')` 一次性提取，**实测 2000/2000 有值**；
> - `link`：**留空**。实测 4 条通知里 3 条 `source_id` 为 NULL（`note_data_import` ×2 / `note_data_sync` ×1），
>   只有 1 条 `llm_gateway_alert` 带 id ⇒ 历史通知本来就没有可靠跳转目标，**不造假**（缺值口径硬约束⑤）。

## 7. 数字订正（推翻 46/47 的旧口径）
