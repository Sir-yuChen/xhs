## 3. 阶段② 排期设计

| 发布模式 | 行为 |
|---|---|
| `immediate` | 立即走发布流程 |
| `scheduled` | 只写 `scheduled_at`，由调度器到点补跑 |

### 3.1 为什么排期必须落库而不是 sleep（核心设计）

> **排期用 `scheduled_at` 落库 + 调度器补跑，绝不在执行侧 `sleep` 等时间。**

理由：
1. **进程崩溃不丢任务** —— `sleep` 方案下进程重启，待发任务全部丢失。
2. **天然幂等** —— 补跑逻辑是「取 `scheduled_at <= now` 且状态为 `scheduled` 的任务」，重复触发不会重复发。
3. **可观测** —— 待发任务在发布中心可见可取消；`sleep` 方案下不可见。

**实现**：`backend/app/services/scheduler_service.py:181` `run_due_publish_jobs`（job 名 `due_publish_runner`，默认每 60s）。

> **这是现有架构的一个优点，二开必须继承。**

### 5.1 图集发布的组装步骤（`_post_uploaded_image_note`）

| # | 步骤 | 关键细节 |
|---|---|---|
| 1 | **组装 `post_loc`（地点）** | 传字符串时先调 `get_location_info` 查 POI；查不到抛 `未找到该地点` |
| 2 | **调用 `get_post_note_image_data(...)`** | 生成发布体 `data`，此时 `common.goods_info` **恒为 `{}`**（`xhs_utils/xhs_creator_util.py:177`） |
| 3 | **⚠️ 空地点必须删键** | `if not post_loc: data["common"].pop("post_loc", None)`（`:137-138`）——**空对象会被服务端以参数错误打回** |
| 4 | **话题处理** | 逐个调 `get_topic` 查 ID → append 到 `hash_tag` → 同时把 ` #话题[话题]# ` 追加到 `desc` 末尾（`:139-156`） |
| 5 | **生成请求参数** | `api._request_params(post_api, data, "POST", referer, target_origin=api.edith_url, order_wire_headers=False)` |
| 6 | **⚠️ 手动补 `x-rap-param`** | `headers["x-rap-param"] = generate_x_rap_param(...)`，用 **Creator 专用 RAP 模板**（`rap_fingerprint_creator.json`，436B，`creator_api_adapter.py:155`） |
| 7 | **POST** | 目标：`{edith_url}/web_api/sns/v2/note` |
| 8 | 结果判定 | `payload["success"] == False` → 抛错，取 `msg` / `message` |

### 5.2 三个容易踩的坑

| 坑 | 说明 |
|---|---|
| **`post_loc` 空对象** | 必须**删除键**，传 `{}` 会被拒 |
| **话题要双写** | 既进 `hash_tag` 数组，也要拼进 `desc` 文本（`#名称[话题]#` 格式） |
| **RAP 签名必须手补** | `order_wire_headers=False`，且要显式 `generate_x_rap_param`——因为 Creator 走**独立 RAP 模板**，与 PC 不同 |

## 6. 状态机

```
                    ┌─────────┐
       建任务 ────▶ │ pending │
                    └────┬────┘
                         │ 触发发布（立即 / 到点补跑）
                         ▼
                   ┌───────────┐
                   │ publishing│  ← 串行约束：同账号不可并发
                   └─────┬─────┘
              ┌──────────┼──────────┐
              ▼          ▼          ▼
      ┌──────────┐ ┌──────────┐ ┌───────────┐
      │ published│ │  failed  │ │ cancelled │
      └──────────┘ └────┬─────┘ └───────────┘
      写 external_note_id │ 写 publish_error
                          │
                    可 retry（回 pending）
```

### 6.1 防重复发布的防线（✅ 第 4 道已于 2026-09-18 补齐）

| # | 防线 | 强度 | 问题 |
|---|---|---|---|
| 1 | 状态机（`publishing` 时不再触发） | 中 | 无原子性保证 |
| 2 | 调度器 `max_instances=1` | **仅单进程内** | 多副本失效（T-108 待做） |
| 3 | 补跑幂等（只取 `scheduled` 态） | 中 | 状态写入前崩溃会重发 |
| 4 | **数据库唯一约束** | ✅ **已补齐** | 2026-09-18（T-103） |

> **原来的判断**：发布是不可逆写操作，前三条都是应用层防线，只有第 4 条可靠。
> **✅ 已落地**：`publish_jobs.idempotency_key`（**nullable + UNIQUE**），键 =
> `{platform}:{账号}:{sha256(标题|正文|规范化 publish_options)[:32]}`。
>
> **关键设计**：列必须 **nullable**——否则「建了 → 取消 → 再建同样内容」这条**合法流程**会被唯一索引无故挡死。
> 生成时机是「**发布前认领**」而不是建任务时。占用语义收敛为一条不变式：
> **键非空 ⇔ 处于占用态（`publishing` / `published` / `scheduled`）**；`failed` 与「从 `scheduled` 取消」**不释放**。
>
> **实现**：`services/publish_service.py`（新增）；决策与完整理由见
> `05_项目沉淀/01_架构决策记录_ADR.md` **ADR-013**。

### 6.1.1 三个「重复发文」入口（必须一起看）

「重复发文」不是一个 bug，而是**同一事实的三个入口**。只修其中一个仍会重复发文：

| # | 入口 | 缺陷 | 状态 |
|---|---|---|---|
| 1 | 重复**创建**同内容任务 | DEF-002 | ✅ 已修（T-103，幂等键） |
| 2 | 重复**执行**同一个已提交任务（原地 retry） | **DEF-031** | ✅ 已修（`external_note_id` 非空即拒绝重试 → 409） |
| 3 | 多副本**重复调度** | DEF-003 | ⬜ 待做（T-108） |

> **三者共用同一个事实：「这个 job 是否已提交给平台」。**
> 因此 **T-108 必须复用 T-103 的幂等键语义**，而**不能**另起一套判断口径——
> 否则会出现「应用层放行 → 数据库 `IntegrityError`」的分裂。
>
> **另一个必须记住的语义收紧**：`external_note_id` 是「**不可逆的已提交证据**」，
> **不是可清空的中间态**。只要它非空，该 job 就是终态，只能新建任务，不能原地重试。

## 9. 二开新增：商品笔记编排约束

| 约束 | 理由 |
|---|---|
| **单店铺 / 单账号串行** | 同账号并发发布 = 重复发布与风控双重风险 |
| **每日上限更保守**（建议 ≤5 篇/日） | 商品笔记是营销内容，平台对「商家批量发营销笔记」更敏感 |
| **最小间隔 ≥60min** | 同上 |
| **同商品冷却 ≥72h** | 同一商品短期内多篇 = 刷屏 |
| **发布前复核商品状态与价格** | 商品可能已下架/改价，生成的笔记价格与实际不符 = 违规 |
| **矩阵分发需内容变异** | 多账号发同款内容会触发去重降权，模板必须按账号维度变异 |

> （为的是「同步 + 批量管理」而非「生成必须依赖它」），这条要复评。
>
> ⚠️ **免责前提**：项目声明仅供学习交流、禁止商业化。商品笔记属商业推广，**用途合规性需自行评估**。

| 段 | 内容 |
|---|---|
| 角色/总则（system） | 只使用【商品信息】给出的事实；不虚构价格/功效/认证/销量/评价；不用绝对化用语；不站外引流；**输出必须是 JSON** |
| 【商品信息】 | **白名单字段**：`item_id` / `title` / `article_no` / `price_min_fen|max_fen` / `stock` / `sku_count` / `on_sale_sku_count` / `category` / `sales_total` + `price_text`（元）。**`xsec_token` 等一律不进 Prompt** |
| 【输出结构】 | 只回 `{"title": "...", "body": "...", "tags": [...]}`，不要解释文字 |
| 【要求】 | 标题 ≤20 字且含核心词；正文 300–800 字分段；**价格只能写给定价格**；标签 3–6 个 |
| 【禁止】 | 医疗/功效宣称、绝对化用语、编造认证/销量/评价、站外引流 |
| 【额外风格要求】 | 调用方传入（长度上限 400 字，避免塞整篇参考文） |

**解析容错**：整段 JSON → ``` 围栏内 JSON → 首 `{` 到末 `}` 的子串；都不行**抛错**
（不把花括号塞进正文发出去）。

### 12.3 护栏流水线（生成后、入库前）

| 关卡 | 判定 | 说明 |
|---|---|---|
| 绝对化用语 | 命中即拦 | 《广告法》第九条口径；词表见 `ABSOLUTE_TERMS` |
| 违禁/引流词 | 命中即拦 | 站外引流（微信/淘宝/私聊…）、违规商品表述（高仿/原单…） |
| 功效宣称 | 命中即拦 | `EFFICACY_TERMS`（治疗/祛痘/美白…） |
| **价格一致性** | 区间外即拦 | 标题/正文里的价格数字必须落在商品价格区间内（分→元换算与展示层同源）；**商品价格未知 → 不拦但明确写「本次未校价」**（缺值不推断） |
| 格式 | 逐条报问题 | 标题/正文/图片三项，**每条都有可读原因** |

**命中结果带 `field`（title/body）与字段内 `position`** —— 页面据此高亮；早期实现把标题与
正文拼起来再找位置会整体偏移（标题多长偏多少），已修正。

> ⚠️ **词表来源**：按法条与行业惯例**人工整理**，**不是**平台官方词表（平台词表不公开）。
> 因此这是「宁可多拦」的保守集：命中即拦并回原因，由人工复核放行 —— 与设计原则「不造假」
> 一致（不假装能给出平台级判定）。

### 12.4 失败与边界（都可判别，不用 500 糊过去）

| 情况 | 响应 |
|---|---|
| 未绑定千帆 | 400 `QIANFAN_BINDING_REQUIRED` |
| 商品不属于本店铺 / 已删除 | 404 `QIANFAN_ITEM_NOT_FOUND`（**不调模型**：省 token，也避免写错商品） |
| 该用户没有默认文本模型 | 400 `AI_MODEL_NOT_CONFIGURED`（模型配置是 **per-user** 的） |
| 模型服务拒绝（如 401） | 502 `AI_PROVIDER_ERROR` +「模型服务返回 401（模型 @ base_url）。请检查 API Key」 |
| 模型没按 JSON 回 / 返回为空 | 502 `AI_GENERATION_FAILED` —— **不编正文** |
| 生成内容被护栏拦下 | **200** + `ok=false` + `block_reason` + `guardrails.hits` + **仍然返回正文**（页面要能显示为什么被拦） |

### 12.5 已知前提（真机实测，2026-09-19）

- **商品来源**：千帆 `search_item_v2` 的 `whole_keywords` 支持按 `item_id` 精确查回（T-29 实测），
