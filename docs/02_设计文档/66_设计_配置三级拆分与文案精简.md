# 设计 66 · 配置三级拆分与界面文案精简

> 用户口径（2026-10-25）：
> ① 「**将 config 进行详细拆分**，系统级只展示系统管理中展示系统公共的，用户级别也是
>    该用户下公共的配置，工作区域级别的是指定工作区域私有的，你详细拆分，**不要混乱展示**」
> ② 「页面中有很多说明都是**占用页面空间，且啰嗦**，应**简短且只说明核心问题**，
>    不必要的说明全部移除」

## §1 问题：三级配置混在一起展示

三级配置的实现是「一张表三个归属」（设计 64 §1.2），但**每个键该属于哪一级从未定义**。
后果是页面上靠「库里哪一级有行」来分区：

| 现象 | 实例（2026-10-25 实测） |
|---|---|
| 同一个键在两级都有行 ⇒ **两个页面都列它** | `crawl_rate_limit_per_minute` 系统级 1 行 + 用户级 **5 行** |
| 全站开关被放进用户级 | `register.enabled` 系统级 1 行 + 用户级 **2 行**，读取还特判「以管理员行为准」 |
| 某键三层都没行 ⇒ **哪个页面都不显示** | 工作区级的 3 个键在库中 0 行 ⇒ 页面上完全看不到，**等于不可配置** |

## §2 判据：归属由**代码**定死（`SETTING_SCOPES`）

不是「数据在哪一级」，而是「这个键在语义上属于哪一级」。见
`services/settings_service.SETTING_SCOPES`：

| 级别 | 判据 | 键 |
|---|---|---|
| **system** | ~~全站唯一事实；让某一用户/工作区覆盖它**没有意义**~~ → **被 §2.1 取代** | ~~限流额度、同步并发、账号间停顿、媒体上传并发、OCR 并发、~~ API/业务日志保留、定时任务日志保留、**开放注册** |
| **user** | 每个用户各自成立（各账号/各店铺） | 订单同步游标 |
| **workspace** | 某个平台工作区私有（不同平台可以不同） | ~~允许重复发布商品笔记、笔记图片总数上限、SKU 名称字数上限~~ → **被 §2.1 取代**：+限流额度、同步并发、账号间停顿、媒体上传并发、OCR 并发 |

### §2.1 归属修订（2026-10-25，**取代 §2 的 system 一栏与 workspace 一栏**）

用户口径：「**私有配置，只在对应工作区域内展示**，不错误的展示在配置管理页面中了」。

**新判据**：凡取值取决于「**接哪个平台**」的，一律归**工作区级** —— 即使本系统
目前只有小红书一个工作区。判据不是"现在有几个平台"，而是"换个平台它是否照用"。

| 键 | 原归属 | 现归属 | 为什么 |
|---|---|---|---|
| `crawl_rate_limit_per_minute` | system | **workspace** | 限的是「对小红书每分钟请求几次」（库里值 8 正是小红书实测口径） |
| `xhs_sync_account_parallelism` | system | **workspace** | 同步几个**小红书账号** |
| `xhs_sync_account_gap_seconds` | system | **workspace** | 账号间停顿 = 小红书风控节奏 |
| `xhs_image_upload_parallelism` | system | **workspace** | 小红书图床上传并发 |
| `xhs_ocr_parallelism` | system | **workspace** | 小红书违规词 OCR 并发 |

**归属分布：8/1/3 → 3/1/8**（系统 3 / 个人 1 / 工作区 8）。

**入口位置也随之推翻**（原「放配置管理页 + 标题标注『只对小红书生效』」被用户否掉：
**标注不等于归属正确**）：工作区配置的入口挂 `business-line-badge.tsx`（业务线标识行），
该组件只在业务线页面渲染 ⇒ 结构上保证「只在对应工作区内出现」。
配置管理页只剩 `scope="system"`。

**必要配套（否则静默失效）**：`effective_value` 原按「用户级 → 系统级」查行，
这 5 个键改归工作区级后行落在工作区级 ⇒ 页面能改、业务读旧值、**零报错**。
已加 `_workspace_row_any`（优先 `workspace IS NOT NULL`，退到早期
`user_id IS NULL ∧ workspace IS NULL` 那一行）。实测三键读取值不变（8 / 5 / 3）。

**`scope_hit` 口径同步修正**：它原按「数据行落在哪一级」上报，与归属打架
（`crawl_rate_limit_per_minute` 的行物理在系统级位置 ⇒ 界面显示"来源：系统级"，
让人以为改的是全站设置）。已改为按 `SETTING_SCOPES` 上报**归属**。

### 三条硬规则

1. **内置键必须登记**：漏登记 ⇒ 三个页面都不显示（等于不可配置）⇒ 守卫会红。
2. **同一个键只属于一级**：不能同时出现在两个页面（「不要混乱展示」的机械判据）。
3. **用户自建的键不受此表限制**：用户有权建任意自定义键；若按清单过滤，
   刚建的键会**立刻从列表消失**（实测：`test_settings_crud_round_trip` 建完再查就找不到）。

## §3 缺行时合成「默认值」虚拟行

`list_scoped_settings()` 按归属定出本级该有的键，**某键在该级还没有行 ⇒ 合成一条
`id=-1` 的虚拟行**（值取 `BUILTIN_DEFAULTS`，不落库）。

* 让「没配过」的键在页面上**可见**（否则它不可配置）；
* `id=-1` 让前端区分「新建（POST）」与「更新（PUT）」；
* 用户点保存时才真正落行。

## §4 存量数据迁移

`register.enabled` 从用户级提到系统级（取管理员那行的值，删其余用户行）；
`crawl_rate_limit_per_minute` 删用户级 5 行残留（系统级为唯一事实）；
三个工作区级键删系统级的 1 行（它们不再属于系统级）。

迁移脚本一次执行，幂等（先查再改）。

## §5 界面文案精简

### 现状（实测字数）

库里的 `description` 是**给开发看的**：把设计依据、历史沿革、实现细节全写进去，
50–170 字。页面「说明」列占一整行，用户读不完也不关心。

| 键 | 原字数 |
|---|---|
| `xhs_ocr_parallelism` | 170 |
| `xhs_image_upload_parallelism` | 159 |
| `xhs_note_image_total_limit` | 140 |
| `register.enabled` | 117 |
| `xhs_allow_duplicate_goods_publish` | 116 |

### 改法

* 新增 `config/initial_data/setting_descriptions.json` —— **界面专用短文案**
  （≤30 字，实测 14–22 字），只回答「这个开关做什么 / 改它会怎样」；
* `serialize_setting()` 下发 `short_description(key)`，**不再下发库里的长 description**；
* 技术依据留在**代码注释与设计文档**，不上界面。

### 页面结构

| 位置 | 改前 | 改后 |
|---|---|---|
| 系统管理 → 配置管理 | 标题下 3 行说明段落 | **无段落**，标题「系统配置」 |
| 个人配置页 | 标题下 3 行说明段落 | **无段落**，标题「个人配置」 |
| 配置表格顶部 | 常驻 `HINTS[scope]` 一句话（三档各一行） | **整块删除**（分区已由页面标题表达） |
| 空表提示 | 30+ 字 | 「暂无系统配置」 |
| 删除确认 | 25 字 | 「删除后回落到默认值。」 |

**判据**：页面上不出现「这个页面是干什么的」的解释性长文 —— 那是文档的活。

## §7 本轮踩到的两个基建缺陷（同批修）

1. **`db_engine` 夹具没给 `db_factory` 路径打桩** ⇒ 服务自开的 Session 连到真实库，
   报 `字段 xxx 不存在`（看起来像代码 bug）。已把 `patch_service_sessions` 移进
   `db_engine`，所有用 engine 的夹具自动覆盖。
2. **`drop_schema` 的 teardown 丢掉过** ⇒ 测试库累积几十个旧结构 schema，
   某些用例的 `search_path` 命中旧 schema ⇒ 假红。已补回并加注释说明「为什么不能省」。
