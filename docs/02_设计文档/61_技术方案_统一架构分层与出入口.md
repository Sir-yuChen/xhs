# 二、市场成熟方案调研（2024–2026 口径）与取捨

| 方案 | 要点 | 本项目的取舍 |
|---|---|---|
| `zhanymkanov/fastapi-best-practices`（社区事实标准） | **按业务域分包**（每域 router/schemas/models/service/dependencies/exceptions）；依赖注入做链式校验；全局 CustomModel 基类 | 域分包**不采纳**为大爆炸重构（会牵动 84 条已修缺陷的判据测试）；采纳其「依赖只能向下」「链式 DI」口径。`get_owned_active_account` 已是该形态 |
| `tiangolo/full-stack-fastapi-template`（官方） | type-based 单层（models/crud/routes/core） | 官方自认适合中小型；本项目 62 表 390 端点已超出适用边界。只借鉴 core/ 三分（config/security/deps）—— 已具备 |
| Netflix Dispatch / 模块化单体 | bounded-context 切模块 + **模块间单向依赖机器强制**（import-linter）+ 模块内不依赖框架 | **采纳**：先立 import-linter 合同让违规可见，再定切分线；`adapters/` 已是「框架外」雏形 |
| 统一响应包络 `{code,message,data}` | Java 风格；FastAPI 社区普遍视为反模式（摧毁 HTTP 语义与 OpenAPI schema） | **成功不包络**（保持原生 + 补 response_model）；**错误统一**（全局 exception_handler + 结构化 detail）—— 与前端 `api.ts` 现有三级兜底完全兼容，零前端改动 |
| 中间件管线 | 声明式集中装配一处；横切关注优先用依赖/装饰器而非全局中间件 | 采纳（G5）；限流维持现有依赖式实现（已是正解） |

# 三、目标架构（一张图）

```
对外统一出入口            main.py（只做装配）= create_app() + uvicorn 入口
│                          ├─ api/registry.py  ★按域声明路由清单，一处 include
│                          ├─ core/middleware.py ★CORS/审计/SPA/缓存头 一处声明式装配
│                          └─ core/startup.py   ★lifespan 分步函数（播种/租约/看门狗/恢复）
├── 中间件与横切           CORS → ApiAudit → （错误统一在 exception_handler，不在中间件）
│                          require_perm + ROUTE_PERMS + get_current_user（现状保留）
├── 业务层                 services/ 按依赖方向分两档：
│                          ├─ services/common/ ★被广泛依赖者（shop_binding/account/…）下沉为稳定公共层
│                          └─ services/<域>    只允许 import common 与 core，禁互相网状
├── 平台适配器             adapters/（零业务依赖；rate_limiter 改构造注入）
├── 基础公共组件           core/（**禁 import services/api**，import-linter 合同强制）
└── 数据                   models/ + alembic（PG-only，现状保留）
```

**错误契约（G3 的落点）**：`core/errors.py` 定义 `BizError(code, message, http_status)` 层级 +
2 个全局 handler（BizError → `{detail: {code, message}}`；兜底 Exception → 500 结构化）。
HTTP 语义与前端解析不变，只是把「事实上靠约定」变成「后端强制」。

# 四、两条机器强制守卫（先于任何搬码）

1. **依赖方向合同**：引入 `import-linter`（或等价 AST 守卫，落 `tests/backend/`）三条合同：
   `core 不得 import services|api`；`adapters 不得 import services|api`；`api 不得 import api.<其他域>`。
   **先豁免现状全部违规点并逐条登记**（G1 的 8+1 处、G8 的 10 处），清一处销一条豁免 ——
   守卫先「如实记账」，再收敛归零。这遵循本项目「规范必须可执行、守卫要过变异验证」的纪律。
2. **response_model 覆盖率**：AST 扫 `api/`，统计「声明 response_model 的端点占比」钉进守卫
   （先钉当前基线值，只许升不许降），随 G2 施工逐域抬升。

# 五、与既有纪律的兼容性

- **不动平台只读边界 / 平台优先本地跟随 / 禁无分页插槽全量方法** —— 本方案全部是结构搬移，不触碰任何平台交互。
- **不大爆炸**：84 条已修缺陷的判据测试是资产，凡是「判据测试锚着的实现文件」移动时**必须连测试锚一起改**并在台账记录。
- 每轮施工走三层测试循环 + 文档回写 + 三校验脚本，与现有节奏完全一致。
