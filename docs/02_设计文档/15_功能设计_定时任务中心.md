# 功能设计 · 定时任务中心（调度模块重构 · 贴近若依）

> - **阶段**：二 · 设计
> - **访问端视角**：**调度侧 + Web 运营端**——调度侧定义"谁在什么时候跑什么"，运营端提供管理界面
> - **覆盖**：任务注册表、`scheduled_jobs` / `scheduled_job_logs` 两张新表、DB 驱动调度器、AutoTask 归宿、`/api/schedule` 端点族、任务中心三 Tab 前端、存量迁移
> - **版本**：v1.0 · 2026-09-24（方案待评审，**未开始写代码**）

---

## 0. 一句话

把现在"硬编码 8 个系统 job + 一张简化 `auto_tasks`"的调度模块，重构为**若依式的统一任务中心**：DB 里的任务行（cron/interval/at 触发器 + 错过策略 + 并发开关 + 暂停/恢复/执行一次）+ 每次执行一行调度日志 + 代码侧注册表白名单；前端任务中心从"只有一张执行记录表"扩成按任务类型体系（§3.1）组织的**一次性任务 / 定时任务 / 周期任务 / 调度日志**四个 Tab。

## 1. 为什么要重构（现状盘点）

### 1.1 现状：两套并存的调度

| 层 | 载体 | 现状 | 问题 |
|---|---|---|---|
| 系统级 job | `scheduler_service.py::build_due_publish_scheduler()` 硬编码注册 8 个 job | 间隔/启停全部来自 `config.py` 环境变量，运行期不可见不可调 | 用户改不了、看不见；`/tasks/scheduler/status` 只暴露 id + next_run_time |
| 用户级自动任务 | `auto_tasks` 表 + `/api/auto-tasks` | `schedule_type ∈ {manual, daily, weekly, interval}` 四档简化调度 | 无 cron、无错过策略、无并发开关、无暂停/恢复按钮（status 可改但无专门入口）、**每次执行不留日志**（只有 `last_run_at` / `total_published` 两个计数器） |
| 执行记录 | `tasks` 表 + `/api/tasks` | 前端"任务中心"只有这一张表 + 调度状态卡 | 看不出"配了什么任务、下次什么时候跑、上次为什么失败" |

### 1.2 已登记的设计缺口（设计 08 §2.2 / §8）

| # | 缺口 | 本方案的处理 |
|---|---|---|
| S-2 | `next_run_at` 在执行**之后**计算 ⇒ 周期漂移 | 改由 APScheduler 触发器维护；行内 `next_run_at` 仅作展示/退避门 |
| S-3 | 失败无退避 ⇒ 60s 重试风暴 | runner 内置**失败退避门**（DB 侧，见 §6.5） |
| S-4 | 调度器时区 UTC，与业务时区不一致 | 调度器改 **Asia/Shanghai**（见 §6.6） |
| S-5 | 无每日上限 / 冷却 | 超出本模块范围（属 M6 编排护栏），本文档不涉及 |
| S-1 | 多副本无分布式锁 | **保持缺口**，技术债 T-03，本文档不改 |
| §2.2-1~3 | 自动运营管线三缺陷（漂移/无退避/无上限） | 前两个随本方案修复；上限仍归 M6 |
| — | `_execute_auto_task_background` 与 `run_auto_task` 是**同一管线的两份实现** | 合并为单一实现（见 §7.2），属 DEF-044/047/058 同型问题 |

### 1.3 已知运行坑（迁移时必须保住）

- **持久化 job store**（§24.9）：`apscheduler_jobs` 表指向同一个 SQLite；store 里已有同 id job 时**跳过注册**，否则 `next_run_time` 重置为"现在 + 周期"，跨重启计时白做。
- **风控三件套**：`max_instances=1` + `coalesce` + 显式 job id，所有现有 job 都带。
- **限流等待式** `wait_allow()` 在业务函数内，不随调度改造改变。
- **总开关** `scheduler.enabled` 默认 `false`：调度器不启动时 job 行仍可增删改（只是不跑），`GET /api/schedule/status` 报告实情。

## 2. 若依定时任务模块调研结论

来源：若依 Cloud 文档站（doc.ruoyi.vip/ruoyi-cloud）+ `ruoyi-job` 模块源码结构（`SysJobController` / `SysJobServiceImpl` / `ScheduleUtils` / `QuartzJobExecution` / `QuartzDisallowConcurrentExecution` / `JobInvokeUtil`）。

### 2.1 功能清单（若依"定时任务"菜单下两块）

**任务管理**：

1. 任务增删改查（任务名称、任务组名、调用目标、cron 表达式、备注）
2. **暂停 / 恢复**（改 `status` 同步更新调度器，不是只改数据库）
3. **执行一次**（不等触发时间，立即手动跑一次，同样记日志）
4. **cron 表达式生成器**（前端组件，可手输可点选，常用预设）
5. **执行策略（misfire）**三档：立即执行（补跑全部积压）/ 执行一次（积压合并补一次）/ 放弃执行（全部丢弃）
6. **是否并发执行**：允许 / 禁止（ Quartz `@DisallowConcurrentExecution` ）
7. 任务分组（`DEFAULT` / `SYSTEM`）

**调度日志**：

8. 每次执行记一行：任务名、组名、调用目标、日志信息、成功/失败、异常详情、起止时间
9. 日志列表查询（按任务名/状态/时间）、按 id 批量删除、一键清空

### 2.2 两张表（若依原版字段）

| `sys_job` | 类型 | 说明 |
|---|---|---|
| `job_id` | bigint | 主键 |
| `job_name` | varchar(64) | 任务名称 |
| `job_group` | varchar(64) | 任务组名（DEFAULT/SYSTEM） |
| `invoke_target` | varchar(500) | 调用目标字符串（Bean 调用 / Class 类调用） |
| `cron_expression` | varchar(255) | cron 表达式 |
| `misfire_policy` | varchar(20) | 1=立即执行 2=执行一次 3=放弃执行 |
| `concurrent` | char(1) | 0=允许 1=禁止 |
| `status` | char(1) | 0=正常 1=暂停 |
| `create_by/create_time/update_by/update_time` | | 审计字段 |
| `remark` | varchar(500) | 备注 |

| `sys_job_log` | 类型 | 说明 |
|---|---|---|
| `job_log_id` | bigint | 主键 |
| `job_name/job_group/invoke_target` | varchar | **执行时快照**（任务删了日志仍可读） |
| `job_message` | varchar(500) | 日志信息 |
| `status` | char(1) | 0=成功 1=失败 |

⚠️ 若依两张表**无外键**——日志故意不随任务删除而消失。

### 2.3 安全设计（必须理解的一条）

若依的 `invoke_target` 是**自由字符串**（`ryTask.ryParams('ry')` / 全限定类名.方法(参数)），靠 `ScheduleUtils` 里的**白名单常量**拦恶意字符串（早期版本出过 RCE 类问题后才加的）。Python 生态里"按字符串 importlib 反射"比 Java 更危险（`os.system` 一行就能拼出来），所以本项目**不抄自由字符串**，改用**代码侧注册表白名单**（见 §5）。

### 2.4 借鉴 / 不借鉴总表

| 若依能力 | 本项目 | 决定 |
|---|---|---|
| 任务 CRUD + 暂停/恢复 + 执行一次 | 照抄（端点族 `/api/schedule`） | ✅ |
| cron 表达式 + 生成器 | 照抄（APScheduler `CronTrigger` 原生支持 6 位 cron） | ✅ |
| misfire 三策略 | 照抄语义，映射为 APScheduler 参数 | ✅（§6.3） |
| concurrent 允许/禁止 | 照抄字段；**注册表可设硬顶**（平台写操作恒禁止并发） | ✅（§6.4） |
| 任务分组 | 照抄（DEFAULT/SYSTEM 两组） | ✅ |
| 调度日志（快照字段 + 批量删 + 清空） | 照抄（无 FK，快照 name/key） | ✅ |
| invoke_target 自由字符串 | **不抄**，改注册表白名单 | ❌（§5） |
| 纯 cron 单一触发器 | **不抄**，cron + interval 双触发 | ❌（§6.2：系统 job 有 60s / 小时级，cron 表达不了秒级） |
| Quartz 引擎 | 不抄，沿用 APScheduler（已在用，不引新依赖） | ❌ |
| 集群 / 多数据源调度 | 不抄（单机单库，S-1 保持缺口） | ❌ |
| 日志自动清理策略 | 不做（手动清理即可，YAGNI） | ❌ |

### 3.1 任务类型体系（2026-09-24 用户口径，任务中心的组织维度）

| 类型 | 语义 | 载体 | 实例 |
|---|---|---|---|
| **一次性任务** | 手动触发，跑一次即止；**没有"定义行"**，点击即执行 | `tasks` 表（执行记录） | 账号卡片「同步笔记」「同步商品」、抓取、AI 改写、导出、手动发布 |
| **定时任务** | 指定未来时刻执行**一次**，成功后自动办结（`status=completed`） | `scheduled_jobs`（`trigger_type="at"` + `run_at`） | 「明天 15:00 跑一次笔记同步」 |
| **定时周期性任务** | 按 cron / interval 反复执行 | `scheduled_jobs`（`trigger_type="cron"/"interval"`） | Cookie 巡检（2h）、自动运营管线（每天 9:00）、清理（6h） |

三条边界：

1. **「执行一次」按钮对三类都可用**——手动触发不改变任务的调度属性（若依同）；
2. **定时发布（`PublishJob` scheduled）不算第四类**：它是发布链路的一次性定时任务，管理界面在发布页（`publish_jobs` 自有台账），任务中心不重复一份（单一真相源）；
3. 一次性任务**不进 `scheduled_jobs`**：`tasks` 行已带进度 / 取消 / 重试，再建调度行就是同一语义两份实现。

任务中心前端按这套体系组织页签（见 §9.1）：**一次性任务 / 定时任务 / 周期任务 / 调度日志**。

> ⚠️ **本节已被修订（2026-09-24 同日 R14 / R15 / R16，原句保留见上）** —— 上面这张表和三条边界
> 是**「任务中心的页面组织维度」**（哪个页签装什么），描述**依然有效**。但**任务自身的类型维度**

**三档语义（R14，2026-09-24 用户口径；取代上文「`cron` / `interval` / `at`」）**

| 档位 | 取值 | 是否参与调度装配 | 备注 |
|---|---|---|---|
| **手动** | `manual` | ❌ **不注册** | 只能点「执行一次」立刻跑；`cron_expression` / `run_at` 留空 |
| **Cron 周期** | `cron` | ✅ | 6 位 cron；「间隔周期」并入此档（每 N 小时写成步长式 cron） |
| **定时一次** | `at` | ✅ | 到 `run_at` 执行一次，成功后 `completed`（语义不变） |

常量：`models/scheduled_job.py` 的 `TRIGGER_TYPES = (TRIGGER_MANUAL, TRIGGER_CRON, TRIGGER_AT)`；
另出 `SCHEDULED_TRIGGER_TYPES = (TRIGGER_CRON, TRIGGER_AT)`（**参与装配的档位**，供装配守卫与筛选复用）。

**`manual` 不装配的两处落点**（缺一即「切档后残留旧注册」）：

1. `scheduler_service._register_job_in_scheduler()` 开头 `if job.trigger_type == TRIGGER_MANUAL: return False`；
2. `sync_job_registration()` 的摘除判据：`status != "active" or trigger_type == TRIGGER_MANUAL` ⇒ `_remove_job_quietly()`。

### 4.1.1 账号维度隔离（2026-09-24 用户口径，DEF-066）

> **需求**：「数据库中的所有数据均需要按照平台账号维度进行数据隔离，避免多用户相互操作同一份数据」。
> 起因是隔离核查发现的三个真实缺口（详见缺陷台账 DEF-066）：① **内置任务是全局共享单行**
> （`user_id IS NULL`）—— 任何登录用户都能改它的 params / cron、暂停、删除、点「执行一次」，
> A 配的 `account_ids` 写在共享行上，B 执行同一行跑的是 A 的账号；② **`POST /jobs` 不过
> `account_ids` 归属校验**（PUT 过）—— 可建引用别人账号的任务行，`system.no_traffic_cleanup`
> 是平台删除操作 ⇒ 跨租户破坏性触发；③ **调度日志零隔离** —— `scheduled_job_logs` 无
> `user_id` 列，列表 / 删除 / 清空三个端点不过滤用户。

| 维度 | 口径 |
|---|---|
| **任务行** | 所有 `scheduled_jobs` 行必归属用户：内置种子行**按用户各一份**（判重从 `job_key + is_builtin` 改为 `job_key + user_id`）。列表 / 详情 / 改 / 删 / 暂停 / 执行一次**只认本人行**（`_get_visible_job` 不再放行 `user_id IS NULL`） |
| **播种时机** | ① 应用启动 `ensure_builtin_jobs()`（为**每个已存在用户**补缺失行）② **新用户注册**（`POST /auth/register` 落库后即播种，注册完打开任务中心就有这 7 条）③ 调度器装配 `sync_jobs_from_db()`（既有路径） |
| **执行范围** | 7 个系统任务的执行函数一律接收**行归属者的 `user_id`**（`JobSpec.user_scoped` 声明，runner 注入），账号查询恒带 `PlatformAccount.user_id == user_id`。`account_ids` 空 = **本人的全部账号**（不再是全库账号） |
| **参数归属** | `account_ids` 在建（POST）与改（PUT）**两条路都过归属校验**（只能选本人存活账号，`ACCOUNT_NOT_OWNED`）；建行 additionally 过 params 键白名单（`params_editable ∪ params_required`，`JOB_PARAMS_NOT_EDITABLE`） |
| **日志** | `scheduled_job_logs` 增 `user_id` 列（**执行时从任务行快照**，不 join）；列表 / 批量删 / 清空三个端点按 `user_id == 当前用户` 收口；任务删除后 `job_id` 置空的历史日志仍可归属（快照列不随任务消失） |
| **清理任务行** | `run_scheduled_cleanups` 把 `account.user_id` 传进 `run_no_traffic_cleanup` —— Task 审计行归属账号主人，不再兜底 `user_id or 1` |

**为什么不是「全局行 + 执行时按触发者收口」**：全局行的**配置本身**（cron / status / params）就是
多用户互相操作的共享状态 —— A 暂停一行，B 的巡检跟着停；执行范围再收口也挡不住配置互相覆盖。
按用户各持一行后，「你的调度你的、我的调度我的」，暂停 / 删改 / 账号范围天然互不影响。

**存量数据**（迁移 `a0b1c2d3e4f5`）：全局内置行按每个用户克隆一份（`account_ids` 重置为空 =
本人全部账号；该用户已有同 `job_key` 行则跳过）后删除原行；存量用户行的 `account_ids` 按归属
清洗（滤掉不属于行主的 id）；日志 `user_id` 从任务行回填，孤儿日志（任务已删）与全局行日志
归属**首个用户**（单用户库即唯一真实用户；历史可见性不丢）。

### 6.2 触发器：~~cron + interval + at 三形态~~ **cron + at 两形态（R14，2026-09-24）**

> ⚠️ **本节已被 R14 取代（原句保留于表内删除线）**：`interval` 形态**退役**，其表达力**并入 cron**
> （「每 N 小时」写成步长式 cron，如 `0 0 */6 * * *`）；新增 `manual` 档**不产生触发器**（不装配）。
> 原「`interval` 是必要的，因为 cron 写不出秒级」的理由**已不成立**：本项目 cron 是 **6 位**（含秒位），
> `0 * * * * *` 即 60s。见 §4.1 三档语义表与 §4.4 存量换算。

| trigger_type | 参数 | 用途 |
|---|---|---|
| `cron` | `cron_expression`（6 位：秒 分 时 日 月 周） | 周期任务（用户自建、自动运营管线、系统 job 的 60s / 2h / 6h 巡检 —— 全部用 cron 表达） |
| ~~`interval`~~ | ~~`interval_seconds`（1~86400）~~ | ⚠️ **R14 已退役**（并入 cron；列已删） |
| `at` | `run_at`（未来时刻） | **定时一次性任务**（§3.1）：到点执行一次，成功后行 `status=completed` 并不再注册；失败不自动重试（触发器已用掉），可「执行一次」或改 `run_at` 重新激活 |
| `manual` | —（无触发器） | **R14 新增**：不注册调度器，只能点「执行一次」立刻跑 |

偏离若依（纯 cron）的理由记在此：APScheduler 的 **date** 触发器是原生能力，`at` 填上"定时任务"这一类（若依无此形态）。
~~APScheduler 的 interval~~ **R14 后不再使用 interval 触发器**：本项目 cron 自带秒位，interval 的表达力是 cron 的真子集，
留着就是同一语义两份实现（`build_trigger()` 对 `manual` 抛 `ValueError`，对 `interval` 不再有分支）。
`job_registry.JobSpec` 的 `default_interval_seconds` 字段**一并删除**，8 个 spec 的默认值全部改为 `default_cron`。

### 6.5 执行包装器 `run_scheduled_job`（唯一执行入口）

```python
def run_scheduled_job(job_id: int, *, trigger_type: str = "scheduled") -> dict:
    # 1. 载入 job 行（独立 session）；行不存在 ⇒ 静默返回
    # 2. 退避门：backoff_until 未到 ⇒ 写 skipped 日志（duration=0），更新 last_run_at/last_status，返回
    # 3. 插日志行 status=running（started_at=now）
    # 4. spec.func(**params)：
    #      成功 ⇒ run_count+1、consecutive_failures=0、backoff_until=NULL、日志 success+message
    #      异常 ⇒ fail_count+1、consecutive_failures+1、
    #             backoff_until = now + min(5min * 2^(n-1), 6h)、日志 failed+exception_info[:2000]
    # 5. 刷新 last_run_at / last_status；next_run_at 由调度器维护（API 展示取活值，列值作兜底）
```

- 退避基数 5min、上限 6h 为常量，落在 runner 模块（**不进 config**——退避是调度正确性的一部分，不是可调业务参数）。
- **`at` 一次性任务的特例**（§3.1）：成功后行 `status=completed`（调度器侧 date 触发器用掉后 `next_run_time=None`，不会再响；下次启动同步自然不再注册）；失败**不进退避门**（没有下一发了，进了只会让「执行一次」被门挡住），留 `failed` 日志等用户处置。
- `skipped` 日志让“撞门不跑”在 UI 可见，不做静默跳过。
- **进度心跳 `progress_probe`（2026-09-27 补，设计 13 §35.17.3）**：`execute_job(..., progress_probe)` /
  `run_job_in_background(..., progress_probe=…)` —— 执行 `spec.func` 期间起 daemon 泵线程，每 **2s**
  把 `progress_probe()` 的 0–100 写进日志行 `progress`；**仅在 `running` 时写、绝不写终态**，
  probe 返回 `None` ⇒ 本次不写（缺值口径，不造 0）。**不传该参数 ⇒ 行为与改造前逐字一致**。
  动机：「任务进度」列原先只在终态被写（成功 100 / 失败 0），而账号卡驱动的同步是**分钟级**的，
  执行期间 UI 看不到任何变化。⚠️ 本能力**保留可用**，但账号卡链路已不再经过 `execute_job`
  （见下条），改由 `run_targeted_job` 自持泵 + 观测线程。
- **`run_targeted_job`：给一个「外部已建好的业务任务行」记账 + 观测（2026-09-27 定稿，设计 13 §35.17.2）**：
  `run_targeted_job(*, user_id, job_key, task_id, task_type, params_extra=None, progress_probe=None) -> log_id`

  | 它做什么 | 它**不**做什么 |
  |---|---|
  | 兜底播种该用户的 job 行（`seed_builtin_jobs_for_user`，幂等） | **不发起执行**（任务行由调用方建好、由账号任务 worker 跑） |
  | 建一行 `scheduled_job_logs`（`trigger_type=manual`）+ 写 `config_snapshot.params_override` | 不阻塞等终态（起 `task-watch-{task_id}` daemon 线程观测） |
  | 起进度泵（`TASK_WATCH_POLL_SECONDS = 2.0`）+ 观测线程 | 不覆写已是终态的日志行（进程被杀后的恢复路径不打架） |

  终态映射：任务行 `done` ⇒ `_mark_success`；其余（`failed` / `cancelled` / `missing`）
  ⇒ `_mark_failed`。**取消也算「没成功」**（用户点取消是显式动作，日志再报 success 就是自相矛盾）。
  ⚠️ **`timeout` 不是终态**：`_watch_task_run` 的 `while True` 只在 `status != "timeout"` 时跳出，
  遇到 `timeout` 只**继续等**（日志保持 `running`、泵继续写心跳）。
  ~~观测超时上限 `TASK_WATCH_TIMEOUT_SECONDS = 60 * 60`。~~ ⇒ **该常量已从代码删除**（2026-09-27
  用户口径「任务无需超时校验」，设计 13 §35.17.3）：观测线程传 `timeout_seconds=None` ⇒ **无限等**。
  ⚠️ `await_task_terminal` 仍**保留** `timeout_seconds` 形参，但当前唯一在传数值的调用方是
  `scheduler_service.TARGETED_AWAIT_TIMEOUT_SECONDS = 60 * 60`（cron **全量定向**路径的等待上限，
  与任务日志的观测线程不是同一回事）。

    终态进度（`sync_task_service.progress_percent(payload["progress"])`）时以它为准（比泵的 2s 采样准）；
  * 观测线程的失败原因**兜底文案不再拼状态码**（~~`f"任务状态 {status}"`~~ ⇒ 用户看到

### 6.8 调度器守活（DEF-067，2026-09-25 本机实测补）

**现场**：2026-09-25 16:00:06，六个作业正常跑完之后，APScheduler 主循环在
`base.py::_process_jobs` 的 `jobstore.update_job()` 上抛
`sqlite3.OperationalError: database is locked` ⇒ **整个主循环线程带异常退出**；
此后 **14 分钟一个作业都没跑**（`system.due_publish` 是 `0 * * * * *`，本该每分钟跑一次）。
16:14 手工重启后 **启动即复现** —— 新进程的启动段（`alembic` / `init_db` 的写事务
与 job store 首次写撞车）又死了一次主循环。

**为什么当时"看不出来"**：APScheduler 3.11 的 `state` **只在 `shutdown()` 里改**，
主循环线程带异常死掉时它仍是 `STATE_RUNNING` ⇒ `scheduler.running` 返回 `True`；
`/api/schedule/status` 的 `running` 原来直接读它，前端顶栏照挂「运行中」。
**端点、UI、日志三处都没有任何异常信号**（§13「UI 不谎报」当时只做到了 `enabled` 那一半）。

**根因**：`SQLAlchemyJobStore` **自建引擎**，不走 `core/database.py` 的连接事件监听
⇒ 拿不到 `PRAGMA busy_timeout=5000`，只剩 pysqlite 默认的 **5 秒**。5 秒内抢不到写锁就抛，
而这一抛恰好发生在**主循环里** ⇒ 线程死。「等锁时长」是唯一能把它从「抛」变成「等」的旋钮。

**两半修法（缺一不可）**：

| 半边 | 实现（`services/scheduler_service.py`） | 守的什么 |
|---|---|---|
| **治因** | `_persistent_jobstores()` 传 `engine_options={"connect_args": {"timeout": 30, "check_same_thread": False}}` | 把「抢不到就抛」变成「最多等 30 秒」 |
| **治果** | `scheduler_thread_alive()` / `revive_scheduler()` / `start_scheduler_watchdog()`（`main.py::lifespan` 起停） | APScheduler **不自愈** ⇒ 每 30 秒巡检一次，发现线程没了就**重建一台**换进 `app.state.scheduler` |

**三条不许改的判断**：

1. **存活判据只能是线程探针** —— `scheduler_thread_alive()`（进程里有没有**活着的**
   `"APScheduler"` 线程）是唯一可信来源；`/api/schedule/status` 的 `running` 已改走它。
   `scheduler.running` 在这件事上**是错的**，别拿它当判据。
2. **重建必须是新实例** —— `shutdown()` 会把 `ThreadPoolExecutor` 一起关掉，而
   `BaseExecutor.start()` **不重建池子** ⇒ 复用同一台会造出「循环在跑、作业提交不了」
   的僵尸。只有 `BackgroundScheduler(...)` 新实例是干净的。
3. **看门狗自己不能被带走** —— 重建失败按 `interval` 指数退避（上限 600 秒）重试，
   防「库长期不可用」时每 30 秒造一台调度器把线程/连接耗光。

**验证与观测**：`tests/backend/test_scheduler_watchdog.py`（**9 条**，含 `lifespan` 接线
AST 守卫与状态端点守卫）+ 变异验证 `.hermes/scripts/mutate_verify_scheduler_watchdog.py`
（**11 个变异全被抓**）；库侧观测用 `.hermes/scripts/probe_scheduler_alive.py`
（看 `apscheduler_jobs.next_run_time` 有没有**冻在过去**、每分钟档有没有落日志 ——
**不看 `running`**）。修前实测 20/36 行冻结、修后 0/36。

## 7. AutoTask 的归宿

### 7.1 1:1 job 行 + 单一调度 UI

- 每个 `auto_tasks` 行对应一行 `scheduled_jobs`（`job_key="auto_ops.keyword_pipeline"`、`params={"auto_task_id": id}`）。
- **调度设置 UI 统一收敛**：自动运营页的创建/编辑表单里，"调度"区块复用任务中心的同一套组件（类型选择：定时一次 / 周期；周期内含 cron 构建器预设 + interval）。预设覆盖旧四档的一键等价：每天 9:00 / 每周一五 9:00 / 每 N 小时。
- **旧的 daily/weekly/interval/manual 枚举从 API 消失**（`AutoTaskCreateRequest` / `AutoTaskUpdateRequest` 的 `schedule_*` 字段移除，改为可选 `schedule` 对象，支持 §3.1 的全部三种触发器）；"manual"概念由 job 行 `status=paused` 表达（暂停调度，"执行一次"仍可用）。

### 7.2 合并两份管线实现（DEF-044/047/058 同型）

`auto_ops_service.run_keyword_pipeline(*, auto_task_id, ...)` 成为**唯一实现**（现 `api/auto_tasks.py::run_auto_task` 的手动完整版与 `scheduler_service._execute_auto_task_background` 的简化版合并，取完整版的步骤与错误处理）：

| 调用方 | 路径 |
|---|---|
| 调度触发 | APScheduler → `run_scheduled_job(job_id)` → pipeline |

### 9.1.1 执行详情弹窗（R19，2026-09-24 用户口径）

用户口径：「任务日志中的执行详情弹窗重新布局使用**快照配置**和**执行日志信息**两块」+「执行详情弹窗调整为 **70%**」。

- **宽度**：`width="70%"`（原 720px 固定）。
- **两块独立 `<Card>`**（不是一块里嵌套 `Descriptions.Item`）：
  1. **执行日志信息**（**在前**）—— 状态 / 触发方式 / 起止时间 / 耗时 / 进度 / 消息 / 异常 / 结果；
  2. **快照配置**（**在后**）—— 触发器 / 错过策略 / 并发 / 参数 / 备注（执行时的配置快照，任务删了仍可读）。

  定向执行（账号卡按钮，日志带 `config_snapshot.params_override`）⇒ 显示
  `params_override.account_name`（**执行那一刻的账号名称快照**）；定时 / 手动「执行一次」
  的日志没有这一层 ⇒ 仍按任务配置显示「全部账号 / N 个账号」。
  ⚠️ 不能只看 `params.account_ids`：那是 job 行的**任务配置**（种子统一为 `[]` = 本人全部
  账号），账号卡的一次单账号执行会被说成「全部账号」（用户实测报障）。后端同时把定向执行
  快照里的 `account_ids` 收窄成那一个账号（只改快照，不改 job 行），让「调用参数」块的
  JSON 与这一行同口径。名称缺失 ⇒ 退「1 个账号」，不猜名字（硬约束⑤）。

## 15. 账号卡「同步中」的判据 = 该账号最新一条同步日志（2026-09-27 用户口径）

> **用户原话**：「根据任务日志详情的状态判断终态即可」「只有任务日志状态在『正在执行』，
> 才展示同步中」「账号信息卡的判断逻辑应只需要关注最新一条的同步笔记任务日志的状态即可」
> 「不做兼容逻辑，历史错误数据修复」「任务无需超时校验」。

**判据**（`sync_task_service.status_payload`）：按 `(user_id, account_id, job_key)` 取
**最新一条**日志（`id` 倒序）；`running` ⇒ `status="running"`（前端显示「同步中」），
其余（`success` / `failed` / `skipped`）⇒ `status="idle"` + `last_result`。
**不留兼容回落**（不再读业务任务行）—— 两套判据并存正是「日志 failed / 卡片同步中」的土壤。

**为什么改判据**：任务行与「用户点的那一下」**不是一一对应**（同一任务行会被复用 / 被恢复
重跑），而日志行才是「一次点击 = 一条记录」；且任务行终态由**执行方**写、日志终态由**观测方**
写，两者曾给出**相反结论**（实测 `log=14821` failed ↔ `task=51` running）。

**前置缺口**：`scheduled_job_logs` **原先不记账号**（本次加可空列 + 索引，迁移
`j1k2l3m4n5o6`）⇒ 按账号取「最新一条」无从下手（唯一替代是 `task_id`，而账号卡路径上
那个字段同样是空的 —— 两条路都断）。迁移**幂等**（`stamp` 回父版本再 `upgrade` 不炸）。

**观测不再超时**（`scheduled_job_runner._watch_task_run` ⇒ `timeout_seconds=None`）：
旧实现 60 分钟超时就把日志写成 `failed`，**而那句失败文案自己写着「任务仍在后台继续执行」**
⇒ 用户同时看到「日志失败」与「卡片同步中」。长同步任务（页内联补齐 + 令牌刷新翻页）实测
**105 分钟仍在中途**是**正常形态**，用超时把观测方提前放走只会制造矛盾结论。

**历史数据修复**：`.hermes/scripts/fix_scheduled_job_logs_20260927.py`
① 从 `config_snapshot.params_override.account_id` 回填日志 `account_id`（存量 15119 条中

### 15.1 本轮一并落地的界面与操作口径（2026-09-27 用户连续口径）

### 15.2 孤儿日志收口（进程重启后的 `running` 日志）

观测线程 `_watch_task_run` 是**进程内**的；重启后它消失，而它负责的日志仍是 `running`
⇒ 任务行已被复位 / 重跑完成，**日志却永远「正在执行」**，账号卡据此显示「同步中」
（实测 `log=14821` running ↔ `task=51` done，卡片骗了用户一个多小时）。

**收口点**（两条腿，缺一不可）：

* **启动时**：`account_task_service.recover_account_tasks` 在复位任务行**之后**调
  `sync_task_service.close_orphan_running_logs` —— 按 `task_id` **精确**回查任务行真实终态；
  查不到（存量 NULL / 任务行被记录清理）⇒ 回落「该账号最近一次终态任务」；再没有 ⇒
  `failed` + 「执行被应用退出中断」（「日志 running 而任务行连终态都没有」只可能是中断）。
* **取消时**：`close_running_logs_for_task`（见 §15.1 末行）—— **不等**观测线程。

与 `_watch_task_run` 的「无限等」互补：那条保证「进程活着时日志不因超时误判」，这两条保证
「进程不在 / 用户取消时日志不留孤儿」。缺任一条都会出现「日志与实际任务不一致」。

## 16. 任务级并行闸门 + `run_targeted_job` 退场（2026-09-27，用户口径「不同任务之间应支持并行」）

> 本节是**调度侧**的契约变更；账号侧的完整方案（含「账号级任务」概念移除与删除清单）
> 见设计 13 §39。用户三问三答：并行粒度 = **每类任务一个**、并行上限 = **新增独立配置项**、
> 执行记录 = **只留任务日志**。
>
> ⚠️ **状态：本节（连同设计 13 §39）尚未落地**（2026-09-28 实查：全仓无
> `scheduler_task_parallelism`、`execute_job` 无 `BoundedSemaphore` / `on_task_created`、

### 16.1 新增运行时配置 `scheduler_task_parallelism`

| 项 | 值 |
|---|---|
| 键 | `scheduler_task_parallelism` |
| 默认 | **3** |
| 范围 | `[1, 8]`（越界夹取；坏值 / 缺值 ⇒ 默认） |
| 语义 | **同时执行的定时任务实例数上限**（一行 `scheduled_job_logs` = 一个实例） |
| 与 `xhs_sync_account_parallelism` 的关系 | **各自独立**：前者管「几个任务同时跑」，后者管「一个同步任务内部几条 worker 跑不同账号」。两者相乘才是「同时打平台的账号数上限」 |
| 三处同值 | `config/initial_data/system_settings.json` = `settings_service.BUILTIN_DEFAULTS` = `config/default.yaml`（§38.8 立的纪律，打包时**逐文件**正向断言） |
| 生效 | 运行时配置中心（设计 10 §7）：改完**立即生效**；**已在跑的实例不被打断** |

### 16.2 闸门：`execute_job` 入口的 `BoundedSemaphore`

| 项 | 契约 |
|---|---|
| 位置 | `scheduled_job_runner.execute_job` 的**参数校验之后、`spec.func` 之前** |
| 行为 | `acquire(timeout=TASK_SLOT_WAIT_SECONDS)`（默认 300s）：拿到 ⇒ 跑；超时 ⇒ `log.status = skipped` + 说明「任务并行槽已满（N/N）」，**不抛异常**、不静默 |
| 释放 | `finally` 里 `release()` —— 任何路径（成功 / 失败 / 抛错 / 取消）都必须还槽，否则槽会永久泄漏（与「安全网不条件性」同型：不能只在成功路径还） |
| 不区别对待触发方式 | cron 与 manual **都占槽**（`manual` 不受退避门拦截，但受并行闸门约束） |
| 退避 `skipped` 不占槽 | 退避门在闸门**之前**返回（§6.5 步骤 2 早于步骤 4）⇒ 撞退避门不消耗槽位 |
| 池大小 | 每次 `acquire` **现读配置**（与限流器同口径，见设计 13 §38.2），不缓存进程级常量 ⇒ 改配置立即生效 |

### 16.3 `scheduled_job_logs.task_id` 的写入方变更

| 项 | 原（§15.1） | 现 |
|---|---|---|
| 谁写 | `run_targeted_job`（它拿着**端点预建**的 task_id） | `execute_job` 经 `on_task_created` 回调（执行体**建行后立刻**写） |
| 何时写 | 建日志行时（执行前） | 执行**期间**（建 `tasks` 行之后） |
| 为什么改 | 端点不再预建 `tasks` 行 —— 执行体自己建 | 同左 |
| 缺值口径 | `null` = 无对应业务任务行 ⇒ 前端不渲染取消按钮 | **不变**（不猜 id） |

### 16.4 `run_targeted_job` 退场

删除该函数（设计 13 §39.5）。它的两条口径**分别迁移，不随函数一起消失**：

| 原口径 | 出处 | 新落点 |
|---|---|---|
| 「失败时进度不清零 + 失败兜底不拼状态码」 | §15.1 / 设计 13 §35.17.3 | `execute_job._mark_failed` —— 该口径与「谁发起执行」无关，是**展示**口径（失败也要看得见进度比） |
| 「定向执行快照收窄账号 + `account_name` 快照」 | §9.1.1（DEF-079） | `execute_job` 处理 `params_override` 时：快照仍把 `account_ids` 收窄成 `[account_id]`，仍写 `params_override.account_name`（**只改快照，不动 job 行**） |

⚠️ **`run_job_in_background` 与 `execute_job` 的进度泵保留**（`progress_probe` 能力不变）——
退场的是「只记账不执行 + 起观测线程等终态」这一层，不是进度心跳本身。
