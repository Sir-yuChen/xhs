## 0. 先说结论：**「新增 → 草稿箱」这条路已经真机打通**，红线是被平台数据模型强制的

| 能力 | 可得性 | 真机判据（2026-10-07） |
|---|---|---|
| 打开新增商品页的表单结构（类目 / 图片 / SKU 字段名） | ✅ 可得 | `POST /api/edith/product/publish_render`（`publishType=1, sourceType=1`）；**无签名 406，带签名 200**，回 28KB「空表单」树（类目 61 个 + 卖家配置） |
| **创建草稿**（落草稿箱） | ✅ **已打通** | `POST /api/edith/product/create_product_drafts`，body `{"draft": "<JSON 字符串>"}`；真机返回 `{"productDraftId":"6ac673ae424eb00001f69ae9","response":{"code":200}}` |
| 草稿回读（校验草稿里到底存了什么） | ✅ 可得 | `publish_render` + `sourceType=4 + draftId`；实测「标题 / 类目 / 主图 2 张 / 长图 1 张 / SKU 2 条」**逐字段可读回** |
| 草稿箱列表 | ✅ 可得 | `POST /api/edith/product/query_product_draft_list_v3`（**无签名也能通**，与只读接口同档） |
| 草稿删除 | ✅ 可得 | `POST /api/edith/product/batch_delete_draft`，body `{productDraftIds:[…], channel:2}`（bundle `8591.80981179.js` 逐字取证） |
| **直接「发布到线上」** | ❌ **不做（红线）** | 平台侧「提交商品」走 `publish_async` + `publish_async_operate` 两段写链路（bundle 取证）。**本项目不接入** —— 需求明确「只能保存到草稿箱」 |

### 0.1 为什么「只能草稿箱」是**平台数据模型**强制的，不是我们保守

真机实测（2026-10-07）：`create_product_drafts` **只吃最小草稿体**。

* ✅ 能落的：`categoryId` / `name` / `standardImages` / `longImages` / `skuData`
  （回读逐项命中，见下表 §2.3）；
* ❌ **落不进去的**：`itemName` 以外的商品标题、`properties`（属性）、
  `images` / `imageDescriptions`、`skuList`（**注意不是** `skuData`）。
  实测把这些键塞进草稿体，平台**静默丢弃**（回读为 `[]`），不报错 ——
  「看起来存了、其实没存」是本链路最容易上当的地方。
* ⇒ **草稿箱里的草稿本就不完整**：它保存的是「商品骨架」（类目 + 图 + SKU），
  详细字段必须**在千帆页面里点「编辑」继续填**。这与平台自己的
  「发布助手 / 必填项指引」一致（学习中心《商品发布全流程介绍》步骤 03/04）。

> ⚠️ **平台限流**：单店铺 **每分钟最多 2 个草稿**
> （真机原文 `提示：单店铺每分钟限制发布2个草稿！`，`code=10001`）。
> 批量新增必须在该闸门内排队，见 §5.3。

### 1.2 签名档位（沿用设计 20 §11.2 的结论，**不新增一档**）

`appId=itemark` / `signVersion=4.4.4` / `tier=0101` / `Authorization` 不需要 /
`x-s-common` 不校验。**本文档零新增签名参数** —— 新增商品与既有商品写链路
共用同一套 `_signed_post`。

### 1.3 ⚠️ 本文档顺带修掉一个真 bug：**大 body 签名撑爆命令行**

`_signed_post` 把签名入参 `json.dumps(payload)` 直接当**命令行参数**传给
`node sign.js '<json>'`。商品草稿体实测 **~10KB+**（含图 + SKU），
Windows 命令行上限 32767 字符 ⇒ 命中 `FileNotFoundError: [WinError 206]
文件名或扩展名太长`。

⇒ 改用 `sign.js` **已支持但没被用上**的 `@file` 形态
（`sign.js` 第 150 行：`arg.startsWith('@') ? fs.readFileSync(...)`），
写入临时文件由 Node 读。**这是一处通用修复**（未来任何大 body 写操作都受益），
不是商品新增的专属补丁。

## 2. 数据模型：**零新表**，草稿落平台

草稿是**平台的资产**，不是本项目的资产。落库口径：

| 数据 | 落库 | 位置 |
|---|---|---|
| 商品数据包（xlsx + 图片） | ❌ 不落库 | 用户本地磁盘；本功能**只读它、上传它** |
| 上传后的图片 | 落**平台图片空间** | 千帆 `material_space`（复用设计 22 既有链路） |
| **草稿本体** | 落**平台草稿箱** | 千帆 `query_product_draft_list_v3` 可查 |
| 新增记录（谁在什么时候建了哪些草稿） | ✅ 落本地 | `tasks` 表（`task_type = xhs_shop_item_draft`，与商品操作任务同构） |

⚠️ **为什么不落本地草稿表**：草稿的**唯一真相源在平台**（用户在千帆页面里
点「编辑」继续填、平台审核、平台限流都在那边）。本地存一份镜像必然漂移，
而漂移的表现是「本地有、平台没有」或反之 —— 用户按哪份都对不上。
本地只记**操作留痕**（`tasks`），列表一律**实时查平台**。

## 3. 端点契约（3 个新端点）

挂在 `qianfan.py` 现有 router（`/api/xhs/qianfan`），归属校验复用 `_owned_account`。

| # | 端点 | 语义 | 平台请求 |
|---|---|---|---|
| 1 | `POST /api/xhs/qianfan/item-drafts` | **新增商品（存草稿）**：收「商品数据包」（类目 + 标题 + 图片本地路径 + SKU 列表），上传图片 → 建草稿，返回 `draft_id` | 多次（1 permit + N PUT + 1 add + 1 create） |
| 2 | `GET /api/xhs/qianfan/item-drafts` | **草稿箱列表**（实时查平台，一页） | 1 次只读 |
| 3 | `POST /api/xhs/qianfan/item-drafts/parse` | **解析商品数据包**（读 xlsx + 列图片，**零平台请求**）：给前端预览用 | 零 |

### 3.1 字段级契约

```python
# 3: 解析数据包（纯本地；用户在弹窗里选目录 / 上传 xlsx）
class DraftPackageParseRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    platform_account_id: int = Field(ge=1)
    package_path: str = Field(min_length=1, max_length=512)   # 数据包目录绝对路径

DraftPackageParseResult = {
    "package_path": str,
    "sku_rows": [{"name": str, "price": float | None, "stock": int | None,
                  "image_path": str | None}],                  # 来自 xlsx（列名见 §4.1）
    "main_images": [str], "detail_images": [str], "videos": [str],   # 绝对路径
    "suggested_title": str,        # 独立文案不拼凑：取第一条 SKU 名 + 目录名线索
    "warnings": [str],             # 缺列 / 缺图 / 尺寸超限等，如实列出不静默
}

# 1: 建草稿（⚠️ 本请求**不含任何「发布」开关** —— 没有就是不可能）
class ItemDraftCreateRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    platform_account_id: int = Field(ge=1)
    category_id: str = Field(min_length=1, max_length=64)   # 叶子类目（由 /search-category 选）
    name: str = Field(min_length=1, max_length=60)          # 草稿名（= 平台商品标题位）
    main_images: list[str] = Field(default_factory=list, max_length=MAX_DRAFT_IMAGES)
    detail_images: list[str] = Field(default_factory=list, max_length=MAX_DRAFT_IMAGES)
    skus: list[ItemDraftSku] = Field(min_length=1, max_length=MAX_DRAFT_SKUS)

ItemDraftSku = {
    name: str (1..120),
    price_yuan: float (gt=0),
    stock: int (ge=0),
    image_path: str | None,      # 有则作为该 SKU 的规格图
}

ItemDraftCreateResult = {
    "draft_id": str,
    "name": str,
    "uploaded_images": int,       # 真正上传成功的张数
    "failed_images": [{"path": str, "reason": str}],   # 逐条如实报，不静默丢
    "sku_count": int,
    "note": str,                  # 固定写清「已存入草稿箱，未上架」
}
```

### 3.2 三个必须钉住的口径

1. **`ItemDraftCreateRequest` 结构上就没有「发布 / 上架」字段**
   （`extra="forbid"`）。红线不靠文案承诺，靠**契约里不存在那个开关** ——
   想发布必须改后端代码，不是改一个布尔值。守卫断言 `"publish" not in fields`。
2. **上限同值前后端一份**：`MAX_DRAFT_IMAGES = 20` / `MAX_DRAFT_SKUS = 200`
   / `MAX_DRAFT_PER_MINUTE = 2`（平台限流，§5.3）。常量只在后端定义，
   前端读端点下发的值（`MAX_BATCH_DELETE` 同一纪律）。
3. **图片上传失败不阻断建草稿**（部分成功照建），但**必须逐条回执**
   （`failed_images[]`）—— 静默丢一张主图的后果是「商品图不全，用户不知道」。

## 4. 业务逻辑

### 4.1 数据包解析（**纯本地，零平台请求**）

数据包目录约定（用户 2026-10-07 的实际形态，**按实测结构写死，不做「智能猜测」**）：

```
<包目录>/
  *.xlsx                  # SKU 表：列 = sku名称 | 图片 | 原价 | 计算价格 | 库存 | ID
  SKU/                    # 每个 SKU 一张规格图，文件名前缀 SKU<NN>_
  主图/                    # 主图（含「商品属性图.png」这类非主图素材，见下）
  详情图/                  # 长图 / 详情图
  视频/                    # 视频
```

* **xlsx 读取**：找第一个 `.xlsx`；**列名按表头匹配**（不按列序 ——
  列序是最容易漂移的东西）。缺列 ⇒ 进 `warnings`，不进结果（缺值口径⑤）。
* ⚠️ **`主图/` 里混着「商品属性图.png」**（用户 2026-10-07 追加的素材：
  属性参数表，不是商品主图）。判据：文件名含「属性图」⇒ **不计入主图**，
  也不计入详情图（它不是图集的一部分，是**属性数据的图片形态**）。
  如实列在 `warnings` 里提示「属性图需在千帆页面手工录入属性字段」——
  因为草稿体**不接受 `properties`**（§0.1 实测）。
* **SKU 名 → 规格值拆分**：xlsx 的 `sku名称` 形如
  `颜色分类:【中古风】实木三斗柜` ⇒ 规格名 = `颜色分类`（冒号前），
  规格值 = 冒号后全文。**冒号必须是半角 `:`**（真机数据如此）；
  全角冒号也接受（用户手输可能混）。拆不出就整串当规格值、规格名留空。
* **图片尺寸**：上传前读宽高（`PIL` 已有依赖）—— 平台 `additionalData.width/height`
  缺值不写（设计 22 的 `For input string: ""` 教训），有值才带。

### 4.2 建草稿执行链（**有平台写操作，用户显式点击才走**）

```
1) 逐张上传图片（主图 → 详情图 → SKU 图，**去重**：同一路径只传一次）
   ├─ upload_web_permit(biz_name="ark", scene="goods_image")
   ├─ upload_file(PUT)
   └─ register_material_files（登记进图片空间，拿回 link + path）
2) 组装 draft body（§4.3）
3) POST create_product_drafts {"draft": "<json>"}
4) 回读 publish_render(sourceType=4, draftId) **校验真的落进去了**
   —— 不校验就是「接口说成功、草稿是空的」，本链路最容易漏的一步
5) 回执 draft_id + 上传统计 + 回读校验结果
```

⚠️ **第 4 步不是可选项**：真机实测「接口 200 但字段被静默丢弃」是常态
（§0.1）。回读后把**实际落库的字段**与**提交的字段**做差集，
差集非空 ⇒ 在 `note` 里如实说明「以下字段平台草稿不接受，请在千帆页面补充」。

### 4.3 草稿体组装（**真机回读验证过的形状**）

```python
draft = {
    "categoryId": <叶子类目 id>,
    "name": <草稿名>,                     # 回读落在 item.itemName
    "standardImages": [<主图条目>],         # 回读命中（实测 2 张 → 2）
    "longImages": [<详情图条目>],           # 回读命中（实测 1 张 → 1）
    "skuData": [<sku>],                   # ⚠️ 不是 skuList（那个被静默丢弃）
}

# 图片条目（回读命中，取自图片空间条目字段）
img = {"link": <https url>, "path": <material_space/<id>>, "extension": ".jpeg",
       "width": 800, "height": 800, "materialId": <id>, "size": <bytes>,
       "sourceLink": <http url>}

# SKU 条目（bundle 8091.31a2a571.js「itemFormSku.getFormData」逐字逆出 + 回读验证）
sku = {"rowNumber": 1, "ipq": 1, "available": True,
       "price": {"price": <元>, "originPrice": <元>, "includeTax": False, "taxType": 0},
       "stock": <int>, "stockChange": <int>,
       "variants": [{"attributeId": <规格 id>, "attributeName": "颜色分类",
                     "attributeType": 1, "attributeValue": "实木三斗柜",
                     "attributeValueId": ""}]}
```

⚠️ **`price` 是「元」不是「分」**（与商品列表的 `price_from_fen` 相反！）。
真机实测：传 `1280` 回读 `price=1280`；传 `128000` 回读 `128000`。
**这是最容易搞反的一处** —— 守卫必须钉住「草稿体用元」。
（`basePriceInfo`/`skuList` 那套是**读**形态的字段名，**写**形态是 `price`/`skuData`。
两个形态混用是本节最大的坑。）

### 4.4 规格 id（`variantId`）从哪来

`variants[].attributeId` 必须是**平台规格 id**（如
`60404e0de85df80001991224` = 颜色分类）。真机来源：**该店铺任一既有商品**的
`publish_render` 回读里 `skuVariantInfos[].variantId`。

⇒ 取值顺序（**降级链，逐级如实标注**）：
1. 用户在弹窗里手选（从**本店既有商品**扫出的规格集，去重）；
2. 未选 ⇒ 回退到**台账里最近同步过的一个商品**的同名规格 id；
3. 都没有 ⇒ **不猜**：回 400 `DRAFT_VARIANT_ID_REQUIRED`，
   提示「请先在千帆随便建一个商品，或手选规格」。

⚠️ **绝不硬编码 id**：平台的规格 id 是**店铺级 / 类目级**的，写死一个值
在别的店 / 别的类目上必然错。取自本店数据是唯一诚实的做法。

### 9.2 ⚠️ 本轮实测抓到并修掉的问题

1. **大 body 签名撑爆命令行**（`WinError 206`）：`_signed_post` 把签名入参当
   argv 传，商品草稿体 ~10KB+ 直接超 Windows 32767 字符上限，而错误信息
   报的是「签名运行时不可用」—— **完全指错方向**。改用 `sign.js` 已支持但
   从没用过的 `@file` 形态（**通用修复**，未来任何大 body 写操作都受益）。
   ⚠️ 临时文件含 Cookie ⇒ `finally` 里**必删**（硬约束②）。
2. **数据包 `计算价格` 全空**（真机 26 行全空，值都在 `原价`）：只认 `计算价格`
   会让整批商品价格全空，而草稿建完**看不出来**（价格留空是合法状态）。
   改为「优先计算价格、空则回退原价」。
3. **图片上传没有重试**：本机系统代理（`127.0.0.1:8899`）下大 body 的 ROS PUT
   偶发 `ProxyError` / `SSLEOFError`。不重试的表现是「同一份数据包这次少两张图、
   下次又好了」—— 用户无法归因。加 3 次指数退避重试。
4. **图片上限定成 20（拍的值）**：真机新增页原文是「已选择 0 / **100** 项」，
   而一个家具数据包就有 69 张（5 主图 + 38 详情图 + 26 SKU 图）⇒
   「一个完整数据包」根本传不完。改为 **100**（取自平台原文，不是我们拍的）。
5. **首轮变异 2 条 ESCAPED**（守卫是假的，已修）：
   * `drop-readback-check` —— 只测了 `diff_draft_readback` 纯函数，**没人测
     `create_draft` 有没有调它** ⇒ 去掉调用照样绿。补
     `test_create_reports_readback_diff`（断言差集落进 `warnings`）。
   * `silent-ark-fallback` —— 判据写成 `code in {DRAFT_ARK_REQUIRED,
     ARK_SESSION_REQUIRED}`（宽判据），被下游另一处令牌检查满足 ⇒
     塞个假 cookie 绕过照样绿。收紧为**精确等于** `DRAFT_ARK_REQUIRED`。
   ⇒ 教训：**「函数存在」不等于「被调用」**；`in {A, B}` 形式的判据会被
   另一条路径满足（本技能 §0 第 3 条：宽锚点 = 假绿）。
