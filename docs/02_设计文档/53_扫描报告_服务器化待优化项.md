# 53 · 全面扫描报告 · 服务器化（桌面端退场）需要优化的地方

> 触发口径（2026-10-23）：**「后续我将把项目部署到服务器，不再以桌面端为主」+「桌面端不再使用」**
> 方法：对 `backend/app` 全量 1000+ 文件做**模式化扫描**（8 类假设 × 逐文件计数），再对每一项**核实真伪**（排除注释误报）。
> **本文只报「实测确认的问题」**，不写推测。每个问题带：位置 → 为什么在服务器上出事 → 修法 → 优先级。

# 一、🔴 A 类：服务器上会直接崩 / 卡死（必改）

## A1 · `package_precheck.py` 的原生文件夹选择框（最严重）

**位置**：`backend/app/api/platforms/xhs/package_precheck.py`
- 桌面逻辑占 **第 96–436 行（约 340 行）**：`_ask_directory_windows`(96) / `_has_interactive_desktop`(143) / `_ask_directory`(177)
- 暴露为**独立端点** `POST /pick-folder`（第 437 行）—— 前端点「加载数据包」时调它
- 文件总 842 行，**40% 是桌面专属**

**实测**：
| 模式 | 命中数 |
|---|---|
| `tkinter` / `pywebview` / `webview.` | **22 处**（全仓就这一个文件） |
| `os.name == "nt"` / `winreg` / `windll` / `powershell` | **18 处**（同文件） |

**服务器上会发生什么**：
- `_ask_directory()` 优先走 tkinter → Linux 无 X11 ⇒ `TclError: no display name and no $DISPLAY environment variable`
- 回退走 `powershell.exe -NonInteractive -STA` → Linux 无此命令 ⇒ `FileNotFoundError`（被 `except Exception` 吞掉 → 返回 `None`）
- 最终落 `NO_DESKTOP`，前端**只能手填服务器上的绝对路径** —— 而用户根本不知道服务器上数据包在哪

**更糟的**：`subprocess.run(..., timeout=5)` 在用户点「加载数据包」时**同步阻塞一个请求线程 5 秒**。
10 个用户同时点 = 10 个线程卡 5 秒。

**修法**：
1. **删除 `_ask_directory_windows` / `_has_interactive_desktop` / `_ask_directory` 三函数（第 96–436 行，约 340 行）+ `POST /pick-folder` 端点**
2. 改为**浏览器上传**：前端 `<input type="file" webkitdirectory>` 上传整个文件夹 → 后端接收落 `storage/staging/`
3. 保留「手填路径」作为**管理员专用**兜底（挂在 `xhs:packageImport:serverPath` 权限码下，普通用户看不到）

**工作量 1 人日**（前后端契约变化：`/pick-folder` 端点删除 → 前端改上传）。

> ⚠️ **端点影响**：删 `POST /api/xhs/package-precheck/pick-folder` 后，端点总数 **391 → 390**，
> path **320 → 319**（设计 49/50 的数字需回写）。这条属于「用户口径导致的功能退场」，不是缺陷。

## A2 · `storage_dir` 是**相对路径**

**位置**：`backend/app/core/config.py:308-310`
```python
@property
def storage_dir(self) -> Path:
    return Path("backend/app/storage")      # ← 相对 CWD
```

**实测消费方：11 个文件**
```
adapters/xhs/creator_api_adapter.py   api/files.py            api/notes.py
api/platforms/xhs/analytics.py        services/ai_service.py   services/asset_downloader.py
services/material_scan_service.py     services/media_generation.py
services/note_publish_service.py      services/package_staging_service.py
```

**服务器上会发生什么**：
`systemd` 的 `WorkingDirectory=/opt/spider-xhs`、Docker 的 `WORKDIR`、或从别的目录跑 uvicorn ——
**任何一处 CWD 不同，媒体文件立刻「全部丢失」**（读不到，也不报错，只是 0 条）。
而且不同入口会写到**不同目录**（`/opt/spider-xhs/backend/app/storage` vs `/backend/app/storage`）。

**同类问题**：`frontend_build_dir: str = "./frontend/dist"`（`config.py:248`，被 `main.py` 消费）
⇒ CWD 不对，**整个前端 404**。

**修法**：
```python
# core/paths.py（新建，唯一真相源）
APP_ROOT = Path(__file__).resolve().parents[2]          # 到仓库根
def storage_dir() -> Path: return APP_ROOT / "backend/app/storage"
def frontend_dist() -> Path: return APP_ROOT / "frontend/dist"
```
所有 11 个消费方改调 `paths.storage_dir()`；`config.py` 的两处相对默认值改成 `None` + 由 paths 兜底。
**守卫**：`test_no_cwd_relative_paths.py` —— 除 `paths.py` 外出现 `Path("./` 或 `Path("backend/` ⇒ 红。

**工作量 0.5 人日。**

## A3 · 数据库连接池（SQLite 默认 `NullPool`，PG 需要显式池）

**位置**：`backend/app/core/database.py:43-48`
```python
engine = create_engine(settings.database_url, connect_args=_connect_args)
# SQLite ⇒ NullPool（每次新建连接），这在本机是合理的
```

**服务器上会发生什么**：
- PG 上仍用默认池（SQLAlchemy 对 PG 默认是 `QueuePool`，size=5/overflow=10）——**能用但没调优**
- 更关键：**`pool_pre_ping` 未开** ⇒ PG 重启、网络闪断后，池里的死连接会被取出来用 ⇒ `server closed the connection unexpectedly`
- 多 worker 时每个 worker 各 5 连接 ⇒ 4 worker = 20 连接，需要与 PG 的 `max_connections` 对账

**修法**：
```python
if is_postgres():
    engine = create_engine(url,
        pool_size=int(cfg.db_pool_size or 10),
        max_overflow=int(cfg.db_max_overflow or 20),
        pool_pre_ping=True,          # ← 关键
        pool_recycle=1800,           # 30 分钟回收，避开 PG 的 idle timeout
        connect_args={"connect_timeout": 10},
    )
```
外加启动自检：`SELECT 1` 探活失败 ⇒ 明确报错（不要静默重试到超时）。

**工作量 0.5 人日。**

# 二、🟠 B 类：服务器上行为错，但不会崩

## B1 · 进程内缓存与「多用户/多副本」不一致

**实测**：
| 项 | 数量 |
|---|---|
| `threading.` / `Lock()` / `RLock()` | **111 处 / 24 文件** |
| 模块级可变状态（`_XXX = {}` 之类） | **11 处 / 8 文件** |

**为什么在服务器上是问题**：
- 单副本：完全正常（这也是现状能用的原因）
- **多副本（docker `--scale app=2` / K8s）**：每个进程一套锁、一套缓存 ⇒
  - 权限缓存不一致（A 副本改了角色，B 副本 60s 内仍给旧权限）
  - 「账号级互斥」（同一账号不被两个同步任务同时抓）**跨副本失效** ⇒ 可能对同一小红书账号并发请求 ⇒ 风控

**修法（分层）**：
| 层 | 做法 |
|---|---|
| 本期 | **明确约束单副本部署**，写进 `52` 部署文档 + `docker-compose` 里 `deploy.replicas: 1`；启动时打印「单副本模式」横幅 |
| 中期 | 权限缓存迁 PG 表（带 `expire_at`）；账号互斥改 PG advisory lock |
| 不做的 | 不引 Redis（单副本下零收益） |

**工作量 0.5 人日（文档 + 启动横幅 + compose 约束）。**

## B2 · 27 处 `time.sleep` 阻塞请求线程

**实测**：**27 处 / 16 文件**，集中在：
```
services/scheduler_service.py     5
services/note_publish_service.py  3
services/shop_draft_service.py    3
services/business_note_publish_service.py 2
services/login_state_service.py   2
```

**服务器上会发生什么**：
FastAPI 的同步端点跑在 anyio 线程池（默认 40 线程）。单个请求 `sleep(3)` 不是灾难，
但**并发 40 个用户 + 每个卡 3 秒** = 线程池打满 ⇒ 全站请求排队。

**修法**：
- 已经在后台 worker 线程里跑的 sleep（发布队列 / 同步队列）⇒ **不影响请求**，可保留
- 在**端点内**同步 sleep 的 ⇒ 改 `await asyncio.sleep()`（`async def` 端点）或移到后台任务

**需要逐处判定**，不能一刀切。**工作量 0.5 人日。**

## B3 · `datetime.now()` 裸调 4 处（时区不一致）

**位置**：
```
services/violation_service.py:?     2 处
api/platforms/xhs/qianfan/goods.py:2007  1 处
services/material_save_service.py:?  1 处
```

**服务器上会发生什么**：服务器时区若为 UTC（Docker 默认），`datetime.now()` 比项目口径（Asia/Shanghai）**少 8 小时**。
项目已有 `shanghai_now()` 统一实现，这 4 处是漏网。

**修法**：全部改 `shanghai_now()`。**守卫**：`test_no_naive_datetime_now.py` —— 除 `core/time.py` 外出现 `datetime.now()` 无 tz ⇒ 红。

**工作量 0.2 人日。**

## B4 · `os.environ` 直读 17 处（绕过 `settings`）

**位置**：
```
services/system_update_service.py   8
core/version.py                     3
adapters/xhs/request_env.py         2
core/config.py / database.py / initial_data.py  各 1
```

**服务器上会发生什么**：`.env` / Docker `environment:` / systemd `EnvironmentFile` 三套来源，
绕过 `settings` 直读 `os.environ` 的代码**在容器里行为与本地不同**（尤其 `system_update_service` 8 处 —— 服务端自动更新逻辑会在 Linux 上乱跑）。

**修法**：
- `services/system_update_service.py` → **服务器模式下整个禁用**（服务端不该自己 git pull 重启）
- 其余 9 处收敛到 `settings`

**工作量 0.3 人日。**

## B5 · `material_scan_service.py` 有 6 处写死 Windows 绝对路径

**位置**：`backend/app/services/material_scan_service.py`（6 处 `C:\\...`）

**服务器上**：素材扫描直接在 Linux 上失败（路径不存在）。

**修法**：改为配置项 `material_scan_roots: list[str]`，默认空；服务器上由管理员配置挂载点。
**工作量 0.2 人日。**

# 三、🟡 C 类：安全隐患（服务器必须处理）

## C1 · `secret_key` 默认值 `dev-only-change-me` 🔴

**位置**：`backend/app/core/config.py:152`
```python
secret_key: str = "dev-only-change-me"
```

**服务器上**：忘改 ⇒ **任何人可伪造任意用户的 JWT**（包括 admin）。

**修法**：启动自检，非 SQLite 模式下仍是默认值 ⇒ **拒绝启动**（不是 warning）。
**同类**：`database_mysql_password` 等敏感项也应做「非空校验」。

**工作量 0.2 人日。**

## C2 · CORS 默认只含 localhost:5173

**位置**：`config.py:160` `backend_cors_origins: str = "http://127.0.0.1:5173,http://localhost:5173"`

**服务器上**：如果前端由 Nginx 独立托管在不同域名，**所有 API 请求被浏览器拦**。
反过来，若有人图省事改成 `*`，则**跨站请求可带 Cookie**（若将来加 Cookie 认证）。

**修法**：默认保持收紧；部署文档明确要求填生产域名；**守卫：禁止 `*`**（`test_cors_not_wildcard.py`）。
**工作量 0.1 人日。**

## C3 · 无 IP 维度登录限流

**现状**：按**用户名**限流（`auth.py:166 _login_locked_for`），5 次失败锁。
**服务器上**：攻击者用 1000 个不同用户名撞库 ⇒ 用户名限流**完全无效**。

**修法**：加 IP 维度（同 IP 每分钟 ≤ N 次登录尝试，读 `X-Forwarded-For` 最左可信值，**只信 Nginx 设的那一个**）。
**工作量 0.3 人日。**

## C4 · `api_logs` 无保留期策略

**实测**：70,325 行，且只记写操作。
**服务器上**：长期跑会无限涨；且服务器是**多用户**，写操作量远大于单机。

**修法**：加清理任务（项目已有 `system.queue_record_cleanup` 框架，复用）+ `api_logs` 按天分区索引（PG 上）
**工作量 0.2 人日。**

# 四、🔵 D 类：架构约束（不是 bug，必须写清楚）

## D1 · 定时任务 = 同进程单实例 ⇒ 不能多副本

**位置**：`core/singleton.py`（文件租约 + PID 探针，112 行）

**判断**：**单副本下完全正确**，`52` §三已分析。多副本时文件租约各看各的 ⇒ 重复调度。

**核实过的一件事（排除误报）**：`_pid_alive(pid)` **在 Linux 上没问题** ——
`psutil.pid_exists` 优先，缺失时 `os.name == "nt"` 才 `import ctypes`，POSIX 分支走 `os.kill(pid, 0)`。
所以「跨平台崩」这条**不成立**，不要改这段代码。

**真正要改的是文档声明**——`singleton.py:44-48` 文件头写着：
> 「只覆盖**同机**多实例（桌面版就是同机场景）。跨机多副本仍需 DB 锁或部署层单副本
>  —— 本项目是**桌面单机应用**（`data/spider_xhs.db` 本地文件），跨机不在范围内。」

服务器化之后这句话**直接与新定位冲突**（不再是桌面单机应用）。必须改，否则下次有人读代码会
按「桌面单机」的前提做判断。改法：把注释改成「当前形态为单副本服务器部署；多副本需 PG advisory lock（未实现，见 52 §三）」

**要做的**：部署文档写死 `replicas: 1`；`singleton.py` 抽策略接口，PG advisory lock 留口子（`NotImplementedError`，**不静默降级**）。

## D2 · `env_bootstrap_service.py`（917 行）是桌面端遗产

**位置**：`backend/app/services/env_bootstrap_service.py`，4 处 Windows 专属 + 4 处 subprocess

**内容**：首次启动下载 webview 内核（179.9MB）/ OCR 模型 / node.exe
**服务器上**：webview 内核**完全不需要**（那是桌面窗口用的）；OCR 模型与 ffmpeg **需要**（真在跑 OCR）。

**要做的**：按功能拆 —— 保留 OCR/ffmpeg 下载（改由部署时预装，不首启下载），删除 window_host 分支。
**本期只标废弃 + 加注释，不删**（917 行一次性删风险高）。

## D3 · `system_update_service.py` 服务端不该自我更新

**位置**：`backend/app/services/system_update_service.py`（8 处 `os.environ`）

**实测内容**（非推测）：`system_update_service.py` 308 行，导出 4 个函数并被 `api/system.py` 挂在端点上：
`load_update_source`(41) / `check_for_update`(61) / `download_installer`(70) / `launch_silent_installer`(85)。
其中 `launch_silent_installer` 直接 `subprocess` 跑 **Inno Setup `/VERYSILENT /NORESTART`** —— 纯 Windows 桌面语义。
**服务器上**：`git pull` / 重启进程由运维做，服务自己更新会导致**容器反复重启**。

**要做的**：`is_desktop_mode()` 为假时整模块禁用（端点返回 501 + 明确原因）。
