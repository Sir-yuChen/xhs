`getProductExtraRule` · `getSupportAfterSale` · `getMaterialRule` · `getRecommendTrendingWords` ·
`checkNeedBrand` · `searchMarketableBrands` · `getShortTitleRuleConfig` · `getSupportNoLogistics` ·
`getSellerCarriageTemplate` · `getSetSizeTableInfo` · `getSupportCrossBorderMiniPackage` ·
`getPriceLimit` · `getSalePropertyNumLimit` · `getProductQualificationRule` ·

## 五、「智能生成」到底生成了什么（用户问题直答）

**第二部分有两处「智能生成」，分别对应两个接口，生成的是不同数据：**

| 「智能生成」位置 | 触发接口 | 入参 | 生成的数据（响应） |
|---|---|---|---|
| **基础信息 · 商品标题**右 | `getRecommendItemTitle` | `{mainImages:[{key,path,link,uploaderInfoModel,...}]}` | `product.productTitle.productRecommendTitleDTO`：`recommendItemTitle`（标题候选，如「美式乡村实木梳妆台简约现代化妆桌带抽屉书桌学习桌」）+ `recommendItemTitleSourceImage` + `recommendVersion:2` ⇒ 前端弹「智能推荐 + 立即使用」 |
| **导购短标题**右（属性区同款入口） | `generateItemShortTitle` | `{title, categoryId}` | 导购短标题候选（≤24 字）|
| **商品属性**区「智能生成」 | `predictProductProperty` | `{categoryId, itemName, imageUrl, ...}` | 属性预测（材质/风格/是否组装…带 AI 标签）|
| 标题校验 | `productTitleCheck` | `{title, categoryIdPath, unionType}` | 标题合法性 |
| 短标题校验 | `productShortTitleCheck` | `{shortTitle, categoryId}` | 短标题合法性 |

⚠️ **不是**「一键填满整个第二部分」—— 智能生成只产出**标题 / 短标题 / 属性预测**三类，
其余参数（发货模式、物流模板、价格、规格）**不参与智能生成**，由用户在第二部分手动配。

## 七、对实现的意义

1. **千帆的两部分参数并入本项目发布弹窗的第二步，且内部合并为一部分**（用户口径 2026-10-09）：
   本项目保留自己的三步向导（预检 → 配置商品参数 → 发布）；第二步里千帆的
   【第一部分 图/标题/类目】（`publish-config-step1`）+【第二部分 参数配置】
   （`publish-config-step2`）**同屏合并，不再在第二步内部再分「商品属性 / 其余参数」两步**。
2. **布局：左右两栏**（用户口径 2026-10-09）—— 左「商品发布助手」（只读字段 + 错误原因），
   右「商品配置」四个分区（基础信息 / 图文信息 / 价格库存 / 服务信息）一次铺完。
3. **商品图片 / 商品标题 / 商品类目并入「基础信息」区**（用户口径 2026-10-09）：
   第一部分的这三块不再独立成块，而是作为 `headSlot` 落在第二部分「基础信息」区最前，
   且**不重复展示**（标题不再有第二个只读框，主图不再在「图文信息」重复铺）。
   「自动加载参数」按钮逻辑不变。
4. **OCR 提速：分块并行 + 一进程多图**（用户口径 2026-10-09「检测违规词还是太慢」）——
   实测每次 `powershell -File` 冷启动 **~1.2s**，而真正 OCR 只 **~0.3s**
   ⇒ 一图一进程时约 **80% 时间花在进程启动**。两步提速：
   ① 一进程 OCR 多图（`win_ocr_batch.ps1`，引擎只装配一次）；
   ② 再把图拆成 `MAX_WORKERS` 块、**每块一个批量进程并行**（吃满多核）。
   **68 张图 3.9s**（对照旧的 4 路并发逐图 **~23s**），**约 6×**；
   批量脚本不可用时回退逐图 + 线程池。
5. **执行进度**：预检跑 OCR 期间前端按 token 轮询 `GET …/{token}/progress` 显示
   「已处理/总数 + 进度条」。
6. 类目确认后**批量拉 16+1 项**（第三节），把规则/候选填进控件。
7. 智能生成只做**标题 / 短标题 / 属性预测**三件（第五节），不神话它。
8. 属性 / 规格类型 / 尺码表**按类目动态渲染**（本类目无尺码表）。
9. 缺值留空不造假；点「提交商品」= 真实上架，**后端发布成功后立即下架**（红线）。
10. **「商品发布助手」栏不扩成字段状态表**（决定 2026-10-09）—— 保持「发布提示 (N)」+
    字段/原因两列的形态。理由：真机该栏就是**校验提示列表**（顶部常驻条 + 可展开计数），
    右侧四个分区已经逐字段可见；再铺一遍全字段状态属重复展示（与 2026-10-09
    「参数不用重复展示」同一口径），且真机无此形态。

## 八、自动加载参数 · 各阶段真实入参（2026-10-09 复测，本轮修复依据）

> 探针：`.hermes/tmp/verify_fix.py`（走 SDK 真实签名请求，账号 8）。
> 结论：**入参错 ⇒ 平台不报错、静默回空值**，表现为「短标题未生成 / 未自动生成属性」。

### 8.1 `generateItemShortTitle`（导购短标题）

| 项 | 真机抓包 | 修复前代码 | 后果 |
|---|---|---|---|
| 入参 | `{"title":…, "categoryId":…}` | `{"name":…, "mainImages":[…]}` | 参数名错 ⇒ **恒回空短标题** |
| 取值 | `data.product.productTitle.itemShortTitle.generatedShortTitle` | `data.itemShortTitle` / `shortTitle` | 顶层键在真机响应里**不存在** ⇒ 恒空 |

实测（修后）：`generatedShortTitle = "侘寂风实木梳妆台书桌"` ✅

### 8.2 `predictProductProperty`（属性预测）

| 入参 | 结果 |
|---|---|
| `{categoryId}` | `predictItemProperties: []` |
| `{title, categoryId}` | `predictItemProperties: []` |
| `{title, categoryId, imageUrls[…]}` | **有值**（14 条，如 `风格=明清古典`） |
| `{name, categoryId, imageUrls[…]}` | `success:false`（入参名必须是 `title`） |

⚠️ 两条修复：① 必须带图（**不给图 = 平台没料可预测**）；② 入参名是 `title` 不是 `name`。
⚠️ 响应值是 **`propertyValueList:[{value,valueId}]` 数组**（不是标量）——
早期按 `propertyValue` / `value` 标量取 ⇒ 恒空 ⇒ 前端永远提示「平台未给出可填充的属性值」。

### 8.3 关键属性判据（`getCategoryProperty` 实测 22 项）

* `importantProp` / `searchImportantProp` **全为 false**；
* `requiredProp=true` 恰好 **4 项**（材质 / 风格 / 是否组装 / 门数量）= 真机「关键属性 3/4」的分母；
* ⇒ **关键属性判据 = `requiredProp`**（早期按 `importantProp` ⇒ 关键属性恒空、全落「其他属性」）。

### 8.4 布局：属性控件宽度

真机控件 x=642/974/1307（列距 332px）是千帆自己在 1176px 内容宽度下的结果。
本项目右栏随弹窗（80vw）变化 ⇒ 固定 332px 列 + 控件写死 `width:320` 必然溢出，
与**邻格属性名重叠**（用户报「布局拥挤、输入框和标题重叠」）。
修法：列宽 `repeat(3, minmax(0, 1fr))` + 控件 `width:100%`（多选属性横跨两列）。

### 8.5 「自动加载参数」的阶段清单（8 阶段）

真机「自动加载」= 进第二步按 `categoryId` 批式拉 16+1 项（§三）+ 生成类三件（§五）。
本项目落为**居中进度弹窗**逐阶段显示：上传主图 → 生成标题 → 识别类目 → 上传详情图 →
上传视频 → 生成短标题 → **按类目加载参数**（新增，取 `getCategoryProperty`）→ 生成属性。

## 九、商品视频上传失败 · 根因与修法（2026-10-09 实测）

> 探针：`.hermes/tmp/probe_video.py` / `probe_video2.py` / `probe_video3.py`（走 SDK 真实签名）。

### 9.1 现象

「自动加载参数」第 5 阶段「上传商品视频」报 `获取上传文件[v]信息失败`。

### 9.2 根因（逐步排除后定位）

| 步骤 | 走图片链路（`scene=goods_image`） | 结论 |
|---|---|---|
| 申请凭证 | ✅ 成功（预分配 `arkgoods/<id>`） | 不是这里 |
| PUT 字节到 ROS | ✅ 200，回 `X-Ros-Preview-Url` | 不是这里 |
| **登记图片空间**（`material_space/batch_add`） | ❌ `{"success":false,"msg":"获取上传文件[v]信息失败"}` | **就是这里** |

换 `scene=common_file` 同样在**登记**一步失败 ⇒ 与 scene 无关，**是「图片空间」本身不收视频**：
它是**图片库**（登记条目 `type:2`，`additionalData` 要 `width`/`height` 数值），
视频没有尺寸、也不属于该库。

### 9.3 真机的视频上传是**另一条路**（bundle 逆出）

`9515.*.js` 里「上传视频」用的是：

```js
new Uploader({ bizName: "ark", scene: "common_file", fileFormat: ".mp4" })
  .post({ Body: file })            // 直传，成功回 { url, fileId }
```

⇒ **`scene=common_file` 独立直传，不经过图片空间登记**（预分配落 `ark-common/<id>`）。
实测（修后）：PUT 成功，`X-Ros-Preview-Url` = `https://ros-preview.xhscdn.com/ark-common/<id>?sign=…`。

### 9.4 修法

新增端点 `POST /api/xhs/qianfan/video/upload`（申请凭证 `common_file` → PUT → 回链，**不登记**）；
自动加载第 5 阶段改走 `uploadProductVideo`，并把失败原因带进进度弹窗。

## 十、售后服务「七天无理由」是否可编辑（2026-10-09 调研）

> 探针：`.hermes/tmp/probe_aftersale.py` / `probe_aftersale3.py`（14 个类目对过）。

`getSupportAfterSale {categoryId}` → `data.fulfillmentInfo.afterSaleRule[]`，每条：

```json
{"name":"支持七天无理由退货","type":"freeReturn","defaultSupport":true,"mustSupport":true}
```

### 10.1 `mustSupport` **按类目不同** ⇒ 这就是「是否可编辑」的判据

| 类目 | mustSupport | 含义 |
|---|---|---|
| 其他宠物服务 / 绝育服务 / 梳妆台桌 / 斗柜 | `true` | **必须支持** ⇒ 勾选强制、不可取消 |
| 实体服务 / 求职·留学·其他咨询服务 | `false` | **可选** ⇒ 用户自己决定 |

## 十一、两个实现缺陷（2026-10-09 修复，均由用户真机报出）

### 11.1 上传视频报「不支持的图片扩展名：.mp4」

根因：视频走了 `lib/publish-config.ts::md5_file_name`，而它的允许集**只有图片扩展名**
（`IMAGE_EXTS`），`md5` 命名前先校验扩展名 ⇒ 视频直接被拦下。

修法：新增 `VIDEO_EXTS` + `MEDIA_EXTS = IMAGE_EXTS + VIDEO_EXTS`，命名与 `search_keyword`
**都用 `MEDIA_EXTS`**（`search_keyword` 原先也只列图片 ⇒ `.mp4` 去不掉后缀，
视频检索名会带着扩展名，与图片口径不一致）。报错文案相应改为「不支持的媒体扩展名」。

### 11.2 现货发货时间**默认没有选中**

根因：默认值写死 `useState("48小时")`，而候选值是 `"48小时（推荐）"`
（`SPOT_SHIP_TIME_OPTIONS`）—— 值与选项**对不上** ⇒ 单选一项都不选中，
页面看起来「没有默认值」。

修法：默认值改为**取自候选数组**：`SPOT_SHIP_TIME_OPTIONS[SPOT_SHIP_TIME_OPTIONS.length - 1]`
（末项 = 真机标「推荐」的那项）。这样候选改了默认也跟着走，不会再对不上。

## 十二、预检「商品sku表格」+ 价格/库存批量修改（用户口径 2026-10-09）

### 12.2 规格的价格 / 库存**批量修改**

用户口径：「规格的价格，和库存均支持批量修改，原参数基础上加减去固定值或
原参数值基础倍数+固定值，或直接统一修改成固定值」。

三种模式（`lib/precheck-publish.ts::BatchEditMode`）：

| 模式 | 语义 | 例（原值 1280） |
|---|---|---|
| `delta` 加减固定值 | 原值 + N（N 可负） | N=100 ⇒ 1380 |
| `scale` 倍数+固定值 | 原值 × K + N | K=2, N=50 ⇒ 2610 |
| `fixed` 统一改固定值 | 一律 = N（不看原值） | N=999 ⇒ 999 |

落点与约束：

* 纯逻辑在 `lib`（`applyBatchRule` / `applyBatchRuleToTable` / `priceColumnIndex` /
  `stockColumnIndex`），**可 vitest 直测**（10 条）；
* 列识别与 `tableToSkus` **共用同一套别名**（`原价/价格/单价/price`、`库存/stock/数量`）——
  否则「批量改的列」和「读出的列」不是同一列（改了个寂寞）；
* ⚠️ **空值不参与**（缺值口径）：原值为空的单元格保持空，不写 `"0"`；
* 价格下限裁剪到 0（不为负）；库存给上限；
* 整数不补 `.00`、小数保留两位；
* 应用前**二次确认**（整列几十行，误点代价高），确认文案写明「将修改 N 行（空值不参与）」。

### 12.3 规格列表复选框（勾选后只改选中的行）

用户口径（2026-10-09）：「规格列表加一个复刻框支持选中的再批量修改」（「复刻框」= 复选框）。

  只保留 antd 表头自带的全选；

* ⚠️ 范围外行**一个字符都不碰**（`applyBatchRuleToTable` 的 `onlyRows` 分支先短路返回原行）；

### 12.4 批量修改：**先选列** + 中间符号可选（用户口径 2026-10-09）

* 「有原价有计算价格，还有可能是更多其它值，应选择指定的列，而不是写价格列和库存列」

* ⚠️ **不再写死「价格 / 库存」两条** —— 改成一个**列选择器**（`Select`，选项 = `table.columns`
  全部列，默认可识别到价格 / 库存列时预选它、否则第一列）。表里有什么列就能批量改什么列

  故「倍数+负数」= 原值 × K − N；
* 确认文案写明**改的是哪一列**（「批量修改「计算价格」…」）。

### 12.6 缺陷：**第二次改库存点「应用」无响应**（2026-10-09 修复）

现象（用户实测）：预检「商品sku表格」里第一次批量改库存成功，**第二次点「应用」无反应**。

根因（跨组件状态被 drop，非按钮本身）：
* 页面把 **`tables.filter(t => !Array.isArray(t.kv))`** 的**子集**（只 SKU 表）交给
  `TablesPanel`，但面板改完把**子集**整体上抛给 `onTablesChange` ⇒ 父级 `tables` 里
  的**属性表（kv）被丢掉**；
* 属性表一丢 ⇒ 页签集合变化（「商品属性」页签消失）⇒ `TablesPanel` **重挂载** ⇒
  面板内的 `operand` / `mode` / `sign` 全部**归零** ⇒ 「应用」按钮回到 `disabled`
  （`operand === null`）⇒ 第二次点击看起来「无响应」。

修法（单一职责：面板只管单表，父级管映射）：
* 面板改为上抛 **`(panelIndex, nextTable)`** 单表；
* 父级用 `mergePanelTable(full, panelIndex, next)` 按 **`skuTableIndices`（SKU 表真实下标）**
  嵌回**完整数组**再落库 —— 属性表原地保留，页签不再重建；
* 纯逻辑（`replaceAt` / `skuTableIndices` / `mergePanelTable`）下沉到 lib，vitest 可直测
  （含「连续两次改同一列都落上」与「越界原样返回」）。

### 12.7 移除批量修改的二次弹窗提醒（用户口径 2026-10-09）

用户口径：「移除批量修改的二次弹窗提醒」。

* 点「应用」**直接落改**（不再 `modal.confirm` 阻塞确认）；
* 落改后给一条**轻提示**（`message.success`）交代改了什么：
  「把「库存」每条加 10 已应用（26 行）」/ 勾选时「（勾选 5 行中 3 行）」；
* 空值不参与、范围外不动、价格下限 0 等既有口径**不变**；

### 12.8 缺陷：**点「应用」列数据不变化**（2026-10-09 修复）

现象（用户实测）：点「应用」后列数据没变（看起来「未生效」）。

根因（勾选键与行下标**类型不符**）：
* `Table` 的 `rowKey` 写成 **``${tIndex}-${index}``**（字符串）⇒ `selectedRowKeys` 里是
  `"0-5"` 这类**字符串**；
* 批量修改把勾选键直接当行下标用 —— `applyBatchRuleToTable(..., onlyRows)` 内部
  `scope.has(rowIndex)`，`rowIndex` 是**数字** 5 ⇒ **永不匹配** ⇒ 只要存在勾选，
  所有行都被「范围外」短路掉，整列也改不动；
* 未勾选时 `scope` 为 `undefined`，本应整列可改 —— 但同一份勾选状态只要非空就
  全局失效，表现为「点了应用没反应」。

修法：`rowKey` 改为返回**数字行下标**（`record.__index`），与 `scope` 的比对口径一致。

## 二十、「依旧不生效」的**真根因**：静态产物无 `Cache-Control`（2026-10-10）

用户连续多轮报「适用对象展示**依旧**换行」，而**服务端产物已是最新**（`/` 指向
`index-1eanSb34.js`，包内含 `maxTagCount:1` 与卡片红框样式）—— 排查到浏览器侧：

* Starlette `StaticFiles` **不发 `Cache-Control`**（实测 `/` 与 `/assets/*.js` 的响应头里
  只有 `etag` / `last-modified`）⇒ 浏览器走**启发式缓存**，`index.html` 被缓存后不再回源校验，
  于是**长期指向旧的 `index-<hash>.js`**。这解释了「源码/产物都对，用户仍看到旧行为」。
* 修法（`backend/app/main.py`）：加响应中间件
  * `index.html` 与客户端路由（末段无 `.`）⇒ **`Cache-Control: no-cache`**（每次回源校验）；
  * `assets/*`（带内容 hash）⇒ **`public, max-age=31536000, immutable`**（hash 变即文件名变，
    天然免冲突）。
* 守卫：`tests/backend/test_root_main.py::test_static_assets_get_cache_headers`（真起 app 打端点，
  断言入口 `no-cache` + 产物 `immutable`；用例内 `importlib.reload` 属**全局副作用**，已在
  `finally` 还原模块态）。变异（删中间件）**CAUGHT**。

⚠️ 结论口径：**改前端后若用户报「依旧」，先确认浏览器加载的是不是新 hash**，不要在源码层反复改。
