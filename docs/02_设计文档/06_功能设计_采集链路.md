## 2. 账号登录（三种方式）

### 2.1 扫码登录

```
前端                          后端                     小红书
 │  POST /xhs/login-sessions/{pc|creator}/qrcode
 │────────────────────────────▶│
 │                             │ 建 LoginSession(status=pending) + 加密存临时 Cookie
 │                             │ 请求平台生成二维码
 │                             │────────────────────────▶│
 │◀── {session_id, qr_url} ────│◀─── qr_id + code ───────│
 │ 展示二维码                    │
 │  每 2s GET /xhs/login-sessions/{id}（轮询）
 │────────────────────────────▶│ check_qrcode_status
 │                             │────────────────────────▶│
 │                             │   codeStatus: 0 未扫 / 1 已扫 / 2 已确认 / 3 过期
 │◀── {status: pending/scanned/confirmed/expired}
 │                             │
 │                             │ 【码 2：确认】换 web_session
 │                             │ → upsert platform_accounts（按 external_user_id）
 │                             │ → 追加 account_cookie_versions（Fernet）
 │◀── {status: confirmed} ─────│
```

**状态机**：`pending → scanned → confirmed`（或 `expired`）

**关键实现点**：
- PC 与 Creator 是**两条独立链路**（不同域名、不同签名域、不同常量）：
  - PC：`apis/xhs_pc_login_apis.py`（`XHSLoginApi`），域名 `edith` / `as` / `www` / `pages`
  - Creator：`apis/xhs_creator_login_apis.py`（`XHSCreatorLoginApi`），域名 `customer` / `creator` / `as` / `edith`
- Creator 登录牵涉 **CAS 域**，QR 与验证码 POST 走 `mns0201/nop` 冷路径
- Creator 侧 `CREATOR_WEB_BUILD='1.29.1'`（`xhs_creator_login_apis.py:34`）是**硬编码版本号**，同时进入 Cookie 头与 MNS 签名物料 → 平台发版后会过期（已发生一次，见 `05_项目沉淀/02`）

### 2.2 手机验证码登录

```
POST /xhs/login-sessions/{sub_type}/phone/send-code   → 平台下发短信
POST /xhs/login-sessions/{sub_type}/phone/confirm     → 校验并换取会话
```

### 2.3 Cookie 导入

```
POST /api/accounts/import-cookie
  → 校验 Cookie 格式（必须含 a1 等关键项）
  → upsert platform_accounts
  → 追加 account_cookie_versions（Fernet 加密）
```

> **设计要点**：Cookie **永不覆盖写**，永远追加新版本（详见 `03_数据模型设计.md` §3.2）。

### 3.4 用户主页笔记

**存在两条语义不同的入口，不可混用**：

| 入口 | 语义 | 路由 | 状态 |
|---|---|---|---|
| 全量循环 | 适配器 `get_user_notes()` → `apis/xhs_pc_apis.py:321 get_user_all_notes()`，**内部循环翻页** | `POST /api/xhs/crawl/user-notes`（`crawl.py:302`） | ⚠️ 真实但**有全量循环**，前端未调用；已知限流风险 **DEF-033** |
| **单页** | 适配器 `get_user_posted_page()`，**只取一页，不含循环** | `POST /api/xhs/pc/users/notes` | ✅ **2026-09-18 去 mock，供「我的笔记」使用** |

> **设计原则（新增）**：面向前端**交互式浏览**的读取，一律走**单页**入口并分页拉取（前端加载更多），
> 不得复用全量循环方法。理由：一个有几百篇笔记的账号会在**单次请求**里打出几十个平台调用，
> 既触发风控，也超出前端超时。全量循环只保留给后台批处理（监控巡检 / 数据抓取），
> 且该路径的限流护栏尚未补齐，已登记为 DEF-033。

**我的笔记四类数据（纯实时、不落库，详见 `12_功能设计_我的笔记与互动数据.md`）**：

| 范围 | 平台接口 | 列表键 |
|---|---|---|
| 我发布的 | `user_posted` | `data.notes` |
| 我赞过的 | `user_liked`（feed 形态） | `data.items` |
| 我收藏的 | `user_collected`（feed 形态） | `data.items` |
| 互动消息（赞藏/提及/新关注） | `you/likesAndcollects` / `you/mentions` / `you/newConnections` | `data.message_list` |

> ⚠️ **三个列表键名不同**，归一化层用探测而非单一假设（`_extract_list`）。

## 4. 流式抓取（SSE）

```
前端 POST /api/xhs/crawl/data
      │  参数：account_id, mode(url|keyword|comments), targets, page, count, interval, save_to_library, filters
      ▼
后端逐条处理，每处理一条推一个 SSE 消息
      │
      ├─ 搜索/详情 → pc_api_adapter
      ├─ 素材下载 → asset_downloader（存 storage/media/）
      └─ save_to_library=true → 写 notes + note_assets + note_comments
      ▼
前端 Table 实时追加行
```

**关键工程点**：
1. Vite 代理必须对 SSE 关闭缓冲（`vite.config.ts:13-20`），否则进度不实时。
2. 前端用**原生 fetch** 而非 axios（axios 无 SSE 支持）。
3. `save_to_library` 是**请求级开关，不持久化**。
4. 请求间有 `interval` 间隔，降低被识别为爬虫的概率。

## 5. 素材下载与归一化入库

### 5.1 素材下载

| 项 | 内容 |
|---|---|
| 服务 | `backend/app/services/asset_downloader.py` |
| 落盘 | `backend/app/storage/media/` |
| 访问 | 经 `GET /api/files/media/{name}` |
| 记录 | `note_assets.url`（远端）+ `note_assets.local_path`（本地） |

### 5.2 归一化原则

| 原则 | 说明 |
|---|---|
| **保留原始响应** | 每条 `notes` 都存 `raw_json` → 平台字段变化时可回溯补数据 |
| **URL 与本地双存** | 远端链接可能失效，本地是可靠副本 |
| **排序显式化** | `sort_order` 字段，不依赖返回顺序 |
| **时间不转换** | 远端时间以字符串原样存（`created_at_remote`），避免解析误差 |

## 6. 监控目标抓取

```
调度器 monitoring_refresh_runner（每 interval_seconds）
  → 取 status=active 的 monitoring_targets
  → 按 target_type 抓取（keyword / account / brand / url）
  → 写 monitoring_snapshots
  → 失败累计 consecutive_failures++，≥3 → status=paused + 发通知
```

**设计要点**：
- 抓取选号只取 `platform_accounts.status == "active"` 的账号（`monitoring_crawl_service.py:33,40`）
- ⚠️ `crawl_interval_minutes` 字段**未被读取**，定时刷新是全局全量（死配置）
- ⚠️ 手动 refresh 端点**不校验 target.status**

## 7. 采集链路的复用模式（二开参照）

> 二开的「店铺 / 商品同步」应当**完整复用本节模式**，不另起一套。

| 环节 | 现有做法 | 二开沿用方式 |
|---|---|---|
| 账号 | Cookie 加密 + 不覆盖写 | 千帆 Cookie 独立账号/独立域存储 |
| 适配器 | `XhsPcApiAdapter(cookies)` 构造签名 | 新建 `ShopApiAdapter(cookies)`，同形态 |
| SDK | `apis/xhs_pc_apis.py` 用 `XHSPcAuth` | 新建薄封装，复用 `PcDeviceProfile` |
| 归一化 | `raw_json` 留证据链 | `shops.raw_json` / `shop_products.raw_json` |
| 调度 | 复用 `monitoring_refresh_runner` 模式 | 复用同一调度器，加一个 job 或并入现有 job |
| 失败处理 | 累计失败自动暂停 + 通知 | 复用 `notification_service` |

### 7.1 二开新增：店铺与商品同步

```
千帆商家后台（人工登录 → 导出 Cookie）
   │
   ▼ POST /api/shops/import-cookie
shops（含 capabilities_json）
   │
   ▼ POST /api/shops/{id}/sync
shop_products（含 raw_json）
   │
   ▼ 定时（复用调度器）
增量更新 shops.synced_at / shop_products.synced_at
```

**为什么不需要重新逆向**（关键判断依据）：

| # | 证据 | 出处 |
|---|---|---|
| 1 | `run_signer(api, data)` 签名输入**只有 path + body**，**host 完全不参与** | `xhs_utils/xhs_pc/runtime.py:68-106` |
| 2 | `XHSPlatformConfig` 本就是多业务域扩展点，已有 PC / Creator 两个实例 | `xhs_utils/xhs_core/auth.py:15-84` |
| 3 | `HostCookieStore` 已按 host 分域管理 Cookie | `xhs_utils/xhs_core/cookies.py:44-171` |
| 4 | **已有先例**：`apis/xhs_pugongying_apis.py:19-26` 直接构造 `PcDeviceProfile` 给 `pgy` 域签名 | 同栈服务多域在本仓库跑通过 |

> **结论：接千帆是「加配置 + 加接口」的工程，不是「重新逆向」。**
> 未知量只剩三个，全靠抓包定：`app_id`（参与 MNS 签名与 DS 获取）、登录态 Cookie 名、是否携带 `x-s-common` / `x-rap-param`。

### 7.3 范式：「新增一个只读业务域」的标准六步（2026-09-18 由「我的笔记」沉淀）

> 本节是**可复制的清单**。二开再要接一类新的平台读取（如真千帆的商品/订单列表），照这六步走，
> 不要自由发挥——每一步都有对应的既有机制，跳过任何一步都会留下一类已知缺陷。

| # | 步骤 | 落点 | 反面教训 |
|---|---|---|---|
| 1 | **文档先行** | 先写需求规格 + 功能设计，再动代码 | 跳过会出现「代码有了但设计文档没跟上 = 未完成」 |
| 2 | **SDK 探能力，不改 `apis/`** | 只确认 SDK 有单页方法 | 直接改 SDK 会破坏逆向层的独立可复用性（H-6） |
| 3 | **adapter 薄封装** | `backend/app/adapters/xhs/pc_api_adapter.py` 加方法，返回 `(success, msg, payload)` | 让路由直接调 SDK = 绕过适配层，域名/Cookie 差异无处安放 |
| 4 | **归一化探测而非假设** | 列表键、分页键、身份字段全部**探测**（`_extract_list` 等） | 三个平台接口用了三个不同列表键；写死一个必然漏 |
| 5 | **诚实降级** | 拿不到就**结构化报错**（带 `code`）或**返回 `null`**，不造假 | 「0 处假数据」是验收硬指标；编造一个空商品比报错更坏 |
| 6 | **限流与架构守卫** | 只用**单页**方法；写 AST 断言把「禁全量循环」钉进测试 | 单页是风控要求，靠人自觉一定会被后续重构破坏 |
