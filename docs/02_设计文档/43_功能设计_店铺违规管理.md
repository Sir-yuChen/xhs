## 1. 业务逻辑与判据

### 1.1 这个页面是什么

千帆后台 `店铺体检 → 违规管理`（`/app-violation/violation-manage/*`）是商家处理平台处罚的唯一入口：
看清被罚了什么、处罚方式与生效期、能不能申诉、有没有整改/考试机会、赔付与仲裁单、抽检违规、免罚权益。
本系统把它**一比一搬到店铺线**，让用户不必在两个后台之间来回切。

### 1.2 零落库（用户口径，硬判据）

| 项 | 判据 |
|---|---|
| 新建表 | **0** |
| 迁移 | **0** |
| 写本地表 | **0**（服务层不 import ORM/Session，仅路由用 `db` 做归属校验与取令牌） |
| 平台数据 | 现取现渲染；页面刷新即重新拉取 |

> 为什么能零落库：违规数据是**平台权威状态**（用户随时在千帆后台处理），本地存一份必然与平台漂移，
> 而用户的需求是「看到平台真实状态」，不是「看历史快照」。与设计 22 图片空间同一取舍。

### 1.3 只读边界（比「只读页面」更严）

平台对这个域提供两个写接口，本系统**刻意不接**：

| 平台接口 | 千帆的行为 | 本系统的处置 |
|---|---|---|
| `POST /api/edith/ark/violation/read_mark` | 打开详情自动标已读（影响「未读 N」角标） | **不调用**。前端可本地标记，UI 明示「本地标记，不同步平台」 |
| `POST /api/edith/violation/appeal/*`（提交申诉） | 真实提交申诉材料 | **不调用**。申诉弹窗一比一复刻 UI 与校验，点提交后**明确告知**「本系统不代提交申诉，请在千帆后台提交」，不伪造成功回执 |

判据（源码级，守卫 `test_violation_manage.py` 钉住）：
`violation.py` / `violation_service.py` / `qianfan_api_adapter.py` 的违规域方法里
**不得出现** `read_mark`、`appeal/submit`、`batch_delete` 字符串；违规域 SDK 方法**必须**走
`_signed_post` / `_signed_get`。

### 1.4 批量操作的执行口径（**2026-10-18 用户口径推翻首版**）

> 首版理解成「批量一律拦截」，用户当天明确纠正：
> 「**系统支持批量功能**，只是在你开发过程中不要使用大量的数据去测试批量功能，
> 只使用一条数据测试批量按钮即可」。

所以：**批量是真功能，必须点得动、跑得出结果**；「安全」体现在
① 开发与验收阶段只用 **1 条数据**；② 批量项**不含任何写平台的动作**。

| 批量项 | 写平台？ | 说明 |
|---|---|---|
| 标记为已读 / 标记为未读 | 否 | 与单条同源（本地标记），**幂等设定**而非逐条切换 |
| 导出选中记录 | 否 | 只读导出 CSV（UTF-8 BOM，Excel 可直接看） |
| 批量删除 / 批量申诉 | **不提供** | 千帆违规域**没有**批量写接口（列表页连行勾选框都没有），凭空造一个会动平台数据的按钮比不给更危险 |

判据（`frontend/src/lib/violation-manage.ts` + vitest）：

- `BATCH_ACTION_LABELS` 恰为三项，且任一项文案都**不含**「删除 / 申诉」；
- `setReadMarks()` 是**幂等设定**：已读的 3 条 + 未读的 2 条一起「全部标已读」⇒ 5 条全已读
  （若循环调 `toggleReadMark`，那 3 条会被翻成未读 —— 这是批量最容易出的错）；
- `keepVisibleKeys()`：跨页残留的勾选**不许生效**，动作只能落在当前页可见的行上；
- 导出只含被勾选的行，列顺序 = `EXPORT_HEADERS`（中文表头）。

⚠️ 数量上限：**不做**。功能本身允许全选，限制只在「开发测试阶段只用一条数据」。

### 1.5 数据口径（缺值不造，硬约束⑤）

| 字段 | 缺值时 |
|---|---|
| 违规原因 / 处罚方式 / 单号 / 时间 | 渲染 `-`（不渲染 `0`、不渲染空串） |
| 未读 / 待处理角标 | 平台返回 0 时渲染 `0`（这是真实计数，与「缺值」不同） |
| 违规证据 | 平台 `data:null` ⇒ 显示「平台未提供证据」，不造占位 |
| 申诉记录 | 空数组 ⇒ 显示「暂无申诉记录」 |
| 高价商品卡 | 接口失败 ⇒ **不渲染那张卡**（不显示 0） |

### 1.6 违规原因是 tagId 分组，不是文案

真机 `user_tag` 返回 10 个 tag 组，其中：

```
违反法律法规            → ["80001101","80001738","80001764","80001776","80001801"]
违反法律法规<尾空格>    → ["80005677"]        ← 与上面是两条不同 tag
账号下存在搬运…          → ["79548255"]
笔记存在创作质量不佳的内容<尾空格> → ["79548256"]
```

判据：`reason_tag_ids()` **精确匹配、不 trim**。按名字 trim 去重会把两组合并，用户选中
`违反法律法规` 时漏掉 `80005677` 那组数据 —— 请求仍 200，静默少几条。
守卫：`test_tag_name_not_trimmed_or_deduped`（变异「加 `.strip()`」必须红）。

## 附录 B · 本轮实测踩到的坑（都不是「写错代码」，而是「平台/组件真实行为」）

1. **违规域整片强制签名**：不带 `x-s`/`x-t` 连**只读 GET 枚举**都回 `{"code":-1,"success":false}`。
   ⇒ 14 个 SDK 方法全部签名，`test_violation_sdk_methods_are_all_signed` 钉死（变异 `unsig_sdk` CAUGHT）。
2. **`normalize_detail` 入参两种形态**：路由拿到的是完整 envelope（`{code,data:{detail:{info}}}`），
   首版按 `detail.info` 直接取 ⇒ **详情字段全空但不报错**。⇒ 改为同时兼容 envelope 与 data 层。
3. **`TABLE_SCROLL_X` 写大 = 表格被强行拉宽**：写 1400 而 8 列合计 930 ⇒ 右侧 4 列被推出视口，
   用户看到的是「页面少了四列」。**这个值必须等于列宽之和**。
4. **antd `Tag` 在 60px 列宽里会把文字竖排**（自带 4px 边框 + 8px 内边距 + 8px 外边距）
   ⇒ 两个状态列改用纯色 `Text`。
5. **`ellipsis` 挡不住内容把列撑宽**：列宽生效后仍需 `white-space: nowrap` 的表头，
   否则「处罚处理状态」被拆成两行、整行高度翻倍。
6. **凭证过期 ≠ 空表**：`arkBlocked` 只判「本地有没有令牌」，平台回的「登录凭证已过期」
   必须**常驻红条**（`upstreamError`），否则用户读到的是「本店没有违规」。
7. **店铺体检是视图不是子 Tab**：`/violation-manage/checkup` 是**独立路由**（页面组件内 `useMatch` 判分支），`?view=checkup` 保留为等价旧口径。

## 6. 实测数字与边界（2026-10-18 ~ 2026-10-19）

### 6.1 ⚠️ 实测推翻调研报告一处：尾空格 tag 实际是 **U+200B 零宽空格**

调研报告 §3 记作「`违反法律法规`(尾空格) → 80005677」。本轮 `meta` 实测的 tagName 字面是
`'违反法律法规\u200b'`（**零宽空格 U+200B**，不是普通空格 `\x20`）。

| 项 | 影响 |
|---|---|
| `reason_tag_ids` 的匹配方式 | **不变** —— 仍是「精确字符串相等、不 trim、不去重」。零宽空格 trim 也去不掉（`str.strip()` 只去空白字符），所以两种写法下「不 trim」都成立 |
| 前端的显示 | `\u200b` 不可见 ⇒ 下拉里两条「违反法律法规」**看起来同名**，极易被用户当成重复项 |
| 后端的防线 | 不能按名字合并/去重（会合并两组 tagIds，实测 5 个 vs 1 个）；**必须用 `tag_ids` 区分** |

> 结论：设计判据（R2/R3）不变，但**原因下拉必须显示 `tag_ids` 数量或后缀提示**，否则用户
> 在 UI 上无法区分两条同名原因。（卡 2 已落地：原因下拉显示 `tag_ids` 条数，见前端 `violation-manage.ts`。）

### 6.2 本轮实测修掉的 bug 与工具约定

| 项 | 事实 |
|---|---|
| `quick_filter_body` 预警分支 | 键名写成**平台字段名**（`severePunishmentFlag` / `correctableFlag` / `allowAppeal`）而不是**服务层入参**（`severe_only` / `correctable` / `allow_appeal`）⇒ 点「高危预警 / 可整改 / 可申诉」一次性 `TypeError: build_list_body() got an unexpected keyword argument` ⇒ 500。已修，`test_quick_filter_warning_set` 钉住 |

## 8. 店铺体检页布局对齐千帆（2026-10-19）

### 8.1 用户口径

### 8.2 千帆原页结构（截图取证）

```
┌────────────────────────────────────────────────────────┐
│ [图标] 店铺经营状况良好，未检测到待优化项                │  ← 状态条（一行）
│        ✓ 暂无违规风险 ✓ 暂无经营建议 ✓ 暂无负反馈风险     │
│        体检时间范围：2026.9.19 ~ 2026.10.19              │

├────────────────────────────────────────────────────────┤

│                     暂无数据                             │
├────────────────────────────────────────────────────────┤
│ 10条/页  共0条,1页                        ‹ 1 › 跳至__页 │  ← 分页栏
└────────────────────────────────────────────────────────┘
```

### 8.3 改前 vs 改后

| 项 | 改前（不符） | 改后（对齐） |
|---|---|---|
| 顶部 | `Text` 一句话 + `Segmented` | **状态条**：图标 + 结论 + 三项 ✓/✗ + 体检时间范围 |
| Tab | `Segmented`（分段控件） | **`Tabs`**（与原页同款下划线页签） |
| 内容 | 每个风险类型一张 `Card` + 独立 `Table` | **一个 `Table`**，列随 Tab 变 |
| 分页 | 无（`pagination={false}`） | **有**：10/20/30/40/50 + 共 N 条 + 跳页 |

### 8.4 两个实测坑（都会导致「看起来没生效」）

1. **给 `Tabs` 设 `height: 100%` 会把表格挤出可视区** —— 实测表头与数据整块空白，
   只剩 Tab 和一大片空白。Tabs 不该占满高度。
2. **`scroll={{x}}` + 默认 `auto` 布局会忽略列 `width`** —— 「风险场景」被挤成
   逐字竖排（`风/险/场/景`）。必须 `tableLayout="fixed"`。
