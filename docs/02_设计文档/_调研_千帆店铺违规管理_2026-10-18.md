## 1. 页面结构

`/app-violation/violation-manage/*` 是一个单页应用，顶部两个 Tab，第二个 Tab 内再分 6 个子 Tab：

```
店铺体检 | 违规管理
            ├── 店铺状态卡（严重违规 0 / 高危预警 0，各带「查看全部」）
            ├── 预警列表        /warning_service
            ├── 违规列表        /list   ← 默认落点
            ├── 赔付列表        /order-compensation
            ├── 仲裁列表        /arbitrate
            ├── 抽检违规列表    /spot_check
            └── 免罚机会        /punishment（内含「现货爆单豁免」「优质发货免赔付」两个子页）
```

URL 与 Tab 一一对应（改 URL 可直接落子 Tab）。首次进入会弹引导层（`dm-tour-guide`），必须走完/跳过才能点。

## 7. 我方落地的关键结论

1. **列表是同一接口双场景**：`warnFlag` 0=违规、1=预警，其余字段语义一致 ⇒ 我方只需一张「违规单」表 + `warn_flag` 列，不必建两套。
2. **违规原因必须走 `tagIdGroup` + tagId 映射表**，不能用原因文案过滤；映射来自 `user_tag`，且存在**同名不同 ID**（`违反法律法规` 与 `违反法律法规`(尾空格) 是两条 tag）——入库时**不能 trim 去重**，否则两组合并会漏数据。
3. **时间过滤是「天粒度补齐」**：开始取当天 00:00:00.000，结束取当天 23:59:59.999；只传日期串会被服务端按毫秒判定。
4. **严重违规 = `severePunishmentFlag`**，与 `violationLevel.violationLevel` 是两个字段，别混用（实测 1 条记录 `level=2` 且 `severePunishmentFlag=false`）。
5. **`canAppeal` 与 `appealStatusInfo.appealStatus` 要一起看**：`canAppeal=true` 但状态可能仍是「不可申诉」（历史单已撤），展示层以 `appealStatusInfo.displayName` 为准。
6. **签名必须复用站点运行时**：`/api/edith/*` 无 `X-s/X-t` 一律 406。若要接入我方，只能走真实浏览器会话（与现有千帆 ark 会话方案一致），不要试图在 Python 侧复算签名。
7. **`read_mark` 是写接口**：打开详情即自动标已读 ⇒ 抓取时会影响「未读」计数。我方同步若只读，应直接调 `list` 与 `info`，避免调用 `/read_mark`。
