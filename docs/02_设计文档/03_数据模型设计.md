## 2. 用户域

### 2.1 `users`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | Integer | PK, index | — |
| `username` | String(80) | unique, index | 登录名 |
| `password_hash` | String(128) | — | `pbkdf2_sha256$260000$<salt>$<hash>`；兼容旧裸 sha256 |
| **`role`** | String(32) | default `user`, **server_default `user`**, index | **权限角色**：`admin` / `user`。✅ 2026-09-18 新增（T-104 / 迁移 `b1e4d7c9a2f3`） |
| `created_at` | DateTime | default `shanghai_now` | — |

**`role` 设计要点**（2026-09-18 新增）：

1. **刻意不做完整 RBAC**。系统只有「全局级设置」一处需要区分身份，其余资源全靠 `user_id` 隔离
   → 单一 `role` 列足够。**原任务书写的「加 `is_admin` / `role`」已收敛为只落 `role`**：
   两个字段表达同一件事必然出现不一致。
2. **`server_default='user'` 是必需的**，不是可选优化——它保证迁移后**存量行立即有值**，
   否则非空校验/判定会在旧行上出问题。
3. **未知取值 → 保守降级为 `user`**（与 `sub_type` 的策略**相反**，见 ADR-014）。
4. **迁移的引导规则**：把**最早创建**的用户提升为 `admin`。
   若不提升，迁移后系统里不存在任何管理员 → **全局开关将永久无人可改**（实测：用户 `zy晨` 升为 `admin`）。
5. 权威定义在 `core/roles.py`（`ROLE_ADMIN` / `ROLE_USER` / `normalize_role` / `is_admin`）；
   鉴权依赖 `core/deps.py::require_admin`（非管理员返回 403）。

## 3. 账号矩阵域

### 3.1 `platform_accounts`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | Integer | PK, index | — |
| `user_id` | Integer | FK→users.id, index | 归属用户 |
| `platform` | String(32) | index | 平台标识，现仅 `xhs` |
| **`sub_type`** | String(32) | nullable | **协议链路**：`pc`（采集）/ `creator`（发布）。⚠️ 仅表达技术链路，不表达业务含义 |
| `external_user_id` | String(128) | nullable | 小红书侧用户 ID（登录 upsert 的键） |
| `nickname` | String(128) | default `""` | — |
| `avatar_url` | Text | default `""` | — |
| `status` | String(32) | default `unknown` | `active` / `expired` / `unknown` |
| `status_message` | Text | default `""` | 状态原因（给前端展示） |
| `profile_json` | Text | default `{}` | 平台返回的原始资料 |
| **`note_sync_cursor_ms`** | BigInteger | **NOT NULL, default 0** | **笔记增量游标**（设计 13 §17.9）：上次**成功落库**的最大 `publish_time`（毫秒）。**0 = 从未同步过 → 下一轮自动走全量**。只在落库成功后推进，且只增不减 |
| **`note_sync_cursor_note_id`** | String(64) | default `""` | 同毫秒并列时的**防漏保险**（同 `publish_time` 的第二条会因此被纳入）。调试辅助，不参与早停判定 |
| **`deleted_at`** | DateTime | **nullable** | **软删标记**（台账 §4.9 / I3）：非空 = 已删除。行**不物理删**，唯一索引因此永久成立 |
| `created_at` / `updated_at` | DateTime | — | — |

**唯一键（I1，2026-09-20 新增）**：`(user_id, platform, sub_type, external_user_id)`，
**部分唯一索引** `uq_platform_accounts_identity`（仅 `external_user_id` 非空时生效）。

- **必须含 `sub_type`**：同一小红书账号的 `pc` 与 `creator` 是两条**合法链路**
  （`_sync_creator_account_from_pc_cookie()` 有意派生、卡片上明确区分「类型：PC / Creator」）。
  合成一条看似「更干净」，实际会**丢掉发布能力**（发布闸门要求 `sub_type == "creator"`）。
- **必须只作用于非空 `external_user_id`**：空 id **不构成身份**；若参与约束，多个空 id 账号会互相冲突。
  空 id 的重复改由业务层 `(user_id, platform, sub_type, nickname)` 兜底匹配拦住 —— **既不伪造 id，也不无界新建**。
- 与代码**逐字对齐**：`upsert_platform_account_from_login()` 的查询条件就是这个键。DB 约束是它绕过不去的那道底。

**设计要点**：

**`idempotency_key` 为什么必须 nullable**（最容易做错的一处）：

| 若设为 NOT NULL | 后果 |
|---|---|
| 「建了 → 取消 → 再建同样内容」 | 这条**合法流程**会被唯一索引无故挡死，且报错不可理解 |
| 多条「未认领」任务共存 | 不可能（多个 NULL 不违反唯一索引，但多个相同的非空值会） |

**释放规则**（详见 ADR-013）：仅当能证明**从未提交给平台**时才释放。
`从 pending 取消` → 释放；`从 scheduled 取消` / `failed` → **不释放**。

### 9.2 `shop_account_bindings`（**⛔ 已被取代 · 整表已移除**；关系回到 **1:1**，现行形态见 §9.2.1）

> **2026-09-22 变更**：店铺↔账号**不再是 N:M**，`shop_account_bindings` **整表移除**（迁移 `m5n6o7p8q9r0`）。

> 现行契约见 **§9.2.1**；设计侧动机见 `docs/02_设计文档/13_功能设计_账号矩阵同步.md` §20 与 ADR-020。

#### 9.2.1 现行形态：店铺 ↔ 账号 **1:1**（2026-09-22，用户口径）

用户口径原文：**「不再允许同店铺多账号，一个店铺下只存多个平台的会话令牌」**。
⇒ 关系不再需要中间表，**三件事各归其位**：

| 要表达什么 | 落在哪 | 约束 / 唯一入口 |
|---|---|---|
| **关系**（这个账号读哪个店） | `platform_accounts.shop_id_fk` | **部分唯一索引** `uq_platform_accounts_shop_id_fk` —— `UNIQUE (shop_id_fk) WHERE shop_id_fk IS NOT NULL AND deleted_at IS NULL` ⇒ 一店至多**一个活跃账号**；**软删账号不再占店**；多行 `NULL` 不冲突（故不能写成整列 `unique=True`） |
| **凭据**（千帆登录态） | `account_cookie_versions` 的 **`ark` 通道** | 唯一取票入口 `qianfan_cookies_for_account(db, account_id)`；无令牌返回**空串**（**不借、不兜底**） |
| **状态 / 游标**（`status` / `status_message` / `goods_note_total` / `goods_synced_at` / `goods_cursor_ms` / `health_checked_at`） | `platform_accounts.shop_state`（JSON 文本） | 读写只经 `get_shop_state` / `set_shop_state`，且必须赋**新 dict**（见 §「SQLAlchemy JSON 列原地改不标记脏」） |

`shop_note_goods` 的归属列 **`binding_id` → `platform_account_id`**（**换列不改语义**：映射本来就按账号挂）。
迁移 `m5n6o7p8q9r0` 五步：凭据搬家（账号自有通道优先）→ 关系 + 状态搬家（软删账号不继承店铺）→
SQLite 显式重建 `shop_note_goods` → `DROP TABLE shop_account_bindings` → 清理**多余账号历史数据**
（`id IN (1, 15)`，从属行一并物理删除）。

**为什么 1:1 反而更对**：N:M 的**唯一动机**是企业店「多子账号读同一店」，而用户已明确该场景不成立
（要的是**同店多平台令牌**，不是多账号读同一店）。用中间表表达 1:1 ⇒ 必然长出两个病：①「同一店铺
好几行、这次用哪一行」的随机性（旧实现要靠 `goods_synced_at` 排序 + `id` 倒序兜）；② 跨租户脏行
（真实库里确实躺着一条）。改成**列 + DB 约束**后，这两个问题**结构上不存在**（不是"管住了"，是没有了）。

**换店 = 旧店作废**：`attach_shop` 在换店时先 `detach_shop(db, account)` 清掉旧店映射 —— 否则
`shop_note_goods` 按账号挂会在换店后**跨店串数据**。

**并发/越权兜底**：`bind_shop` 两道闸 —— 租户内 `account_for_shop(db, shop_pk, user_id)` +
**全库** `any_account_for_shop(db, shop_pk)`，把 IntegrityError 换成 **409 `QIANFAN_SHOP_TAKEN` + 人话**
（全库那道是必须的：部分唯一索引是**全库级**约束，只看本租户会漏掉别的租户的残留行）。

|---|---|
| 1 | **同步过商品映射的优先**（`goods_synced_at` 非空，按时间倒序）——有映射的那条才「能显示商品」 |

| 计划 | 实现 | 理由 |
|---|---|---|
| `shop_id_fk → shops.id` | **已放回**（T-32） | `shops` 表已建；`shop_user_id` / `shop_name` 按计划保留为冗余展示字段 |

### 9.5 迁移与兼容性

| 项 | 结论 |
|---|---|
| 现有表改动 | **零改动**（不新增 `platform_accounts` 字段、不新增 `sub_type` 取值） |
| 新增 Alembic 版本 | 计划里是「4 张表一次迁移」，**实际分开**：`c7a4e51d9b02`（`shop_account_bindings` + `shop_note_goods`）、`e2b8f1a6c4d7`（`health_checked_at`）、**`f4a1c8e2d935`（T-32：`shops` + 绑定表重建为 N:M）**、**T-802（`shop_products`，账号矩阵同步）**。拆开是因为每条迁移都对应一次已交付的窄需求；攒成一条大迁移会让「哪次交付改了结构」不可考 |
| 是否影响一期功能 | 否。新增表无反向依赖 |

| **唯一性迁移（2026-09-20）** | `d4e5f6a7b8c9`：加 `deleted_at` + 两个唯一索引 + **存量去重（保留最新）**。**必须幂等**（见 §9.5.1）；已在库副本上验证 `upgrade` / `downgrade` / 重复 `upgrade` **三向可用**，并验证了「重复账号被拒 / 重复笔记被拒 / 空 `external_user_id` 两行可共存」三种行为 |

#### 9.5.1 为什么唯一性迁移必须幂等（2026-09-20 实测事故）

**症状**：应用**连续崩溃重启**，日志里只有
`api(uvicorn 127.0.0.1:8000) exited (code 3) → restart in 5s`，**没有 Python traceback**
（启动失败那一层没被记进 `app.log`），而库停在**半迁移**状态：
`deleted_at` **已加**、唯一索引**不存在**、`alembic_version` **仍是旧值**。

**机理**：SQLite 的 DDL **不在事务里**（alembic 自己会打印 `Will assume non-transactional DDL`）。
迁移中途失败 ⇒ 已执行的 `ALTER TABLE ADD COLUMN` **留在了库里**，而 `alembic_version` **没推进**。
下次启动（应用启动时自动 `upgrade head`）从**同一个 revision 重头再跑**，
在 `ADD COLUMN` 上抛 `duplicate column name` ⇒ 启动失败 ⇒ 监督进程 5 秒后重启 ⇒ **再失败**。

**两条对策**（均已落地）：

1. **幂等**：加列前查 `PRAGMA table_info`，建索引用 `CREATE ... IF NOT EXISTS`；
   去重逻辑天然幂等（没有重复就是空操作）。
2. **去重里的「改挂」不能直接 `UPDATE`**：`shop_account_bindings` 的唯一键**含 `platform_account_id`**，
   而重复账号**往往绑的是同一个店** —— 直接改挂会当场撞唯一约束
   （`UNIQUE constraint failed: shop_account_bindings.shop_id_fk, shop_account_bindings.platform_account_id`）。
   正确做法是**先把可能撞键的去重做完、再合并账号**，且改挂绑定时要「**同店已存在就合并**」而不是覆盖。

**通用教训**：**「迁移失败」不是原子的**。任何可能在**启动路径**上跑的迁移，都必须假设
「自己上次已经跑了一半」，并且能在那种状态下**继续跑完**。

| `synced_at` | DateTime | — | 本次同步时间 |

**唯一约束**：`UNIQUE (platform_account_id, note_id)` —— 约束名 `uq_shop_note_goods_account_note`
（**被取代**：原为 `UNIQUE (binding_id, note_id)` / `uq_shop_note_goods_binding_note`，随绑定表移除一并更名；语义不变）

**设计要点**：

1. **为什么落库**（与需求 D2「不落库」的边界）：D2 说的是**笔记本身**不落库。
   这里是「另一平台的映射缓存」——若每次浏览都去翻千帆的页，等于把翻页成本摊到每一次浏览上；
   而**按需补齐**（v1.12）用一个 `note_ids` 过滤参数把成本压到「每页 ≤1 次」：
   `GET /api/edith/goods-note/list?note_ids=a,b,c` 支持逗号分隔多 ID，只返回这些笔记的挂载商品。
   ~~千帆的商品笔记列表没有按 `note_id` 查询的口子（实测加 `note_id` / `keyword` 参数被忽略）~~
   —— 该结论**被 v1.12 取代**：早前只试了**单数** `note_id`（被忽略），**复数 `note_ids` 才是口子**
   （实测单条命中 total=1、阴性 0、2/6/10/20/50 个 ID 精确返回）。
   落库仍必要：命中过的笔记第二次浏览**零平台请求**（平台不返回「无商品」的负记录）。
2. **存整条 `entry_json` 而不是逐列建模**：千帆字段集还会变，
   新增一个展示项不应再打一次平台、也不该改表。
3. **只在完整同步时清理陈旧行**：未扫完就删 = 丢数据（同步纪律见 §12 设计文档 §24.3）。

## 11. 设计约定（新增表时必须遵守）

1. **时间字段**：一律 `DateTime`，`default=shanghai_now`。**禁止** `datetime.now()`、禁止存 naive UTC。
2. **半结构化数据**：优先 JSON 列；只有需要 SQL 过滤/排序/索引的字段才抽成独立列。
3. **证据链**：任何来自平台的原始响应，都要有 `raw_json` 字段留存。
4. **归属字段**：用户级数据必须有 `user_id`（带 index）；账号级数据必须有 `platform_account_id`。
5. **软删除**：当前项目**用硬删除**，新增表沿用（如需软删，必须先在设计文档中说明）。
6. **迁移**：所有表结构变更必须写 Alembic 版本脚本，**不允许**依赖 `create_all` 兜底上线。
