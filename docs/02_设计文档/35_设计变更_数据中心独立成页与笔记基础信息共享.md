## §1 一句话

「我的笔记」里的「商业笔记 / 普通笔记」两个 Tab 本质上不是「我的账号的笔记」，
而是**千帆数据中心的历史统计数据** —— 它从两条链路落进 `notes` 表（一条写 `raw_json.ark`、
一条写 `raw_json.metrics`），与内容库的数据搅在一起，且笔记一删、统计跟着消失。

本设计把它拆成两个正交实体：**`notes`（笔记基础信息，内容库/数据中心共享）** 与
**`note_datacenter_stats`（数据中心统计，独立历史，不随笔记删除消失）**；
分类判据从「两写入者、判据不同源」的 `note_category` 列，收敛为统计表里的
**平台原生 `note_flag`** 单一权威。

按调用方参数顶上。**两条通道在同一账号上互相消音**。

## §3 目标形态

```
notes（笔记基础信息 · 唯一表，内容库 + 数据中心共享）
   基础信息：note_id / title / content / author_name / 封面(资产表) / created_at
   状态：    note_type / publish_status / publish_error / published_at
   来源：    raw_json（只看来源原文，不再承载数据中心指标）
   hydrated_at / platform_missing_at

note_datacenter_stats（数据中心统计 · 新建，无外键，历史独立）
   键：user_id / platform_account_id / note_id（字符串，非外键）
   窗口：stat_date + window（recent_1/7/90/custom）
   分类：note_flag（平台原生，唯一权威）
   快照列：title / cover_url / item_id / item_title / variant_desc / publish_time
   指标 26 列（真实列，可 SQL 筛选排序）
   删除标记：platform_deleted_at（笔记删了统计仍在）
   元数据：synced_at / created_at
```

**核心关系**：`notes` 是「身份」（可能被删），统计表是「历史」（永在）。数据中心列表
`stats LEFT JOIN notes`，`notes` 缺行时用统计行的快照列渲染。

## §4 归属与展示（用户问的三种情况）

| 情况 | `notes` 行 | 展示 |
|---|---|---|
| A · 两页都展示 | ✅ 存在 | 内容库显示 `notes`；数据中心显示 `notes` 最新基础信息 + 统计列 |
| B · 只在数据中心 | ❌ 不存在/已删 | 数据中心用统计行**快照列**渲染，标「笔记已不在内容库」 |
| C · 只删统计 | 不出现 | 数据中心不支持「只删统计」；清理时统计行打 `platform_deleted_at` 保留 |

**内容库保持原样**：`GET /notes` 全表，不 JOIN 统计表，**不显示指标列**（指标归数据中心）。
两页行集合各自定义，不再需要对总数（拆解「同一批笔记两页给不同总数」的老问题）。

## §5 数据模型

### 5.1 `note_datacenter_stats` 表

| 列 | 类型 | 语义 |
|---|---|---|
| id | Integer PK | |
| user_id | Integer FK users.id, index | 租户隔离 |
| platform_account_id | Integer, index | 归属账号 |
| note_id | String(128), index | 平台 note_id，**非外键**（笔记删了统计仍在） |
| stat_date | String(10), index | 同步执行日 YYYY-MM-DD |
| window | String(16) | 数据窗口 recent_1/7/90/custom |
| note_flag | String(24) | 平台原生分类（goods_note/空） |
| title / cover_url / item_id / item_title / variant_desc / publish_time | 快照列 | `notes` 缺行时渲染用 |
| read_count / like_count / collect_count / comment_count / share_count / follow_count / danmaku_count | Integer | 互动 |
| video_duration / avg_view_time / full_view_rate | Numeric | 观看 |
| pay_gmv / pay_order_cnt / pay_user_cnt / item_click_cnt / item_click_uv / item_click_pv_rate / pay_pv_rate / pay_uv_rate | Numeric | 商品 |
| refund_gmv / refund_order_cnt / refund_user_cnt / cart_item_cnt / lead_user_page_view_cnt / lead_user_page_pay_gmv / lead_live_view_cnt / lead_live_pay_gmv | Numeric | 退款/引流 |
| browse_num_30d | Integer | 平台补充（ark 的 note_browse_num30d） |
| platform_deleted_at | DateTime nullable | NULL=未删，非空=已从平台清理（历史保留） |
| synced_at / created_at | DateTime | |

唯一键：`uq_datacenter_note_date_window (user_id, platform_account_id, note_id, stat_date, window)`
索引：`(user_id, platform_account_id)` / `(note_id)` / `(stat_date)`

### 5.2 为什么指标落真实列（非 JSON）

数据中心三个核心动作（列表展示 / 按指标筛选 / 阈值判定）都要 SQL。JSON 无法筛选排序，
落列后「阅读 < 50 且支付订单 = 0」是一个 WHERE，「清理无流量」候选查询即候选，
不再全表扫 + Python 过滤。

### 5.3 为什么 `window` 进唯一键

`butterfly/data` 返回的是**所选窗口的累计值**，不是「当天值」。不记 window 会把
「近 30 天阅读」冒充「今日阅读」。记上 window，同一笔记不同窗口各一行是诚实的，
列表取用户所选窗口那一行。

### 5.4 `note_metric_snapshots` 去留

**保留不动**，与新表语义不同：

| | `note_metric_snapshots` | `note_datacenter_stats` |
|---|---|---|
| 键 | `note_pk` FK → `notes.id` | `note_id` 字符串，无外键 |
| 源 | 内容库笔记 `raw_json`（creator/www） | 千帆数据中心 |
| 用途 | 内容洞察指标趋势（内容线） | 数据中心列表/筛选/清理（店铺线） |
| 随笔记删除 | 跟着删 | 保留 |

两条业务线的数据本就该分开（设计 32 方向），此处落实。

## §7 写入链路

### 7.1 链路 A · 笔记管理 → 只写 `notes` + 顺带写统计

| 现状 | 改为 |
|---|---|
| 新建行 `raw_json = ark_raw`（扁平） | 只留基础信息，**不写指标** |
| 命中行 `raw_json.ark = ark_raw`（嵌套） | 同上，**形态统一**（修掉同一源两种形状） |
| 写 `note_category` | **不写**（分类归统计表 `note_flag`） |
| 指标写 `notes` | 同步时**顺带写一行统计**（window=recent_1） |

### 7.2 链路 B · 数据中心 → 写统计表 + 补基础信息

| 动作 | 规则 |
|---|---|
| 写统计 | UPSERT `note_datacenter_stats`（26 列 + 快照列 + `note_flag` + `window`） |
| 补基础信息 | `note_id` 在 `notes` 不存在 ⇒ 建一行；存在 ⇒ 只补空字段**不覆盖** |
| `note_category` | **不写** |
| xlsx 导入 | 与 butterfly 同一落库函数，window 记 `custom` |

### 7.3 指标优先级（合并契约）

```
重叠字段：A（笔记管理）有值就用 A，A 缺/None 才回退 B
    browse_num → read_count   like_num → like_count   collect_num → collect_count
    comment_num → comment_count   share_num → share_count
    note_pay_gmv → pay_gmv   note_pay_order_cnt → pay_order_cnt
B 独占 15 项：原样透传
「A 有值」判据：value is not None（0 是有效值，不因假值跳过）
```

## §8 删除语义

| 动作 | `notes` | 统计行 | 平台 |
|---|---|---|---|
| 内容库删笔记（`purge_note`） | 删 | **保留** | 不动 |
| 数据中心「清理无流量」 | 删（清理成功后） | **保留** + 写 `platform_deleted_at` | 真删（goods→千帆批量 / 其他→creator 逐篇） |
| 数据中心「批量删除」 | 删 | 保留 | 勾选「删本地+平台」时真删（goods→千帆批量 / 其他→creator 逐篇）；默认只删本地不动平台 |

三条纪律：
1. `purge_note` docstring 补「不删统计行」说明（现实现也不删，但要把「为什么不删」写清，否则下一个维护者会「顺手补上」）。
2. 清理执行器从 `candidate.local_id → db.get(Note)` 改为**按 `note_id` 查**（统计行没有 local_id）。
3. 列表默认 `platform_deleted_at IS NULL`，给「含已删除」开关。

> ⚠️ **批量删除是正常产品能力，完整保留**（2026-10-12 用户澄清）：`/notes/batch-delete`
> 的「只删本地 / 删本地+平台」两种方式**都保留**，千帆批量删、creator 逐篇删的原有
> 分流逻辑**不变**，仅分流判据由 `note_category` 改为 `note_flag`。用户此前说的
> 「不允许批量删除平台数据」指的是**测试/开发过程中不得触发真实平台批量删除**，
> 不是要删掉代码里的批量删除功能。
