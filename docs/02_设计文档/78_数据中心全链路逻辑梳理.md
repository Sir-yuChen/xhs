> 2026-10-28 现状快照。所有数字与端点均**实测**（`/openapi.json` + PG 元数据 + 代码路径），
> 不是转述设计文档。数据中心与内容库已彻底拆分：**读路径互不 join**。

## 1. 一句话

数据中心 = **平台笔记事实的本地快照**（`note_datacenter_stats` 一张表），
不存 `notes`、不查 `notes`、删只删平台。数据进来源有三条（定时同步 / 手动导入 / 补链接），
出有四条（列表查询 / 详情实时拉 / 批量删平台 / 无流量清理）。

## 2. 数据落点：`note_datacenter_stats`（1 张表 / 43 列 / 3697 行）

| 列组 | 列 |
|---|---|
| 归属 | `id` `user_id` `platform_account_id` `note_id` |
| 窗口 | `stat_date` `window`（`recent_1` / `custom`） |
| 分类 | `note_flag`（`goods_note` / 空） |
| 快照（渲染用） | `title` `cover_url` **`note_url`**（含 `xsec_token`，详情唯一入口）`item_id` `item_title` `variant_desc` `publish_time` |
| 互动 | `read_count` `like_count` `collect_count` `comment_count` `share_count` `follow_count` `danmaku_count` |
| 观看 | `video_duration` `avg_view_time` `full_view_rate` |

## 3. 数据进（3 条写入路径）

### 3.1 定时同步（主路）
```
job: system.note_data_sync（每 6h）
  → scheduler_service.run_scheduled_note_data_syncs（按用户 fan-out）
  → 千帆 butterfly/data 列表接口（只读、无签名直连）
  → parse_butterfly_response → NoteDataRow
  → upsert_note_data_rows → _upsert_datacenter_stat（UPSERT）
```
- UPSERT 键 = `(user_id, account_id, note_id, stat_date, window)`
- **只写统计表，不碰 `notes`**（2026-10-28 拆除的副产物写入）
- 缺值写 `None` 不写 0（缺值口径）

### 3.2 手动导入（xlsx）
```
POST /api/notes/import-data（multipart: file + category + account_id）
  → 校验 .xlsx / 非空 / 账号归属（越权 404）
  → 落临时文件 → 异步线程解析 → 同一套 _upsert_datacenter_stat
  → 进度写 scheduled_job_logs（任务中心「任务日志」可见）
  → 完成后站内通知推统计；临时文件删除
```

### 3.3 补链接（`note_url` 回填）
`note_url` 是 2026-10-28 新增列。**存量 3697 行的 `note_url` 为空** ⇒ 那些笔记点详情会返回
`no_url`。只有重新同步 / 重新导入的数据才带链接。

## 4. 数据出（4 条读/写路径）

### 4.1 列表查询 `GET /api/notes/offline`
**零平台请求，一条 SQL**。

| 维度 | 参数 | 落到 |
|---|---|---|
| 分类 | `category`（`goods`/`normal`） | `note_flag == 'goods_note'` / `!=` |
| 账号 | `platform_account_id` | 等值 |
| 标题 | `keyword` | `title ILIKE %kw%` |
| 单篇 | `note_id` | 等值 |
| 已删除 | `deleted`（`all`/`deleted`/`active`） | `platform_deleted_at` 是否为空 |
| 发布时间 | `published_from` / `to` | `publish_time` 闭区间 |
| 七项指标 | `read_from/to` `like_*` `collect_*` `comment_*` `share_*` `pay_gmv_*` `pay_order_*` | 各列闭区间 |
| 排序 | `sort_by`（白名单列）+ `sort_order` | `ORDER BY` |
| 分页 | `page` / `page_size`（≤100） | `LIMIT/OFFSET` |

⚠️ **同 note 多窗口去重**：先按 `stat_date desc` 取，前端拿到的是最新窗口那行。

### 4.2 详情 `POST /api/notes/{note_id}/hydrate`
```
读统计表（只认 user_id + note_id）→ 无行 ⇒ 404 DATACENTER_NOTE_NOT_FOUND
  → fetch_datacenter_note_detail(note_url)
  → explore SSR（匿名，无需登录，靠 URL 自带 xsec_token）
  → 返回 {status, content, topics, image_urls, video_url}
```
- **纯读零落库**：不写 `notes`、不写 `note_assets`、不写 `topics`
- `status` ∈ `ok` / `no_url`（缺 token）/ `skipped_by_limit`（限流）/ `failed`
- 与线上笔记 `POST /xhs/pc/notes/detail` 同口径（都不落库）

### 4.3 批量删平台 `POST /api/notes/batch-delete`
```
入参 {note_ids[], platform_account_id（必填）}
  → 账号归属校验
  → 读统计表 note_flag 分流
     · goods_note：千帆 batch_delete_notes → 创作者逐篇兜底
     · 普通笔记：创作者 delete_note → 千帆批量兜底
     · 任一成功即止，不重复删
  → 返回 {deleted, failed[], results[]}
```
**只动平台，不碰本地 `notes`**（表都不读）。数据中心 UI 只有一个「删除平台笔记」入口。

### 4.4 无流量清理（异步任务，两步）

**候选** `POST /api/xhs/pc/users/no-traffic/candidates`
- 候选池 = 统计表，**零平台请求**（原 docstring 说调千帆 `mix_search_word`，已改）
- 条件全部下推 SQL：账号 / 分类 / 标题 ILIKE / 指标区间 + 阈值合并成区间上界
- 门禁 = `creator` 通道有令牌（不是 ark：删的是创作者平台的笔记）
- 返回 `{candidates, total, page, page_count, coverage}`

**执行** `POST /api/xhs/pc/users/no-traffic/cleanup` → 后台任务
```
建 tasks 行 + no_traffic_cleanup_logs 行（开账）
  → 读统计表拿候选（同 4.4 上半段的条件）
  → 分流：goods_note 千帆批量（每片 ≤50）/ 普通笔记创作者逐篇
  → 平台删成功：deleted += 1，明细行记 RESULT_DELETED
  → 平台说「笔记不存在」：等价已删，不算失败
  → 平台删失败：failed += 1，明细记真实原因
  → _finish 写 log（计数 + 耗时 + aborted）
  → _record_items 写 no_traffic_cleanup_items（逐篇「为什么没删」）
```

**只在平台删，本地一律不动**（`purge_note` / `is_deleted` 已全部移除）。

**进度查询**：`GET .../cleanup/active`（有没有在跑）、`GET .../cleanup/{task_id}`（进度）、
`GET .../cleanup-logs`（历史批次）。

`draft_to_dict()` / `publish_to_dict()` 字段与合并前逐字段一致
（`draft_id` / `file_path` 是 `parent_id` / `local_path` 的别名）⇒ 前端 8 个请求函数
与响应模型无需改动。展示层逻辑（`url` 拼 `/api/files/media/`、

## 12. 字典两表合并（2026-10-28，34 → 33 张）

用户口径「dict_types 和 dict_items 合并一张表，父子，懒加载，项目骨架基础表」。

### 12.1 结构

`dict_types`(46) + `dict_items`(219) → **`dict_rows`**（L0 项目骨架，**不加 `xhs_` 前缀**）

| 层 | `row_type` | 字段 |
|---|---|---|
| 类型 | `type` | `name` / `code`（唯一）/ `status` / `remark` |
| 项 | `item` | `parent_id` / `type_code`（冗余）/ `label` / `value` / `list_class` / `sort_order` |

### 12.2 为什么用**单表继承**而不是别名

`DictType` / `DictItem` 是 `DictRow` 的两个子类（`polymorphic_on=row_type`）。
`select(DictType)` 自动带 `WHERE row_type='type'` ⇒ **现有几十处查询一行不用改**，
也不会因为漏加条件把类型行和项行混读。

`DictItem.type_id` 用 `synonym("parent_id")` ⇒ 构造点、过滤点、序列化全都不用改。

⚠️ 判据是 `row_type`，不是 `parent_id IS NULL` —— 后者只是「类型行没有父」的巧合，
任何孤儿项行都会被当成类型读出来。

### 12.3 两条唯一索引必须是**部分索引**

* `uq_dict_rows_type_code ON (code) WHERE row_type='type'` —— 普通 UNIQUE(code)
  会被「项行 code 为空串」互撞。
* `uq_dict_rows_parent_value ON (parent_id, value) WHERE row_type='item'`

### 12.4 字典仍是**镜像**

Python 常量（`note.PUBLISH_STATUSES` 等）是代码的唯一真相源，字典只服务前端下拉。
漂移由守卫报红，**不做双向同步**。这条口径没有因合表改变。
