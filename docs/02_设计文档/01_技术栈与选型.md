## 1. 一句话技术形态

> **单体 Python 服务 + React 单页应用 + Node.js 签名子进程**，单机 Docker 部署，SQLite 默认 / MySQL 生产。

---

## 2. 开发语言

| 层 | 语言 | 版本要求 | 选择理由 |
|---|---|---|---|
| 后端服务 | **Python** | 3.10+ | 逆向 SDK 生态成熟；`curl_cffi` 提供浏览器 TLS 指纹伪装；与 SDK 同语言，避免跨语言边界 |
| 签名算法 | **JavaScript（Node.js）** | 20+ | 签名算法的原生形态就是 JS（从浏览器侧提取），移植到 Python 需要重写并承担双份实现漂移风险 → **直接跑原版 JS** |
| 前端 | **TypeScript** | 5.9+ | 类型安全；配合 antd 的组件类型定义 |
| 数据库 | SQL | — | SQLAlchemy 2.0 声明式映射 |

**为什么后端不用 Go/Java**：核心难点是**逆向签名**而非吞吐。`xhs_utils/**/js/` 的 16 个 JS 文件是资产本身，换语言不会降低维护成本，反而增加跨语言调用面。

**为什么签名不用 Python 重写**：

> 签名算法唯一实现位于 `xhs_utils/**/js/`，Python 侧无第二份实现。这是硬约定（见 `03_开发文档/01_开发规范与架构硬约定.md`）。

理由：① JS 是原版，行为可对齐浏览器；② 单源实现，平台改版只需改一处；③ Python 侧只负责序列化输入、调 Node、校验输出。

## 3. 系统架构形态

| 维度 | 选型 | 理由 |
|---|---|---|
| 架构风格 | **单体应用 + 严格分层** | 单机自部署、小时级中低频负载；微服务只增加运维成本 |
| 进程模型 | 单进程（FastAPI + APScheduler 同进程） | 简单；代价是多副本不安全（技术债，见 `05_项目沉淀/02`） |
| 前后端分离 | 是（开发期分离，生产期前端静态文件由后端托管） | 开发体验与部署简便兼顾 |
| 通信协议 | REST（JSON）+ SSE（抓取进度流） | SSE 用于长任务实时进度，比 WebSocket 轻 |
| 有状态部分 | 签名运行时状态（设备指纹、MNS 序号）随请求构造 | 无独立会话服务 |

## 4. 数据库选型

| 环境 | 选型 | 理由 |
|---|---|---|
| 默认 / 开发 / 单机 | **SQLite**（`data/spider_xhs.db`） | 零配置、单文件、便于自部署；本项目写入频率低 |
| 生产 / 多用户 | **MySQL 8**（`mysql+pymysql`，`utf8mb4`） | 并发写入与锁行为优于 SQLite |

**ORM / 迁移**：**SQLAlchemy 2.0**（`Mapped` / `mapped_column` 声明式）+ **Alembic**（迁移脚本）。

**选型理由**：
- SQLAlchemy 2.0 的类型化声明与 Pydantic 风格一致，前端 TS 类型可对应。
- Alembic 保证已有部署可平滑升级（首次启动会自动 `stamp head` + `upgrade head`）。

**已知代价（必须知道）**：
1. SQLite 使用 `PRAGMA journal_mode=MEMORY`（`backend/app/core/database.py:31`），**不是 WAL** → 并发写入更易锁表。
2. SQLite 下时间字段以裸 `DATETIME` 存储，历史数据曾为 UTC，启动时有幂等修复会整体 `+8h` 迁移（`database.py:94-149`）。

**为什么不用 PostgreSQL**：无强需求（无 JSONB 高级查询、无地理、无全文检索诉求），引入会增加自部署门槛。

**JSON 字段的使用**：`profile_json`、`raw_json`、`publish_options`、`capabilities_json` 等用 JSON 列存半结构化数据。**原则**：需要被 SQL 过滤/索引的字段必须抽成独立列，JSON 只放「整体读写的证据链或配置」。

## 5. 是否有移动端

> **没有移动端，本项目是纯 Web 运营后台。**

| 项 | 结论 |
|---|---|
| 移动 App | ❌ 不做 |
| 移动 H5 适配 | ❌ 不做（antd 桌面端布局，侧边栏 + 多栏工作区） |
| 响应式 | 仅桌面浏览器；页面按 ≥1280px 设计 |
| 移动端相关服务 | 无（无推送、无小程序） |

**理由**：核心操作（三栏编辑器、表格批量操作、拖拽排序、图片工坊）在移动端体验无法成立；且系统是运营人员坐在电脑前使用的后台工具。

**注意**：系统内的「手机验证码登录」是**借用手机接收验证码**，不是移动端功能。

## 8. 第三方依赖的集中风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| `curl_cffi` 的 `chrome146` 指纹过期 | 全链路请求被拒 | 版本号是常量，需跟进 curl_cffi 发布；建议做启动自检 |
| Node.js 不可用 | 所有签名失败 → 全系统不可用 | 启动时检测 `node --version`；错误信息要能定位到这一点 |
| 平台改版签名失效 | 采集/发布失败 | 输出门禁会先失败（长度/前缀校验），不会静默发错签 |
| sqlite 并发锁 | 写入失败 | 生产改用 MySQL |
| APScheduler 多副本 | 重复发布 | 见 `05_项目沉淀/02` 技术债 T-03 |
