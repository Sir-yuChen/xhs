## 1. 名词、边界与不做

### 1.1 名词

| 词 | 含义 | 落库 |
|---|---|---|
| 工作流（workflow） | 一张**有向无环图**（DAG）：触发器在头，业务节点按边依次执行 | `workflows` |
| 节点（node） | 图上的一个执行步骤，7 种类型（§3） | `workflow_nodes` |
| 运行实例（run） | 一次具体执行（手动点「立即执行」或定时触发产生） | `workflow_runs` |
| 步骤日志（run log） | run 内**每个节点**一行，先插 `running`，终态回写 | `workflow_run_logs` |
| DAG 边 | 节点间的前后依赖，存 JSON 邻接表（`workflows.graph`） | `workflows.graph` |

### 1.2 硬边界（AGENTS.md 只读约束 + 本期范围）

1. **平台收敛**：工作流的「发布」节点只面向 **www / creator / ark 三平台**（§0.1），与发布队列一致。
2. **写操作只读例外**：工作流链路里唯一触碰小红书写接口的是**发布节点**，走一期发布队列
   （已授权链路，见 `13_功能设计_发布队列与多账号发布.md`）；**其余节点全部只读/本地**。
3. **审核节点默认人工**：不自动放行、不跳过、不可配置为自动（§3.3）。这是设计 16 §6.2 的明确口径。
4. **发布显式确认 + AIGC 标识**：发布节点执行时带 AIGC 标识参数，一期已有逻辑原样复用，不新增判定。
5. **用户隔离**：所有表带 `user_id`，API 一律 `user_id == 当前用户` 过滤（与 `scheduled_jobs` DEF-066 同一纪律）。
6. **不造新底座**：账号级互斥 / 跨账号并行 / 批次号 / 快照 / 孤儿清理 / 调度装配，
   全部复用一期 `note_queue_service` / `note_publish_service` / `scheduler_service`（§5）。

### 1.3 明确不做（排除断点，避免二次评审）

- ❌ 不做**条件分支/网关节点**（if/switch）：DAG 只支持**线性链 + 并行扇出后全部汇合**，不做表达式路由；
  用户要分支就拆成两个工作流。
- ❌ 不做**循环/重试到成功为止**：单节点重试受 `tasks.max_retries`（默认 3）约束，重试耗尽即 `failed`，
  由人在 UI 上点「从失败节点重跑」（§9.3）。
- ❌ 不做**跨工作流调用 / 子工作流嵌套**。
- ❌ 不做**节点拖拽连线编辑器**：一期编排页是**「加节点到链尾 / 删除节点 / 改参数」**的列表式编排
  （§11），连线 = 数组顺序，DAG 结构由后端按数组顺序生成。
- ❌ 不做**实时执行流图动画**：执行进度靠 `workflow_run_logs` 轮询（与一期任务中心同一交互）。
- ❌ 不做**工作流模板市场 / 分享**：工作流行全部私有，无内置种子（§7.4 说明为何不做种子）。

### 2.5 与设计 16 §10 表口径的差异（落地记录）

| 项 | 16 §10 旧口径 | 本文档口径 | 理由 |
|---|---|---|---|
| 表数量 | 「`workflows` / `workflow_nodes` / `workflow_runs` / `workflow_run_logs`，见 §6.2」 | **4 张，字段如 §2.1–2.4** | 旧表只有名字没有字段，本文档补齐 |
| 节点存法 | 未定义 | 节点**独立成表**（`workflow_nodes`）+ DAG 存 `workflows.graph` 邻接表 | 编排页列表式渲染直接查节点表；图结构集中存，校验 DAG 在一处 |
| 快照 | 未定义 | run 三类快照（`graph_snapshot` / `global_params_snapshot` / 日志四列快照） | 一期 `scheduled_job_logs.config_snapshot` 已验证过的纪律：改/删工作流不毁历史 |
| 承载 | 未定义 | run 不自带执行线程，**下沉 `tasks` 队列**（§5.2） | 不新造队列/线程池，账号互斥/批次/快照/清理全复用 |

**净增表 4 张**（`workflows` / `workflow_nodes` / `workflow_runs` / `workflow_run_logs`），全部为**新增**，无一期表加列。

## 3. 节点类型与参数 schema

白名单只在**一处**定义（模型层常量 + 注册表，API 层不重抄 —— 与 `scheduled_jobs` 的 `job_registry` 同一纪律）：

```python
NODE_TRIGGER  = "trigger"    # 触发器：链头，唯一，不可删除
NODE_TOPIC    = "topic"      # 选题（热点匹配，方向 2/3 链路，可选）
NODE_GENERATE = "generate"   # 生成（方向 1 LLM 链路）
NODE_REVIEW   = "review"     # 人工审核：默认人工，不自动放行
NODE_SCHEDULE = "schedule"   # 定时发布：把发布时刻定到指定时段
NODE_PUBLISH  = "publish"    # 发布：复用一期发布队列
NODE_MONITOR  = "monitor"    # 监控回填：触发指标快照任务
NODE_TYPES = (NODE_TRIGGER, NODE_TOPIC, NODE_GENERATE, NODE_REVIEW,
              NODE_SCHEDULE, NODE_PUBLISH, NODE_MONITOR)
```

### 3.1 `trigger`（触发器）

- **位置约束**：链首，`seq=0`，每个工作流**恰好一个**（建表时后端自动补，不可删）。
- `config`：
  ```json
  {"manual_button_label": "立即执行", "note": "每天 9:00 自动跑"}
  ```
- 触发语义**不存这里**：`trigger_type`/`cron_expression`/`run_at` 在 `workflows` 主表上
  （§2.1），因为它们是**调度器装配参数**，与 `scheduled_jobs` 同构（§7.1）。
- 运行时：trigger 节点**不做业务**，仅写入运行上下文（`run.context.global_params`），立即 `succeeded`。

### 3.2 `generate`（生成）

- `config`：
  ```json
  {
    "source": "products" | "topics",          // 商品选题 / 热点选题
    "product_ids": [1, 2, 3] | "$.global.product_ids",
    "template_id": 12 | "$.global.template_id",
    "model_key": "gpt-4o-mini" | null,         // null = 走用户默认
    "review_mode": "manual",                    // 保留位，本期恒 manual（§3.3）
    "notes_per_product": 1
  }
  ```
- **执行**：调用一期生成链路的**入队函数**（`note_gen_llm_worker.enqueue` 语义），
  为每个（商品 × 账号）组合入队一条生成任务，`task_type='workflow_generate'`，
  `payload` 带 `workflow_run_id` / `node_key` / `batch_no`。
- 节点**同步等待全部生成任务终态**（轮询 `tasks` 表，复用一期 worker 的状态词表），
  产出 `detail = {"note_ids": [...], "generated_count": N}`，供下游 `review`/`publish` 节点消费。
- 生成产物落 `notes` + `generation_records`（设计 17 口径），工作流**不新表**。

### 3.3 `review`（人工审核）

- **硬约束**：`config.review_mode` 只接受 `"manual"`；写 `"auto"` 一律 400（§1.3）。
- `config`：
  ```json
  {"reviewers": [1, 2], "review_timeout_hours": 24, "reject_action": "fail_run"}
  ```
- 执行语义：
  1. 节点进入即 `status='waiting'`，run 进入 `status='paused'`，回写 `review_deadline`；
  2. UI 列出本节点产出的 `note_ids`（从上游 `detail` 取），人工**逐条**审：通过 / 驳回 / 跳过；
  3. 全部审完 → 节点 `succeeded`，run 回 `running`，继续下游；
  4. `reject_action='fail_run'` 时任一条被驳回 → 节点 `failed`，run `failed`，`error_type='review_rejected'`。
- **无超时自动放行**：`review_timeout_hours` 只用于 UI 展示「已超时 N 小时」，不触发任何自动动作。
- 审核界面**只读 + 通过/驳回两个写动作**，不触碰笔记正文（符合 AGENTS.md 只读约束）。

### 3.4 `schedule`（定时发布）

- `config`：
  ```json
  {"publish_window": {"start": "18:00", "end": "20:00"}, "timezone": "Asia/Shanghai"}
  ```
- 执行语义：把上游产出的 `note_ids` **打散到时间窗内**（均分 + 随机抖动 ±10 分钟），
  计算出每条笔记的 `scheduled_publish_at`，写入 `notes.scheduled_publish_at`（一期已有列），
  然后**立刻 `succeeded`** —— 它不发布，只「排期」。
- 本节点**不阻塞**：真正的发布由 `publish` 节点或一期的「定时发布」调度任务（`system.due_publish`）消费。
  二者**互斥**：`publish` 节点存在时，`notes.scheduled_publish_at` 已排期的笔记由本工作流接管，
  不再被系统定时任务重复捞（§8.4）。

### 3.5 `publish`（发布）

- `config`：
  ```json
  {
    "account_ids": [10, 11] | "$.global.account_ids",
    "platform": "www" | "creator" | "ark",
    "aigc_mark": true,
    "publish_immediately": false      // false = 等 schedule 节点排期时刻；无 schedule 节点时必须 true
  }
  ```
- **执行**：调一期 `note_publish_service.start_batch_publish`（同账号互斥、跨账号并行、批次号、快照全在它里面），
  `task_type='workflow_publish'`，`payload` 带 `workflow_run_id` / `node_key` / `batch_no`。
- `aigc_mark=true` 时透传发布参数的 AIGC 标识位（一期已实现的合规标识，工作流不新增判定逻辑）。
- 节点等待发布任务终态；失败明细写 `detail.failed`，节点状态按**失败策略**（§9.2）定。

### 3.6 `monitor`（监控回填）

- `config`：
  ```json
  {"metrics": ["note_views", "note_interactions", "note_publish_count"], "snapshot": true}
  ```
- 执行：触发一期**指标快照任务**（`task_type='note_metrics_snapshot'`，已有迁移 `c9d0e1f2a3b4` 支撑的快照表），
  对本 run 产出的 `note_ids` 做一次快照，`detail` 回写快照行数。
- **不直接写仪表盘**：仪表盘读快照表，工作流只负责「让快照新一份」（§12）。

### 3.7 `topic`（选题，可选）

- `config`：
  ```json
  {"topic_ids": [5, 6] | "$.global.topic_ids", "match_top_n": 10}
  ```
- 执行：读 `hot_topics` / `topic_goods_match`（设计 16 §10 方向 2 表），选出 top-N 商品写入运行上下文，
  供下游 `generate` 节点的 `source='topics'` 消费。
- **只读**：不采集热点（热点采集是方向 2 的独立调度任务，工作流只消费结果）。

### 3.8 参数引用语法

`config` 里任何标量可为字符串 `"$.global.xxx"`，执行前由引擎**一次性**从 `global_params_snapshot` 解析：
未命中 → 节点 `failed`（`error_type='param_unresolved'`），不静默用空值跑。
解析结果写入 `workflow_run_logs.detail.resolved`，审计可见。

## 4. 执行引擎

### 4.1 run 状态机

```
pending ──start()──► running ──全部节点终态成功──► succeeded
   │                   │
   │                   ├──审核节点 waiting──► paused ──人工审完──► running
   │                   │
   │                   ├──任一节点 failed──► failed
   │                   │
   │                   └──用户取消──► cancelled
   │
   └──节点重跑（rerun）──► running（从 current_node_id 起）
```

- `paused` **只**由审核节点产生，**只**由人工审核动作解除（§3.3）。
- `cancelled` 只能由用户在 UI 上点「取消运行」，且仅当 run 处于 `running`/`paused`。
  取消是**协作式**的：引擎在每个节点边界检查取消标记，已下沉到队列的任务**不强行终止**
  （与一期队列的取消语义一致：标记取消，队列项自然跑完落库，不产生半发布）。

### 4.2 引擎主循环（伪码）

```python
def execute_run(run_id: int) -> None:
    run = lock_run(run_id)                      # SELECT ... FOR UPDATE，防并发重入
    if run.status not in ("pending", "paused"):  # rerun 允许从 paused/failed 进
        return
    run.status = "running"; run.started_at = now_or_keep()
    nodes = sorted(run.graph_snapshot["nodes"], key=lambda n: n["seq"])
    for node in nodes:
        if not node["enabled"]:
            log(run, node, status="skipped"); continue
        if run.cancel_requested: mark_cancelled(run); return
        run.current_node_id = node["id"]; commit()
        log_row = upsert_log(run, node, status="running")     # 唯一约束兜底重跑
        try:
            resolved = resolve_params(node["config"], run.global_params_snapshot)
            ctx = run.context                                    # 跨节点传递 detail
            if node["type"] == "review" and not ctx["review_done"]:
                log_row.status = "waiting"; run.status = "paused"
                run.review_deadline = now() + node.config.review_timeout_hours
                commit(); return                                 # 等人工
            outcome = REGISTRY[node["type"]].run(resolved, ctx, run)  # 同步阻塞
            log_row.status = "succeeded"; log_row.detail = outcome.detail
            ctx.update(node["key"], outcome.detail)
        except RetriableTaskError as e:                          # §9.2
            log_row.status = "failed"; log_row.error_type = e.code
            run.status = "failed"; run.error_type = e.code; run.error_message = e.msg
            commit(); return
        except Exception as e:
            log_row.status = "failed"; log_row.error_type = "node_error"
            run.status = "failed"; ...; commit(); return
        finally:
            log_row.finished_at = now(); commit()
        run.finished_nodes += 1; commit()
    run.status = "succeeded"; run.finished_at = now(); commit()
```

要点：
- **节点是顺序执行的同步函数**，一个 run 在一个工作线程里跑完（引擎只负责顺序推进 + 状态落库）；
  「并行」只发生在**节点内部下沉到队列之后**（账号级互斥由一期队列保证，§8）。
- `REGISTRY` 是**同进程注册表**（与 `job_registry` 同构）：`node_type -> {run, validate}`，
  `validate` 在保存工作流时校验 `config` schema，不合法直接 400，不进库。
- 引擎线程来自**一期线程池**（`note_queue_service` 已有的池），工作流只**多占一个槽位**，
  不自建 ExecutorService。

### 4.3 并发与重入保护

- run 启动时 `SELECT ... FOR UPDATE`（SQLite 用 `BEGIN IMMEDIATE`，见 §10.3），
  同一 run 两次「立即执行」第二次直接返回，不产生两份日志。
- **工作流级互斥**：同一 `workflow_id` 同时只允许一个活跃 run（`status in (pending, running, paused)`）。
  这是对设计 16 §6.2「账号级互斥」的**工作流层补丁**：否则两个 run 会抢同一批账号。
  二次触发 → 直接 409，返回当前活跃 run id，UI 跳转过去。
- 调度器侧的 `concurrent='forbid'`（§7.1）是第二重保护，与工作流级互斥叠加。

## 5. 与一期底座的复用关系（不重造）

### 5.1 复用清单

| 一期能力 | 工作流怎么用 | 改动 |
|---|---|---|
| `tasks` 队列 | 生成/发布/监控节点的实际执行**全部下沉**为 task 行 | **零改动**（payload 加字段即可） |
| `note_queue_service` 批次号 | run 的 `batch_no` 下沉到 `tasks.batch_no`，复用 `NB` 格式生成器（前缀换 `WF`） | 抽出 `generate_batch_no(prefix)` 共用 |
| 账号级互斥 / 跨账号并行 | 发布节点调 `start_batch_publish`，互斥在它内部 | 零改动 |
| `xhs_sync_account_parallelism` | 发布/生成节点的并行度**读同一个设置项** | 零改动 |
| `note_publish_service` 快照 + 孤儿清理 | 发布节点入队即生成快照；run 被杀后孤儿任务由既有清理任务兜底 | 零改动 |
| `scheduler_service` | 工作流的 cron/at 触发**注册成一个 job**，装配/退避/补偿/日志全部既有 | 注册表加一个 job_key |
| `settings_service.live_int_process` | 工作流执行期间占用 LIVE_KEYS，改设置时提示「有工作流运行中」 | 加 key 类型 |
| 线程池 | 引擎主循环提交到既有池 | 零新建 |

### 5.2 下沉约定（task 行的形状）

每个会下沉的节点，`tasks` 行：

```
task_type  = 'workflow_generate' | 'workflow_publish' | 'workflow_note_metrics_snapshot'
user_id    = run.user_id
platform   = 'xhs' | 'creator' | 'ark'（发布节点带）
status     = 'pending' → 一期 worker 认领 → 终态
payload    = {...业务参数, "workflow_run_id": 123, "node_key": "publish_matrix_a",
              "batch_no": "WF20261004090000-7K2M"}
parent_task_id = run 自己的**批次父行** id（若引擎为 run 建了批次父行）
batch_no   = run.batch_no（复用 ux_tasks_batch_no 唯一约束）
```

`workflow_run_logs.task_id` 回指，UI 从步骤日志可一路点进任务详情（§11.4）。
**反向**：一期任务详情页的 payload 里带 `workflow_run_id` 时，加「返回工作流运行」链接。

### 5.3 进程被杀的恢复

一期已验证的纪律：进程被杀 → 队列里留 `running` 行、调度日志留 `running` 行。
工作流同一套：run 留 `running`，重启后由**启动期恢复扫描**（§7.3）处理：
- run `running` 但其全部 log 行已终态 → 直接置 `failed`（`error_type='interrupted'`），可重跑；
- run `running` 且有 `running` 的 log 行 → 检查其 `task_id`：task 已终态 → 用 task 结果收口；
  task 也 `running` → 走一期队列的孤儿清理（`purge_orphaned_note_goods` 同族逻辑）后，run 置 `failed`；
- run `paused` → 原样保留（本来就等人）。

**不做**自动续跑：恢复只负责「把僵死 run 收敛到 failed」，重跑由人决定（§9.3）。

## 7. 定时调度接入

### 7.1 注册为一个 job

工作流的 `trigger_type='cron'` 或 `'at'` 时，在 `scheduled_jobs` 里**注册一行**：

```
job_key  = f"workflow.{workflow_id}"          # 注册表白名单按前缀放行
name     = f"工作流 · {workflow.name}"
params   = {"workflow_id": workflow_id}        # 不存任何调度字段（设计 15 §4.1 纪律）
user_id  = workflow.user_id                    # 必填（DEF-066）
```

- 调度语义（触发器、misfire、concurrent、退避、补偿、日志）**全部由 `scheduled_jobs` 承担**，
  `workflows` 表上的 `trigger_type`/`cron_expression`/`run_at` 只是**编辑态镜像**，
  装配时复制到 job 行（单向：编辑工作流 → 重装配；不在 job 行上直接改）。
- 执行函数：读 job params 的 `workflow_id` → 建 run（`trigger_source='cron'`/`'at'`）
  → 提交引擎 → 把 `scheduled_job_log_id` 回写进 run（§2.3）。
- **工作流行不存 `last_run_at`/`next_run_at` 的权威值**：那是 job 行的运行态，
  工作流表上的两列只是给列表页用的镜像，由执行函数顺手回写（与一期 `auto_tasks` 回写 `scheduled_jobs` 同一做法）。

### 7.2 `at` 一次性的语义

`trigger_type='at'`：到点执行一次。成功后**不**把 `workflows.status` 改成 `disabled`
（用户口径：一次性工作流执行完仍是 enabled，方便改 run_at 再跑）；
一次性由**调度侧**保证 —— job 行执行成功后由一期 `at` 逻辑把 job 置 `completed`（设计 15 §3.1 既有），
`next_run_at` 清空。再次执行需用户重设 `run_at`（此时重装配一个新 job）。

### 7.3 启动期恢复扫描

在 `main.py` 的 `lifespan` 里、一期已有的启动恢复钩子之后追加一步：

```python
recover_workflow_runs()   # §5.3 的三档收敛
```

幂等：每一档都先判终态再改；重复执行无副作用（一期恢复钩子同一风格）。

### 7.4 为什么不做内置种子工作流

一期 `scheduled_jobs` 按用户各播种一份内置 job（设计 15）。工作流**不播种**：
内置工作流必然带「账号矩阵/商品范围」这类**强业务默认值**，猜错就是批量发布事故（§1.3 排除断点）。
若后续确需模板，走「另存为我的工作流」的**复制**语义（只复制结构，账号/商品留空，必填校验挡住空跑）。

## 8. 并发、互斥与去重

### 8.1 账号级互斥

发布/生成节点下沉到队列后，互斥由一期 `note_publish_service` 的账号锁保证（同账号同时只跑一个发布任务）。
工作流引擎**不自己加账号锁**，否则和队列锁互不可见，必然死锁。

### 8.2 跨账号并行

读 `settings.xhs_sync_account_parallelism`（同一设置项，不给工作流单开并行度 ——
否则两处并行度相加超过用户预期）。工作流的引擎主循环占 1 个槽位，发布任务占 N 个槽位，共用池。

### 8.3 工作流级互斥

§4.3：同一工作流同时一个活跃 run（DB 层唯一约束兜底：
`ux_workflows_active`（`workflow_id`, `status`）只对 `status IN ('pending','running','paused')` 生效
—— 用**部分唯一索引**，Postgres 直接支持；SQLite 用 `WHERE` 过滤的条件唯一索引，两者同一写法）。

### 8.4 与系统定时发布任务的互斥

`notes.scheduled_publish_at` 已排期且**属于某个活跃 workflow_run** 的笔记，
一期 `system.due_publish` 任务**跳过**（判定：`notes.workflow_run_id` 非空且 run 活跃）。
⚠️ 这需要 `notes` 表**加一列** `workflow_run_id`（NULL）—— 与 §2.5 声明的「一期表零加列」冲突。

落地修正（二选一，本文取 **A**）：
- **A（推荐，零加列）**：发布节点 `publish_immediately=false` 时，**不入 `scheduled_publish_at`**，
  而是把排期时刻写进 `workflow_run_logs.detail` + 一个 `workflow_scheduled_publishes` 视图（临时表，见下）；
  一期 `due_publish` 只认 `notes.scheduled_publish_at`，天然不冲突。
- B：给 `notes` 加 `workflow_run_id` 列，`due_publish` 加跳过条件。

A 的代价是多一张**轻量表** `workflow_scheduled_publishes`（`run_id`/`note_id`/`scheduled_at`/`published`），
但它比改 `notes` 安全：`notes` 是全项目最热的表，一期/二期多个方向都在加列，
改它属于**碰撞热点**。本文取 A，`workflow_scheduled_publishes` 计入 §2.5 的表数。

> 净增表因此为 **5 张**（§2.1–2.4 + `workflow_scheduled_publishes`）。§2.5 的「4 张」口径在此修正。

## 9. 异常、重试与幂等

### 9.1 错误类型词表（与 `tasks.error_type` 同构，API 层不重抄）

| error_type | 含义 | 可重跑 |
|---|---|---|
| `param_unresolved` | `$` 引用没命中 | 否（改工作流） |
| `node_error` | 节点执行异常（未分类） | 是 |
| `review_rejected` | 审核驳回 | 否（改内容后重跑生成） |
| `review_timeout` | 超时（仅展示用，不产生此终态） | — |
| `account_busy` | 账号被占（队列互斥） | 是 |
| `publish_guard_blocked` | 一期发布护栏拦截（如商品未挂车） | 否 |
| `rate_limited` | 平台限流 | 是（退避后） |
| `interrupted` | 进程被杀，恢复扫描收敛 | 是 |
| `dag_invalid` | 保存时校验出的结构错误 | 否（保存阶段就 400，不会到运行） |

### 9.2 重试策略

- **节点级**：可重跑错误类型 + `tasks.max_retries`（默认 3）由**一期 worker**保证（节点下沉的任务自带重试）；
  引擎层不重复实现重试，只**透传** task 的 `retry_count` 到 `detail`。
- **节点耗尽重试**：task 行重试耗尽 → 节点 `failed` → run `failed`。**不自动跳过失败节点继续跑**
  （工作流语义要求全链成功；「跳过失败继续」是危险开关，本期不做，§1.3）。
- **退避**：走一期队列/调度器的既有退避（`scheduled_jobs.backoff_until` 同族），引擎不加自己的退避表。

### 9.3 从失败节点重跑（rerun）

`POST /workflow-runs/{run_id}/nodes/{node_key}/rerun`：
1. run 必须是 `failed`（否则 409）；
2. 把该节点及其**全部下游**节点的日志行重置为 `pending`，`finished_nodes` 回退；
3. run `status='running'`，`trigger_source='rerun'`，从该节点重跑（§4.2 的 `nodes` 切片）；
4. 上游已成功的节点**不重跑**（§4.2 的幂等要求：重跑只动下游，因为重跑可能改库状态，重复执行生成/发布是事故）。

**幂等保证**：每个节点的执行函数对同一 `(run_id, node_key)` 必须可安全重复执行 ——
- `generate`：以 `batch_no + node_key` 为幂等键，已生成过的（`generation_records` 里有记录）跳过，复用已有 note_ids；
- `publish`：以 `batch_no + note_id + account_id` 为幂等键，发布队列快照里已存在的直接认领结果；
- `schedule`：`workflow_scheduled_publishes` 里已有排期就跳过；
- `review`：已通过的审核结果在 run context 里，重跑下游时直接放行（不要求重新审核）。

幂等键 = `batch_no`（一期批次号语义的直接延伸，用户 2026-09-26 口径）。

## 10. 安全、隔离与库相关

### 10.1 用户隔离

- 5 张新表全部带 `user_id` 且 NOT NULL；所有端点在 service 层第一步就 `filter_by(user_id=user.id)`；
- run 的 `user_id` 是**执行时快照**，工作流后来归属变化不影响历史 run（一期 `scheduled_job_logs` 同纪律）；
- 定时触发时，执行函数从 job 行拿 `user_id`，**不退化成全库**（DEF-066 的 user_scoped 检查原样适用）。

### 10.2 敏感数据

- 工作流不存任何 cookie/session；账号引用只存 `account_ids`（数字）。
- `global_params` 里可能出现商品名/文案，属于用户自己的业务数据，明文落库（与 `notes` 同级，不升敏）。
- 日志的 `error_message` 截断 2000 字符，**且必须脱敏平台返回体里的 cookie/token 片段**
  （与一期日志脱敏同一过滤器，复用不复造）。

### 10.3 SQLite 与 Postgres 双跑

- 唯一索引一律写 **双方言兼容** 形式：`ux_*` 命名 + 条件唯一索引用 `sqlite` / `postgresql` 两套 `Index` 定义；
- `SELECT FOR UPDATE` 用 `with_for_update()`（SQLite 退化为 `BEGIN IMMEDIATE`，一期 `note_queue_service` 已有同款封装）；
- JSON 列用 `JSON` 类型（一期已在双库跑通），不用方言专属类型。

  `序号 / 类型 chip / 名称 / 参数摘要 / [上移][下移][删除][改参数]` + 底部 `[+ 添加节点]`（7 类白名单下拉，不含 trigger）。
- 参数编辑用**弹窗**，弹窗宽度按视口百分比（`75vw`，用户既有偏好），不用固定像素；
  标题/说明文案**不与表单项挤在一行**（用户既有偏好）。
- 节点 chip 的连线**只是视觉装饰**（CSS 的 → 分隔），不代表可拖拽边（§1.3）。
- 多选项（账号多选、商品多选、指标多选）**不放「全选」按钮**（用户既有偏好：有上限的多选不要全选）。

### 11.4 运行详情页

- 顶部状态条：`状态 / 触发来源 / 开始时间 / 耗时 / 进度（finished_nodes/total_nodes）`；
- 节点步骤列表：每行 `状态点 / 节点名 / 耗时 / detail 摘要 / [查看任务]（跳 tasks 详情）/ [重跑]（failed 且可重跑时）`；
- 审核节点 `waiting` 时，行内展开笔记列表 + `[通过][驳回][跳过]` 三按钮，逐条操作；
- `paused` 时顶部加一条「等待人工审核 · 已超时 N 小时」提示（不自动放行）；
- 轮询：详情页 5s 轮询 run 状态（终态停轮询），与一期任务中心同一交互节奏。

## 12. 监控节点与仪表盘的关系

- `monitor` 节点**只**触发指标快照任务，快照落一期已有的指标快照表（迁移 `c9d0e1f2a3b4`）；
- 仪表盘（方向 3，独立设计文档）**读快照表**，与工作流**无直接耦合**：
  工作流不知道仪表盘存在，仪表盘不知道工作流存在，两者通过快照表解耦；
- run 详情页的「复盘」= 直接读快照表渲染本 run 产出笔记的指标小表（不做图表，图表归仪表盘）。

## 14. 验收用例（TC-WF）

| 用例 | 场景 | 期望 |
|---|---|---|
| TC-WF-001 | 建一个 6 节点链（trigger→topic→generate→review→schedule→publish→monitor），cron `0 9 * * *` | 保存成功；`scheduled_jobs` 出现 `workflow.<id>` 行，user_id 正确，next_run_at 次日 09:00 |
| TC-WF-002 | 同一工作流连续两次「立即执行」 | 第二次 409；只产生一个 run |
| TC-WF-003 | run 执行到 review 节点 | run `paused`，节点 `waiting`；UI 审核前 run 不前进；`review_deadline` 已写入 |
| TC-WF-004 | 审核驳回一条 | 节点 `failed`，run `failed`，error_type=`review_rejected` |
| TC-WF-005 | 发布节点执行 | `tasks` 出现 `workflow_publish` 行，payload 带 run_id/node_key/batch_no；账号互斥生效；`workflow_run_logs.task_id` 回指成功 |
| TC-WF-006 | run 跑到一半杀进程重启 | 恢复扫描把僵死 run 收敛为 `failed`（error_type=`interrupted`），`workflow_run_logs` 无 `running` 残留 |
| TC-WF-007 | 对 failed run 点「从失败节点重跑」 | 上游成功的节点日志保持终态；下游重跑；生成/发布幂等键命中不重复执行 |
| TC-WF-008 | 删除工作流 | run 行保留（workflow_id SET NULL），`workflow_name` 快照可读；节点行 CASCADE 删除 |
| TC-WF-009 | 工作流的 `global_params` 写在 `account_ids`，节点 config 用 `$.global.account_ids` | 执行时解析成功；引用不存在的键 → 节点 failed（param_unresolved） |

| TC-WF-011 | 保存时 `review` 节点写 `review_mode:'auto'` | 400（白名单挡住，不入库） |
| TC-WF-012 | `at` 触发的工作流到点执行一次成功 | job 行 `completed`；再次执行需重设 run_at |

## 15. 风险与对策

| 风险 | 对策 |
|---|---|
| 批量发布事故（一次跑出几十条笔记） | ① 审核节点人工兜底；② 发布护栏（一期 `_check_goods_publish_guard`）原样复用；③ 工作流级互斥 + `concurrent=forbid`；④ 列表页「立即执行」二次确认 |
| 引擎线程被慢节点占死 | 节点内部全部下沉队列（异步），引擎只轮询；轮询超时（单节点 30 分钟）→ 节点 failed（error_type=`node_error`），不无限挂 |
| 工作流与系统定时发布重复发布同一笔记 | §8.4 方案 A：排期不入 `notes.scheduled_publish_at`，走独立表，天然不冲突 |
| `notes` 表成为碰撞热点 | 本文档**不动 `notes`**（方案 A 的直接收益）；所有新列都在新表上 |
| 迁移在真库打到错库 | 显式 `cfg.set_main_option('sqlalchemy.url', ...)` 指向 `data/spider_xhs.db`（项目既有坑，见 AGENTS.md） |
