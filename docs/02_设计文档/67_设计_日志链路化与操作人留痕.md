# 67 · 设计 · 日志链路化（W3C Trace Context）与操作人留痕

> 用户口径（2026-10-25，原文）：
> ① 「所有日志必须有操作人账号」
> ② 「未登录不算，所有已登录的用户操作，日志必须有操作人记录」
> ③ 「日志应以链路式记录，你调研市场成熟方案，实现，后台支持使用链路id查该链路请求的所有日志」
>
> 状态：**已实现并真机验收**。守卫 `tests/backend/test_trace_logging.py`（14 条）。

## 1. 调研结论：选 W3C Trace Context，不自造

| 方案 | 结论 |
|---|---|
| **W3C Trace Context**（`traceparent` 头） | ✅ **采用**。OpenTelemetry 默认传播器；Nginx / Envoy / 各云厂商 APM 都认 |
| OpenTelemetry SDK 全量接入 | ⏸ 暂不。需要 collector + 导出器，本项目日志落在自己的表里，先做**上下文传播**这一层，将来接 OTel 只需把 `trace_id` 映射成真实 span |
| 自造 `X-Request-Id` 格式 | ❌ 不做。将来接任何外部系统都要转换；且没有父子语义 |

**`traceparent` 格式**：`00-<32位trace_id>-<16位span_id>-<flags>`
全部小写十六进制，**全零 trace_id 是 W3C 明令禁止的**（表示"无 trace"）。

## 2. 链路怎么串起来

```
浏览器请求
  │  Header: traceparent（可选，网关传入）
  ▼
TraceMiddleware  ← 最外层（Starlette 后注册者先执行）
  │  ① 解析入站 traceparent（合法则接续，非法则丢弃并新建 —— W3C 不许"修复"）
  │  ② trace_id/span_id 写入 contextvars + request.state
  │  ③ 响应头回写 X-Trace-Id ← 用户拿到 id 的唯一入口
  ▼
ApiAuditMiddleware → api_logs.trace_id
  业务代码 business_log_service.record() → business_logs.trace_id（自动取，调用方不用传）
  定时任务 scheduled_job_runner → scheduled_job_logs.trace_id（用户点"立刻执行"时继承那次点击）
```

## 3. 按链路查全部日志

`GET /api/system/logs/trace/{trace_id}`

把三张表的记录**合成一条按时间升序的平铺时间线**：

| 来源 | `source` 值 | 该链路里记什么 |
|---|---|---|
| `api_logs` | `api` | 谁调了哪个端点、状态码、耗时 |
| `business_logs` | `business` | 业务语义（改了什么配置、登录等） |
| `scheduled_job_logs` | `job` | 定时任务执行过程 |

响应：`{trace_id, count, by_source, events[], found}`，每个事件含 `source / at / level /
actor_id / actor_name / title / summary / detail`。

### 3.1 为什么是平铺时间线，不是 span 树

企业方案（Jaeger / Tempo）返回 span 树，因为它们的 span 有**显式父子关系**
（`parent_span_id`）。本项目只在 HTTP 入口记一个 span，后台任务与触发它的那次点击之间
**没有可靠数据来源**。硬造一棵树会给出**错误的层级**——那比平铺更糟，因为它是"看起来
对的错"。⇒ 先给真实时间顺序（正是用户读日志的方式），接 OTel 有真实 span 关系后再升级。

### 3.2 安全边界

非管理员按 `actor_id` 只看到**自己**的记录；管理员看全部 —— 这是运维排查的前提
（用户报一个 `X-Trace-Id`，管理员要能查完整链路）。端点挂 `system:log:view`。

## 4. 操作人留痕（用户口径 ①②）

| 表 | 操作人字段 | 现状 |
|---|---|---|
| `api_logs` | `user_id` | 已登录请求 0 条缺失（实测） |
| `business_logs` | `actor_id` + `actor_name` | 171 条历史为空，新写入自动带 |
| `scheduled_job_logs` | `user_id` | 0 条缺失 |

**"未登录不算"的落地**：401 / 403 的拦截记录本来就没有操作人（请求没通过认证），
这是正常的。**已登录请求必须 100% 有操作人** —— 实测「已登录但没记操作人」= **0 条**。

## 5. 审计口径的修订（重要）

原口径：`api_logs` 只记「审计前缀下的**写**操作 + 任何失败」。
新口径（本设计）：**审计前缀下的读与写都记**。

**理由**：用户要「按链路 id 查该链路请求的**所有**日志」。只记写的话，一条链路里
"用户点了什么、页面读了哪些数据"全是空白，链路**残缺** —— 排查时看到"改了配置"
却不知道改之前读了什么，因果链断掉。

**边界仍然守着**：非审计前缀（`/api/notes`、`/api/tasks` 等业务读）不记 —— 那会把
`api_logs` 撑成全量访问日志（每次页面加载几十行），淹没有价值的行。

**登录/注册**：整体由 `SKIP_PREFIXES` 跳过（凭据语义由 `business_logs` 定向埋点记），
但 `TRACE_ALWAYS_PREFIXES` 例外留一条链路起点 —— 否则"某用户登录后做的所有事"
这条链路的开头是空的。**不落 body、不落 token**。

## 6. 三条实测踩坑（都写进守卫了）

1. **`BaseHTTPMiddleware` 的 `call_next()` 返回后上下文已恢复** ⇒ 在 `dispatch` 里读
   contextvar 拿到空值。实测 11081 条 `api_logs` 的 `trace_id` 全 NULL，而**代码
   看起来完全正常**（零报错）。修法：审计中间件主路径读 `request.state`。
2. **迁移 revision id 重名**：初稿用 `e1f2a3b4c5d6`，与既有 `hot_topics` 迁移撞车
   ⇒ alembic 报 `Cycle is detected in revisions`。改用 `f1a2b3c4d5e6`。
3. **`AUDITED_WRITE_PREFIXES` 里 `/api/settings/` 带尾斜杠** ⇒ `GET /api/settings`
   （列表端点，不带斜杠）从来没被记过。已补齐并加 `/api/accounts` 等前缀。

另：守卫首次把**注释里的类名**当注册点（`find("TraceMiddleware")` 命中注释），
说明"按名字找符号"对注释敏感 —— 锚点必须落在**调用形态**上。
