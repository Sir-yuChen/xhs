> 本文是 `docs/README.md` 第二节的可执行版本：把「五阶段」落成可操作的流程、门禁与模板。
>
> **适用范围**：本项目所有开发活动，含本次二开与后续任何迭代。
>
> **2026-10-04 修订（v1.1）**：**阶段四由「五项必须执行」扩为「六项」** —— 新增第 6 项
> 「**开发完毕后生成/更新业务链路验收文档**」（用户口径：「业务角度以链路对功能点进行测试验收」）。

## 1. 一条铁律

> **代码变更必须由文档变更发起。** 没有设计文档的功能不写；写了代码但设计文档没跟上，视为未完成。

这条铁律是整套体系的地基。违反它的直接后果是：文档与实现漂移 → 下一轮开发无法据此施工 → 文档先行失效。

**唯一的例外**：修复生产事故（线上不可用）时可以先改代码，但必须在 **24 小时内**补回文档并登记到 `04_测试文档/04_测试跟踪与缺陷标记.md`。

## 2. 五阶段执行细则

### 阶段一 · 需求（小模型）

**输入**：业务想法 / 用户口头描述 / 上一轮迭代的遗留项。

**执行步骤**：

1. **先建目录**。任何需求在写描述之前，先把项目/模块目录骨架落地——目录结构本身就是最稳定的需求表达。
2. **写「10 句话需求」**。严格约束：用不超过 10 句话覆盖四要素：
   - 开发者在项目中的角色
   - 项目名称
   - 项目主要功能
   - 项目主要用户有哪些
3. **显式列出「范围外」**。写下这次明确不做的事，防止范围蔓延。
4. **🧭 先画逻辑导图**（**2026-10-16 用户口径新增**）—— **需求级**，四段：
   - **牵动哪些模块**（前端页 / 后端服务 / 表 / 外部平台）
   - **谁调谁**（调用链）
   - **哪一步会失败、失败会怎样**（**这段最值钱** —— 设计阶段才发现「原来这步会失败」= 返工起点）
   - **明确不碰的**（与「范围外」呼应）
   ⚠️ **不写字段** —— 字段是设计阶段「总②」的事，写在这儿 = 提前重复。
   ⚠️ **用 Markdown 文本图**（本项目不引入 mermaid：无渲染依赖）。
5. 落到 `01_需求文档/0X_需求规格_XXX.md`。

**需求文档骨架（含逻辑导图，复制即用）**：

```markdown
# 0X · <需求名>

## 一、需求（10 句话）
（≤10 句，覆盖四要素：背景 / 用户 / 想解决什么 / 成功长什么样）

## 二、范围外
- 不做 …
- 不做 …

## 三、🧭 逻辑导图（需求级，**不写字段**）

### 3.1 牵动哪些模块
| 层 | 会动到 |
|---|---|
| 前端 |  |
| 后端 |  |
| 表 |  |
| 外部平台 |  |

### 3.2 调用链
\`\`\`text
用户动作 → 前端 → 端点 → 服务层 → 平台 → 落库 → 回显
\`\`\`

### 3.3 哪一步会失败、失败会怎样  ⭐ **这段最值钱**
| # | 失败点 | 会怎样 | 谁负责报错 |
|---|---|---|---|
| 1 |  |  |  |

### 3.4 明确不碰的
- （与「范围外」呼应）
```

**为什么要有导图**：需求写成散文，**牵动面与失败点埋在字缝里**。
导图逼你在**动手之前**把「会碰到什么、会怎么坏」摊开 ——
这正是商品发布返工 4 次的那类问题（**设计前不知道会动 `skuData[].deliveryTime`**）。

**为什么要求小模型**：需求文档的读者不是人，是下一步执行施工的小模型。信息密度越高、术语越多、上下文越长，小模型的执行偏差越大。**需求文档写不长是优点，不是缺陷。**

**模板**：

```markdown
# XXX 需求规格

## 一句话
<一句话说清这是什么>

## 10 句话需求
1. 你的角色：<开发者是谁>
2. 项目名称：<...>
...
10. <...>

## 主要用户
| 用户 | 是谁 | 核心诉求 |

## 范围外
- <明确不做的事>
```

**放行条件（Gate 1）**：

- [ ] 10 句话内四要素齐全
- [ ] 「范围外」非空
- [ ] 通读一遍无歧义，任一术语在本文内有定义或指向外部权威定义

#### §2.0 · 功能设计文档的**「总—分—总」必备结构**（2026-10-15/16 用户口径）

用户口径：「详细的设计文档要包含**业务逻辑**，也要包含**接口设计逻辑**，以及**前后端的数据交互逻辑**，
以达到执行实现代码时避免重复推翻修改」。

**为什么必须分三层**（商品发布实测）：该链路 **9 次提交、13,201 行**、同一判据改 4 次 ——
根因是文档里**记录的是「改了什么」（§9 落地记录 / §22 第 N 批），不是「该是什么」**；
没有稳定规格锚点 ⇒ 每次都以「最新一批改动」为准 ⇒ 下一批又推翻。

⇒ **每份功能设计文档，这三节必须齐**（缺哪节就是将来返工的地方）：

**「总—分—总」四段**（用户 2026-10-16 口径：「**总**是需求的总体设计逻辑，详细化；**分**是前后端
**分析设计具体的实现逻辑、交互使用的工具、底层数据结构、组件**等，**分开设计前后端**；
**总**是将前后端**关联**起来，实现整个需求完整化」）：

| # | 段 | 必须写清 | 商品发布里踩的坑（都在这一段） |
|---|---|---|---|
| 1 | **总① 需求总体设计** | 目标与边界 / **端到端一张图** / 关键设计决策（为什么这么选）/ 涉及范围速览 | 没有总① ⇒ 前后端各自设计时**对不齐目标** |
| 2 | **分 · 前端设计** | 页面组件 / **底层数据结构（逐字段形态）** / 实现逻辑（判据式）/ **用了什么工具组件** / **交互与时序** / 状态来源 | `useCallback` 漏依赖 ⇒ 改图后提交用旧快照；`Popconfirm` 压到相邻按钮 ⇒ 两次提交连发 |
| 3 | **分 · 后端设计** | 端点 / 请求响应契约（含**单位**与**白名单**）/ **表与模型** / 实现逻辑（判据式）/ 状态机 + 不变量 / 工具依赖 / 错误码 / **外部契约抓包快照** | `extra="forbid"` 漏字段 ⇒ **静默丢弃**；`price` 单位是**分** |
| 4 | **总② 前后端关联** ⭐⭐ | **逐字段「谁传 → 谁读 → 什么形态」** + **端到端链路（7 步，每步标失败谁报错）** + 跨层竞态 + 失败路径表现 | `spec` 形态不一致全被滤掉；`delivery_label` 前端传了后端没读 |

⚠️ **为什么必须「总分」而不能只有「分」**：设计 24 涨到 **25 个大节**、绝大多数是「第 N 批」
—— **两层混着写 ⇒ 改一处看不懂另一处**；而「总②」是唯一能收口「单测全绿但链路错」的地方
（**两层各自自洽，接缝没人管**）。

**⚠️ 「总②」是最高发区**：本项目绝大多数「单测全绿但链路错」都在这一段 ——
**两层各自自洽，接缝没人管**。

**写法要求**：「总②」用**表格**，一行一个字段，三列（谁传 / 谁读 / 形态）。
```text
| 字段 | 前端产出（形态） | 后端读点（形态） | 不一致会怎样 |
|---|---|---|---|
| spec | `颜色分类:【中古风】三斗柜`（带前缀） | `visible` 比对的 `c.spec`（带前缀） | 缺前缀 ⇒ 全被滤掉、价格库存一行不落 |
```

**放行判据**：四段齐（总①/前端/后端/总②）+ **总②** 每个字段都能回答「不一致会怎样」。
答不上来 ⇒ **还没设计完**，别进编码。

**📋 模板**：`docs/00_管理规范/02_功能设计文档模板.md` —— **复制它写新设计文档**；
末尾带一行 `<!-- gate2: 总-分-总 … -->` 声明，`.hermes/scripts/check_gate2.py` 会检查它在不在
（只检查「声明在不在」，**不去猜内容** —— 关键词猜内容实测误报严重，2026-10-15 已否决该做法）。

#### §2.1 · 外部平台写接口：**抓包必须发生在设计阶段**

**触发条件**：本功能会向**外部平台**发**写**请求（发布 / 上架 / 提交 / 保存草稿…）或依赖其**返回契约**。

**怎么做**：CDP 挂**平台自己的页面**，人工把该动作**做一遍**，抓下真实请求体，存成契约快照：

```
.hermes/tmp/evidence_<功能>/<动作>.json     ← 逐字段对照用
```

**为什么必须在设计阶段**（2026-10-15 商品发布实测，这条最贵）：

| 顺序 | 代价 |
|---|---|
| ❌ 先写代码 → 发布 → 用户报错 → 才抓包 | 每轮约**半天**；商品发布这一条链路**重复了 4 次** |
| ✅ 设计阶段先抓包 → 按真实契约写码 | 抓包本身约 **10 分钟** |

⚠️ **抓包会发现「你猜的那个字段不是载体」** —— 商品发布的实证：

| 猜的 | 真的 |
|---|---|
| 顶层 `deliveryMode` 是发货模式 | 恒为 `1`（**不是**载体）；真载体是 `skuData[].deliveryTime` |
| 货号是 `attributes[]` 里的一项 | **顶层 `articleNo`** |
| `variantIds` 可空 | 空 ⇒ 平台 `mainSpecEnable=0` ⇒ 规格图开关关闭 |

⇒ **这三条读代码/读文档永远发现不了，只有抓包能。**

**⚠️ 抓包快照会过期**：平台契约自己会变（商品发布的图片条目格式在 3 周内被认知修正 **3 次**：
相对路径 → `spaceImage` → `uploadImage`+短 fileId）。⇒ 快照**存进仓库**并**记日期**，
下次改这条链路时**先对一遍快照是否还成立**。

---

#### §2.2 · 业务判据必须写成「判据式」，不是「举例式」

**判据**：这条规则**换一批数据还成立吗？**

| 写法 | 例子 | 换数据后 |
|---|---|---|
| ❌ **举例式** | 「匹配用**最后一段**完整文案」 | 换一批命名不同的数据 ⇒ 立刻失效 |
| ✅ **判据式** | 「匹配判据 = **图片名包含 SKU 名**；消歧 = 全局最长优先 + 一图一用」 | 任何数据都成立 |

**为什么这是硬要求**：同一个判据（SKU 匹配）**改了 4 次**，每次文档里都写着「定论」——
根因就是**前三版都是举例式**，被下一批数据推翻。

⇒ **举例式规格注定被下一批数据推翻。** 写设计时先问「这判据能穷举所有情况吗」，
不能就继续收敛，**别急着写「定论」**。

### 阶段三 · 开发（小模型）

**输入**：Gate 2 通过的设计文档。

**核心约束**：

> **开发的功能以详细设计文档为准则。**（图片原文）
>
> 与之配套的是「尽量不改 bug」——这不是说 bug 不修，而是说：**如果按设计写出来的代码有 bug，说明设计有问题，应该先改设计文档再改代码**，而不是就地打补丁让代码和设计文档分家。

**执行步骤**：

0. ⭐ **改动前置评估**（2026-10-15 用户口径 —— **任何改代码 / 改文档之前先做**）：

   > 用户口径：「任何需要改代码修改文档等操作时，均需要先评估修改影响范围，需要修改什么，
   > 修改后关联哪些逻辑内容需要同步修改，最后修改后检查测试等验证工作」。

   **三问**（答不上来就别动手）：

   | # | 问什么 | 判据 |
   |---|---|---|
   | 1 | **要改什么？**（精确到 `文件:行号` / 文档 §) | 列不出具体位置 ⇒ 你还没搞清现状，先读代码 |
   | 2 | **改完连带什么？**（谁读它 / 谁写它 / 谁与它同源）| **用符号反查**，不靠回忆（见下「连带排查四把尺子」）|
   | 3 | **怎么验？**（跑哪条命令判定合格）| 答不上来 ⇒ **这次改动没判据，等于没做完** |

   **⚠️ 连带排查四把尺子**（本项目实测有效的四种反查方式）：

   | 改的是什么 | 怎么找连带 | 本项目实例（真踩过）|
   |---|---|---|
   | **后端符号**（函数 / 常量 / 模型字段）| `search_files` 全仓反查调用点 | 删 `note_category` ⇒ **后端 9 文件 + 测试 42 处** |
   | **数据模型**（表 / 键 / 列）| 反查「读了这张表的全部读点」 | `note_goods` **改键 ⇒ 牵动 6 处**（读取端 / 筛选 / 计数 / item-notes / 发布 / 生成）|
   | **前端形态**（字段形状 / 类型）| **反查接缝两侧**（谁产出 / 谁消费）| `passedSkuSpecs` 改形态 ⇒ `visible` 过滤**全失效**（两层各自自洽）|
   | **文档数字** | 跑 `verify_doc_counts.py` | 改数字只改一处 ⇒ 校验脚本 FAIL |

   **⚠️ 常见漏项清单**（这五类最容易连带却没被想到）：
   1. **守卫/测试里写死的旧形态**（改契约必须 grep 断言里的类名 / 字段名）
   2. **变异脚本的锚点**（被改的函数一删，锚点就失效 ⇒ 变异假绿）

   4. **文档里的数字**（AGENTS §5 + `docs/README.md` + 设计文档头部 ⇒ 三校验）
   5. **注册表 / 白名单 / 枚举**（`QUEUE_REGISTRY` / `TASK_TYPE_LABELS` / `NOTE_TYPE_*` 等硬编码清单）

   **🔧 辅助工具**：`.hermes/scripts/impact_check.py` —— 第 2 问（连带）的机械部分交给它：

   ```bash
   python .hermes/scripts/impact_check.py <符号名>          # 反查调用点（源码/测试/文档分组）

   ```

   （实测样例：`QUEUE_REGISTRY` ⇒ 6 源码文件，**连 alembic 迁移里都引用了它** —— 人极易漏）。

   ⚠️ **改「流程/规范文档」本身时，连带对象与改代码不同**（2026-10-15 助手实例）：
   同层其它 Gate（**加条目前先核对是否已被别处覆盖** —— 否则重复）/

   `AGENTS.md` §6 索引。细则见速查表「改流程文档的专属连带清单」。

   ⇒ **把三问的答案写进任务台账**（一行不为过），再动手。

1. 从 `03_开发文档/03_二开任务分解与里程碑.md` 取任务，把状态改为 `进行中`。

> | **验证性质** | **代码级**：pytest / tsc / 变异（判断「实现对不对」）| **业务级**：链路端到端（判断「功能能不能用」）|

### 阶段四 · 测试（大模型）

**输入**：Gate 3 通过的实现。

**六项必须执行**（图片原文五项 + 本项目第 6 项）：

| # | 要求 | 产出文档 |
|---|---|---|
| 1 | 执行 codegraph 型代码图谱 | `04_测试文档/02_代码图谱_codegraph.md`（**一次性快照**，见下注） |
| 2 | 生成系统总体测试进度文档、各功能点测试用例、各功能点测试跟踪文档 | `04/01` + `04/03` + `04/04` |

> **第 1 / 4 / 5 项「每轮必做」降级为「按触发更新」**（2026-10-06 工作流精简，理由见
> `05_项目沉淀/04_开发工作流冗余分析与精简方案.md`）：
> 这三项产出是**一次性静态快照**——它们描述「代码图谱长什么样」「mock 有哪些」「开关有没有生效」，
> 一旦做完、代码结构没有对应变化时，重做只是重复劳动；而本项目实测（mock 已清零、端点 274、
> 页面 34）证明这三份文档长期停在旧数字，却仍挂在进度表「🟢 已完成」占位，形成**僵尸快照**。
> 触发条件（满足才更新，不满足跳过）：
> - 第 1 项 codegraph：新增/删除**模块或分层**（不是新增端点/字段那种增删）；
> - 第 4 项 mock 清单：新增/移除** mock 标记或端点**（当前 mock 已清零，无新 mock 则永久跳过）；
> - 第 5 项开关核查：新增/改动**运行时配置项或管理端开关**。
> 每轮真正必做的是**第 2 / 3 / 6 项**（用例库、缺陷标记、验收链路）——它们才是随代码逐轮演进、必须当场维护的活文档。

**第 6 项的执行标准**（2026-10-04 新增，用户口径「业务角度以链路对功能点进行测试验收」）：

| 要求 | 说明 |
|---|---|
| **单元是链路，不是功能点** | 功能点会退化成「按钮清单」；链路才能回答「这条业务跑不跑得通」 |
| **一条链路 = 一串前端入口按真实业务顺序** | 例：同步商品 → 列表核对 → 筛选 → 分组 → 导出。**不许只写后端契约**，入口必须落到「哪个页面、点哪个按钮」 |
| **判据放末端** | 末端业务结果对 ⇒ 链路通；末端错 ⇒ 一眼看出**断在第几步** |
| **每条链路四段齐全** | ①入口链（步序表）②末端业务结果 ③通过判据 ④断链点（点名它防的是哪个已修缺陷） |
| **新增入口必进链路** | 新需求的前端入口必须**新开一条链路**或**接入既有链路**，不许只在测试文件里被覆盖 |

> **为什么它是独立一项、而不是并进第 2 项**：第 2 项的用例是**按功能点**编号（`TC-*`），
> 适合查「有没有这个功能」；但它**不回答跨页面的业务闭环**。本项目最贵的缺陷（DEF-044/067/069/048）
> 全是**跨模块 + 静默**类 —— 恰恰只有把链路端到端串起来走一遍才显形（判据见 `04_测试文档/01` §13.1）。

**缺陷标记规范**（第 3 条的执行标准）：

| 标记 | 含义 | 打标时机 |
|---|---|---|
| `[OPEN]` | 已发现，未修复 | 测出即打 |
| `[FIXING]` | 修复中 | 开始修时改 |
| `[FIXED]` | 代码已改，**未回归** | 改完即改，但必须填「拟修复版本/提交」 |
| `[VERIFIED]` | 回归通过，可关闭 | 回归通过后 |
| `[WONTFIX]` | 确认不修 | 必须写明理由与决策人 |
| `[DUP]` | 与已有条目重复 | 指向主条目编号 |

> **关键**：`[FIXED]` 与 `[VERIFIED]` 必须分开。只标 `[FIXED]` 的条目不算关闭，审计时按未关闭统计。

**放行条件（Gate 4）**：

- [ ] 活文档产出齐全（用例库 / 缺陷标记 / 业务链路验收，见阶段四「六项」降级注）
- [ ] 前后端接线覆盖度**若本轮涉及**则有明确数字；未达 100% 的部分逐条列出原因
- [ ] 所有开关**若本轮涉及**则有「是否生效 / 是否落库」的结论
- [ ] 全部缺陷标记处于 `[VERIFIED]` / `[WONTFIX]` / `[DUP]` 之一
- [ ] **业务链路验收文档的四段已补齐**：本次每个受影响链路都有完整四段
      （入口链 / 末端业务结果 / 通过判据 / 断链点）——**这是真走过一遍的产物**，
      不是把 Gate 3 登记的「挂上号」抄一遍
      （新增入口「挂上号」已在 Gate 3 判过，此处不重复判）

> ⚠️ Gate 4 的「接线覆盖度」「开关核查」两项已随阶段四第 4 / 5 项**降级为按触发更新**——
> 本轮没动 mock / 没动开关，就**不需要**重复产出一份和上一轮一模一样的快照。

### 阶段五 · 回流沉淀

阶段四的发现按性质分流，**不允许只改代码**：

```
测试发现
   ├─ 设计缺失/错误  → 回阶段二：修订设计文档，追加 ADR 条目
   ├─ 实现不符设计    → 回阶段三：修代码，登记偏差
   ├─ 需求理解偏差    → 回阶段一：修订需求文档，级联更新设计
   └─ 环境/工具问题   → 记入 05_项目沉淀，不阻塞流程
```

**沉淀的落点检查**（✅ 该记哪就记哪，别串 —— 记错地方等于没记）：

| 内容 | 落到哪 | 判据 |
|---|---|---|
| **不变量 + 判据词**（禁 / 必须 / 唯一） | `AGENTS.md` §3 + 设计文档 | **确定性出现**，不能靠检索碰运气 |
| **怎么实现的**（链路 / 队列 / 话题细节） | `docs/02_设计文档/` | 项目内按需读，人也能读 |
| **踩过的坑 / 调试过程 / 一次性结论** | **`hindsight_retain`** | 检索到才有用，检索不到不致命 |
| **可复用操作流程** | **`.hermes/skills/`** | 开工时按需加载 |
| **改了什么 / 数字口径** | `AGENTS.md` §5 + `docs/README.md` | **跑三校验脚本**（改数字不回写 = 未完成）|

⚠️ **反面例子（本项目真实发生过）**：把「过程教训」写进设计文档 ⇒
设计文档越来越像日志（设计 24 有 **25 个大节**，绝大多数是「第 N 批」），
**规格锚点被淹没** ⇒ 下一批改动推翻上一批。⇒ **过程教训进 Hindsight，不占设计文档。**

## 3. 变更管理

### 3.1 需求变更

1. 在需求文档中**追加**变更条目（不删除原文），标注版本与日期。
2. 评估对设计文档的影响范围，逐一列出需要更新的设计文档章节。
3. 更新受影响的设计文档，标注「因需求 vX 变更」。
4. 更新任务台账。

### 3.2 设计变更（开发中被动发现）

使用 **ADR** 记录：`05_项目沉淀/01_架构决策记录_ADR.md` 追加一条，格式：

```markdown
## ADR-00X · <决策标题>
- 日期：
- 状态：已采纳 / 已废弃
- 背景：<为什么需要这个决策>
- 备选方案：A / B / C
- 决策：<选了什么>
- 理由：<为什么>
- 代价：<放弃了什么>
```

**判断标准**：一个变更如果需要「换技术栈、换数据模型、换链路、改架构硬约定、或影响两个以上模块」，就必须写 ADR。

## 5. 反面清单（这些做法已被本项目验证会出问题）

| 做法 | 曾经造成的后果 |
|---|---|
| 先写代码，事后补分析报告 | v1 产出 25 份文档，结论互相取代，需要再写一份「总纲」来收口 |
| 用一个巨大文件装下所有内容 | 单文件近千行，无法按访问端分工，改一处要通读全文 |
| 结论不标证据 | 后续无法判断某条结论是否还成立，只能重新全量核代码 |
| 归档用删除 | 决策理由丢失，同样的问题被重复评估（v1 的无头浏览器方案评估了 4 份文档） |
| 缺陷只标「已修复」 | 无法区分「改完了」和「验证过了」，回归遗漏 |
| 开发完只跑自动化测试，不生成业务链路验收文档 | 用户验收时只能「按按钮清单逐个点」，查不出**跨页面闭环断在哪**；而本项目最贵的缺陷（静默/跨模块类）正是只在链路端到端时才显形 |
| **外部平台写接口不在设计阶段抓包**，等发布后才发现契约不对 | 商品发布链路因此返工 **4 次**（发货模式载体 / 规格图开关 / 货号位置 / 图片格式），每轮约半天；而抓包本身只要 10 分钟 |
| **业务判据写成「举例式」**（描述某批数据的长相，而非规则） | 同一个判据（SKU 匹配）改了 **4 次**，每版都标「定论」——举例式注定被下一批数据推翻 |
| **改动不进 git**（长期留工作区） | ① 出事不能 `git checkout` 恢复；② **「修好了」与「跑的是修好的那份」是两件事** —— 实测过「修完没提交 ⇒ 重跑踩同一个坑」 |
