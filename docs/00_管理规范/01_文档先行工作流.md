# 文档先行工作流

> 本文是 `docs/README.md` 第二节的可执行版本：把「五阶段」落成可操作的流程、门禁与模板。
>
> **适用范围**：本项目所有开发活动，含本次二开与后续任何迭代。

---

## 1. 一条铁律

> **代码变更必须由文档变更发起。** 没有设计文档的功能不写；写了代码但设计文档没跟上，视为未完成。

这条铁律是整套体系的地基。违反它的直接后果是：文档与实现漂移 → 下一轮开发无法据此施工 → 文档先行失效。

**唯一的例外**：修复生产事故（线上不可用）时可以先改代码，但必须在 **24 小时内**补回文档并登记到 `04_测试文档/04_测试跟踪与缺陷标记.md`。

---

## 2. 五阶段执行细则

### 阶段一 · 需求（小模型）

**输入**：业务想法 / 用户口头描述 / 上一轮迭代的遗留项。

**执行步骤**：

1. **先建目录**。任何需求在写描述之前，先把项目/模块目录骨架落地——目录结构本身就是最稳定的需求表达。
2. **写「10 句话需求」**。严格约束：用不超过 10 句话覆盖四要素：
   - 开发者在项目中的角色
   - 项目名称
   - 项目主要功能
   - 项目主要用户有哪些
3. **显式列出「范围外」**。写下这次明确不做的事，防止范围蔓延。
4. 落到 `01_需求文档/0X_需求规格_XXX.md`。

**为什么要求小模型**：需求文档的读者不是人，是下一步执行施工的小模型。信息密度越高、术语越多、上下文越长，小模型的执行偏差越大。**需求文档写不长是优点，不是缺陷。**

**模板**：

```markdown
# XXX 需求规格

## 一句话
<一句话说清这是什么>

## 10 句话需求
1. 你的角色：<开发者是谁>
2. 项目名称：<...>
...
10. <...>

## 主要用户
| 用户 | 是谁 | 核心诉求 |

## 范围外
- <明确不做的事>
```

**放行条件（Gate 1）**：

- [ ] 10 句话内四要素齐全
- [ ] 「范围外」非空
- [ ] 通读一遍无歧义，任一术语在本文内有定义或指向外部权威定义

---

### 阶段二 · 设计（大模型）

**输入**：Gate 1 通过的的需求文档。

**产出物**：`02_设计文档/` 下的对应文档。

**七项必查清单**（写完后逐项打勾，缺一不可）：

| # | 必查项 | 落到哪份文档 |
|---|---|---|
| 1 | 依据需求文档逐条给出设计 | 全部设计文档，末尾附「需求 → 设计」对照表 |
| 2 | 技术栈：开发语言、系统架构、数据库选型、是否有移动端、所有第三方技术 | `01_技术栈与选型.md` |
| 3 | 用户量（并发设计） | `02_系统架构设计.md` 容量章节 |
| 4 | 开发环境与生产环境如何隔离 | `02_系统架构设计.md` 环境隔离章节 |
| 5 | 用 AI 发散思维，功能是否可完善（加分项） | `00_设计总览.md` 的「可完善点」章节 |
| 6 | 系统中的开关、配置要在后台设计系统管理功能 | `10_系统管理功能设计.md` |
| 7 | 系统安全性设计 | `11_安全设计.md` |

**拆分规则**（图片要求：「如果文件太大了，把架构设计与功能设计拆开，把功能设计以访问端为基准去拆开」）：

```
按「关注点」拆：架构  ≠  功能
按「访问端」拆功能：
   Web 运营端（浏览器）      → 04
   HTTP API（第三方/前端调用） → 05
   采集链路（数据入口）        → 06
   发布链路（数据出口）        → 07
   调度侧（无人值守）          → 08
   SDK 侧（底层能力）          → 09
```

**放行条件（Gate 2）**：

- [ ] 七项必查清单全部覆盖
- [ ] 每个功能点都能追到具体实现位置（`文件:行号`）或明确标记为「二开新增」
- [ ] 需求文档中的每一条需求，都能在设计文档中找到对应章节
- [ ] 涉及开关/配置的，已登记到 `10_系统管理功能设计.md` 的开关台账

---

### 阶段三 · 开发（小模型）

**输入**：Gate 2 通过的设计文档。

**核心约束**：

> **开发的功能以详细设计文档为准则。**（图片原文）
>
> 与之配套的是「尽量不改 bug」——这不是说 bug 不修，而是说：**如果按设计写出来的代码有 bug，说明设计有问题，应该先改设计文档再改代码**，而不是就地打补丁让代码和设计文档分家。

**执行步骤**：

1. 从 `03_开发文档/03_二开任务分解与里程碑.md` 取任务，把状态改为 `进行中`。
2. 打开该任务对应的设计文档章节，**严格按文档实现**。
3. 实现中若发现设计文档有误/不完备：
   - **停止编码** → 回阶段二修订设计文档 → 记录到 ADR 或设计文档修订记录 → 再继续编码。
4. 完成后更新任务台账，状态改为 `已完成（待测）`，并记录实际改动文件清单。

**放行条件（Gate 3）**：

- [ ] 任务台账中该任务状态为「已完成（待测）」
- [ ] 实现与设计文档逐条对齐，**任何偏差都在台账中登记了原因**
- [ ] 新增的 API / 表 / 开关，已回写到对应的设计文档

---

### 阶段四 · 测试（大模型）

**输入**：Gate 3 通过的实现。

**五项必须执行**（图片原文逐条落地）：

| # | 要求 | 产出文档 |
|---|---|---|
| 1 | 执行 codegraph 型代码图谱 | `04_测试文档/02_代码图谱_codegraph.md` |
| 2 | 生成系统总体测试进度文档、各功能点测试用例、各功能点测试跟踪文档 | `04/01` + `04/03` + `04/04` |
| 3 | 每次测出 bug 与修改完 bug 后，从文档上打好标记，以便后续审计 | `04/04` 的缺陷标记表 |
| 4 | 查系统里所有 mock 标记，核对前后端接线覆盖度（100%） | `04/05_Mock清单与接线覆盖度.md` |
| 5 | 查管理端开关在 UI 上是否生效、是否落库（数据库 / git 库） | `04/06_系统开关与配置核查表.md` |

**缺陷标记规范**（第 3 条的执行标准）：

| 标记 | 含义 | 打标时机 |
|---|---|---|
| `[OPEN]` | 已发现，未修复 | 测出即打 |
| `[FIXING]` | 修复中 | 开始修时改 |
| `[FIXED]` | 代码已改，**未回归** | 改完即改，但必须填「拟修复版本/提交」 |
| `[VERIFIED]` | 回归通过，可关闭 | 回归通过后 |
| `[WONTFIX]` | 确认不修 | 必须写明理由与决策人 |
| `[DUP]` | 与已有条目重复 | 指向主条目编号 |

> **关键**：`[FIXED]` 与 `[VERIFIED]` 必须分开。只标 `[FIXED]` 的条目不算关闭，审计时按未关闭统计。

**放行条件（Gate 4）**：

- [ ] 五项产出齐全
- [ ] 前后端接线覆盖度有明确数字；未达 100% 的部分逐条列出原因
- [ ] 所有开关有「是否生效 / 是否落库」的结论
- [ ] 全部缺陷标记处于 `[VERIFIED]` / `[WONTFIX]` / `[DUP]` 之一

---

### 阶段五 · 回流沉淀

阶段四的发现按性质分流，**不允许只改代码**：

```
测试发现
   ├─ 设计缺失/错误  → 回阶段二：修订设计文档，追加 ADR 条目
   ├─ 实现不符设计    → 回阶段三：修代码，登记偏差
   ├─ 需求理解偏差    → 回阶段一：修订需求文档，级联更新设计
   └─ 环境/工具问题   → 记入 05_项目沉淀，不阻塞流程
```

## 3. 变更管理

### 3.1 需求变更

1. 在需求文档中**追加**变更条目（不删除原文），标注版本与日期。
2. 评估对设计文档的影响范围，逐一列出需要更新的设计文档章节。
3. 更新受影响的设计文档，标注「因需求 vX 变更」。
4. 更新任务台账。

### 3.2 设计变更（开发中被动发现）

使用 **ADR** 记录：`05_项目沉淀/01_架构决策记录_ADR.md` 追加一条，格式：

```markdown
## ADR-00X · <决策标题>
- 日期：
- 状态：已采纳 / 已废弃
- 背景：<为什么需要这个决策>
- 备选方案：A / B / C
- 决策：<选了什么>
- 理由：<为什么>
- 代价：<放弃了什么>
```

**判断标准**：一个变更如果需要「换技术栈、换数据模型、换链路、改架构硬约定、或影响两个以上模块」，就必须写 ADR。

## 4. 每阶段的责任与产物总表

| 阶段 | 模型规格 | 产物 | 门禁 | 禁止事项 |
|---|---|---|---|---|
| 一 需求 | 小模型 | `01_需求文档/` | Gate 1 | 需求文档写成技术方案 |
| 二 设计 | 大模型 | `02_设计文档/` | Gate 2 | 设计文档含代码实现细节（可含接口签名） |
| 三 开发 | 小模型 | 代码 + 台账 | Gate 3 | 设计文档没写的功能不写 |
| 四 测试 | 大模型 | `04_测试文档/` | Gate 4 | 只标 `[FIXED]` 就认为关闭 |
| 五 沉淀 | — | `05_项目沉淀/` | — | 只改代码不回写文档 |

## 5. 反面清单（这些做法已被本项目验证会出问题）

| 做法 | 曾经造成的后果 |
|---|---|
| 先写代码，事后补分析报告 | v1 产出 25 份文档，结论互相取代，需要再写一份「总纲」来收口 |
| 用一个巨大文件装下所有内容 | 单文件近千行，无法按访问端分工，改一处要通读全文 |
| 结论不标证据 | 后续无法判断某条结论是否还成立，只能重新全量核代码 |
| 归档用删除 | 决策理由丢失，同样的问题被重复评估（v1 的无头浏览器方案评估了 4 份文档） |
| 缺陷只标「已修复」 | 无法区分「改完了」和「验证过了」，回归遗漏 |
