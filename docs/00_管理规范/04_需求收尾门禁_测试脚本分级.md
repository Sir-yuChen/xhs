# 需求收尾门禁：测试脚本分级与清理

> 2026-10-26 用户口径立规，**强制**。违反 = 需求未完成。
>
> 用户原话：
> 「每个需求做完必须对当前需求产生的测试脚本做分级，一次性测试脚本和没有保留价值的
> 测试脚本需随着验收通过彻底移除无需保留堆积，达到大量的测试无用的测试脚本产生」

## 1. 规则

**每个需求验收通过后，必须对「本需求新增/修改的测试脚本」逐个分级，并执行对应动作。**
分级动作**和验收是同一步** —— 不分级 = 该需求未收尾。

## 2. 四个等级与处置

| 等级 | 判定 | 处置 |
|---|---|---|
| **L1 全链路** | 从入口（HTTP/UI 动作）→ 服务层 → 落库 → 可观测结果，一条用例走完 | **保留**（每功能点最多 1 个） |
| **L2 架构不变量** | 钉「静默且运行时炸」的错误，行为断言测不到，且 docstring 写明理由 | **保留**（可进变异验证） |
| **L3 一次性验收** | 验证某次改动是否生效（抓包核对、格式转换、迁移一次）+ 源码/文案/布局断言 | **验收通过后立即删** |
| **L4 无保留价值** | 断言恒真（被测代码已删）、重复测点、为凑覆盖率而写 | **立即删** |

## 3. 机械判据

```bash
python .hermes/scripts/grade_new_tests.py            # 逐文件出分级建议
python .hermes/scripts/grade_new_tests.py --enforce  # 有 L3/L4 未清理则 exit 1（进 CI / 收尾必跑）
```

判定依据（按顺序取第一个命中）：

| 特征 | 判为 |
|---|---|
| `client.get/post/put/patch/delete` 或 `db.query/execute/add` **= 0** 且 `read_text(` ≥ 2 | **L3**（纯源码断言） |
| 断言恒真：`assert X not in <源码>` 而 X 在实现侧零命中 | **L4**（测已删代码） |
| 与另一文件测同一端点 + 相同断言组合 | **L4**（重复测点） |
| 有业务调用 + 完整链路 | **L1** |
| `docstring` 含「为什么行为断言测不到」或「架构不变量」 | **L2** |

## 4. 收尾检查清单（每个需求抄一遍）

- [ ] 本需求新增/修改的测试文件已跑 `grade_new_tests.py`
- [ ] L3 全部删除（或写清为什么留）
- [ ] L4 全部删除
- [ ] L1 合并到「每功能点 1 个」
- [ ] L2 在 docstring 写明「为什么行为断言测不到」
- [ ] 用例总数**没有净增长**（或写明为什么必须增长）

## 5. 为什么必须有这门禁（实测账）

2026-10-26 盘查本项目：**3334 条用例里 32% 是纯源码断言（1073 条）**，
而真正走通业务链路的只有 **412 条（12%）**。

| 文件 | 用例 | 业务调用 | 性质 |
|---|---|---|---|
| `test_page_optimizations.py` | **417** | **0** | L3，全部删除 |
| `test_gate2_guard_wiring.py` | 51 | 0 | L3，删除 |
| `test_menu_integration.py` | 34 | 0 | L3，删除 |
| `test_packaging_version_history.py` | 34 | 0 | L3，删除 |

这些文件不是「一次写坏」，而是**每个需求都往里加几条**、从不清理，
三年下来堆成 417 条。**没有收尾门禁 ⇒ 必然堆积。**
