## 0. 全景（**两条通道** + 五阶段四门禁）

```
                    ┌─ 新需求 / 新功能 / 跨模块 ──▶ 【通道 A · 五阶段】
   拿到一件事 ──────┤
                    └─ 优化 / 修 bug / 改文案 / 改文档 ──▶ 【通道 B · 改动红线】四步
                              │
                        拿不准 ⇒ 按五阶段（宁重勿漏）
```

**通道 A · 五阶段**（本页 §①–§⑤）：

```
① 需求 ──Gate1──▶ ② 设计 ──Gate2──▶ ③ 开发 ──Gate3──▶ ④ 测试 ──Gate4──▶ ⑤ 沉淀
   10句话          总分总四段+抓包        改前评估+代码级验证    链路四段+业务级验收  回写+记忆
```

**通道 B · 改动红线**（**四步强制**，细则见 `03_改动红线.md`）：

```
① 列清单（改哪些文件/§）② 反查连带（impact_check.py --changed）
③ 定判据（跑哪条命令算合格）④ 改完验证 + 留痕
```

⚠️ **触发规则由脚本自动判定**（按**改动对象类型**，**不按规模** —— 实测 1 文件 `+0/-0`
也可能危险、72 文件也可能危险）。最常用的一条：

```bash
python .hermes/scripts/impact_check.py --changed
```

它会打印「**本次必须额外做**」（公共层⇒全量回归 / 守卫⇒变异 / 文档数字⇒三校验 / …）。

> ⚠️ **两条通道的例外**：**小优化但触及公共层或契约** ⇒ 走红线四步 **+ 回设计文档同步**
>（契约变了文档就过期了 —— 硬约束 1「文档先行」的触发条件）。

**贯穿全程的一条铁律**：**代码变更必须由文档变更发起**；发现设计有误 ⇒ **先改文档再改代码**（不许就地打补丁让两者分家）。

## ② 设计（Gate 2）⭐ 最容易省、最不该省

**模板**：`cp docs/00_管理规范/02_功能设计文档模板.md docs/02_设计文档/NN_功能设计_<名>.md`

**「总—分—总」四段**（§2.0，缺哪段就是将来返工的地方）：

| 层 | 写清什么 |
|---|---|
| **总① 需求总体设计** | 目标边界 + 端到端一张图 + 关键决策 + 涉及范围 |
| **分·前端** | 组件 + **数据结构（逐字段形态）** + 判据 + 工具 + 交互时序 |
| **分·后端** | 端点 + 契约（**单位/白名单**）+ 表模型 + 状态机 + 错误码 + **抓包快照** |
| **总② 前后端关联** ⭐⭐ | **逐字段「谁传→谁读→什么形态」** + **端到端 7 步** + 跨层竞态 |

**⚠️ 涉及外部平台写接口 ⇒ 第 0 步先抓包**（§2.1）：

```bash
# CDP 挂平台自己的页面，人工把动作做一遍，抓真实请求体
# 存 .hermes/tmp/evidence_<功能>/<动作>.json   ← 记日期
```
> **实证**：商品发布链路 **4 次返工**（发货模式载体 / 规格图开关 / 货号位置 / 图片格式）
> **全部**因「没在设计阶段抓包」。抓包 **10 分钟** vs 每轮返工 **半天**。

**Gate 2 判据**：

- [ ] 业务判据是**判据式**
- [ ] 外部写接口已抓包、快照**记了日期**
- [ ] 跑自检：`python .hermes/scripts/check_gate2.py` → 无 `[GATE2]` 提示

## ③ 开发（Gate 3）

### 步骤 0 · **改动前置评估**（用户 2026-10-15 口径 —— 动手之前）

**三问**（答不上来就别动手）：

| # | 问 | 工具 |
|---|---|---|
| 1 | **要改什么？**（精确到 `文件:行号` / 文档 §）| 读代码 |
| 2 | **改完连带什么？** | ⭐ `python .hermes/scripts/impact_check.py <符号名>` |
| 3 | **怎么验？**（跑哪条命令判定合格）| 见下方「验证命令速查」|

```bash
python .hermes/scripts/impact_check.py QUEUE_REGISTRY   # 反查调用点（源码/测试/文档分组）
python .hermes/scripts/impact_check.py --changed        # 按 git 未提交改动自动反查
```
> 实测：`QUEUE_REGISTRY` ⇒ 6 个源码文件，**连 `alembic/versions/*` 都引用了它** —— 人极易漏。

**五类常漏项**（反查命中就单独确认）：
① 守卫/测试里写死的旧形态 ② 变异脚本锚点（函数一删锚点失效 ⇒ 假绿）
③ 前端 `extra="forbid"` 白名单 ④ 文档数字（三校验）⑤ 注册表/白名单/枚举

**⚠️ 改流程/规范文档时的专属连带清单**（2026-10-15 助手自己踩了，故单列）：

| 连带对象 | 为什么 |
|---|---|
| **同层的其它 Gate** | 往某个 Gate 加条目时，**必须回头核对其它 Gate 是否已覆盖** —— 实测：给 Gate 3 加「登记链路」而 Gate 4 本就有「更新链路」⇒ **重复，读者以为要跑两趟** |
| **自检脚本的判据** | 改清单条数 / 改节标题 ⇒ `check_gate2.py` 的判定是否还成立？（它若硬编码条数就会失配）|
| **守卫里写死的措辞** | `test_gate2_guard_wiring.py` 断言了具体字串（如「十项」「挂上号」）⇒ 改措辞就要同步 |
| **速查表 ↔ 细则一致性** | 两处写同一件事 ⇒ 改一处必须改另一处（它们已被守卫钉住）|
| **`AGENTS.md` §6 索引** | 新文档不登记 = 没人知道它存在 |

### 编码

```bash
# 三层循环（不要每次跑全量）
python .hermes/scripts/pick_tests.py                 # 按 git 改动自动选测试文件

cd frontend && node node_modules/typescript/bin/tsc --noEmit               # 前端类型
```

### 改完验证（Gate 3）

- [ ] 按步骤 0 第 3 问答的判据**跑完并记录结果**（跑了哪条命令 + 结果）
- [ ] 有设计偏差 ⇒ 台账登记原因
- [ ] 新增 API / 表 / 开关 ⇒ **已回写设计文档**
- [ ] 新增/变更的**前端入口已在业务链路验收清单里「挂上号」**

- [ ] ⚠️ **验证的对象是实际执行的那份**（实测踩过：修好的补丁躺工作区没提交 ⇒ 重跑踩同一个坑）

## ④ 测试（Gate 4）

> **与 Gate 3 的分工**（别把同一件事做两遍）：
> - **Gate 3 = 代码级**（pytest / tsc / 变异 ⇒ 判断「实现对不对」）
> - **Gate 4 = 业务级**（链路端到端真走一遍 ⇒ 判断「功能能不能用」）
> - 链路验收：**Gate 3 只「挂上号」**，**Gate 4 才写「四段完整」**

**验证命令速查**（本项目现行）：

| 用途 | 命令 |
|---|---|
| 后端测试（只看 xml 四数，**不看退出码**）| `pytest tests/ -q -n auto --junitxml=<f>` |
| 前端类型 | `cd frontend && node node_modules/typescript/bin/tsc --noEmit` |
| 前端单测 | `cd frontend && npm test` |
| 构建（8000 吃产物 / 发版前）| `cd frontend && node node_modules/vite/bin/vite.js build` |
| 文档数字自洽 | `python .hermes/skills/xhs-doc-stats-verify/verify_doc_stats.py` |
| 文档 vs 实测 | `python .hermes/skills/xhs-doc-stats-verify/verify_doc_counts.py` |
| 验收清单自洽 | `python .hermes/skills/xhs-doc-stats-verify/verify_acceptance_links.py` |
| 设计评审自检 | `python .hermes/scripts/check_gate2.py` |
| 改动影响反查 | `python .hermes/scripts/impact_check.py <符号>` |

**变异验证**（铁律：**没被咬住过的守卫等于没有守卫**）：
```bash
python .hermes/scripts/mutate_verify_<域>.py      # 改坏 → 必须红 → 还原 → 基线绿
```
> ⚠️ 变异跑时**不并发任何 pytest**（会把变异体留在源码里 —— 已踩 4 次）。
> ⚠️ 变异没红时，**先查锚点是否打偏**，再怀疑守卫是摆设。

**业务链路验收**（本项目第 6 项）：`docs/04_测试文档/09_第二阶段功能点全链路验收清单.md`
— 以**业务链路**为单元，把前端入口串起来做全链路；**新增前端入口必须新开一条链路或接入既有链路**。

**Gate 4 判据**：
- [ ] 用例库 / 缺陷标记 / 业务链路验收 三件已更新
- [ ] 缺陷全部处于 `[VERIFIED]` / `[WONTFIX]` / `[DUP]`（**只标 `[FIXED]` 不算关闭**）
- [ ] 每个受影响链路都有完整四段（入口链 / 末端业务结果 / 通过判据 / 断链点）

## 附 · 三条最贵的通用教训（本项目实测）

| # | 教训 | 实证 |
|---|---|---|
| 1 | **外部契约靠抓包，不靠想**（抓包放设计阶段）| 商品发布 4 次返工 |
| 2 | **判据式 > 举例式**（举例式注定被下批数据推翻）| SKU 匹配判据改 **4 次**、每版都写「定论」 |
| 3 | **规范要能被执行**（不接线的规矩 = 纸面规矩）| `library_item_filter.cjs` 写进文档但从未被跑过 |

### 返工三类归因（判断某次返工该不该防）

| 类型 | 占比 | 对策 |
|---|---|---|
| **A 平台契约类** | ~6 成 | **抓包**（「想清楚」防不住）|
| **B 交互规格类** | ~2 成 | **写进设计文档**（能防）|
| **C 需求收敛类** | ~2 成 | **不该防**（需求在收敛，不是返工）|

⚠️ **别用「设计文档不足」当万能借口** —— 它只对 B 类成立。
