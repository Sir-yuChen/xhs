**决策记录（本轮新增）**

1. **T-110 选了「注册为最低优先级源」而不是「从 YAML 删键」**。删键会让 YAML 的配置能力整体退化——那是把一种错误换成另一种错误。→ 已回写 `05_项目沉淀/01_架构决策记录_ADR.md`。
2. **T-105 选了「下线」而不是「实现真实更新」**。已核实 `PlatformAccount` 上**不存在用户可编辑字段**（`nickname`/`avatar_url`/`profile_json` 由平台同步且会被健康检查覆写）。保留一个「改了不生效还不报错」的接口比 404 更危险。
3. **`sub_type` 与 `role` 的失败策略刻意相反**：前者是**路由开关**（猜错会打错域名与 Cookie 域）→ 未知即 `raise`；后者是**权限开关**（猜错只会少给权限）→ 未知即**保守降级为 `user`**。这条差异已在 TC-M1-06 / TC-M1-14 固定。
4. **T-104 只落 `role`，不落 `is_admin`**。原任务书写的是「加 `is_admin` / `role`」，实施时收敛为单一 `role` 列——两个字段表达同一件事必然出现不一致，而系统只有「全局级设置」一处需要区分身份，不需要完整 RBAC。
5. **顺带修了 DEF-031（新发现）**。详见 `04_测试文档/04` §2.2。

**核心设计决策（D1–D10，详见需求 04 §10.1）**：异步任务（接口立即返回 task_id）；复用 `tasks` 表两个 task_type；防重两道（手动 + 调度器）；表名沿用 `shop_products`；有界的全部（默认 3 页上限 20×100=2000）；笔记/商品同步共用同一个 `CrawlRateLimiter`；调度器开关默认关 6 小时；不跳过已同步笔记（取最新值）；`notes_count` 对比判「有待同步」，缺值视为待同步；前端轮询不引入 SSE。

> **⑨ 增量同步的补充决策（D11–D13，2026-09-19 千帆真机调研后确立，详见设计 13 §17）**：
> **D11 全量/增量由 `mode` 区分**：手动触发默认 `full`（全量重扫 + upsert），调度器默认 `incremental`（游标 + 时间窗 + 早停）。
> 理由是笔记的**变更维度做不到时间窗**（列表无 `update_time`、无时间窗参数），调度若要覆盖变更只能翻满 98 页，与风控直接冲突；
> 而增量模式下调度请求量与「新增速度」成正比、与账号总量无关，正是「慢慢同步」的形状。
> **D12 删除维度显式声明不感知**：平台两个列表都不返回已删行，不做软标记（软标记要全量比对，与「调度只增量」矛盾，
> 且易把平台临时下架误判成删除）；本地行不因同步而删除，由「无流量清理」等独立需求另行处理。
> **D13 游标只在成功落库后推进**：存「已落库行的最大值」而非「平台返回的最大值」，半途限流/失败时停在最后一次成功落库位置 ——
> 这同时是 **DEF-043（同步永远走不完）的正式解**，两者在实现侧是同一批代码。
> ⚠️ **单位陷阱**：商品时间窗参数 `create_time_from/to` 单位是**秒**，响应字段 `create_time`/`update_time`/笔记 `publish_time` 是**毫秒**（相差 1000 倍，传毫秒被 ES 拒成 500）。

**风控纪律**：有界翻页 + 按账号限流 + 页间停顿 ≤60s + 超限停本次 + 调度 `max_instances=1 + coalesce` + 账号间停顿；**禁用** `get_all_posted_notes` / `get_user_all_notes` 全量循环（C5）。

### 4.9.1 问题（用户报出，已在本机真实库 `data/spider_xhs.db` 实测复现）

| # | 现象 | 实测证据 | 根因 |

> ⚠️ **不是问题、别去「修」**：同一小红书账号同时存在 `pc` 与 `creator` 两条账号行（如 `观隅好物`，id 1 与 id 8）
> **是有意设计** —— `_sync_creator_account_from_pc_cookie()` 专门从 PC Cookie 换出创作者链路；账号卡片上也明确区分「类型：PC / Creator」。
> 因此**唯一性键必须包含 `sub_type`**，否则会把两条合法链路合成一条、丢掉发布能力。

### 4.9.2 设计（三条不变量）

| 不变量 | 落地方式 |
|---|---|
| **I1 · 账号唯一** —— 同一 `(user_id, platform, sub_type, external_user_id)` 只允许一行 | DB 层**部分唯一索引**（`external_user_id` 非空时生效）+ 所有建号路径收敛到**唯一写入点** `upsert_platform_account()`；`external_user_id` 为空时退化为 `(user_id, platform, sub_type, nickname)` 兜底匹配 —— **既不伪造 id，也不无界新建** |
| **I2 · 笔记唯一** —— 同一 `(user_id, platform, note_id)` 只允许一行，落库即**覆盖更新** | DB 层唯一索引 + `_save_normalized_notes` / `batch_save_notes` 共用同一套 upsert 语义；命中既有行时**同步刷新 `platform_account_id`**（修 P2）。全程**不换 `notes.id`**，保证 `note_assets` / `note_tags` / 草稿引用不被打断 |
| **I3 · 删除不留孤儿** —— 删账号后 `notes` / 绑定不悬空 | 账号删除改**软删**（`deleted_at`）；重新导入同一账号时 upsert 命中软删行 → **复活**（清空 `deleted_at`）而**不是新建** → 从根上消灭「删了再导入又来一条」的重复源 |

**为什么是软删而不是级联硬删**：`notes` 是用户的**内容库**（可被批量转草稿 / 打标签），硬删账号会连带丢掉这些工作，
而「不静默删除」是本项目硬约定。软删让身份行**一直在位**，唯一索引因此永久成立，笔记与绑定也不需要迁移。

### 4.10.7 收尾复核发现：DEF-048 用例**不稳定**，根因是「探活静默降级」

**现象**（量化，两套独立观测）：
- 该用例**单跑 4 次 → 3 红 1 绿**，红时输出恒为 `AssertionError: {"detail":"登录已过期"} / assert 502 == 200`；
- **全量跑 2 轮 → 第 1 轮 `446 passed / 0 failed`、第 2 轮 `446 passed / 1 failed`（正是它）**。

⇒ 所以「某次全量 446 passed / 0 failed」是**侥幸**，**不能作为验收依据** —— ~~判定必须**重跑 ≥3 次**~~。<br>⚠️ **2026-09-22 用户调整**：操作要求已放宽 —— 判定以 `--junitxml` 为准，**默认只跑 1 轮**（重启服务后验证一次即可）；**只在真的出现红绿不一致时**才重跑定位（那是 flaky 排查，不是「要 3 轮才成立」）。**原句保留**：「某次全绿是侥幸」这个**事实判断仍成立**，被取消的只是「必须 3 轮」这个**操作要求**。

**根因（本轮定位，此前只登记为「探活被静默跳过」）**：链路有三步，任何一步断掉都会退化成「取第一个候选」：

| 步 | 代码 | 本例实况 |
|---|---|---|
| ① URL → note_id | `_note_id_from_url()` 要求路径段 `all(c in 0-9a-fA-F) and len >= 16` | 夹具 URL 是 `.../explore/detail-note-001?...` → 段含 `-`、长度 15 → **返回 `""`** |
| ② 有 note_id 才探活 | `if not probe_note_id: return cookies`（`pc.py` ≈ 988） | `probe_note_id == ""` → **第一个带 `web_session` 的候选直接返回，不探活** |
| ③ 候选顺序 | `order_by(AccountCookieVersion.created_at.desc())`，三行 `created_at` 同级 | 顺序由 SQLite 自行决定 → 有时先返回**过期的**那行 → 502 |

即：**「解析不出 note_id」= 静默失去探活保护**。生产里真 note_id 是 24 位 hex，所以线上不易撞到；
但它把「探活」这个安全网做成了**条件性**的，属于设计缺陷，不只是夹具问题。

**为什么不在本轮修**：DEF-048 已在 `docs/04` §2.3 登记为 `[OPEN]` 并注明「**不擅自修**（放宽借用＝扩大他人会话使用面，须先拍板）」。

- **保守**：解析不出 note_id 时**不借**（宁可 400 让用户重登），不拿未验证的会话去读；
- **宽松**：解析不出时按 DEF-048 原意**放宽为同平台**并**强制逐个探活**（用 `note_id` 之外的可用探针）。

### 4.10.8 三方令牌通用性：真机矩阵实验（2026-09-20，回答用户提问）

> **问题（用户原话）**：「千帆，创作者平台以及PC端，三个平台的登录令牌是否通用，如果通用则就无需创建多个账号，
> 只需要一个账号使用相同令牌即可。」
> **结论**：**不通用，但也不是三个独立体系 —— 是「两套体系」**。创作者平台与千帆**同属一个 SSO、可以互相顶替**；
> PC 网页版是另一套，且**只能单向派生**（PC → 创作者），**反向不成立**。

**方法**：真实 Chrome 窗口 + 隔离 profile + CDP（`--remote-debugging-port=9222`），
**每份凭据各起一个干净 profile**，只注入那一份 Cookie，再依次访问三个平台；
www 的登录态用项目自己的只读适配器 `get_self_profile()` 验（不靠页面长相判断）。
脚本 `.hermes/tmp/probe_token_matrix.py` / `probe_token_chain.py` / `probe_guest_control.py`。
全程只做 GET 导航 + 只读 `/v2/user/me`，**不打印 Cookie 值**，不写库。

**互认矩阵（实测）**：

| 只注入 | → `www` | → `creator` | → `ark`（千帆） |
|---|---|---|---|
| **PC 凭据**（acct 7 · 晨晨家，14 键，含 `web_session`/`id_token`） | ✅ `nickname=晨晨家` | ✅ 创作中心显示「晨晨家」 | ❌ 被打回 `customer.xiaohongshu.com/login` |
| **创作者凭据**（acct 8 · 观隅好物，15 键） | ❌ 只有**游客**会话 | ✅ 显示「观隅好物」 | ✅ **进 `ark.xiaohongshu.com/app-system/home`，显示「观隅好物的店」** |
| **千帆凭据**（binding 1，24 键） | ❌ 只有**游客**会话 | ✅ | ✅ |

**两套体系**：
- **网页版**：`web_session` + `id_token` → `www` / `edith` / `sns/web`；
- **customer 单点登录**：`customer-sso-sid` + `customerClientId` + `access-token-<service>` →
  **`creator` 与 `ark` 共用**，凭 `POST /api/cas/customer/web/service-ticket`
  （`{'service': <目标站>, 'type': 'tgt'}`，见 `apis/xhs_creator_login_apis.py::_build_session_request`）互相换取。
  PC jar 里**没有** `customer-sso-sid`，所以拿不到 ark 的 ticket。

**对现有实现的三条结论**：
1. **PC → 创作者**：可派生且已在用（`_sync_creator_account_from_pc_cookie` → `exchange_from_user_cookies`）。
2. **创作者 → 千帆**：**浏览器里能，服务端不能** —— 本节的「浏览器矩阵」只证明**浏览器**能自动登录；
   服务端复现的可行性复核**不通过**（换不出 `access-token-ark`，最后一步是带签名的 `ssologin`）⇒
   **千帆绑定仍需单独做**。⚠️ 本节初稿曾写「千帆绑定理论上可免单独绑定」，**已被 §4.10.9 取代**。
3. **创作者 / 千帆 → www**：**不成立**（全仓只有 `exchange_creator_session_from_user_cookies` 一个方向）。
   ⇒ §17.6.3 的「同身份借会话」**是唯一办法，不是绕路**；「只保留一个账号、删掉借用逻辑」在平台侧做不到。

**⚠️ 同轮抓出的新缺陷（DEF-051，🟠P1 **已修 `[FIXED]`**）**：**`web_session` 存在 ≠ 已登录**。
**什么都不注入**的干净 profile 访问 `www.xiaohongshu.com` 也会被种上 `web_session`；
这份 jar 调 `/v2/user/me` 回 `ok=True` 但 **`nickname=None`、`user_id` 每次不同**（游客）。
而全项目唯一的判定 `account_service.has_web_session()` **只看键在不在且非空** ⇒ 游客会话被判成「网页会话可用」。
**修法（已实施，见 §4.10.10）**：判定收紧为「有 `web_session` **且** 有 `id_token`」——
上面这**三组矩阵正好给出了 `id_token` 这个零请求判据**：游客 / 创作者 / 千帆凭据都拿不到 `id_token`，
只有真的在 www 登录过的 jar 才有。

**方法论教训**：**对照实验不可省**。第一轮实验里「注入创作者 jar 后 www 出现了 `web_session`」看着像
「creator 能登 www」；是**空 profile 对照组**（什么也不注入照样出现）把「游客会话」这个解释钉死的。
另外：**探针脚本对每一份凭据都要用干净 profile** —— 复用同一个 profile 会让上一轮的会话污染下一轮。

* 新增 **5 条守卫用例**：
  * `test_self_content.py`（3 条）—— 只有 ark 通道的账号**借到会话读详情**（DEF-056 回归）/
    笔记维度**拿到笔记维度那句原因**（不套用户维度的话）/ **借用不吞归属错误**（404 保持）；

    失败**必须**降级成一行说明（断言前先 `_code_only()` **去注释**）。

* 全量回归见 §4.10.13 同口径（`--junitxml` 判定，**连跑 3 轮**）。

#### ⑤ 三条教训

1. **「有没有 A」不能写成「能不能做 B」的前置条件** —— 一旦写成，兜底分支就变成**永不执行**的死代码，
   而它**看起来还在那里**（读代码的人会以为兜底生效）。与 DEF-048 同型：**兜底的顺序、
   以及它到底会不会被执行，本身就是契约**。
2. **能力推断 ≠ 能力实测**：能用「试一次」判定的，不要用「按类型猜」—— 猜错的表现是**挡掉可达的功能**，
   且给出的理由是假的（与 DEF-054「账号 15」同型：**错误理由比没有门禁更糟**，会把人引向错误方向）。
3. **`in source` 型断言先数目标串出现几次，并剥掉注释** —— 本轮首版断言 `"capabilityFor" not in source`
   **被自己写的解释性注释命中**。改为正则去注释 + 断言 `function capabilityFor` 这类**代码形态**后
   才真正承重（这是本项目第 N 次栽在同一处）。

#### ② 三条根因

| # | 根因 | 位置 |
|---|---|---|
| 1 | **信息销毁（全站范围）**：`typeof detail === "string" ? detail : "请求失败，请稍后重试"` —— **只认字符串**，而后端**所有**可自救的失败都返回**结构化** detail（`{code, message, platform_message}`）⇒ 后端给的原话在**最后一步**被替换 | `frontend/src/lib/api.ts` 全局 response 拦截器 |

> **根因 1 的严重性被低估过一次**：它不是「三个页签的 bug」，而是**任何**走结构化 detail 的端点
> 都会把真原因替换掉 —— 换言之，**后端前几轮所有「诚实降级」的努力，在最后一步被前端抹掉**。

#### ③ 改动

* **文案解析收敛成唯一实现**：`lib/api.ts::detailMessage(detail)`（导出）——
  字符串原样、结构化对象取 `message` → `platform_message`、**422 的数组按 `loc：msg` 还原**
  （多项用 `；` 连接，丢掉 `type`/`input` 内部细节）。拦截器与页面 `readError()` **共用这一份**。
  > v1.29 更正：第一版写的是「422 的数组**显式排除**（校验错误不是给人看的原因）」——
  > 结果它只剩英文 axios 文案兜底（`Request failed with status code 422`），**换了一种看不清**。
  > 数组恰恰最该给人看（哪个字段没通过哪条约束）：不还原它，**前端任何字段名写错都会静默降级成通用文案**。
* **失败展示权归调用点**：自有内容四个 loader（`fetchXhsSelfNotes` / `Liked` / `Collected` /
  `InteractionMessages`）加 `_silent`（先例 `fetchXhsSelfCapabilities`）。
* **三分法**：`my-notes-page.tsx::renderFailure(error)` ——

  | 情形 | 判定 | 呈现 |
  |---|---|---|
  | 有数据 | 200 且非空 | 渲染列表（翻页失败时列表保留，另给可重试提示） |
  | **没数据** | 200 且为空 | **空态** —— 不是错误 |
  | **取不到** | `WEB_SESSION_REQUIRED` / `XSEC_TOKEN_REQUIRED` | 一行 25–30 字 **安静说明** + Tooltip |
  | **真·接口异常** | 其余（含 **422 请求校验失败**） | **红块 + 真实原因**（`description={error.full}`） |

* **后端**：删掉那句假归因，改为「只讲凭据 + 怎么修」；docstring 里同步写明为什么不写它。
* **短文案改为可执行**：「需在网页版重新登录」。

* **行为验证（本轮新增的一层）**：`tests/frontend/detail_message.cjs` —— esbuild 打包**真实**
  `lib/api.ts`，取出**真实** response 拦截器并驱动它，断言 antd 收到的文案；antd 用桩替换

* **源码守卫 5 条**（`test_page_optimizations.py`，该文件 30→**35**）+ **后端 2 条**
  （`test_self_content.py`，74→**76**）。
* **变异验证 8/8 按预期变红**（`.hermes/scripts/mutate_verify_def058.py`；v1.29 追加 ⑧「删掉 422 数组分支」），
  行为脚本自身三个开关 `generic` / `silent` / `validation` 也各自转红；基线复跑绿。
* **回归**：`--junitxml` 判定，**连跑 3 轮**，见 §14 变更记录。

#### ⑤ 四条教训

1. **「不让用户看到内部错误」与「不让用户看到真原因」只差一步** —— 兜底文案只能在
   **确实没有真原因**时出现。用「反正用户看不懂」当理由去替换结构化原因，代价是
   用户**彻底失去自救能力**。
2. **错的归因比不说更糟**：把「凭据缺失」说成「平台没有这个能力」，用户**永远不会去重登** ——
   错的归因会让人放弃唯一有效的动作。
3. **源码断言证明不了行为**：把 `detailMessage` 改成 `return ""`，
   `"Array.isArray(detail)" in source` **依然为真**。凡「函数怎么跑」的要求，
   必须**打包真实源码 + 驱动真实调用点**（`detail_message.cjs` 即为此而建）。
4. **负向断言（`not in`）会因别处改动静默失效**：DEF-057 用例里的
   `assert "这三类数据" not in message` 找的是**旧版文案**里的词，本轮改写那句文案后
   **变成恒真**、变异验证**不再变红**（是变异脚本把它抓出来的）。
   ⇒ 负向断言应指向**两侧的关系**（如 `a != b`）或断言「断言对象自己的措辞」，
   **不要指向别处会变的一个词**。
