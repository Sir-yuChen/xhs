# 开发规范与架构硬约定

> - **阶段**：三 · 开发
> - **性质**：**写代码前必读。** 本文的约定是硬约束，违反会导致架构腐化或生产事故。
> - **原则**：开发的功能**以详细设计文档为准则**；设计文档没写的不写；追求「写完即对」，尽量不要改 bug。
> - **版本**：v1.2 · 2026-09-18（新增 H8 视图实体身份不变式 + 红线 X17；§9 本地运行与排障自 v1.1 起）

## 1. 八条架构硬约定（不可违反）

### H1 · `apis/` 禁止直接修改

> `apis/` 是底层 SDK，**上层只能经 `backend/app/adapters/xhs/` 中转**。

| 允许 | 禁止 |
|---|---|
| 在 `adapters/xhs/` 里新增适配方法调用 SDK | 在 `backend/app/api/*` 或 `services/*` 里 `import apis.*` |
| 在 `apis/` 里新增文件（新业务域） | 为了「顺手」在 `apis/` 里改业务逻辑 |

**理由**：`apis/` 承载逆向签名，变更影响面是全项目。适配层是唯一的翻译边界。

**唯一例外**：二开向 SDK 加新参数时（如 `goods_info`），**必须保证默认值向后兼容**（`= {}`）。参照 `xhs_utils/xhs_creator_util.py:119` 的改法。

---

### H2 · 时区统一用 `shanghai_now()`

> **全项目禁止裸 `datetime.now()`。**

```python
# ✅
from backend.app.core.time import shanghai_now
created_at = shanghai_now()

# ❌
from datetime import datetime
created_at = datetime.now()
```

**理由**：曾经有过 UTC 存储的存量数据，项目已写过两段幂等迁移把时间 `+8h`。再引入裸 `datetime.now()` 会让问题重演。

**注意调度器时区**：`BackgroundScheduler(timezone="UTC")`（`scheduler_service.py:700`）——job 内部做业务时间比较时**必须显式处理时区**，不要假设一致。

---

### H3 · 签名算法唯一实现源

> **算法只存在于 `xhs_utils/**/js/`，Python 侧不重复实现。**

```python
# ✅ Python 侧只做：序列化输入 → 调 Node → 校验输出
result = subprocess.run(['node', sign_js, json.dumps(payload)], ...)
if not valid(result):   # 长度 / 前缀 / 正则门禁
    return None         # 显式失败，绝不降级

# ❌ 在 Python 里重写一遍 RC4 / XXTEA / CRC32
```

**理由**：① JS 是原版，行为可对齐浏览器；② 单源实现，平台改版只需改一处；③ 双份实现必然漂移。

---

### H4 · 签名输入只有 path + body

> `run_signer(api, data, ...)` **不吃 host**。域名差异只体现在 HTTP 层。

**推论**：新增业务域（如千帆）只需加 platform config + 加接口，**不需要重新逆向**。

**违反后果**：如果在签名里塞 host，就会破坏「同栈服务多域」的复用能力，每个域都要独立逆向。

---

### H5 · Cookie 不覆盖写

> 往 `account_cookie_versions` **追加版本**，取用按 `created_at desc, id desc`；内容 Fernet 加密。

**理由**：平台可能拒绝新 Cookie（换回旧的可用）；账号被限流时可对比历史；审计需要。

---

### H6 · 适配层调用必须包在 `direct_xhs_request_env()` 里

```python
from backend.app.adapters.xhs.request_env import direct_xhs_request_env

def search_note(self, keyword: str):
    with direct_xhs_request_env():          # ← 必须
        return self._api().search_note(query=keyword)
```

**理由**：本机/服务器常设 `HTTP_PROXY` 等环境变量，`curl_cffi` 会读取 → 请求经代理发出 → 出口 IP 变化 → 触发风控。上下文管理器会临时摘除这些变量（**加线程锁**），并在 finally 恢复。

**违反后果**：开发机上测试正常，部署后全部请求走代理，账号被风控。

---

### H7 · 受控取值的失败策略**按猜错后果**定，且必须走统一 helper

> ⚠️ 这条约定是 2026-09-18（T-102 / T-104）确立的。**不要"顺手统一一下"。**

系统有两个「取值集合受控」的字段，**策略刻意相反**：

| 字段 | 字段性质 | 未知取值（非空、不认识）时 | 唯一权威定义 |
|---|---|---|---|
| `platform_accounts.sub_type` | **路由开关**（决定 adapter / 域名 / Cookie 域） | **`raise UnknownSubTypeError`** | `core/account_types.py` |
| `users.role` | **权限开关** | **保守降级为 `user`** | `core/roles.py` |

**理由**：路由类猜错是「**做错事**」（打错域名，静默失败），必须立刻响亮失败；
权限类猜错是「**少做事**」，沉默地保守才是正确行为。

**必须区分「缺失」与「未知」**：

```python
normalize_sub_type(None)   # → "pc"    缺失（历史数据从没写过）→ 隐式默认
normalize_sub_type("")     # → "pc"    同上
normalize_sub_type("shop") # → raise   未知（有人写了我不认识的东西）→ 危险信号
```

**判定身份/角色只能用 `core/roles.py::is_admin()`，不得读裸字段、更不得用 `sub_type` 判断。**
`sub_type` 与「是不是管理员」完全正交。

**违反后果**：统一抛错 → 历史数据缺字段时**整个系统登不进去**；统一兜底 → 新增链路**静默走错分支**。

---

### H8 · 一个视图实体的「身份」与「内容」必须同源；异步响应必须带身份

> ⚠️ 这条约定是 2026-09-18（DEF-036 + DEF-038，**同族复发**）确立的。

**不变式**：界面上展示的那个实体，必须就是正在被读写/轮询的那个实体。任何允许两者
**短暂或永久漂移**的写法都是缺陷，而且症状几乎总是「**没有任何报错，页面就是不动**」。

**禁止的写法**（`frontend/src/components/account/qr-login-panel.tsx` 均为真实历史缺陷）：

| 形态 | 后果 | 正确做法 |
|---|---|---|
| 偏好/开关作为**会话创建 effect 的依赖** | 改偏好 → 建新会话 → 旧实体作废（DEF-036） | 偏好用 `ref` 读；要传给后端就做成**实时覆盖参数** |
| 无条件合并响应：`setState(cur => ({...response, 保留cur的某字段}))` | 迟到响应把 `id` 拉回旧值，而「某字段」仍是新的 → **屏幕是 B，轮询器盯着 A**（DEF-038） | 先校验 `response.id === activeIdRef.current`，再在 updater 内校验 `cur.id === id`，否则**原样返回 `cur`** |
| 生成请求无「代次」概念 | 被取代的迟到响应覆盖当前实体 | 单调 `generationRef`，过期即丢弃 |

**为什么必须按不变式修而不是调时序**：竞态只在抖动时出现 → 表现为「以前偶尔能用、
现在几乎用不了」，靠 sleep / 减请求只会把它变得更隐蔽。

**副作用提醒**：`React.StrictMode`（dev）会把 effect **调用两次**。任何带副作用的
初始化 effect 都必须自备幂等守卫（本项目是 `initialisedForRef` 记「已按哪个值初始化过」），
否则一次用户动作会产生两份实体（DEF-038 就是 18 条会话里 10 条从未被轮询）。

**验收要求**：这类修复只跑断言**不算完成**——必须做一次**变异验证**：
把守卫改成恒假，断言必须变红。做法见 `tests/frontend/qr_session_identity.cjs` 的
`QR_MUTATE=old` 模式。

## 2. 分层与依赖规范

### 2.1 依赖方向

```
api/  ──▶ services/  ──▶ adapters/  ──▶ apis/ + xhs_utils/
  │            │
  └────────────┴──▶ models/ (可被任意层引用)
core/  ← 被所有层引用（基础设施，无业务）
```

**禁止**：
- `apis/` 或 `xhs_utils/` 里 `import backend.app.*`
- `services/` 里 `import backend.app.api.*`
- `models/` 里 `import services` 或 `api`（模型只做数据定义）

### 2.2 各层职责边界

| 层 | 该做 | 不该做 |
|---|---|---|
| `api/` 路由 | 鉴权、参数校验（Pydantic）、调 service、序列化返回 | 写业务规则、直接查复杂 SQL、直接调 `apis/` |
| `services/` | 业务规则、事务边界、跨模块编排 | 处理 HTTP 细节、直接返回 Response |
| `adapters/` | 翻译 SDK 的 `(success, msg, data)` 为业务对象；管理请求环境 | 业务规则、持久化 |
| `apis/` `xhs_utils/` | 签名、HTTP、响应归一化 | 任何业务概念（用户、草稿、发布） |
| `models/` | 表结构定义 + 关系 | 查询逻辑（放 service 或路由） |

## 3. 编码规范

### 3.1 Python

| 项 | 规范 |
|---|---|
| 版本 | 3.10+，使用 `from __future__ import annotations` |
| 类型标注 | **全部函数必须标注**参数与返回值类型 |
| ORM 风格 | SQLAlchemy 2.0 声明式：`Mapped[T]` + `mapped_column(...)` |
| 命名 | 文件 `snake_case.py`；类 `PascalCase`；函数/变量 `snake_case`；常量 `UPPER_SNAKE` |
| 私有 | 模块内部用 `_prefix`；跨模块不复用私有符号 |
| 导入 | 顶层导入标准库与三方；**`apis/` 与 `xhs_utils/` 在函数内延迟导入**（照现有 adapter 写法，避免启动期加载 Node 依赖） |
| 异常 | 业务异常抛 `RuntimeError` 或 `HTTPException`；**不吞异常**（现有 bug 很多源于 except 后没记录） |
| 日志 | 用 `logging`，不 `print`；**日志不得输出 Cookie / API Key / 密码** |
| 注释 | 解释「为什么」而非「做什么」；关键反直觉处必须写注释（如 `# 浏览器实抓：未选地点时省略 post_loc 键`） |

### 3.2 TypeScript / React

| 项 | 规范 |
|---|---|
| 组件 | 函数组件 + Hooks，**不用 class 组件** |
| 命名 | 组件文件 `kebab-case.tsx`；组件名 `PascalCase`；hooks `useXxx` |
| 类型 | 所有 props 显式定义类型；后端实体类型集中在 `types/index.ts` |
| API 调用 | **必须走 `lib/api.ts`**，不在组件里直接 `fetch`/`axios` |
| 状态 | 页面级 `useState`；跨页共享再考虑引入状态库（当前**未引入**） |
| UI 库 | 统一用 antd 6 组件，不自己造轮子 |
| 时间 | 展示用后端返回的东八区时间，**前端不做时区转换** |
| 错误 | 请求失败要有可见反馈（message / Alert / 空态），**不静默失败** |

### 3.3 前端「能力驱动」原则

```tsx
// ✅ 读能力，置灰 + 说明原因
<Button disabled={!shop.capabilities.can_attach_goods}>
  挂商品
</Button>
{!shop.capabilities.can_attach_goods && (
  <Text type="secondary">
    {shop.capabilities_verified_at ? "该店铺无商品分享权限" : "能力未验证"}
  </Text>
)}

// ❌ 读类型做分支
if (shop.shop_type === "personal") { /* ... */ }

// ❌ 直接隐藏
{shop.capabilities.can_attach_goods && <Button>挂商品</Button>}
```

**理由**：隐藏会被当成 bug 报过来；用户需要理解「为什么不能」。

## 5. 变更管理规范

### 5.1 何时必须先改设计文档

> **停止编码，先改设计文档，再改代码。**

| 情况 | 动作 |
|---|---|
| 发现设计文档有误 | 修订设计文档 → 记 ADR（若影响架构）→ 再编码 |
| 需要新增一个 API/表/开关 | 先补 `02_设计文档/05` / `03` / `10` → 再实现 |
| 需要改 `_select_adapter` 之类的兜底分支 | 先补 `ADR` → 再改，并**改成显式枚举 + raise** |

### 5.2 何时写 ADR

判断标准：需要「换技术栈、换数据模型、换链路、改架构硬约定、或影响两个以上模块」→ **必须写 ADR**（`05_项目沉淀/01_架构决策记录_ADR.md`）。

### 5.3 提交规范

```
<类型>(<范围>): <简述>

类型：feat | fix | docs | refactor | test | chore
范围：api | web | sdk | scheduler | model | docs

示例：
feat(api): 新增店铺列表与能力探测端点
fix(sdk): 修正 goods_info 参数未透传导致商品笔记无挂链
docs(design): 补充发布链路幂等键设计
```

**要求**：一个提交只做一件事；**代码改动与设计文档改动放在同一批提交里**（否则文档必然漂移）。

## 9. 本地运行与排障（**改了代码先重启后端**）

### 9.1 后端默认**不开热更新** —— 这是「改了没生效」的第一嫌疑

`python main.py` 的 `--reload` 是**可选开关且默认关闭**（`main.py:18` 定义，`main.py:71` 传给 `uvicorn.run(..., reload=args.reload)`）。
因此**改完 Python 代码，正在跑的后端进程仍是旧构建**，重启前所有改动都不可见。

| 服务 | 启动方式 | 改代码后 |
|---|---|---|
| 后端 | `python main.py`（PID 常驻，默认无 reload） | **必须重启**；或改用 `python main.py --reload` |
| 前端 | Vite dev server | 有 HMR，**不用重启** |

### 9.2 识别「进程是旧构建」的方法

进程路由数与源码路由数不一致 = 旧构建。取运行中进程的 OpenAPI：

```python
# 运行中进程真实暴露的路由（会明显少于源码）
import json, urllib.request
d = json.load(urllib.request.urlopen("http://127.0.0.1:8000/openapi.json"))
print(len(d["paths"]), sorted(d["paths"]))
```

**本项目的实测锚点（两个数都对，只是口径不同，别混用）**：

| 口径 | 取法 | 新构建 | 历史旧构建 |
|---|---|---|---|
| **path 条数** | `len(spec["paths"])` | **116** | **115**（缺 `/api/xhs/pc/users/capabilities`） |
| **端点（operation）数** | 各 path 的 method 累加 | **136** | 135 |

⚠️ 文档里说的「端点 136 / 135」是**第二行**（method+path 对，见 `04_测试文档/05`）；`05_测试文档` 之外的排障脚本若直接 `len(paths)` 会得到 **116**。**两者都能判断新旧，但不要互相印证为矛盾。**

### 9.3 这个坑的**典型症状**（极易误判为代码 bug）

1. **修好的 bug 看起来没修** —— 代码、测试、构建全部正确，但页面依旧复现。
2. **前端弹 `Not Found` 提示** —— 前端请求了旧进程里**尚不存在的新路由**，HTTP 返回 404，全局 axios 拦截器再把它渲染成 `message.error`。
   ⚠️ 这与 DEF-037 是**两个不同成因**：DEF-037 是「路由存在但探针失败被拦截器误报」；本条是「路由根本不在旧进程里」。**排障时先确认进程新旧，再怀疑前端逻辑**。
3. **`/openapi.json` 里搜不到刚写的端点** —— 最直接的证据。

### 9.4 验证新构建而**不影响用户正在跑的服务**的做法（推荐）

不要杀掉用户的服务进程。在**临时端口**起一份新构建做验证，验完即回收：

```bash
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8099   # 后台启动
# → 拉 http://127.0.0.1:8099/openapi.json 核对路由 / 打真实接口
# → 验证结束后回收该进程，确认 8099 释放
```

好处：既能证明「新代码本身是对的」，又不必中断用户排查现场。

> **重启是运维动作，不是代码修复。** 报告「已修复」之前，**先确认跑的是新构建**，否则文档、测试、构建全绿也可能被用户现场打回。
