4. 我修正过的判断（前后对照）

对象我一开始说实测后改成
account_cookie_versions 「多版本是故意的，不能压」 可以压。代码注释原文是「无法在 SQL 里过滤，只能逐条判定」—— 多行是没做 JSON 列时的妥协。20+ 读点无一读「第几版」
auto_tasks 0 行 ⇒ 可并进账号表 不能并。它有 pc_account_id + creator_account_id 两个账号外键 + schedule_job_id，是「自动运营任务定义」
monitoring_targets 0 行 ⇒ 可并进账号表 不能并。有 target_type + 独立调度 crawl_interval_minutes + 失败计数，是「监控对象」实体
publish_jobs max/父 = 1 ⇒ 可并 不能并。全库只有 1 条是业务没用起来； 一个账号可发 N 篇，external_note_id 是防重复发文判据
「≤1 行/父 ⇒ 可合并」这个脚本判据 按全局行数比父表行数 判据本身是错的。必须按父键 group by 数子行取 max， 且行数少不能当 1:1 的证据（业务未起 ≠ 结构恒 1:1）

5. 风险与代价

最大的代价：draft_assets / publish_assets / no_traffic_cleanup_items 转 JSON 后， 「单条增删 / 重排」要改成「整组读-改-写」。
现在 POST /drafts/{id}/assets 返回的是独立资源、前端按数组消费、sort_order 支持重排。 转 JSON 后：新增 = 读数组 + append + 写回；删除 = 读 + filter + 写回。 并发下两次同时 append 会丢一条（当前每行独立 INSERT 不会丢）。
缓解方案：这些表的写入频率极低（draft_assets 1 行 / publish_assets 1 行）， 且都是单用户单草稿内操作。加上行级乐观锁（version 列）即可覆盖。 若将来出现并发写，再拆回独立表。
不重构的部分（明确不做）：27 张 L1 表的改名加 xhs_ 前缀不在本轮。 理由：它不减少表数、不改结构，只是重命名，却要动全部 ORM __tablename__ + SQL 字符串 + 前端类型。 先做结构合并（真有收益），改名单独排期。
