# XHS_ALL_IN_ONE 签名体系

> 本项目最有技术含量的部分。详见仓库根目录 `SIGNATURE_ALGORITHM_DEEP_DIVE.md`（27KB），本文档是其在架构层面的凝练与代码定位。

---

## 1. 为什么要签名

小红书 web 端的每个 API 请求都需要携带由前端 JS 实时计算的签名参数。缺少或错误 → 请求被拒绝。签名算法不公开、随平台更新而变化，是采集类项目的**核心壁垒**，也是**最高风险点**。

---

## 2. 四层结构

```
┌─────────────────────────────────────────────┐
│ 4. 指纹 / 业务扩展                            │
│    profileData（DES-ECB）、x-rap-param       │
├─────────────────────────────────────────────┤
│ 3. 请求签名                                   │
│    b1（RC4+Base64）、x-s / x-t（MNS 三档）、  │
│    x-s-common（CRC32）、追踪头                │
├─────────────────────────────────────────────┤
│ 2. 认证态                                     │
│    Cookie（a1、web_session）、DS 锚点、       │
│    websectiga（执行服务端下发的 JSVMP）       │
├─────────────────────────────────────────────┤
│ 1. 传输层伪装                                  │
│    curl_cffi chrome146 + http2 + 固定 Header  │
└─────────────────────────────────────────────┘
```

### 2.1 传输层伪装

- **curl_cffi** `impersonate='chrome146'`、`http_version='v2tls'`、`discard_cookies=True`。
- 每个场景有**严格固定的 Header 顺序**契约（PC / Creator 各 8~10 套顺序常量）——顺序错了也会被识别。
- 代理隔离：`direct_xhs_request_env()` 在调用期间临时摘掉 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY`（大小写全摘），`threading.RLock` 保护并发安全。

### 2.2 认证态

| 组件 | 说明 |
|---|---|
| Cookie | `a1`（设备标识）、`web_session`（登录态） |
| DS 锚点 | 请求级随机数，参与签名 |
| **websectiga** | **执行服务端下发的 JSVMP 程序**，本地最小宿主跑完后拿到 64-hex Cookie |

`xhs_core/runtime.py:generate_websectiga()` 明确注释了 websectiga 的性质：

> This is browser-independent but is not a zero-host pure algorithm: XHS supplies the program at runtime. The returned 64-hex Cookie is therefore classified separately from locally generated request parameters.

即：websectiga 是**服务端下发程序 + 本地执行**，与纯本地算法分类对待。

### 2.3 请求签名

| 参数 | 算法 | 说明 |
|---|---|---|
| **b1** | RC4 + 自定义 Base64 | 设备级参数，一次生成会话内复用 |
| **x-s / x-t** | MNS 签名 | **三档自适应**：`mns0101_` 冷启动 Base58、`mns0201_` 安全域 XXTEA、`mns0301_` 稳态 XOR |
| **x-s-common** | CRC32 | 公共参数签名 |
| 追踪头 | — | x-mns、x-b3-traceid 等 |

### 2.4 指纹 / 业务扩展

| 参数 | 端 | 算法 |
|---|---|---|
| `profileData` | PC | 自定义 DES-ECB |
| `profileData` | Creator | CryptoJS DES-ECB |
| `x-rap-param` | Creator 发布 | rap 指纹 + 请求路径 + body |

## 3. 工程实现：Node 单源 + 输出校验护栏

### 3.1 单源原则

**签名算法只存在于 `xhs_utils/**/js/`**（共 2,449 行 JS），Python 侧**不重复实现任何算法**。Python 通过 `xhs_core/runtime.py:run_node_json()` 起 Node 子进程执行：

```
Python 业务代码
  → runtime.run_node_json(['node', xxx_cli.js], stdin_payload={...}, timeout=30)
  → subprocess.run（capture_output, text, timeout）
  → 取 stdout 最后一行 → json.loads
  → 返回 dict
```

**失败处理**：

- `returncode != 0` → 只保留 stderr **最后 12 行**（vm 会先打印整段 JSVMP 源码，保留尾部才能看到真正的首个运行时错误），并截断到 2000 字符。
- 无输出 / JSON 解析失败 → 抛 `RuntimeError`，消息中带输出前 300 字符。

### 3.2 输出校验护栏（关键）

算法输出不是无条件接受的，而是先过**长度 / 前缀 / 正则校验**：

| 输出 | 校验规则 |
|---|---|
| `b1` | 长度 ≥500 且为 4 的倍数 |
| `x3`（x-s） | 必须匹配档位前缀（`mns0101_` / `mns0201_` / `mns0301_`）与长度 |
| `profileData` | 必须是 `base64-des-ecb-zero-padding-hex` 且 10000~20000 位 hex |
| `websectiga` | 正则 `^[0-9a-f]{64}$` |

**这是防止算法静默降级的护栏**：如果 JS 算法被平台改坏或本地执行异常，返回了畸形输出，校验会立即失败并抛错，而不是把一个错误签名默默发出去导致账号被风控。

## 4. 三套签名状态机

| 子包 | 端 | 结构 |
|---|---|---|
| `xhs_utils/xhs_core/` | 通用/PC 核心 | `auth.py`、`params.py`、`http.py`、`dsl.py`、`runtime.py`、`cookies.py`、`js/` |
| `xhs_utils/xhs_pc/` | PC 端 | 同结构 + `state.py`、`js/`（aes 加解密、deflate、rap） |
| `xhs_utils/xhs_creator/` | Creator 端 | 同结构 + `state.py`、`js/xhs_creator_signature.js` |

三者结构完全对齐，差异在具体算法实现与 JS 文件。

**入口**：`XHSPcAuth.from_cookie(cookies)` / `XHSCreatorAuth.from_cookie(cookies)`，由适配层调用。

## 5. 调用链路（以搜索为例）

```
XhsPcApiAdapter.search_note(keyword, page)
  └ direct_xhs_request_env()              摘代理环境变量
     └ XHS_Apis(auth).search_note(...)
        └ _request_params(...)            组装 header 顺序 + 签名参数
           ├ params.py: b1 / x-s / x-t / x-s-common
           │   └ runtime.run_node_json()  → Node 子进程执行 JS
           │      └ 校验输出格式（护栏）
           └ http.py: curl_cffi.post(impersonate='chrome146')
        └ 解析响应
```

## 6. 风险与维护

| 风险 | 影响 | 缓解 |
|---|---|---|
| 平台更新签名算法 | 采集/发布全部失效 | 单源 JS，替换 JS 文件即可；输出校验护栏让失效**快速暴露**而非静默 |
| Node.js 不可用 | 全部签名失败 | Docker 镜像必须装 Node 20；`run_node_json` 有明确报错 |
| 代理环境污染 | 签名异常 | `direct_xhs_request_env` 隔离 |
| Header 顺序变化 | 请求被拒 | 顺序常量集中管理，随平台更新 |

> **维护要点**：算法失效时**只改 `xhs_utils/**/js/` 下的 JS**，不要在 Python 侧复制算法实现——这会破坏单源约束，导致两份实现漂移。
