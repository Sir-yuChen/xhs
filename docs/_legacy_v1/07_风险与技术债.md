# XHS_ALL_IN_ONE 风险与技术债

> 所有条目均经源码核实，附证据位置。按严重程度排序。

---

## 🔴 高：架构级风险

### 1. 多副本调度不安全（无分布式锁）

**位置**：`backend/app/services/scheduler_service.py:740` + `backend/app/main.py:22-25`

调度器是 APScheduler `BackgroundScheduler`，**与 FastAPI 同进程**。

```python
scheduler = BackgroundScheduler(timezone="UTC")
scheduler.add_job(job_func, "interval", ..., max_instances=1, coalesce=True)
```

- 多 worker / 多副本部署时，**每个进程各起一套定时器** → 发布任务**重复执行**
- `max_instances=1` 只约束**单进程内**，跨进程无效
- 无分布式锁、无 leader 选举，只靠 `scheduler.enabled` 单开关

**影响**：多副本部署时同一条笔记被发布多次。**当前只适合单进程部署**。

**建议**：换用独立调度服务（Celery beat / Quartz / 外部 cron 调 API），或加 Redis 分布式锁 + leader 选举。

### 2. 密钥不分离导致的数据不可解密风险

**位置**：`backend/app/core/security.py:108-116`

```python
def _derive_fernet_key(secret: str) -> bytes:
    digest = hashlib.sha256(secret.encode("utf-8")).digest()
    return base64.urlsafe_b64encode(digest)

def get_fernet() -> Fernet:
    key = settings.fernet_key or None
    return Fernet(key.encode() if key else _derive_fernet_key(settings.secret_key))
```

- `fernet_key` 为空时**由 `secret_key` SHA-256 派生**
- 改 `secret_key` → 历史加密的 Cookie、API Key、登录临时 Cookie **全部解不开**
- 默认值 `dev-only-change-me`，生产若忘记改则密钥可猜

**建议**：生产**必须显式固定 `FERNET_KEY`**，并独立于 `SECRET_KEY` 轮换。

### 3. 逆向 SDK 的脆弱性（项目固有风险）

**位置**：`apis/` + `xhs_utils/`

签名算法依赖小红书前端 JS，平台端更新即可导致失效。

**已有的缓解**（做得不错）：
- 算法单源在 JS，Python 不重复实现
- 输出校验护栏（b1 长度/前缀、x3 档位匹配、profileData hex 位数、websectiga 64-hex）——**失效会快速抛错而非静默降级**

**不可消除的部分**：平台更新后需人工跟进替换 JS。

## 🟡 中：功能与质量缺口

### 4. 半成品接口（返回 mock 数据）

**位置**：`backend/app/api/platforms/xhs/pc.py:386,391,398`（+ `services/task_service.py:9`）

| 端点 / 函数 | 返回 |
|---|---|
| `POST /xhs/pc/search/users`（`:342`） | 硬编码 `{"total": 1, "items": [{"id": "demo-user", "nickname": "运营研究员"}]}` |
| `POST /xhs/pc/users/notes`（`:386`） | `mock_data.sample_notes()` |
| `GET /xhs/pc/homefeed/channels`（`:391`） | 硬编码单频道 |
| `POST /xhs/pc/homefeed/recommend`（`:396`） | `mock_data.sample_notes()` |
| `note_comments_placeholder()`（`:382`） | 硬编码评论，但**未被任何路由引用**（`/notes/comments` 在 `:364` 已接真实接口），是死函数 |
| `services/task_service.py:9` | `sample_tasks()` |

**影响**：任务中心页面、PC 端用户笔记/推荐/用户搜索功能读到的是假数据。

**注意**：`pc.py` 中 `/notes/comments`（`:364`）与 `/notes/detail`（`:347`）**已接真实接口**，不在 mock 名单内；真正返回假数据的是 `/search/users`、`/users/notes`、`/homefeed/*`。`note_comments_placeholder()` 是未被路由引用的死函数。评论抓取的主入口是 `crawl.py` 的 `/xhs/crawl/data`（mode=comments）。清理时删掉 mock 端点与死函数即可。

### 5. 蒲公英 / 千帆能力已实现但完全未接线

**位置**：`apis/xhs_pugongying_apis.py`、`apis/xhs_qianfan_apis.py`、`xhs_utils/xhs_pugongying_util.py`、`xhs_utils/xhs_qianfan_util.py`

**证据**：在 `backend/` 全目录搜索 `pugongying|qianfan` **零命中**。

README 功能清单里这两块标了 ✅，但 Web 层没有任何 adapter / API / 页面。**现成但没接线的能力**，接线成本不高（补 adapter + 路由 + 页面三件套）。

### 6. 测试覆盖与声明不符

**位置**：`tests/backend/`（仅 3 个文件）

README 写「126 passed」，但：

- 只有 `test_api.py`、`test_platforms.py`、`test_root_main.py` 三个文件
- 测试策略混合了后端集成测试 + **前端源码字符串断言**（读 `.tsx` 断言关键字存在）
- 核心业务（签名、发布、自动运营、调度）**无单测**

**影响**：重构前端时测试会大面积误报；核心链路无回归保护。

### 7. 自动运营失败不入通知

**位置**：`scheduler_service.py:619-623`

```python
except Exception as exc:
    logger.warning(f"Auto task {task.id} execution failed: {exc}")
```

自动运营失败只写日志，**不写 Notification 表**。用户在前端铃铛里看不到自动运营失败。对比：Cookie 过期会写 Notification。

发布失败则只落在 `publish_jobs.publish_error`，也不入通知。

### 8. SQLite 并发设置

**位置**：`database.py:32`

```python
cursor.execute("PRAGMA journal_mode=MEMORY")
```

不是 WAL，并发写入下更容易锁表。调度器 + API 请求并发写时可能 `database is locked`。

**建议**：生产换 MySQL；单机 SQLite 可试 `journal_mode=WAL`。

## 🟢 低：代码卫生

### 9. 死代码

| 文件 | 证据 |
|---|---|
| `backend/app/core/task_runner.py` | `InProcessTaskRunner` 只被实例化（`task_runner = InProcessTaskRunner()`），**从未被调用** |
| `xhs_utils/xhs_util.py` | 纯转发层：`from xhs_utils.xhs_pc.params import *`（向后兼容用，可删） |

### 10. 硬编码常量

**位置**：`scheduler_service.py:719-736`

- `auto_tasks_runner` 间隔 **60s 硬编码**（`due_publish_runner` 用的是可配置的 `interval_seconds`）
- `cookie_health_checker` 间隔 **2h 硬编码**

建议统一走配置。

### 11. 调度计时的一个偏差

**位置**：`scheduler_service.py:619-626`

`run_due_auto_tasks` 的 `next_run_at` 是在任务**执行完毕之后**才算的，任务执行耗时（搜索 + AI 改写 + 上传 + 发布，可能数分钟）被计入下一轮间隔。间隔 24h 的任务实际周期会略长于 24h。

### 12. 素材文件与数据库记录不同步

前端图片管理页删除只删库记录，`storage/media/` 下的**文件不会自动清理**（`files` 路由的删除只删行）。长期运行会堆积孤儿文件。

### 11'. 平台扩展的前端兜底较粗

`/platforms/:platformId` 统一落到 `ComingSoonPage`，扩展新平台需补 adapter + API + 页面三件套，无脚手架辅助。

## ✅ 做得好的工程实践（值得保持）

1. **适配层隔离** —— `adapters/` 是唯一碰 SDK 的地方，README 明示约束，替换 SDK 影响面可控
2. **签名单源 + 输出校验护栏** —— JS 单源、Python 不重复算法、畸形输出立即抛错
3. **Cookie 多版本加密存储** —— 只增不改、Fernet 加密、可回溯
4. **时区统一** —— 全项目 `shanghai_now()`，启动时幂等修历史数据
