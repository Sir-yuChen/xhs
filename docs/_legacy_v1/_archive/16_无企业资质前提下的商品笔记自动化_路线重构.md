# 16 · 无企业资质前提下的商品笔记自动化：路线重构

> 状态：待实机验证（阶段 0 未执行）
> 本文取代 `docs/15` 中依赖官方开放平台的 **①登录店铺、②店铺/商品列表** 两节；`docs/15` 的 ③生成、④发布、合规护栏、防重发设计**继续有效**。
> `docs/10/12/13`（无头浏览器）维持搁置。

---

## 0. 结论先行

企业资质这条路断掉之后，方案的重心发生了一次**偏移**，但不是崩塌：

| | 变更前（docs/15） | 变更后（本文） |
|---|---|---|
| 登录店铺 | 官方 OAuth，零逆向 | **人工登录 + Cookie 导入**（不做登录逆向） |
| 店铺/商品数据 | 官方开放接口 | 逆向 ark 只读接口 |
| 成本重心 | 申请资质、对接开放平台 | **抓包定参数 + 3 张新表** |
| 地基假设 | 有企业资质 | **个人店能否挂商品**（待验证） |

三个判断：

1. **官方通道确实关闭，且是机制性关闭**（§1.1），不是流程问题，无法绕。
2. **但逆向 ark 的成本比 `docs/15` 估计的低一个量级**——代码核查发现签名器与业务域解耦，接千帆不需要重写签名核心（§2）。
3. **地基假设从「有无企业资质」换成了「个人店能否获得商品分享权限」**。这一条如果为否，需求④（发布商品笔记）直接落不了地，方案要退到只有 ③（生成）——**这是阶段 0 必须最先验证的一件事**（§6.1）。

## 1. 约束的实际后果

### 1.1 官方路线为什么彻底关闭

`open.xiaohongshu.com` 的自用型应用，其设计前提是**创建应用时绑定千帆店铺即可自动完成企业认证**。这条链路的第一跳就是企业主体。没有企业资质 → 无法创建应用 → 拿不到 `client_id` → OAuth 全流程无法启动。

**这不是"申请难"的问题，而是入口本身不面向无主体开发者开放。** 因此无需再评估申请周期或替代资质。

### 1.2 但真正需要先确认的是「店铺」本身还在不在

平台的店铺主体分三类，**这个分类直接决定后续一切**：

| 店铺类型 | 资质要求 | 可经营类目 | 保证金 |
|---|---|---|---|
| 个人店 | 身份证 + 人脸验证，**免营业执照** | **受限**（服饰/家居/文创/数码配件等） | 1000 元起，可先发品后缴 |
| 个体工商户店 | 个体工商户营业执照 + 经营者证件 | 大多数普通类目 | 1000 元起 |
| 企业店 / 专卖 / 旗舰 | 企业营业执照等 | 全部 | 数千至数万 |

**这里有一个口径问题必须先澄清**：`个体工商户营业执照` 算不算你说的「企业资质」？

- 如果**个体工商户也拿不到** → 只剩个人店 → 可经营类目受限，且商品分享权限存疑（§6.1）
- 如果**个体工商户可以拿到** → 可选范围大很多，个体工商户店在千帆侧是正常商家主体

这个区别会显著改变方案的目标形态，建议先拍板。

### 1.3 一个连带风险

若最终落在个人店：商品类目被限制在服饰/家居/文创/数码配件一类，且**商品分享权限（笔记挂商品）能否开通，外部资料互相矛盾**（见附录 A）。这意味着需求②的"商品列表"可能只有几个受限类目的商品，需求④的挂载能力也待定。

## 2. 代码侧的决定性发现：接入千帆的成本被高估了

`docs/15` 判断"全逆向 ark 要新逆向一套签名，与移除算法维护的初衷背道而驰"。**这句话是错的**，代码核查推翻了它。四条证据：

### 2.1 签名器与业务域解耦（最关键）

`xhs_utils/xhs_pc/runtime.py:68-106`：

```python
def run_signer(api, data='', *, a1, cookie, b1, dsl_pair, tier, sign_context, ...):
    payload = {'api': api, 'data': data, 'cookie': cookie, 'a1': a1, ...}
```

签名输入只有 **path + body + cookie + 设备态**，**host 完全不参与**。域名差异只体现在 HTTP 层（`self.base_url + api`）。所以 `ark.xiaohongshu.com` 的接口对签名器而言，和 `edith.xiaohongshu.com` 的接口没有区别。

### 2.2 `XHSPlatformConfig` 就是为多业务域准备的扩展点

`xhs_utils/xhs_core/auth.py:15-84` 已定义两个实例：`PC_PLATFORM_CONFIG`（`app_id='xhs-pc-web'`）和 `CREATOR_PLATFORM_CONFIG`（`app_id='ugc'`）。新增千帆只是再加一个实例，不需要架构改动。

### 2.3 Cookie 已按 host 分域管理

`xhs_utils/xhs_core/cookies.py:44-171` 的 `HostCookieStore` 模拟浏览器同源策略，不同 host 只发送匹配的 cookie。**ark 域名的隔离cookie天然被支持**，无需改造。

### 2.4 已有先例：蒲公英正在复用 PC 签名栈

`apis/xhs_pugongying_apis.py:19-26` 直接构造 `PcDeviceProfile(cookies=cookies)` 来给 `pgy.xiaohongshu.com` 的接口签名。**"同一套 PC 指纹服务另一个业务域"这件事，本仓库已经做过一次并且跑通了。**

### 2.5 所以真正的未知量只剩三个

| 未知量 | 为什么重要 | 怎么定 |
|---|---|---|
| **`app_id`** | 参与 mns 签名（`SIGNATURE_ALGORITHM_DEEP_DIVE.md:265-266`、`:338` 的 `x3: appId`）与 DS 获取（`/api/sec/v1/ds?appId=xxx`） | 抓包 |
| **登录态 cookie 名** | 千帆可能用小红书账号 SSO，cookie 名或与 creator 的 `customer-sso-sid` 不同 | 抓包 |
| **是否携带 `x-s-common` / `x-rap-param`** | 决定走 `generate_xs` 还是 `generate_xs_xs_common` 路径 | 抓包 |

**结论：接千帆是一次"加配置 + 加接口"的工程，不是一次"重新逆向"。**

## 3. 官方关闭后的三条路线

| | 路线 A：全逆向 ark | 路线 B：不挂商品 | **路线 C：Cookie 导入 + 只读逆向（推荐）** |
|---|---|---|---|
| 登录店铺 | 逆向扫码/密码 | 不需要 | **人工登录后导入 Cookie** |
| 店铺列表 | 逆向 | 不需要 | 逆向（只读） |
| 商品列表 | 逆向 | 手动导入 CSV | 逆向（只读） |
| 生成笔记 | 现有 `ai_service` | 现有 `ai_service` | 现有 `ai_service` |
| 发布 | 逆向 ark 或复用 creator | 现有 creator | **现有 creator + `goods_info`** |
| 新增签名维护面 | 中（登录风控最重） | **零** | 低（只读接口） |
| 落地前提 | 店铺已存在 | 无 | 店铺已存在 |

### 3.1 为什么推荐 C：把「登录」降级为人工

**登录逆向是全链路中成本最高、风控最严、失效最频繁的一环。** 千帆登录入口是 `zhaoshang.xiaohongshu.com/seller/company?from=ark-login`，涉及账号体系、验证码、可能的滑块与设备风控。而它带来的收益只是"省去一次人工操作"。

改人工之后：
- 用户在自己浏览器正常登录千帆 → 导出 Cookie → 系统按现有 `account_cookie_versions` 机制加密存储
- 系统只负责**只读**拉取店铺/商品，失败即提示重新导入
- 完全复用 `HostCookieStore`、`PcDeviceProfile`、`XhsPcApiAdapter` 的现有形态，**构造签名可保持不变**

### 3.2 可能白捡一个便宜（待验证）

百度百科称「用户可直接使用小红书账号登录千帆，无需额外注册」。若成立，**千帆与 creator 可能共用 `.xiaohongshu.com` 域的 `a1` / `web_session`**——那么已接入的账号 Cookie 或许能直接请求 ark 接口，连人工导入都省了。这一条验证成本极低，列为阶段 0 第二项。

### 4.3 新增数据模型

```
shops
  id / platform_account_id(FK, sub_type="shop") / shop_id / shop_name
  seller_id / shop_type(个人店|个体户|企业) / status
  synced_at / raw_json

shop_products
  id / shop_id(FK) / item_id / title / price / stock / category
  images_json / detail_url / status(在架|下架|审核中) / synced_at / raw_json

product_note_jobs
  id / product_id(FK) / creator_account_id(FK) / draft_id(FK, nullable)
```

`idempotency_key` 是**防重发的核心**（写操作不可逆），沿用 `docs/15` 的设计：`{seller_id}:{item_id}:{creator_account_id}:{素材hash}`。

## 6. 阶段 0：全部只读，不改一行代码

### 6.1 第一优先：商品分享权限是否可得（**决定方案存亡**）

- 该账号是否已开通专业号？是否为个人店/个体户店？
- 创作者后台的笔记编辑页**是否出现「添加商品」入口**？
- 千帆商品管理页是否有「发布商品笔记」/「批量生成智能笔记」入口？

**若"添加商品"入口不存在 → 需求④不可实现 → 方案收缩为「生成 + 普通笔记发布」**（路线 B），这是完全不同的形态，必须最先知道。

### 6.2 第二优先：Cookie 复用性（可能省掉一整个模块）

用已登录的 creator 账号 Cookie（含 `a1` + `web_session`）直接请求一个 ark 只读接口，看是否返回 401。**通过则不需要新增登录交互。**

### 6.3 第三优先：抓包定三个参数

DevTools 过滤条件与字段清单：
- 过滤：`ark.xiaohongshu.com/api`
- 记录：请求头 `x-s` / `x-t` / **`x-s-common`（有无）** / `x-rap-param`（有无）/ `referer` / `origin`
- 记录：`x-s-common` 解码后的 `x3` 字段（即 `app_id`）
- 记录：Cookie 中与登录态相关的名字（对照 `web_session` / `customer-sso-sid`）

### 6.4 第四优先：`goods_info` 结构

创作者后台发布一篇带商品的笔记，抓 `post_note` 请求体，导出 `common.goods_info` 完整结构。

## 7. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **需求④落不了地** | 个人店可能无商品分享权限 | 阶段 0.1 先验，为否则走路线 B |
| **合规（最高）** | 商品笔记是商业推广内容，受广告法约束；个人店类目受限 | 违禁词库 + 一致性校验 + 人工审核闸门（长期保留） |
| **重复发布** | 写操作不可逆 | `idempotency_key` + 账号级锁 + 复用 `scheduler_service.py:181` 的补发幂等 |
| **Cookie 过期** | 人工导入的 Cookie 有生命周期 | 沿用现有 2h 巡检机制，失效即停并通知重新导入 |
| **千帆写操作风控** | 本次路线 C **不触碰 ark 写接口**，风险显著降低 | 保持只读边界 |
| **`app_id` 拿不到** | 若 ark 用了独立的签名体系而非通用 PC 栈 | 阶段 0.3 判定；若为独立体系，需重新评估 |
