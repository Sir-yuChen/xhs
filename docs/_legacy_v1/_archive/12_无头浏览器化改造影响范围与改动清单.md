# 底层无头浏览器化改造：影响范围与改动清单

> **文档日期**：2026-09-17
> **性质**：汇总分析（汇总 00–11 号文档结论 + 本次实测依赖数据）→ **改造影响范围与具体改动清单**
> **约束**：本文为分析与设计文档。依据用户「不要改动项目代码」的既有指示，**不修改任何源码、配置或依赖**；本文产出的是「要改什么」的清单，供评审后执行。
> **事实依据**：所有结论均可在代码中找到出处，引用格式 `path:line`。关键数字由本次会话实测（见 §7 数据来源）。

---

## 0. 汇总结论（三句话）

1. **可行**：签名算法层可以被无头浏览器整体替换。依据是**所有平台调用都被收拢在 6 个 adapter 文件里**，业务层（API 层、Service 层、调度器、模型）**零直接依赖** SDK。
2. **改造量比预想小**：核心改动集中在 **6 个 adapter 文件（共 435 行）+ 1 个新增浏览器进程池**。`xhs_utils/`（9,856 行）与 `apis/`（除登录态维护外）**整体可删**，不需要逐文件改造。
3. **不是全换**：**上传链路保持现状**（独立签名直传对象存储，不属于易变算法）；**发布链路建议保留现有 HTTP SDK**（`/web_api/sns/v2/note` 在 RAP 白名单内，浏览器化收益不足）；改造的主战场是**登录 + 采集 + 巡检**。

## 1. 当前架构分层与依赖边界（实测）

### 1.1 分层现状

```
frontend (12,392 行)
   │  HTTP API
   ▼
backend/app/api/          ← 131 个路由端点
   ▼
backend/app/services/     ← 业务逻辑（调度、AI、账号）
   ▼
backend/app/adapters/xhs/ ← 【关键边界】6 个 adapter，共 435 行
   ▼  ← 唯一越过此线的地方
apis/ + xhs_utils/        ← 【待替换层】9,856 行签名算法 + 接口封装
   ▼
小红书平台接口
```

### 1.2 实测依赖数据（本次会话扫描）

**后端越过 adapter 边界、直接 import SDK 的位置——只有 6 处，全部在 adapter 内：**

| 文件 | 行 | import 内容 |
|---|---|---|
| `adapters/xhs/pc_api_adapter.py` | `:13-14` | `XHS_Apis`, `XHSPcAuth` |
| `adapters/xhs/pc_login_adapter.py` | `:11,27,40,61,72` | `XHSLoginApi`（5 处） |
| `adapters/xhs/creator_api_adapter.py` | `:13-14, 88-95` | `XHS_Creator_Apis`, `XHSCreatorAuth`, `generate_x_rap_param` |
| `adapters/xhs/creator_login_adapter.py` | `:11,21,36,49,72,83` | `XHSCreatorLoginApi`（6 处） |
| `api/accounts.py` | `:28, :192` | `trans_cookies`（工具函数），`XHS_Creator_Apis` ⚠️ |
| `services/account_service.py` | `:12` | `trans_cookies`（工具函数） |

**⚠️ 两处越界（adapter 不是唯一边界，需一并改造）：**

- `api/accounts.py:192` —— API 层**直接** import `XHS_Creator_Aapis`。这是分层被穿透的地方，改造时必须一并下沉到 adapter。
- `services/account_service.py:12` —— 仅引用 `trans_cookies`（纯工具函数，与签名无关），**可保留**。

### 1.3 调度器与业务层的解耦程度（利好）

调度器**已经通过依赖注入**使用 adapter，不直接碰 SDK：

- `scheduler_service.py:262`：`run_due_publish_jobs_once(..., adapter_factory=XhsCreatorApiAdapter)` —— 默认参数注入
- `scheduler_service.py:120-159`：`_run_one_due_publish_job(..., adapter_factory)` 全程通过工厂取 adapter，`adapter_factory(_latest_account_cookies(db, account.id)).post_note(note_info)`
- `scheduler_service.py:439-465`：`XhsPcApiAdapter(cookies)` → `adapter.search_note(keyword, page=1)`

**含义**：切换实现只需替换 `adapter_factory` 指向新的浏览器实现，**调度器、Job、模型、前端全部不用改**。这是本方案改动量小的结构性原因。

### 1.4 签名层直接调用点（仅 2 处，均在 creator_api_adapter）

- `creator_api_adapter.py:95` → `generate_x_rap_param`
- `creator_api_adapter.py:147` → `api._request_params(...)`
- `creator_api_adapter.py:155` → `headers["x-rap-param"] = generate_x_rap_param(...)`

**这是发布链路保留现有 HTTP SDK 的技术理由**：`_post_uploaded_image_note` 的精确组装逻辑（`x-rap-param` + `post_loc` 删键等）是浏览器实抓对齐出来的，迁到浏览器后这些对齐知识仍然要用上，不能假设平台页面替你组装（见 10 号文档 §2.4）。

### 1.5 分层未强制（既有技术债，改造时一并处理）

- `services/` 反向 import `api/` 层：本次扫描**未检出**（此前记录的 3 处可能已重构或为间接引用，落地阶段需二次确认）。
- `pc_api_adapter.py` 与 `creator_api_adapter.py` 内的 SDK import 写在**方法内部（懒加载）**，而非模块顶部 —— 这是为了规避循环导入，改造时新 adapter 沿用此模式即可。

## 2. 三条链路的改造判定（逐条）

| 链路 | 判定 | 依据 | 改造量 |
|---|---|---|---|
| **登录** | ✅ **改，收益最大** | 远端 JSVMP 在本地 `vm` 执行是当前最脆弱一环（`xhs_pc_login_apis.py:346` `_initialize_security`；`websectiga_cli.js:204`）；浏览器天然执行平台下发混淆代码 | **中**（重写 `pc_login_adapter` + `creator_login_adapter`） |
| **采集** | ✅ **改，主战场** | 搜索/详情/评论均无 x-rap-param 依赖，页面上下文 fetch 即可（10 号 §2.2） | **中**（重写 `pc_api_adapter`） |
| **巡检** | ✅ **改** | `cookie_health_checker` 复用登录态，随登录链路一并迁移 | **小** |
| **发布** | ⚠️ **不改（建议）** | `/web_api/sns/v2/note` 在 RAP 白名单内；`_post_uploaded_image_note` 的精确组装逻辑迁移成本高、且是**写操作**，DOM 脆弱 + 重复发布即事故 | **0**（保留 `creator_api_adapter` 现状） |
| **上传** | ❌ **不改** | 独立签名 `getSignature` + 直传对象存储（`xhs_creator_apis.py:350/364`），不属于易变算法 | **0** |
| **自动运营** | ⚠️ **重新设计** | 浏览器是重资源，不适合 60s 轮询频率（`scheduler_service.py:719`） | **中**（改调度策略，不改 adapter） |

## 3. 改造清单：新增 / 修改 / 删除

### 3.1 新增（3 个模块）

| 模块 | 职责 | 位置建议 |
|---|---|---|
| **浏览器进程池** | 登录态池：每账号一个持久化 browser context，管理 cookie 生命周期 | `backend/app/services/browser_pool.py` |
| **PC 采集 adapter** | 实现 `XhsPcApiAdapter` 同名方法（`search_note`/`get_note_info`/`get_note_comments`/`get_user_notes`/`get_self_info`），内部走 CDP | `backend/app/adapters/browser/pc_adapter.py` |
| **登录 adapter** | 替换两个 login adapter：驱动真实登录页（扫码/Cookie 导入），登录态写入 `browser_pool` | `backend/app/adapters/browser/auth_adapter.py` |

**方法签名必须逐一对齐现有 adapter**（这是业务层零改动的前提）：

- `pc_api_adapter`：`search_note(keyword, page)` / `get_note_info(url)` / `get_note_comments(note_url)` / `get_user_notes(user_url)` / `get_self_info()`
- `creator_api_adapter`：`get_topic(keyword)` / `get_location_info(keyword)` / `get_published_notes()` / `upload_media(file_path, media_type)` / `post_note(note_info)`

### 3.2 修改（5 处，均为切换指向，不改业务逻辑）

| 文件 | 行 | 改动 |
|---|---|---|
| `scheduler_service.py` | `:262` | `adapter_factory=XhsCreatorApiAdapter` → 浏览器实现（发布链路保留原实现作为 fallback） |
| `scheduler_service.py` | `:439-465` | `XhsPcApiAdapter(cookies)` → 浏览器版 `XhsPcApiAdapter`（构造参数从 `cookies: str` 变为 `account_id`） |
| `api/accounts.py` | `:192` | **下沉** `XHS_Creator_Apis` 的直接使用到 adapter（修复分层穿透） |
| `api/platforms/xhs/*.py` | 全部 | 这些路由调 adapter 方法，**方法签名不变则无需改**；但构造调用处需适配新构造参数 |
| `adapters/xhs/__init__.py` | `:1` | 导出浏览器实现或保留双实现开关 |

### 3.3 删除 / 弃用（粗估 9,000+ 行）

| 范围 | 行数 | 前置条件 |
|---|---|---|
| `xhs_utils/`（auth/state/params/runtime、js 签名 JS、JSVMP 执行器） | ~9,856（含 JS 2,449） | **登录 + 采集 + 巡检迁移完成且稳定运行后** |

## 代码风格与约定（改造时遵守）

- adapter 的 SDK import 采用**方法内懒加载**（现有模式，规避循环导入）
- 新 adapter **必须保持方法签名与返回结构一致**（业务层零改动的前提）
- 构造参数从 `cookies: str` 迁移到 `account_id` 时，所有调用处需同步修改（已列 §3.2）
- `x-rap-param` 相关的发布组装逻辑**不得删除**（发布链路保留）

## 4. 数据落库链路（需求①的具体实现）

```
无头浏览器（加载平台真实页面）
   ├── 【被动通道】CDP Network.responseReceived 拦截平台真实返回
   │      └─ 适用：搜索结果、详情页、评论流 —— 页面自己发的请求
   └── 【主动通道】页面执行上下文内 fetch 同源接口
          └─ 适用：登录态接口、无 x-rap-param 的采集接口
   │
   ▼ CDP 回传
归一化层（复用现有 normalize_* 逻辑）
   ▼
业务库（21 张表，结构不变）
```

**关键约束**：
- 主动通道 **fetch 不会自动补 x-rap-param**（`rap.js:8` 逐请求按 url+body 现算、`xhs_pc_apis.py:135` 仅覆盖白名单路径）——故主动通道**只用于采集**，发布走平台原生请求或保留本地算
- 归一化逻辑（如 `normalize_comment_payload`）**必须保留**，浏览器返回的原始结构与入库结构不同

## 6. 风险与回退方案

| 风险 | 等级 | 应对 |
|---|---|---|
| 平台 DOM 结构变更导致驱动脚本失效 | **中** | 页面上下文 fetch 优先（比 DOM 驱动稳）；DOM 驱动仅用于登录扫码 |
| 浏览器资源占用（内存/CPU） | **中** | 按账号 lazy-open context，空闲超时关闭；限制并发 context 数 |
| 发布链路误迁移 | **高** | §3.3 已明确保留范围；迁移以「链路」为单位，发布不迁 |
| `x-rap-param` 边界判断未在真机验证 | **中** | 10 号文档已标注；落地阶段一/二**先实测**平台 RAP SDK 拦截边界 |
| 多副本调度不安全（既有风险） | 中 | APScheduler 无分布式锁（`scheduler_service.py:740`）；浏览器化后**必须单副本**或加速理锁 |

**回退方案**：因 adapter 通过 `adapter_factory` 注入，保留原 `adapters/xhs/` 实现作为 fallback —— 出现问题只需改回 `adapter_factory` 指向，**分钟级回退**。

## 8. 建议执行顺序（供排期）

1. **阶段 1 — 登录链路迁移**（`browser_pool` + `auth_adapter`）→ 稳定后删登录相关 SDK
2. **阶段 2 — 采集链路迁移**（`pc_adapter`，双通道数据落库）→ 稳定后删采集 SDK
3. **阶段 3 — 巡检 + 自动运营调度策略调整**（降频：60s → 浏览器友好的频率）
4. **阶段 4 — 清理**（删除 `xhs_utils/` 与无用 `apis/`，保留发布/上传链路）

**每阶段结束的稳定运行标准**：新实现连续运行 ≥7 天无签名错误，且 `adapter_factory` 回退开关验证可用。
