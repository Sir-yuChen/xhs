# 无头浏览器方案可行性分析

> **方案命题**：弃用自维护的签名算法层（`xhs_utils/` + Node JS 运行时），改为**整合小红书平台浏览器接口**——无头浏览器加载平台真实页面，由平台自己的 JS 计算签名，自定义前端页面驱动交互并把接口数据同步落本地库。
>
> - **分析日期**：2026-09-16（2026-09-17 补充实测延迟与 x-rap-param 边界，见 §2.2 / §3.1.1）
> - **性质**：可行性分析 + 利弊对比，**不改动项目任何代码**
> - **事实依据**：本文所有结论均可在代码中找到出处，见 [08_调用链路与扩展点.md](./08_调用链路与扩展点.md)

---

## 0. 一句话结论

**可行，且是正确的方向；但不是「换一个 HTTP 客户端」，而是「换整个交互范式」。**

得分链路来看：

| 链路 | 可行性 | 收益 | 关键约束 |
|---|---|---|---|
| **登录**（扫码/验证码/Cookie 导入） | ✅ **高度可行** | ★★★★★ | 平台下发混淆 JSVMP 由浏览器天然执行，**这是当前最脆弱的一环** |
| **采集**（搜索/详情/评论） | ✅ **可行** | ★★★★☆ | 需自定义页面驱动 + 数据落库 |
| **巡检**（Cookie 健康检查） | ✅ **高度可行** | ★★★★☆ | 复用登录态即可 |
| **发布**（图集笔记） | ⚠️ **有条件可行** | ★★★☆☆ | 话题/地点/post_loc 业务逻辑需保留 |
| **上传**（素材到 ROS） | ❌ **不建议浏览器化** | ★☆☆☆☆ | 独立签名 + 直传对象存储，浏览器化成本远高于收益 |
| **自动运营**（无人值守管线） | ⚠️ **需重新设计** | ★★☆☆☆ | 浏览器是重资源，不适合每 60s 一次的频率 |

## 1. 方案形态：三种可能的架构

### 形态 A：浏览器宿主 + 自定义页面（推荐的方案二本体）

```
┌──────────────────────────────────────────────────────────────┐
│  后端 FastAPI（不变）                                          │
│    ├── 业务库（notes/publish_jobs/... 不变）                   │
│    ├── 适配层 adapters/browser/（替换 adapters/xhs/）          │
│    └── 浏览器进程池 services/browser_pool.py（新增）           │
└──────────────────────────────────────────────────────────────┘
     ↓ CDP / Playwright
┌──────────────────────────────────────────────────────────────┐
│  无头浏览器（每个平台账号一个持久化 context）                   │
│    ├── 加载平台真实页面（登录页 / 搜索页 / 创作者页）           │
│    │   → 平台自己的 JS 计算 x-s/x-t/x-s-common（不再需要 xhs_utils/）│
│    │   → 白名单路径的 x-rap-param 由平台页面自己的请求顺带完成  │
│    └── 注入自定义前端脚本（browser_pages/*.html + inject.js）  │
│        → 驱动搜索 / 解析接口响应 / 回传后端落库                 │
└──────────────────────────────────────────────────────────────┘
     ↓ 平台真实接口（浏览器内发起，带真实签名）
小红书
```

**核心机制**：浏览器加载真实页面后，页面里的平台 JS 会接管所有签名计算。自定义脚本只需**驱动 DOM 交互**（填关键词、点搜索、滚动翻页）或**直接在页面上下文里 `fetch` 同源接口**（此时签名由平台 JS 的拦截器自动加上），然后通过 CDP 把响应数据回传后端落库。

### 形态 B：混合模式（浏览器只补签名，请求仍由后端发）

```
后端需要发请求 → 让浏览器在页面上下文里 fetch 同一接口 → 拿到签名头
             → 后端用同样的 url+body+签名头直接发（curl_cffi）
```

**这条路径的致命问题**：**x-s 签名覆盖请求体**（`sign.js:89` `c = api + dataStr`）。同一签名只能用于**完全相同的 body**。后端只要有任何参数变化（分页 page、关键词），就必须回到浏览器重算一次——**等于每个请求都要过浏览器**，那还不如直接让浏览器发（形态 A）。

> **结论：混合模式（B）不成立**。这不是实现难度问题，是签名覆盖 body 这一事实决定的。

### 形态 C：浏览器 + CDP 网络拦截（纯被动采集）

不做任何页面驱动，只让浏览器正常浏览，**监听 CDP `Network.responseReceived` 把接口数据扒下来落库**。

- 优点：零侵入，完全不碰签名
- 缺点：**只能采集，不能发布**；数据取决于浏览器浏览了什么
- 适用：只做采集的场景，或作为形态 A 的数据兜底通道

## 2. 可行性分析（分链路）

### 2.1 登录链路：✅ 收益最大

**现状的脆弱性**（`apis/xhs_pc_login_apis.py:_initialize_security`）：

登录冷链要依次执行：拉蜜罐程序 → 拉验证码程序 → 拉 SEM SDK → **拉远端 DS 程序并正则提取 `getdss()`** → **拉远端 sec 程序并在本地 `vm.runInThisContext` 执行生成 websectiga**。

这些程序是**服务端下发的混淆 JSVMP**，平台每次更新都可能改变。项目自己的注释承认这一点（`xhs_pc/auth.py:152`）：

> `websectiga` is not a zero-host pure algorithm... it is still an environment adapter and **may require maintenance after a release change**.

**浏览器方案下**：这些程序**由平台自己的页面在真实浏览器里执行**，项目完全不需要维护。扫码和验证码流程也变成「浏览器打开登录页 → 用户扫码/输码 → 浏览器拿到 cookie」，不再需要自己生成 `a1`/`webId`、不需要自己初始化安全 cookie。

**Cookie 落库**：`account_cookie_versions` 表设计完全兼容——浏览器登录成功后，从 context 导出 cookie 字符串，Fernet 加密后追加新版本即可。**表结构不用改**。

**这一环的收益是决定性的**：当前项目里「登录失败 / Cookie 拿不到」的故障，绝大多数出在这条冷链上。

### 2.2 采集链路：✅ 可行

两种驱动方式：

**方式一：DOM 驱动**（模拟人工操作）
```
浏览器打开搜索页 → 填入关键词 → 点搜索 → 等待结果渲染 → 解析 DOM / 拦截接口响应 → 落库
```
- 优点：行为最接近真人，风控风险最低
- 缺点：慢（要等渲染）、脆弱（DOM 结构变了选择器就失效，但比签名算法失效好维护得多）

**方式二：页面上下文 fetch**（推荐）
```
浏览器打开平台页面（让平台 JS 加载完成）
  → 自定义脚本在页面上下文内 fetch('/api/sns/web/v1/search/notes', {...})
  → 平台的请求拦截器自动加上 x-s/x-t/x-s-common（你完全不用管）
  → 响应直接拿，通过 CDP 回传后端落库
```
- 优点：**不需要解析 DOM**，不需要等渲染，拿到的是结构化 JSON
- 优点：x-s/x-t/x-s-common 由平台拦截器算，**永远正确**
- 缺点：需要确认平台 JS 拦截器覆盖了你 fetch 的接口（一般同源 XHR 都覆盖）
- ⚠️ **例外：x-rap-param 不会由拦截器自动补**。见下方「x-rap-param 不是平台自动加的」。

> 方式二是本方案的核心：**「整合平台浏览器接口」的实际含义就是——在平台页面的执行上下文里发请求，让平台自己签名。**

**x-rap-param 不是平台自动加的**（重要，影响方式二的适用范围）

平台在**页面自己发起的**请求上才会带 x-rap-param。本仓库的 RAP 实现（`xhs_utils/xhs_pc/js/rap.js`）是对平台该行为的**逆向后纯算复刻**——它是一个**按请求现算**的参数，不是一个全局拦截器能力。证据：

- `xhs_utils/xhs_pc/js/rap.js:7-9`：`RequestHash = xxHash32(url_pathAndBeyond + jsonBody, seed=0)`，即 x-rap-param 的输入包含**完整 url + 完整 body**。
- `xhs_utils/xhs_pc/js/rap.js:111-122`（`buildRapPure`）：发布接口用**完整 https URL** 求 hash。
- `xhs_utils/xhs_pc/js/reference_profile.json` 里存在 `__rap_hijack_installed__` / `__rap_report__` 等 RAP SDK 自检键，说明它是页面内 SDK 的运行时状态，不是静态常量。
- `apis/xhs_pc_apis.py:135`（`_request_params`）：x-rap-param 只对**白名单路径**（`_RAP_PATH_MARKERS`：search/notes、user_posted、feed、comment/post）生成，且**每次请求都要现算**——平台侧同理，不是一次签名全局复用。

**结论**：方式二适用于**不需要 x-rap-param 的接口**（搜索、详情、评论、用户笔记、登录态相关接口）。一旦目标路径在 RAP 白名单内，要么走方式一（让平台页面自己发请求，平台自然挂上 x-rap-param，用 CDP `Network.responseReceived` 把响应扒下来），要么仍然需要本地算 x-rap-param。**Creator 发布接口（`/web_api/sns/v2/note`）属于后者**，这是 §2.4 发布链路只能「有条件可行」的直接原因。

（本节为 2026-09-17 补充。技术判断基于上述仓库内代码事实：一个参数若按 url+body 逐请求现算、且只覆盖白名单路径，就不可能由一个全局拦截器对外部 `fetch()` 透明地补上。**未在真实浏览器内直接验证**平台 RAP SDK 的拦截边界，落地阶段一/二时需先实测确认。）

**落库对接**：现有的 `_normalize_search_item` / `handle_note_info` 归一化逻辑可以直接复用，后端 `notes` 表不用改。

### 2.3 巡检链路：✅ 高度可行

现状是调度器每 2h 调 `adapter.get_user_info` 探活。浏览器方案下，**只要 context 的 cookie 有效，打开任意页面看是否跳登录页即可**，甚至可以直接判断 `document.cookie` 里 `web_session` 是否存在。比发接口更稳，且完全不消耗接口配额。

### 2.4 发布链路：⚠️ 有条件可行

**业务逻辑必须保留**（与签名无关，`creator_api_adapter.py:_post_uploaded_image_note`）：
- 话题解析后拼接 `#话题名[话题]#` 到 desc
- 未选地点时**必须删掉 `post_loc` 键**（空对象会被服务端参数错误打回）
- 发布选项 topics/location/privacy_type 的组装

**在浏览器里发布有两条路**：

| 路径 | 做法 | 评价 |
|---|---|---|
| 页面上下文 fetch | 打开创作者笔记发布页 → 在页面上下文 fetch 发布接口 | x-s/x-t/x-s-common 由平台算，但 **x-rap-param 不会自动补**（见 §2.2），且**业务体的拼装规则仍需自己写**，要精确对齐平台版本 |
| 驱动发布页表单 | 打开发布页 → 自动填标题/正文 → 上传图片 → 点发布 | 最稳（发布接口由平台页面自己发，x-rap-param 自然带上），但最慢，且 DOM 脆弱 |

> 对发布链路，**「驱动表单」反而比「页面上下文 fetch」更省事**：发布接口在 RAP 白名单内，走平台自己的请求能连带把 x-rap-param 省掉；走 fetch 则必须本地算 x-rap-param（本仓库已有 `generate_x_rap_param`，`xhs_pc/params.py:213`）。这是采集（无 x-rap-param）与发布（有 x-rap-param）两条链路结论不同的技术根源。

**风险**：发布是**写操作**。采集失败重试无害，发布失败/重复发布是真实事故。当前方案 `_post_uploaded_image_note` 的精确组装（含 `x-rap-param`）是浏览器实抓对齐出来的，迁到浏览器方案后**这些对齐知识仍然要用上**，不能假设平台页面会替你组装。

### 链路 2.5：上传链路：❌ 不建议浏览器化

这是**最不适合**浏览器化的一环（`apis/xhs_creator_apis.py:upload_media`）：

1. **签名独立**：用 `xhs_creator_signature.js` 的 `getSignature`（PyExecJS），与主签名体系无关——它本来就不随平台主签名易变
2. **直传对象存储**：`PUT /spectrum/{fileIds}` 直连 ROS，不经业务网关
3. **二进制流**：浏览器页面里上传走平台 OSS SDK，**注入自定义二进制流的成本远高于直接 HTTP PUT**

> **建议：上传链路保持现状**（PyExecJS + 独立签名）。这不是"易变算法"，是稳定的对象存储上传协议。保留这一环不影响「弃用易变签名层」的目标。

### 2.6 自动运营链路：⚠️ 需重新设计

现状是 APScheduler 每 60s 扫一遍 `auto_tasks`（`scheduler_service.py:604`），算上执行耗时，实际是**常驻循环**。

浏览器是**重资源**（每个 context ~150-300MB 内存），不适合 60s 频率常驻。需要改为：

- **降低频率**：自动运营本来就是「批量生产内容」，间隔从 60s 轮询改为按任务的 `schedule_interval_hours`（最小 1h）调度
- **按需启动浏览器**：到点才拉起浏览器 context，跑完管线（搜索→改写→上传→发布）就销毁
- **浏览器池化**：登录态用 `storageState` 持久化（cookie 落 `account_cookie_versions`），context 按需创建

这不是方案的缺陷，是**资源模型从「轻量 HTTP 客户端」变成「重量浏览器」后的必然适配**。

## 3. 切换前后利弊对比

### 3.1 维度对比表

| 维度 | 现方案（自维护签名） | 方案二（无头浏览器） | 判定 |
|---|---|---|---|
| **单链路请求延迟** | 本地签名 **~50-105ms**（见下方实测）+ 网络往返；热路径纯 HTTP 约 **100-300ms** | 冷启动到就绪 **~325ms**、页面导航 **~2.1s**、同源页面内 fetch **~205ms/次**（见下方实测） | **现方案胜**（约 5-10x，文档原估 5-15x 量级正确） |
| **并发能力** | 高（异步 HTTP，连接池） | 低（浏览器进程/CPU/内存瓶颈） | **现方案胜**（数量级差） |
| **单请求资源** | ~MB 级（Node 子进程偶发） | ~150-300MB / context | **现方案胜** |
| **维护成本** | 高（平台更新 → 算法失效 → 人工逆向） | 低（平台自己算，**x-s/x-t/x-s-common 零维护**） | **方案二胜**（核心收益） |
| **失效响应** | 算法失效 → 全量接口同时不可用 | 平台更新 → 页面 JS 变 → 浏览器仍执行 | **方案二胜** |
| **失效恢复** | 需重新逆向 + 验证（天-周级） | 平台自己更新页面，**自动恢复** | **方案二胜**（决定性） |
| **风控风险** | 中（指纹是静态模板，可被识别） | 低（真实浏览器，真实指纹） | **方案二胜** |
| **登录链路稳定性** | 低（冷链 JSVMP 本地执行，最脆弱） | 高（平台页面原生执行） | **方案二胜** |
| **部署复杂度** | Node + Python + curl_cffi | + 浏览器运行时（Chromium ~200MB 镜像） | **现方案胜** |
| **多账号隔离** | cookie 字符串天然隔离 | 每账号一个 context，天然隔离 | 平 |
| **平台扩展成本** | 需写整套 SDK + 签名 | **加载平台页面即可，SDK 层可省** | **方案二胜** |
| **写操作（发布）可控性** | 高（请求体精确组装） | 中（需对齐平台页面行为，且 x-rap-param 仍需自理，见 §2.2） | **现方案胜** |
| **可观测性** | 高（每个请求可见） | 中（需 CDP 拦截 + 日志建设） | **现方案胜** |

#### 3.1.1 延迟实测（2026-09-17，本机）

**现方案 —— 本地签名开销**（`subprocess` 起 Node，跑项目自带 JS）：

| 算法 | 中位 | 范围 | 说明 |
|---|---|---|---|
| `xhs_utils/xhs_core/js/sign.js`（x-s / x-t / x-s-common） | **49.2ms** | 47.5-124.9ms | 每个业务请求都要起一次（`run_signer`，`xhs_pc/runtime.py:108`） |
| `xhs_utils/xhs_pc/js/rap_cli.js`（x-rap-param） | **54.9ms** | 52.5-218.9ms | 仅 RAP 白名单路径（`apis/xhs_pc_apis.py:135`） |
| **两者合计** | **103.7ms** | 102-343.8ms | 即一个 homefeed 类请求的**本地签名成本**，不含网络往返 |

> 注：b1 有会话级缓存（`xhs_pc/state.py:550` `current_b1`，命中时不再起 Node），所以多数请求只付 sign.js 一次约 49ms；首次请求或 profile 切换时额外付一次 b1 生成（约 45ms，`b1.js`）。

**方案二 —— 真实无头 Chrome（Chrome 152，CDP，本机实测）**：

| 环节 | 中位 | 说明 |
|---|---|---|
| 冷启动浏览器到调试端口就绪 | **325ms** | 进程拉起到 `/json/version` 可用 |
| 新建页面 + WebSocket 握手 | **161ms**（握手）+ 30ms（HTTP 建页） | 池化后此项可摊销 |
| 页面导航（真实 https 站点，含 TLS + 下载） | **~2.1s** | 每次新页面都要付 |
| 页面内同源 fetch（含一次真实网络往返） | **205ms** | 这是「签名已由平台算好」后的单请求成本 |
| CDP `Runtime.evaluate` 往返（无业务负载） | **<1ms** | CDP 通道本身不是瓶颈 |

**换算**：方案二一个采集请求 ≈ 导航 2.1s（首次，页面缓存后可降到数百 ms）+ 每请求约 205ms；现方案 ≈ 每请求 49-105ms 本地签名 + 网络往返。**延迟差距约 5-10 倍**，与原表「5-15x」的估计一致，此处用实测数字坐实。

**量化结论**：对本项目的负载（采集手动触发、发布小时级、巡检 2h），即使按最坏情况每请求 2-3s，单次自动运营管线（搜索 1 次 + 上传 N 张 + 发布 1 次）也在 10-30s 量级，完全可接受。**但若未来要转向高频采集（>1 QPS 常驻），方案二的导航与页面开销会成为真实瓶颈**，这是 §4「即时响应」边界的量化依据。

### 3.2 核心权衡

**方案二牺牲了「性能与并发」，换来「维护成本归零 + 失效自动恢复」。**

这个交换值不值，取决于业务特征：

- **如果业务是「大批量高频采集」**（每天数万次接口调用）→ 现方案的性能优势不可放弃，方案二不合适
- **如果业务是「运营人员驱动 + 中低频 + 长期可用性优先」**（本项目的实际形态：搜索入库 → 改写 → 定时发布，小时级）→ **方案二的收益远大于代价**

**本项目的实际负载特征**（从 `scheduler_service.py` 读出）：
- 采集：用户手动触发 / 按关键词批量，**非高频常驻**
- 发布：小时级调度（`schedule_interval_hours` 默认 24）
- 巡检：2h 一次
- 自动运营：分钟级扫描但**执行是小时级任务**

→ **结论：这个项目的负载特征适合方案二。** 性能损失在实际业务中几乎感知不到，而维护成本归零是刚需。

## 4. 方案二做不到什么（诚实边界）

| 环节 | 为什么做不到 |
|---|---|
| **绕过服务端风控** | 无头浏览器解决的是「签名正确」，不是「行为可信」。高频/异常行为仍会被风控。反检测（stealth 补丁、行为模拟）是**独立且持续**的工作量 |
| **设备指纹一致性** | `reference_profile.json` 里的静态指纹模板是"假"的；真实浏览器的指纹是真的。**但**平台可能做「浏览器指纹 vs Cookie 设备标识」一致性校验——用真实浏览器反而更容易一致 |
| **上传链路的简化** | 见 §2.5，对象存储直传不适合浏览器化 |
| **零维护** | 平台改页面结构 → 自定义脚本的选择器失效（比签名算法好维护，但不是零） |
| **绕过验证码** | 无头浏览器不自动解验证码；触发验证码时仍需人工或第三方服务 |
| **即时响应** | 浏览器方案不适合做需要 <1s 响应的实时接口 |

## 5. 过渡路线（三个阶段）

### 阶段一：登录链路先行（收益立竿见影，风险最低）

**范围**：只用无头浏览器做**登录**（扫码 + 手机验证码），拿到 cookie 后落 `account_cookie_versions`。

- 复用现有表结构、加密存储、健康巡检
- 现有 SDK 的登录冷链代码**保留但不作为主路径**，作为降级方案
- **可立即消除当前最常见的登录失败类故障**

验证点：登录成功率、cookie 有效期分布、和现方案的对照。

### 阶段二：采集链路迁移（页面上下文 fetch）

**范围**：搜索 / 详情 / 评论 / 用户笔记，用「页面上下文 fetch + CDP 回传 + 落库」。

- 归一化逻辑（`_normalize_search_item` / `handle_note_info`）原样复用
- 采集走浏览器，**上传/发布仍走现方案**
- 沉淀浏览器池、storageState 持久化、CDP 数据通道

验证点：采集数据完整率（字段对齐）、单次采集耗时、稳定性（7 天无算法维护）。

### 阶段三：发布链路迁移（最后做，写操作最慎重）

**范围**：发布中心 + 自动运营。

- 保留话题/地点/post_loc 业务组装逻辑
- 自动运营调度频率从 60s 轮询改为按 `schedule_interval_hours` 调度 + 按需拉起浏览器
- 上传链路**保持现状**（PyExecJS 独立签名）

验证点：发布成功率对照、重复发布防护（浏览器方案的并发控制更要做扎实）。

| 层 | 变化 |
|---|---|
| `adapters/` | `adapters/xhs/` → 并存 `adapters/browser/`（按链路灰度切换） |

**关键设计约束**（无论怎么实施都要遵守）：
1. **适配层接口不变** —— `adapters/browser/` 要实现和 `adapters/xhs/` 同样的方法签名，上层路由零改动
2. **表结构不变** —— 落库的是归一化后的数据，数据来源切换对上层透明
3. **上传链路不动** —— 见 §2.5
4. **现方案保留为降级路径** —— 灰度期间可按链路回切

## 7. 最终判定

| 问题 | 判定 |
|---|---|
| 方案是否可行？ | **可行**，分链路可行性见 §0 |
| 混合模式（浏览器补签名 + 后端发请求）可行吗？ | **不可行**，x-s 覆盖请求体，见 §1-B |
| 「页面上下文 fetch」能完全替代签名层吗？ | **不能**。x-s/x-t/x-s-common 会由平台拦截器补上，但 **x-rap-param 不会**——它按 url+body 逐请求现算、且只覆盖白名单路径（含 Creator 发布接口），仍需本地算，见 §2.2 |
| 是否值得切换？ | **值得**，本项目负载特征（小时级、中低频）下，x-s 系算法维护归零的收益远大于性能损失（实测约 5-10x，见 §3.1.1） |
| 优先做哪？ | **登录链路**（阶段一），收益最大风险最低 |
| 有哪些做不到？ | 见 §4，最主要是不能绕过服务端风控、上传链路不适合 |
