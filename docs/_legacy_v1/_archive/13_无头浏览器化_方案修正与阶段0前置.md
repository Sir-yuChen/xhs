## 1. 为什么这个方向值得做（一句话复述，不展开）

`apis/ + xhs_utils/` 约 9,856 行里，真正**易变**的只有「x-s / x-t / x-s-common / b1 / MNS / profileData / websectiga / DS」这一类**平台每次发版都可能变**的算法。这部分在浏览器方案下由平台自己的页面 JS 计算，**维护成本归零**。本项目是小时级中低频负载，用 5-10x 的延迟换取「签名算法零维护 + 失效自动恢复」，交换比划算。

## 2. 生死假设：页面内 fetch 到底会不会被自动签名

### 2.1 这个假设为什么是生死假设

10 号文档 §2.2 的核心机制是：

> 自定义脚本在页面上下文内 `fetch(...)` → 平台的请求拦截器自动加上 x-s / x-t / x-s-common

**这个机制成立与否，决定整个方案的实现形态：**

- **成立** → 采集链路只是「在页面里发 HTTP」，实现极简（注入一段 JS 即可）
- **不成立** → 需要改为「劫持平台自己的请求器」（包装 `XMLHttpRequest` / `fetch`，把我们的参数喂给平台的签名函数，或直接调用平台暴露的签名函数），实现复杂度上一个台阶

10 号文档自己也标注了这一点未在真机验证（`10_...md:129`：「未在真实浏览器内直接验证平台 RAP SDK 的拦截边界」）。**这必须在写任何 adapter 之前先跑掉。**

### 2.2 为什么不能想当然认为成立

`fetch` 是浏览器原生 API，平台**无法自动**给一个原生 `fetch` 加自定义请求头。平台只能通过两种方式让签名生效：

1. **改写全局 `fetch` / `XMLHttpRequest`**（monkey-patch）——若平台这么做，则裸 `fetch` 也生效
2. 在自己的请求封装里加头——则裸 `fetch` **不生效**，必须走平台的封装

本仓库的 RAP 侧证据倾向于「平台是按需现算、不是全局透明拦截」：`xhs_utils/xhs_pc/js/rap.js:7-9` 的 `RequestHash` 输入含完整 url + body，`apis/xhs_pc_apis.py:135` 只对白名单路径生成。**但这是对平台行为的旁证，不是直接证据，必须实测。**

### 2.3 判定 spike（建议作为「阶段 0」的第一个动作）

**目标**：用半天时间，在不改项目代码的前提下，拿到 3 个 yes/no 答案。

**准备**：真实 Chrome（`channel="chrome"`，非 headless）、持久化 `user-data-dir`、手动登录 `www.xiaohongshu.com` 一次。

**步骤**：

| 步 | 动作 | 要拿到什么 |
|---|---|---|
| 1 | 注入 hook：包装 `window.fetch` 和 `XMLHttpRequest.prototype.open/send`，记录每条请求的 `method / url / 请求头` | hook 生效 |
| 2 | 在页面里**手动**搜索一个关键词 | 平台自己发的 `/api/sns/web/v1/search/notes` 请求头里**有没有** `x-s` / `x-t` / `x-s-common` / `x-rap-param` |
| 3 | 在页面上下文里对**同一接口、同一 body** 发一次**裸** `fetch` | **返回码 / 返回体**——成功 or `461/406/{"success":false}` |
| 4 | 若第 3 步失败：枚举 `window` 上的可疑签名入口（历史版本 web 端存在形如 `_webmsxyw(url, data)` 的签名函数），尝试用它给**任意** (url, body) 签名后再自行 fetch | 是否存在**可复用、非白名单、任意 body 可用**的签名入口 |
| 5 | 对 RAP 白名单路径（如 Creator 发布 `/web_api/sns/v2/note`）重复第 2-4 步 | `x-rap-param` 是否由平台层补；若需自算，则保留 `generate_x_rap_param` 的判断成立 |
| 6 | 用第 1 步的 hook 记录**平台自己**的发布请求头 | 发布接口的完整头部契约（用于对照现有 `_post_uploaded_image_note` 的组装） |

**三种结论对应的实现路径：**

| spike 结果 | 实现路径 | 对方案的影响 |
|---|---|---|
| 第 3 步成功 | 裸 `fetch` 可用（10 号文档方式二成立） | 采集链路实现最简；发布仍需确认 x-rap-param |
| 第 3 步失败、第 4 步成功 | **劫持平台请求器**：调用平台的签名入口签名，再由我们发请求 | 增加「定位并稳定引用平台签名函数」的维护点（但它比逆向算法稳定得多） |
| 第 3、4 步均失败 | 只能**DOM 驱动**（让平台页面自己发请求，CDP 被动拦截响应） | 采集链路变慢、变脆；10 号文档形态 C 成为唯一路径 |

> **这个 spike 的产出必须写回文档**，因为它同时决定 §5 中「`generate_x_rap_param` 能否删」和「发布链路能否迁移」这两个问题。

## 3. 修正：「API 端点零改动」不成立

12 号文档 §5 称「131 个 API 端点零改动」，但同文 §3.2 又列出需要改调用处——两处表述冲突。经代码核对，**确实必须改的有 4 处**：

### 3.1 登录会话的两道硬校验会挡住浏览器方案

```
backend/app/api/login_sessions.py:224
    if session.sub_type not in {"pc", "creator"} or not session.qr_id:
        raise HTTPException(400, "Unsupported login session")

backend/app/api/login_sessions.py:229
    if not session.code:
        raise HTTPException(400, "Unsupported login session")
```

`qr_id` 与 `code` 是**平台扫码接口的内部概念**，是现有 SDK（`adapters/xhs/pc_login_adapter.py:9` `create_qrcode` 返回 `qr_id` / `code`）才有的东西。浏览器方案下没有这两个值。

**好消息**：模型层不用改——`backend/app/models/login_session.py:23-24` 里 `qr_id` / `code` 都是 `nullable=True`，`login_session.py:19` 的 `status` / `login_method` 也够用。

**要改的**：把上面两道校验放宽（例如有 `qr_url` 或新增的 context key 即可通过），或让浏览器版 `create_qrcode` 塞入占位值。**推荐前者**，语义更干净。

### 3.2 前端登录面板可以**不改**（这一点比 12 号文档设想的乐观）

现有 QR 登录的前端契约是：

```
frontend/src/components/account/qr-login-panel.tsx:41   createXhsPcQrLoginSession(...)
frontend/src/components/account/qr-login-panel.tsx:63   pollXhsLoginSession(session_id)
frontend/src/components/account/qr-login-panel.tsx:66   qr_image_data_url
```

后端在 `login_sessions.py:174` 返回 `qr_image_data_url`（由 `qr_url` 本地生成图片）。

**浏览器方案下可以保住这个契约**：打开平台登录页 → **对二维码区域截图** → 编码为 data URL 返回。前端一行都不用改。

> 结论修正：12 号文档「前端零改动」在**登录页**这一点上其实**可以成立**，但成立的前提是「截图二维码」这一实现选择，而不是「浏览器会给你 qr_url」。这是一个必须写进设计说明的约束。

### 3.3 手机验证码登录：建议不迁移

`adapters/xhs/pc_login_adapter.py:59` `create_phone_session` / `:70` `confirm_phone_login` 是纯接口调用。浏览器化后要走登录表单，而 **web 端手机号登录必经滑块验证码**，headless 下无法自动通过（10 号文档 §4 已原则性提到「不自动解验证码」，但没有指出**手机登录是必然撞上的路径**）。

**建议**：浏览器化后**扫码作为唯一主路径**；手机验证码登录保留在旧 SDK 路径（它是纯接口，不依赖浏览器），或直接下线。这一条要提前决定，否则会在阶段 1 卡住。

### 3.4 adapter 构造参数

`XhsPcApiAdapter(cookies)` 的调用点（如 `scheduler_service.py:439`）需要在浏览器方案下拿到「某个账号的浏览器 context」。**本文 §4 的建议可以把这个改动压到最小甚至为零。**

## 4. 架构修正建议：独立浏览器网关，而非进程内 browser_pool

12 号文档建议在 `backend/app/services/browser_pool.py` 里管理浏览器。**建议改为独立进程**：

```
【12 号文档建议】                        【本文建议】
FastAPI 进程                             FastAPI 进程（无状态，可多 worker）
  ├── api/                                ├── api/
  ├── services/                           ├── services/
  ├── adapters/browser/                   ├── adapters/browser/  ← 退化为 HTTP 客户端
  └── services/browser_pool.py  ← 问题      └── (无浏览器代码)
        └── Chromium                            ↓ HTTP (127.0.0.1:9xxx)
                                                浏览器网关进程（单实例、有状态）
                                                  ├── context 池（每账号一个）
                                                  ├── storageState 持久化
                                                  └── Chromium / Chrome
```

### 4.1 为什么

| 问题 | 进程内 browser_pool | 独立网关 |
|---|---|---|
| 多 worker / 多副本 | 每个 worker 各起一套浏览器，**登录态分裂、定时任务重复执行** | 浏览器状态单点，与后端副本数解耦 |
| 浏览器崩溃 | 带走 API 进程 | 只挂网关，后端返回 5xx 由前端重试 |
| 内存/CPU | 与 API 争资源 | 可独立限额、独立扩容 |
| Docker | 后端镜像被迫塞进 Chromium（~200MB+） | 后端镜像不变，网关单独一个服务 |
| 复用给 `XhsSkills` | 不行 | 可以（网关是语言无关的 HTTP 服务） |
| 调用方改动 | adapter 内嵌 Playwright（同步/异步纠缠） | adapter 退化为 `httpx` 调用，**方法签名可完全不变** |

### 4.2 关键收益：构造签名可以不变

`XhsPcApiAdapter(cookies)` 的现有调用点无需改动，只要网关**按 cookie 指纹/account_id 复用 context**：

```python
# adapters/browser/pc_adapter.py —— 方法签名与现有一模一样
class XhsPcApiAdapter:
    def __init__(self, cookies: str, account_id: int | None = None): ...
    def search_note(self, keyword, page=1, **filters) -> Any: ...
    def get_note_info(self, url: str) -> Any: ...
    def get_note_comments(self, note_url: str) -> Any: ...
    def get_user_notes(self, user_url: str) -> Any: ...
    def get_self_info(self) -> Any: ...
```

方法签名对齐 `adapters/xhs/pc_api_adapter.py:19/42/46/50/54`，业务层零感知。`account_id` 作为可选参数用于让网关稳定复用 context（cookie 会轮换，指纹会变）。

### 4.3 网关对外接口（建议）

| 端点 | 用途 |
|---|---|
| `POST /v1/login/{pc\|creator}/qrcode` | 打开登录页、截图二维码 → `{context_key, qr_image_data_url}` |
| `GET /v1/login/{context_key}/status` | 查登录态 → `{status, cookies}` |
| `POST /v1/pc/search` | 关键词搜索 |
| `POST /v1/pc/note` | 笔记详情 |
| `POST /v1/pc/comments` | 评论 |
| `POST /v1/pc/user_notes` | 用户笔记 |
| `POST /v1/pc/self_info` | 自身信息（巡检用） |
| `POST /v1/contexts/{key}/close` | 释放 context |
| `GET /healthz` | 探活（含浏览器是否可用） |

**约束**：网关只做「浏览器 + 平台接口」，**不做业务归一化**——归一化继续留在后端 `_normalize_search_item` / `normalize_comment_payload` 等现有函数里，避免业务知识外溢。

## 5. 动 adapters 之前必须先修的 2 个既有缺陷

### 5.1 creator 账号健康检查**必定误判为 expired**（严重）

```
backend/app/api/accounts.py:190-201
    if account.sub_type == "creator":
        try:
            from apis.xhs_creator_apis import XHS_Creator_Apis
            creator_cookies = decode_cookie_text(cookies_text)
            api = XHS_Creator_Apis()                                  # ← :194
            success, msg, _ = api.get_fileIds("image", creator_cookies)  # ← :195
            if not success:
                account.status = "expired"
                ...
        except Exception as upload_exc:
            account.status = "expired"          # ← :200 「上传凭证验证异常」
```

两个问题：

1. `XHS_Creator_Apis()` **缺 `auth` 参数**。`apis/xhs_creator_apis.py:129-134` 明确要求：

   ```python
   def __init__(self, auth: XHSCreatorAuth):
       if not isinstance(auth, XHSCreatorAuth):
           raise TypeError('XHS_Creator_Apis 仅支持 XHSCreatorAuth；...')
   ```

   → `:194` **必定抛 TypeError**。

2. `get_fileIds(self, media_type, proxies=None)` 的第二个形参是 `proxies`，而 `:195` 传入的是 **cookies**。即便补上 auth，也是错的。

**后果**：`POST /accounts/{id}/check` 对 **creator 账号**永远走 `:199` 分支——第 182 行刚设好的 `status = "active"` 被第 200 行覆盖成 `"expired"`，`status_message` 变成「上传凭证验证异常: XHS_Creator_Apis 仅支持 XHSCreatorAuth…」。

这不属于签名问题，但它落在「上传链路凭证探测」上，**浏览器化改造必然要碰这段代码**，且会污染迁移期间的验收数据（无法区分「登录态真的失效」和「这个 bug」）。**必须在阶段 0 一并修掉**（二选一：补 `XHSCreatorAuth.from_cookie(...)`，或改用 `XhsCreatorApiAdapter.upload_media` 之外的健康探测方式）。

### 5.2 adapter 边界实际是 7 处，不是 6 处

`backend/app/api/accounts.py:48` 定义了一个 adapter 类：

```python
class XhsSelfProfileAdapter:
    def get_self_profile(self, cookies_text: str):
        return XhsPcApiAdapter(cookies_text).get_self_info()
```

它没有直接 import SDK（是对 adapter 的二次封装，属于轻度越界），但 **12 号文档「6 个 adapter 文件」的统计漏了它**，迁移时应把它一并下沉到 `adapters/browser/` 或复用 `XhsPcApiAdapter.get_self_info()`。

## 8. 未解风险

| 风险 | 说明 |
|---|---|
| headless 可被检测 | Chrome headless 有可识别特征。建议优先用**真实 Chrome + 持久化 user-data-dir + headed 或 `--headless=new`**，而非默认 headless；是否引入 stealth 补丁需单独评估 |
| 仍不能绕过风控 | 浏览器解决的是「签名正确」，不是「行为可信」。高频自动化依旧会触发限流/滑块/账号异常 |
