> **命题**：**放弃无头浏览器方案**，在现有「自维护签名 SDK」基础上继续开发，新增：
> ① 登录小红书店铺 → ② 获取店铺列表 → ③ 根据商品信息 AI 生成商品笔记 → ④ 自动化发布商品笔记全流程
>
> - **调研日期**：2026-09-17
> - **性质**：调研分析 + 实施方案（**不含代码实现**）
> - **与既有文档的关系**：
>   - `docs/10` / `docs/12` / `docs/13`（无头浏览器方案）**本次全部搁置**，不再作为前置依赖
>   - `docs/11_商品AI笔记自动化方案.md` 的结论**部分被本文取代**：它假设商品数据靠浏览器抓取或手动导入，本文改为**官方开放平台接入**，并补上了它未覆盖的「店铺登录 + 店铺列表」
> - **证据分级**（贯穿全文，务必区分）：
>   - `[代码]` = 本仓库源码可验证
>   - `[公开]` = 多个独立公开来源一致，但非官方文档原文

## 0. 结论摘要

| 需求 | 可行性 | 推荐路径 | 主要风险 |
|---|---|---|---|
| ① 登录小红书店铺 | ✅ **可行，且有官方路径** | **官方开放平台 OAuth 授权**（无需逆向） | 需企业资质 + 应用审核 |
| ② 获取店铺列表 | ✅ **可行** | 同上，授权后可拿店铺 + 商品数据 | 「店铺列表」的口径需先定义 |
| ③ 商品 → AI 生成笔记 | ✅ **可行，基础设施已就绪** | 复用现有 `ai_service.generate_note` | **合规风险最高**（广告法 + 违禁词） |
| ④ 自动化发布商品笔记 | ⚠️ **可行，但有一个必须先验证的接口细节** | **复用现有 Creator 发布链路 + `goods_info`** | 开放平台**不提供笔记发布**（见 §2.4） |

**三条最重要的判断：**

1. **「登录店铺」不必逆向千帆后台。** 小红书有官方电商开放平台，走标准 OAuth 授权即可拿到**店铺级** accessToken，商品与店铺数据都在开放接口权限范围内。这比逆向 `ark.xiaohongshu.com` 稳得多，也不增加签名维护面——**与你「移除算法维护」的初衷同向**。

2. **但「发布商品笔记」开放平台覆盖不到。** 开放平台的应用类目权限包里只有 `公共/授权/商品/库存/素材中心/订单/售后` 接口，**没有笔记接口** `[公开]`。所以发布这一环必须走现有 Creator 逆向下发链路。

3. **好消息是：Creator 发布体里商品槽位早就存在。** `[代码]` `xhs_utils/xhs_creator_util.py:177` 与 `:246`，图片/视频两种发布体的 `common` 里都写着 `"goods_info": {}`——**这是空着的商品挂载位**。也就是说，**发商品笔记很可能不需要碰千帆的签名体系，只需要把 `goods_info` 填对**。这是整个方案里投入产出比最高的一条线索。

**因此推荐架构是混合的**：

```
① 登录店铺 + ② 店铺列表 + 商品数据  →  官方开放平台（零逆向）
④ 发布商品笔记                      →  现有 Creator 链路（goods_info 补全）
③ 商品→笔记生成                     →  现有 ai_service（加商品专用 Prompt + 合规护栏）
```

## 1. 需求拆解与「放弃无头浏览器」的影响

### 1.1 「放弃无头浏览器」意味着什么

| 方面 | 影响 |
|---|---|
| 登录链路 | 继续用现有扫码/短信/Cookie 导入，**登录冷链（远端 JSVMP）的维护成本仍然存在**——这是当初想切换的核心动因，现在选择接受它 |
| 采集链路 | 继续用 `apis/xhs_pc_apis.py` + 签名算法，算法改版仍需人工逆向 |
| **本方案的收益** | 数据来源从「浏览器抓取」换成了**官方开放平台**，反而**比浏览器方案更稳**（有协议保障、不被页面改版影响）。这是放弃浏览器后捡到的一个额外好处 |
| 新增风险 | 商品笔记发布依赖 Creator 逆向链路，属于**新增的业务面**，一处新接口失配会中断本功能的发布 |

### 1.2 需求边界要先对齐

| 需求 | 本文采用的口径 | 备选口径（若不符请纠正） |
|---|---|---|
| 「登录小红书店铺」 | 取得**店铺级授权**，可读写该店铺的商品数据 | 仅浏览店铺数据即可 |
| 「获取店铺列表」 | 一个账号/应用授权范围内的**多店铺列表**（含店铺基础信息） | 只要商品列表，不要店铺维度 |
| 「商品笔记」 | 笔记正文**挂载自己店铺的商品**（可点击跳转的带货笔记） | 纯种草笔记，不挂商品 |

> **口径 3 是分水岭**：如果**不挂商品**，则需求 ①② 可以不依赖店铺授权，整个方案大幅简化（只需现有 Creator 链路 + AI 生成）。**建议先确认这一点。**

## 2. 关键调研发现

### 2.1 【代码】仓库里叫「千帆」的 SDK，打的其实是蒲公英的域名

`apis/xhs_qianfan_apis.py` 全部接口都在 `pgy.xiaohongshu.com`：

| 实际内容 | 出处 |
|---|---|
| `https://pgy.xiaohongshu.com/api/draco/distributor-square/...` | `apis/xhs_qianfan_apis.py:10` / `:30` |
| `authority: pgy.xiaohongshu.com` | `xhs_utils/xhs_qianfan_util.py:6` / `:24` |
| 方法全是 `get_user_*`（分销商维度）：`get_user_detail` / `get_user_cooperation` / `get_user_shop` / `get_user_item` / `get_user_fans` | `apis/xhs_qianfan_apis.py:52-116` |

而平台侧的准确对应关系 `[公开]`（多个独立来源一致）：

| 平台 | 域名 | 定位 |
|---|---|---|
| **千帆** | **`ark.xiaohongshu.com`** | 商家后台：商品、订单、店铺数据、**笔记管理 / 发布笔记** |
| 蒲公英 | `pgy.xiaohongshu.com` | 买手/达人合作（找博主带货） |
| 乘风 | `chengfeng.xiaohongshu.com` | 电商广告投流 |
| 聚光 | `ad.xiaohongshu.com` | 广告管理 |

**结论**：项目自称的「千帆平台（分销商列表 & 合作品类 / 商品信息）」`[代码]` `README.md:110`，**实为蒲公英的分销商广场 API**。

**这对本方案有两个直接后果**：

1. **现有 SDK 对本次需求几乎无用。** 它拿的是「我能分销什么货」（`get_user_item`），不是「我店铺里有什么货」，也不是「我有哪几个店铺」。`docs/11:93-102` 已经指出过这一点，本文进一步确认根因是**命名错位**。
2. **命名必须修。** 否则后续新增真正的千帆（`ark`）代码，会出现两个「千帆」并存——建议本方案落地时把现有文件重命名为 `xhs_pugongying_distributor_*`，或至少在文件头注明真实平台。`[代码]` 现状是 `apis/` 下 `xhs_qianfan_apis.py` 与 `xhs_pugongying_apis.py` **同时存在且都打 pgy 域名**，本身就是混淆源。

### 2.2 【代码】商品槽位已存在，且是空的

发布体构造函数 `get_post_note_image_data` / `get_post_note_video_data` 返回的 `common` 中：

```python
"goods_info": {},     # xhs_utils/xhs_creator_util.py:177（图片）
"goods_info": {},     # xhs_utils/xhs_creator_util.py:246（视频）
```

`common` 里其它字段都已填（`title` / `desc` / `hash_tag` / `post_loc` / `privacy_info` / `business_binds`），**唯独 `goods_info` 恒为空对象**。

**推断**：`goods_info` 就是把笔记与商品绑定的字段，项目从未使用过它（因为此前没有商品概念）。

**因此需求④的技术核心收敛为一个问题：`goods_info` 的正确结构是什么？**

这是一个**单点、可验证**的问题，而不是「重写发布链路」。验证方法见 §6.1：浏览器登录创作者后台，发布一篇带商品的笔记，抓包对比 `goods_info` 即可。**这是全方案里最该先做、成本最低的一步。**

### 2.3 【公开】官方电商开放平台是存在的，且支持店铺授权

`open.xiaohongshu.com`（小红书开放平台）`[公开]`：

| 能力 | 说明 |
|---|---|
| 应用类型 | 支持**自用型应用**（商家自研），创建账号时**绑定千帆即可自动完成企业认证** |
| 应用类目 | 一键搬家 / 商品优化 / 打单工具 / 订单管理 / 企业ERP / 跨境企业ERP / **商家后台系统（全部权限包）** |
| **权限包** | `公共接口、授权接口、商品接口、库存接口、素材中心接口、订单接口、售后接口` |
| 授权流程 | 生成 `https://ark.xiaohongshu.com/ark/authorization?appId=&redirectUri=&state=` → 商家登录授权 → 回调带 `code` → 调 `oauth.getAccessToken` 换 `accessToken` + `refreshToken` |
| Token 有效期 | accessToken **2 小时**、refreshToken 较长；需自动刷新 |

**这套流程的落点正好是 `ark.xiaohongshu.com`**——也就是说，官方授权的登录入口本身就是千帆后台，**「登录店铺」在官方语义下就是 OAuth 授权，不需要逆向千帆的签名**。

**优势对比现有逆向体系**：

| 维度 | 官方开放平台 | 逆向 ark 后台 |
|---|---|---|
| 签名维护 | **无**（AppKey/AppSecret + 官方 SDK） | 需逆向 ark 的签名体系（是否复用 x-s 未知）`[待实测]` |
| 店铺/商品数据 | ✅ 官方接口 | 需逆向 |
| 合规性 | ✅ 有协议授权 | 依赖绕过，风险高 |
| 稳定性 | 有版本管理，变更会公告 | 页面/接口随时改 |
| 门槛 | 企业资质 + 应用审核（有周期） | 无门槛，但技术风险自担 |
| **笔记发布** | ❌ **权限包内无笔记接口** | ✅（千帆后台有笔记中心/发布笔记） |

> **结论：能用官方的地方全部用官方，只有「发布商品笔记」这一环官方覆盖不到。** 但结合 §2.2，这一环很可能**不需要**走千帆逆向，而是继续用 Creator 链路补 `goods_info`。

### 2.4 【公开】开放平台不提供公开的笔记发布接口

- 开放平台应用类目的权限包枚举中**没有笔记/内容类接口**（只有商品、库存、素材、订单、售后）`[公开]`
- 多方资料一致指向：笔记发布未对普通开发者开放，仅对通过资质审核的头部品牌/MCN/官方合作服务商定向开放；即使带完整 Cookie 与签名头复现客户端发布请求，也会被风控拦截 `[公开]`

**对本方案的意义**：**不要把「自动发布商品笔记」的期望寄托在官方开放平台上**。可行路径只有两条，均基于**现有 Creator 逆向下发链路**：

| 路径 | 做法 | 评价 |
|---|---|---|
| **P1（推荐）** | 复用 `XhsCreatorApiAdapter._post_uploaded_image_note`，补全 `common.goods_info` | 改动最小，只差一个字段结构 |
| P2 | 逆向千帆后台（ark）自己的「笔记中心 → 发布笔记」接口 | 需新逆向一套签名，**成本高且与放弃浏览器的初衷冲突** |

**建议先做 P1 的验证。** 只有 P1 确认不可行（例如服务端校验「发布者必须是店铺绑定的专业号」且 Creator 链路拿不到该身份），才考虑 P2。

### 2.5 【代码】新增账号类型会撞上硬编码的联合类型

现有账号类型 `sub_type` 在代码里是**硬编码的二值联合**，不是数据驱动：

| 位置 | 内容 |
|---|---|
| `frontend/src/types/index.ts:51` | `sub_type: "pc" \| "creator" \| null` |
| `frontend/src/lib/api.ts:770,809,821` | `sub_type: "pc" \| "creator"` |
| `frontend/src/components/account/add-account-drawer.tsx:15,20` | `type AccountType = "pc" \| "creator"` |
| `qr-login-panel.tsx:12` / `phone-login-panel.tsx:11` / `cookie-import-panel.tsx:9` | `accountType: "pc" \| "creator"` |
| `backend/app/api/publish.py:415,453` | `sub_type != "creator"` 守卫 |
| `backend/app/services/scheduler_service.py:124,652` | `sub_type != "creator"` 守卫 / 适配器二选一 |
| `backend/app/services/account_service.py:129` | 按 `sub_type` 过滤 |
| 前端页面过滤 | `discovery-page.tsx:98` / `crawler-page.tsx:182` / `auto-ops-page.tsx:123-124` / `publish-page.tsx:104` / `accounts-page.tsx:195` 均按 `"pc"`/`"creator"` 硬筛 |

**后果**：新增 `sub_type="shop"` 需要同步改 **7 个前端文件 + 4 处后端守卫**，且**每个新页面都要重复一遍 `filter(sub_type === ...)` 的写法**。

**建议**：本方案顺手把 `sub_type` 提升为可扩展枚举（如后端 `AccountSubType(str, Enum)` + 前端 `type AccountType = "pc" | "creator" | "shop"`，并把过滤逻辑收敛到一个 helper），**不要在多处散落字符串字面量**。这是一次低成本的重构机会，不做的话后续每加一个类型都要重复这个代价。

### 2.6 【公开】平台自带「商品笔记」与「批量生成智能笔记」能力

千帆后台本身已经提供：

- **笔记中心 → 笔记管理 / 发布笔记**（PC 端左侧「内容 → 笔记中心」）
- **商品管理页有「批量生成智能笔记」按钮**
- 商品列表会提示「N 个在架商品无笔记 → 去发布」，并明确「商品笔记是获取流量和粉丝的最重要方式」
- App 端功能列表含「【商品笔记】支持一键发布小红书商品笔记，获取热搜词」

**这是必须正视的竞争性事实**：**平台已经内置了「批量生成商品笔记」这个功能**。

**对本方案的意义（不是要放弃，而是要想清楚差异化）**：

| 平台自带能力的局限（推断，`[待实测]`） | 本方案可以做到的不同 |
|---|---|
| 模板化文案，风格统一、易同质化 | 自定义 Prompt，可控人设/口吻/卖点侧重 |
| 用平台自己的商品图 | 可 AI 润色、加贴纸、改尺寸做**图片差异化** |
| 绑定单一店铺后台操作 | 可跨店铺/跨账号统一编排、批量排期 |
| 无外部数据输入 | 可结合采集到的**爆款笔记结构**反向生成 |

> **建议**：本方案的真正价值不在「批量生成」，而在「**可控 + 差异化 + 可编排**」。如果只是复刻平台按钮，投入产出比很差。

## 3. 技术路线对比与推荐架构

### 3.1 三条候选路线

| 路线 | 店铺登录 | 店铺列表/商品 | 商品笔记发布 | 签名维护增量 | 评价 |
|---|---|---|---|---|---|
| **R1 全官方** | 开放平台 OAuth | ✅ 官方接口 | ❌ **不可行** | 0 | 需求④做不到 |
| **R2 全逆向** | 逆向 ark 登录 | 逆向 ark 接口 | 逆向 ark 发布 | **+1 套签名面** | 与「移除算法维护」背道而驰 |
| **R3 混合（推荐）** | 开放平台 OAuth | ✅ 官方接口 | ✅ **Creator 链路 + `goods_info`** | 0（复用现有） | 唯一能同时满足四项需求的路线 |

### 3.2 推荐架构

```
┌────────────────────────────────────────────────────────────────┐
│  前端（新增「店铺 / 商品 / 商品笔记」三个页面）                    │
│    └── 账号页新增 sub_type = shop（授权式，非扫码）               │
└────────────────────────────────────────────────────────────────┘
                              ↓ FastAPI
┌────────────────────────────────────────────────────────────────┐
│  新增 services/shop_service.py（店铺授权 + 商品同步）             │
│    ├── 授权：生成 authorize URL → 收 code → 换 token → 加密落库   │
│    ├── token 自动刷新（accessToken 2h 过期）                     │
│    └── 商品同步：拉店铺列表 → 拉商品列表 → 落 products 表          │
├────────────────────────────────────────────────────────────────┤
│  新增 services/product_note_service.py（商品 → 笔记）             │
│    ├── 组装 reference（标题/卖点/价格/规格/图片描述）             │
│    ├── 调 ai_service.generate_note + generate_tags               │
│    ├── 合规校验（违禁词/绝对化用语/长度）                         │
│    └── 写 ai_drafts（复用）→ 可选人工审核闸门                     │
├────────────────────────────────────────────────────────────────┤
│  复用 services/scheduler_service.py + publish_jobs（批量排期）    │
│    发布执行 → adapters/xhs/creator_api_adapter.py                │
│      └── _post_uploaded_image_note  ← 补 common.goods_info       │
│         （上传链路完全不动，PyExecJS 独立签名保持现状）            │
└────────────────────────────────────────────────────────────────┘
```

**关键设计原则**（与 `docs/10` §6 一致，本次继续遵守）：

1. **适配层接口不变**，业务层不感知数据来自官方还是逆向
2. **上传链路不动**（`apis/xhs_creator_apis.py` 的 PyExecJS 独立签名）
3. **不新增签名维护面**——这是 R3 相对 R2 的核心优势，务必守住
4. **`ai_drafts` / `publish_jobs` 全部复用**，只新增商品域的表

## 4. 数据模型设计

项目现有 20 张表 **没有任何商品/店铺概念** `[代码]`（`backend/app/models/` 全表名已核对，无 product/goods/shop/sku）。需新增：

```
shops（店铺）                                        新表
  ├── id, user_id
  ├── platform_account_id  → platform_accounts（sub_type=shop）
  ├── external_shop_id, shop_name, logo, status
  ├── auth_provider: official_open_platform | ark_reverse
  ├── profile_json（店铺基础信息快照）
  └── created_at / updated_at

shop_tokens（店铺授权凭证）                           新表
  ├── id, shop_id
  ├── encrypted_access_token, encrypted_refresh_token   ← 复用 Fernet 加密设施
  ├── expires_at, refreshed_at
  └── created_at
  ※ 建议参照 account_cookie_versions 的「追加版本、不覆盖写」设计
  ※ 不要存进 account_cookie_versions：语义是 token 不是 cookie，混存会污染巡检逻辑

products（商品）                                     新表
  ├── id, user_id, shop_id
  ├── external_item_id（商品ID，发布商品笔记时必须用）
  ├── title, sub_title, price, price_min/price_max
  ├── selling_points（卖点，JSON 数组）
  ├── specs（规格，JSON）
  ├── image_urls（主图/详情图，JSON 数组）
  ├── category, tags
  ├── source: official_api | manual_import
  ├── sync_status, last_synced_at
  └── created_at / updated_at

product_notes（商品 → 笔记 的生成记录）               新表
  ├── id, user_id
  ├── product_id, shop_id
  ├── draft_id → ai_drafts（复用现有草稿体系）
  ├── publish_job_id → publish_jobs（复用现有发布体系）
  ├── ai_model_config_id, prompt_version, ai_instruction
  ├── generated_title, generated_body, generated_tags
  ├── compliance_status: pending | passed | rejected
  ├── status: pending | generated | approved | published | failed
  ├── idempotency_key（商品+账号+时间窗，防重复生成）
  └── error
```

**设计要点**：

1. **`shops` 与 `platform_accounts` 的关系**：建议 `platform_accounts` 增加 `sub_type="shop"` 作为「店铺身份」的载体，`shops` 表挂 1:1 或 1:N。这样账号列表、Cookie 巡检、加密设施**全部复用**，符合项目既有范式。
2. **token 必须加密且分表**：开放平台的 accessToken 相当于店铺操作权限，**泄露即等于店铺被控**。加密复用 `core/security.py` 的 Fernet，但**不要与 Cookie 混存**（巡检逻辑按 `account_cookie_versions` 最新版本判断健康度，混入 token 会造成误判）。
3. **`product_notes` 必须带幂等键**：同一商品短时间重复生成 = 重复发布 = 营销刷屏风险。`docs/11:163` 已提出，这里落为字段。
4. **`external_item_id` 是发布链路的关键外键**——没有它就无法在 `goods_info` 里指定商品。

### 5.1 现有能力盘点（可复用，不必新写）

**结论**：基础设施完备。`generate_note` 的 `reference` 参数正好可以装商品信息（`docs/11:148` 也是这么设想的）。

### 5.2 需要新增的：商品专用 Prompt 与结构化输入

现有 `generate_note` 的 Prompt 是**通用内容策划**（`ai_service.py:198`：`"你是小红书内容策划，输出可发布的标题和正文。"`）。商品笔记需要专用 Prompt，建议新增 `generate_product_note()`，把商品字段结构化组装：

```
角色：小红书商品笔记写手（不是泛内容策划）
输入：
  ├── 商品标题 / 副标题
  ├── 核心卖点（3-5 条）
  ├── 价格与规格
  ├── 适用人群 / 使用场景
  └── 商品图描述（调 describe_image 得到，或走多模态）
结构要求：
  ├── 痛点切入 → 场景描述 → 卖点展开 → 使用感受 → 价格理由 → 轻行动号召
  ├── 标题 ≤ 20 字（平台限制）
  ├── 正文 300-800 字
  └── 标注 3-5 个话题标签
禁止：
  ├── 绝对化用语（最/第一/顶级/国家级）
  ├── 功效宣称（治疗/根治/美白/祛痘 等医疗与化妆品功效词）
  ├── 虚假承诺（保证/永久/100%）
  └── 与商品不符的描述（编造参数、编造销量）
```

**Prompt 应版本化**（`prompt_version` 落库），否则生成质量回退时无法定位。

### 5.3 合规护栏（本方案风险最高的一环）

商品笔记 = **商业推广内容**，合规要求显著高于普通种草笔记。必须内建：

| 护栏 | 说明 | 实现位置 |
|---|---|---|
| **违禁词/敏感词过滤** | 广告法绝对化用语 + 平台违禁词 + 行业特殊词（食品/化妆品/医疗器械） | 生成后、入库前 |
| **功效宣称拦截** | 非特殊用途化妆品不得宣称功效 | 同上 |
| **长度与格式校验** | 标题 ≤20 字、正文区间、图片数量（1-18 张）、图片比例 | 发布前 |
| **与商品一致性校验** | 生成的卖点/价格必须来自 `products` 表，**不允许 AI 编造** | 生成时约束 + 入库后比对 |
| **人工审核闸门** | `auto_publish=false` 默认开启，人工过一遍再发 | 状态机 `pending_approval` |
| **AIGC 标识** | 如平台要求标注 AI 生成内容，需支持 | 发布体预留字段 |

> ⚠️ **免责前提**：本项目 README 标注**仅供学习交流、禁止商业化** `[代码]`。商品笔记属于商业推广，**用途合规性需自行评估**，本文只做技术分析。

### 5.4 图片来源与图片差异化

商品主图直接复用有**判重风险**（平台会识别重复图片，且同一图片重复用于多篇笔记会降低推荐）。建议：

| 方案 | 说明 |
|---|---|
| AI 润色 | `generate_image` 以商品图为参考重绘（保留商品特征的二次创作） |
| 合成图 | 商品图 + 场景底图 / 文字贴纸（`note_assets` 体系可承接） |
| 多图轮换 | 商品有多张图时，每篇笔记用不同组合 |
| 尺寸适配 | 3:4 竖版（小红书主推比例），需裁剪而非拉伸 |

**注意**：AI 重绘有**商品失真风险**（颜色/款式改变 → 与实物不符 → 售后与违规风险）。**建议电商类目优先用真实商品图 + 版式差异化，AI 只做背景/文字/版式处理。**

## 7. 自动化编排（复用为主）

`[代码]` 现有调度体系已能覆盖绝大部分需求，**建议最大限度复用，不要另起一套**：

| 现有能力 | 出处 | 复用方式 |
|---|---|---|

| 发布资产 | `models/publish.py:34`（`publish_assets`） | 直接复用 |

**需要补的**：`publish_schedule`（批量排期，`docs/11:187` 已设计）。**本文建议沿用其设计**，三种策略（固定间隔 / 定点 / 随机窗口）+ 护栏（每日上限、最小间隔、失败熔断）。

**为什么排期必须用 `scheduled_at` 而不是执行侧 sleep** `[代码]`：`scheduler_service.py:181` 的补跑机制让已排期任务在进程重启后不丢，且天然幂等。这是现有架构的一个优点，**继承它**。

**商品笔记特有的编排约束**：

| 约束 | 理由 |
|---|---|
| **单店铺/单账号串行** | 同账号并发发布 = 重复发布与风控双重风险 |
| **每日上限更保守** | 商品笔记是营销内容，平台对「商家批量发营销笔记」更敏感 |
| **同商品冷却期** | 同一商品短期内多篇 = 刷屏（如 ≥72h） |
| **发布前复核商品状态** | 商品可能已下架/改价，生成的笔记价格与实际不符 = 违规 |
