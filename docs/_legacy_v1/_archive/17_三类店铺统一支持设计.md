# 17 · 个人店 / 个体店 / 企业店：三类店铺的统一支持设计

> 本文是 `docs/16` 的设计细化，不改变其路线选择（路线 C：人工 Cookie 导入 + 只读逆向 + 复用 creator 发布）。
> 本文取代 `docs/16` §1.2 / §1.3 / §4.3 / §6.1 中"假设店铺为个人店"的表述。
> `docs/16` §2（接入千帆的成本证据）、§3（三条路线）、§7（风险）继续有效。

## 0. 需求与核心判断

**需求**：店铺可能是个人店、个体工商户店、企业店中的任意一种，**三种场景均须支持**。

**核心判断**：

> 把"支持三种店铺"实现为 **1 套能力探测机制**，而不是 **3 套类型分支**。

因为类型→能力的映射关系**目前是猜的**——外部资料在"个人店能否挂商品"上直接矛盾（`docs/16` 附录 A）。**任何写死的类型判断，都是在用一个未经验证的假设去驱动代码分支。** 一旦猜错，错误会扩散到前端、后端、调度三层。

正确的做法是：**类型只用于展示，能力才用于驱动逻辑。**

---

## 1. 反模式：按类型分支写代码

```python
if shop.shop_type == "personal":
    can_attach_goods = False          # ← 这个假设可能是错的
elif shop.shop_type == "individual":
    can_attach_goods = True
elif shop.shop_type == "enterprise":
    can_attach_goods = True
```

三个代价：

1. **映射是猜测**：一旦"个人店其实可以挂商品"被证伪或证实，这段逻辑要重写
2. **扩散成本高**：这个判断会出现在发布校验、前端渲染、任务调度、错误提示至少 4 处
3. **无限扩展**：平台还有旗舰店、专卖店、专营店、买手店……每新增一种都要重付一次

## 2. 正模式：能力驱动

```
店铺（运行时探测）
   ├─ shop_type      → 仅用于展示与统计
   └─ capabilities   → 驱动一切逻辑分支
          ├─ can_attach_goods
          ├─ can_publish_note
          ├─ categories[]
          ├─ requires_deposit_before_listing
          └─ supports_sub_account
```

**代码只读 `capabilities`，永不读 `shop_type` 来决定行为。** `shop_type` 只出现在两处：前端展示的 badge，以及探测失败时的保守兜底默认值。

这样得到的性质：

- 三种场景天然支持（因为不假设类型）
- **未来出现第四、第五种店铺类型，代码零改动**
- 探测失败时行为可预测（走保守默认），而不是崩溃或误发

## 3. 三类店铺的预期差异（能力矩阵）

> **本表是"待验证的预期"，不是设计依据。** 设计依据是 §2 的运行时探测结果。
> 本表的作用是：指导阶段 0 的探测脚本该采集哪些字段，以及探测失败时兜底默认值该取什么。

| 能力项 | 个人店 | 个体工商户店 | 企业店 |
|---|---|---|---|
| 资质要求 | 身份证 + 人脸 | 个体户执照 | 企业执照 |
| **可经营类目** | **受限**（服饰/家居/文创/数码配件） | 大多数普通类目 | 全部 |
| **商品分享（挂商品）** | **未知（来源矛盾）** | 预期可 | 预期可 |
| 保证金 | 1000 元起，可先发品后缴 | 1000 元起 | 通常 20000 元，**发品前必须缴** |
| 子账号体系 | 无 | 无 / 有限 | **有**（岗位权限细分） |
| 同主体多店 | 一人一店 | 待确认 | **一执照最多 3 店** |
| Creator 侧绑定 | 专业号绑定店铺 | 同左 | 同左 |

**两个直接影响设计的推论**：

1. **企业店的"店铺列表"确实是复数**（一执照最多 3 店），且**有子账号** → 账号与店铺必须是 **N:M**，不能是一对多（§4.2）
2. **企业店有"发品前必须缴保证金"的硬前置** → 探测结果要包含这个状态，否则会在"商品无法上架"时给出错误诊断

## 4. 数据模型调整

### 4.1 修订后的表

```
shops
  id
  seller_id                # 商家主体 ID（平台侧），唯一键组成之一
  shop_id                  # 店铺 ID（平台侧），唯一键组成之一
  shop_name
  shop_type                # personal | individual | enterprise | unknown
  capabilities_json        # 探测结果（见 §5.1）
  capabilities_verified_at # 上次探测时间；NULL 表示从未验证
  status                   # active | suspended | closed
  synced_at                # 上次数据同步时间
  raw_json                 # 店铺信息原始返回，便于回溯与补探测
  UNIQUE (seller_id, shop_id)

shop_account_bindings      # 新增：账号 ↔ 店铺 N:M
  id
  shop_id_fk               # → shops.id
  platform_account_id_fk   # → platform_accounts.id（sub_type="shop"）
  access_role              # owner | sub
  can_sync                 # 是否用这个账号的 Cookie 同步该店数据
  created_at
  UNIQUE (shop_id_fk, platform_account_id_fk)

shop_products
  id / shop_id_fk / item_id / title / price / stock / category
  images_json / detail_url / status / synced_at / raw_json
  UNIQUE (shop_id_fk, item_id)

product_note_jobs
  id / product_id_fk / creator_account_id_fk / draft_id_fk
  status / idempotency_key(unique) / goods_info_json
  publish_job_id_fk / error_message / created_at / updated_at
```

### 4.2 为什么必须引入 `shop_account_bindings`

三类场景的账号-店铺基数完全不同：

| 场景 | 账号 : 店铺 | 说明 |
|---|---|---|
| 个人店 | 1 : 1 | 最简单 |
| 个体户店 | 1 : 1（或 1 : N） | 待确认 |
| 企业店 | **N : M** | 一执照最多 3 店 × 主账号 + 多个子账号 |

如果沿用 `shops.platform_account_id` 单外键：

- 企业店下同一店铺被子账号同步时会**产生重复行**
- 或反过来说，一个店铺会被"哪个账号同步的"这个偶然事实唯一确定，**丢失了其他账号的访问路径**

`shop_account_bindings` 用 `can_sync` 标记"用哪个账号的 Cookie 拉这家店的数据"（每个店铺**同时只有一个** `can_sync=True`，保证数据来源稳定），其余绑定仅表示访问关系。

### 4.3 与现有机制的衔接

| 现有对象 | 复用方式 | 改动 |
|---|---|---|
| `platform_accounts` | 千帆登录态存这里，`sub_type="shop"` | **不用改表**（`sub_type` 是自由字符串） |
| `account_cookie_versions` | Cookie 按账号版本化存储，沿用 | **不用改** |
| `Cookie 巡检`（2h） | 巡检对象是**账号**，不是店铺；失效则其绑定的店铺全部标记不可同步 | 需补一条聚合逻辑 |
| `profile_json` | 存账号级信息 | **不用改**；店铺级能力放 `shops.capabilities_json` |

**关键约定：Cookie 存账号层，能力存店铺层。** 因为能力是店铺的属性（同一店铺被主账号和子账号访问，能力相同），而登录态是账号的属性。

## 5. 能力探测机制

### 5.1 能力项与探测方式

| 能力键 | 含义 | 探测思路（具体接口待阶段 0 抓包确定） |
|---|---|---|
| `can_attach_goods` | 笔记能否挂商品 | Creator 侧：笔记编辑页「添加商品」入口是否存在对应的权限接口/字段 |
| `can_publish_note` | 千帆侧是否有笔记发布能力 | 千帆笔记中心入口对应的接口是否返回可用 |
| `categories` | 本店可经营类目 | 店铺信息 / 类目接口返回 |
| `requires_deposit_before_listing` | 发品前是否必须先缴保证金 | 店铺状态字段（企业店为真） |
| `supports_sub_account` | 是否有子账号体系 | 店铺信息中的主体类型标识 |
| `shop_type` | 店铺类型 | 店铺信息接口；**拿不到则记 `unknown` 并强制走兜底** |

### 5.2 探测时机

| 时机 | 说明 |
|---|---|
| **绑定店铺时** | 首次探测，建立基线 |
| **手动触发** | 店铺列表页提供「重新检测能力」按钮 |
| **定时巡检** | 复用现有 2h 巡检，顺带复核能力（防止平台调整权限后系统仍按旧能力运行） |
| **发布前兜底** | 执行 `product_note_jobs` 前读一次缓存能力，`capabilities_verified_at` 超过阈值（建议 7 天）则先重探 |

### 5.3 探测失败的降级（重要）

**探测失败时不能"当作支持"，也不能"直接失败"，而是取保守默认并显式标记：**

```python
CONSERVATIVE_DEFAULTS = {
    "can_attach_goods": False,          # 保守：不挂商品
    "can_publish_note": False,
    "categories": [],
    "requires_deposit_before_listing": True,
    "supports_sub_account": False,
    "shop_type": "unknown",
}
```

同时置 `capabilities_verified_at = NULL`，前端对该店铺显示「能力未验证」提示，并**只开放只读功能**（浏览商品、生成草稿），**不开放发布**。

这个设计的价值：**系统在信息不全时既不会误发，也不会死锁**——用户仍可用它生成草稿、导出内容，等探测通了再发布。

## 6. 功能可用性的统一处理

### 6.1 后端：能力守卫

单一判定入口，避免分支散布：

```python
class ShopCapability:
    def __init__(self, shop): ...
    @property
    def can_attach_goods(self) -> bool: ...
    @property
    def can_publish(self) -> bool: ...
    def require(self, cap: str) -> None:
        """不满足则抛业务异常，携带可读原因"""
```

调用点只在两处：`api/shops.py` 的写操作入口，和 `product_note_jobs` 执行前的校验。

### 6.2 前端：能力驱动渲染

**置灰 + 说明原因，而不是隐藏。** 三种店铺共存时，用户需要理解"为什么这家店不能挂商品"，否则会以为是 bug。

```
店铺卡片
  个人店  [可挂商品 ✗ 未验证]
  个体户店 [可挂商品 ✓]
  企业店  [可挂商品 ✓] [待缴保证金]
```

### 6.3 降级路径内置

**无 `can_attach_goods` 的店铺 → 自动走"生成 + 普通笔记发布"**（即 `docs/16` 的路线 B）。

这条路径**不是异常处理，而是合法业务流程**——它正是三种店铺场景统一支持的关键：个人店若确实不能挂商品，该店铺依然可用，只是产出不挂链的种草笔记。

## 7. 三类场景的端到端对照

| 环节 | 个人店 | 个体户店 | 企业店 |
|---|---|---|---|
| 登录 | 本人账号，人工登录导 Cookie | 经营者账号，同左 | **法人/员工子账号**，同左（路线 C 已由人工吸收差异） |
| 账号-店铺绑定 | 1:1，1 行 binding | 1:1 | **N:M** |
| 数据同步 | 用该账号 Cookie 只读拉取 | 同左 | 指定一个 `can_sync` 账号同步 |
| 能力探测 | 探测后可能得 `can_attach_goods=False` | 预期为真 | 预期为真 + 需查保证金状态 |
| 生成 | 一致（`ai_service` + 商品 Prompt） | 一致 | 一致 |
| 发布 | 视能力走挂商品 / 不挂商品 | 视能力 | 视能力；**未缴保证金时禁止发品类操作** |
| 类目约束 | 从 `capabilities.categories` 读，**不硬编码** | 同左 | 同左 |

**唯一有实质差异的是绑定基数与保证金前置，其余全部收敛到能力探测。**

## 8. 阶段 0 调整

`docs/16` §6.1 原为「验证个人店能否挂商品」。**改为：**

> **为每种实际持有的店铺类型，各产出一行完整的能力矩阵记录。**

具体：

1. 按 §5.1 的六个能力项，对每种可访问的店铺类型各探测一次
2. 记录原始返回体（存 `raw_json`），**为将来补探测留证据链**
3. 若某类型当前无可访问店铺 → 该行留空，**不影响系统上线**（`shop_type=unknown` + 保守默认已能兜住）
4. 顺带确认两件事：
   - 企业店下**子账号登录后能看到几个店铺**（验证 N:M 是否真实存在）
   - 未缴保证金时，商品上架与笔记发布分别报什么错（决定错误诊断文案）

## 9. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **能力探测本身失效** | 探测依据的接口若不可得，全部店铺落入保守默认 → 系统只能生成不能发布 | 保留 `raw_json` 证据链；提供手动覆盖入口（人工确认后写死能力并标记来源为 `manual`） |
| **店铺类型拿不到** | 平台可能不直接返回类型标识 | 允许 `unknown`；不影响功能（逻辑只依赖能力） |
| **子账号权限粒度** | 企业店子账号有岗位权限细分，可能出现"账号能看到店铺但无权发笔记" | 探测需按**账号+店铺**组合维度做，不能只按店铺。`shop_account_bindings` 已预留位置（可加 `capabilities_json`） |
| **能力过期** | 平台调整权限后系统仍按旧能力运行 | §5.2 的定时复核 + 发布前有效期检查 |
| **`can_sync` 单点** | 企业店指定一个同步账号，该账号 Cookie 失效则该店数据停更 | 巡检失效时提示"可从其他绑定账号切换同步" |

## 附录 A：置信度

| 结论 | 置信度 |
|---|---|
| 个人店免营业执照、个体户店需个体执照、企业店需企业执照 | **中高**（多来源一致） |
| 个人店可经营类目受限 | **中高** |
| 企业店一个营业执照最多开 3 家店 | 中（单来源，**需验证**） |
| 企业店有子账号与岗位权限体系 | **中高**（多来源一致，功能说明详实） |
| 企业店发品前必须缴纳保证金（个人店/个体店可先发品） | 中（单来源） |
| `shop_type` 能否从店铺信息接口直接拿到 | **未知**（设计已容错为 `unknown`） |
| 各能力的**具体探测字段/接口** | **全部未知，阶段 0 抓包确定** |

**本文所有能力矩阵均为预期值，唯一可信来源是运行时探测结果。**
