### ISS-003 · Creator 账号检查报错：XHS_Creator_Apis 缺 auth 参数
- **任务卡**：`t_61c13d60`
- **报告时间**：2026-09-18
- **现象**：Creator 扫码登录成功后，检查登录状态报 `上传凭证验证异常: XHS_Creator_Apis.__init__() missing 1 required positional argument: 'auth'`。
- **根因**：`api/accounts.py:190-201` 用 `XHS_Creator_Apis()` 无参构造，但 SDK 要求传 `XHSCreatorAuth`（只能由 `from_cookie()` 创建）；同时 `get_fileIds("image", creator_cookies)` 把 cookies 传给了 `proxies` 形参。
- **状态**：待修复（卡已建，优先级随登录链路一起处理）。
- **测试影响**：`test_account_check_creator_builds_auth_and_calls_get_fileIds` 与
  `test_creator_api_adapter_check_upload_permit_passes_media_type` 因此失败。
  这两个测试用 `monkeypatch.setattr(adapter_module, "XHS_Creator_Apis", …)`
  拦截，但 `creator_api_adapter.py` 在函数内部 `from apis.xhs_creator_apis
  import XHS_Creator_Apis` 惰性导入，monkeypatch 打到模块名上拦不到，属于
  既有问题，与 ISS-002 的修复无关。

### ISS-002 · PC 扫码登录：手机确认后前端无反应
- **任务卡**：`t_60952b27`
- **修复时间**：2026-09-18
- **现象**：PC 端扫码后前端一直停在「请扫描二维码」，手机端确认也无效；但二维码本身有效（最终会变 expired）。
- **根因**（实测定位，无需扫码）：建码与轮询分属两个独立请求/进程，轮询时用存的
  cookies 重建 `XHSLoginApi`，设备态系统性漂移。诊断脚本实测 create 进程 vs
  重建进程的签名上下文：

  | 字段 | create | 重建（修复前） |
  |---|---|---|
  | tier | 0301 | 0101 |
  | fingerprint_ready | True | False |
  | envConst | 1352 | 1327 |
  | envFpTail | 249,65,… | 249,83,… |
  | last_tiga | 有值 | 0 |
  | seq | 8 | 1 |

  三处独立缺陷叠加：

  1. **`gid` 不可从 cookies 恢复**：`gid` 只由 webprofile 请求下发，绝不进
     Cookie 头；而 `PcDeviceProfile.__post_init__` 用
     `bool(cookie['gid'])` 判 `fingerprint_ready`。后端
     `create_qrcode()` 在 `generate_qrcode` 后就返回，没做
     `ensure_webprofile`（对照 CLI 链路 `qrcode_login` 的 [3/5] 步）。
     轮询侧新 profile 永远 `fingerprint_ready=False` →
     `resolve_mns_tier` 退回 0101 → 轮询请求与建码请求不是同一台
     「已激活指纹」的设备 → 平台不认这次状态查询 → codeStatus 恒为 0。
  2. **`update_storage` 的键名对不上**：`state_snapshot()` 发
     `lastTigaUpdateTime`（驼峰），`update_storage`/`__post_init__` 读
     `last_tiga_update_time`（下划线）→ 快照里的 `lastTigaUpdateTime` 与
     `fingerprintReady` 被静默丢弃。
  3. **host-only Cookie 丢失**：`acw_tc` 按 host 隔离、不进 shared dict，
     跨请求重建时轮询的 Cookie 头比建码时少一个字段。

- **改动**：
  - `apis/xhs_pc_login_apis.py`：`check_qrcode_status` 在缺 `gid` 时惰性
    `ensure_webprofile`（自愈兜底）；新增
    `state_snapshot()`/`restore_state(state, *, host_cookie_state=)`。
  - `xhs_utils/xhs_pc/state.py`：`update_storage` 与 `__post_init__` 统一为
    快照键名，并补齐 `fingerprintReady`/`mnsSeq` 的恢复
    （`fingerprintReady` 是唯一的 MNS 档位闸门）。
  - `backend/app/adapters/xhs/pc_login_adapter.py`：建码返回
    `device_state`/`host_cookie_state`，轮询接收并回写。
  - `backend/app/api/login_sessions.py`：临时态
    `{cookies, sync_creator, device_state, host_cookie_state}` 加密存库、
    轮询时还原。
  - `tests/backend/test_pc_qrcode_device_state.py`（新，真实链路）：断言
    create 与 restored 的签名上下文逐字段一致、tier=0301、host-only Cookie
    不丢、旧格式不崩。
  - `tests/backend/test_api.py`：Fake 适配器跟上新契约，2 处断言从「整串
    相等」改为结构断言。
- **验证**：真实适配器端到端实测 create→存库→还原→轮询，tier 保持 0301、
  `fingerprint_ready=True`；修复前同路径为 0101/False。全量 139 passed，
  另有 2 个失败属 ISS-003 的既有 creator bug（与本次改动无关）。
- **残留**：最终「扫码→确认」仍需一次真实扫码确认，但该链路的设备态连续性
  已由实测证明修复。

### ISS-001 · Creator 二维码登录 406：获取二维码失败
- **任务卡**：`t_35600103`
- **修复时间**：2026-09-18
- **根因**（两处）：
  1. `webBuild` 版本号过期：代码硬编码 `1.18.0`，线上实际 `1.29.1`。该值同时进入 Cookie 头 **和** MNS 签名物料，两处必须一起改。
  2. customer 域 CAS POST（qr-code / verify-code）走 mns0101/a1 档被平台拒绝，改走 0201/nop 冷路径（与 zones/service-ticket 一致）。
- **附带修复**：匿名早期请求无 Cookie 时 `ordered_wire_headers` 误抛 `wire header contract drifted`。
- **改动**：`apis/xhs_creator_login_apis.py`、`xhs_utils/xhs_creator/js/reference_profile.json`、`xhs_utils/xhs_core/http.py`、`tests/backend/test_creator_login_406.py`（7 个回归测试）。
- **验证**：API 端点连续 200 返回真实二维码；全量 137 passed。
- **残留**：webBuild 仍是写死常量，平台发版会再次过期（建议后续做运行时探测）。
