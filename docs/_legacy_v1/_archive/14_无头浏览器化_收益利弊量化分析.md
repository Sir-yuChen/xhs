# 无头浏览器化：切换前后的收益与代价（量化分析）

> **分析日期**：2026-09-17
> **分析对象**：`docs/10_无头浏览器方案可行性分析.md` 所提方案——弃用自维护签名算法层，改为无头浏览器加载平台真实页面、由平台 JS 自行签名
> **本文性质**：**决策依据**。不复述 `docs/10` 的可行性结论，只回答一个问题——**这次切换，净收益是正还是负，取决于哪几个变量**
> **与既有文档的关系**：`docs/10` 给了分链路可行性与延迟实测；`docs/12` 给了改动清单；`docs/13` 修正了三处误判。本文是第四份，专门做**成本-收益的量化与临界条件**
> **证据限制（重要）**：本仓库**不是 Git 仓库**（`Test-Path .git` = false），且 `apis/`、`xhs_utils/`、`backend/` 全部文件的 mtime 集中在同一天（2026-09-08，218 个文件），说明该 SDK 是**一次性整体导入**，没有任何增量演进历史。因此**「平台改版导致算法返工的实际频率」在本仓库内无法测量**。本文凡涉及该频率的推算，均标注为假设，并在 §6 给出把假设变成实测的方法。

---

## 0. 结论先行

| 维度 | 判定 |
|---|---|
| 净收益方向 | **为正**，但**不是压倒性为正**；收益集中且明确，代价分散且长期 |
| 收益的确定性 | **高**。维护面归零、失效自恢复这两项是机制性的，不依赖运气 |
| 代价的确定性 | **高**。延迟、内存、运维复杂度是物理性的，无法用工程技巧消除 |
| 最大的认知风险 | **「删掉近万行算法」是错觉**。真正能被删除的只有约 **70KB/1600 行**签名算法，且其中 **`rap.js` 系（13.7KB）在采集链路上很可能保不住**（详见 §3） |
| 最大的落地风险 | **灰度维度错了**。`docs/10` 建议「按链路灰度」，但同一账号下新浏览器与旧 HTTP 客户端指纹会混用，可能触发一致性风控。**正确维度是按账号整体切换**（详见 §5.4） |
| 决策的关键变量 | `平台算法改版的年返工频率 × 单次返工人天`。这一项**没有实测数据**，只有它足够大，切换才划算 |
| 建议 | **可以推进，但把阶段 0 的目标从「验证可行性」改为「拿到决策数据」**——可行性 `docs/10` 已经论证过了，现在缺的是返工频率和指纹一致性这两组数字 |

一句话概括这次交换的性质：

> **用「可预测的资源消耗」换掉「不可预测的人力返工」。**
> 前者是钱和机器，能扩容、能摊销、能做预算；后者是人天和不确定性，且每次都在最不方便的时候发生。对一个小团队长期维护的项目，这个方向的交换通常是划算的——但**换算比率（5-10x 延迟、150-300MB/账号）必须真的落在你的负载曲线内**，否则会变成用资源换资源。

## 1. 收益侧：逐项量化

### 1.1 收益 A：易变算法维护面归零（核心收益）

先把「近万行」拆开。`xhs_utils/` 下 JS 共 **16 个文件 / 2,174 行 / 92.8KB**，但**不是全部易变**：

| 类别 | 文件 | 体积 | 平台改版后是否会失效 |
|---|---|---|---|
| **易变（平台签名体系）** | `sign.js` 7.0KB、`mns.js` 12.1KB、`b1.js` 7.6KB、`xs_common.js` 3.0KB、`websectiga_env.js` 18.8KB、`websectiga_cli.js` 7.3KB、`rap.js` 8.4KB、`rap_crypto.js` 4.2KB、`rap_cli.js` 1.1KB | **≈69.6KB / 约1600行** | **会**。这是「每次平台改版可能要重做」的全部 |
| 稳定（通用协议） | `deflate.js` 10.4KB、`aes_encrypt.js` 1.8KB、`aes_decrypt.js` 1.6KB、`profile.js`×2 7.8KB、`xhs_creator_sign(ature).js` 1.6KB | ≈23.3KB | **不会**。是标准压缩/AES/模板，浏览器化也照样保留 |

**所以准确说法是：切换能让约 70KB、1600 行、9 个文件的「平台对抗代码」退出维护范围，而不是「近万行」。**

（`xhs_utils` 的 4,808 行 Python 里，真正与签名绑定的也只占一部分；`apis/` 3,841 行中，请求组装、业务参数、分页、错误处理等逻辑与签名无关，**在浏览器方案下依然要写**。）

**为什么这仍是核心收益**：这 1600 行的性质不是「代码量大」，而是**「不能靠读代码维护」**——它需要逆向能力（`SIGNATURE_ALGORITHM_DEEP_DIVE.md` 的存在本身就是证据：一个文件 300 行代码要配一份深度分析文档）。这类代码的成本不体现在行数上，而体现在**「只有特定能力的人能改、且改完需要验证」**。

**收益折算**：把「需要逆向能力的维护」换成「需要浏览器自动化的维护」，后者的人才池大一个数量级，且可交接、可文档化。

### 1.2 收益 B：失效自恢复（机制性收益，最值钱）

现状的失效链路是**同步的、全局的**：
```
平台改版 → JSVMP/签名变 → 所有接口同时返回异常 → 全量功能不可用
        → 人工发现 → 逆向 → 验证 → 发版   （恢复时间：天级到周级）
```

浏览器方案的失效链路是**异步的、局部的**：
```
平台改版 → 平台自己更新页面 JS → 浏览器加载到的就是新版 → 签名天然正确
        → 只有在「平台改了 DOM 结构」时，自定义脚本的选择器才失效（局部、可逐条修）
```

**这一项的价值 = 故障时长 × 故障频率 × 业务影响**。对本项目更关键的是：**签名失效期间，定时发布任务是静默失败的**——`scheduler_service.py` 里发布补跑、自动运营都会连续失败，而运营人员未必立刻发现。浏览器方案把这个故障模式从「全量静默失败」降级为「局部可见失败」。

> 这是全部收益里**唯一无法用工程手段在现方案中复制的**。性能可以加机器，指纹可以调模板，但「让平台替自己维护签名」只能靠换范式。

### 1.3 收益 C：登录链路稳定性（当前最痛的一环）

现状登录要依次执行：拉蜜罐 → 拉验证码程序 → 拉 SEM SDK → 拉远端 DS 程序并正则提取 `getdss()` → 拉远端 sec 程序并本地 `vm.runInThisContext` 执行（`apis/xhs_pc_login_apis.py:346` `_initialize_security`）。

这条冷链的特点是**每一步都依赖服务端下发的混淆程序，且全部在本地用 Node 复现执行环境**。项目自己的注释都承认这一点（`xhs_pc/auth.py:152`）：

> `websectiga` is not a zero-host pure algorithm... it is still an environment adapter and **may require maintenance after a release change**.

浏览器方案下这些程序由平台页面在真实环境里执行，**执行环境保真度从「尽力模拟」变成「本来就是」**。

**量化角度**：`getdss()` 依赖正则提取远端 JS（`apis/xhs_pc_login_apis.py`），**平台改动一次代码格式，正则就可能失配**——这类脆性在源码里是可见的。切换后这一整类脆性消失。

### 1.4 收益 D：降低认知负担与交接成本

现状：新人要理解项目，必须跨过 `SIGNATURE_ALGORITHM_DEEP_DIVE.md`（一份专门的逆向文档）+ 16 个 JS 算法文件 + 六类参数的分类体系（`xhs_pc/auth.py:21` `PC_PARAMETER_SOURCES`）。

切换后：新人只需要理解「浏览器加载页面 → 页面内发请求 → 数据回传落库」，**不需要理解签名为什么正确**。

对一个要长期交接的项目，这是实打实的成本下降，虽然无法精确折算成人天。

### 1.5 收益 E：风控指纹真实性（方向正确，但不是免死金牌）

现状 `reference_profile.json` 里是**静态伪造指纹模板**（PC 8.6KB、Creator 8.7KB），平台做设备一致性校验时是弱势方。

浏览器方案下指纹是真实的。

**但要诚实**：`docs/10 §4` 已经写了「不能绕过服务端风控」。收益的准确定义是——**从「伪造的设备」变成「真实的设备」**，而不是「不再被风控」。行为层面的风控（频率、路径、交互模式）与这个方案无关，仍需独立投入。

### 1.6 收益 F：巡检链路顺带变简单

现状：每 2h 调 `adapter.get_user_info` 探活，**消耗真实接口配额**，且探活本身也可能触发风控。

切换后：判断 `document.cookie` 里 `web_session` 是否存在、或打开任意页面看是否跳登录页，**零接口消耗、更稳**。

这是成本最低、最容易先拿到的一个收益点。

## 2. 代价侧：一次性成本

### 2.1 迁移面是可以量化的，而且不大（好消息）

适配层是这个方案的「接缝」。实测：

| 文件 | 行数 | 公开方法数 |
|---|---|---|
| `adapters/xhs/creator_api_adapter.py` | 152 | 5 |
| `adapters/xhs/creator_login_adapter.py` | 74 | 6 |
| `adapters/xhs/pc_login_adapter.py` | 65 | 5 |
| `adapters/xhs/pc_api_adapter.py` | 49 | 5 |
| `adapters/xhs/request_env.py` | 29 | 0 |
| **合计** | **369 行** | **21 个方法** |

**21 个方法**——这是全部需要「换实现」的接口面。`docs/13` 又发现 1 处边界在 `api/accounts.py:48`（`XhsSelfProfileAdapter` 定义在 API 层），实际是 22 处。

**这个数字偏小，是方案风险可控的根本原因**。改动集中在接缝处，而不是散落在业务代码里。

### 2.2 但「接缝小」不等于「工作量小」——真正的新增件

| 新增件 | 说明 | 量级判断 |
|---|---|---|
| 浏览器网关进程 | context 池、按账号复用、超时回收、崩溃重启 | 中等（新服务，需独立运维） |
| CDP 数据通道 | 页面内脚本 → 后端落库的回传协议 | 中等 |
| 登录会话模型改造 | `login_sessions.py` 的两道校验会挡路（见 §2.3） | 小但要动 |
| 注入页面脚本 | `browser_pages/*`，采集/发布的自定义驱动 | 中等，且**是新的脆弱面** |
| 浏览器运维 | 僵尸进程、Chromium 升级、反检测补丁 | **持续**（见 §4） |
| 验收体系 | 新旧路径对照、数据完整率、发布成功率对账 | 中等，但**必须做**，否则无法判断成败 |

### 2.3 一处必须改的既有代码（硬约束）

`login_sessions.py:224`（`not session.qr_id`）与 `:229`（`not session.code`）这两道校验**必然挡住浏览器方案**——`qr_id` / `code` 是平台扫码接口的内部概念，浏览器方案里不存在这两个值。

模型层不用改（两字段 nullable），但**这两处校验必须重写**。

### 2.4 顺带必修的真实 bug（不修则验收数据不可用）

`api/accounts.py:190-201`，creator 账号健康检查**必定被误判为 expired**：

- `:194` 的 `XHS_Creator_Apis()` 缺 `auth` 参数 → 被 `xhs_creator_apis.py:129-134` 的 `isinstance(auth, XHSCreatorAuth)` 校验抛 TypeError
- `:195` 的 `get_fileIds("image", creator_cookies)` 把 cookies 传给了 `proxies` 形参
- 结果 `:200` 的 except 把 `:182` 刚设好的 `status="active"` 覆盖成 `"expired"`

**必须在迁移前修掉**：否则迁移期的验收数据里，「登录态真失效」和「这个 bug」无法区分，**你会失去唯一的判断依据**。

## 3. 关键反直觉发现：「删掉算法层」是错觉

这是本文最重要的部分，也是 `docs/10` 的收益表最容易被误读的地方。

### 3.1 采集主接口正好在 RAP 白名单里

`apis/xhs_pc_apis.py:37-44`：

```python
_RAP_PATH_MARKERS = (
    "api/sns/web/v1/homefeed",
    "api/sns/web/v1/search/notes",
    "api/sns/web/v2/search/notes",
    "api/sns/web/v1/user_posted",
    "api/sns/web/v1/feed",
    "api/sns/web/v1/comment/post",
)
```

而 `v1/search/notes`、`v1/feed`、`v1/user_posted` **正是采集链路的核心接口**。

`docs/10 §2.2` 已指出「x-rap-param 不会被平台拦截器自动补」。**把这两件事叠起来，结论变得尖锐**：

> **采集链路——也就是浏览器方案收益最大的那条链路——恰恰是在 RAP 白名单里的那条。**

于是采集只能二选一：

| 方案 | 代价 |
|---|---|
| **DOM 驱动**（平台页面自己发请求，天然带 x-rap-param） | 慢（等渲染）、**脆弱**（DOM 结构变了选择器就废）、并发更差 |
| **页面上下文 fetch + 保留本地 `rap.js`** | 省不掉 `rap.js`+`rap_crypto.js`+`rap_cli.js`+`profile.js`（**约 13.7KB / 350 行**），且每次都要起 Node |

**两条路都拿不到「采集链路零签名维护」这个头号收益。**

**对收益的修正**：如果采集走 DOM 驱动，换来的收益是「签名零维护」但代价是「DOM 选择器维护」；如果走 fetch，`rap` 系代码原地保留。**无论哪条，`xhs_utils` 都不可能被删除**。

### 3.2 上传链路明确不动，Node 依赖原地保留

`docs/10 §2.5` 已判定上传链路不建议浏览器化（独立签名 + 直传 ROS 对象存储 + 二进制流）。这意味着：

- `xhs_creator_signature.js` + `xhs_creator_util.py`（PyExecJS）**必须保留**
- **Node 运行时必须留**在镜像和部署里
- `deflate.js` / `aes_*.js` 属稳定通用算法，也不会删

**推论**：切换完成后，部署栈是 **Python + Node + Chromium 三者并存**——比现在**更重**，不是更轻。`docs/10 §6` 写「`apis/` + `xhs_utils/` 不删除，作为降级路径保留」是正确的，但要意识到这意味着**新旧两套成本的叠加期会很长**。

### 3.3 收益兑现是「递延」的，不是「即时」的

承接上一条，把逻辑推到底：

```
阶段一（登录走浏览器）：算法层保留 ← 双份成本，收益为 0（除了登录变稳）
阶段二（采集走浏览器）：算法层仍保留（降级路径 + RAP 可能还需要）
阶段三（发布走浏览器）：算法层仍保留（上传链路要它）
        ↓
  只有在「确认新路径稳定运行足够久、且 RAP 也能去掉」之后
  才真正删除 rap.js 等文件 → 收益才兑现
```

> **在能删除文件之前，你付出的是「双轨成本」，拿到的是「潜在收益」。**
> 这不是否定方案，而是纠正预期：**不要把收益写在切换当天，要写在「降级路径正式下线」那天**。如果团队因为收益迟迟不兑现而中途放弃，双轨成本会白付。

## 4. 代价侧：持续成本（这是最容易被低估的）

### 4.1 性能与并发：损失真实存在

`docs/10 §3.1.1` 已实测：

| 项 | 现方案 | 浏览器方案 |
|---|---|---|
| 单请求本地签名 | **49.2ms**（`sign.js`）+ **54.9ms**（`rap_cli.js`）= **103.7ms** | — |
| 页面内同源 fetch | — | **≈205ms**（签名已由平台算好） |
| 页面导航（每新页面） | — | **≈2.1s** |
| 单 context 内存 | — | **≈150-300MB** |

**注意一个容易漏掉的对比细节**：上面 103.7ms 是「当前方案**多付的**成本」，而浏览器方案的 205ms 是「**另一套**成本」。**两者不是同类项直接相减**——现方案还有网络往返，浏览器方案还有导航摊销。**真实差距是 5-10x 量级，而不是 2x。**

**并发是更硬的天花板**：

| 指标 | 现方案 | 浏览器方案 |
|---|---|---|
| 并发模型 | 异步 HTTP + 连接池 | 每账号一个 context，CPU/内存受限 |
| 资源/并发单元 | ~MB 级 | **150-300MB** |
| 10 个账号并发 | 无压力 | **1.5-3GB 内存** |

如果账号规模会增长到几十个，**内存成本会线性增长**，而现方案几乎不增长。

### 4.2 自动运营的调度模型必须重构（不是优化）

现状 `scheduler_service.py:719` 是 **60s 轮询** `auto_tasks`，实为常驻循环。浏览器**不可能**按这个频率常驻。

必须改成：按 `schedule_interval_hours`（`models/auto_task.py:26`，默认 24，最小 1h）调度 + **按需拉起浏览器、跑完即销毁**。

**这不是「顺手优化」，而是架构改动**，且带来一个新的权衡：**浏览器冷启动 + 页面导航的开销（约 2.4s）在每个任务上都要重付一次**，无法像 HTTP 方案那样靠常驻进程摊薄。

### 4.3 新增单点故障：浏览器网关

`docs/13` 建议做成独立进程（这是对的），但独立进程意味着**新增一个单点**：

| 故障 | 影响 | 现方案对比 |
|---|---|---|
| 网关进程崩溃 | 所有浏览器链路全断 | 无此风险 |
| Chromium 内存泄漏 | 需定期重启，重启期间链路中断 | 无此风险 |
| 僵尸 Chromium 进程堆积 | 资源耗尽 | Node 子进程是短生命周期的，风险低得多 |
| Chromium 版本升级引入行为变化 | 需回归测试 | Node 升级影响面小得多 |

**推论**：必须为网关建设**健康检查、自动重启、并发限额、优雅降级到旧路径**这一整套机制——这些全是要写的代码，**且不属于「迁移」，属于「新建一个服务」**。

### 4.4 多副本部署问题会被放大

`docs/13` 已指出调度器与 FastAPI 同进程、多 worker 会重复执行定时发布。浏览器方案让这个问题**更严重**：

- 浏览器 context **不能跨进程共享**，多 worker 下每个进程会各起一套浏览器 → 内存爆炸
- 同账号的写操作（发布）必须有 **账号级互斥锁**，否则「驱动表单 + 点发布」这种慢操作比 HTTP 请求**更容易发生重复发布**

> 对齐一下严重性：**采集失败重试无害，发布重复是真实事故**。浏览器方案下发布的并发控制**必须做扎实**，这是设计约束而非可选项。

### 4.5 新增脆弱面：注入的页面脚本

| 脆弱来源 | 现方案 | 浏览器方案 |
|---|---|---|
| 签名失效 | 有（全局、致命） | 无 |
| **DOM 结构变化** | 无 | **有**（局部、可修） |
| **平台反自动化检测** | 无 | **有**（需持续对抗） |
| **平台 CSP / 页面改版导致注入失败** | 无 | **有** |

**净判断**：脆弱点的**数量**变多了，**严重性**降低了。这是「把一次性致命故障换成多处轻微故障」，通常是好交易——但**前提是团队有监控能力发现这些轻微故障**。现方案「签名失效会立刻全量报错」反而是个好特性：**失败很响**。浏览器方案下，采集少了几条、某字段空缺，**可能几天没人发现**。

### 4.6 可观测性与调试难度上升

| 维度 | 现方案 | 浏览器方案 |
|---|---|---|
| 每个请求可见性 | **高**（HTTP 请求/响应完整可见） | 中（需 CDP 拦截 + 日志基建） |
| 问题定位 | 看日志 → 定位到具体请求参数 | 要看浏览器内部状态、页面脚本执行情况 |
| 复现 | 容易（构造请求即可） | 难（依赖页面状态、时序） |
| 回归测试 | 容易 | 难 |

**这是实打实的效率损失**，且**需要额外投入建设**（CDP 日志、页面截图留证、失败现场 dump）。这笔投入往往在估算时被漏掉。

### 4.7 部署与环境成本

| 项 | 变化 |
|---|---|
| Docker 镜像 | 增加 Chromium（约 +200MB 起） |
| 依赖 | 新增 Playwright/Puppeteer 类依赖（当前 `requirements.txt` 中 playwright/selenium/pyppeteer 数量 = **0**） |
| 资源诉求 | **从 CPU 型转向内存型** |
| 服务器规格 | 可能需要换更高内存的机器 → **新增固定月度成本** |
| 本地开发 | 需要能跑浏览器（Windows 开发机没问题，Linux CI 需 headless 配置） |

## 5. 风险清单（按严重度排序）

### 5.1 【致命】核心机制未验证

`docs/13 §2.3` 已指出但值得再强调：整个方案的效率前提是「在页面上下文 `fetch` 同源接口，平台会自动补签名」。**这个假设尚未在真实浏览器里验证过。**

原生 `fetch` 不可能被自动加请求头，**除非平台 monkey-patch 了全局 `fetch`/`XMLHttpRequest`**。而仓库内 RAP 的证据（按 url+body 现算、只覆盖白名单）反而倾向「平台是按需现算、不是全局透明拦截」。

**如果这个假设不成立**，采集只能退回 DOM 驱动 → 速度更慢、脆弱面更大、§1.1 的收益进一步缩水。

**这是阶段 0 必须跑掉的第一个验证。**

### 5.2 【高】RAP 在白名单上卡住了核心链路

见 §3.1。**直接影响收益规模**，且**没有好的绕法**——要么牺牲速度，要么保留 RAP 代码。

### 5.3 【高】指纹混用风险（`docs/10` 未覆盖）

现有 Cookie 是在**伪造指纹模板**（`reference_profile.json`）下铸造的；新浏览器是**真实指纹**（真 UA、真 Canvas/WebGL）。同一个账号在迁移期会出现：

```
旧 HTTP 客户端请求 → UA / 指纹 = reference_profile.json 的模板
浏览器请求       → UA / 指纹 = 真实 Chrome
        ↓
   同账号、同 Cookie、两套设备指纹
```

**如果平台做「浏览器指纹 ↔ Cookie 设备标识」一致性校验，迁移期反而是风控暴露最大的窗口。**

**未验证**，但风险方向明确。**建议的缓解措施**：灰度维度用**按账号整体切换**（一个账号要么全浏览器、要么全 HTTP），**不要按链路灰度**。

> 这一点与 `docs/10 §5` 的「按链路灰度」建议**冲突**。`docs/10` 从「回退成本最小」角度想，是对的；但从「风控一致性」角度，按链路灰度会让每个账号都处于混用状态。**建议阶段一/二用账号级灰度，阶段三再考虑链路级**。

### 5.4 【高】发布是写操作，浏览器方案下更难保证幂等

DOM 驱动发布 = 「填表单 + 点按钮」，**没有幂等的请求 ID**可做去重。网络卡顿、页面超时、脚本重试都可能点两次。

**建议**：发布前必须查平台侧「最近已发布列表」做前置校验，并在本地 `publish_jobs` 用账号级锁 + 状态机严格串行。

### 5.5 【中】「维护成本归零」不等于零

准确表述是：**签名零维护，但新增了 DOM / 注入 / 反检测的维护**。

- 平台改 DOM 结构 → 选择器失效（比签名好修，但**可能改版频率更高**）
- 平台加强反自动化 → 需持续投入 stealth 对抗
- 浏览器版本升级 → 需回归

**净收益仍是正的**（DOM 维护的门槛远低于逆向签名），但不能按「零」做预算。

### 5.6 【中】性能天花板限制了未来的业务形态

如果未来要做**高频采集**（如关键词监控、竞品实时追踪，接近 1 QPS 常驻），浏览器方案的导航与页面开销会成为**真实瓶颈**，且**无法通过加机器线性解决**（每并发 150-300MB）。

**这需要现在就想清楚**：这次切换会**锁死「高频采集」这个产品方向**。如果那是路线图上的事，现在就要重新权衡。

### 5.7 【中】合规风险不因技术方案改变

切换不改变「是否遵守平台协议」这个问题。反而要意识到：浏览器方案是**更明确的「模拟真人操作」**，在合规判断上不构成任何缓冲。

## 6. 把假设变成数据：阶段 0 要拿到的三组数字

**这是本文最可执行的建议。** `docs/10` 已经论证了「可行」；现在真正缺的不是可行性，而是**决策数据**。

| # | 要测的量 | 怎么测 | 为什么决定成败 |
|---|---|---|---|
| 1 | **裸 `fetch` 是否被平台签名** | `docs/13 §2.3` 的 6 步 spike | 决定采集是「极简」还是「DOM 驱动」，直接决定收益规模与成本 |
| 2 | **算法返工频率** | 无本地数据（§证据限制）。方法：检查 `xhs_utils` 中各 JS 文件的**上游来源/版本标记**；或用 `data/` 下历史数据的**时间分布**反推「上次平台改版导致采集中断」的时间点 | **这是整个决策的分母**。没有它，所有「值不值得」都是感觉 |
| 3 | **指纹一致性是否被校验** | 用同一账号，分别用「旧客户端 Cookie + 真实浏览器」和「旧客户端 Cookie + 旧客户端」发同类请求，比对是否出现异常响应/额外验证 | 决定灰度维度（§5.3），也决定迁移期风险窗口大小 |

**补充第 4 项（低成本高价值）**：先只做**巡检链路的浏览器化**。它是只读的、无需签发、零接口配额消耗，**可以在不改任何架构的前提下验证「浏览器上下文能否稳定复用登录态」**——这是整个方案的地基假设，用一个最小的改动就能验。

## 7. 逐链路净收益评分

| 链路 | 收益 | 代价 | 净收益 | 建议 |
|---|---|---|---|---|
| **登录** | ★★★★★（冷链全免维护，当前最痛） | ★★（需重写 `login_sessions.py` 两道校验） | **★★★★★** | **先做**，收益最大风险最低 |
| **巡检** | ★★★★（零配额、更稳） | ★（几乎无） | **★★★★★** | **和登录一起先做**，验证地基假设 |
| **采集** | ★★★（被 RAP 白名单打折，见 §3.1） | ★★★★（慢、DOM 脆弱、需 CDP 通道） | **★★** | 做，但**先跑 spike 再定形态** |
| **发布** | ★★★（写操作风险高，收益被 RAP 抵消） | ★★★★★（重复发布风险、慢、DOM 脆弱） | **★** | **最后做**，且必须先做幂等防护 |
| **上传** | ☆（本就稳定） | ★★★★★（二进制流经浏览器成本极高） | **负** | **不做**，维持现状 |
| **自动运营** | ★★（随采集/发布而定） | ★★★★（60s 轮询必须重构为小时级） | **★** | 跟随发布链路推进 |

**结构解读**：净收益集中在**只读、低频、接口简单**的链路上（登录、巡检），而在**写操作、高频、复杂组装**的链路上（发布、自动运营、上传）净收益很低甚至为负。

> **这个分布本身就给出了实施策略：先吃掉两头最肥的（登录 + 巡检），中间那条（采集）用 spike 定形态，尾巴（发布/上传）能不动就不动。**

## 8. 最终判定

| 问题 | 判定 |
|---|---|
| 切换的净收益是正的吗？ | **是，但主要来自登录 + 巡检 + 失效自恢复，而不是「删掉算法层」** |
| 「删掉近万行复杂算法」成立吗？ | **不成立**。真实可退出维护的约 **70KB/1600行/9个文件**；`rap` 系（13.7KB）在采集链路上很可能保不住；上传链路的独立签名必须保留；**Node 依赖不会消失** |
| 收益什么时候兑现？ | **递延**。在旧路径正式下线前，是「双轨成本 + 潜在收益」。中途放弃则白付 |
| 代价里最容易被低估的是什么？ | **① 浏览器网关的持续运维 ② 可观测性建设 ③ 内存成本随账号线性增长 ④ 发布幂等控制** |
| 最大的认知风险？ | 把收益写在切换当天。**实际应写在「降级路径下线」那天** |
| 最大的落地风险？ | **灰度维度**（§5.3 指纹混用）。建议**按账号**而非按链路灰度 |
| 建议动作 | ① 修 `api/accounts.py:190-201` 的 bug（否则验收数据不可用）② 跑 §6 的三组数据 ③ 先做登录 + 巡检 ④ 采集用 spike 定形态 ⑤ 发布/上传先不动 |
| 什么情况下应该**不**做？ | 如果路线图上有**高频采集**（接近 1 QPS 常驻），或账号规模会到**几十个以上**（内存线性增长），则性能与资源的代价会压倒收益，**此时应维持现方案 + 投入监控告警把「失效发现时间」压短** |
