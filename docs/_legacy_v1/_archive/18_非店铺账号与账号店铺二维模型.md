# 18 · 非店铺账号：账号 × 店铺的二维模型

> 本文是 `docs/17` 的上游设计补充。`docs/17` 处理**店铺层**（三种店铺类型如何统一），本文处理**账号层**（有店铺的账号与没有店铺的账号如何统一）。
> 本文**修正** `docs/17` §4.3 中 `sub_type="shop"` 的设计（见 §6、附录 B）。
> 本文不改变路线选择（路线 C：人工 Cookie 导入 + 只读逆向 + 复用 creator 发布）。

---

## 0. 需求与核心判断

**需求**：账号有两种形态——**有店铺的账号**和**没有店铺的账号（非店铺账号）**，两种都须支持。

**核心判断**：

> 「有没有店铺」是**业务维度**，「账号走哪条技术链路」是**协议维度**。**把前者塞进 `sub_type`，就是用业务状态去驱动技术路由。**

这一条比 `docs/17` 的判断更硬，因为它还多了一层后果：`sub_type` 是 `_select_adapter` 的路由依据（`api/accounts.py:57-58`），**改错 `sub_type` 会直接换掉登录适配器，导致登录态失效**。

正确的做法：

```
sub_type        ∈ {pc, creator}        ← 只表达协议链路，不含业务含义
shop_count      ∈ {0, 1, ..N}          ← 由 shop_account_bindings 推导，不是字段
```

**「非店铺账号」= `sub_type="creator"` 且 `shop_count = 0`。**

---

## 1. 「非店铺账号」到底是什么

需求口头语可能对应三种情况，三者在本设计下**收敛到同一个模型**，不需要分别处理：

| 可能的含义 | 本模型下的表达 | 是否需要新代码 |
|---|---|---|
| (a) 没开店的小红书创作者账号 | `creator` + 0 个 binding | 否 |
| (b) 千帆后台里的子账号但未绑定店铺 | `creator`（或独立 `shop` 账号）+ 0 个 binding | 否 |
| (c) 现有 pc 采集账号（与"店铺账号"对照举例） | `pc` + 0 个 binding | 否 |

**这里有一个让人安心的事实**：现有代码里**从来不存在"账号必须绑店铺"的校验**。全部 creator 相关守卫只看 `sub_type`：

- `api/platforms/xhs/creator.py:76-81` → 只校验 `sub_type == "creator"`
- `api/publish.py:415` / `:453` → 只校验 `sub_type == "creator"`
- `services/scheduler_service.py:124` → 只校验 `sub_type == "creator"`

**所以非店铺账号在系统里一直是可用的、合法的、零改动的。** 它只是一直没有名字，也没被产品化。这一点很重要——它意味着本次需求是**把既有能力显性化**，而不是新建一套机制。

## 2. 反模式：把账号形态做成 `sub_type` 的第四种取值

```python
# 不要这样
if account.sub_type == "shop":
    shops = fetch_shops(account)
else:
    shops = []          # ← 非店铺账号
```

四个代价，其中前两个是 `docs/17` 的代价，后两个是本文新增的：

1. **映射是猜测**：creator 账号既可能有店也可能没店，`sub_type` 无法表达"creator 且无店"
2. **无限扩展**：还要区分"店铺账号" vs "个人店账号" vs "企业子账号"……每加一种重付一次
3. **改绑即改路由（新增）**：`_select_adapter`（`api/accounts.py:57-58`）是 `creator → creator_adapter`，**否则一律 pc_adapter**。用户今天开店、明天关店，如果这改动 `sub_type`，登录适配器会跟着变，登录态立刻失效
4. **状态与事实不同源（新增）**：`sub_type` 是静态字段，"有没有店铺"是**平台侧事实**。一旦二者不一致（店铺被平台关停、子账号被移除绑定），系统会拿一个过期的本地字段当真，且没有任何机制能发现

## 3. 正模式：两个正交维度

```
账号（platform_accounts）
   │
   ├─ 维度 A｜协议链路：sub_type          → 决定 adapter、域名、cookie 域
   │      pc  /  creator
   │
   └─ 维度 B｜业务关系：shop_account_bindings（0..N 行）  → 决定能力集
          ↓
       能力解析（§5）
          ↓
       逻辑分支只读能力
```

**关键性质**：两个维度**正交**。任何组合都合法，且**组合数不进入代码**——代码只读能力解析结果。

## 4. 全域组合矩阵

| | `shop_count = 0` | `shop_count ≥ 1` |
|---|---|---|
| **`sub_type = pc`** | 采集/巡检专用号（现状主力） | 理论上可能，实际少见 |
| **`sub_type = creator`** | **非店铺账号（本次新增场景）** | 店铺账号 = 发布端 |

两种账号在五条链路上的可用性：

| 链路 | pc + 0 店 | **creator + 0 店（非店铺）** | creator + N 店 |
|---|---|---|---|
| 搜索采集 | ✅ 主力 | ✖（`crawl.py:220` 要求 pc） | ✖ |
| 评论抓取 | ✅（`notes.py:436` 要求 pc） | ✖ | ✖ |
| 普通笔记发布 | ✖（`publish.py:415` 要求 creator） | **✅ 零改动** | ✅ |
| 挂商品笔记发布 | ✖ | **✖（无店铺可挂）** | ✅ 视 `can_attach_goods` |
| 商品数据同步 | ✖ | ✖ | ✅ 视 `can_sync` |
| 店铺列表 | ✖ | **空列表（不是错误）** | 有 |

**读法**：非店铺账号不是"残缺的店铺账号"，而是**另一条产品线的完整主体**——它能做的事（普通笔记发布）并不比店铺账号少，只是**能挂的商品数为 0**。

## 5. 能力解析：唯一入口

`docs/17` §9 已经指出"子账号权限粒度"要求探测按**账号+店铺组合**维度做。非店铺账号把这一点从"边界情况"变成了**常态**——因为最常见的调用就是"账号没有店铺"。

因此能力解析的签名必须是二元输入：

```python
def resolve_capabilities(account, shop=None) -> Caps:
    """
    shop=None  → 返回账号级基础能力（不涉及挂商品）
    shop=S     → 先查 binding(account, S) 是否存在，再合并 S.capabilities_json
    """
```

解析顺序（短路，任一步失败即返回保守默认）：

```
1. binding 是否存在？
   ├─ 否 → can_attach_goods=False, can_publish_note=基础值   ← 非店铺账号走这条
   └─ 是 ↓
2. 该 binding 是否有账号级限制？（docs/17 §9 的子账号权限粒度）
3. 合并 shop.capabilities_json
4. capabilities_verified_at 是否过期（>7 天）？→ 过期先重探
```

**账号级基础能力**（与店铺无关，两种形态共有）：

| 能力键 | 含义 | 非店铺账号 |
|---|---|---|
| `can_publish_note` | 能否发普通笔记 | ✅（creator 链路天然具备） |
| `can_browse_goods` | 能否浏览商品库 | ✅（只读，无绑定要求） |
| `has_shop` | 派生：`shop_count > 0` | ❌ |
| `shop_count` | 派生：绑定店铺数 | `0` |

**`has_shop` / `shop_count` 建议作为 API 派生字段返回，不落库。** 落库就变成了需要同步的状态，而它是可以随时从 `shop_account_bindings` 算出来的。

## 6. 数据模型：修正 `docs/17` §4.3

`docs/17` §4.3 原文建议"千帆登录态存 `platform_accounts`，`sub_type="shop"`"。**本文修正这一条**，因为它与非店铺账号的模型冲突：

| 方案 | `sub_type` 取值 | publish/creator 守卫 | 结论 |
|---|---|---|---|
| `docs/17` 原设计：新增 `shop` | `{pc, creator, shop}` | **shop 账号会被 `publish.py:415` 拒绝** | 需连带改 13 处后端守卫 |
| **本文推荐：不新增类型** | 维持 `{pc, creator}` | 不动 | ✅ |
| 备选：新增但限定只读 | `{pc, creator, shop}` | shop 账号**永不发布**，发布只走 creator | 可用，但要改 pattern 与巡检适配器 |

**推荐做法**：**`sub_type` 保持 `{pc, creator}` 不变。**

- 「有没有店铺」由 `shop_account_bindings` 的存在性推导
- 千帆登录态**优先复用 creator 账号的 Cookie**（`docs/16` 已提出这个可能：若千帆与创作者后台共用 `a1` / `web_session`，连人工导入都省掉）→ 阶段 0 验证
- 只有当千帆确实需要**独立登录态**时，才引入 `sub_type="shop"`，且该类型**明确定义为只读同步用途、永不承担发布**，同时必须改 `api/accounts.py:35` 的 pattern 与 `scheduler_service.py:652` 的适配器选择

**表结构增量**：`docs/17` §4.1 的 `shops` / `shop_account_bindings` / `shop_products` / `product_note_jobs` **全部有效，无需改动**。本文不新增表。

**唯一需要补的语义**是：`product_note_jobs.creator_account_id_fk` **允许指向非店铺账号**（见 §7）。

## 7. 非店铺账号在商品笔记流程里的角色（本文最重要的推论）

原流程（`docs/15` / `docs/16`）隐含假设：**商品来源账号 = 发布账号**。非店铺账号打破了它。

正确的分工：

```
商品库（店铺账号 A 同步）
      │
      ├─→ 挂链笔记  →  发布账号必须是「绑定该店铺的 creator 账号」  ← 店铺账号
      │
      └─→ 种草笔记  →  发布账号可以是任意 creator 账号            ← 非店铺账号也在其中
```

**这意味着 `docs/17` §6.3 的"降级路径"需要重新定性。**

`docs/17` 把它描述为"无挂商品能力时的降级"。但非店铺账号的存在说明它其实是**独立的业务模式**：

| | 挂链商品笔记 | 不挂链种草笔记 |
|---|---|---|
| 目的 | 直接转化 | 内容种草 / 铺量 / 养号 |
| 账号要求 | 店铺账号 + `can_attach_goods` | 任意 creator 账号 |
| 账号池规模 | 受店铺数限制（可能 1-3 个） | **不受限（可几十个）** |
| 内容同质化风险 | 低 | **高**（多号发同款内容） |

**由此产生一个新增业务能力**（`docs/15` 未覆盖）：

> **同一商品 × 多账号矩阵分发**——店铺号挂链发布 1 篇，N 个内容号各发 1 篇不挂链种草笔记。

这解释了非店铺账号为什么值得被单独立项：**它是矩阵铺量的载体**，而店铺账号的数量被平台（一执照最多 3 店）天然限制住了。

### 8.3 需要修的既有 bug（影响非店铺账号）

`api/accounts.py:190-201` 的 creator 健康检查 bug（`docs/13` 已记录）：`XHS_Creator_Apis()` 缺 `auth` 参数 → 必抛 TypeError → **`POST /accounts/{id}/check` 对 creator 账号从未成功过**。

**非店铺账号让这个 bug 的优先级上升**：非店铺账号就是 creator 账号，而矩阵铺量场景下账号数量多、以编程方式批量探活是常态——**主力账号群体的健康检查现在是 100% 误报**。

## 9. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **营销号识别（本文新增，最高）** | 非店铺账号发布商业推广内容，平台对"无店铺账号发营销内容"的判定更严 | 内容差异化（非改写而是重写）；控制频率与账号活跃画像；**不做跨账号同文分发** |
| **内容同质化** | 矩阵分发时多号发同款商品内容，易触发去重降权 | 同一商品的内容模板必须按账号维度变异；加入标题/结构/图片版式扰动 |
| **账号数量带来的巡检压力** | 非店铺账号可能几十个，2h 巡检全量探活会放大配额消耗与风控暴露 | 复用 `docs/14` 结论：把"cookie 是否存在"作为低成本前置判断，避免无谓探活；巡检按账号状态分级，低风险账号降频 |
| **creator 巡检 bug（既有）** | 见 §8.3，主力账号群体健康检查全误报 | 阶段 0 一并修复 |
| **类型新增的静默路由** | 若未来真引入 `sub_type="shop"`，两处 `else` 兜底会静默走错 | 改为显式枚举 + `raise`（§8.1 注） |
| **模型误用** | 开发者可能直接读 `account.sub_type` 判断"是不是店铺账号" | 代码评审规则：**判断店铺关系只能读 binding / 能力解析结果**；`sub_type` 仅用于 adapter 路由 |

## 10. 阶段 0 追加验证项

在 `docs/17` §8 基础上追加：

1. **千帆登录态能否复用 creator Cookie**（决定是否引入 `sub_type="shop"`，也决定 §6 的取舍）
   - 用已登录 creator 账号的 Cookie 请求一个 ark 只读接口，看是否 401
   - 可为是 → 非店铺账号与店铺账号共用一条链路，**改动面进一步缩小**
2. **非店铺账号实际占比**：现有 creator 账号中有多少没有绑定店铺（决定前端 badge 与默认行为的排列顺序）
3. **非店铺账号发布普通笔记的完整链路**：走一遍 `publish.py` 的 creator 路径，确认无隐藏的店铺依赖
4. **一个 creator 账号能否同时绑定多家店铺**（与 `docs/17` §8 的子账号问题同源，验证 N:M 是否真实存在）
