# XHS_ALL_IN_ONE 业务流程

> 六条核心链路的逐步流转。所有状态码/字段名均从代码中核实。

---

## 1. 账号接入（三种登录方式）

```
前端选择登录方式
   ├── 扫码登录       → login_sessions 创建会话 → 轮询二维码状态
   ├── 手机验证码     → login_sessions 创建会话 → 发送/校验验证码
   └── Cookie 导入    → 直接导入 Cookie 字符串
       ↓
适配层校验 Cookie（pc_login_adapter / creator_login_adapter）
       ↓
写 platform_accounts（sub_type = pc | creator）
       ↓
追加 account_cookie_versions（Fernet 加密，不覆盖写）
```

**关键设计**：

- **双账号类型**：`sub_type=pc` 负责**搜索采集**，`sub_type=creator` 负责**上传发布**。自动运营任务必须同时绑定两者。
- **Cookie 多版本**：每次登录/导入都 `append` 新版本，取用时按 `created_at desc, id desc` 取最新。可回溯历史。
- **PC → Creator 换取**：`creator_login_adapter.exchange_from_user_cookies` 可用 PC Cookie 换 Creator Cookie，免去二次登录。
- **加密**：`security.encrypt_text()` 用 Fernet；`fernet_key` 为空时由 `secret_key` SHA-256 派生。

**健康巡检**（`cookie_health_checker`，每 2 小时）：

```
遍历全量 platform_accounts
  → 取最新 cookie_version 解密
  → adapter.get_user_info() 探活
  → 成功: status=active；失败: status=expired + status_message
  → 新过期（old != expired）→ 写 Notification（level=warning）
```

## 2. 采集入库

### 2.1 搜索采集

```
前端输入关键词 + 筛选条件
  → POST /api/xhs/pc/search/notes（或 /api/xhs/crawl/search-notes）
  → XhsPcApiAdapter.search_note(keyword, page)
  → direct_xhs_request_env() 摘掉代理环境变量
  → SDK: XHS_Apis.search_note → curl_cffi（chrome146 指纹）+ Node 签名
  → 返回原始 JSON
  → _normalize_search_item() 归一化为统一结构
  → （可选）save_to_library=true → 批量 upsert 到 notes
  → asset_downloader 下载无水印图/视频到 storage/media/
  → note_assets 记录本地路径
```

### 2.2 URL 直查 / 用户笔记 / 评论

| 入口 | 路径 | SDK 方法 |
|---|---|---|
| URL 直查 | `/api/xhs/crawl/note-urls` | `get_note_info` |
| 用户笔记 | `/api/xhs/crawl/user-notes` | `get_user_all_notes` |
| 评论抓取 | `/api/xhs/crawl/data`（mode=comments） | `get_note_all_comment`（递归展平二级评论） |

**注意**：真实评论抓取走 `crawl` 模块的 `/api/xhs/crawl/data`（mode=comments）。`/api/xhs/pc/notes/comments` **也接了真实接口**（`pc.py:364` → `adapter.get_note_comments`），与 crawl 模块共用 `normalize_comment_payload`，两条入口都能取评论；pc.py 中 `note_comments_placeholder()`（`:382`）是**未被路由引用的死函数**。pc.py 里真正返回 mock 的是 `/users/notes`（`:386`）与 `/homefeed/*`（`:391,396`）。

### 2.3 内容库管理

- `notes` 支持**卡片/列表双视图**、自定义标签（`tags` + `note_tags` 多对多）、关键词搜索、批量操作、JSON/CSV 导出（`storage/exports/`）。
- 素材可拖拽排序（`@dnd-kit`，`a54213910de0_add_sort_order_to_note_assets` 迁移）。

## 3. AI 改写与草稿工坊

```
内容库笔记
  → 深拷贝为 AiDraft（保留标题/正文，不污染原笔记）
  → 三栏编辑器：草稿队列 | 编辑器 | AI 助手
       ↓
  AI 能力（均走 OpenAICompatibleTextClient，端点用户自配）：
    ├── rewrite_note()    改写正文（保留事实，小红书语感）
    ├── generate_titles() 生成标题（解析「标题：」前缀）
    ├── generate_tags()   生成标签（去 #、按逗号/换行切分）
    ├── polish_text()     润色片段
    └── generate_note()   从选题+参考材料整篇生成
       ↓
  DraftAsset 管理草稿素材（可拖拽排序）
  → 编辑完成「送入发布中心」→ 创建 PublishJob + PublishAsset
```

**AI 服务设计**：

- `TextAiClient` / `ImageAiClient` 是 **Protocol**（接口），`OpenAICompatible*Client` 是唯一实现 —— 支持**任意 OpenAI 兼容 API**（火山引擎、阿里云百炼、OpenAI 中转等）。
- 模型配置存 `model_configs`（`model_type` = text | image），API Key 用 Fernet 加密，可设默认、可测连通性。
- 响应解析做了**多编码兜底**（utf-8-sig → utf-8 → apparent → encoding），避免中文乱码导致 JSON 解析失败。

## 4. 发布中心

### 4.1 流程

```
草稿「送入发布中心」
  → 创建 PublishJob（publish_mode = immediate | scheduled）
  → 创建 PublishAsset（asset_type，当前仅 image）
       ↓
素材上传 Creator
  → creator_api_adapter.upload_media(file_path, "image")
  → _resolve_file_data(): 支持 http URL / /api/files/media/ 本地路径 / 本地磁盘路径
  → webp 自动转 JPEG（PIL quality=92，Creator 不收 webp）
  → publish_assets.creator_upload_info = {"fileIds": ...}（JSON）
       ↓
发布
  ├── immediate → 直接 post_note
  └── scheduled → scheduled_at 落库，等 due_publish_runner 补跑
       ↓
  _post_uploaded_image_note()（见下）
       ↓
  成功: status=published + external_note_id + published_at
  失败: status=failed + publish_error（可重试/取消）
```

### 4.2 发布实现关键（`_post_uploaded_image_note`）

图集发布**不走** SDK 的通用 `post_note`，而是自行组装请求（浏览器实抓对齐）：

1. `get_post_note_image_data()` 组装业务体；
2. **未选地点时必须 `data["common"].pop("post_loc", None)`** —— 空地点对象会被服务端以参数错误打回；
3. 逐条 `get_topic` 解析话题 → 拼接 `#{name}[话题]#` 进 `desc`，并 append 到 `hash_tag`；
4. 手动补 `x-rap-param` 头（`generate_x_rap_param` + Creator rap 指纹 hex）；
5. 校验 `payload.success`，失败抛 `RuntimeError(msg)`。

### 4.3 发布选项

`publish_options`（JSON 列）承载所有非正文选项：

| 字段 | 含义 |
|---|---|
| `topics` | 话题列表（字符串数组） |
| `location` | 地点（字符串，发布时查 POI） |
| `privacy_type` | 0 = 公开，1 = 私密 |
| `is_private` | `privacy_type` 的布尔别名（双向同步） |
| `draft_tags` | 兜底：topics 为空时用草稿标签 |

**定时发布补跑**（`run_due_publish_jobs_for_all_users`）：按 user 遍历到期 job → 校验账号归属与类型（必须是 creator）→ 执行 → 无论成败都写 `Task` 审计记录。

## 5. 自动运营（无人值守管线）

### 5.1 配置

`auto_tasks` 表：关键词列表、`pc_account_id`、`creator_account_id`、`ai_instruction`、`schedule_type`（manual / daily / weekly / interval）、`next_run_at`、`total_published`、`last_run_at`。

> `manual` 类型**只能手动触发**，调度器不拾取（`schedule_type != "manual"` 过滤）。

### 5.2 执行管线（`_execute_auto_task_background`）

```
APScheduler auto_tasks_runner（每 60s，硬编码）
  → 取 status=active 且 schedule_type != manual 且 next_run_at <= now 的任务
  → 取 PC 账号最新 Cookie
  → random.choice(keywords) 随机选一个关键词
  → XhsPcApiAdapter.search_note(keyword)
  → _normalize_search_item 归一化前 10 条
  → max(likes + collects + comments + shares) 选互动最优笔记
  → 创建 AiDraft（标题/正文取自原笔记）
  → AI 改写（非致命，失败也继续）：
       ├── rewrite_note()  → 覆写 body
       └── generate_titles() → 覆写 title（失败静默跳过）
  → 取 Creator 账号 Cookie
  → 逐张 upload_media（最多 9 张，失败跳过该张）
  → 创建 PublishJob（immediate）+ PublishAsset（upload_status=uploaded）
  → creator_adapter.post_note()
  → total_published += 1，last_run_at 更新
  → 无论成败，_calculate_next_run_at() 重算下次运行时间
```

### 5.3 调度安全现状

调度器是 `BackgroundScheduler`，**与 FastAPI 同进程**：

- 多 worker / 多副本部署时**每个进程各起一套定时器** → 发布任务会重复执行（`max_instances=1` 只约束单进程内）。
- 无分布式锁，目前只靠 `scheduler.enabled` 单开关控制。
- `next_run_at` 在执行**之后**才算，任务耗时被计入下一轮间隔。

## 6. 竞品监控

### 6.1 配置

`monitoring_targets`：`target_type`（keyword / account / brand / url）+ `value` + `status`。

### 6.2 刷新逻辑

```
monitoring_refresh_runner（每 interval_seconds）
  → 取全部 active 监控目标
  → 在「已有内容库 notes」中匹配（不是实时爬取！）
       _note_haystack(note) = note_id + title + content + author_name + raw_json（全转小写）
       needle in haystack 模糊匹配
  → 按互动量（likes+collects+comments+shares）降序取 Top 10
  → 写 monitoring_snapshots（payload 含 matched_count / total_engagement / top_notes）
  → 写 Task 审计（task_type=monitoring_refresh）
```

> **重要**：监控「刷新」本质是**对本地内容库的再查询**，不触发新的平台请求。要监控新内容，需先用「数据抓取」入库。

## 7. 通知系统

| 触发 | 来源 | 级别 |
|---|---|---|
| Cookie 过期 | `cookie_health_checker`（2h 巡检） | warning |
| 自动运营失败 | `run_due_auto_tasks` 的 except 分支 | 日志（**未入通知库**） |

前端通知铃铛读 `/api/notifications`，支持单条已读 / 全部已读。

> 观察：`run_due_auto_tasks` 的失败只写 `logger.warning`，**没有写 Notification 表**——自动运营失败时用户在铃铛里看不到。发布失败则只落在 `publish_jobs.publish_error`。

## 8. 平台扩展机制

```
后端 platforms.py 注册表（6 平台，仅 xhs enabled）
  → /api/platforms 返回注册表
  → 前端 platform-select-page 渲染平台卡片
  → 点击非 xhs 平台 → /platforms/:platformId → ComingSoonPage
```

**扩展一个新平台需要补「三件套」**：`adapters/<platform>/` 适配层 + `api/platforms/<platform>/` 子路由 + `pages/platforms/<platform>/` 前端页面。

## 9. 任务审计（Task）

所有可观测的异步动作都写 `tasks` 表：

| task_type | 写入点 |
|---|---|
| `crawl` | `crawl.py` 抓取任务 |
| `creator_publish_scheduler` | 定时发布补跑 |
| `monitoring_refresh` | 监控刷新 |
| 发布/自动运营 | 见各自流程 |

`tasks` 表是「任务中心」页面的数据源（**当前页面读到的是 `task_service` 的 mock 数据**）。

## 10. 各流程的状态机

### PublishJob.status

```
pending → publishing → published
                    └→ failed（可重试回 publishing，可取消）
```

### PlatformAccount.status

```
（无 cookie 版本）→ expired
有 cookie → active（巡检通过）↔ expired（巡检失败或无版本）
```

### AutoTask.status

```
active（可被调度）↔ paused/stopped（手动）
```

### LoginSession

临时会话，登录成功后即完成使命，结果落 `platform_accounts`。
