## 1. 五层调用链与参数流动

```
┌─────────────────────────────────────────────────────────────────────┐
│ ① 前端页面 pages/platforms/xhs/*.tsx                                │
│    ↓ axios（lib/api.ts，/api 前缀，401 自动 refresh token）          │
├─────────────────────────────────────────────────────────────────────┤
│ ② FastAPI 路由 backend/app/api/*.py（131 端点）                      │
│    ↓ 参数校验 + 编排                                                 │
├─────────────────────────────────────────────────────────────────────┤
│ ③ 适配层 adapters/xhs/（上层唯一允许调 SDK 的入口）                  │
│    ↓ 注入 cookies，所有方法包 direct_xhs_request_env()               │
├─────────────────────────────────────────────────────────────────────┤
│ ④ SDK 层 apis/（接口语义） + xhs_utils/（签名算法）                  │
│    ↓ curl_cffi（chrome146 指纹）+ Node 子进程（JS 算法）             │
├─────────────────────────────────────────────────────────────────────┤
│ ⑤ 小红书平台（PC / Creator / 蒲公英 / 千帆）                         │
└─────────────────────────────────────────────────────────────────────┘
```

**核心事实**：从 ③ 到 ⑤ 的数据流是**「cookies 字符串 → 签名参数 → HTTP 请求」**，适配层只传 cookies，不碰签名细节。这是整个方案的关键约束点。

## 3. 签名参数的来源分类（决定浏览器方案能否替换）

这是本次方案分析最关键的一张表。`xhs_utils/xhs_pc/auth.py:21` 的 `PC_PARAMETER_SOURCES` 已把参数分成六类：

| 类别 | 参数 | 浏览器能否生成 | 现状 |
|---|---|---|---|
| **本地纯算** | `b1`、`MNS0101/0201/0301`、`X-s`、`X-t`、`X-S-Common`、`x-b3-traceid`、`xy-direction`、`x-rap-param`、`search_id`、`request_id`、`profileData` | ✅ 能（浏览器本来就是这么算的） | 项目用 Node 子进程算 |
| **逆向对齐覆写** | `b1_state`、`local_storage`、`session_storage`、`xsecappid`、`webBuild`、`envConst`、`envFpTail`、`rap_fingerprint`、`web_profile_*` | ✅ 能（浏览器里天然存在） | 从 reference_profile.json 取静态模板 |
| **托管生命周期状态** | `dsllt`、`mns_seq`、`last_tiga_update_time`、`p1`、`sc`、`XHS_TAB_DEVICE_ID`、`XHS_RWP_FINGERPRINT` | ✅ 能（浏览器自己维护） | 项目在 Python 侧模拟 |
| **远端程序本地执行** | `_dsl`、`websectiga_scripting_code`、`websectiga` | ✅ 能（浏览器天然执行） | 项目拉远端 JSVMP 在本地 `vm` 跑 |
| **服务端下发** | `web_session`、`secure_session`、`id_token`、`gid`、`sec_poison_id`、`acw_tc`、`abRequestId` | ❌ 不能（只能登录换取） | 登录流程获取 |
| **用户交互** | 扫码确认、手机号 + 短信码 | ❌ 不能（必须人/设备参与） | 前端面板驱动 |

**结论（事实层面）**：签名体系的**全部本地计算参数**，浏览器都能自然产生。当前项目用「本地 JS + Node 子进程 + 静态模板」的方式**模拟**浏览器，本质是在重建浏览器环境。这正是无头浏览器方案的可行性基础。

## 4. 每请求签名成本（实测）

| 参数 | 是否每请求重算 | 证据 |
|---|---|---|
| `x-s` / `x-t` | **是** | `generate_xs_xs_common` 每次都调 `run_signer`（`params.py:184`），`sign_context` 含 `now`（当前时间戳）和 `next_seq()`（自增序列号） |
| `x-s-common` | **是** | 同上 |
| `b1` | **否**（有缓存） | `state.py:550` `current_b1`：有 `fixed_b1` 直接返回；`_named_b1_values` 按 profile 缓存 |
| `profileData` | 每请求算 | `generate_profile_data` 每次调 Node |
| `x-rap-param` | 每请求算（覆盖 body） | `xhs_pc/js/rap.js:8,90`：`RequestHash = xxHash32(url_pathAndBeyond + jsonBody, seed=0)`；Python 入口 `params.py:213 generate_x_rap_param` 经 `rap_cli.js` 传 api+body |
| `dsl`（DS 锚点） | 15 分钟刷新一次 | `xhs_creator/state.py:19` `DS_REFRESH_INTERVAL_MS = 15 * 60 * 1000` |

**x-s 签名覆盖请求体**：`sign.js:89` `const c = String(input.api) + dataStr;` —— **换 body 必须重算签名**。这意味着「浏览器算一次签名、后端复用」的思路**只对同一 body 有效**，不同 body 必须回到浏览器重算。

## 5. 登录链路的特殊性（对方案影响最大）

`apis/xhs_pc_login_apis.py` 的登录**不是**调几个接口那么简单，而是一条冷链：

```
generate_init_cookies()        本地生成 a1 / webId（common_util.generate_a1）
  ↓
_initialize_security(cookies)  ★ 冷链安全初始化（最脆弱的一环）
  ├── _fetch_honeypot()        拉蜜罐程序
  ├── _fetch_redcaptcha()      拉验证码程序
  ├── _fetch_sem_sdk()         拉 SEM SDK
  ├── _post_scripting(ds)      拉远端 DS 程序 → 正则取 getdss() → self.dsl
  ├── _fetch_sbtsource()
  └── _post_scripting(sec)     拉远端 sec 程序 → 本地 vm 执行 → websectiga
  ↓
_activate()                    拿匿名 visitor web_session
  ↓
generate_qrcode / send_phone_code
  ↓
扫码确认 / 输验证码
  ↓
_login_by_qrcode_status / login_by_phone   合并正式 web_session
  ↓
ensure_webprofile()            补全设备指纹
```

**关键事实**：登录冷链里 `_post_scripting` 拉的 DS 程序和 sec 程序是**服务端下发的混淆 JSVMP**，项目用本地 `vm.runInThisContext`（`websectiga_cli.js:205`）执行。**这一环在无头浏览器里是最自然、最不需要维护的**——浏览器本来就在执行这些程序。

## 6. 上传链路的独立性

```
upload_media(path, media_type)
  ├── get_fileIds(media_type)          拿上传许可（fileIds / token / expireTime / uploadAddr）
  ├── get_file_info(path)              读文件 + 取宽高（opencv / Pillow）
  ├── signature_js.call('getSignature', message, file_ids, file_size, upload_host)
  │                                     ★ 独立签名（execjs，不走主签名体系）
  └── http.put(upload_url + /spectrum/{fileIds}, headers=..., data=file)
                                        ★ 直传 ROS 对象存储，不经过 XHS 业务网关
```

**关键事实**：上传是**独立的签名体系**（`xhs_creator_signature.js` 的 `getSignature`，PyExecJS 执行），且**直传第三方对象存储**。这条链路对无头浏览器方案**最不友好**——浏览器页面里上传走的是平台的 OSS SDK，自定义页面注入二进制流的成本远高于直接 HTTP PUT。

## 7. 发布链路的业务组装

`_post_uploaded_image_note()`（适配层自实现，不在 SDK 里）：

```
get_post_note_image_data(title, desc, postTime, post_loc, type, image_file_infos)
  ↓
if not post_loc: data["common"].pop("post_loc", None)    ★ 空地点必须删键
  ↓
for topic in topics: get_topic() → hash_tag.append + desc += " #话题[话题]# "
  ↓
headers["x-rap-param"] = generate_x_rap_param(post_api, body, fingerprint_hex)
  ↓
api.http.post(edith_url + post_api, ...)
```

**关键事实**：发布请求的**业务组装**（话题拼接、地点处理、`post_loc` 删除）是适配层自己做的，与签名算法无关。这部分逻辑在浏览器方案里**必须保留**（无论签名怎么来）。

## 11. 结论：对方案二的事实输入

1. **签名参数全部分布在浏览器可产生域内**（本文 §3），本地纯算 + 逆向对齐 + 托管状态 + 远端程序**四类**浏览器都能自然产生。
2. **但 x-s 覆盖请求体**（本文 §4），「浏览器算一次、后端复用」**不可行**（除非 body 不变）。
3. **登录冷链是最脆弱、最值得交给浏览器的一环**（本文 §5）：DS/sec 程序是服务端下发混淆代码，本地 `vm` 执行是逆向工程的重灾区。
4. **上传链路最不适合浏览器化**（本文 §6）：独立签名 + 直传对象存储。
5. **业务组装逻辑（话题/地点/post_loc）与签名无关**（本文 §7），方案二必须保留。
6. **扩展新平台时方案二可省掉整个 SDK 层**（本文 §8）。

这些事实直接决定方案二的形态，详见 [10_无头浏览器方案可行性分析.md](./10_无头浏览器方案可行性分析.md)。
