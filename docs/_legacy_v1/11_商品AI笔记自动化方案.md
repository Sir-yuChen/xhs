# 商品 AI 笔记自动化方案设计

> **命题**：基于无头浏览器方案（见 [10_无头浏览器方案可行性分析.md](./10_无头浏览器方案可行性分析.md)），实现**商品 → AI 自动生成笔记 → 按间隔批量发布**的闭环。
>
> - **分析日期**：2026-09-17
> - **性质**：方案设计文档（**不含代码实现**），供评审与排期
> - **前置约束**：只读分析项目代码，未改动任何源码、配置、依赖

## 0. 一句话结论

**整体可行，但有一个硬前置必须先解决：项目当前没有「商品」概念。**

三个需求拆开看：

| 需求 | 可行性 | 关键约束 |
|---|---|---|
| ① 只监控浏览器真实返回 / 主动调浏览器平台接口取数据 | ✅ **可行** | 两种模式各有适用场景，建议双通道并存 |
| ② 笔记部分扩展：根据商品 AI 自动生成笔记 | ⚠️ **有前置** | 项目**无商品模型**，商品数据从哪来必须先定 |
| ③ 批量按间隔时间发布 | ✅ **可行**（架构已支持） | 现有 `auto_tasks` + `publish_jobs` 的调度能力可复用 |

## 1. 需求①：浏览器数据获取的两种模式

用户明确提到了两种模式，它们**不是互斥的，而是互补的**：

### 1.1 模式 A：被动监控（只监控浏览器真实返回）

```
浏览器正常加载页面 / 执行业务流程
  → CDP 监听 Network.responseReceived / Fetch.requestPaused
  → 匹配关心的接口（URL pattern）
  → 提取响应体 → 归一化 → 落库
```

**特点**：
- ✅ 零侵入，完全不碰签名、不构造请求
- ✅ 拿到的是**平台真实返回**，和用户在浏览器里看到的一模一样
- ❌ **数据取决于浏览器浏览了什么**——不主动搜索就没有数据
- ❌ 只能读，不能写

**适用场景**：Cookie 健康巡检（看是否跳登录页）、账号数据同步（已发布笔记列表）、被动素材积累。

### 1.2 模式 B：主动调用（浏览器上下文内 fetch）

```
浏览器加载平台页面（平台 JS 初始化完成）
  → 自定义脚本在「页面执行上下文」内 fetch 同源接口
  → 平台的请求拦截器自动注入签名（x-s / x-t / x-s-common 平台算）
  → ⚠️ x-rap-param **不会**由拦截器自动补（RAP 白名单路径的发布接口需自理或走平台页面原生请求，见 10 号文档 §2.2）
  → 响应通过 CDP 回传后端 → 归一化 → 落库
```

**特点**：
- ✅ **签名由平台算，永远正确，零算法维护**
- ✅ 主动决定取什么数据（关键词、分页、用户）
- ✅ 拿到结构化 JSON，不用解析 DOM
- ⚠️ 依赖平台 JS 拦截器覆盖目标接口（同源 XHR 一般都覆盖）
- ⚠️ 需要页面保持存活（context 池管理）

**适用场景**：按关键词搜索、笔记详情、评论抓取、商品信息获取。

### 1.3 建议架构：双通道并存

```
┌─────────────────────────────────────────────────────┐
│  BrowserContext（每账号一个，持久化 storageState）    │
│  ┌───────────────┐    ┌──────────────────────────┐  │
│  │ 主动调用通道   │    │ 被动监控通道              │  │
│  │ (InjectScript │    │ (CDP Network 域)         │  │
│  │  → fetch)     │    │  → responseReceived      │  │
│  └───────┬───────┘    └─────────────┬────────────┘  │
└──────────┼──────────────────────────┼──────────────┘
           │                          │
           ▼                          ▼
    采集队列 → 归一化 → 落库（notes / note_assets）
```

**理由**：模式 B 负责「我要的数据」，模式 A 负责「经过的数据顺手存下」。两者共用同一个 BrowserContext 和同一套归一化落库逻辑，成本很低。

## 2. 需求②：商品 → AI 生成笔记 —— 硬前置

### 2.1 项目现状（已核实）

```
grep -rin 'product\|商品\|sku\|spu\|goods' backend/app/models/ → 零命中
```

**项目里没有商品模型、没有商品表、没有商品来源。** 现有的「内容库」（`notes`）装的是**采集来的他人笔记**，不是商品。

千帆 API（`apis/xhs_qianfan_apis.py:get_user_item`）拿到的是**分销商的合作商品**：

```python
url = "https://pgy.xiaohongshu.com/api/draco/distributor-square/distributor/cooperative/item/v2"
data = {"buyer_id": user_id, ...}  # 查的是某个分销商的商品
```

这是「我能分销什么货」，**不是「我店铺里有什么货」**。

### 2.2 商品数据的三个可能来源

| 来源 | 数据内容 | 获取方式 | 适合场景 |
|---|---|---|---|
| **A. 商家自己的商品** | 标题、卖点、主图、价格、规格 | 千帆/商家后台接口，或浏览器打开商品管理页 | 自营店铺带货 |
| **B. 分销商品库** | 分销商品列表 + 详情 | `get_user_item`（已有 SDK），或浏览器打开千帆页面 | 无货源分销带货 |
| **C. 手动导入** | Excel / 手动填写商品信息 | 前端导入 | 测试验证、灰度起步 |

> **这是必须先拍板的问题**：商品数据从哪来？不同来源决定了完全不同的实现路径。
>
> 建议：**先用 C（手动导入）跑通闭环**，再接 A/B。理由是 A/B 都依赖额外的平台接口逆向或浏览器页面分析，而 C 能最快验证「AI 生成 → 批量发布」这条主链路。

### 2.3 建议的数据模型扩展（供参考）

在现有 `notes` / `ai_drafts` 体系上**新增**，不改既有表：

```
products（新表）
  ├── id, user_id
  ├── source: manual | qianfan | merchant_browser
  ├── 外部商品 id / 标题 / 卖点 / 价格 / 主图 URL 列表
  ├── category, tags
  └── created_at

product_notes（新表，商品→笔记的生成记录）
  ├── id, product_id
  ├── draft_id → ai_drafts（复用现有草稿体系）
  ├── status: pending | generated | published | failed
  ├── ai_instruction（本次生成指令）
  └── error
```

**设计原则**：
- `ai_drafts` / `publish_jobs` **完全复用**，不动
- 新表只描述「商品 → 草稿」这一层关系
- 生成失败可重试，发布失败可重试，两层独立

### 2.4 AI 生成笔记的流程

```
商品（products）
  ↓ 提取素材：标题 / 卖点 / 主图
  ↓
AI 生成（复用 ai_service.OpenAICompatibleTextClient）
  ├── generate_note(topic=商品标题, reference=卖点+图片描述, instruction=用户指令)
  │   → 标题 + 正文（现有方法已支持「标题：/正文：」解析）
  ├── generate_tags() → 话题标签
  └── generate_image()（可选，商品主图 AI 润色）
  ↓
ai_drafts（现有表）
  ↓ 人工审核（可选）/ 自动放行
  ↓
publish_jobs（现有表）
```

**关键设计点**：

1. **生成与发布解耦** —— AI 生成可能出质量不稳的内容，**建议保留人工审核闸门**（一个布尔开关：`auto_publish=true|false`）
2. **图片来源** —— 商品主图可以直接用作笔记图（走上传链路），或 AI 润色后用。**注意上传链路建议保持现有 PyExecJS 方案不变**（见 [10 号文档 §2.5](./10_无头浏览器方案可行性分析.md)）
3. **生成结果去重** —— 同一商品短时间内重复生成应拦截（`product_notes` 状态机 + 幂等键）

## 3. 需求③：批量按间隔发布

### 3.1 好消息：现有架构已支持

项目的 `auto_tasks` + `publish_jobs` 已经是一套**「任务 + 调度 + 定时发布」**的完整体系：

| 现有能力 | 出处 | 可否复用 |
|---|---|---|
| 调度类型 | `auto_task.py:23` `schedule_type`（manual/daily/weekly/interval） | ✅ 直接复用 |
| 间隔配置 | `auto_task.py:26` `schedule_interval_hours`（默认 24） | ✅ 直接复用 |
| 定时发布 | `publish_jobs.scheduled_at` + `due_publish_runner` 补跑 | ✅ 直接复用 |
| 发布重试 | `publish_jobs.status` 状态机 + `publish_error` | ✅ 直接复用 |
| 批量创建 | `auto_tasks` 一次任务可带多个关键词 | ✅ 模式可复用 |

### 3.2 需要补的能力：「批量排期」

现有模型是**一个 auto_task 对应一条管线**（选一个关键词 → 生成一篇 → 发一篇）。批量发布需要的是**一个商品列表 → 生成 N 篇 → 按 N 个不同时间点发布**。

建议补一个轻量排期表：

```
publish_schedule（新表）
  ├── id, user_id
  ├── name（如「新店开业 30 篇种草」）
  ├── product_ids[]（商品列表）
  ├── strategy: fixed_interval | fixed_times | random_window
  ├── interval_minutes | publish_times[]
  ├── visibility: public | private
  └── status: draft | running | paused | done
```

**三种排期策略**（覆盖常见运营诉求）：

| 策略 | 行为 | 典型用法 |
|---|---|---|
| `fixed_interval` | 每篇间隔固定分钟数（如每 120 分钟一篇） | 养号期均匀铺量 |
| `fixed_times` | 指定多个绝对时间点 | 大促节点定点发布 |
| `random_window` | 在时间窗内随机选点（更像真人） | 长期日常铺量 |

### 3.3 批量发布的执行流

```
publish_schedule 启动
  → 遍历 product_ids
  → 每个商品：
       ├── AI 生成笔记 → ai_drafts（失败 → 标记失败，继续下一个）
       ├── 图片处理 + 上传 Creator（现有链路）
       ├── 创建 publish_job（scheduled_at = 排期算出的时间）
       └── publish_mode = scheduled（由 due_publish_runner 补跑）
  → 发布间隔由 scheduled_at 保证，不在执行侧 sleep
```

**为什么用 `scheduled_at` 而不是执行侧等待**：
- 进程崩溃后已排期的 job 不会丢（`due_publish_runner` 会补跑）
- 发布动作天然幂等（同一 job 只执行一次）
- 与现有定时发布完全一套机制

### 3.4 风控与节流（批量发布必须有的护栏）

| 护栏 | 理由 |
|---|---|
| **每日发布上限**（如每账号 ≤10 篇） | 小红书对高频发布有风控 |
| **最小间隔强制**（如 ≥30 分钟） | 防止触发风控 |
| **发布前内容校验** | 标题/正文长度、图片数量合规 |
| **失败熔断** | 连续失败 N 次暂停整个 schedule，避免持续撞风控 |
| **人工审核闸门** | AI 生成内容质量不稳，建议默认开启审核 |

## 4. 与无头浏览器方案的关系

这三个需求里，**只有需求①强制依赖无头浏览器**：

| 需求 | 是否依赖无头浏览器 | 说明 |
|---|---|---|
| ① 浏览器数据获取 | ✅ **是** | 这就是方案二的核心 |
| ② 商品 AI 生成笔记 | ❌ **否** | 纯后端 + AI 接口，与浏览器无关 |
| ③ 批量按间隔发布 | ❌ **否** | 现有 HTTP SDK 链路即可（发布签名稳定） |

**因此建议的落地顺序**：

```
阶段 0（先做，不依赖浏览器）
  └── 需求②③ 的最小闭环：手动导入商品 → AI 生成 → 批量定时发布
       └── 复用现有 HTTP SDK 发布链路，不碰签名风险
       └── 这能最快验证业务价值，且与方案二完全解耦

阶段 1（无头浏览器：登录链路，见 10 号文档）
  └── 解决 Cookie 获取的稳定性

阶段 2（无头浏览器：采集链路）
  └── 需求① 的主动调用 + 被动监控双通道
  └── 此时「商品数据自动获取」才具备条件（来源 A/B）

阶段 3（商品数据自动化）
  └── 阶段 2 落地后，把阶段 0 的「手动导入」换成自动获取
```

**这个顺序的核心洞察**：**「AI 生成 + 批量发布」这条业务链路与「无头浏览器替代签名」是两个正交的事情。** 不需要等浏览器方案落地就能先跑通业务闭环。浏览器方案解决的是「数据从平台来」和「登录稳定」，而业务闭环可以先用人工/半自动数据跑起来。

## 5. 需要用户拍板的决策点

| # | 决策 | 选项 | 建议 |
|---|---|---|---|
| D1 | **商品数据来源** | A 商家自有 / B 分销库 / C 手动导入 | **C 先行**，再接 B |
| D2 | **AI 生成是否需人工审核** | 是 / 否 | **是**（初期），稳定后可关 |

| D4 | **发布上限** | 每日篇数 / 最小间隔 | 建议每日 ≤10、间隔 ≥30min |

| D6 | **被动监控默认开不开** | 是 / 否 | 巡检场景开，采集场景按需 |

## 7. 风险提示

| 风险 | 级别 | 应对 |
|---|---|---|
| **无商品模型**，来源未定 | 🔴 阻塞 | 必须先定 D1 |
| AI 生成内容质量不稳 → 发布即事故 | 🔴 高 | 人工审核闸门 + 发布前校验 |
| 批量发布触发风控 → 封号 | 🔴 高 | 每日上限 + 最小间隔 + 熔断 |
| 商业化合规（README 禁止商业化） | 🟡 中 | 仅限学习交流用途 |
| 无头浏览器资源占用（每 context ~150-300MB） | 🟡 中 | 按需拉起，跑完即销毁 |
