## 一、项目是什么

项目对外是**两个身份**，共用同一套底层能力：

| 身份 | 形态 | 使用者 |
|---|---|---|
| **Web 运营平台** | FastAPI + React SPA | 运营人员（多账号矩阵 + 内容管线） |
| **XHS 底层 SDK 仓库** | `apis/` + `xhs_utils/`（逆向签名 + HTTP 接口封装） | 上层 Agent 工具链（Clawbot / Claude Code / Codex），经 [XhsSkills](https://github.com/cv-cat/XhsSkills) 引入 |

> ⚠️ README 明确标注：**仅供学习交流使用，禁止任何商业化行为**。

## 二、技术栈与规模

| 层 | 选型 |
|---|---|
| 后端 | FastAPI + Uvicorn + SQLAlchemy 2.0 + Alembic + APScheduler |
| 数据库 | SQLite（默认）/ MySQL（生产） |
| 鉴权 | 自研 JWT（HS256）+ PBKDF2-SHA256（26 万次）+ Fernet 加密 |

| 前端 | React 19 + Vite 7 + TypeScript 5.9 + antd 6 + recharts 3 + @dnd-kit |
| 部署 | 多阶段 Dockerfile（Node 构建前端 → Python 运行）+ docker-compose |

| 模块 | 行数 |

三层规模均衡，无单点膨胀。

## 三、架构

```
前端 SPA（React 19）
   ↓ axios（/api，自动 refresh token）
FastAPI 路由层（131 端点，21 router）
   ↓
服务层 services/（AI、调度、账号、下载、限流、通知、监控爬取）
   ↓
适配层 adapters/xhs/  ← 上层唯一允许调用 SDK 的入口
   ↓
SDK 层 apis/ + xhs_utils/（curl_cffi + Node 签名）
   ↓
小红书（PC / Creator / 蒲公英 / 千帆）
```

**核心约束**：`apis/` 是底层 SDK，**请勿直接修改**，上层必须经 `adapters/` 中转（README 明示）。

**四条主链路对应的表流转**：

```
采集：  notes ← note_assets / note_comments
AI：    notes → ai_drafts → draft_assets / ai_generated_assets
发布：  ai_drafts → publish_jobs → publish_assets → external_note_id
自动：  auto_tasks（pc_account_id + creator_account_id 双账号）
```

## 四、模块功能点速览

### 底层 SDK（`apis/` + `xhs_utils/`）— 项目的核心资产

- **PC 端 36 个方法**：搜索（笔记/用户）、笔记详情、评论（外/内/全量递归）、用户笔记/喜欢/收藏、首页推荐、未读消息、**无水印图/视频**
- **Creator 端 18 个方法**：话题/地点搜索、素材上传、转码查询、发布、视频封面提取、已发布作品
- **登录**：PC / Creator 各自的扫码 + 手机验证码
- **蒲公英 / 千帆**：已实现（KOL 列表、分销商品），**但后端零引用**
- **签名四层**：传输伪装（curl_cffi + 固定 Header 顺序）→ 认证态（Cookie/DS/websectiga）→ 请求签名（b1、x-s/x-t 三档、x-s-common）→ 指纹扩展（DES-ECB profileData、x-rap-param）
- **工程护栏**：算法只存于 JS，Python 调 Node 子进程，输出经**长度/前缀/正则校验**才接受（b1 ≥500 且 4 的倍数、x3 档位匹配、profileData 10000~20000 位 hex、websectiga 64-hex）

### 后端（`backend/app/`）

- **core/**：分层配置、数据库 + 幂等迁移、JWT/Fernet、依赖注入、时区、平台注册表
- **models/**：21 张表（用户 / 账号矩阵 / 内容库 / AI 草稿 / 发布 / 自动运营 / 监控 / 系统）
- **api/**：21 个 router、131 个端点，全部 `/api` 前缀
- **services/**：AI 服务（OpenAI 兼容）、调度器（四条 Job）、账号、素材下载、图片处理、监控爬取、通知、限流
- **adapters/xhs/**：PC/Creator API 适配 + 登录适配 + 代理环境隔离
- **storage/**：`media/` 素材 + `exports/` 导出

### 前端（`frontend/src/`）

16 个 XHS 功能页：仪表盘、账号矩阵、笔记发现、数据抓取、关键词组、内容库、草稿工坊（三栏）、竞品监控、图片工坊、视频工坊、发布中心、自动运营、数据洞察、监控详情，加任务中心 / 模型配置 / 设置。无全局状态库，组件本地 state + 直接 API 调用。

## 五、核心业务逻辑

### 1. 账号接入

三种方式（扫码 / 手机验证码 / Cookie 导入）→ `login_sessions` 临时会话 → 校验通过写 `platform_accounts`（`sub_type` = pc 采集 / creator 发布）→ **追加** `account_cookie_versions`（Fernet 加密，只增不改）。PC Cookie 可换 Creator Cookie。

**2 小时自动健康巡检**：全量账号 `get_user_info` 探活 → 新过期发 Notification。

### 2. 采集入库

选 PC 账号 → 搜索/URL/用户笔记 → `direct_xhs_request_env()` 摘代理 → curl_cffi + Node 签名 → 归一化 → upsert `notes` + 下载无水印素材到 `storage/media/`。支持评论递归展平、Excel 导出。

### 3. AI 改写

内容库深拷贝为 `ai_drafts` → 调 **任意 OpenAI 兼容 API**（用户自配端点：火山引擎/阿里云百炼/中转）改写正文 / 生成标题 / 生成标签 / 润色 / 整篇生成。响应解析有多编码兜底。

### 4. 发布

草稿 → `publish_jobs`（immediate/scheduled）→ 素材上传 Creator（webp 自动转 JPEG）→ `publish_assets.creator_upload_info` 存 fileIds → 发布。

**关键实现**：图集发布**不走** SDK 通用 `post_note`，而是 `_post_uploaded_image_note()` 自行组装——**未选地点时必须删掉 `post_loc` 键**（空对象会被服务端参数错误打回）、逐条解析话题拼 `#话题[话题]#`、手动补 `x-rap-param`。定时发布由 `due_publish_runner` 补跑。**当前仅支持图片发布**。

### 5. 自动运营（无人值守）

APScheduler 每 60s 扫 `auto_tasks` → 随机选关键词搜索 → 按互动总量选最优笔记 → 建草稿 → AI 改写（非致命）→ Creator 上传图片 → 建 publish_job 直接发布 → 无论成败重算 `next_run_at`。支持 manual/daily/weekly/interval 四种调度。

### 6. 竞品监控

注意：监控「刷新」**本质是对本地内容库的再查询**（模糊匹配 + 互动量排序 + Top 10 快照），**不触发新的平台请求**。要监控新内容需先入库。

## 六、当前状态与缺口

### 已核实的缺口

| 级别 | 缺口 | 证据 |
|---|---|---|
| 🔴 | **多副本调度不安全** —— 调度器与 FastAPI 同进程，无分布式锁，多副本会重复发布 | `scheduler_service.py:740`、`main.py:22-25` |
| 🔴 | **密钥不分离** —— `fernet_key` 空时由 `secret_key` 派生，改 secret_key 导致历史加密数据全解不开 | `security.py:108-116` |
| 🔴 | 逆向 SDK 脆弱（固有风险，已有护栏缓解） | `apis/`、`xhs_utils/` |
| 🟡 | **mock 遗留路由** —— `/xhs/pc/search/users`、`/xhs/pc/users/notes`、`/xhs/pc/homefeed/*` 返回假数据，`task_service` 同样返回 mock；另有 `note_comments_placeholder()` 是未被路由引用的死函数 | `pc.py:343,386,391,396,382`、`task_service.py:9` |
| 🟡 | **蒲公英/千帆完全未接线** —— README 标 ✅ 但 backend 零引用 | `grep pugongying|qianfan backend/` 零命中 |
| 🟡 | **测试覆盖与声明不符** —— README 写 126 passed，实际 3 个文件，核心链路无单测，部分测试是对前端源码的字符串断言 | `tests/backend/` |
| 🟡 | 自动运营失败只写日志，**不入 Notification** | `scheduler_service.py:619-623` |
| 🟡 | SQLite `journal_mode=MEMORY`（非 WAL），并发写易锁表 | `database.py:32` |
| 🟢 | 死代码：`core/task_runner.py`（`InProcessTaskRunner` 从未调用）、`xhs_utils/xhs_util.py`（纯转发） | grep 证实 |
| 🟢 | `auto_tasks_runner` 60s 与 `cookie_health_checker` 2h **硬编码** | `scheduler_service.py:719-736` |
| 🟢 | `next_run_at` 执行后才算，耗时计入下一轮间隔 | `scheduler_service.py:619-626` |
| 🟢 | 删素材只删库记录，`storage/media/` 堆积孤儿文件 | `api/files.py` |

### 值得保持的工程实践

1. **适配层隔离** —— SDK 变更影响面可控
2. **签名单源 + 输出校验护栏** —— 算法失效快速暴露而非静默降级
3. **Cookie 多版本加密存储** —— 只增不改、可回溯
4. **时区统一** —— 全项目 `shanghai_now()` + 启动时幂等修历史数据

## 八、结论

这是一个**把逆向 SDK 与完整运营后台缝合在一起**的工程：`apis/` + `xhs_utils/` 是硬核资产（签名四层、Node 单源算法、输出校验护栏），`backend/` 是标准 FastAPI 三层架构加一套 APScheduler 驱动的自动化，`frontend/` 是 antd 6 + React 19 的运营后台。

**工程质量整体在线**：加密存储、时区统一、幂等迁移、适配层隔离、签名护栏都做到位了。

**主要短板集中在四处**：**多副本调度安全**（架构级，需引入分布式锁或独立调度服务）、**mock 遗留路由与未接线的蒲公英/千帆**（现成能力没接上）、**测试覆盖**（核心链路无回归保护）、**密钥分离**（生产部署必改）。

若要投入生产使用，优先级建议：固定 `FERNET_KEY` → 调度器上分布式锁或拆独立服务 → 清理 mock 路由 → 补核心链路单测。
