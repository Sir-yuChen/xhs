### 1.4 DEF-038 · 二维码登录：屏幕上的码 ≠ 正在轮询的会话（**已闭环**）

| 项 | 内容 |
|---|---|
| 现象 | 手机已点「确认登录」，浏览器面板既不报错也不前进；**勾选与不勾选「同步 Creator」都复现** |
| 根因 1 | `React.StrictMode` 双挂载 + `startSession` 无幂等守卫 → 一次开抽屉建**两个**会话，只有一个被轮询 |
| 根因 2 | 轮询回调**无条件**合并写回 state → 旧会话的迟到响应把 `session_id` 拉回旧会话，而二维码图片仍是新会话的 → 手机确认记在**无人观测**的会话上 |
| 修复 | 三层守卫：`initialisedForRef`（一次挂载只建一个会话）/ `createGenerationRef`（被取代的创建不得上屏）/ 轮询响应与 state updater **双重身份校验**，不匹配即丢弃 |
| 验证 | ① jsdom 真组件行为验证 `tests/frontend/qr_session_identity.cjs`（6 PASS；**变异验证**删守卫后 3 FAIL）；② 源码守卫 `tests/backend/test_login_panel_identity.py`（随 pytest）；③ **真机复验**：修复后会话 90/91 双双 `confirmed` 且「≈2.2s 成对」指纹消失，账号落库 |
| 详见 | `04_测试文档/04_测试跟踪与缺陷标记.md` DEF-038（含完整证据链） |

## 2. 结构性技术债

### 2.1 发布安全类（最高优先级）

#### T-01 · 发布无数据库级幂等约束

| 项 | 内容 |
|---|---|
| 对应缺陷 | DEF-002 |
| 结构性问题 | 「检查状态 → 执行发布 → 回写状态」三步非原子；发布是**不可逆写操作**，但唯一的可靠防线（DB 唯一约束）缺失 |
| 现有防线 | 状态机（中）、`max_instances=1`（仅单进程）、补跑幂等（中）、DB 约束（**缺失**） |
| 偿还 | 给 `publish_jobs` 加 `idempotency_key` 唯一索引 |
| 成本 | 低（一个迁移 + 生成逻辑） |
| 不还的后果 | 重复发布 → 真实账号重复发文（客户可感知的事故） |
| 承接 | T-103 |
| **状态** | ✅ **已偿还（2026-09-18）** |
| **实际偿还方式** | `publish_jobs.idempotency_key`（**nullable + UNIQUE**）。键 = `{platform}:{账号}:{sha256(标题\|正文\|规范化 publish_options)[:32]}`。<br>**关键设计修正**：列必须 **nullable**——否则「建了 → 取消 → 再建同样内容」这条**合法流程**会被唯一索引无故挡死。占用语义收敛为一条不变式：**键非空 ⇔ 处于占用态（publishing / published / scheduled）**，`failed` 与「从 scheduled 取消」**不释放**。 |
| **两段式防护** | ① 应用层 `claim_publish_idempotency` 给出**可读** 409；② 唯一索引做并发兜底。两者判定口径严格统一（只看列有无值，**不按状态过滤**），否则会出现「应用层放行 → 数据库 IntegrityError」的分裂 |
| **顺带收益** | 实施过程中发现并修复了**同一事实的第二个入口** DEF-031（已提交的失败任务可被原地重试 → 重复发文），见 §4.1.6 |
| 落点 | `models/publish.py`、`services/publish_service.py`（新增）、`api/publish.py`、`services/scheduler_service.py`、迁移 `b1e4d7c9a2f3` |
| 回归 | `test_m1_governance.py` 4 条（确定性 / 唯一索引兜底 / 释放后可重认领 / 列 nullable+unique）；全量 158 passed |

#### 4.1.7 本轮验证到的工程规律（供后续轮次沿用）

| 规律 | 证据 | 后续动作 |
|---|---|---|
| **修一类缺陷时，相邻入口会浮出来** | 修 T-103（幂等键）时发现 DEF-031——「重复发文」的第二个入口 | 每修一项，必须反问「**同一个事实还有没有别的入口在读它？**」。本轮的答案是「有三个入口」（DEF-002 / DEF-031 / DEF-003），已回写任务台账 |
| **旧测试可能固化了 bug 的行为** | `test_publish_job_retry_...` 的夹具是 `status=failed` + `external_note_id='old-note'`，却断言「重试应清空 `external_note_id`」——正是 DEF-031 的错误行为 | 修 bug 时若旧用例变红，先判断「**这个断言当初在描述需求，还是在描述实现？**」本例该改的是断言，**不能为了让用例通过而放宽实现守卫** |
| **视图实体的「身份」与「内容」必须绑定在同一份数据上**（**追加，2026-09-18 晚**） | DEF-038：二维码图片留在 state、`session_id` 由响应合并覆盖 → 屏幕上是 QR-B、轮询器盯着 session-A，手机确认**永远无人观测**。这是本项目**第二次**栽在「UI 显示的码 ≠ 后端在盯的会话」上（前一次 DEF-036） | 禁止 `setState(resp => ({...resp, 保留当前某字段}))` 这类**无身份合并**；异步响应必须带身份，不匹配就**整条丢弃**。同族缺陷**第二次**复发 → 必须留**源码级守卫**，而不只是修一遍（已升格为硬约定 **H8** / 红线 **X17**） |
| **断言全绿不等于守卫必要 → 要做「变异验证」**（**追加，2026-09-18 晚**） | 在加载期把 DEF-038 的三个守卫就地改成恒假，同一套断言立刻变红：`createPc 1→2`、上屏变成被取代的旧响应、轮询目标 `[301]→[301,999]`（6 PASS → 3 FAIL） | 凡是为「竞态/不变式」加的守卫，交付前**必须证明删掉它断言会变红**——否则你只是在断言一个巧合 |
| **统计数字只能从明细反推，禁止增量手改合计**（**追加，2026-09-18 晚**） | 同一份缺陷台账**连续两轮**出现口径漂移（第一轮「合计对、分域错」；第二轮「列求和 39/16 vs 合计 38/15」）。且**每行内部都是自洽的**，只有列求和才暴露 | 任何统计改动，跑一遍「列求和 vs 合计」脚本核验；**校验脚本自身也不可信**——不可用「以 `\| 级别 \|` 开头的行」当汇总行特征（明细行也会以它开头，实测产生假阳性） |
