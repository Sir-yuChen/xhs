# 三平台定位与「商家为主入口」架构方案

> 调研日期：2026-09-30
> 结论性质：**架构定位决策**，非代码迁移任务
> 一句话：**「迁移到千帆」不可行；正确方向是「千帆为主干 + 创作者补发布 + 网页版补竞品监控与互动数据」三平台互补，底层代码无需改动。**

---

## 1. 结论先行

用户最初诉求「全量迁移到千帆、网页和创作者只保留账号登录绑定」，调研后判定**不可行**；
结合补充信息「主用户是商家，创作者和网页为辅」后，结论修正为：

**商家为主 = 千帆为主干 + 创作者补「种草笔记发布」 + 网页版补「竞品监控 / 互动数据」，三者互补，不是冗余，都不该砍。**

底层代码（三平台适配器、令牌三通道 www/creator/ark、同步双源、发布分流）**已经是这个架构**，无需改动。
真正要做的是**前端信息架构与登录引导**的「主辅」强化。

---

## 2. 三平台能力边界（不可替代性）

| 平台 | 本质 | 覆盖能力 | 缺的能力 |
|---|---|---|---|
| 千帆 `ark` | B 端**商家后台** | 店铺绑定、商品台账、SKU、商品笔记 AI 生成+发布（挂链）、无流量笔记、店铺健康 | 普通笔记发布、搜索/feed、互动数据、笔记详情正文 |
| 创作者 `creator` | B 端**内容创作者** | 普通笔记发布（图文/视频）、删除、定时发布、话题/地点查询、媒体上传、笔记列表 | 商品挂链、商品数据、搜索、互动数据 |
| 网页版 `www` | C 端**普通用户** | 关键词/账号/品牌/笔记对标监控、笔记详情正文 SSR、互动数据（粉丝/关注/获赞） | 发布、商品、店铺 |

**核心事实**：三个平台是小红书 API 分层的必然产物（C 端 / 创作者 B 端 / 商家 B 端），
没有任何一个能替代另外两个。千帆能干的「商品经营闭环」恰恰覆盖不了商家最需要的三件事：

1. **发不挂链的种草笔记**（引流）→ 只有创作者平台能发；
2. **竞品监控**（关键词/账号/品牌对标）→ 只有网页版 C 端搜索能给；
3. **笔记详情正文 + 互动数据** → 只有网页版能给全。

---

## 3. 现状代码印证（三平台已是互补架构）

以下事实来自代码实读，证明「迁移」是个伪命题，架构已经是对的：

1. **笔记同步双源**：`note_sync_service._note_sources()`（第 166 行）已只返回
   `creator`（普通笔记）+ `ark`（商品笔记）两个源，**www 源 2026-09-22 已整体移除**（§21.4）。
2. **发布天然分流**：普通笔记走 `XhsCreatorApiAdapter.post_note()`；商品笔记走
   `XhsQianfanApiAdapter.publish_note()`（带 `biz_relations` 挂链），两者请求体与签名完全不同，不可互换。
3. **令牌三通道解耦**：`account_service` 定义 `CHANNEL_WWW/CREATOR/ARK`，
   `channel_for_cookies()` 按平台域强键判定 jar 形态，一次登录只更新自己那个平台。
4. **网页版唯一承担的三件事**（砍掉即失去）：
   - 笔记详情正文/图集/视频地址补齐（`hydrate_note_detail` 走 explore SSR，列表接口全都不带正文）；
   - 账号互动数据（`XhsSelfProfileAdapter.get_user_other_info`，创作者 `/v2/user/me` 无 `interactions`，DEF-039）；
   - 监控采集（`monitoring_crawl_service` 唯一走网页版搜索接口）。

## 4. 推荐的落地方向：前端「主辅」强化，不动底层

### 4.1 导航信息架构调整（`app-shell.tsx` 的 `mainNavItems`）

当前 13 个一级菜单项平铺，未体现「商家为主」。建议按商家经营链路重组为分组：

| 分组 | 现有菜单项 | 主/辅 |
|---|---|---|
| **店铺经营（主）** | 总览、账号矩阵、商品列表、我的笔记、数据洞察、竞品监控 | 千帆为主 |
| **内容生产（主）** | 发布中心、笔记工坊、笔记发现、内容库 | 创作者为主 |
| **流量工具（辅）** | 关键词组、数据抓取 | 网页版为辅 |
| **自动化（主）** | 自动运营 | 混合 |

> 说明：这是产品层面的信息架构方案，是否落地、按什么顺序落地，需用户确认后再动 `app-shell.tsx`。

### 4.2 登录引导「千帆优先」

`accounts-page.tsx` 已实现三平台登录态标签（千帆/创作者/网页版各一个 tag），
且「同步笔记」弹窗已做到「优先引导补千帆」。可进一步强化的点：

- **绑定账号入口**：首次绑定主引导「千帆扫码/邮箱登录」，「创作者/网页版」降为次级可选；
- **文案**：明确「千帆 = 店铺经营主平台，创作者/网页版 = 能力增强可选」。

### 4.3 不改的底层（明确边界）

- 三平台适配器（`pc_api_adapter` / `creator_api_adapter` / `qianfan_api_adapter`）**全部保留**；
- 令牌三通道、`sub_type` 枚举、`LINK_RANK` 合并逻辑**不动**；
- 同步双源、发布分流、监控采集逻辑**不动**。

## 5. 若强行砍平台的代价（供决策参考）

| 砍什么 | 失去的能力 | 可接受吗 |
|---|---|---|
| 砍网页版 | 笔记详情正文、粉丝/关注/获赞、关键词竞品监控 | 商家运营刚需，**不建议** |
| 砍创作者 | 普通种草笔记发布（图文/视频） | 商家引流刚需，**不建议** |
| 砍千帆 | 商品经营全链路 | 主用户场景，**绝对不行** |

**三者都砍不得。** 所谓「网页和创作者只保留账号登录绑定」的正确理解是：
**保留登录绑定能力，但在 UI 上把它们的入口降为「能力增强」而非「主平台」。**
