# 笔记发布挂商品 · 复盘（2026-10-20）

> 用户口径：*「内容库中展示有商品但是发布的笔记实际未挂商品」* →
> *「你重点深入分析这个问题」* → *「跑全流程，最终确认发布成功的笔记挂商品了，再结束告诉我」*。
>
> 本文只记这一条链路的真实教训。商品发布（`batch_create_item`）慢的原因见
> `05_复盘_商品发布功能开发为何慢.md`，两者根因不同，别混。

## 一、实测账

| 项 | 实测值 |
|---|---|
| 为查这一个问题发到用户账号上的测试笔记 | **十余篇**（全部未挂商品，需用户手动清理） |
| 试过的字段假设 | **6 个**（全部无效） |
| 真正根因 | **2 个字段值**（`goods_id`、`goods_name`） |
| 抓到真实请求体后到修好 | **1 次发布** |
| 抓包本身耗时 | 约 **20 分钟**（含调试抓包方法） |

⇒ **与商品发布同一条规律：慢在「没有先抓包」，不在「没想清楚」。**

## 二、根因（真机抓包逐字段 diff 得出）

```json
"biz_relations": [{
  "biz_type": "GOODS_SELLER_V2",
  "biz_id": "6a334f51a0915b001516d97a",          // SKU ID
  "extra_info": "{\"goods_id\":\"6a334f51a0915b001516d97a\",   // ← 必须 = biz_id（SKU ID）
                  \"goods_name\":\"商品名 空格 规格名\", …}"    // ← 必须拼规格
}]
```

| 字段 | 原实现（错） | 正确值 | 症状 |
|---|---|---|---|
| `extra_info.goods_id` | 商品 `item_id` | **SKU ID**（与 `biz_id` 逐字相同） | 平台回 success、笔记发出、**不挂商品** |
| `extra_info.goods_name` | 纯商品标题 | **商品名 + 空格 + 规格名** | 同上 |

**SKU ID 的正确来源**：`shop_products.raw_json.first_sku_id`（= `first_buyable_sku_id`）。

- ❌ `item_id` —— 商品层，不是挂链层；
- ❌ `variant_ids[0]` —— **规格模板 ID**，26 个 SKU 共用同一个值，填进去平台照收但不挂。

**规格名的正确来源**：本地 `raw_json` **没有这个字段**（只有 `main_spec_id` / `first_sku_id` /
`variant_ids`），必须发布前实时调
`POST /api/edith/aigc-publish/attributes` 取 `data.sku_list[].sku_specification`（按 `sku_id` 匹配）。

## 三、试错掉进去的 6 个坑（全部不是根因，**别再试**）

| # | 假设 | 为什么看起来像对的 | 实测结果 |
|---|---|---|---|
| 1 | `biz_id` 用商品 `item_id` | SDK docstring 明写「`biz_id: 商品 item_id`」 | ❌ 平台回 success，不挂 |
| 2 | `biz_id` 用 `variant_ids[0]` | 历史文档写「挂链粒度是 SKU 不是 item」 | ❌ 那是规格模板 ID |
| 3 | `goods_name` 用商品标题 | 觉得「挂哪个商品就写哪个商品名」 | ❌ 少拼规格 |
| 4 | 补 `aigcTaskId`（调 `sellerpoint/aigc` 现取） | 抓包体里确实有这个字段 | ❌ 平台对该 SKU 恒定回同一个号，不是变量 |
| 5 | Referer 加 `mainPublishType=agi` 场景参数 | 真实发布页 URL 确实带这个参数 | ❌ 不是判据 |
| 6 | 读 `business_bind_results` 判断挂没挂 | 名字就叫「业务绑定结果」 | ❌ **平台恒返回空数组**，与成败无关 |

**为什么连续掉 6 个坑**：每个假设都有「看起来权威」的依据（docstring / 历史文档 / 抓包体里
真实存在的字段），而平台的失败方式是**静默**的 —— 它不回错误，所以任何假设都不会被打脸，
只能靠**逐一排除**。而每次排除都要真发一篇笔记。

## 四、抓包方法：页面 JS 钩子必然失效

这条单独拎出来，因为**我在这上面浪费了最多时间**（连续 5 次抓到 0 条）。

❌ **错法**：`window.fetch` / `XMLHttpRequest` 包一层，塞进 `window.__CAP__`。

失败原因（三层，逐层发现）：
1. 千帆是 SPA，发布发生在 `/app-note/publisher` 页 —— **页面跳转后注入的钩子消失**；
2. 发布完成会跳 `/publish-success-v2`，且**可能开新标签页**；
3. 最关键：**我装钩子的标签页，不是用户操作的那个标签页**
   （`Target.getTargets` 一列就看见 3 个 page target，钩子只装在第一个）。

✅ **正法**：CDP WebSocket 订阅 `Network.requestWillBeSent`：

```python
# 必须在页面打开之前 enable，且 maxPostDataSize 给足
await send(ws, "Network.enable", {"maxPostDataSize": 20000000}, sid)
await send(ws, "Page.navigate", {"url": "https://ark.xiaohongshu.com/app-note/publish"}, sid)
# 事件 params.request.postData 就是完整请求体
```

现成脚本：`.hermes/scripts/cdp_capture_publish.py`（连 `127.0.0.1:9222` 的 browser ws）。

⚠️ **`performance.getEntriesByType('resource')` 只告诉你「请求发过」，永远不给 body** ——
我一度拿它当数据源，只能看到 URL 列表。

⚠️ **先确认用户操作的就是这个浏览器实例**：本机 `browser_exec` 工具连的可能是另一个实例
（判据：`http://127.0.0.1:9222/json/list` 返回 0 条 ≠ 没开浏览器，而是它管的是别的实例）。

## 五、合规红线（照抄抓包值会违规）

`goods_info.extension.is_adjust_ai` 语义是**「内容是否经千帆 AI 调整」**，不是挂链开关。

- 平台 UI 发 `"1"`，因为那篇正文由千帆 AI 现场生成并人工调整过；
- 本项目正文由**本地 LLM** 生成 ⇒ 必须填 `"0"`；
- 填 `"1"` = **向平台虚报 AI 溯源**，违反 2026 版平台规则（篡改 AI 标识 = 违规）。

**真机已验证 `"0"` 同样挂得上** —— 挂链不依赖该字段。
⇒ **抓包给的是「平台自己怎么填」，不是「我方该填什么」。溯源/审计类字段必须按我方真实情况填。**

## 六、判据

```
GET /api/edith/goods-note/list?page_num=1&page_size=N&note_ids=<平台笔记ID>
```

- 能查到 + `note_flag == "goods_note"` + `goods_infos` 非空 ⇒ **挂上了**；
- 查不到（只出现在「普通笔记」类）⇒ **没挂上**；
- ⚠️ `note/publish` 响应里的 `business_bind_results: []` **不可作判据**。

⚠️ **中间还误判过一次「成功了」**：某次发完立刻查，笔记出现在列表里，我据此宣布通过；
几分钟后再查它**消失了**。⇒ **回读要跨时间点复核一次**，瞬时可查不等于稳定。

## 七、下次怎么做（可直接照做）

1. **写任何「A 挂到 B」的代码之前**，先 CDP 抓一次平台 UI 的真实提交体（约 20 分钟）；
2. 在平台上找一件**关联成功的历史对象**，读出它存的关联字段值 —— 这一步零写操作，
   却是最快锁定「哪个 id 才对」的办法；
3. 逐字段 diff，把差异分成「值错 / 来源错 / 格式错 / 元数据」四类，
   **先验证「值」，再验证「元数据」**（本次两次都不是元数据）；
4. 一次改全 → **回读判据**验证 → 跨几分钟再复核一次；
5. 写进设计文档：每个关联字段的「正确来源 + 填错会怎样」。

相关技能：`silent-platform-link-failures`（本类缺陷的通用打法）、
`xhs-publish-flow` §「笔记发布挂商品」。
