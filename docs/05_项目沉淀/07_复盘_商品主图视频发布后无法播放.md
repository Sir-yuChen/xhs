# 07 · 复盘：商品主图视频「发布后无法播放」为何排查了 8 轮

> 2026-10-22 立。用户报障原文：**「商品发布提交后视频就无法播放」**。
> 提交 `a390c97`。现象与原因之间隔了 **5 层**，中途我自己还制造了一个新 bug。

---

## 一、一句话结论

**`scene="common_file"` 用错了 —— 视频被放进 `ark-common/` 桶，而图片空间登记只认
`arkgoods/` 桶 ⇒ 登记失败 ⇒ `materialId` 为空 ⇒ 提交体引用无效 ⇒ 平台拉不到视频。**

改成 `scene="goods_video"`（一处）即修好。

---

## 二、症状与原因的 5 层距离

用户看到的是「发布后视频空白」，真因在最底层，中间每一层单独看都「没报错」：

| 层 | 现象 | 为什么没被发现 |
|---|---|---|
| 1 | 发布后主图视频是空白框 | 平台不报错，只是播不了 |
| 2 | 提交体 `videos[]` 引用无效 | 提交照样 HTTP 200、`success: true` |
| 3 | `materialId` 是空串 | 前端不校验它，空串照传 |
| 4 | 登记返回「获取上传文件[xxx.mp4]信息失败」 | **被 `except` 吞成 warning** |
| 5 | 文件在 `ark-common/` 桶，登记只认 `arkgoods/` | 上传本身成功（PUT 200） |

**第 4 层是放大器**：静默吞异常让「失败」表现为「成功」。这是我方代码的问题，
不是平台的。修法：登记失败**必须报错**（`VIDEO_REGISTER_FAILED`），宁可上传这步失败
（用户能重试），也不留下必然播不了的商品。

---

## 三、8 轮排查的账（每一轮花在哪）

| 轮 | 我的假设 | 实测结果 |
|---|---|---|
| 1 | 签名 URL 过期 | **被用户推翻**：「上传了不到 5 分钟」 |
| 2 | `size_bytes` 字段名错 | 查 `ConfigMainImage` 类型，字段存在，不成立 |
| 3 | cv2 读不出元数据 | 实测 720×960、8s，正常 |
| 4 | `path` 前缀 / `type` / `scene` 组合试错 | 4×4 组合**全失败** —— 因为文件根本不在对的桶 |
| 5 | 文件名（MD5 vs 原名） | 两种都失败 |
| 6 | 桶名（`arkgoods` vs `ark-common`） | 只是必要不充分 |
| 7 | 用图片走同一套登记做对照 | **关键一步**：图片成功、视频失败 ⇒ 差异只在 scene |
| 8 | 用户要求「浏览器抓包吧」 | **一抓即明**：平台自己就是 `scene=goods_video` |

**教训：第 1–6 轮全是「在自己代码里猜参数」，浪费了 6 轮。**
第 7 轮的**对照实验**和第 8 轮的**真机抓包**各用一次就把范围锁死了。

平台契约类问题（写接口参数、上传链路），**穷举试错是错的工具** ——
组合空间大、每次实验都有网络延迟、而且历史代码里可能留着错误的「依据」
（本例就是 `9515.*.js` 里一句 `scene:"common_file"`，被当成了商品视频的依据）。

## 四、我自己制造的那个 bug（最值得记）

修完 `scene` 后，我「顺手」给视频的 `link` 加了永久 CDN 兜底：

```python
permanent_link = f"https://qimg.xiaohongshu.com/{file_id}"   # ← 照抄图片侧
```

**实测打脸：**

```
GET https://qimg.xiaohongshu.com/arkgoods/<id>              → 404
GET https://ros-preview.xhscdn.com/arkgoods/<id>?sign=…&t=… → 206 + ftypisom
```

`qimg` **只服务图片**。视频唯一可用地址是 PUT 响应头 `X-Ros-Preview-Url` 给的
**签名预览地址**；登记响应对视频的 `additionalData` 还是**空的**
（`path`/`link` 均 `None`），根本拿不到永久地址。

⇒ 这一改把「签名地址可用」变成「必然 404 空白」，比原问题更糟。已回退。

**规矩：两个媒体类型的 CDN 域不同，不能互相照抄。**
已有守卫 `test_link_uses_signed_preview_not_qimg` 钉死。

## 五、还有一个「假故障」

用户中途截图显示**全部接口 500**（详情图 50 张全红）。查下来：

**是我自己把后端进程杀了** —— 为验证 launcher 退避逻辑跑了个测试进程，
`pkill -f test-backoff` 匹配范围太宽，把 launcher 和 uvicorn 一起带走了。
后端不在，Vite 反代连不上，全部 `/api` 返 500。

**规矩：验证脚本要杀进程时，用精确 PID，不要用 `pkill -f <模糊词>`。**

同一轮还发现「改了没生效」的真正原因：

- uvicorn 启动 `23:58:21`，我改源码 `00:04:38` ⇒ **跑的是旧代码**。

**判据：比 `uvicorn 子进程 CreationDate` 与 `源码 mtime`，前者必须更晚。**
（这条在 `AGENTS.md` §7 已有，我这次还是忘了查，白排了一轮。）

## 六、可复用的判据（下次直接查）

1. **写接口参数一律先抓包**，不要从 bundle 里读一句话当依据（那可能属于别的场景）。
2. **对照实验优先于试错**：同类对象（图片 vs 视频）一个成功一个失败时，
   把两者走**同一套代码**做对照，差异立刻只剩一两个变量。
3. **失败不许静默**：登记 / 注册 / 上报这类「中间步骤」，失败必须让上游失败。
   `logger.warning` + 返回 `success: true` 是最贵的写法。
4. **CDN 域按媒体类型分开记**：
   - 图片：`qimg.xiaohongshu.com`（永久）+ `ros-preview.xhscdn.com`（签名）
   - 视频：**只有** `ros-preview.xhscdn.com`（签名，会过期）
5. **杀进程用精确 PID**；重启后**先比启动时间与源码 mtime**，再判断「改了没生效」。
