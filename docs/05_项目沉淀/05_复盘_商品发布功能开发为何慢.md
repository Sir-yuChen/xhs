# 商品发布功能开发复盘

> 用户口径 2026-10-15：「商品发布功能开发周期达到两周左右才完成，非常非常慢，整体梳理和项目
> 记忆和踩坑点等等综合分析为何如此慢，总结成技能为后面的开发总结经验」。
>
> ⚠️ 本文的**每个数字都是实测**（git numstat / 代码行数 / 提交史），不是印象。

## 一、先纠正一个事实：**慢不在「天数」，在「返工率」**

| 指标 | 实测值 | 出处 |
|---|---|---|
| 发布链路 4 个文件当前行数 | **13,201 行** | `wc -l` |
| 最大单文件 | **6,665 行**（`product-publish-wizard.tsx`） | `wc -l` |
| git 上的开发跨度 | **10-11 02:54 → 10-15 18:21（4.5 天）** | `git log --follow` |
| 实际有提交的工作日 | 10-08 / 10-11 / 10-12 / 10-13 / 10-15（**5 天**） | 会话快照分布 + 提交史 |
| 该链路的提交次数 | **9 次** | `git log` |
| 同期「靠真机抓包才修正」的提交 | **4 次**（`7526ca1` / `ceb55d2` / `760c454` / `1057460`） | `git log \| grep 真机` |

⇒ **「两周」的体感是真的，但它的构成不是「写了 14 天」，而是：**

```
少量「首次写对」 + 大量「写完→真机一试→不对→重写」
```

**证据链**：单文件 6,665 行、9 次提交 ⇒ 平均每次提交 1,467 行。
这不可能是一次成型的代码量，只能是**同一个文件被反复大改**。

## 二、五条结构性原因（按「浪费了多少」排序）

### 原因 1️⃣ 契约靠真机抓包才发现，而抓包在**最后**（最贵）

**实证**：发货模式 / 规格图 / 货号三条，**全部**是用户装包后实测报错、再抓包才定案的。

| 问题 | 表面现象 | 真身（抓包后才知道） |
|---|---|---|
| 发货模式发布变现货 | 配置了全款预售，发布成现货 48h | **`deliveryMode` 恒为 1，根本不是载体**；真载体是 `skuData[].deliveryTime` |
| 规格图开关关闭 | 传了图但平台没开 | API 层**写死 `variant_ids=[]`** 而 `variantSequence` 已算出 |
| 货号没上送 | 本地报「无货号属性」 | 货号是**顶层 `articleNo`**，不是 `attributes[]` 里的一项 |

**代价**：每一个都走完「写→发→用户发现→抓包→改」一整轮，**单轮约半天**。

⇒ **根因**：**平台的契约是「抓包可得」的，但我们把抓包排在了「发布后发现」之后**。
正确顺序是**第 0 步就该抓包**（写代码之前拿到平台的真实请求体）。

### 原因 2️⃣ 十几个跨层字段没有单一真相源

**实证**：这轮踩的字段没有一个是一处定义的 ——

| 字段 | 曾断在哪 |
|---|---|
| `spec` | 前端是「匹配键」（与 `spec_combinations` 对齐），**不能改数据只能改显示** |
| `itemNo` | 前端提交体缺字段 → 后端写顶层 `articleNo` |
| `delivery_label` / `ship_aging` | **不在 `extra="forbid"` 的白名单里** ⇒ 静默丢弃 |
| `passedSkuSpecs` | 产出**行名**，而 `visible` 比的是**带前缀的 spec** ⇒ 全被滤掉 |

⇒ **代价**：每次都是「后端有、前端没传」或「前端传了、后端没读」，
**而这类断链在单元测试里全绿**（因为两层各自都自洽）。

### 原因 3️⃣ 单文件 6,665 行 —— 改任何一处都要重读上下文

**实证**：`product-publish-wizard.tsx` 6,665 行 + `publish-config-step2.tsx` 3,933 行
+ `precheck-publish.ts` 1,962 行 = **12,560 行在前端**。

⇒ 每一个需求都要在这三个文件里**同时**找到对应位置。这轮里出现过：
- 改 `spec` 显示 → 发现它是匹配键 → 撤回
- 改 `clearImportTargets` → 打断了 `test_page_optimizations.py` 的锚点
- 改 `setOpenSeq` → **造成「第一步重挂 + 两套 UI」的自伤**

⇒ **改 A 坏 B 的比例极高**，每次都要重跑一遍守卫。

### 原因 4️⃣ **修改长期不进 git ⇒ 没有检查点 ⇒ 自伤无法回退**

**实证**：这轮**两次真实事故**都是「没有检查点」导致的：

| 事故 | 后果 |
|---|---|
| `table-pattern.ts` / `publish-property-fields.ts` **始终没进 git** | 出事**不能**靠 `git checkout` 恢复 |
| 上一轮的 `Write-Py` 修复**躺在工作区没提交** | 重打包时跑的仍是 git 版 ⇒ **踩同一个坑第二次** |

⇒ 第二条是本轮最贵的教训：**「修好了」与「跑的是修好的那份」是两件事**。

### 原因 5️⃣ 变异脚本与 pytest **并发**跑 ⇒ 污染基线、留残留（踩了 4 次）

**实证**：`变异体残留源码 4 次`（`_sa_update` 2 处 / `return value` / `return value[body_start:]`）。

⇒ 每次都要重跑、重查、重提交。

## 四、这次「慢」里**不该**被指责的部分

避免复盘变成自我否定 —— 以下几条**是必要的**：

1. **真机抓包 6 次 `save_product_drafts`** —— 不抓就永远不知道 `deliveryTime` 是载体。
   这是**唯一可靠**的取证方式（平台文档不存在）。
2. **用户口径连续推翻**（发货模式 / 弹窗尺寸 / 文案）—— 那是需求在收敛，
   不是返工。**UI 类需求本来就靠"看到才知道"**。
3. **逐需求闭环 + 真机验收攒批** —— 这是 `AGENTS.md` §2 已立的规矩，方向对的。

⇒ 真正该改的是 **1️⃣2️⃣4️⃣**（顺序错、无单一真相源、无检查点），
**不是**「少抓包、少问用户」。

## 四·补：**「反复大改」再往下一层 —— 为什么会被反复改**

> 用户追问（2026-10-15）：「被反复大改是慢的主要原因，那为何反复大改，是否由于设计文档不足、
> 不够细化？」——**问对了，但要按「能不能靠设计预防」分成三类**。

### 三类归因（逐提交核对得出）

| 类型 | 例子 | 占比 | 设计能否预防 |
|---|---|---|---|
| **A 平台契约类** | 图片条目格式 / 发货模式载体 / 规格图开关 / 货号位置 | **约 6 成** | ❌ 「先想清楚」防不住 —— **但抓包能防** |
| **B 交互规格类** | `Popconfirm` 位置压到隔壁按钮 / `useCallback` 漏 3 个依赖 / 文案说反 | **约 2 成** | ✅ **能** —— 靠思考就能避免 |
| **C 需求收敛类** | 按钮拆分 / 弹窗尺寸 / 文案反复 | **约 2 成** | ⚠️ **不该防** —— 那是需求在收敛，不是返工 |

### ⚠️ 我（助手）第一版复盘的错误说法，在此订正

第一版写「**A 类设计文档写不了**」——**说得太绝对**。准确的是：

> **A 类不能靠「想」写出来，但能靠「抓包」在设计阶段拿到。**
> 它不是「文档的极限」，是「**流程顺序**」问题。

⇒ 所以对策**不是「写更多文档」**（那会造出没人读的文档），而是
**把抓包提前到设计阶段**（已落进 `01_文档先行工作流.md` §2.1）。

### 更深一层的真根因：**「举例式规格」**

设计 24 里同一个判据（SKU 匹配）**改了 4 次**，每次标题都写着「定论」：

```
§22.13  SKU 匹配的最终语义：完整文案（2026-10-13 第三次修正 · 定论）
§22.14  定论：两档都要求相等
§22.16  SKU 匹配定案：图片名包含 SKU 名（2026-10-14，推翻 §22.13 / §22.14）
```

**为什么会被连推 4 次**：前三版都是**举例式**（描述「某批数据长什么样」）：

| 写法 | 换一批数据 |
|---|---|
| ❌ 「匹配用**最后一段**完整文案」 | **立刻失效** |
| ✅ 「匹配判据 = **图片名包含 SKU 名**；消歧 = 全局最长优先 + 一图一用」 | 任何数据都成立 |

⇒ **举例式规格注定被下一批数据推翻。** 这才是「反复大改」的**最底层机制**
（比对错更根：它让「写完了」这个判断本身不可靠）。

⇒ 已落进工作流 **§2.2**，并要求**判据式**才算写完。

---

## 五、一句话结论

> **这次慢的主因不是「写得多」，而是「第一次就写对的少」** ——
> 契约没先抓、字段无单一真相源、单文件过大、改动不落盘。
> 四者叠加 ⇒ 每次修正都要**重新理解一遍 6,665 行**，而不是改一行。
>
> **再往下追一层**：为什么「第一次写不对」？因为**规格是举例式的**（§四·补）
> —— 举例式注定被下一批数据推翻，所以「写完了」本身不可靠。
>
> ⇒ **对策只有两条，都不需要写更多文档**：
> ① **设计阶段抓包**（外部平台写接口）② **业务判据写成判据式**。
