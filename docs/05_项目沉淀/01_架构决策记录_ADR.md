## ADR-001 · 放弃「无头浏览器替换自维护签名算法」方案

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-17 |
| **状态** | ✅ **已采纳（方案被否决）** |
| **决策人** | 项目负责人 |

### 背景

项目底层维护着一套自实现的逆向签名算法（16 个 JS 文件）。曾评估过一个替代方案：**把签名算法换成无头浏览器**——在浏览器内直接调平台后台官方接口，数据全部来源于浏览器，从而彻底移除算法维护成本。

该方案曾经过完整评估：可行性分析 → 改动清单 → 方案修正 → 收益利弊量化，共 4 份文档。

### 备选方案

| 方案 | 内容 |
|---|---|
| **A. 保持现状** | 继续维护自实现签名算法 |
| **B. 无头浏览器替换** | 用 Chromium 运行时替代签名算法，算法返工归零 |

### 决策

> **选择 A：放弃方案 B，在现有签名 SDK 基础上继续开发。**

### 理由（量化依据）

| 维度 | 结论 |
|---|---|
| 交换性质 | 用「可预测的资源消耗」换「不可预测的人力返工」——**方向本身是对的** |
| 最大收益 | **失效自恢复**：平台改版后由平台自己更新页面，算法返工归零。这是唯一无法用工程手段在现方案里复制的收益 |
| 延迟代价 | **5–10x**：现方案本地签名多付 **103.7ms**；浏览器方案每请求 **205ms** + 首次导航 **2.1s** |
| 内存代价 | 每 context **150–300MB** |
| 架构代价 | 自动运营的 60s 轮询必须重构为小时级 + 按需拉起 |
| **「删掉近万行算法」是错觉** | 实测签名层 16 文件 / 92.8KB，**真正可退出的只有 60%**（55.9KB / 1335 行）。RAP 系 13.7KB **很可能保不住**（`apis/xhs_pc_apis.py:37-44` 的 RAP 白名单内含 `search/notes`、`feed`、`user_posted`——正是采集核心接口）；上传链路的独立签名 + Node 运行时**必须保留** |
| 部署栈后果 | 切换后是 **Python + Node + Chromium 三者并存，比现在更重** |
| 收益兑现是递延的 | 降级路径正式下线前，付的是双轨成本、拿的是潜在收益；中途放弃则双轨成本白付 |
| 新增单点 | 浏览器网关崩溃 → 全链路断；僵尸进程、Chromium 升级、反检测补丁都需持续投入。这属于**新建一个服务**，不是迁移 |

### 最终理由

> 本项目是**小时级中低频负载**，收益主要集中在「登录稳定性、失效自恢复、巡检零配额」三处，而不是「删算法」。但这些收益的实现前提（多进程浏览器状态管理 + 反检测持续投入 + 新增单点运维）与「降低维护成本」的初衷**相抵**，且会引入一个全新的重型运行时。

### 未验证的生死假设（现已无需验证，记录备查）

方案依赖「在页面里 `fetch` 同源接口，平台拦截器会自动补签名」。原生 `fetch` 不可能被自动加请求头，除非平台 monkey-patch 了全局 `fetch`/`XMLHttpRequest`——而仓库里 RAP 的证据反向倾向「按需现算、非全局透明拦截」。该假设成立与否会决定实现形态是「在页面里发 HTTP」还是「劫持平台自己的请求器」，**复杂度差一个台阶**。

### 代价

- 仍需持续维护签名算法（平台改版时要跟进）
- 失去「失效自恢复」这一项无法复制的收益

### 关联

- 归档文档：`docs/_legacy_v1/_archive/10`、`12`、`13`、`14`
- 二开决策参考：ADR-010

## ADR-002 · 签名算法唯一实现于 JS，Python 侧不重写

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |

### 背景

签名算法（RC4、XXTEA、DES-ECB、CRC32、自定义 Base64 等）的原生形态是 JavaScript（从浏览器侧提取）。

### 备选方案

| 方案 | 内容 |
|---|---|
| A | 用 Python 重写全部算法 |
| **B** | **保留 JS 原版，Python 通过 Node 子进程调用** |

### 决策

**选择 B。**

### 理由

1. **JS 是原版**，行为可对齐浏览器，无移植误差
2. **单源实现**，平台改版只需改一处；双份实现必然漂移
3. Python 侧职责收敛为：序列化输入 → 调 Node → **校验输出**

### 代价

- 依赖 Node 运行时（新增部署依赖）
- 每次签名约 100ms 的进程启动开销
- 需要**输出门禁**（长度/前缀/正则）防止静默降级

### 关联

- 实现：`xhs_utils/xhs_pc/runtime.py:68`、`xhs_utils/xhs_creator/runtime.py:68`
- 硬约定：`03_开发文档/01_开发规范与架构硬约定.md` H3

## ADR-003 · 采用单体 + 严格分层，不拆微服务

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |

### 决策

单体应用 + 严格分层（前端 SPA → API → Service → Adapter → SDK）。

### 理由

1. 单机自部署，**单实例并发用户数十人量级**
2. 小时级中低频负载，**真正的瓶颈在平台侧风控而非本机吞吐**
3. 微服务会新增服务发现、配置中心、链路追踪、分布式事务等运维成本
4. 分层已足以隔离变更影响面（`apis/` 被 adapters 隔离）

### 代价

- **多副本不安全**（APScheduler 与 FastAPI 同进程，无分布式锁）—— 见 `05_项目沉淀/02` T-03
- 单点故障

### 适用边界

账号数 < 100 时单机足够；账号数 100–500 换 MySQL；**需要多副本时必须先解决调度锁**。

## ADR-004 · Cookie 版本化存储，不覆盖写

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |

### 决策

每次登录/导入成功，向 `account_cookie_versions` **追加**一条新版本；取用按 `created_at desc, id desc`。内容 Fernet 加密。

### 理由

1. 平台可能拒绝新 Cookie（换回旧的可用）
2. 账号被限流时可对比历史版本
3. 审计需要（何时换了凭证）
4. 泄露单一版本不必然影响当前使用

### 代价

- 表会累积（需定期清理，目前无清理任务）
- 查询需 `order by` 取最新

### 关联

- `03_数据模型设计.md` §3.2、硬约定 H5

## ADR-005 · 全项目时区统一东八区

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |

### 决策

全项目时间统一走 `backend/app/core/time.py::shanghai_now()`，**禁止裸 `datetime.now()`**；数据库存 **naive 东八区时间**。

### 背景

历史上曾存入 UTC 时间，导致排期错乱。项目已写过两段幂等迁移（`app_migrations` 登记）把存量时间整体 `+8h`。

### 代价

- 数据库存的是 naive 时间，跨系统对接时需注意
- ⚠️ **调度器时区是 UTC**（`BackgroundScheduler(timezone="UTC")`），job 内做业务时间比较需显式处理

### 关联

- `core/time.py:9-10`、`core/database.py:94-149`、硬约定 H2

## ADR-006 · `apis/` 禁止直接修改

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |

### 决策

`apis/` 是底层 SDK，**上层只能经 `backend/app/adapters/xhs/` 中转**。

### 理由

1. `apis/` 承载逆向代码，变更影响面是全项目
2. 适配层是唯一的翻译边界（把 `(success, msg, data)` 三元组翻译成业务对象）
3. SDK 可独立作为能力层被外部 Agent 工具链复用（skills）

### 代价

- 每次调用多一层间接
- 适配层需要重复维护方法签名

### 例外

向 SDK 加新参数时（如二开的 `goods_info`），**必须保证默认值向后兼容**。

## ADR-007 · 能力驱动而非类型分支

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-17 |
| **状态** | ✅ 已采纳 |

### 背景

二开需要支持三种店铺类型（个人店 / 个体工商户店 / 企业店）与非店铺账号。

### 备选方案

```python
# 方案 A：按类型分支
if shop.shop_type == "personal":
    can_attach_goods = False          # ← 这个假设可能是错的
elif shop.shop_type == "enterprise":
    can_attach_goods = True

# 方案 B：能力驱动
if shop.capabilities["can_attach_goods"]:
    ...
```

### 决策

**选择 B：代码只读运行时探测出的 `capabilities`，永不读 `shop_type` 决定行为。**

### 理由

1. **映射是猜测**：外部资料在「个人店能否挂商品」上直接矛盾
2. **错误会扩散**：会扩散到发布校验、前端渲染、任务调度、错误提示**至少 4 处**
3. **平台还在演进**：还有旗舰店/专卖店/买手店，每新增一种都要重付一次
4. **方案 B 下新增第四第五种类型，代码零改动**

### 代价

- 必须实现能力探测（多一个模块）
- 探测失败时需要保守默认与显式标记（不能当支持，也不能直接失败）

### 关联

- `08_功能设计_自动化调度与矩阵运营.md` §4

## ADR-008 · 排期用 `scheduled_at` 落库 + 补跑，不用执行侧 sleep

| 项 | 内容 |
|---|---|
| **状态** | ✅ 已采纳 |

### 决策

定时发布只写 `scheduled_at` 落库，由调度器（每 60s）扫描补跑。**不在执行侧 sleep 等待。**

### 理由

1. **进程崩溃不丢任务** —— sleep 方案下进程重启，待发任务全部丢失
2. **天然幂等** —— 补跑逻辑是「取 `scheduled_at <= now` 且状态为 `scheduled` 的任务」，重复触发不会重复发
3. **可观测** —— 待发任务在发布中心可见可取消；sleep 方案下不可见

### 代价

- 排期精度受调度器 interval 限制（默认 60s）
- ⚠️ 依赖调度器可用（`scheduler.enabled` 默认 false → 定时发布不生效）

### 关联

- `services/scheduler_service.py:181`、`07_功能设计_发布链路.md` §3.1

## ADR-009 · 账号与店铺是二维正交模型，不引入新 `sub_type`

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳（2026-09-18 拍板 D3；并已按此实施，T-102 完成）** |
| **决策人** | 项目负责人（D3 拍板）+ 用户（2026-09-18 确认不引入新 `sub_type`） |

### 背景

二开需要支持「有店铺的账号」与「没有店铺的账号（非店铺账号）」。直觉做法是给 `platform_accounts.sub_type` 加一个取值。

### 备选方案

| 方案 | 内容 |
|---|---|
| A | `sub_type` 新增取值（如 `creator_shop` / `creator_noshop`） |
| **B** | **`sub_type` 只表达协议链路；「有没有店铺」由 `shop_account_bindings` 的存在性推导**（*被取代* 2026-09-22：由 `platform_accounts.shop_id_fk` 是否为 `NULL` 判定；**`sub_type` 不表达通道/业务含义这条结论不变**） |

### 决策建议

**选择 B。**

```
sub_type   ∈ {pc, creator}      ← 只表达协议链路（决定 adapter / 域名 / cookie 域）
shop_count ∈ {0, 1, ..N}        ← 由绑定表推导，不是字段、不落库
```

### 理由（四个代价，后两个是账号层特有的）

1. **映射是猜测**：creator 账号既可能有店也可能没店，`sub_type` 无法表达「creator 且无店」
2. **无限扩展**：还要区分「个人店账号」「企业子账号」……每加一种重付一次
3. **改绑即改路由**：`_select_adapter`（`api/accounts.py:57-58`）是 `creator → creator_adapter`，**否则一律 pc_adapter**。用户今天开店明天关店，若改动 `sub_type`，登录适配器会跟着变 → **登录态立刻失效**
4. **状态与事实不同源**：`sub_type` 是静态字段，「有没有店铺」是平台侧事实。店铺被平台关停、子账号被移除绑定时，系统会拿过期字段当真，且无机制发现

### 支撑事实

> 全量 grep 确认：**现有代码里从不存在「账号必须绑店铺」的校验**——13 处 creator 守卫全部只看 `sub_type`。
> **非店铺账号一直是合法、可用的，普通笔记发布零改动。二开是把既有能力显性化。**

### 代价

- 需要引入 `shop_account_bindings` 中间表
- 「有没有店铺」需实时推导（可加缓存）

### ✅ 实施记录（2026-09-18，T-102）

本决策的**必要配套**已落地：`sub_type` 收敛为显式枚举（`core/account_types.py`，
`SUB_TYPE_PC` / `SUB_TYPE_CREATOR`），`api/accounts.py::_select_adapter` 与
`services/scheduler_service.py::_check_single_account` 的 `else` 兜底改为**显式分支 + `raise UnknownSubTypeError`**。

> **这为什么是本决策的必要配套**：原实现是 `creator if sub_type == "creator" else pc`。
> 若将来有人真的给 `sub_type` 加了取值，**它会静默走 pc 分支**——打错域名、用错 Cookie 域，
> 且不报错。**「不引入新 sub_type」这条约定靠人记住是不牢的，靠 raise 才是牢的。**
> 这两处曾被本 ADR 列为「改绑即改路由」的风险点，现已变为**编译期式**的显式失败。

### 关联

- `08_功能设计_自动化调度与矩阵运营.md` §3、`03_数据模型设计.md` §9.2
- 实施：`core/account_types.py`、`api/accounts.py`、`services/scheduler_service.py`
- 相关决策：ADR-014（未知取值的失败策略）

## ADR-010 · 二开走「人工登录 + 只读逆向」，不逆向千帆登录

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳（2026-09-18 拍板 D2：只读逆向 `ark.xiaohongshu.com`，不做 CSV 降级）** |
| **决策人** | 用户 |

### 背景

二开需要获取店铺与商品数据。官方开放平台通道因无企业资质而**机制性关闭**。

### 备选方案

| | A. 全逆向 ark | B. 不挂商品 | **C. 人工登录 + 只读逆向（推荐）** |
|---|---|---|---|
| 登录店铺 | 逆向扫码/密码 | 不需要 | **人工登录后导入 Cookie** |
| 店铺列表 | 逆向 | 不需要 | 逆向（**只读**） |
| 商品列表 | 逆向 | 手动导入 CSV | 逆向（**只读**） |
| 发布 | 逆向 ark 或复用 creator | 现有 creator | **现有 creator + `goods_info`** |
| 新增签名维护面 | 中（登录风控最重） | **零** | 低（只读接口） |

### 决策建议

**选择 C。明确否决 A。**

### 理由

> **登录逆向是全链路中成本最高、风控最严、失效最频繁的一环，而它换来的收益只是「省一次人工操作」。**

绕开它之后，整条链路对现有代码的侵入只剩 `goods_info` 一处。

### 关键支撑：接千帆不是「重新逆向」

| # | 证据 | 出处 |
|---|---|---|
| 1 | `run_signer(api, data)` 签名输入**只有 path + body**，**host 完全不参与** | `xhs_utils/xhs_pc/runtime.py:68-106` |
| 2 | `XHSPlatformConfig` 本就是多业务域扩展点，已有 PC / Creator 两实例 | `xhs_utils/xhs_core/auth.py:15-84` |
| 3 | `HostCookieStore` 已按 host 分域管理 Cookie | `xhs_utils/xhs_core/cookies.py:44-171` |
| 4 | **已有先例**：`apis/xhs_pugongying_apis.py:19-26` 直接构造 `PcDeviceProfile` 给 `pgy` 域签名 | 同栈服务多域跑通过 |

> **结论：接千帆是「加配置 + 加接口」的工程。**

### 代价

- 需要人工登录一次千帆导出 Cookie

## ADR-011 · 项目文档体系重建为「文档先行」五阶段

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ 已采纳 |

### 背景

v1 文档是**事后补写**的：代码写完 → 分析代码 → 输出报告。结果产生 25 份文档，彼此覆盖、结论互相取代，读的人要先分辨「哪份才算数」。

### 决策

重建为**驱动开发顺序**的五阶段体系：需求（小模型）→ 设计（大模型）→ 开发（小模型）→ 测试（大模型）→ 沉淀。

核心铁律：

> **代码变更必须由文档变更发起。** 没有设计文档的功能不写；写了代码但设计文档没跟上，视为未完成。

1. 文档是**开发的前置输入**而非副产品，才能防止漂移
2. 按「模型规格」分阶段：需求文档要短（小模型零歧义），设计文档要细（大模型穷尽）
3. 功能设计**以访问端为基准**拆分，便于并行分工与影响面定位
4. 归档用**移动而非删除**，保留决策理由（v1 的无头浏览器方案评估了 4 份文档，这些理由必须可回溯）

### 代价

- 增加了文档维护成本（**这是有意的**，用文档成本换返工成本）
- 需要纪律执行，否则体系会再次腐化

### 关联

- `docs/README.md`、`docs/00_管理规范/01_文档先行工作流.md`

## ADR-012 · 配置来源优先级：YAML 降为**最低优先级源**，不删键

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳** |
| **决策人** | 实施结论（承接 DEF-004 / T-010 / T-110） |

### 背景

`get_settings()` 原实现把 `default.yaml` 展平后作为**初始化参数**传给 `Settings(**yaml_values)`。
按 pydantic-settings 语义「初始化参数 > 环境变量」，`default.yaml` 里已存在的键**确实覆盖同名环境变量**。

已实测确证：注入 `SCHEDULER_ENABLED=true` / `FRONTEND_SERVE_STATIC=true` / `SECRET_KEY=ENV_SECRET_WINS`，
实际取值为 `False` / `False` / `'dev-only-change-me'`——**三个环境变量全部失效**。
生产后果：JWT 用默认弱密钥签发、`FERNET_KEY` 失效导致**容器重建后历史 Cookie 永久解不开**（不可逆数据损失）。

### 备选方案

| 方案 | 内容 | 评价 |
|---|---|---|
| A | 在 `Settings` 上实现 `settings_customise_sources`，把 YAML 注册为**最低优先级源** | ✅ 采纳 |
| B | 从 `default.yaml` **删除**应由环境变量控制的键 | ❌ 否决 |

### 决策

> **选择 A。来源顺序固定为：`init > env > .env > YAML > secrets`。**

实现要点（三个动作缺一不可）：
1. 新增 `_YamlSettingsSource(PydanticBaseSettingsSource)`，把 YAML 展平结果包成「一个源」；
2. 覆写 `settings_customise_sources`，返回上述顺序的源元组；
3. **`get_settings()` 里去掉 `Settings(**yaml_values)` 的初始化参数**——初始化参数优先级最高，**正是缺陷根因**。

### 理由

1. **方案 B 会让 YAML 的配置能力整体退化**。YAML 的价值在于「给一整套默认值，让部署方只覆盖需要改的」。
   删键之后，那些配置只能写在代码默认值里，运维无法在不改代码的前提下调整——
   **那是把一种错误换成另一种错误。**
2. **方案 A 的语义与注释声明一致**，消除了「文档说一套、实现做一套」的根源。
3. YAML 仍保留在链路上，**原本靠 YAML 生效的配置行为不变**（已回归 `server.cors_origins` 三个来源）。

### 代价与残余风险

| 项 | 内容 |
|---|---|
| ⚠️ **行为变更** | 原本被 YAML「意外压住」的环境变量**现在会生效**。若生产环境里恰好存在同名但取值不同的环境变量，**部署行为会变** |
| **必须做的动作** | **生产部署回归一次**。这不是可选建议——`Dockerfile:66` 的 `FRONTEND_SERVE_STATIC=true` 会从「被压住」转为「真正生效」 |
| 与 T-19 的联动 | `FERNET_KEY` 现在真的能生效了，但也意味着「忘了显式固定」不再是"被 YAML 挡住"，而是"每次换密钥" |

### 防回退

3 条用例锁定：正向（环境变量必须生效）/ 反向保护（YAML 必须仍然生效）/ **顺序锁定**（防止一次重构改回去）。

### 关联

- `core/config.py`（`_YamlSettingsSource` + `settings_customise_sources` + `get_settings()`）
- 缺陷：DEF-004；任务：T-010 → T-110
- 用例：TC-M1-01 / TC-M1-02 / TC-M1-03

## ADR-013 · 发布幂等用 **nullable 唯一键**，不变式为「键非空 ⇔ 占用态」

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳** |
| **决策人** | 实施结论（承接 DEF-002 / T-103） |

### 背景

发布是**不可逆写操作**，但 `publish_jobs` 表**无任何唯一约束**，防重复完全依赖状态机 + 单实例调度。
「检查状态 → 执行发布 → 回写状态」三步非原子，状态回写前崩溃就会重发。

### 备选方案

| 方案 | 内容 | 评价 |
|---|---|---|
| A | 建任务时就生成并落 `idempotency_key`（非空 + 唯一） | ❌ 否决 |
| **B** | **键在「发布前认领」，列 nullable + 唯一** | ✅ 采纳 |

### 决策

> **选择 B。`publish_jobs.idempotency_key`：`nullable=True` + `unique=True`。
> 键 = `{platform}:{账号}:{sha256(标题|正文|规范化 publish_options)[:32]}`。**

**核心不变式（一句话）**：

```
idempotency_key 非空  ⇔  该 job 处于「占用槽位」的状态（publishing / published / scheduled）
```

### 理由

1. **方案 A 会挡死合法流程**。用户「建了任务 → 取消 → 再建同样内容」是完全合法的，
   唯一索引会**无故**把他挡在门外——而且是不可理解的报错。**nullable 是让「未认领」与「已占用」可区分。**
2. **生成时机必须在发布前**，因为「是否占用」是**发布那一刻**的事实，不是建任务那一刻的意图。
3. **判定口径必须统一**：应用层与数据库**都只看列有无值，不按状态过滤**。
   若应用层按状态过滤而数据库不过滤，就会出现「应用层放行 → 数据库 `IntegrityError`」的分裂。

### 释放规则（最容易做错的一处）

| 场景 | 是否释放键 | 为什么 |
|---|---|---|
| 从 `pending` 取消 | ✅ **释放** | 可证明**从未提交**给平台 |
| 从 `scheduled` 取消 | ❌ **不释放** | 平台已受理，本地取消**撤不回** |
| `failed` | ❌ **不释放** | `post_note` 抛错**不保证平台没收到** |

> **通则：只有当能证明「从未提交给平台」时才释放。**
> 宁可让用户看到 409 去平台核对，也**不能替平台做「没发出去」的假设**。

### 代价（必须让用户知道的行为变更）

⚠️ **同一账号 + 完全相同内容只能发布一次**；重发需**改内容或换账号**。
这是**有意的**（验收指标「重复发布 0 次」是硬指标），但**属用户可感知的行为变化**，
需在 UI 文案与用户文档中说明，否则会被当成 bug 报上来。

### 连带决策：已提交的任务不得原地重试

实施本决策时发现**同一事实的第二个入口**（DEF-031）：
`retry_publish_job` 会无条件把 `failed` 重置为 `pending` 并**清空** `external_note_id`。
若该 job 实际已提交给平台（`external_note_id` 非空）但回写状态前崩溃，重试会**再发一篇**。

> **决策：只要 `external_note_id` 非空即拒绝重试（409）。**
> 语义变为「**已提交 → 终态，只能新建任务，不能原地重试**」。
>
> 也就是说：**`external_note_id` 是「不可逆的已提交证据」，不是可清空的中间态。**
> 这一条同时为 T-108（多副本调度）确立了判断口径——**T-108 必须复用本不变式，不得另起一套**。

### 防回退

4 条用例：键确定性（含 JSON 键顺序不敏感）/ 唯一索引兜底 / 释放后可重认领 / 列 nullable+unique。
另有 TC-PUB-17（已提交禁重试）、TC-PUB-18（未提交可重试）。

### 关联

- `models/publish.py`、`services/publish_service.py`（新增）、`api/publish.py`、`services/scheduler_service.py`、迁移 `b1e4d7c9a2f3`
- 缺陷：DEF-002、DEF-031；任务：T-103（T-108 依赖本决策）
- 后续：`03_数据模型设计.md` 二开的 `product_note_jobs.idempotency_key` 应沿用同一不变式

## ADR-014 · 未知取值的失败策略**按猜错后果**定，不统一处理

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳** |
| **决策人** | 实施结论（承接 DEF-014 / T-104，配套 ADR-009 / T-102） |

### 背景

本轮同时引入了两个「取值集合受控」的字段：`platform_accounts.sub_type` 与 `users.role`。
一个自然的想法是**统一处理**：都抛错，或都兜底。**这个想法是错的。**

### 决策

> **失败策略取决于「猜错的后果」，不取决于字段长得像不像。**

| 字段 | 字段性质 | 未知取值时 | 猜错的后果 |
|---|---|---|---|
| `sub_type` | **路由开关**（决定 adapter / 域名 / Cookie 域） | **`raise UnknownSubTypeError`** | 打错**域名**与 Cookie 域 → 静默失败或更糟 |
| `role` | **权限开关**（决定能否改全局设置） | **保守降级为 `user`** | 少给权限 → 只是功能受限，**属安全方向** |

### 理由

1. **路由类字段猜错的后果是「做错事」，权限类字段猜错的后果是「少做事」。**
   前者必须**立刻、显式、响亮地**失败；后者**沉默地保守**才是正确行为。
2. **统一抛错会制造可用性事故**：历史数据里 `role` 为空（迁移前的行）若抛错，**整个系统登不进去**。
3. **统一兜底会制造安全问题**：`sub_type` 未知若兜底为 `pc`，新增链路时**静默走错分支**——
   这正是 DEF-015 之后最需要防止的事情（见 ADR-009 实施记录）。

### 唯一允许的隐式默认

| 情形 | 处理 | 理由 |
|---|---|---|
| `sub_type` 为 `None` / `""` | → `pc` | 历史数据可能根本没写该字段；`pc` 是初始版本唯一存在的链路 |
| `role` 为 `None` | → `user` | 迁移前的行 |

> 注意区分：**「缺失」（`None` / `""`）走隐式默认，「未知非空取值」走各自策略。**
> 这两者不是一回事——前者是数据从来没写过，后者是**有人写了我不认识的东西**，后者才是危险信号。

### 防回退

`TC-M1-06`（`sub_type` 未知抛错）、`TC-M1-14`（`role` 未知保守降级）——**把这条差异固定成用例**，
防止后人「顺手统一一下」。

### 关联

- `core/account_types.py`、`core/roles.py`、`core/deps.py::require_admin`
- 决策：ADR-009（不引入新 `sub_type`）；缺陷：DEF-014；任务：T-102 / T-104

## ADR-015 · 假实现宁可**下线**，不新增「无法生效」的接口

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳** |
| **决策人** | 实施结论（承接 DEF-007 / T-105） |

### 背景

`PATCH /api/accounts/{id}` 是**假实现**：恒返回 `{"id":..., "status":"updated"}`，
**不查库、不落库、无鉴权**。前端当前未调用，但一旦接上就会造成「改了没生效」且**无任何报错**。

修复有两条路：**实现真实更新**，或**直接下线**。

### 决策

> **选择下线。同时确立判据：一个接口若在数据模型上找不出「它应该改什么」，就不该存在。**

### 理由

已核实 `PlatformAccount` 上**不存在用户可编辑字段**：

| 字段 | 为什么用户不能改 |
|---|---|
| `nickname` / `avatar_url` / `profile_json` | 由平台同步，且**会被健康检查覆写**——用户改了下次巡检就没了 |
| `status` | 系统推导（健康检查/巡检的结论），不是用户的输入 |
| `sub_type` | 由绑定方式决定（见 ADR-009） |

→ **没有任何字段满足「用户可改且改了有意义」。**

> **核心判断：保留一个「改了不生效还不报错」的接口，比返回 404 更危险。**
> 404 至少会让人发现走错了路；假成功会让人以为路走通了。

### 代价与后续

| 项 | 内容 |
|---|---|
| 代价 | 前端若已有调用会失败（已核实**未调用**，无影响） |
| **后续（不是否决，是另开需求）** | 若确实需要「账号本地别名 / 停用标记」（矩阵场景区分数十个账号**确有价值**），应作为**独立需求**新增**专用列**（如 `local_alias` / `is_disabled`），与平台同步字段**物理隔离**，**不要复用本路由的旧契约** |

> **为什么强调「物理隔离」**：这个接口之所以会变成假实现，根因就是**把「本地意愿」和「平台事实」混在一个对象上**。
> 复用旧契约会把同一个混淆再引入一次。

### 关联

- `api/accounts.py`（路由已删除，原位留决策说明注释）
- 缺陷：DEF-007；任务：T-105；用例：TC-ACC-13 / TC-M1-08
- 同类风险：`05_项目沉淀/02` §2.5 T-15（后端死模块）、T-16（mock 端点）——**同一判据可复用**

## ADR-016 · 账号级互动数据只有**一个真相源**（`/v1/user/otherinfo`），取不到就显式说不可得

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳** |
| **决策人** | 实施结论（承接 DEF-039） |

### 背景

账号卡片要展示「粉丝 / 关注 / 获赞数」。原实现从 `/v2/user/me` 的 `data.interactions` 取。
**实测该响应没有这个字段**（`data` 只有 8 个键），于是三项**恒为空**，而页面只是安静地显示 `-`。

### 决策

> **① 计数只来自 `/v1/user/otherinfo` 的 `data.interactions`；② 取数实现只有一份
> （`services/account_service.fetch_account_metrics`），`/check`、`/import-cookie`、
> `/metrics` 三个入口全部复用它；③ 取不到时返回**可读原因**，不许填 0，也不许静默为空。**

### 理由

| 理由 | 说明 |
|---|---|
| 一个事实不能有两个形状 | 身份字段（`/v2/user/me`）与计数（`/v1/user/otherinfo`）**本来就是两个接口**；把它们当成一个，是这次缺陷的根因 |
| 「猜出来的可用」比「明确不可用」危险 | 猜一次字段名的代价是**静默为空**；明确写出「不可得 + 原因」则会被人发现并补上 |
| 能力优先于类型 | 路由按 Cookie 是否含 `web_session` 判定，**不看 `sub_type`**：creator 账号将来带上 www 会话即可自动取数 |
| 省请求但不赌 | 优先用落库的 `external_user_id` 当 `target_user_id`（PC 账号上它等于 `/v2/user/me` 的 `user_id`），失败才回退身份请求 |

### 代价与后续

| 项 | 内容 |
|---|---|
| creator 链路 | **结构性不可得**（身份接口无计数；数据中心候选端点实测 404）→ 卡片显示 `-` + 一行灰字原因，且**零平台请求**。补齐需真实抓包（看板卡⑧） |
| 状态分离 | `/metrics` 只刷数字，**不改 `status`**；「账号是否可用」仍由 `/check` 裁决 |
| 失败不擦数据 | 刷新失败时保留旧值（`_first_present(新值, 旧值)`），避免一次网络抖动把好数据清零 |

### 防回退

## ADR-017 · 列表翻页改为**滚动触发**，取代「加载更多」按钮

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳**（**推翻** v1.3 「不做无限滚动」的结论） |
| **决策人** | 用户明确要求（设计文档 §20 / 需求 R7 / D13） |

### 背景

v1.3 的设计是「`cursor` + 显式『加载更多』按钮，不做无限滚动」，理由是「避免隐式全量拉取触发风控」。
用户要求改成滚到底部自动加载，并移除按钮。

### 决策

> **改为 sentinel + `IntersectionObserver` 触发翻页。** 风控护栏从「按钮」转移到
> **「一页一请求 + in-flight 去重 + 失败即停 + 无自动重试 + 无后台预取」**。

### 理由

旧理由把**触发方式**当成了**风控面**的来源。真正的风控面来自**循环拉取**：
用户连点 10 次按钮与连续滚动 10 屏，产生的请求数完全相同。
相反，自动触发如果缺护栏会更糟（例如失败后自动重试），所以护栏写在触发器里而不是按钮上。

| 措施 | 具体做法 |
|---|---|
| 有界 | 一次触发**只拉一页**；候选值来自面板状态，用 ref 读取以防 observer 重建 |
| 失败即停 | 任何一页失败 → 停止自动触发，渲染可读错误 + 显式「重试」；**不做自动重试** |
| 不预取 | 只在哨兵进入视口（提前 240px）时才请求；无后台预取、无定时器 |
| 观测方式 | 用 sentinel 而不是监听 `scroll`：窗口滚动与祖先容器滚动两种布局都成立 |

### 代价与后续

| 项 | 内容 |
|---|---|
| 代价 | 用户对「还能不能继续加载」的感知变弱 → 页脚用文案补上（继续下滑加载后续笔记 / 已全部加载） |
| 搜索态 | **不启用**无限滚动（搜索有自己的「继续搜索更早内容」，语义不同） |
| 风险 | 若将来出现「滚到底自动重试」这类改动，**必须同时改回这条 ADR** |

### 防回退

- `tests/backend/test_page_optimizations.py`：源码里**不得出现**「加载更多」字样、
  必须存在 `IntersectionObserver` / `sentinelRef` / 失败态文案与「重试」
- 设计文档 §20 的契约表 + §12 风控表（原「手动翻页」一行已标注被取代）

### 关联

- 需求：R7 / D13；设计：`02_设计文档/12` §20；用例：TC-SELF-39/40/41

## ADR-018 · 互动数据缺值**渲染 `0`**，提示文案**钉死在 25–30 字**；Creator 计数按 WONTFIX 收口

| 项 | 内容 |
|---|---|
| **日期** | 2026-09-18 |
| **状态** | ✅ **已采纳**（用户拍板；**修改** ADR-016 的「取不到就不显示」呈现口径） |
| **决策人** | 用户（需求 `01_需求文档/03` R10 / D16） |

### 背景

ADR-016 定下「账号级计数取不到就显式说不可得」，落地成卡片渲染 `-` + 一段**很长的**说明
（原文 ≈70 字：「创作者平台（creator.xiaohongshu.com）不返回账号级互动数据：身份接口实测无任何计数，
数据中心候选端点实测 404。需网页版登录的账号才能读取该三项。」）。

用户 2026-09-18 晚验收后给出两条相反方向的调整：
① 三项计数**缺值就显示 `0`**（`-` 让人以为是坏了）；② 那段提示**太长**，要压到 **25–30 字**。

### 决策

> **计数缺值渲染 `0`（不是 `-`）+ 一行 25–30 字的原因；Creator 计数不再追（WONTFIX）。**

### 理由

- `0` 是**可读的默认值**：卡片五字段结构恒定、视觉不空洞；而「真 0」与「没取到」的判断
  由**旁边那行原因**承担——信息并没有丢，只是从「字段本身」搬到了「原因行」。
- 长度上限是**注意力预算**：一句 70 字的解释贴在卡片上等于没写；25–30 字够说清「为什么是 0」与「怎么才能拿到」。
- Creator 侧无可用来源（§21.3 实测：身份接口无计数、四个数据中心候选端点 404），
  继续投入的期望收益低于成本 → **WONTFIX**，而不是「待办」。

### 代价与护栏

| 项 | 内容 |
|---|---|
| 代价 | `0` 会让不看原因行的人误以为「粉丝就是 0」——**这是用户明确选择的取舍** |
| 不变量 | 库里 `profile_json` **仍写「未知」**，不得把 `None` 改写成 `0`（写库口径不变，只有渲染变） |
| 长度 | 四条固定原因 26 / 28 / 27 / 25 字；**动态部分（平台 `msg`、异常文本）由 `_clamp_reason()` 截断到 30 字** |
| 小红书号 | 保持 `-`——它不是计数，「没有」与「是 0」对它没有区别 |

### 防回退

- `tests/backend/test_account_metrics.py`：钉死四条原因文本与 **25–30 字窗口**、`_clamp_reason` 的截断行为
- `tests/backend/test_page_optimizations.py`：账号页三项计数**不得再出现 `|| "-"`**、必须是 `?? "0"` 兜底
- 需求 R10 / D16；设计 `02_设计文档/12` §21.2+§21.3、`04_功能设计_Web运营端.md` §2.4；用例 TC-ACC-22 / TC-ACC-27

### 修订（2026-09-19）· 长文案的溢出呈现

用户 2026-09-19 验收账号卡片时指出：「读取互动数据失败，请稍后重试，或重新登录网页版账号」这类提示
**在窄列里一行展示不完**。补一条**呈现规则**（**只改呈现，不改文案、不改长度窗口**）：

> **一行放不下的文案 → 单行 `…` 收起 + 悬停 Tooltip 显示全文；不要换成换行。**

- **适用范围**：`metrics_reason` 原因行、`status_message` 平台原文行、「更新时间」行、M1.9 同步进度/结果行。
- **实现**：antd `Text ellipsis={{ tooltip }}` —— 它**只在真被截断时**才出 tip，没截断时不会平白多一个悬停气泡。
- **为什么不换行**：换行会把卡片撑高、把下面的按钮挤出可视区，而且同一屏的账号卡高度会参差不齐。
- **与原决策的关系**：`0` 兜底、25–30 字窗口、库内写「未知」三条**全部不变**；本次只回答「放不下时怎么办」。

### 关联

- 需求：R10 / D16；设计：`02_设计文档/12` §21.2 / §21.3；用例：TC-ACC-22 / TC-ACC-27
- 修改的前置决策：**ADR-016**（真相源不变，只改「取不到时怎么显示」）

## ADR-019 · 笔记挂载商品的来源定为**千帆**，且千帆只读链路**不引入签名**

> **日期**：2026-09-19 · **状态**：已实施 · **承接**：需求 R5 / D8；设计 `02_设计文档/12` §19 / §24

### 背景

用户验收「我的笔记」时报告：**创作者账号下所有笔记都不显示挂载商品**。
追问一句话定调：**移除「PC 链路不返回…待接入」的占位说明，直接对接千帆后台**；
随后追加：**创作者账户数据全部接入千帆**。

### 决策

1. **商品的唯一真相源 = 千帆商家后台（`ark.xiaohongshu.com`）的商品笔记列表**
   （`GET /api/edith/goods-note/list` → `note_infos[].goods_infos[]`）。
   PC 链路与创作者链路**都不返回**该数据，这不是适配遗漏。
2. **千帆登录态独立存储**（~~新表 `shop_account_bindings.encrypted_cookies`~~ → **2026-09-22 起：`account_cookie_versions` 的 `ark` 通道**，随绑定表移除改口径），
   **复用账号 Cookie 不可行**：实测 `code=-13000 缺失登录凭证`，浏览器访问 ark 被 302 到
   B 端统一登录 `customer.xiaohongshu.com`。
3. **千帆只读链路不实现签名**：实测不带 `x-s` / `x-t` / `x-s-common` 也返回 200
   ⇒ 满足二开 C4「不新增签名维护面」；`QIANFAN_PLATFORM_CONFIG`（T-201）在只读链路上**不需要**。
4. **映射落本地表 `shop_note_goods`**（`note_id` → 商品 + 千帆指标）：

### 备选与否决

| 备选 | 否决理由 |
|---|---|
| 继续在 PC / 创作者链路找商品字段 | 已三层实测为空壳/不存在（§19.0），继续找只是重复劳动 |
| 逆向 App 端签名取商品 | 成本与风控面最高（D8 早已否决） |
| 第三方聚合 API | 外部付费依赖 + 数据合规存疑 + 字段口径不透明 |
| 每次浏览现查千帆 | 千帆按页给数据且无 note_id 过滤 ⇒ 每翻一页笔记要打多次千帆 |

### 代价与护栏

| 项 | 内容 |

| 护栏 2 | 登录态失效 → 502 + 绑定标 `invalid` + 可读原因，**不清空已有映射** |
| 护栏 3 | 绑定响应**白名单**构造，千帆响应里的 `user_email` / `config_values` 一律丢弃 |
| 护栏 4 | 覆盖率必须对用户可见（`synced_notes / shop_total`），否则「没同步到」会被读成「没挂商品」 |

## ADR-020 · 店铺 ↔ 账号定为 **1:1**（由 DB 强制），`shop_account_bindings` 整表移除

**日期**：2026-09-22　**状态**：已实施（回归 558 passed / 0 failed）　**推翻**：ADR 早期「账号↔店铺 N:M」（v1.15 / T-32）

### 背景

T-32 把店铺↔账号从 1:1 改成 N:M，动机是「企业店多子账号读同一店」。该动机需要用**中间表 +
「用哪条绑定」排序规则**来维持唯一性，并留下了两个已知副作用：① `binding_for_account()` 的
确定性排序（同步过映射的优先 → `id` 倒序）；② 真实库里一条跨租户脏行（DEF-054 的「账号 15」）。

### 决策（用户 2026-09-22 原文）

> **「不再允许同店铺多账号，一个店铺下只存多个平台的会话令牌」**

⇒ **关系回到 1:1**，且**由 DB 强制**（不靠应用层判断）。

### 理由

1. **N:M 的动机不成立**：用户要的是**同店多平台令牌**（www / creator / ark），不是**多账号读同一店**。
2. **中间表表达 1:1 必然产生随机性**：一店多行就必须回答「用哪一行」，而这个答案只能靠**排序规则**
   维持 —— 与「不写第二份真相源」冲突（真相变成「哪条排序在前」）。
3. **DB 约束优于应用闸门**：部分唯一索引让「同店第二个账号」**根本插不进去**，跨租户残留行也会
   在写入时被拒（`bind_shop` 再把 IntegrityError 翻成 409 + 人话）。应用层闸门是**可以漏的**（DEF-054 就是漏的）。
4. **软删必须不占店**：约束写成 `WHERE shop_id_fk IS NOT NULL AND deleted_at IS NULL` —— 整列 `unique=True`
   会让软删账号继续占店（DEF-055 的同类陷阱）。

### 后果

* 表数 **25 → 24**；`shop_note_goods.binding_id` → `platform_account_id`（换列不改语义）。
* 千帆取票收敛为**唯一入口** `qianfan_cookies_for_account()`（只认本账号 `ark` 通道，**无兜底**）。
* `account_count` / `shop_account_count` 从契约里**删除**（1:1 下无信息量）。
* 迁移 `m5n6o7p8q9r0` 顺带**物理删除多余账号**（`id IN (1, 15)`）及其从属行；备份在 `data/spider_xhs.db.bak-20260922-pre-drop-bindings`。

### 被这条决策取代的旧结论

| 旧结论 | 出处 | 现状 |
|---|---|---|
| 账号 ↔ 店铺必须 N:M（企业店多子账号） | v1.15 / T-32 | **被取代**（用户否决该场景） |
| 唯一约束 `(shop_id_fk, platform_account_id)` | 数据模型 §9.2 | **被取代** → 部分唯一索引 `uq_platform_accounts_shop_id_fk` |
| 「用哪条绑定」排序规则 | 设计 12 §24.3.3 | **被取代** → 一行即答案 |
| `shop_account_bindings` 是取票兜底 | 归档 §4.10.9 前后 | **被取代** → 只剩账号 `ark` 通道 |

> ⚠️ **教训（可复用）**：**中间表只该表达真 N:M**。用中间表表达 1:1，等于把唯一性从 DB 挪到
> 「应用层的排序规则」上 —— 而排序规则是**可以被漏掉的**，唯一索引不行。
