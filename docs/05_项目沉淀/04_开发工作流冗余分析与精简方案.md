# 开发工作流冗余分析与精简方案

> - **性质**：阶段五 · 项目沉淀（对「开发全流程效率很低」的调研结论 + 精简方案）
> - **建立**：2026-10-06
> - **调研方法**：逐环节实测 docs 规模、各文档最后修改时间、被引用次数、与代码实测值的偏差，判定「重资产（每轮要维护） vs 轻资产（一次性快照）」。
> - **结论一句话**：五阶段流程本身不冗余，是被**过度实体化**了——每轮要求产出的文档里，有一半是「做完一次就不再变化」的快照，却挂在「每轮必做」清单里占位，形成僵尸文档；另有「任务台账 vs 看板卡」「教训文档 vs 技能」两处双轨重复。

## 三、根因

1. **文档自我增殖**：阶段四「六项必须执行」里，codegraph / mock 清单 / 开关核查是**一次性静态快照**，却和「用例库 / 缺陷标记」这些活文档混在同一个「每轮必做」清单里 → 要么不更新变僵尸、要么机械更新浪费力气。
2. **进度源双轨**：设计上任务台账是「唯一进度真相源」，实际操作全走看板卡 → 台账 147KB 停在 9-21 再没动，必然腐烂。
3. **沉淀与技能重复**：`核心教训提炼.md`（196KB）与技能 `xhs-feature-increment-loop`（281 行）同源，但技能是**按需加载、真被消费**的载体，文档是**摊开摆着、只被索引指一下**的档案。
