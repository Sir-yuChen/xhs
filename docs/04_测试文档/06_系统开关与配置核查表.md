## 1. 核查方法：每个开关必须回答三问

| # | 问题 | 判定方法 | 判定陷阱 |
|---|---|---|---|
| **Q1** | **存在哪里？** | 分类：`数据库` / `git 配置文件` / `代码常量` / `请求参数` | — |
| **Q2** | **UI 上能不能改？** | 找页面与组件；找不到 → 「无 UI 入口」 | 「只读展示」不算能改 |
| **Q3** | **改了真的生效吗？** | **读代码找运行时读取点** | ⚠️ **存在字段 ≠ 生效**（关键陷阱） |

### 1.1 判定示例（最容易出错的一类）

```
monitoring_targets.crawl_interval_minutes
  Q1：存在 DB          ✅
  Q2：无 UI（前端类型里都没这个字段）
  Q3：❌ 未找到运行时读取点 → run_monitoring_refresh_for_all_users
      按调度器全局 interval 全量刷新，从未读这个字段
  → 结论：【死配置】——字段存在，但配了不生效
```

> ⚠️ **2026-09-24 DEF-066 补注**：上文 Q3 提到的 `run_monitoring_refresh_for_all_users`
> （全库 active targets）**已被删除** —— 内置任务行按用户各持一份后，监控刷新改走
> `run_monitoring_refresh_once(user_id)`（只刷行主人的 targets）。【死配置】结论本身
> **不受影响**（新函数同样不读 `crawl_interval_minutes`），原句保留备查。

## 4. 问题清单

### 4.1 🔴 严重问题（3 个）

#### 问题 1 · S14 死配置：`crawl_interval_minutes`
| 项 | 内容 |
|---|---|
| 现象 | 字段存在于 `models/monitoring.py:28`（默认 60），前端也有创建时的输入框（`benchmarks-page.tsx:273-299`），但 `run_monitoring_refresh_for_all_users`（`scheduler_service.py:385-401`）**从未读取该字段** |
| 影响 | 用户配置的刷新间隔**完全无效**，实际按调度器全局 interval 全量刷新 |
| 严重性 | 高——这是典型的「**界面看起来能用，实际不生效**」，用户会反复调大间隔却毫无效果 |
| 修复 | 二选一：① 接线（读该字段决定每个 target 是否到期）② 删除字段与 UI 输入项 |
| 关联 | DEF-016 / T-111 / TC-MON-06 |

> ⚠️ **2026-09-24 DEF-066 补注**：本条的 `run_monitoring_refresh_for_all_users` 调用点**已被删除**（内置任务行按用户各持一份后改走 `run_monitoring_refresh_once(user_id)`）；【死配置】结论不变（新路径同样不读该字段），原句保留备查。
#### 问题 2 · S11 部分生效：`platform_accounts.status`
| 项 | 内容 |
|---|---|
| 现象 | 状态被用于：概览健康统计、监控抓取选号、Cookie 巡检。但**发布路由（`api/publish.py`）与采集路由都不校验 `status`** |
| 影响 | 已过期账号仍会进入完整的发布流程（含素材上传等耗时操作），最后在平台侧失败，错误信息误导 |
| 严重性 | 高——白跑 + 误导 |
| 修复 | 发布与采集前加 `status == "active"` 前置校验 |
| 关联 | DEF-005 / T-109 / TC-PUB-16 |
| 附带风险 | `PATCH /accounts/{id}`（`accounts.py:222`）是假实现——如果将来有人接上这个前端入口，就会出现「改了状态但不落库」的**双重问题**（DEF-007） |

#### 问题 3 · S13 无法手动恢复：`monitoring_targets.status`
| 项 | 内容 |
|---|---|
| 现象 | 连续失败 ≥3 时系统**自动**置 `paused`（`monitoring_crawl_service.py:238-240`）；但 `updateMonitoringTarget`（`api.ts:655`）**无任何页面调用** → 用户无法恢复 |

| 关联 | DEF-012 / T-112 / TC-MON-05 |

### 4.3 ✅ 配置优先级缺陷（1 个，已实测确认并**已修复**）

#### 问题 7 · ~~`get_settings()` 的 YAML **确实**覆盖环境变量~~ → ✅ 已修复
| 项 | 内容 |
|---|---|
| 位置 | 原 `backend/app/core/config.py:154-157` |
| 现象 | YAML 展平结果作为**初始化参数**传给 `Settings(**yaml_values)`；按 pydantic-settings 语义「初始化参数 > 环境变量」，`default.yaml` 里已存在的键**覆盖同名环境变量** |
| 与注释矛盾 | `default.yaml:6-7` 与 `core/config.py:18-20` 均声明「环境变量优先级最高」——**注释是错的，代码行为与注释相反** |
| **实测结论** | ✅ **2026-09-18 实测：环境变量全部失效**。注入 `SCHEDULER_ENABLED=true` / `FRONTEND_SERVE_STATIC=true` / `SECRET_KEY=ENV_SECRET_WINS` → 实际取值分别为 `False` / `False` / `'dev-only-change-me'`。三个全被 YAML 压过 |
| 影响 | ① `Dockerfile:66` 的 `FRONTEND_SERVE_STATIC=true` **确定被覆盖** → 生产静态服务失效；② 生产 `SECRET_KEY` **确定失效** → JWT 用默认弱密钥签发；③ `FERNET_KEY` 失效 → Cookie 加密密钥不稳定，容器重建后历史 Cookie **永久解不开**（不可逆） |
| 置信度 | ✅ **已实测确认（Python 3.12 / pydantic-settings 2.15.0）** |
| 验证 | TC-SYS-07（✅ 已执行）→ T-010（✅ 已完成） |
| **修复状态** | ✅ **已修复（2026-09-18，T-110）** |
| **修复方式** | 在 `Settings` 实现 `settings_customise_sources`，把 YAML 注册为**最低优先级源** `_YamlSettingsSource`（`init > env > .env > YAML > secrets`），并去掉 `get_settings()` 的 `Settings(**yaml_values)` 初始化参数（**初始化参数优先级最高，正是根因**） |
| **未采用的方案** | ❌ 从 `default.yaml` 删键——会让 YAML 配置能力整体退化。详见 ADR-012 |
| **对开关表的整体影响** | ✅ **本表所有开关的「环境变量」一列从「受 DEF-004 影响」转为「可信」**。即：下方 S3、S6 等标注的风险已解除 |
| 回归 | `test_m1_governance.py::test_config_*`（3 条：正向 / 反向保护 / 顺序锁定） |
| **残余动作** | ⚠️ **生产部署需回归一次**：原本被 YAML 意外压住的环境变量现在会真正生效 |
