# 74 · 测试体系问题分析与优化方案

> 2026-10-26 立。用户口径：「测试体系还是有很大的问题，你记录下来后续分析，
> 对测试体系优化补全相关逻辑，测试整体要系统化，降低耗时提高效率」。
>
> 本文是**分析 + 方案**，不是已完成事项。每条问题都带本轮实测证据。

## 1. 触发这次记录的三次实况

| # | 现象 | 实测证据 |
|---|---|---|
| 1 | 全量回归「跑不完」 | `-n auto` 两次跑到 50~89% 被杀：`too many clients already` → `pytest_sessionfinish` 抛 `OSError: cannot send (already closed?)` → **xml 不落盘**、退出码 `127` |
| 2 | 看起来「17~30 个失败」，实际全绿 | 我读的是**旧 xml**（17:18 / 04:29）。逐个文件 `-n0` 复查：`test_system_api` 30 ✅ / `test_app_settings` 29 ✅ / `test_initial_data` 24 ✅ / `test_scheduled_jobs` 63 ✅ / 权限 360 ✅ |
| 3 | 全量越跑越慢 | 两个 pytest 同时在跑（全量 `-n4` + 我启动的单文件串行），抢同一批 DB 连接，`pg_stat_activity` 30 条、含 `idle in transaction` |

**共同点：三次都不是代码缺陷，全是「测试基础设施」问题** —— 却被误读成「代码大面积坏了」。

## 2. 根因分析（按严重度）

### 2.0 【P0 · 最严重】测试仍大量跑 SQLite，而生产已完全切 PG

用户口径（2026-10-24）「完全放弃 SQLite」；`core/database.py` 现在**非 PG 直接拒绝启动**。
但测试侧没有跟着切完：

| 事实 | 实测 |
|---|---|
| 公共夹具 `conftest.make_engine` | ✅ 已改成 **PG + 每用例独享 schema**（`CREATE SCHEMA` + `search_path`） |
| **但** 34 个测试文件、**41 处**自己另建 `create_engine("sqlite:///…")` | `test_api.py` 6 处、`test_perms_core.py` 5 处、`test_no_traffic_cleanup_runner.py` 4 处、其余每文件 1~3 处 |

**危害（比「慢」严重得多）**：

* 这些用例在一个**生产上已不存在**的方言上验证行为 —— 全绿也不能说明线上跑得通；
* SQLite 特有写法会被当成「契约」固化下来：实测 `test_api.py` 里
  `CREATE TABLE model_configs (id INTEGER PRIMARY KEY, …)`（SQLite 自增语法，
  PG 需 `SERIAL`/`IDENTITY`）、`create_engine("sqlite:///:memory:")`（PG 无此形态）；
* 反向也成立：PG 特有的 `ON CONFLICT` / `ILIKE` / `timestamptz` / 部分唯一索引
  在 SQLite 上要么报错、要么被静默降级 —— 那批用例永远测不到真正的 SQL。

⇒ **这是「测试全绿但线上崩」的直接通道**，优先级高于并发与耗时问题。

按 `docs/04` 的纪律，SQLite 退役后**测试必须也只跑 PG**。整改在 §3.0。


### 2.1 【严重】并发数与连接池没有对账 —— 全量必然打爆 PG

* `pytest.ini` 原为 `-n auto` ⇒ 本机 8 核 ⇒ **8 个 worker**
* `core/database.py` 池参数：`pool_size=10 + max_overflow=20` ⇒ **每 worker 最多 30 条**
* 8 × 30 = **240**，而本机 `max_connections = 100`
* 结果：连接耗尽 → 每个用例在 setup 阶段等连接（`pool_timeout`）→ **整体变慢**；
  再往后 `too many clients` 直接抛错 → worker 崩 → 汇总进程拿不到结果 → xml 不落盘

**这是「慢」与「跑不完」的同一个根因。**

### 2.2 【严重】xml 不落盘时，退出码会伪装成「测试失败」

`pytest-xdist` 的 `pytest_sessionfinish` 在 worker 已断开时抛 `OSError`，
退出码变成 **127**（`command not found` 的经典码），而 stdout 里只有一堆点与 `F`。
⇒ 人（和我）会先怀疑代码，实际一行代码都没错。

### 2.3 【中】判定链缺一环：没有「xml 是否是本次产物」的检查

我读旧 xml 得出「17 个失败」，白白查了两轮。
缺的是：**跑之前先删旧 xml，跑之后校验 mtime / 生成时间**。

### 2.4 【中】测试之间争用同一份 PG（没有隔离）

大量用例走 `db_factory` / `SessionLocal` 打真库，并行时互相锁表、
`UNIQUE constraint failed` / `重复键违反唯一约束 "users_pkey"` 反复出现。
这类失败**不是代码错**，是并发不隔离。

### 2.5 【中】长跑进程没有生命周期管理

我先后启动 3~4 个后台全量，被杀后 worker 仍占着连接（`pg_stat_activity` 里留残留）。
AGENTS.md 早有「长跑任务彼此不并发」的纪律，但**没有落成可执行判据**。

### 2.6 【轻】「测试范围」纪律执行不到位

铁律明写「默认只跑改动涉及的文件」，但本轮为了省事反复跑全量，
既慢又制造了上述所有问题。

### 2.7 【轻】半成品测试文件长期污染收集阶段

`test_resolve_business_provider.py` 停在半成品（docstring 未闭合、import 残缺），
以「collection error」形态存在很久，让「全量四数」里永远有 1 个 error。
（本轮已按用户口径彻底删除。）

## 3. 优化方案（按优先级，可分轮做）

### 3.0 P0 · 消灭测试里的 SQLite（最高优先级）

**目标：测试进程里 `sqlite` 出现次数 = 0**（守卫钉死）。

| 步 | 做法 |
|---|---|
| ① | 34 个文件里 41 处 `create_engine("sqlite:///…")` 全部改调 `conftest.make_engine()`（PG + 独享 schema） |
| ② | `Base.metadata.create_all` 掉的表由夹具统一建，用例只造自己需要的行 |
| ③ | SQLite 特有 SQL（`INTEGER PRIMARY KEY` 自增、`:memory:`、`IFNULL`、`group_concat`）逐条换成 PG 等价写法 |
| ④ | **加守卫** `test_no_sqlite_in_tests.py`：`grep -r "sqlite:///" tests/` 必须为空（白名单只留注释里说明历史的行，且逐条带理由） |

**为什么不能「先放着」**：`core/database.py` 已经非 PG 拒绝启动，测试却还在
验证一个不存在的运行环境 —— 全绿不等于线上可用。这类缺陷只在真机上才暴露，
正是本仓最贵的那一类（DEF-048 / DEF-067 同型：**看起来跑过了，其实没测到**）。

### 3.1 P0 · 并发数与连接池对账（已做一半）

* ✅ **已完成**：`pytest.ini` 的 `-n auto` 改 `-n 4`，注释写明算式与踩坑。
  同步改了 AGENTS.md 的命令与说明。
* ⬜ **待做**：在 `conftest.py` 加一条**启动期自检**——算
  `workers × (pool_size + max_overflow)`，若 > `max_connections × 0.7` 就
  `pytest.exit()` 并给出可用 `-n` 值。这样换机器/换池参数时**自动拦住**，
  不再靠人记。

### 3.2 P0 · 判定链补一环：xml 产物校验

* ⬜ 加 `pytest_sessionfinish` 钩子（或 wrapper 脚本）：
  1. 开跑前删旧 xml；
  2. 结束时断言 xml 存在且 `mtime >= 开始时间`；
  3. 不存在 ⇒ 打印「**本次未产出判据，不得据此判断失败**」并 exit 2
     （**不要**用 127 这种会被误读的码）。
* 目的：把「xml 缺失」与「测试失败」彻底区分开。

### 3.3 P1 · 测试分层：默认只跑该跑的

现状：`pytest tests/backend` 一把跑 529 条，其中大量是 contract / integration。
方案（与 AGENTS.md 三层循环对齐）：

| 层 | 命令 | 目标耗时 |
|---|---|---|
| 内循环 | `pytest <改动的测试文件> -n0 -x` | < 10s |
| 中循环 | `pytest <受影响文件集>` | < 60s |
| 外循环 | 全量（仅收尾/发版） | < 180s |

配套：
* ⬜ 给「需要真 PG」的用例统一打 `@pytest.mark.integration`，其余用替身；
* ⬜ 内循环默认 `-m "not integration and not slow"`，把 DB 争用移出快反馈回路。

### 3.4 P1 · 测试隔离：每个 worker 一个 schema（或一个库）

* ⬜ 现状：所有 worker 打同一个 PG 库 ⇒ 锁表 + 唯一键冲突。
* 方案：`pytest-xdist` 的 `worker_id` 拼进 schema 名
  （`test_w{worker_id}`），session 级建 / 拆。
* 收益：**消除一大类假失败**（本轮看到的 `UNIQUE constraint failed` 基本都是它）。
* 代价：首次跑要多建 schema（~1s/个），可接受。

### 3.5 P1 · 进程生命周期治理

* ⬜ 跑全量前自动检测「已有 pytest 在跑」并拒绝启动（或提示先结束）；
* ⬜ 异常退出时回收 worker 连接（`engine.dispose()` 放 `finally` / `atexit`）；
* ⬜ 把「并发跑测试」写成守卫：`conftest` 里起一个 `data/.pytest.lock`，
  第二个进程直接 `pytest.exit("已有回归在跑")`。

### 3.6 P2 · 慢用例清单治理

* 现状：`--durations=15` 有输出，但没人为最慢的用例做过归因。
* ⬜ 每轮收尾把 Top15 记下来，标「真慢（必须跑）」vs「白等（可优化）」；
  后者改 `waitFor(条件)` / 假时钟（AGENTS.md 已有此纪律，需落到清单）。

### 3.7 P2 · 收集阶段健康度守卫

* ⬜ 加一条守卫：`pytest --collect-only` 必须 0 error。半成品文件
  （docstring 未闭合、import 残缺）**当场红**，而不是以
  「collection error」长期挂在全量报告里。

## 4. 本轮的即时处置（已完成）

| 项 | 处置 | 状态 |
|---|---|---|
| `-n auto` → `-n 4` | `pytest.ini` + AGENTS.md 同步 | ✅ |
| **每条用例重建 63 张表**（8s/条） | 改为**每进程复用 schema**：首次建表，之后 `TRUNCATE` 清数据 | ✅ **8 分钟 → 1 分 20 秒** |
| **全局清数据钩子** | `pytest_runtest_setup` 拦所有用例（含走 `_override_database` 自己建 engine 的） | ✅ |
| **44 处自建 SQLite** | 批量改 `make_engine()`（PG）| ✅ |
| 半成品 `test_resolve_business_provider.py` | 按用户口径彻底删除 | ✅ |
| **全量回归唯一入口** | `.hermes/scripts/run_regression.py`：删旧产物 → 跑 → 校验新鲜度 → 读四数；缺产物 exit **2**（不是 127） | ✅ |
| 残留 pytest 抢占连接 | 入口脚本自动 `Stop-Process` 清理 | ✅ |

### 4.1 「每进程复用 schema」的踩坑记录（3 个，都会复发）

1. **`_CLEARED` 这类模块级「只清一次」标志** —— 原设计依赖「每条用例换新 schema」，
   schema 复用后它让清表只发生一次。`test_scheduled_jobs.py` 实测：3 条用例
   单跑绿、串行红。**判据**：任何 `global _XXX_FLAG` 的清数据逻辑，都是在
   假设「环境天然干净」，schema 复用后必须改成「每次用例都清」。
2. **`weakref.finalize(engine, drop_schema)`** —— `test_hot_topics.py` 用它按用例
   删 schema，与复用直接冲突（engine 一换 schema 就没了）。已移除，改用全局钩子。
3. **清数据时机** —— 必须「engine 建好之后、用例体之前」。放在 fixture setup
   阶段时 `_ENGINE` 还是 `None`，清了个寂寞（`test_scheduled_jobs` 的
   `_fresh_job_definitions` 就是这个 bug）。

### 4.2 仍然合理的 SQLite 引用（**不是**欠账，别误改）

| 位置 | 为什么合理 |
|---|---|
| `test_perms_core.py` 的 `is_sqlite("sqlite:///x.db")` | 测的是**方言判断函数本身** |
| `test_perms_core.py` 的「sqlite + 默认密钥必须拒绝启动」 | 必须用 sqlite URL 才测得到 |
| `test_scheduled_jobs.py` 的 `SQLAlchemyJobStore(url="sqlite:///…")` | APScheduler 的**内部持久化**，不是业务库 |
| `conftest.py` 的注释 | 只是历史说明 |

## 5. 一句话结论


> 本轮所有「测试失败」都是假警报，**真实问题是并发数、连接池、产物校验三者没有对账**。
> 先把 3.1 / 3.2 做掉（P0，约半小时），全量的「跑不完 / 假失败 / 慢」会一起消失；
> 3.4（worker 隔离）能再消掉一大类偶发冲突。
