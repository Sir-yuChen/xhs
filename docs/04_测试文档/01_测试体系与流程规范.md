## 2. 测试对象与范围

| 层 | 测什么 | 方式 |
|---|---|---|
| **后端 API** | 136 个端点的正常路径、鉴权、参数校验、错误码 | 自动化（pytest + TestClient） |
| **服务层** | 业务规则、状态流转、幂等 | 单元测试 |
| **适配层 / SDK** | 签名输出、header 契约、响应归一化 | 回归测试（离线构造，不打真实平台） |
| **数据层** | 表结构、唯一约束、迁移幂等 | 集成测试 |
| **前端** | 页面渲染、交互、错误反馈、接线正确性 | 手工 + 接线覆盖度静态核查 |
| **端到端** | 采集 → 入库 → 改写 → 发布 全链路 | 手工（需真实账号，**受限**） |
| **开关与配置** | UI 生效性、落库位置、运行时影响 | **静态核查 + 手工验证**（见 `06`） |
| **接线覆盖度** | 前端调用 ↔ 后端端点双向比对 | **静态核查**（见 `05`） |

### 2.1 测试的客观限制（必须承认）

| 限制 | 影响 | 应对 |
|---|---|---|
| 真实平台操作需真实账号 | 采集/发布类用例无法全自动 | 拆分：**离线可测的部分自动化**（签名、归一化、状态机）；需真实账号的列为手工用例并标注 |
| Cookie 有生命周期 | 依赖登录态的用例易失效 | 用例设计时避免依赖长期登录态 |
| 平台风控 | 高频测试可能触发风控 | **测试频率必须保守**，禁止对真实平台做压力测试 |
| 平台改版 | 签名类用例会周期失效 | 门禁用例关注「失败能被检出」而非「永远通过」 |

## 3. 测试流程

```
① 读设计文档
   └─ 提取每个功能点 → 写入 03_测试用例库.md

② 静态核查（不需运行）
   ├─ mock 标记排查        → 05
   ├─ 前后端接线覆盖度      → 05
   └─ 开关 UI 生效性与落库  → 06

③ 自动化测试
   └─ pytest tests/backend/

④ 手工用例执行
   └─ 结果回写 04_测试跟踪与缺陷标记.md

⑤ 业务链路验收（本项目第 6 项，2026-10-04 新增 · §14）
   └─ 从「本次改了什么入口」反查 → 更新 10（链路）与 09（功能点）
   └─ 一个前端按钮只是一步；要串成「入口链 → 末端业务结果」才算验完

⑥ 缺陷处理（关键）
   测出 bug → 打 [OPEN] 标记
   修复中   → 改 [FIXING]
   改完代码 → 改 [FIXED]（必须填修复位置）
   回归通过 → 改 [VERIFIED]（**此时才算关闭**）

⑦ 回流
   设计问题 → 回 docs/02_设计文档/
   实现问题 → 回代码 + 任务台账
   链路断点 → 记入 10 的「断链点」列 + 登记 DEF
```

## 5. 用例设计规范

### 5.1 用例结构（每条必须包含）

```markdown
#### TC-<模块>-<序号> · <用例标题>
- **功能点**：<对应需求编号 F1–F15 / R1–R5>
- **优先级**：P0（阻塞）/ P1（核心）/ P2（一般）
- **前置条件**：<数据、配置、账号状态>
- **步骤**：1) … 2) …
- **预期结果**：<可判定的结果>
- **可自动化**：是 / 否（否 → 说明依赖）
- **状态**：⬜ / ✅ / ❌
```

### 5.2 优先级定义

| 级别 | 含义 | 覆盖要求 |
|---|---|---|
| **P0** | 阻塞级：失败则系统不可用或产生不可逆后果 | **必须 100% 通过** |
| **P1** | 核心级：主流程功能 | 必须通过 |
| **P2** | 一般级：边缘功能、提示文案 | 可接受带缺陷上线 |

**P0 清单（不可妥协）**：

| # | 用例类型 | 理由 |
|---|---|---|
| 1 | 发布幂等（重复发布被拦截） | 发布不可逆 |
| 2 | 鉴权失败被拒（无令牌 / 过期 / 伪造） | 数据隔离 |
| 3 | 数据隔离（A 读不到 B 的数据） | 隐私 |
| 4 | 签名门禁（不合法签名必须显式失败，不得静默通过） | 防止带错签发请求 |
| 5 | 护栏拦截（违禁词样本全部拦截）— 二开 | 合规 |
| 6 | 能力未验证时禁止发布 — 二开 | 防止误发 |

## 6. bug 标记规范（审计要求）

> **要求原文：每次测试出 bug 和修改完 bug 以后，要从文档上打好标记，以便后续审计。**

| 标记 | 含义 | 必填字段 |
|---|---|---|
| `[OPEN]` | 已发现，未修复 | 发现时间、复现步骤、影响面 |
| `[FIXING]` | 修复中 | 负责人、预计修复里程碑 |
| `[FIXED]` | **代码已改，未回归** | **修复位置（文件:行）、改动说明** |
| `[VERIFIED]` | 回归通过，**可关闭** | 回归人、回归时间、回归用例编号 |
| `[WONTFIX]` | 确认不修 | **理由 + 决策人** |
| `[DUP]` | 与已有条目重复 | **指向主条目编号** |

### 6.1 两条铁律

1. **`[FIXED]` ≠ 关闭**。审计时只统计 `[VERIFIED]`。只标 `[FIXED]` 的条目按未关闭计入。
2. **标记必须就地更新，不能另起文档**。所有缺陷标记集中在 `04_测试跟踪与缺陷标记.md`。

## 7. 前后端接线覆盖度的判定标准

> 图片要求「前后端的接线覆盖度（100%）」。

| 方向 | 指标 | 当前值 | 目标 |
|---|---|---|---|
| 前端 → 后端 | **前端有效应答率**（前端调用的路径后端都存在） | **100%**（112/112） | 100% ✅ |
| 后端 → 前端 | **后端被接线率**（后端端点被前端调用） | **86.8%**（118/136） | 待定 |

### 7.1 为什么「后端被接线率」不必强求 100%

后端端点未接线有三类合法原因：

| 类型 | 例子 | 是否有问题 |
|---|---|---|
| **合理未接线** | `GET /api/health`（容器健康检查，不需要前端调） | ❌ 无问题 |
| **备用入口** | `xhs/creator/*` 6 个平台级接口（前端走 `/publish/*` 业务层） | ⚠️ 需标注用途 |
| **应当接线但没接** | `PATCH /xhs/monitoring/targets/{id}`（导致无法手动暂停监控）；`crawl/user-notes`（真实能力闲置） | ✅ **是问题** |

**因此判定标准是**：每个未接线端点必须**归类并说明原因**，不允许「不知道为什么不接」。

详见 `05_Mock清单与接线覆盖度.md` §3。

## 8. 开关生效性的判定方法

> 图片要求「管理端的开关在 UI 端的是否生效是否落库（a|数据库；b|git 库）」。

对每个开关，必须回答三个问题：

| # | 问题 | 判定方法 |
|---|---|---|
| 1 | **它存在哪里？** | 数据库 / git 配置文件 / 代码常量 / 请求参数 |
| 2 | **UI 上能不能改？** | 找页面与组件；找不到就是「无 UI 入口」 |
| 3 | **改了真的生效吗？** | **读代码找运行时读取点**——找到才算生效，只看到定义不算 |

**特别注意**：存在字段 ≠ 生效。例如 `monitoring_targets.crawl_interval_minutes` 字段存在，但定时刷新逻辑**从未读取它** → 死配置。

核查结果全部落 `06_系统开关与配置核查表.md`。

## 9. 回归测试要求

### 9.1 三层循环（**默认按这个来，不要一上来就跑全量**）

| 循环 | 什么时候跑 | 命令 | 实测耗时 |
|---|---|---|---|
| **① 内循环** | **每改一次代码就跑** | `pytest tests/backend/test_xxx.py -q -x --lf`（改哪个源文件就跑对应的那一个测试文件；`pytest.ini` 已固化 `-n auto`/`--junitxml`；`-x` 首个失败即停、`--lf` 优先跑上次失败的；慢用例多时加 `-m "not slow"`） | 秒级 ~ 1 分钟 |
| **② 中循环** | 一个功能点做完；或动了公共层（`models/`、`core/`、`lib/api.ts`、认证/中间件） | `pytest <受影响文件集> -q`（自动并行） | 1 ~ 3 分钟 |
| **③ 外循环** | **收尾**、或用户明确要求全量 | `pytest tests/ -q`（自动并行 + 自动写 `.hermes/reports/reg.xml`） | **150s**（原 499s） |

**「涉及哪些文件」用脚本选，不靠人脑反查**（P1-1，2026-09-25 新增，`AGENTS.md` §2 同文）：

```bash
python .hermes/scripts/pick_tests.py               # 按 git 未提交改动自动选测试文件
pytest $(python .hermes/scripts/pick_tests.py) -q  # 直接跑选出的文件集
```

原理：扫 `tests/backend/test_*.py` 的 import 建「源模块 → 测试文件」反向索引（缓存
`.hermes/tmp/test-dep-index.json`，按 tests/ mtime 失效），命中完整模块名 + 一级父包
（不再级联到 `backend.app` —— 那会把半个测试树算进来，过度跑比漏跑更贵：中循环从 2 分钟
变 5 分钟，人就开始不看结果）。公共层改动（`models/`、`core/database`、`lib/api.ts` 等）
会 WARN 并建议全量；无 git 的环境用 `--since-minutes N` 按 mtime 退路。

**判「涉及哪些文件」**：以 `pick_tests.py` 的输出为准（见上）；拿不准时先跑**直接相关的那一个文件**，红了再扩大范围。`--lf`/`--sw`（stepwise）用于修红灯场景：从失败处继续，不必整文件重跑。

> ⚠️ **全量不许当内循环用**。8 分钟一轮会让人下意识少跑验证，反而更容易带病交付 ——
> 这是本项目真实发生过的事（§12.1 有实测账）。

### 9.2 按改动类型的必跑项

| 触发 | 必须回归 |
|---|---|
| 修改 SDK / 签名 / HTTP 层 | 全部签名门禁用例 + 受影响链路的端到端用例 |
| 修改发布链路 | 发布幂等 + 状态机 + 素材上传 |
| 修改数据模型 / 迁移 | 迁移幂等（**库副本上 upgrade→downgrade→upgrade**）+ 唯一约束 + 关联查询 |
| 修改鉴权 / 安全 | 全部 P0 鉴权用例 |
| 修改 `frontend/src/**` | 对应 `.cjs` 行为脚本 + `tsc --noEmit`（**增量**：`tsconfig.json` 已开 `incremental`，二次 ~10s）；`vite build` **仅 8000 验证 / 发布前**跑，日常开发走 5173 热更新 |
| 改到 `backend/app/**` | 重启 8000 并复核 `/openapi.json` 里新字段真的在 |
| **修改配置加载** | 环境变量覆盖用例（因有已知缺陷，风险高） |
| 每次发布前 | P0 清单全量 |

### 9.3 判据（**只看 junit，不看退出码**）

```
pytest tests/ -q
```

`pytest.ini` 已把 `-n auto --junitxml=.hermes/reports/reg.xml --durations=15` 固化进
`addopts`：裸跑即并行、判据自动落盘（想串行调试用 `-n0` 覆盖）。
退出码会因沙箱清理系统 temp 而**假性变 1**（曾一次刷出 268 个假错误）。
判定一律读 xml 的 `tests / failures / errors / skipped` 四个数。

## 10. 测试环境要求

| 项 | 要求 |
|---|---|
| 数据库 | 独立测试库，**禁止连生产库** |
| 账号 | 使用专用测试账号，**不用真实运营账号做破坏性用例** |

## 12. 执行工作流与提速规范（2026-09-24 · v1.3 新增）

> **这一节是「以后写测试 / 跑回归的固定流程」**。前面 §1–§11 讲**测什么**，这一节讲**怎么跑才不浪费时间**。
> 所有结论都是本仓实测出来的，不是照搬通用经验。

### 12.1 先说清「慢」是怎么被量化出来的

用户反馈「开发与测试以及回归的工作方式非常慢」。实测（`--durations` + 逐个脚本单独计时）后，账是这样的：

| 项 | 实测值 | 说明 |
|---|---|---|
| 全量回归（优化前） | **499s** / 837 用例 | 串行、无 xdist |
| 最慢的 6 条用例 | 各 **~14.4s** | 全是 `test_login_state.py::TestFrontendBehaviourScripts` 的 node 子进程 |
| `add_account_modal.cjs` 单独跑 | **16.05s** | ← 元凶 |
| `qr_session_identity.cjs` 单独跑 | **8.80s** | ← 次凶 |
| 其余 8 个 `.cjs` | **0.72~0.92s** | 打的是纯逻辑 `lib/*.ts` |
| 那俩为什么慢 | **44 次固定 `await sleep()`** | `add_account_modal` 38 次/12.2s、`qr_session_identity` 6 次/6.35s |
| esbuild 打包占多少 | **0.7s**（产物 2.5MB） | 打包**不是**瓶颈，别去优化它 |
| `add_account_modal.cjs` 被 pytest 调几次 | **6 次**（1 基线 + 5 变异） | ⇒ 12.2s × 6 = **96s 纯浪费** |

**关键教训**：慢的**不是**后端测试、**不是** pytest、**不是**缺 conftest、**不是** esbuild。
是**两个前端脚本里的盲等被「变异测试」成倍放大**。盲等写的时候只跑一次不觉得贵，
一旦被 pytest 调 6 次就是 96 秒。

> 🔑 **可复用的诊断手法**：判「某条用例为什么慢」，**先量化单条** ——
> ① `node <脚本>` 单独计时 → ② `pytest <单条>` 计时 → ③ 两者差 30 倍以上，
> **问题就在脚本/被测代码里，不在 pytest**。别一上来查 conftest / 插件 / 子进程捕获
> （本次把这些全查了一遍，**全部被探针否定**，白花十几次工具调用）。

### 12.2 已落地的优化（三项）

| # | 措施 | 效果 | 涉及文件 |
|---|---|---|---|
| ① | **固定 sleep → `waitFor(条件, {timeout})`** | `add_account_modal` 16.05s → **3.5s**；`qr_session_identity` 8.80s → **5.4s** | `tests/frontend/add_account_modal.cjs`、`tests/frontend/qr_session_identity.cjs` |
| ② | **装 `pytest-xdist`，全量 `-n auto`** | 全量 499s → **150s**（3.3×） | 无代码改动，只加依赖 |
| ③ | **公共 conftest**（消灭 30 份重复样板） | 新测试少写 ~15 行/文件；且**修掉一个真 bug**（见下） | `tests/conftest.py`、`tests/backend/conftest.py` |

**③顺带修掉的真 bug**：`app.dependency_overrides` 是**模块级全局**，旧样板
`_override_database()` **只写不清** —— 覆盖会泄漏给同会话里后面的用例，让它们连到
一个已经关掉的 engine。表现是「莫名其妙连错库」，而且**不报错**。
新 conftest 的 `api_client` 用 `yield` + `finally` 保证退出时 `pop` 掉自己加的那一个。

### 12.3 三条硬规矩（**写测试时必须遵守**）

#### 规矩一：等异步一律 `waitFor(条件)`，不许固定 `sleep(N>=100)`

```js
// ❌ 慢且 flaky：盲等 500ms，被测慢一点就假红，快一点也白等
await sleep(500);
const modal = document.querySelector(".ant-modal");

// ✅ 一就绪就继续；超时即失败（失败信息比 sleep 清楚得多）
await waitFor(() => document.querySelector(".ant-modal"));
```

**超时给多少**：默认 500ms 够 React 首帧；等**轮询 tick**（真实 `setInterval`）才需要放大
（如二维码轮询 2000ms 一 tick，等 2 次给 6000ms）。
⚠️ 超时别一律给 3s —— 那些「本来就没有该元素」的路径会**白等满超时**（实测把脚本从 5s 拖到 9s）。

**判据要用「内容」而不是「元素在不在」**：`waitFor(modal)` 在 modal 外壳一出现就返回，
那时候里面的输入框/二维码还没渲染，断言照样假红。要等**你接下来要断言的那个东西**。

#### 规矩二：新测试文件必须用公共夹具，不许再抄 engine 三件套

```python
# ❌ 旧样板（29 个文件各抄一份，彼此只差数据库文件名）
engine = create_engine(f"sqlite:///{tmp_path / 'x.db'}", connect_args={"check_same_thread": False})
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base.metadata.create_all(bind=engine)
def override_get_db():
    db = SessionLocal()
    try: yield db
    finally: db.close()
app.dependency_overrides[get_db] = override_get_db

# ✅ 新写法：一个参数拿齐「已连到测试库的 client」+「可再查库的工厂」
def test_xxx(api_client, db_factory):
    api_client.post("/api/auth/register", json={...})
    db = db_factory()
    ...
```

可用夹具：`db_path` / `db_engine` / `db_factory` / `db_session` / `api_client` / `client` / `frontend_runner`。
**用法范例直接看 `tests/backend/test_conftest_fixtures.py`** —— 那个文件就是样板。

#### 规矩三：规范必须是**可执行**的，不能只是文档里的一句话

`tests/backend/test_testing_spec_guards.py` 把上面两条变成了**会红的守卫**：

| 守卫 | 防什么 |
|---|---|
| `test_no_blind_sleep_in_frontend_behaviour_scripts` | 有人把 `waitFor` 改回 `sleep(500)` |
| `test_jsdom_scripts_must_provide_waitfor` | jsdom 脚本被删掉 `waitFor`（用 `\b` 词边界，防子串误命中） |
| `test_new_test_files_must_not_duplicate_the_engine_boilerplate` | 新文件又抄 engine 三件套 |
| `test_legacy_allowlist_matches_reality` | 白名单悄悄过期（本次初版就同时错了 11 处） |
| `test_legacy_engine_allowlist_is_shrinking_not_growing` | 把新文件塞进白名单来绕过守卫 |
| `test_every_behaviour_script_is_wired_into_pytest` | `.cjs` 存在但没被 pytest 调用（DEF-063 同型） |

> ⚠️ 这三条变异（塞 sleep / 新文件抄样板 / 改名 waitFor）**都已实测能被抓住**。
> 守卫没做过变异验证 = 不知道它是不是摆设。

### 12.3b 前端行为脚本的「契约 / 变异」分批（2026-10-14）

**用户口径**：「拆」。

**实测耗时**（`add_account_modal.cjs`）：

| 模式 | 耗时 |
|---|---|
| 契约（`none`，53 条断言） | **11s**（冷缓存首跑 38s） |
| 每个变异 | **~11s** |
| **契约 + 全部变异（9 个 variant）** | **2 分 51 秒** |

而 pytest 是**模块级 fixture 串行**跑这两个脚本（`add_account_modal` + `login_state`），
xdist 的 6 个 worker 谁也帮不上忙 ⇒ **每轮全量回归固定多花 ~3 分钟**。
这是全量长期 10+ 分钟的主要来源之一（另一部分是 `-n` 偶发挂死，见 §12.7）。

**拆法**（两个脚本同形）：

```bash
node tests/frontend/add_account_modal.cjs --self-check          # 默认：只跑契约（11s）
node tests/frontend/add_account_modal.cjs --self-check --full   # 契约 + 全部变异（2m51s）
```

* **契约** = 日常判据：被测代码的可见行为对不对 —— **每轮回归都跑**。
* **变异** = 「守卫真的承重」的判据 —— **改本脚本 / 改对应被测代码时才跑**。

⚠️ **拆的是「跑哪些」，不是「判什么」**：两种模式下**契约都必须全 PASS**，
且 `--full` 下每个变异仍必须至少让一条断言变红。**判据一条不减。**

⚠️ **拆分最大的风险 = 变异被悄悄丢光**（`--full` 分支写错 / 清单被清空）：
那样「守卫承重」的证据链就断了，而**契约照样全绿** ⇒ 静默退化，没有任何红。
守卫 `test_frontend_scripts_expose_a_full_mutation_mode`（`test_testing_spec_guards.py`）
钉两件事：① 脚本真的实现了 `process.argv.includes("--full")`；
② **变异清单非空**。变异 **4/4 CAUGHT**（删 `--full` 判断 / 清空清单 × 两个脚本）。

> 🔑 可复用教训：**任何「为了让回归变快而把某类检查挪到开关后面」的改动，
> 都必须同时加一条守卫钉住「开关存在 + 被开关的内容非空」** ——
> 否则快是快了，丢的是检查本身，而且不报错。

### 12.6 ⚠️ 写文档的纪律：不许用 `cat >>` 追加

本次改这份文档时，用 `cat >> file <<'EOF'` 追加 §12，结果**把 §1–§5 整段冲掉、
编码也被打烂**（混合 CRLF/LF + GBK/UTF-8 字节），`verify_doc_counts.py` 直接崩在
`read_text` 上。这与本项目此前一次 `cat >>` 毁掉 `test_scheduled_jobs.py` 是**同一个坑**
（该文件末行是 CRLF，追加时负载错位插进了原文中间）。

### 12.7 ⚠️ `pytest -n` 会偶发「挂死」——收口用「按影响面选文件」

**2026-10-13 实测**：本机 `pytest tests/ -q -n 4` 两次跑到 **20+ 分钟不出结果**，
而 xdist worker 进程 **CPU 只累计 4~5 秒**（21 分钟挂 5 秒 CPU）—— 即 worker
**空转挂死**，不是慢。同批已知耗时是 **150~250 秒**。

**纪律（收口时按这个来，别硬等全量）**：

1. **优先按影响面选文件**：改到哪个模块，就跑**所有 import 它 / 被它 import 的测试文件**。
   判据用 `grep -rln "<改动的符号>" tests/`，一次性把它们一起跑（可小并行）。
   本次收口即用此口径：**642 passed / 0 failed** 覆盖了改动的全部调用方，比挂死的全量可信。
2. **看 CPU 判死活**：怀疑挂死时查 `Get-Process python | Select Id,CPU,StartTime` ——
   若 CPU 秒数长久不涨，就是挂死，**直接杀掉重跑**（换 `-n 0` 串行或换文件集），
   不要靠 `sleep` 反复探。
3. **别用「后台 + 长 sleep 探文件」的写法**：本次多个 watcher 因目标 xml 未产出而空转退出，
   白等好几轮。要么前台跑（它完成即返回），要么 `notify_on_complete=True`。
4. **判定只看 `--junitxml` 的四数**（tests/errors/failures/skipped），**不看退出码** ——
   `-n` 挂死时退出码无意义（本次一次 `exit=127`，其实根本没跑起来）。

## 13. 需求节奏规范：为什么「攒完所有需求再统一测」在本项目不成立（2026-10-02 · v1.4 新增）

> 用户 2026-10-02 提出备选方案：**「所有需求全部开发完，再统一测试、统一修 bug」**（下称**批处理模式**），
> 与当前的**逐需求闭环**（下称**增量模式**）比较。结论：**维持增量模式**，但吸收其中对的部分
> （见 §13.4「真机验收攒批」）。这一节把**判断依据落成可复核的账**，避免以后被重新讨论一轮。

### 13.1 用本项目自己的缺陷数据判（决定性证据）

对 `04_测试跟踪与缺陷标记.md` 现存 **84 条缺陷**的**发现场景**逐条归类：

| 发现场景 | 条数 |
|---|---|
| 用户真机实测报出 / 真机日志排查 | **24** |
| **做某个需求时顺带揪出**（「做 R13/R14 时」「修 DEF-077 时撞上」「跑全量回归揪出」） | **6** |
| 静态核查 / 隔离审计 | 1 |

⇒ **绝大多数缺陷不是在「统一测试阶段」挖出来的，而是在「做下一个需求、把链路真跑起来」时撞见的。**
「统一测试」这个阶段在本项目**并不产出主要缺陷**，把它当作主收口手段是错配。

再看根因分布：`静默` 一词在缺陷文档命中 **20 次**。最贵的几条全是同一类 —— **不报错、不崩溃、跨模块**：

| 缺陷 | 现象 | 特征 |
|---|---|---|
| DEF-067 | 调度线程死了，`running` 仍报 `True` ⇒ 所有定时任务无声停跑 | 静默 |
| DEF-069 | 批量同步 worker 无声死亡 ⇒「待同步 11」永不下降 | 静默 |
| DEF-044 | 千帆同步读了平台不返回的字段 ⇒ 第 1 页就把其余本地商品**全删**且标 `done` | 跨模块 + 静默 |
| DEF-048 | 安全网条件性短路 ⇒ 借到过期会话 | 跨模块 |

这类缺陷**只有在某条链路被端到端真跑通时才显形**。批处理模式等于把这 N 条链路**同时**点亮，
然后在 N² 种交互里反查是哪个需求干的。

**还有一条硬证据**：缺陷文档里出现 `首轮被误判`、`第二轮`、`重查`、`被真机推翻` 各一次。
**DEF-046**（创作者详情弹窗不展示正文）第一轮被判「非缺陷」并尝试归档，**第二轮被真机推翻重查**。
⇒ 连「这是不是缺陷」都需要真机反馈来定，**预测不可靠**。

### 13.2 四条项目硬约束把批处理的风险放大

不是通用经验，是本项目特有：

| # | 约束 | 批处理为什么会更贵 |
|---|---|---|
| ① | **文档先行**（`AGENTS.md` §3.1 硬约束） | 攒需求 ⇒ 文档 A 引用文档 B 里**尚未定稿**的字段名/判据 ⇒ 设计与设计打架，返工落在**文档层**（比改代码贵）；且 `verify_doc_stats` / `verify_doc_counts` 双脚本盯数字，漂移直接红 |
| ② | **迁移单条线性链**（现 head `f8a9b0c1d2e3`，59 条） | 一次上多条互相依赖的 DDL。已有两例实证：**DEF-077**（改名迁移与播种时序错开 ⇒ 任务双跑）、**DEF-082**（head 前移打掉夹具 ⇒ 四条 slow 用例长期红、报错还被 `CalledProcessError` 吞掉）。迁移必须一条条上、每条在库副本上三向实测 |
| ③ | **`pick_tests.py` 按改动反查** | 批量改动 ⇒ 依赖索引几乎全命中 ⇒ 每轮只能跑接近全量（**150s**）。**省下的小循环会以「大循环更频繁」的形式还回来**，而且还更晚 |
| ④ | **反馈距离** | 缺陷从 1 格变 N 格；而本项目缺陷恰是最难跨 N 格归因的类型（静默 / 跨模块 / 迁移时序） |

### 13.3 成本对照（攒 5 个需求、冒 8 个 bug）

| 环节 | 增量模式 | 批处理模式 |
|---|---|---|
| 定位 | 缺陷就在刚改的 1 个需求里，直接归因 | 要在 5 个需求的 diff 里二分：「是 R1？R2？还是 R2 改了 R1 依赖的字段？」 |
| 修复 | 修完当场回归，收敛一次 | 修 R1 的 bug 可能打掉 R3 的前提（实证：DEF-082）；**修一个→测一轮→再修一个，收敛过程被重复 N 次** |
| 返工 | 真机反馈到达时手上没别的活 | 真机验证是**最高产出手段**（24/84）但**串行**；批处理时用户反馈到达时你已在写 R6，得**放下手上的活回插** |

### 13.4 结论口径：只攒「需要人在场」的那一环

完整闭环（改 → 测 → 文档 → 记忆）里，**只有「真机验收」这一环值得攒批**，其余每一环都必须原地闭环。

| 环节 | 现行 | 规范（不变 + 新增） |
|---|---|---|
| 代码级测试（pytest / tsc / 变异） | 每需求当场跑 | **保持不变** —— 这是安全网，后置即失效 |
| 文档回写 + 双校验脚本 | 每需求当场跑 | **保持不变** —— 批量改数字必漏 |
| 迁移 | 每条单独上 + 库副本三向实测 | **保持不变** |
| **真机冒烟（需要用户在场）** | **每需求都打断用户一次** | **✅ 新增：攒批** —— 见下 |

**真机验收攒批的执行方式（本规范新增）**：

1. 每个需求收尾时，**只跑自动判据**：`pytest <pick_tests 选出的文件集> -q` +（动了 `backend/app/**` 时）重启 8000 并按 `/openapi.json` 复核 + 双文档校验脚本至 PASS。**不为了「请你肉眼看一下」而中断用户的节奏。**
2. 同时把「**只能靠肉眼/真机确认**」的事项**追加成一张清单**（`08_真机验收攒批清单.md`），逐条写清：**看什么页面 / 点什么按钮 / 期望看到什么**。
3. 清单攒 **2–3 个需求**（或用户主动说"给我看"）后，**一次性**交付给用户过一遍。用户批注 → 回写成 `TC`/`DEF` → 回到对应需求的闭环。
4. ⚠️ **攒批只限「真机冒烟」**。任何时刻只要自动判据红了、或发现的是**静默类**缺陷，**立即处理、不进清单排队** —— 静默缺陷在批处理下会互相污染（§13.1）。

> ⚠️ **这条口径的边界**：攒批**不是**「测试后置」的同义词。它省的是**用户被打断的次数**，
> 不是**反馈距离**。自动判据仍然每个需求当场跑完 —— 一旦把它也攒起来，就退化成 §13.3 的批处理模式了。

### 13.5 已有的外循环（澄清一个常见误解）

本项目**不是**「没有统一测试」，而是**小循环 + 大循环都有**（§9.1 三层循环）：

| 循环 | 作用 |
|---|---|
| ① 内循环（秒级~1min） | 每改一次代码 |
| ② 中循环（1~3min） | 一个功能点做完 / 动了公共层 |
| ③ **外循环（150s）** | **收尾跑全量 `pytest tests/ -q` + 双文档校验脚本** ← 这就是「统一测试」 |

批处理方案砍掉的正是那个**便宜且高效的小循环**（① ②），换来的是一个**更晚、更贵、归因更难**的大循环。

## 14. 业务链路验收规范（2026-10-04 · v1.5 新增）

> **用户口径**：「更新项目开发工作流，开发完毕后需生成对应验收文档，**业务角度以链路对功能点进行测试验收**」。
> 本节把这条口径落成**可执行的动作 + 能红的判据**，避免它只停在口号。

### 14.1 为什么必须按「链路」而不是「功能点」

功能点清单（`03_测试用例库.md` 的 `TC-*`、`09` 的 107 条）回答的是「**有没有这个功能**」。
但它**不回答跨页面的业务闭环** —— 而本项目最贵的缺陷**全是跨模块 + 静默类**：

| 缺陷 | 若只按功能点验，会漏掉什么 |
|---|---|
| DEF-044 | 同步读到平台不返回的字段 ⇒ 把其余本地商品**全删**且标 `done`。单看「同步商品」这个功能点是**通过**的 |
| DEF-067 | 调度线程死了但 `running` 仍报 `True`。单看「任务列表」是**通过**的 |
| DEF-069 | 批量同步 worker 无声死亡，页面「待同步 11」永不下降。单看「批量同步按钮」是**通过**的 |
| DEF-048 | 安全网条件性短路 ⇒ 借到过期会话。单看「借会话」单点也是**通过**的 |

⇒ **只有把链路端到端串起来走一遍，这类缺陷才显形**（判据与统计见 §13.1）。

### 14.2 一条合格链路的四要素（缺一不可）

| 要素 | 内容 | 反面（不合格） |
|---|---|---|
| ① **入口链** | 一串**前端入口按真实业务顺序**：哪个页面 → 点哪个按钮 → 填什么 | 只写后端契约 / 只写「调用 xxx 接口」 |
| ② **末端业务结果** | 走完链路后**业务上拿到了什么**（一篇可发布草稿 / 一条平台已发货订单 / 一份与筛选项一致的导出）| 写「返回 200」「无报错」 |
| ③ **通过判据** | 末端的**单一可判定事实**（数字对得上 / 平台侧可见 / 状态正确）| 「看起来正常」 |
| ④ **断链点** | 这条链上**最容易断的几步**，并**点名它防的是哪个 DEF** | 不写；或写「注意异常」 |

> **判据放末端**是刻意的：末端对 ⇒ 链上每一步都会顺；末端错 ⇒ 能一眼看出**断在第几步**，
> 而不是让用户从头逐个功能点试。

### 14.3 每次开发完毕的固定动作（**不许攒**）

> 与 §13.4「真机验收攒批」的区别：**链路文档的生成不许攒**（它是交付物），
> 攒的只是「请用户肉眼过目」这一环。

| # | 动作 | 判据 |
|---|---|---|
| 1 | 从**本次改动的入口**反查：动了哪些页面 / 按钮 / 弹窗 | 有清单（可 `git diff --stat` 出前端文件）|
| 2 | 对每个入口：**新开一条链路**，或**接入已有链路的步序表** | 每个入口都能在某条链路里被找到 |
| 3 | 更新 `09_第二阶段功能点全链路验收清单.md`：步序表 + 末端判据 + 断链点 | 四要素齐全 |
| 4 | 若本次修了 bug：把「这个缺陷会在哪一步显形」**写进对应链路的断链点** | 断链点点名了 DEF 编号 |
| 5 | 跑**链路自检**（见 §14.4） | 脚本 PASS |
| 6 | 同步 `09_第二阶段功能点全链路验收清单.md`（单点口径） | 条目数 = 勾选位数 |

### 14.4 链路自检（**可执行判据，不是口号**）

**`09` 的链路总览表**必须与正文**逐条吻合** —— 这是最容易漂移的地方（加了链路忘了改总览、
或总览写了正文没有）。自检脚本 `verify_acceptance_links.py` 检四件：

1. **条数**：`## 链 N · ` 的 N 连续且从 1 开始；总览表行数 == 正文链路数
2. **步数**：总览表声明的步数 == 该链路正文步序表的行数
3. **四要素**：每条链路都有「业务目标」「通过判据」「断链点」「🔲 链路验收」四块
4. **登记**：`docs/README.md` 与 `AGENTS.md` 都能检索到 `09_第二阶段功能点全链路验收清单.md`

> ⚠️ **与数字校验脚本的分工**：`verify_doc_counts.py` 管「文档 ↔ 代码实测」（端点/表/页面数）；
> 本节脚本管「验收文档 ↔ 它自己的正文」（结构自洽）。两者都不管内容质量。

### 14.5 与既有各环的关系（一张表看清）

| 环 | 产物 | 单元 | 什么时候 |
|---|---|---|---|
| 单元/集成测试 | `tests/**` | 代码行为 | 每需求当场（§9） |
| 用例库 | `03_测试用例库.md` `TC-*` | **功能点** | 需求设计时登记 |
| 测试跟踪 | `04_测试跟踪与缺陷标记.md` | **缺陷** | 测出/修完即打标 |
| **功能点全链路验收清单** | `09_…验收清单.md` | **12 条业务链路 × 串联步序**（每条下挂功能点明细） | 开发完（本项目第 6 项，**用户验收唯一入口**） |
| 真机攒批 | `08_真机验收攒批清单.md` | 需肉眼确认项 | 攒 2–3 需求一次性过（§13.4） |

⚠️ **`09` 与 `07` 是配套而非替代**：`09` 是**用户验收的唯一入口**（按链路走、按功能点核对），
`07` 是**验收标准与 DoD**（判「够不够格」）。两者都要维护，但**用户只走 `09`**。
