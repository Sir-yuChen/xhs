# 功能点测试规范（企业级方案 + 本项目管理）

> 2026-10-26 立。触发：用户口径「调研一个功能点企业级正常应如何测试，给出完整的测试脚本
> 开发流程，对后续开发测试脚本统一规范，避免大量测试脚本堆积、严重占用全量回归耗时」。
>
> 配套：`10_测试脚本生命周期规则.md`（脚本分级与清理）、`11_测试体系重构方案.md`（数据库隔离）。

## 一、业界方案比对（调研结论）

| 模型 | 来源 | 分层比例 | 适用 |
|---|---|---|---|
| **测试金字塔** | Mike Cohn《Succeeding with Agile》 | 单元 70% / 接口 20% / UI 10% | 逻辑密集、UI 稳定 |
| **测试钻石** | Martin Fowler 扩展 / Kent C. Dodds | 削减单元层，**以集成测试为主** | 业务系统、API 驱动 |
| **蛋筒冰淇淋（反模式）** | Alister Scott | UI 极多、单元极少、大量手工 | ❌ 本项目的**前身状态** |
| **5 层金字塔** | Android 官方 | 单元/组件/功能/应用/候选版本 | 客户端 |

三份独立来源的共同结论：

1. **「写测试。不多。主要集成。」** —— Kent C. Dodds
   「100% 覆盖率不是好事，会导致测试没有优先级且需大量维护。」
2. **接口层性价比最高** —— 「接口定义相对稳定，不像界面或底层代码经常变化，
   用例维护成本低」（阿里云实践）。
3. **越往上越慢越脆** —— 「层次越靠上，运行效率越低，失败信息越模糊，越难跟踪」（华为云）。

### 本项目应选：**测试钻石**

理由是实测数据：

* 本项目是 **API 驱动**的业务系统（FastAPI + React），业务规则几乎都在服务层；
* 前端是薄壳（大量页面是列表 + 弹窗），**UI 断言维护成本极高**
  （实测：`test_page_optimizations.py` 417 条源码断言，改一次布局红一片，已删）；
* 2026-10-26 盘查：3334 条里 **32% 是纯源码断言、真正走通链路的只有 12%**
  —— 典型的**蛋筒冰淇淋反模式**。

⇒ 目标比例（按**用例数**，不是代码行）：

| 层 | 占比 | 本项目对应 |
|---|---|---|
| **单元**（纯函数 / 规则引擎） | **20%** | `data_package_rules` 的算子、`sync_pacing`、`media_plan` |
| **接口/集成**（端点 → 服务 → 落库） | **70%** | 绝大多数 `test_*.py` |
| **端到端**（跨服务 / 真机 / 外部平台） | **10%** | `test_*_live.py`、真机冒烟攒批清单 |

⚠️ 与经典金字塔相反（经典是单元 70%）。本项目的"单元"其实是**业务规则引擎**，
数量本来就少；而端点契约是主要质量面。

## 二、一个功能点的标准测试结构

**每个功能点 = 一个文件 / 一个类，固定四段**（缺一段必须写理由）：

```
tests/backend/test_<功能点>.py
├── ① 鉴权与越权  （必有）
│     - 未登录 ⇒ 401
│     - 他人资源 ⇒ 404 / 403
│     - 跨租户读不到
├── ② 主链路成功  （必有）
│     - 入口 → 服务 → 落库 → 可观测结果（一条走完，不是分段）
│     - 包含至少一次「重复调用」验幂等（若该操作应幂等）
├── ③ 关键失败面  （必有，≤3 条）
│     - 只测「会导致数据损坏 / 静默错误」的失败，不测「参数格式错」
│     - 平台 5xx / 凭据失效 / 前置条件不满足
└── ④ 不变量      （按需）
      - 该功能特有的、静默且运行时炸的约束（如「超管唯一」「先平台后本地」）
```

### 数量预算（硬约束）

| 功能点复杂度 | 用例上限 | 说明 |
|---|---|---|
| 简单 CRUD | **6** | 鉴权 1 + 越权 1 + 成功 2 + 失败 1 + 不变量 1 |
| 普通业务链路 | **12** | 上面各段 ×2~3 |
| 复杂链路（发布 / 预检 / 同步） | **20** | 多形态 / 多源 |
| **超出上限** | — | **必须先合并或删除**，不许"再补几条" |

**判据**：一个功能点超过 20 条用例，**说明在测实现细节而不是测行为**。

## 三、测试脚本开发流程（六步，强制）

### 步骤 1 · 先定「验收判据」，再写测试

从需求文档抄一条可判定的判据，例如：

> 「商品发布成功后，平台侧 `goods-note/list` 按 `note_ids` 能查到 + `note_flag=goods_note`」

**写不出判据 = 不许写测试**（写了也是测实现）。

### 步骤 2 · 判定该功能点属于哪一层

| 层 | 判据 | 写在哪 |
|---|---|---|
| 单元 | 纯函数 / 无 IO | 直接 import 函数，无 DB 无端点 |
| 接口 | 有 HTTP 端点 | `client` + `db` 夹具 |
| 端到端 | 需要真机 / 真平台 | `_live.py`，**不进全量** |

### 步骤 3 · 按「四段结构」写，用参数化压条数

**逐分支拆开写是错误做法**（实测 `test_data_package_rules.py` 133 条全是
"取第 N 段 / 越界返回 None" 这类）。正确写法：

```python
@pytest.mark.parametrize("text,sep,idx,expected", [
    ("a;b;c", ";", 2, "c"),        # 取第 N 段
    ("a;b;c", ";", -1, "c"),       # 负索引
    ("a;b",   ";", 5,  None),      # 越界
    ("ab",    ";", 0,  None),      # 分隔符不存在
])
def test_segment_extraction(text, sep, idx, expected):
    assert extract_segment(text, sep, idx) == expected
```

**4 条变 1 条，覆盖率不变。**

### 步骤 4 · 用例必须能独立跑 & 可乱序

* 用 `db` 夹具（事务回滚隔离），**不依赖上一条用例的数据**；
* 不写 `global _CLEARED` 这类"只清一次"的标志（实测会"单跑绿、串行红"）；
* 不 `sleep`，用 `waitFor(条件)`。

### 步骤 5 · 收尾分级（需求收尾门禁）

```bash
python .hermes/scripts/grade_new_tests.py --changed --enforce
```

| 等级 | 判定 | 处置 |
|---|---|---|
| L1 全链路 | 有业务调用 / 业务 import | 保留（每功能点 1 个文件） |
| L2 架构不变量 | 架构层或 docstring 写明理由 | 保留 |
| L3 一次性 | 零业务调用 + 零业务 import | **验收后删** |
| L4 无保留价值 | 重复测点 / 断言恒真 | **立即删** |

### 步骤 6 · 记预算，超了必须删

在功能点文件顶部写：

```python
#: 用例预算：12（本文件当前 11 条）
```

新增用例前先看这个数字。**超预算必须删旧的或参数化合并，不许只加不减。**

## 四、全量回归耗时控制

### 三层循环（沿用，但重新定义触发）

| 循环 | 何时 | 命令 | 目标耗时 |
|---|---|---|---|
| ① 内循环 | 每次改代码 | `pytest <改动文件> -q -x --lf` | **< 10s** |
| ② 中循环 | 一个功能点做完 | `pytest $(pick_tests.py) -q -n 4` | **< 2min** |
| ③ 外循环 | 收尾 / 改公共层 | `run_regression.py -n 0` | **< 5min** |

### 硬红线

| 指标 | 红线 | 超了怎么办 |
|---|---|---|
| 全量用例数 | **≤ 800** | 按分级删 L3/L4、参数化合并 |
| 全量耗时 | **≤ 5 分钟**（单进程） | 先查慢文件 `--durations=20`，再分层（`@pytest.mark.integration` 不进内循环） |
| 单文件用例数 | **≤ 20** | 拆功能点，或参数化 |
| 单用例耗时 | **≤ 2s** | 网络 / 子进程 / 真迁移的标 `integration` |

### 分层标记（已落地）

```python
pytestmark = pytest.mark.integration   # 慢：真跑迁移 / 子进程 / >30s
pytestmark = pytest.mark.contract      # 中：端点契约
pytestmark = pytest.mark.redline       # 快：≤10s，内循环必跑
```

内循环 `pytest -m "not integration"`，外循环才全跑。

## 五、反面清单（这些做法已被实测证明会堆积）

| 做法 | 后果（实测） |
|---|---|
| 用源码字符串断言替代前端测试 | `test_page_optimizations.py` **417 条零业务调用**，改布局红一片，只能改字符串消红 ⇒ 只涨不降 |
| 逐分支拆成独立用例 | `test_data_package_rules.py` 133 条，参数化可压到 20 条以内 |
| 一个功能点多文件 | 权限 **18 个文件 127 条**、LLM **11 个文件 207 条** |
| 只加不减 | 三年从 400 条涨到 3334 条 |
| 一次性验证脚本 commit 进仓库 | `.hermes/scripts/` 里大量 `mutate_*.py` 早已过期 |
| 缓存"只清一次"的标志 | `global _CLEARED` 让清表只发生一次 ⇒ 单跑绿、串行红 |

## 六、一句话

**每个功能点一个文件、四段结构、20 条以内、参数化压条数、收尾必须分级删除。**
回归红线 **800 条 / 5 分钟**，超了先删再提速。
