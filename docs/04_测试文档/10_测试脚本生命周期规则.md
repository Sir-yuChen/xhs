# 测试脚本生命周期规则

> 2026-10-26 用户口径立规，**强制**。违反 = 返工。
>
> 用户原话：
> 「测试问题不应该有那么多，相当于项目开发到现在为止，测试脚本一直在堆积，可能很多无用的脚本，
> 早应该放弃移除，但是还保留并且一直堆积，一次性的脚本测试就应该使用完毕直接移除」
> 「后续的测试脚本开发禁止一直堆积，后续设计到相关功能点改动时，相关的测试脚本同步改动，
> 一次性的测试脚本使用验通过后后即可直接移除避免堆积无用脚本」

## 1. 三条硬规则

### 规则 1 · 只增不减 = 违规

**新增测试必须同时回答「删了什么」。** 一个需求落地时，若只新增测试文件/用例、
没有清理任何过期断言，要在提交说明里写明为什么不需要删。

判据：`git diff --stat` 里 `tests/` 只有 `+` 没有 `-` 时，必须解释。

### 规则 2 · 功能点改动 ⇒ 同步改测试

改一个功能点（改契约、改字段、改页面布局、删端点）时，
**必须在本轮同一批次内**改掉对应测试，不许留到下次「统一修测试」。
反例（本仓真实发生）：2026-10-25 权限改造删了 18 个权限码，
对应的按钮断言留了一个月才修，期间全量回归一直红着。

判据：`python .hermes/scripts/pick_tests.py` 选出的文件必须在本轮跑绿。

### 规则 3 · 一次性脚本用完即删

「验证某个东西 / 跑一次看结果 / 抓一次数据」的脚本
→ **验证通过后立刻 `rm`**，不提交、不留档。

以下**不**属于一次性脚本（应保留）：
* 常规回归入口（`run_regression.py`）
* 按改动选测试的辅助（`pick_tests.py`）
* 文档数字三校验（`verify_doc_stats.py` / `verify_doc_counts.py` / `verify_acceptance_links.py`）
* 长期守卫（变异脚本 `mutate_verify_*.py`，前提是它钉的是**永久不变量**）

判据：`.hermes/scripts/` 里任何脚本，**说不出它的常驻理由，就该删**。

## 2. 判据：什么测试该留、什么该删

### 2.0 【核心规则】每个功能点只保留**一个**全链路测试脚本

用户口径（2026-10-26）：

> 「每个功能点只保留一个全链路功能测试脚本」
> 「所有非功能点全链路测试的脚本，全部属于一次性测试脚本」

**落地判据**：

| 情形 | 处置 |
|---|---|
| 一个功能点有 **N 个**测试文件 | **合并成 1 个**全链路脚本（按业务链路串起来，不按技术分层切碎） |
| 某测试脚本**不覆盖任何功能点全链路** | 属于一次性脚本 ⇒ 验证通过后立即删 |
| 功能点需要多角度验证 | 放在**同一个文件里**（不同 `def test_`），不另开文件 |

**反面实例（本轮实测删除）**：`test_page_optimizations.py` 用 417 条源码字符串
断言「覆盖」了十几个页面功能，但**没有一条走通任何业务链路**（零 `client.get/post`、
零 `db.query`）。它不是一个功能点测试，是**十几条一次性验证清单堆在一个文件里**。

**什么叫全链路**：从入口（HTTP 请求 / UI 动作）→ 服务层 → 落库 → 可观测结果
（响应 / 列表 / 状态变更），一条测试走完。
只验其中一段（只验字段名、只验源码写法、只验常量值）**不是**全链路。

### 2.1 该删（无验证价值）

| 形态 | 例子 | 为什么删 |
|---|---|---|
| **纯源码字符串断言** | `assert "className=\"xxx\"" in read_text("a.tsx")` | 固定的是「代码怎么写」，不是「功能对不对」。改一次布局就红一片，红了只需改字符串 ⇒ 只涨不降 |
| **文档锚点断言** | `assert "某句文案" in doc` | 同上，且与功能无关 |
| **同一功能的逐字段拆分** | 一个发布请求拆成 11 条，每字段一条 | 一条测完整请求体更有效；拆碎后加字段就要加用例 |
| **被新代码取代的旧形态守卫** | `test_xxx_old_form_is_gone` | 该形态已不存在，断言恒真 ⇒ 零信息 |

### 2.2 该留（有真验证价值）

| 形态 | 判据 |
|---|---|
| **端点行为** | 有 `client.get/post/put/patch/delete` + 断言响应/状态码 |
| **数据库状态** | 有 `db.query` / `select` + 断言落库结果 |
| **权限边界** | 断言「无权限的人拿不到 / 有权限的人拿得到」 |
| **不变量守卫** | 钉的是**永久不变量**（如「超管唯一」「先平台后本地」），且**能过变异验证** |

### 2.3 源码字符串断言只在一种情况下允许

**唯一例外**：该断言是「**架构不变量**」，即它防的是**静默的、运行时会炸的**错误，
且无法用行为断言表达。例：
* 「页面不许出现 `Record<string, string>`」（TS 类型守卫，运行时测不到）
* 「不许 import 已退役模块」

写这类守卫必须在 docstring 里写明「为什么行为断言测不到它」。
**没有这句说明 = 该删。**

## 2.4 【2026-10-26 追加】源码断言 = 一次性脚本

用户口径：

> 「源码断言相关的测试是否有必要堆积，是否应作为一次性测试脚本，
> 只在验收通过后彻底移除」

**结论：没有必要堆积。默认一次性，验收通过后删。**

判据（可机械执行）：

* 文件内 `client.get/post/...` 与 `db.query/execute/add` 命中数 **= 0**；
* 且 `read_text(` / `code_only` / `_strip_comments` 命中数 **≥ 2**。

⇒ 纯源码断言文件 ⇒ 一次性脚本。

**唯一例外（必须满足全部三条）**：

1. 钉的是**架构不变量**（不是布局 / 文案 / 类名）；
2. 该错误**静默且运行时炸**，行为断言测不到；
3. docstring 写明「为什么行为断言测不到它」。

例：`assert "Record<string, string>" not in page`（TS 类型守卫，运行时测不到）。
反例：`assert "width: 200" in style`（布局）、`assert "请稍候" in text`（文案）—— 一律删。
