#### DEF-101 · 请求签名运行时**并发不安全** —— 共用固定临时文件 `.sign_input.json` ⇒ 两个下拉恒空

| 级别 | 🔴 **P0**（**功能整体不可用 + 影响面广**：签名临时文件名是**全局固定**的，`_signed_post` 的**所有**调用在并发时互相踩踏；用户看到的是「请求签名生成失败：…Node.js v22.23.2（这不是登录态问题）」这种**指向错方向**的报错，且商品发布第二步的「物流模板 / 运费模板」两个下拉**恒空**） | 状态 | **`[FIXED]`**（2026-10-09 用户实测报出 + 复现 + 修复 + 变异 CAUGHT） |
|---|---|---|---|

**现场（用户报，2026-10-09）**：

```
请求签名生成失败：    at node:internal/main/run_main_module:36:49
       /  / Node.js v22.23.2（这不是登录态问题）
```

用户在发布页看到：**运费模板下拉空 + 物流模板下拉空**（两个都是空）。

**根因**：`apis/xhs_qianfan_apis.py::_sign` 把签名入参写进**固定路径**
`_CORE_JS_DIR/.sign_input.json`，再 `subprocess.run(["node","sign.js","@.sign_input.json"], cwd=_CORE_JS_DIR)`，
跑完 `os.remove`。而前端 `product-publish-wizard.tsx` 进第二步时**并行**拉两个模板
（`fetchShippingTemplates` + `fetchLogisticsTemplates`，两个都是 `_signed_post`）：

```js
Promise.all-ish:  fetchShippingTemplates(...)  ← 签名请求 A
                  fetchLogisticsTemplates(...) ← 签名请求 B（同时）
```

⇒ 两个线程**同时**写/删同一个 `.sign_input.json`：A 写 → B 覆盖 → A 的 `node` 读到 B 的内容或半截
→ B `os.remove` 删掉 A 正在读的文件 ⇒ `sign.js` 第 68 行 `throw new Error('cookie required')`
（文件不存在/为空）或 `Unexpected end of JSON input`（半截 JSON）。错误尾巴被 `tail[-3:]` 截成
`Node.js v22.23.2` ⇒ 用户看到的报错把「文件竞态」误指成「签名运行时」。

**实测复现（2026-10-09，主账号 8）**：

```
16 个并发签名请求（8 线程，carriage / publish_render 交替）：失败 15
   FAIL: (False, '请求签名生成失败：    at node:internal/main/run_main_module:36:49 /  / Node.js v22.23.2…')
   FAIL: (False, '请求签名生成失败：} /  / Node.js v22.23.2…')   ← 读到半截 JSON 的 `}`
```

**修法**：临时文件名**每请求唯一** —— `tempfile.mkstemp(prefix=".sign_input_", suffix=".json", dir=_CORE_JS_DIR)`
（原子创建，名字带 pid + 随机后缀），`node sign.js @<basename>`。`finally` 仍 `os.remove` 清理
（文件含 Cookie，硬约束②不落盘）。

**修后实测**：

```
16 并发签名请求：失败 0（原 15）；无残留 .sign_input*
真机 8 并发打两个端点（shipping-templates ×4 + logistics-templates ×4）：全部 200
   [运费模板] 200 -> 3 项  default=6a32541ed066d700017c968f
   [物流模板] 200 -> [{'plan_id':'6a327c3bd0f2c70015312abe','name':'发货仓','logistics_mode':'内贸'}]
```

**守卫（新增文件 `tests/backend/test_sign_runtime_concurrency.py`，2 条）**：

* `test_sign_temp_file_is_isolated_across_concurrent_calls` —— 两线程并发调 `_sign`，
  用假 `subprocess.run`（`Barrier` 汇合后读 `@file`、按 `data.tag` 回签名）；
  每个调用必须拿回**自己 tag** 的签名 ⇒ 共用固定文件时交叉污染、必红。
* `test_sign_cleans_up_its_temp_file` —— 临时文件含 Cookie ⇒ 请求结束必须删掉 +
  不留旧名 `.sign_input.json`（硬约束②）。

**变异 1/1 CAUGHT**：把 `tempfile.mkstemp(...)` 换回固定 `.sign_input.json` ⇒ 并发用例**必红**
（实测 mutant exit 1 / baseline 0，还原后 marker 仍在）。

⚠️ **影响面**：`_sign` 是**唯一**签名实现（`_signed_post` / `_signed_get` 共用）⇒ 任何
**并发签名**场景都会踩（不止这两个端点）；商品发布的 `publish_item` 也在同一请求里连发多个签名请求。

#### DEF-093 · 商品列表「导出 CSV」**必然 422** —— 前端交的键名（`create_from`）不是导出模型认的（`create_time_from`）

| 级别 | 🔴 **P0**（**功能整体不可用**：链 2 的末端判据「CSV 行数 == 列表命中总数」走不到；用户看到的是「请求失败，请稍后重试」这种**没有指向的原因**） | 状态 | **`[VERIFIED]`**（2026-10-05 同轮修复 + 真机复核 + 变异 5/5 CAUGHT） |
|---|---|---|---|

**复现（100%）**：商品列表 → 选账号 → 点「导出 CSV」⇒ 页面 `请求失败，请稍后重试`；
Network：`POST /api/xhs/qianfan/items/export` → **422**，
响应原文 `{"type":"extra_forbidden","loc":["body","create_from"],"msg":"Extra inputs are not permitted"}`。

**根因**：导出端点用自己的入参模型 `ItemsExportRequest`（`extra="forbid"`），
字段名是 `create_time_from` / `create_time_to`；而前端 `exportCsv()` 发的是
`{...formValuesToDraft(form.getFieldsValue()), platform_account_id, group_id}` ——
`formValuesToDraft()` 交出来的是 **`create_from` / `create_to`**（这两个键名是给**本地筛选缓存**用的），
一到 `extra="forbid"` 的模型上直接 422。

**为什么列表没坏**：列表查询是 `load()` **单独拼** `create_time_from`（`page.tsx:914`），没走 draft ⇒
同一个 bug 只烧到导出。**两个键名体系各写各的，中间没有一条断言把它们绑在一起。**

**连带的第二个洞**：导出只补了 `platform_account_id` 与 `group_id`，
**`status`**（来自 draft，恰好同名）传得上，但**排序**与**日期**都丢了；更关键的是 ——
「导出集合 = 列表集合」这条**设计 20 §2.2 明文口径**目前**没有机械判据**在守
（`tests/backend/test_product_edit.py::TestExport` 是自己拼正确键名的后端直调）。

**修法（已实施，2026-10-05）**：**消除第二份实现**，不是给模型开个后门。

1. 新增 `frontend/src/lib/shop-items-query.ts::formValuesToQuery()` ——
   列表与导出**共用的唯一一处**查询构造（差别只有「带不带分页」）。
   `load()` 与 `exportCsv()` 都调它；导出不再从 `formValuesToDraft()`（本地缓存草稿）取字段。
   ⚠️ `formValuesToDraft()` 保留原职（只服务**本地筛选缓存**，键名故意与后端不同），
   函数 docstring 里写明「别再从这里取字段发出去」。
2. 导出还顺手补齐了两个静默丢失的维度：**排序**（`sort_field`/`order`）与**分组**（`group_id`）——
   改之前导出既不带排序也不带 `group_id`，与「导出集合 = 列表集合」不一致。
3. **契约守卫**（这才是根治）：`tests/backend/test_shop_items_query_contract.py` 从
   **后端 Pydantic 模型**取字段表，交给行为脚本 `tests/frontend/shop_items_query.cjs`
   （esbuild 打包**真实** `shop-items-query.ts`）断言：
   「导出键 ⊆ `ItemsExportRequest` 字段」「列表键 ⊆ `ShopItemsRequest` 字段」
   「导出与列表除分页外逐字段相同」+ 导出键清单冻结（16 个）。
   变异 **5/5 CAUGHT**（`draftkeys` / `exportpaged` / `noteop` / `sortdefault` / `groupsentinel`）。
4. 真机复核（2026-10-05，观隅好物账号 1980 件、筛选后命中 3 件）：
   `POST /items/export` **200**，页面提示「已导出 3 行」，
   payload = `{"platform_account_id":8,"status":"on_shelf","price_from":10,"stock_from":5,"sales_from":1}`，
   **CSV 数据行 3 == 列表命中 3**、BOM 在、16 列、单元格无多余引号。

#### DEF-098 · 自动化工作流的**调度永不装配**（`workflow.<id>` 查不到 JobSpec）⇒ 到点不跑、手动触发也不执行

| 级别 | 🔴 **P0**（方向 5「工作流编排」在调度维度**完全不工作**） | 状态 | **`[VERIFIED]`**（2026-10-07 实测定位 + 修复 + 变异 CAUGHT）⇒ **同日随特性退场，载体已不存在** |
|---|---|---|---|

**现场（真机，2026-10-07 建「每日 · 未发笔记商品生成并发布」时暴露）**：

按设计 19 建一个 `trigger_type=cron` 的工作流，`scheduled_jobs` 行**正常建出**：

```
id=302  job_key='workflow.1'  trigger_type=cron  cron='0 0 9 * * *'  params={"workflow_id": 1}  status=active
```

界面「定时任务」看得到、`workflows.next_run_at` 字段也在 —— 但实测三个面全不对：

| 判据 | 实测结果 |
|---|---|
| `apscheduler_jobs` 里 `job_302.next_run_time` | **NULL**（对照：库里其余 **247** 个 active cron 作业全部有值） |
| 点「执行一次」 | 日志建行后**永久停在 `running`**，`workflow_runs` **一行没建**、`workflow_run_logs` 空 |
| 重启服务 | **不自愈**（store 行已在 ⇒ `_stored_job_exists` 让它继续跳过重注册） |

**根因（已定位）**：**注册表里只有前缀键，查的却是带后缀的真实 job_key。**

`job_registry` 里工作流的声明写的是 `key = WORKFLOW_JOB_KEY_PREFIX`（字面量 `"workflow."`），
而 `scheduler_service._register_job_in_scheduler()` 每一步都拿**行上的真实 `job.job_key`**
（= `workflow.1`）去 `get_job_spec(job.job_key)` ⇒ **`KeyError`** ⇒ 走「unknown job_key」分支
`logger.warning(...); return False`（不注册、不报错、不留任何用户可见痕迹）。

设计 19 §7.1 的注释**预言了这个坑**（「⚠️ 注册表按**精确 key** 查（`get_job_spec`），
前缀本身不是一个可调度任务；工作流在 `workflow_service._sync_scheduler` 建出的行才携带真实 id 后缀」）
—— 但**只写进注释、没落成实现**，也没有守卫钉住「`workflow.1` 必须查得到 JobSpec」。
⇒ 典型「文档说了 / 代码没做 / 测试没盖」。

**为什么测试没抓住**：`test_workflows.py::test_tc_wf_001` 只断言「`scheduled_jobs` 出现了
`workflow.<id>` 行、user_id / params 正确」——**行建出来就算过**，从不验证
「**这个 job 有没有真的被调度器注册**」。注册失败是**静默 warning**，与成功在 DB 里长得一模一样。

**修法（已实施）**：`job_registry.get_job_spec()` 增加**前缀族兜底** —— 精确命中优先，
未命中且以 `WORKFLOW_JOB_KEY_PREFIX` 开头则返回前缀声明；其余未知键**仍抛 `KeyError`**
（兜底不能写成「什么都放行」）。删掉陈旧的空 `apscheduler_jobs` 行后重启即自愈。

`reason` = **本次失败原因**（首条失败笔记的平台原文，`_first_failure_reason()`）；

⚠️ **存量行不回填**：历史行 `reason` 里那句就是当时的文案，回填等于把「历史失败原因」
整列改写成另一件事（用户对比昨天今天的记录会发现同一次操作说法变了）。

**判据**：`test_log_reason_is_empty_when_nothing_failed`（无失败 ⇒ `reason` 为空）、

`test_cleanup_log_reason_is_the_failure_not_the_coverage_note`（端点契约）、
页面守卫 `test_cleanup_log_failure_reason_column_never_shows_the_coverage_note`（前端半边）。

### 2.4 P2 中优先级缺陷

#### DEF-100 · 发布链路 `shippingTemplateId` **恒空** —— 从**不返回该字段**的 `publish_render` 去取运费模板

| 级别 | 🟡 **P2**（**功能静默失效**：发布商品时用户选的「运费模板」不生效，平台回退到店铺默认模板 —— 不报错、不提示，商品照样发布成功，只有订单运费不对时才发现） | 状态 | **`[FIXED]`**（2026-10-09 定位 + 修复 + 变异 CAUGHT 2/2） |
|---|---|---|---|

**背景**：发布体有**两个店级字段**，各有来源（2026-10-09 裸接口实测，主账号 8）：

| 发布体字段 | 正确数据源 | 取值路径 |
|---|---|---|
| `logisticsPlanId`（物流方案 / 发货仓） | 空白 `publish_render({publishType:1,sourceType:1})` | `data.fulfillmentInfo.logisticsPlanList[0].planId` |
| `shippingTemplateId`（运费模板） | `getSellerCarriageTemplate` | `data.fulfillmentInfo.shippingTemplateList[]` / `.defaultShippingTemplate` |

**缺陷**：`shop_item_publish.parse_fulfillment_info(precheck_payload)` **只收一个回执**，
且从它里面同时取这两个值 —— 但**空白 `publish_render` 的 `fulfillmentInfo` 只有
`logisticsPlanList` / `logisticsPlanStatus`**（实测 `keys: ['logisticsPlanList','logisticsPlanStatus']`），
**既无 `shippingTemplateList` 也无 `defaultShippingTemplate`** ⇒ `templates` 恒空、
`shipping_template_id` 恒空串 ⇒ `build_item_body` 因 `if shipping_template_id:` 为假
**整个键不写进发布体** ⇒ 平台用默认运费模板。

**实测复现（2026-10-09）**：

```
parse(publish_render + carriage): {"logistics_plan_id":"6a327c3bd0f2c70015312abe",
                                   "shipping_template_id":"6a32541ed066d700017c968f"}  ← 修后
parse(publish_render only)       : {"logistics_plan_id":"6a327c3bd0f2c70015312abe",
                                   "shipping_template_id":""}                          ← 旧实现，缺陷
```

**为什么长期没被发现**：`shipping-template` 相关的既有守卫全部**只查列表接口**
（`/product/shipping-templates` 的数据路径），**没有一条**验证「发布体里 `shippingTemplateId`
真的被填成了 carriage 的值」—— 发布链路的 `build_item_body` 只在有值时写键，
空值静默省略，与「用户没选」在请求体里长得一模一样。

**修法**：`parse_fulfillment_info(precheck_payload, carriage_payload=None)` 增加第二来源 ——
物流方案仍来自 `precheck_payload`，运费模板**优先**取 `carriage_payload`（回退到
`precheck_payload` 的 `shippingTemplateList`，兼容编辑读回 `publishType:2` 形态）；
`shop_item_publish_service.publish_item` 在取空白 `publish_render` 后**补调一次**
`get_seller_carriage_template()` 并传入。

**守卫（`tests/backend/test_item_publish.py` +3）**：

* `test_parse_fulfillment_info_needs_carriage_source` —— 只喂 blank ⇒ 运费模板**必须为空**
  （钉死「publish_render 不返回它」这个事实）；喂 carriage ⇒ 取到。
* `test_parse_fulfillment_info_accepts_edit_readback_template` —— 编辑读回形态不传 carriage 也认。
* `test_publish_item_fills_shipping_template_from_carriage` —— 端到端：发布请求体
  `itemData[0].shippingTemplateId == "st-carriage"` + `logisticsPlanId == "lp-blank"`。

**变异 2/2 CAUGHT**（`.hermes/scripts/mutate_verify_item_publish_fulfillment.py`）：
① `parse_fulfillment_info` 丢掉 carriage 来源；② `publish_item` 不调 `get_seller_carriage_template`
—— 两个都在**生产代码**上变异，守卫分别变红。

⚠️ `_FakeApi.publish_render` 夹具**同步修正**：原夹具在 `publishType:1` 就返回带
`shippingTemplateList` 的骨架，**正是「夹具带了真实响应没有的字段」**（mutation-verified-guards
shape 11）⇒ 它掩盖了本缺陷。现按真机形状：`publishType:2` 才给骨架、`publishType:1` 只给
`logisticsPlanList`；运费模板单列一个 `get_seller_carriage_template` 假方法。

「运费模板」下拉显示 **`系统默认-非偏远地区包邮模版`** ⇒ **两个下拉确实显示不同数据**，
与两个端点返回一致。

#### DEF-097 · 平台风控时**无账号级短路** ⇒「清理全部」朝一个已被风控告警的账号连打 20 次权限校验

| 级别 | 🟡 **P2**（**无产出 + 加重风控**：功能本身没崩，但平台的账号级拒绝被当成「单篇失败」逐篇重试 —— 剩余每一次都注定同样失败，纯粹是把一个刚被判定有风险的账号再打 19 次） | 状态 | **`[VERIFIED]`**（2026-10-06 同轮修复 + 用例钉住） |
|---|---|---|---|

**根因**：`_cleanup_with_task` 的循环对**每一篇**一视同仁 ——
`validate_delete_permission` 失败就 `failed += 1; continue`。但失败有两类：

* **单篇级**（这一篇的问题：已被删、无权限、参数不合法）⇒ 继续跑下一篇**是对的**；
* **账号级**（风控 / 凭据 / 未登录）⇒ 换一篇也一样失败，继续跑没有产出。

代码此前**不区分**这两类，于是 `code=906 账号存在风险，请重新登录` 被当成单篇失败。

**修法**：`ACCOUNT_LEVEL_FAILURE_MARKERS` + `_looks_like_account_level_failure()`，
命中即 `aborted=True`、`abort_reason=平台原文`，剩余笔记**一次请求都不发**，
并落 `no_traffic_cleanup_items` 的 `result="not_attempted"`（如实说明「没轮到」，
不是「失败」—— 用户看到「未执行」才知道该重试，看到「失败」才知道该查原因）。

**为什么判据用平台原话而不是错误码**：创作者平台这批接口的错误码**没有一个**
被本仓文档化过（千帆那套 `is_credential_error` 是另一条链路的判据，不通用），
而平台原话是**实测拿到**的。认不出时**照旧逐篇继续** —— 误判中止比多打几次请求糟
（「有一篇坏了就整批不跑」）。

**判据**：`test_account_level_failure_aborts_the_batch_and_never_calls_the_rest`
（**数调用次数** —— 只看 `failed` 分不出「短路」与「逐篇都失败」）+

#### DEF-092 · 进度泵用例把**采样周期**设得比**被观测窗口**还长 ⇒ 高负载下跳过中间值（假红）

| 级别 | 🟡 **P2**（测试缺陷，非产品缺陷：**用例自己 flaky**，全量并发跑时偶发红，会浪费排查时间） | 状态 | **`[VERIFIED]`**（2026-10-04 修复 + 隔离 3 次 / 并行 3 次全绿） |
|---|---|---|---|

`test_account_card_sync_job_log.py::test_progress_pump_writes_while_running_and_never_overwrites_terminal`
把 `_ProgressPump` 的**泵间隔**设为 `0.05s`，却用「建库 → 查询 → 关库」的循环去**采样**它。

高负载（全量 `-n auto`，1828 条同时跑）下**一次采样耗时 > 100ms** ⇒ 整段跳过 40 直接看到 80：

```
AssertionError: 运行期间应写入中间进度（泵在写 running 行），实得 [0, 80]
assert 40 in [0, 80]
```

**关键**：这是**测试的采样问题，不是产品的问题** —— 泵确实写了 40，只是**测试没来得及看**。
隔离跑（`-n0`）恒绿，全量跑偶红，正是这类时序假设的典型特征。

**修法**（采样周期必须显著短于被观测窗口）：
- 泵间隔 `0.05s → 0.5s`（让「中间值窗口」10 倍于采样开销）
- 采样 `sleep 0.02 → 0.05`，截止 `5s → 10s`
- 就地写明「为什么是 0.5s」，防止后人「优化」回去

**为什么定 P2 而不是不算缺陷**：它会**间歇性打断全量回归**，且现象（`实得 [0, 80]`）指向产品代码 ⇒
新人会去查泵的实现，方向错。测试自身的 flaky 也要登记，否则同一个坑会被重踩
（本项目已有同类先例：`test_product_note_publish.py` 的负载相关 flaky）。
