### 2.2 P0 高危缺陷
#### DEF-085 · SQLite 写锁竞争导致**静默丢数据**（台账不落行 / 快照采集失败）
| 级别 | 🔴 **P0**（**静默数据丢失 + 无任何用户可见信号**：台账是「唯一用量真相源」，用量看板 / 预警全依赖它；快照同理 —— 失败时**一行不落**，而任务还报「执行成功」） | 状态 | **`[FIXED]`**（同轮修完，2026-10-03 ~ 10-04） |

**两处同型缺陷，根因相同（SQLite 写锁竞争 + 安全网静默吞异常）**：

- **① 台账不落行**（2026-10-03 实测）：`POST /api/ai/generate-note` 返回 200、draft 真实产出，
  但 `llm_gateway_usage_logs` **一条不落**。逐层证伪定位到
  `OperationalError: database is locked` —— `api/ai.py::_recorded_text_task`
  **`flush()` 拿到写锁后跑几十秒的 LLM 调用**，期间记账（另开连接的 INSERT）必然撞锁超时，
  再被 `except Exception: return False` **静默吞掉**。
  ⇒ 修：`flush()` → **`commit()`** 再跑 action（锁只持有毫秒级），`_recorded_text_task` /
  `_recorded_image_task` 两处同类一起修。
- **② 采集在并发下失败**（2026-10-04 实测，自动执行时抓到）：**唯一有数据的 user 2**
  采集 `status=failed`（`database is locked`），其余 16 个用户 `collected: 0`（没数据）
  反而「成功」—— ⚠️ **数据越多越容易失败**，是最坏的失效方向。
  根因：**逐行 `execute()`** 让 3623 条 INSERT 持锁约 6 秒，而定时任务**每用户一个 job**
  ⇒ 17 个任务同一分钟并发（实测 `00:05:00~00:05:06` 交错）必然互撞。
  ⇒ 修：批量写（200 行/批）+ 共用撞锁重试 + 用尽映射 **503**（不是 500）。

**共用实现**：新增 `services/sqlite_retry.py`（`retry_on_lock` / `is_lock_error` /
`LockRetryExhausted`）—— 三处同型链路**单一判据**，不各写一份（DEF-044）。

**验证**：`test_sqlite_retry.py` **15 条** + `test_shop_metrics.py` **18 条** +
台账侧 **6 条**；**变异 9/9 CAUGHT**（`noretry` / `lockall` / `retryonce` /
`noreturnfalse` / `noexponential` / `swallow` / `batch1` / `price_from_string` / …）；
端到端：修前单请求「200 但 0 行」、5 路并发 3/5 且 2 个 500 ⇒ 修后**5/5 成功 + 3623 行落库**。

⚠️ **同类第三处（未修，已知边界）**：`api/ai.py` 另三处 `flush()` 在 action **之后**
（写 draft / asset），持锁毫秒级，不影响记账 —— 刻意不改（避免扩大改动面）。

#### DEF-086 · 测试**静默写生产库**（`db_session` 夹具不打桩服务层 Session）

| 级别 | 🔴 **P0**（**污染真实数据 + 用例假绿**：测试通过不代表被测代码对，只代表它读到了生产库里恰好存在的行） | 状态 | **`[FIXED]`**（同轮修完，2026-10-04） |
|---|---|---|---|

**现象（实测）**：`tests/backend/test_workflows.py` 跑一轮后，真实库
`data/spider_xhs.db` 多出 **4 条 `workflows` + 22 条 `workflow_runs` + 12 条 `workflow_nodes`**
（名称 `t` / `t2`…`t6` / `x`，全为 `user_id=1`，时间戳 02:55–03:47）。

**根因（结构性的，不是「某个用例忘了申请夹具」）**：
只有 `api_client` 夹具会调 `patch_service_sessions()`，**`db_session` 不会** ——
于是「用 `db_session` + 直接调自开 Session 的服务函数」（如
`workflow_service.run_workflow_job`）这类用例**必然**连生产库。
项目此前已两次同类（conftest docstring 记载 2026-09-27 两次、2026-10-02
`material_scan_service` 一次），都只修了当场那一处，**没有堵住这一类**。

**修法（修类，不修点）**：
1. `db_session` 夹具**无条件**调 `patch_service_sessions()` ——
   隔离成为**夹具的属性**，不再是「用例记得申请哪个夹具」的约定；
2. `db_engine` 夹具播种外键基线行（`users` id=1 / `platform_accounts` id=10）——
   隔离修好后，一批此前**靠读生产库才通过**的用例立刻暴露依赖
   （实测 16 条 `FOREIGN KEY constraint failed`）。这不是放宽，是补上「夹具库必须自洽」；
3. 造数助手自己保证外键父行存在（`_make_notes` / `_seed_folder` 各自 upsert 所属 user）。

⚠️ **`_seed_baseline_rows` 必须先 `flush()` 父行再插子行**：同一 commit 里
SQLAlchemy 不保证按声明顺序发语句，实测 `platform_accounts.user_id -> users.id`
会撞外键 ⇒ **全部用例 setup 失败**。

**验证**：新增 `tests/backend/test_prod_db_isolation.py` **6 条**
（3 条源码级 + 3 条**行为级**：调服务后真实库行数不变 —— 唯一不可伪造的判据）；
`test_workflows.py` 21 条全绿（原 2 红：1 条隔离缺陷 + 1 条夹具缺 `platform_accounts` 行）；
修后真实库 `workflow_runs` 恒为 0（清理污染行 + 三次重跑复核）。

⚠️ **污染行已清理**（备份 `data/spider_xhs.db.bak-*-pre-wfclean`）：
清理前 `workflows 4 / workflow_runs 22 / workflow_nodes 12`，清理后全 0；
业务数据未误伤（`notes` 3623 / `shop_products` 1983 / `platform_accounts` 5 / `users` 17 均不变）。

### 2.3 P1 高优先级缺陷
#### DEF-087 · 整批清理在 FK=ON 后失败（删父行早于子行）

| 级别 | 🟠 **P1**（**真机链路失败**：整批清理是「队列记录清理」定时任务与手动清理的共用路径，不是测试专用代码） | 状态 | **`[FIXED]`**（同轮修完，2026-10-04） |
|---|---|---|---|

`tasks.parent_task_id` 是**自引用外键**。全局 `PRAGMA foreign_keys=ON` 后，
`note_queue_service.clean_records()` 的整批清理撞 `FOREIGN KEY constraint failed` ——
代码写的是「先删子再删父」，但 **SQLAlchemy 的 unit of work 不保证按调用顺序发语句**，
实测先发父行 DELETE。修法：删完子行 `db.flush()` 再删父行。
隔离复现：`delete(child)×2; delete(batch); commit()` ❌ ／ 中间加 `flush()` ✅。

### 2.4 P2 中优先级缺陷

#### DEF-089 · `list_orders` 分页参数**只收窄 `LIMIT`**、返回体回显**原始入参** ⇒ 分页器总页数算错

| 级别 | 🟡 **P2**（**用户可见但不错数据**：页面显示「每页 100000 条」而实际只拿到 100 条，用户按显示值算出的总页数是错的、翻页会跳空） | 状态 | **`[FIXED]`**（2026-10-04 同轮修复） |
|---|---|---|---|

原实现：`"page_size": page_size`（回显入参）而 `limit(max(min(page_size, 100), 1))`（实际用收窄值）。
修法：**先归一参数再回显** —— `page = max(int(page or 1), 1)`、
`page_size = max(min(int(page_size or 20), 100), 1)`，返回值就是实际采用值。
守卫：`test_page_size_bounds_are_enforced`；变异 `rawpagesize` **CAUGHT**。

#### DEF-090 · CSV 导出**双重转义**（`_csv_cell` 自己加引号 + `csv.writer` 再加一层）⇒ Excel 打开多出可见引号

| 级别 | 🟡 **P2**（**导出文件不可直接使用**：值以 `"""带,逗号"""""` 形态出现，Excel 里显示带引号的脏数据；用户拿去对账时列值全错） | 状态 | **`[FIXED]`**（2026-10-04 同轮修复） |
|---|---|---|---|

`_csv_cell` 手写了「含 `,` / `"` / 换行就加双引号并翻倍内部引号」的逻辑，
而 `csv.writer` **已经按 RFC 4180 做同一件事** ⇒ 两层叠加。
修法：`_csv_cell` **只做公式注入防护**（前导 `=`/`+`/`@`/`-` 加英文单引号前缀），

守卫：`test_csv_quotes_values_containing_delimiters`（判据是**解析回来逐字相等**，
不是断言原始串里的引号形态 —— 后者会把「双重转义」这种 bug 断言成正确）；
