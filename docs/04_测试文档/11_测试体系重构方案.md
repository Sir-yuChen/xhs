# 测试体系重构方案（企业级方案比对 + 落地）

> 2026-10-26 立。触发：用户口径「测试跑了一下午还没结果，测试体系混乱无章，
> 调研企业级成熟方案分析比对，重构当前项目的测试体系」。

## 1. 现状诊断（数字实测）

| 指标 | 值 | 问题 |
|---|---|---|
| 测试文件 | 158 个 | 一个功能点 8–18 个文件（权限 18 / LLM 11 / 登录 10） |
| 用例 | 2796 条 | 纯行为验证仅约 12% |
| **各文件自建库逻辑** | **36 个文件** | **同一件事 36 份实现**，各改各的 |
| 全量耗时 | 20–30 分钟（且经常跑挂） | 大量时间花在重复建表 / 连接重连 |
| 全量结果可靠性 | 低 | `connection failed`、`EMAIL_TAKEN`、`字段不存在` 全是假失败 |

**核心病灶不是「测试多」，是「36 份各自实现的测试基建」。** 实测后果：

* 有 14 个文件清数据、22 个不清 ⇒ 「单跑绿、串行红」；
* 只有 1 个文件配了连接池上限 ⇒ 145 条用例跑到 50% 时 PG 连接 105 > 100，后半段全挂；
* 有的手写 `CREATE TABLE` DDL 与模型不同步 ⇒ 报「字段不存在」。

## 2. 企业级方案比对

| 方案 | 代表实现 | 隔离度 | 单用例开销 | 能否回滚 `commit()` | 适配本项目 |
|---|---|---|---|---|---|
| A. 每用例新建数据库 | `CREATE DATABASE ... TEMPLATE` | 最高 | ~400ms | ✅ | ❌ 2796 × 400ms ≈ 19 分钟，光建库 |
| B. 每用例建 schema + 建表 | 本项目现状 | 高 | **7.5s** | ✅ | ❌ 这就是现在跑一下午的原因 |
| C. 每用例 `TRUNCATE` 全表 | 常见简化做法 | 高 | ~50ms | ✅ | ⚠️ 要维护表清单、序列/外键副作用多 |
| **D. 单 engine + 外层事务 + SAVEPOINT** | **pytest-pgsql 的 transacted 模式 / SQLA Wrapper `test_transaction()`** | **高** | **~1ms** | ✅（`join_transaction_mode="create_savepoint"`） | ✅ **采用** |
| E. SQLite 内存库 | — | 最高 | 0 | ✅ | ❌ 生产已放弃 SQLite，测一个不存在的方言 |

### 为什么 D 是业界共识

三份独立来源结论一致：

1. **pytest-pgsql 文档**：`transacted_postgresql_db` 比非事务版**快得多**，代价是
   整个用例必须在一个事务里；
2. **SQLA Wrapper**：`test_transaction()` 内部就是「外层 `begin()` → session 绑该连接 →
   `begin_nested()` savepoint → 结束 `rollback()`」；
3. **工程实践总结**：*"isolation is a transaction, not a cleanup"*；
   `join_transaction_mode="create_savepoint"` 让应用代码的 `commit()` 只
   `RELEASE SAVEPOINT`，**外层事务永不提交** ⇒ 夹具最后 `rollback()` 把一切丢掉。

### D 的唯一代价（必须知道）

**第二条连接看不见未提交数据。** 所以「后台 worker 线程写库 / 子进程 / 真并发」
这类用例不能用 `db`，要用 `db_committed`（真提交 + 结束清表）。
本项目这类用例是**少数**（同步 worker / 发布 worker / 会 ProactorEventLoop 的那几条）。

## 3. 重构后的结构

```
tests/backend/
  conftest_db.py      ← 唯一一份测试数据库基座（新）
  conftest.py         ← 其它公共夹具（api_client / 前端脚本 runner …）
  test_*.py           ← 业务测试；不再有任何建库代码
```

### 3.1 新增的三个夹具（`conftest_db.py`）

| 夹具 | 适用 | 机制 |
|---|---|---|
| **`db`** | **默认，95% 用例** | 外层事务 + savepoint，用例结束全回滚 |
| `db_committed` | 跨连接可见（worker 线程 / 子进程） | 真提交 + 结束 `TRUNCATE` |
| `pg_engine` | 会话唯一 engine | `pool_size=5, max_overflow=0` |

### 3.2 测试代码的写法（变得非常简单）

```python
def test_create_user(db, client):
    db.add(User(username="x", password_hash="y"))
    db.commit()                                  # 真实代码怎么调就怎么调
    assert client.get("/api/users").json()["total"] == 1
    # 函数结束 → 自动回滚，下一条用例天然干净
```

**测试里不再出现**：`make_engine` / `create_all` / `reset_test_data` /
`_SCHEMA_BY_ENGINE` / `drop_schema` / 任何清库代码。

### 3.3 自检（证明重构有效）

`tests/backend/test_db_rebase.py` 三条不变量：

1. 用例内 `commit()` 后**同用例可见**；
2. 上一条用例提交的数据，**下一条看不见**；
3. **跨用例重复插同一 username 不撞唯一约束**（`EMAIL_TAKEN` 的根治）。

实测：**3 条全绿**。

## 4. 迁移策略（分批，不一次性推翻）

| 阶段 | 动作 | 风险 |
|---|---|---|
| ① 已做 | 新基座 `conftest_db.py` + 自检 3 条 | 零（新文件） |
| ② 进行中 | 新功能 / 新用例**一律用 `db`**，禁止再写建库代码 | 零 |
| ③ 分批 | 存量 36 个自建库文件逐个改 `db`（按功能点合并测试时顺带改） | 中（每批要跑） |
| ④ 收口 | 删掉 `make_engine` / `reset_test_data` / 全局清数据钩子 | 低（无引用后） |

**不一次性全改的理由**：36 个文件里很多是「单跑绿、串行红」的既得状态，
一次性改必然一次性大面积红，无法区分「改坏了」与「本来就有问题」。

## 5. 配套的测试瘦身规则（同日立）

见 `10_测试脚本生命周期规则.md`：

* 每个功能点**只保留一个全链路测试脚本**（合并测试点，不是合并文件）；
* 所有**非功能点全链路**的测试 = **一次性脚本**，验证通过后彻底删除；
* 功能点改动时**同步**改对应测试，不留欠账。

本轮据此已删 **536 条**（`test_page_optimizations.py` 417 条全是源码字符串断言、
零业务调用，等）。用例 3334 → 2796。

### 样板迁移暴露的关键难点（必须写下来，否则下一个人会重踩）

存量测试的形态是：

```python
def _wire(tmp_path):
    SessionLocal = _make_db(tmp_path)          # 自己的 engine
    app.dependency_overrides[get_db] = ...     # 覆盖到自己的 engine
    client.post("/api/auth/register")          # 端点在**自己**的 engine 上跑
    db = SessionLocal()                        # 又开一个 Session
```

换成新基座后，`pg_engine` 是**会话级唯一 engine**，但测试仍自己
`sessionmaker(bind=pg_engine)` 开独立 Session ⇒ **绕过了外层事务** ⇒
用例之间的数据不再被回滚 ⇒ 整文件红。

**正确迁移不只是换 engine，是把形态换成：**

```python
def test_x(db, client):
    # db 与 client 的 get_db 覆盖**共用同一个 Session**
    client.post("/api/auth/register")   # 写在事务内，结束自动回滚
```

即 `api_client` 夹具必须接受并复用 `db` 这同一个 Session。**这一步没做，
迁移就无法完成** —— 这是下一步的具体工作，不是「再跑一遍」。

### 剩余工作（下一轮）

1. 在 `conftest_db.py` 加 `api_client` 夹具：`app.dependency_overrides[get_db]`
   指向 `db` 这同一个 Session；
2. 逐文件把 `_wire` 形态改成 `(db, client)` 形态（36 个文件，按功能点分批）；
3. 全绿后删除 `make_engine` / `reset_test_data` / 全局清数据钩子。

**问题从来不是「测试太多」，而是「测试基建有 36 份各自演进的实现」。**
